## 3.1 STL 容器是什么

STL 容器（Standard Template Library Container，标准模板库容器）是 C++ 标准库中提供的一类用来存储和管理数据集合的类模板。它们不仅能存放数据，还提供插入、删除、查找和遍历等接口；排序通常通过独立的标准算法（如 `std::sort`）或容器自身的成员函数完成，并非所有容器都支持排序。

### 3.1.1 顺序容器（Sequence Containers）

顺序容器中的元素按照线性顺序排列，元素的位置通常与插入顺序有关。

- **vector**：动态数组，支持快速随机访问，尾部插入和删除效率高。
- **deque**：双端队列，支持在头部和尾部快速插入、删除，也支持随机访问。
- **list**：双向链表，已定位到迭代器时插入和删除效率高，但不支持快速随机访问。
- **forward_list**：C++11 引入的单向链表，内存开销比 list 更小，只能向前遍历。
- **array**：C++11 引入的定长数组，封装了原生数组并提供 STL 接口。

### 3.1.2 关联容器（Associative Containers）

关联容器通常由平衡二叉搜索树实现，常见实现是红黑树。元素会按照 key 自动排序，查找、插入和删除的复杂度通常为 O(log n)。

- **set**：存储唯一的 key，不允许重复。
- **multiset**：存储 key，允许重复。
- **map**：存储 key-value 键值对，key 唯一。
- **multimap**：存储 key-value 键值对，key 可以重复。

### 3.1.3 无序关联容器（Unordered Containers，C++11 引入）

无序关联容器通常由哈希表实现，元素不按 key 排序。查找、插入和删除的平均复杂度为 O(1)，最坏情况下可能退化为 O(n)。

- **unordered_set**：无序且 key 唯一的集合。
- **unordered_multiset**：无序且允许重复 key 的集合。
- **unordered_map**：无序且 key 唯一的键值映射。
- **unordered_multimap**：无序且允许重复 key 的键值映射。

### 3.1.4 其他容器适配器（Container Adapters）

容器适配器不是独立的新容器，而是对已有容器进行封装，只暴露特定的访问方式。

- **stack**：栈，后进先出（LIFO）。
- **queue**：队列，先进先出（FIFO）。
- **priority_queue**：优先级队列，按比较器确定的优先级取出元素。

### 3.1.5 总结

|容器类别|容器名称|底层实现|主要特点|适用场景|
|---|---|---|---|---|
|序列式容器|vector|动态数组|随机访问快，尾部插入/删除快，中间插入/删除慢|动态数组替代，频繁随机访问|
|序列式容器|deque|双端队列（分段数组）|支持头尾快速插入/删除，随机访问也快|需要在两端频繁插入/删除|
|序列式容器|list|双向链表|已定位迭代器时插入/删除快，随机访问慢|插入/删除操作频繁，较少随机访问|
|序列式容器|forward_list (C++11)|单向链表|内存开销小，只能向前遍历，插入/删除快|轻量链表结构，单向遍历场景|
|序列式容器|array (C++11)|静态数组|定长，效率高，支持 STL 接口|固定大小的数据需求|
|关联式容器（有序）|set|平衡树（常见为红黑树）|自动排序，不允许重复，查找/插入 O(log n)|需要唯一有序集合|
|关联式容器（有序）|multiset|平衡树（常见为红黑树）|自动排序，允许重复|需要有序多重集合|
|关联式容器（有序）|map|平衡树（常见为红黑树）|键值对，key 唯一，按 key 排序|唯一键到值的映射|
|关联式容器（有序）|multimap|平衡树（常见为红黑树）|键值对，key 可重复|一键多值映射|
|无序关联容器（哈希表，C++11）|unordered_set|哈希表（实现定义）|无序存储，查找/插入平均 O(1)，key 唯一|快速查找集合|
|无序关联容器（哈希表，C++11）|unordered_multiset|哈希表（实现定义）|无序存储，允许重复|快速查找多重集合|
|无序关联容器（哈希表，C++11）|unordered_map|哈希表（实现定义）|key-value 键值对，无序，key 唯一|快速键值映射|
|无序关联容器（哈希表，C++11）|unordered_multimap|哈希表（实现定义）|key-value 键值对，无序，key 可重复|快速多值映射|

## 3.2 序列容器

序列容器（Sequence Containers）是 STL 中的一类容器，特点是元素按照严格的线性顺序存储，支持顺序访问和插入删除操作。主要包括：vector、deque、list、forward_list、array。

### 3.2.1 vector

vector 是动态数组，元素在内存中连续存储。它支持 O(1) 的随机访问，尾部插入和删除的均摊复杂度为 O(1)，但在头部或中间插入、删除时，后续元素需要移动，复杂度通常为 O(n)。

vector 的优点是连续内存有利于缓存，能够使用下标快速访问；缺点是扩容时需要重新分配内存并移动元素，扩容后原有迭代器、指针和引用可能失效。

### 3.2.2 deque

deque 是双端队列，通常由分段数组和中控器实现。它支持头部和尾部的快速插入、删除，也支持 O(1) 的随机访问，但元素不保证连续存储。

### 3.2.3 list

list 是双向链表。元素不连续存储，节点中除了数据还要保存前后指针。只要已经定位到对应迭代器，在任意位置插入和删除都可以做到 O(1)，但不支持下标随机访问。

### 3.2.4 forward_list

forward_list 是单向链表，只保存后继节点指针，内存开销比 list 更小，但只能向前遍历，插入和删除需要使用前一个位置的迭代器。

### 3.2.5 array

array 是对定长数组的 STL 封装，大小在编译期确定，元素连续存储，支持下标访问和迭代器，但不能动态扩容。

### 3.2.6 序列容器对比

|容器|底层实现|是否支持随机访问|插入/删除效率|适用场景|特点|
|---|---|---|---|---|---|
|vector|动态数组|支持（O(1)）|末尾 O(1)，中间 O(n)|需要频繁随机访问|内存连续，扩容时重新分配|
|deque|分段数组 + 中控器|支持（O(1)）|头尾 O(1)，中间 O(n)|需要两端快速插入/删除|内存不连续，但随机访问效率仍高|
|list|双向链表|不支持|任意位置 O(1)（需先找到迭代器）|需要频繁插入/删除|元素不连续，空间开销较大|
|forward_list|单向链表|不支持|插入/删除 O(1)（需定位到迭代位置）|内存占用敏感，简单链表结构|比 list 更轻量，但只能单向遍历|
|array|静态数组（封装）|支持（O(1)）|固定大小，不支持扩容|数组替代品，性能要求高|大小在编译期固定，不能动态扩展|

## 3.3 关联式容器

关联式容器（Associative Containers）通常使用红黑树实现。元素会按照 key 自动排序，查找、插入和删除的复杂度通常为 O(log n)。

### 3.3.1 关联式容器（Associative Containers）

主要特点：

- 元素可以是单独的 key，也可以是 key-value 键值对。
- 元素按比较器给出的严格弱序排列；默认使用 `std::less`，表现为升序。
- 适合高效查找和范围查询。
- 插入和删除不会使其他元素的迭代器失效，被删除元素对应的迭代器除外。

### 3.3.2 关联式容器分类

|容器|结构|是否允许重复键|是否可以改键|有序性|底层实现|适用场景|
|---|---|---|---|---|---|---|
|set|集合|否|否|自动排序（升序默认）|平衡树（常见为红黑树）|存储不重复元素，查找效率高|
|multiset|集合|是|否|自动排序|平衡树（常见为红黑树）|允许存储重复元素|
|map|键值对（key-value）|否|否（key 不可改）|自动排序|平衡树（常见为红黑树）|键唯一，适合字典、配置表|
|multimap|键值对（key-value）|是|否（key 不可改）|自动排序|平衡树（常见为红黑树）|允许重复键，适合一对多映射|

## 3.4 无序关联式容器

### 3.4.1 无序关联式容器（Unordered Associative Containers）

无序关联式容器由 C++11 引入，通常使用哈希表实现。它不保证元素的顺序，查找、插入和删除的平均复杂度为 O(1)。

主要特点：

- 元素按照哈希值分布，不按 key 大小排序。
- unique 类型不允许重复元素，multi 类型允许重复元素。
- 平均情况下查找、插入和删除为 O(1)，最坏情况可能为 O(n)。
- 容器需要哈希函数将 key 映射到桶。

### 3.4.2 无序关联式容器分类

|容器|结构|是否允许重复键|是否有序|底层实现|适用场景|
|---|---|---|---|---|---|
|unordered_set|集合|否|否|哈希表|高速唯一元素查找|
|unordered_multiset|集合|是|否|哈希表|高速重复元素查找|
|unordered_map|键值对（key-value）|否|否|哈希表|高速唯一键值映射|
|unordered_multimap|键值对（key-value）|是|否|哈希表|高速多值映射|

## 3.5 适配器容器

### 3.5.1 容器适配器（Container Adapters）

容器适配器不是新的底层容器，而是在已有容器的基础上封装出特定的数据访问接口。它隐藏了底层容器的其他操作，使使用方式更符合栈、队列等抽象数据结构。

### 3.5.2 容器适配器分类

|容器适配器|底层容器|数据访问方式|主要特点|适用场景|
|---|---|---|---|---|
|stack|deque（默认，也可用 vector 或 list）|后进先出（LIFO）|只允许访问栈顶元素，push/pop/top|函数调用栈、撤销操作、深度优先搜索|
|queue|deque（默认，也可用 list）|先进先出（FIFO）|只允许访问队头和队尾元素|广度优先搜索、任务调度、消息缓冲|
|priority_queue|vector + 堆|优先级顺序访问|元素按比较器确定的优先级取出（最大堆默认）|优先任务调度、事件处理、堆排序|

### 3.5.3 关键点总结

- stack 默认使用 deque，也可以显式指定 vector 或 list。
- queue 默认使用 deque，也可以使用 list。
- priority_queue 默认是最大堆，队首总是优先级最高的元素。
- priority_queue 默认使用 vector，也可以使用满足随机访问迭代器等要求的容器（如 deque）。
- 适配器只提供与自身抽象对应的接口，不提供底层容器的全部接口。

## 3.6 优先级队列

### 3.6.1 定义

C++ 标准库（STL）里的 `priority_queue` 本质上是一个堆（heap）容器适配器。默认情况下，按 `std::less` 比较时最大的元素位于 `top()`；通过比较器也可以让最小元素或其他自定义优先级的元素位于队首。

### 3.6.2 底层数据结构

priority_queue 默认以 vector 作为底层容器，并使用堆算法维护元素顺序。默认是最大堆，也可以通过比较器实现最小堆或自定义优先级。

### 3.6.3 定义方式

```cpp
#include <queue>
#include <vector>
#include <functional>
using namespace std;

// 最大堆（默认）
priority_queue<int> maxHeap;

// 最小堆
priority_queue<int, vector<int>, greater<int>> minHeap;

// 自定义比较器
struct cmp {
    bool operator()(int a, int b) const {
        return a > b; // 小顶堆
    }
};
priority_queue<int, vector<int>, cmp> customHeap;
```

### 3.6.4 常用操作及复杂度

|操作|函数|复杂度|
|---|---|---|
|插入元素|push(x)|O(log n)|
|删除队首|pop()|O(log n)|
|访问队首|top()|O(1)|
|判断是否为空|empty()|O(1)|
|获取大小|size()|O(1)|

### 3.6.5 使用场景

- 调度系统：优先处理优先级高的任务。
- Dijkstra 最短路径算法：每次取出当前距离最小的节点。
- 霍夫曼编码：反复取出权重最小的两个节点。
- 实时数据流中位数：配合两个堆维护数据流的中间值。

### 3.6.6 总结

priority_queue 是“只能访问最高优先级元素”的容器适配器。默认是最大堆；如果要实现最小堆，可以使用 greater 或自定义比较器。

## 3.7 vector、list、deque 的区别与使用场景

### 3.7.1 vector

- 底层是动态数组，元素连续存储。
- 支持 O(1) 随机访问。
- 尾部插入和删除的均摊复杂度为 O(1)。
- 头部或中间插入、删除通常为 O(n)。
- 连续内存有利于缓存命中和遍历性能。
- 扩容时会重新分配内存并移动元素。

适用场景：需要频繁随机访问、主要在尾部操作、元素数量相对稳定的场景。

### 3.7.2 list

- 底层是双向链表。
- 不支持随机访问，需要从头或尾逐步遍历。
- 已知迭代器位置时，插入和删除为 O(1)。
- 元素不连续，节点有额外指针开销。

适用场景：需要频繁在中间插入和删除，且不依赖随机访问的场景。

### 3.7.3 deque（双端队列）

- 底层通常是分段数组。
- 支持 O(1) 随机访问。
- 头部和尾部插入、删除都很快。
- 内存不保证连续。

适用场景：既需要两端快速操作，又需要随机访问的场景。

### 3.7.4 主要区别总结

- vector：随机访问快、尾部操作快、内存连续。
- list：中间插入和删除快，但随机访问慢、空间开销大。
- deque：两端操作快并且支持随机访问，但内存不连续。

### 3.7.5 使用场景总结

优先选择 vector 作为一般动态数组；需要频繁在两端操作时选择 deque；只有在确实需要大量已定位节点的中间插入、删除时再考虑 list。

## 3.8 map 和 unordered_map 的区别与原理

### 3.8.1 基本概述

map 和 unordered_map 都用于保存 key-value 键值对，但实现方式不同：

- map 通常由红黑树实现，key 按比较器排序（默认使用 `std::less`）。
- unordered_map 通常由哈希表实现，不保证元素顺序。

### 3.8.2 底层实现

map 的节点存储在红黑树中，树高保持平衡，因此查找、插入和删除的复杂度稳定在 O(log N)。

unordered_map 先通过哈希函数计算 key 的哈希值，再将元素放入对应桶中。平均情况下查找、插入和删除为 O(1)，哈希冲突严重时可能退化为 O(N)。

### 3.8.3 时间复杂度对比

|操作|map（红黑树）|unordered_map（哈希表）|
|---|---|---|
|查找|O(log N)|O(1)（平均情况）|
|插入|O(log N)|O(1)（平均情况）|
|删除|O(log N)|O(1)（平均情况）|
|遍历|O(N)|O(N)|

### 3.8.4 元素顺序

map 按 key 自动排序，遍历结果具有确定的顺序；unordered_map 不保证遍历顺序，顺序可能受哈希函数、桶数量和 rehash 影响。

### 3.8.5 哈希函数与键的比较

map 需要 key 支持比较操作，默认使用 less；unordered_map 需要 key 支持哈希函数和相等比较，默认使用 hash 和 equal_to。

```cpp
map<int, string> ordered;
ordered[2] = "two";
ordered[1] = "one";
// 遍历顺序为 1、2

unordered_map<int, string> unordered;
unordered[2] = "two";
unordered[1] = "one";
// 遍历顺序不保证
```

### 3.8.6 内存开销

map 的每个节点通常包含左右子节点指针、父节点指针和颜色等额外信息；unordered_map 需要桶数组以及处理冲突的节点，因此实际内存开销也可能较大。

### 3.8.7 使用场景总结

- 需要按 key 排序、范围查询或稳定遍历顺序时使用 map。
- 只关心快速查找，不要求顺序时使用 unordered_map。
- 对最坏情况复杂度敏感时，map 的复杂度更稳定。

### 3.8.8 总结

map 是有序映射，底层通常是红黑树，操作复杂度为 O(log N)；unordered_map 是无序映射，底层通常是哈希表，平均操作复杂度为 O(1)。

## 3.9 stack、queue、priority_queue 的底层实现

### 3.9.1 stack

stack 是后进先出（LIFO）的容器适配器，只能访问栈顶元素。默认底层容器是 deque，也可以使用 vector 或 list。

常用操作包括 push、pop、top、empty 和 size。stack 适合函数调用栈、撤销操作、括号匹配和深度优先搜索等场景。

### 3.9.2 queue

queue 是先进先出（FIFO）的容器适配器。默认底层容器是 deque，也可以使用 list。它只允许访问队头和队尾，常用操作包括 push、pop、front、back、empty 和 size。

queue 适合任务调度、消息队列、缓冲区和广度优先搜索等场景。

### 3.9.3 priority_queue

priority_queue 底层通常是 vector 加堆算法。默认是最大堆，top 返回优先级最高的元素；通过自定义比较器可以实现最小堆。

### 3.9.4 总结表格

|容器|底层实现|操作类型|适用场景|
|---|---|---|---|
|stack|deque 或 vector|后进先出（LIFO）|表达式求值、回退操作等|
|queue|deque 或 list|先进先出（FIFO）|任务调度、消息队列、BFS|
|priority_queue|vector（默认）或 deque + 堆算法|按优先级访问|任务调度、Dijkstra 算法、Huffman 编码等|

## 3.10 set 和 unordered_set 的区别

### 3.10.1 底层实现

set 通常由平衡二叉搜索树实现，常见实现为红黑树，元素会自动按升序排列；unordered_set 通常由哈希表实现，元素无序存储。

### 3.10.2 时间复杂度

|操作|set（红黑树）|unordered_set（哈希表）|
|---|---|---|
|查找/插入/删除|O(log N)|O(1)（平均情况下）|
|遍历|O(N)|O(N)|

### 3.10.3 元素顺序

set 遍历时按 key 的排序顺序输出；unordered_set 不保证元素顺序，具体遍历顺序由哈希函数和桶布局决定。

### 3.10.4 哈希函数与键的比较

set 需要 key 支持比较操作；unordered_set 需要 key 支持哈希函数和相等比较。使用自定义类型时，要分别提供比较器，或提供哈希函数与 operator==。

```cpp
set<int> orderedSet = {3, 1, 2};
// 遍历结果为 1、2、3

unordered_set<int> hashSet = {3, 1, 2};
// 遍历顺序不保证
```

### 3.10.5 内存开销

set 的每个树节点包含树结构维护所需的指针和颜色信息；unordered_set 需要桶数组和处理冲突的节点。两者都存在额外空间开销，不能只根据平均时间复杂度选择。

### 3.10.6 总结

需要有序、范围查询或稳定的最坏情况复杂度时选择 set；只需要快速判断元素是否存在且不关心顺序时选择 unordered_set。

## 3.11 iterator、const_iterator 与指针的区别

### 3.11.1 指针与迭代器的基本区别

指针通常直接保存对象地址，可以通过解引用访问对象；迭代器是标准库采用的一套抽象访问接口，用于统一遍历不同的数据结构。指针本身也满足连续迭代器（C++20）/随机访问迭代器的操作要求，可以看作一种特殊的迭代器。

指针适合数组和连续内存；容器迭代器则可以适配 vector、list、map 等不同结构，并由对应容器规定可用操作和失效规则。

### 3.11.2 iterator 和 const_iterator 的区别

- iterator 通常可以修改它所指向的元素，但关联容器的 key 是例外：set/multiset 的元素不可通过迭代器修改，map/multimap 只能修改 `second`，不能修改 `first`。
- const_iterator 只能读取元素，不能通过它修改元素。

```cpp
vector<int> values = {1, 2, 3};

vector<int>::iterator it = values.begin();
*it = 5; // 可以修改

vector<int>::const_iterator cit = values.cbegin();
int x = *cit; // 可以读取
// *cit = 6;  // 错误，不能修改
```

### 3.11.3 指针与迭代器的比较

- 指针可以直接进行地址运算，迭代器是否支持随机跳转取决于迭代器类别。
- 指针主要处理连续内存或对象地址，容器迭代器遵循对应容器的访问和失效规则。
- 迭代器更通用，但并不自动提供越界检查；标准库的迭代器抽象通常不会带来额外运行时开销，调试迭代器除外。

### 3.11.4 iterator 和 const_iterator 的功能对比

|特性|iterator|const_iterator|
|---|---|---|
|可修改元素|通常可以；set 元素和关联容器的 key 除外|不可通过该迭代器修改元素，只能读取|
|典型解引用结果|`T&`|`const T&`|
|用途|遍历并可能修改容器元素|遍历容器但保证元素不被修改|
|容器兼容性|适用于可写访问的容器|可用于只读访问的容器或需要保护元素不被修改的场景|
|示例|vector<int>::iterator it; *it = 5|vector<int>::const_iterator it; int x = *it|

### 3.11.5 总结

当需要修改容器元素时使用 iterator；只读遍历或函数参数不应修改元素时使用 const_iterator。对于原生数组可以直接使用指针，但对于 STL 容器应优先使用容器提供的迭代器。

## 3.12 vector 的扩容机制

### 3.12.1 扩容流程

vector 是动态数组，内部维护 size、capacity 和元素存储区。插入前若现有容量不足以容纳新元素（例如 `size() == capacity()` 时执行 `push_back`），就会在插入过程中触发扩容；任何时刻都满足 `size() <= capacity()`。

典型扩容流程如下：

1. 检查当前 capacity 是否足够。
2. 分配一块更大的新内存，容量按实现定义的增长策略增加（有的实现接近旧容量的 2 倍，有的约为 1.5 倍）；标准不强制具体倍数。
3. 将旧内存中的元素移动或复制到新内存。
4. 销毁旧内存中的元素并释放旧存储区。
5. 更新内部指针和 capacity。

### 3.12.2 注意事项

- 单次扩容需要移动或复制全部元素，复杂度为 O(n)。
- 多次尾部插入的均摊复杂度仍然可以达到 O(1)。
- 扩容会使原有迭代器、指针和引用失效。
- 可以使用 reserve 预留容量，减少扩容次数。

```cpp
vector<int> values;
values.reserve(100); // 提前预留容量
for (int i = 0; i < 100; ++i) {
    values.push_back(i);
}
```

### 3.12.3 总结

vector 扩容的核心是重新申请更大的连续内存并迁移元素。它牺牲了偶发的 O(n) 扩容成本，换取了尾部插入的均摊 O(1) 性能。

---

## 3.13 vector 为什么采用成比例扩容

### 3.13.1 原因分析

vector 通常采用指数式增长。不同标准库的策略不同，例如一些实现接近 2 倍，另一些实现接近 1.5 倍；选择固定增长比例主要有以下原因：

- 如果每次只增加一个元素，频繁分配和复制会使连续插入退化为 O(n²)。
- 按比例扩容可以使连续多次插入的总迁移次数受控，从而获得均摊 O(1) 的尾部插入复杂度。
- 增长比例太小会导致扩容频繁，增长比例太大又会造成更多空间浪费，固定比例是在时间和空间之间的折中。
- C++ 标准并没有规定 vector 必须按照 2 倍扩容，具体策略由标准库实现决定。

### 3.13.2 总结

“2 倍扩容”只是部分实现采用的策略，不是 C++ 标准要求。实际编程中如果能够预估元素数量，应优先使用 reserve 减少重新分配。

## 3.14 使用迭代器删除元素的注意事项

删除元素后，哪些迭代器失效取决于容器的底层结构。最安全的做法是使用 erase 的返回值接收下一个有效迭代器。

### 3.14.1 vector / deque

vector 的 `erase` 会使被删除位置及其之后的迭代器、指针和引用失效。deque 的规则更严格：删除中间元素时，所有迭代器和引用都会失效；删除首元素（但未删到尾部）时，仅指向被删除元素的迭代器和引用失效；删除尾元素时，还会使原先的尾后迭代器失效。`erase` 会返回指向下一个元素的迭代器。

```cpp
for (auto it = values.begin(); it != values.end();) {
    if (*it % 2 == 0) {
        it = values.erase(it);
    } else {
        ++it;
    }
}
```

### 3.14.2 list / forward_list

list 删除一个节点时，只有被删除节点对应的迭代器、指针和引用失效；`forward_list` 没有 `erase`，必须使用 `erase_after` 删除指定位置之后的节点。

`list` 示例：

```cpp
for (auto it = values.begin(); it != values.end();) {
    if (*it % 2 == 0) {
        it = values.erase(it);
    } else {
        ++it;
    }
}
```

`forward_list` 示例（`prev` 指向待删除节点的前一节点）：

```cpp
for (auto prev = values.before_begin(), it = values.begin();
     it != values.end();) {
    if (*it % 2 == 0) {
        it = values.erase_after(prev);
    } else {
        prev = it;
        ++it;
    }
}
```

### 3.14.3 map / multimap 与 set / multiset

关联容器删除一个元素时，只有被删除元素对应的迭代器失效，其他迭代器仍然有效。

对 `map`/`multimap`，可以按 key 判断：

```cpp
for (auto it = data.begin(); it != data.end();) {
    if (it->first < 0) {
        it = data.erase(it);
    } else {
        ++it;
    }
}
```

对 `set`/`multiset`，迭代器直接指向 key：

```cpp
for (auto it = values.begin(); it != values.end();) {
    if (*it < 0) {
        it = values.erase(it);
    } else {
        ++it;
    }
}
```

### 3.14.4 无序关联容器

unordered_set、unordered_map 等无序关联容器执行 `erase` 时，只会使被删除元素的迭代器和引用失效。不过插入操作如果触发 `rehash`，会使所有迭代器失效（元素的指针和引用仍保持有效）。

### 3.14.5 总结

- 优先使用 erase 的返回值更新迭代器。
- vector 删除元素会使该位置及之后的迭代器失效；deque 删除中间元素会使所有迭代器和引用失效。
- list 和关联容器通常只使被删除元素的迭代器失效。
- 不要在范围 for 循环中直接删除当前元素，除非明确处理迭代器失效问题。

## 3.15 auto、decltype 与 decltype(auto) 的区别

### 3.15.1 auto

auto 用于让编译器根据初始化表达式推导变量类型。单独使用 auto 时不会保留顶层 const 和引用，需要用 auto& 或 auto&& 明确保留引用语义。

```cpp
int value = 10;
const int constValue = 20;

auto a = value;          // int
auto b = constValue;     // int，顶层 const 被丢弃
auto& c = value;         // int&
const auto& d = value;   // const int&
```

### 3.15.2 decltype

decltype 用于获取表达式的类型，并保留表达式的引用和 const 属性。对于未加括号的变量名，decltype 得到变量声明类型；对于一般表达式，decltype 根据表达式的左值、将亡值或右值属性推导。

```cpp
int value = 10;
decltype(value) a = 1;       // int
decltype((value)) b = value; // int&
```

### 3.15.3 decltype(auto)

decltype(auto) 使用 decltype 的规则进行自动推导，能够保留返回表达式的引用和 const 属性，常用于包装函数和转发函数的返回值。

```cpp
int value = 10;

decltype(auto) getValue() {
    return (value); // 返回 int&
}
```

### 3.15.4 使用场景举例

- auto：普通变量类型推导，减少冗长类型书写。
- decltype：需要获取表达式准确类型，或声明与已有表达式相同类型的变量。
- decltype(auto)：函数返回值需要完整保留表达式类型时使用。

### 3.15.5 总结

auto 更关注“根据初始化值推导一个变量类型”；decltype 更关注“表达式本身的精确类型”；decltype(auto) 则把 decltype 的精确规则与 auto 的自动推导结合起来。

## 3.16 哈希碰撞与桶冲突

### 3.16.1 哈希碰撞（Hash Collision）

哈希碰撞是指不同的输入经过哈希函数后得到相同的哈希值。例如：

- key1 = abc，hash(key1) = 5
- key2 = xyz，hash(key2) = 5

虽然两个 key 不同，但哈希值相同，这就是哈希碰撞。

### 3.16.2 桶冲突（Bucket Collision）

实际资料常把“哈希碰撞”和“哈希冲突”当作同义词。若要进一步区分，可以把不同 key 最终映射到同一个桶称为“桶冲突”。例如哈希表大小为 10：

- hash(key1) % 10 = 2
- hash(key2) % 10 = 2

两个 key 最终落到同一个桶，需要通过拉链法或开放寻址法继续处理。严格来说，相同哈希值一定会导致同桶，但不同哈希值也可能因为取模后的桶索引相同而发生同桶冲突。

### 3.16.3 解决桶冲突的常用方法

- **拉链法（Separate Chaining）**：每个桶保存一个链表或其他节点集合，冲突元素挂在同一个桶中。
- **开放寻址法（Open Addressing）**：发生冲突时按照线性探测、二次探测等规则寻找其他空桶。
- **rehash**：扩大桶数量并重新计算元素位置，降低装载因子。
- **调整负载因子**：控制元素数量与桶数量的比例，减少冲突概率。

### 3.16.4 总结

“碰撞”和“冲突”通常没有统一的术语边界。若按本节的细分，原始哈希值相同属于哈希碰撞，而不同 key 落入同一桶属于桶冲突；相同哈希值必然导致桶冲突，不同哈希值也可能经桶映射后落入同一桶。工程上可通过合理的哈希函数、负载因子和冲突解决策略维持哈希表性能。

## 3.17 range-based for 循环原理

### 3.17.1 语法

range-based for 循环由 C++11 引入，可遍历原生数组、容器，以及能通过成员函数或 ADL 找到 `begin`/`end` 的自定义类型。

```cpp
for (auto value : container) {
    // 使用 value
}

for (auto& value : container) {
    // 可以修改容器元素
}

for (const auto& value : container) {
    // 只读访问，避免复制
}
```

### 3.17.2 原理

编译器会把范围 for 循环转换为基于 `begin`、`end` 和迭代器的循环。以 `for (auto& value : container)` 为例，逻辑上近似如下（实际规则还会处理原生数组、ADL `begin/end`，并从 C++17 起允许起止迭代器类型不同）：

```cpp
auto&& range = container;
auto begin = range.begin();
auto end = range.end();
for (; begin != end; ++begin) {
    auto& value = *begin;
}
```

其中，`auto&& range` 用于绑定待遍历对象，`begin` 和 `end` 分别表示起始和结束位置，循环变量由 `*begin` 初始化。若原循环声明为 `auto value` 或 `const auto& value`，展开时也应使用相同的循环变量声明，而不是固定使用 `auto&`。

### 3.17.3 详细示例

```cpp
vector<int> values = {1, 2, 3};

for (const auto& value : values) {
    cout << value << endl;
}
```

使用 const auto& 可以避免复制元素，同时保证循环体不会修改容器中的元素。

### 3.17.4 背后实现与编译器的优化

范围 for 的本质仍是迭代器遍历。编译器通常会对简单循环进行优化，减少不必要的临时对象和复制。对于大型对象，使用 const auto& 往往比按值遍历更合适。

### 3.17.5 使用场景

- 遍历 vector、list、map、set 等 STL 容器。
- 遍历原生数组和提供 begin/end 接口的自定义类型。
- 只读遍历时使用 const auto&。
- 需要修改元素时使用 auto&。

### 3.17.6 总结

range-based for 只是迭代器循环的语法糖。它依赖 begin、end 和迭代器操作；按值遍历会复制元素，按引用遍历可以修改元素，按 const 引用遍历则能避免复制并保证只读。
