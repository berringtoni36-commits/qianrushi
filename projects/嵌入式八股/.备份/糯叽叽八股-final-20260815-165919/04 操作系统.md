## 4.1 用户态与内核态、两者的切换方式

在操作系统中，**用户态**和**内核态**是两种不同的执行模式，它们有不同的权限和功能。用户态（user mode）是程序运行时的普通模式，而内核态（kernel mode）则是操作系统核心代码的执行模式。两者之间的切换是由操作系统通过上下文切换机制来实现的。

### 4.1.1 用户态与内核态的定义

- **用户态（User Mode）**：程序在执行普通任务时，运行在用户态中，具有有限的权限。用户态的程序不能直接访问硬件资源或执行敏感的操作（如修改系统内存、管理进程等）。如果用户态程序需要这些操作，它必须通过系统调用（syscall）请求内核的帮助。
- **内核态（Kernel Mode）**：操作系统的核心部分（内核）运行在内核态，具有完全的硬件访问权限和执行任何操作的能力。内核态允许程序访问所有硬件资源、控制进程调度、管理内存、执行系统调用等。内核态代码可以直接与硬件交互。

用户态与内核态的切换通常发生在**系统调用**、**中断**、**异常**等事件发生时。以下是这几种常见切换的详细描述：

**系统调用引发的用户态到内核态切换**

系统调用是用户程序请求内核执行特权操作的方式。例如，文件读写、进程管理、内存分配等操作都需要通过系统调用进行。用户态进入内核态的入口由架构、内核和 ABI 决定：旧 x86 Linux 曾使用 `int 0x80`，现代 x86-64 通常使用 `syscall`，ARM 则使用相应的 SVC/系统调用入口，不能一概称为“软中断”。

**过程：**

1. **用户程序发起系统调用**：用户程序通过标准库（如C语言的printf()、open()等）或直接发起系统调用，进入用户态与内核态切换的准备阶段。
2. **系统调用入口**：程序通过 ABI 规定的系统调用指令或陷入入口（如 `syscall`、`int 0x80` 或 ARM 的 SVC）向内核发出请求。
3. **保存入口现场**：处理器和内核保存必要的寄存器/返回信息并切换到内核态；这不是一次普通线程调度，是否发生进程切换要看系统调用是否阻塞及调度器决定。
4. **执行内核代码**：操作系统的内核代码接管控制，完成系统调用请求。此时，程序在内核态执行操作，如内存管理、文件系统操作等。
5. **返回用户态**：系统调用完成后，内核将控制权返回给用户程序，恢复上下文，继续执行用户程序。

**中断引发的内核态到用户态切换**

硬件中断或外部设备请求会导致中断服务程序（ISR）被触发，从而导致内核态执行。中断服务程序可以在执行完后，通过调度程序将执行权交还给用户程序。

**过程：**

1. **中断触发**：硬件（如定时器中断、I/O设备中断）向CPU发出中断请求，导致CPU进入内核态。
2. **中断服务程序（ISR）执行**：中断请求被操作系统接收后，进入内核态执行相应的中断处理程序（ISR）。
3. **恢复到用户态**：ISR执行完毕后，操作系统调度器检查是否需要将控制权返回给用户程序，恢复到用户态。

**异常引发的用户态到内核态切换**

当程序运行时发生异常（如除零、非法内存访问等），操作系统会通过异常处理机制进行中断处理，导致从用户态切换到内核态。

**过程：**

1. **异常触发**：程序发生异常（如除零错误、无效内存访问等），CPU检测到异常并将控制权交给操作系统。
2. **内核态处理异常**：操作系统的内核态代码会捕获异常，执行适当的异常处理程序（如错误日志、终止程序等）。
3. **恢复用户态**：在处理完异常后，操作系统决定是否恢复到用户态，继续执行原程序或终止程序。

### 4.1.2 用户态与内核态的切换过程

用户态与内核态的切换通常发生在系统调用、中断、异常等事件发生时。以下是这几种常见切换的详细描述：

**系统调用引发的用户态到内核态切换**

系统调用是用户程序请求内核执行特权操作的方式。用户态进入内核态的具体入口由架构、内核和 ABI 决定：例如旧 x86 Linux 的 `int 0x80`、现代 x86-64 的 `syscall`，以及 ARM 的 SVC 入口；`syscall` 并不是 Linux `softirq` 机制的同义词。

**过程：**

1. 用户程序发起系统调用：用户程序通过标准库（如C语言的printf()、open()等）或直接发起系统调用，进入用户态与内核态切换的准备阶段。
2. 系统调用入口：程序通过 ABI 规定的陷入指令向内核发出请求。
3. 保存入口现场：处理器和内核保存必要的寄存器/返回信息并进入内核态；是否进一步切换到其他任务取决于阻塞和调度。
4. 执行内核代码：操作系统的内核代码接管控制，完成系统调用请求。此时，程序在内核态执行操作，如内存管理、文件系统操作等。
5. 返回用户态：系统调用完成后，内核将控制权返回给用户程序，恢复上下文，继续执行用户程序。

**中断引发的内核态到用户态切换**

硬件中断或外部设备请求会导致中断服务程序（ISR）被触发，从而导致内核态执行。中断服务程序可以在执行完后，通过调度程序将执行权交还给用户程序。

**过程：**

1. 中断触发：硬件（如定时器中断、I/O设备中断）向CPU发出中断请求，导致CPU进入内核态。
2. 中断服务程序（ISR）执行：中断请求被操作系统接收后，进入内核态执行相应的中断处理程序（ISR）。
3. 恢复到用户态：ISR执行完毕后，操作系统调度器检查是否需要将控制权返回给用户程序，恢复到用户态。

**异常引发的用户态到内核态切换**

当程序运行时发生异常（如除零、非法内存访问等），操作系统会通过异常处理机制进行中断处理，导致从用户态切换到内核态。

**过程：**

1. 异常触发：程序发生异常（如除零错误、无效内存访问等），CPU检测到异常并将控制权交给操作系统。
2. 内核态处理异常：操作系统的内核态代码会捕获异常，执行适当的异常处理程序（如错误日志、终止程序等）。
3. 恢复用户态：在处理完异常后，操作系统决定是否恢复到用户态，继续执行原程序或终止程序。

### 4.1.3 用户态与内核态切换的开销

切换到内核态会涉及到上下文切换，它通常比在用户态中执行代码要慢。以下是导致切换开销的主要因素：

- **上下文切换**：切换到内核态时，操作系统需要保存当前程序的上下文（包括CPU寄存器、堆栈等），然后加载内核态相关的上下文。这个过程需要时间并会增加系统开销。
- **缓存失效**：当执行系统调用时，CPU的缓存可能会失效，导致系统访问内存的速度降低。
- **模式切换开销**：从用户态切换到内核态和从内核态切换回用户态时，CPU需要改变运行模式，这会产生额外的时间开销。

操作系统设计中尽量减少用户态与内核态的切换次数，以提高系统效率。

### 4.1.4 为什么需要用户态与内核态分离？

- **资源管理**：操作系统内核负责资源的管理，如内存、进程调度、设备管理等。用户态程序不能直接管理这些资源，必须通过系统调用向内核请求，确保资源的合理分配和使用。

### 4.2.1 背景概念

在现代操作系统中（如 Linux）：

- **用户空间（User Space）**：普通应用程序运行的空间
- **内核空间（Kernel Space）**：操作系统内核运行的空间

二者隔离是为了**安全性和稳定性**，因此需要**受控的通信机制**。

### 4.2.2 主要通信方式

**（1）系统调用（System Call）**

- **最常见、最标准方式**
- 用户态通过系统调用陷入内核态执行

典型接口：

```c
open / read / write / ioctl / mmap
```

特点：

- 安全、受控
- 有上下文切换开销

**（2）字符设备（Char Device）**

- 通过 /dev/xxx 与内核驱动通信
- 基于文件操作接口

```c
open("/dev/mydev", O_RDWR);
read();
write();
ioctl();
```

特点：

- 驱动开发常用
- 接口统一、易扩展

**（3）proc 文件系统（/proc）**

- 内核向用户空间暴露运行信息
- 主要用于**状态查询、参数配置**

```bash
cat /proc/cpuinfo
```

特点：

- 不适合高频读写
- 以文本为主

**（4）sysfs 文件系统（/sys）**

- 面向**设备模型**
- 用于设备、驱动参数配置

```bash
echo 1 > /sys/class/xxx/enable
```

特点：

- 结构清晰
- 一般一文件一属性

**（5）Netlink Socket**

- 用户态 ↔ 内核态 **双向通信**
- 网络子系统、udev 常用

特点：

- 异步通信
- 支持多播

**（6）共享内存（mmap）**

- 将文件、设备或驱动缓冲区按映射规则暴露到用户空间
- 在生产者和消费者直接共享同一缓冲区、且驱动/设备支持时可以减少一次复制；`mmap()` 本身不自动保证“零拷贝”或缓存一致性

```c
mmap(NULL, size, PROT_READ, MAP_SHARED, fd, 0);
```

特点：

- 高性能
- 需要同步机制

**（7）信号（Signal）**

- 内核向用户进程发送事件通知

```c
kill(pid, SIGIO);
```

特点：

- 轻量
- 只能传递简单信息

## 4.3 原码、反码、补码的定义

### 4.3.1 原码（Sign-Magnitude）

1. **定义**
    - 最高位为**符号位**
        - 0 表示正数
        - 1 表示负数
    - 其余位表示**数值的绝对值**
2. **表示规则（以 8 位为例）**
3. **特点**
    - 表示直观，容易理解
    - **存在 +0 和 −0**
    - 不利于运算，硬件实现复杂

### 4.3.2 反码（One’s Complement）

1. **定义**
    - 正数的反码：**与原码相同**
    - 负数的反码：**符号位不变，其余位取反**
2. **表示规则（8 位）**
3. **特点**
    - 加减运算比原码简单
    - **仍然存在 +0 和 −0**
    - 需要“循环进位”，实现仍较复杂

### 4.3.3 补码（Two’s Complement）

1. **定义**
    - 正数的补码：**与原码相同**
    - 负数的补码：**反码 + 1**
2. **表示规则（8 位）**
3. **特点**
    - **只有一个 0**
    - 加减法可以统一用加法实现
    - 硬件电路最简单
    - **现代计算机统一使用补码**

### 4.3.4 三者对比总结

| 表示法 | 正数 | 负数 | 0 的个数 | 运算特点 |
|---|---|---|---|---|
| 原码 | 符号位为 0，其余位表示绝对值 | 符号位为 1，其余位表示绝对值 | +0、-0 两个 | 加减需要单独处理符号和进位 |
| 反码 | 与原码相同 | 符号位不变，其余位按位取反 | +0、-0 两个 | 加法可能需要循环进位 |
| 补码 | 与原码相同 | 反码加 1 | 只有一个 0 | 加减统一为补码加法，硬件实现简单 |

以 8 位为例：`+5 = 0000 0101`，`-5` 的原码为 `1000 0101`，反码为 `1111 1010`，补码为 `1111 1011`。这里的“统一使用补码”指整数算术的通常硬件表示；具体语言对象的位宽和有符号溢出规则仍由语言和实现决定。

### 4.3.5 为什么计算机使用补码？（面试重点）

1. 统一加减运算逻辑，硬件实现简单
2. 消除了 +0 和 −0 的问题
3. 可以自然表示最大负数（如 8 位的 −128）

### 4.3.6 总结

> 原码是符号位加绝对值；反码是负数除符号位外按位取反；补码是在反码基础上加 1，补码消除了双零问题并简化了硬件运算，因此被计算机广泛采用。

## 4.4 内存碎片

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/Linux物理内存碎片高频面试题#第 19 题：为什么系统”总空闲内存还够”，却仍然可能分配不出大块连续物理内存？|内存项目 19：系统”总空闲内存还够”，却仍然可能分配不出大块连…]]
> - [[projects/嵌入式八股/1. 项目八股/Linux物理内存碎片高频面试题#第 21 题：外部碎片、内部碎片、伙伴系统、SLAB/SLUB 之间是什么关系？这个项目主要观测哪一类碎片问题？|内存项目 21：外部碎片、内部碎片、伙伴系统、SLAB/SLUB…]]

内存碎片是指在内存中出现的一些非连续的空闲区域，导致内存无法被有效利用。内存碎片通常发生在动态内存分配时，特别是在堆内存管理过程中。内存碎片分为两种主要类型：**外部碎片** 和 **内部碎片**。

### 4.4.1 外部碎片（External Fragmentation）

外部碎片是指内存中存在一些空闲的、不连续的内存块，虽然总的空闲内存空间足够大，但是这些空闲空间分散在内存的不同位置，导致无法满足程序对大块连续内存的需求。

**外部碎片的原因**

- 动态内存分配和释放：当程序不断地分配和释放不同大小的内存块时，空闲内存的空间会逐渐被切割成多个不连续的块，形成外部碎片。
- 不均匀的内存分配：当系统分配内存的方式不够高效时，会导致内存分布不均匀，产生很多小的空闲内存区域。

**外部碎片的后果**

- 内存的浪费：虽然总的空闲内存是足够的，但是由于它们是分散的，无法满足大内存请求，从而浪费了大量可用内存。
- 内存分配失败：某些情况下，程序可能无法申请到足够的连续内存空间，导致内存分配失败。

**解决方法**

- **内存紧凑化（Compaction）**：通过将内存中的块移动，使得空闲空间集中到一边，从而减少碎片。操作系统可以在适当的时候执行内存紧凑操作。
- **使用更好的分配算法**：例如，**Buddy System**、**Slab Allocator** 等算法可以帮助减小外部碎片的产生。
- **虚拟内存**：操作系统通过虚拟内存机制将程序的内存空间映射到物理内存中，使得程序访问的内存可以是非连续的，从而减少了外部碎片的影响。
- 内存池：预先申请一大块连续内存，切成固定大小 / 固定几种规格的块，只在池内分配和回收

### 4.4.2 内部碎片（Internal Fragmentation）

内部碎片是指内存中的某个分配区域内部有未被使用的空间。即，内存分配时，为了满足分配请求的最小单位或对齐要求，分配了比实际需求更大的内存块，导致分配的内存中一部分无法被有效利用。

**内部碎片的原因**

- **对齐要求**：为了提高内存访问效率，许多系统要求内存按照一定的对齐方式分配（例如，4字节对齐、8字节对齐等）。这会导致当实际分配的内存不满足对齐要求时，内存块的末尾部分出现无法使用的空间。
- **最小分配单位**：操作系统和分配器通常会为内存分配提供一定的最小分配单位。例如，内存分配器可能会以 8 字节为单位进行分配，如果请求分配 10 字节的内存，实际分配的内存可能是 16 字节，这样就会出现 6 字节的浪费。

**内部碎片的后果**

- **内存浪费**：虽然每个内存块内部的空间可能只浪费一小部分，但当大量小内存块的内部都存在浪费时，最终会导致相当大的内存浪费。
- **降低内存利用率**：每次分配内存时，都会有一部分空间未被利用，从而影响了整个内存系统的效率。

**解决方法**

- **内存池（Memory Pool）**：通过使用固定大小的内存池（例如，按 8 字节、16 字节等为单位分配内存），可以避免小块内存的浪费。
- **使用更小的分配单位**：通过更细粒度的内存管理和分配策略，减少分配时的对齐空间和多余内存块。
- **定制化分配器**：为不同大小的内存请求提供定制化的内存分配器，避免统一的最小分配单位导致的浪费。

### 4.4.3 其他类型的内存碎片

除了外部碎片和内部碎片，还有一些特殊类型的碎片：

- **文件系统碎片** 文件系统在读写数据时，如果连续空间不可用，就会将文件分散存储在不同的磁盘块中，导致文件碎片。这种碎片虽然不是内存层面的碎片，但会影响文件的读取性能。
- **共享内存碎片** 在多进程或多线程系统中，共享内存区域如果不均匀分配，也可能导致共享内存的碎片，进而影响系统性能。

### 4.4.4 总结

内部碎片是已分配块内部未使用的空间，外部碎片是空闲空间被分散后难以满足连续分配；文件系统碎片和共享内存布局问题属于相关但不同层面的现象。应按分配器、页分配器或文件系统分别选择内存池、合并空闲块、分页/压缩或重新布局等策略。

### 4.5.1 RTOS 中的内存管理

RTOS 通常用于嵌入式系统，内存受限，所以管理策略更“轻量化”：

**(1) 静态分配**

- **在编译期就分配好内存**（如任务栈、全局变量）。
- 优点：无碎片，运行时安全。
- 缺点：不灵活，浪费空间。

**(2) 动态分配（堆）**

RTOS（如 FreeRTOS、uC/OS）也提供 malloc/free 或自带的 pvPortMalloc/pvPortFree。

- 如果直接用 C 标准库的 malloc/free，容易产生内存碎片，导致长时间运行出错。
- 常见替代方案是 **内存池（Memory Pool/Block Pool）**：
    - 提前分配一块大内存，分割成固定大小的块。
    - 分配时直接取空闲块，释放时直接归还，不会碎片化。

### 4.5.2 C++ 中的内存管理

C++ 主要依赖操作系统提供的堆 + 自己的内存分配机制：

**(1) 静态 / 栈分配**

- 局部变量、RAII 对象，内存自动回收，不会碎片化。

**(2) 动态分配**

- 使用 new/delete，底层调用 OS 的 malloc/free。
- 容器（如 std::vector）会自己申请一块连续内存，避免碎片。

**(3) 碎片预防方法**

- 自定义分配器 (Allocator)：STL 容器支持传入 Allocator，可以实现内存池分配，减少碎片。
- 对象池 (Object Pool)：适合频繁创建/销毁小对象。
- 智能指针 (unique_ptr, shared_ptr)：减少内存泄漏风险，但碎片问题仍依赖底层分配器。

### 4.5.3 通用操作系统 (Linux/Windows) 的内存管理

操作系统的内存管理更复杂，主要有：

**(1) 虚拟内存机制**

- 每个进程有自己的虚拟地址空间，内核负责映射到物理内存。
- 外部碎片被虚拟内存屏蔽（进程看到的是连续空间）。
- 内核页表维护，页大小一般 4KB。

**(2) 内核分配算法**

- **伙伴系统 (Buddy Allocator)**：内核管理物理页，减少碎片。
- **slab/slub/slob 分配器**：针对小对象（结构体、内核对象），减少碎片。

**(3) 用户态堆管理**

- malloc/free 通常使用 **ptmalloc, jemalloc, tcmalloc** 等高级分配器。
- 它们通过：
    - 内存池 + 空闲链表
    - 大小分类（small/large bin）
    - 延迟释放、合并空闲块
       来减少碎片。

### 4.5.4 总结

1. 在 RTOS/嵌入式中：
    - 少用 malloc/free，用 **内存池** 或 **静态分配**。
    - 如果必须动态分配，考虑 TLSF 或 Buddy allocator。
2. 在 C++ 大型项目中：
    - 优先用 STL 容器代替手写动态数组。
    - 对高频小对象，使用 **对象池** 或自定义 Allocator。
3. 在 Linux 应用层：
    - 大多数情况交给 malloc 实现（jemalloc/tcmalloc 已经很优化）。
    - 如果是嵌入式/实时要求，用 mmap + 内存池管理更可控。

## 4.6 嵌入式系统中为什么要尽量避免动态内存分配？

在嵌入式系统中，动态内存分配通常会带来一系列的挑战和问题。由于嵌入式系统的硬件和软件环境有限，动态内存分配不当可能导致系统的不稳定、性能下降或其他严重后果。因此，通常建议尽量避免动态内存分配，尤其是在系统中对实时性和可靠性要求较高的场景中。

### 4.6.1 内存碎片问题

动态内存分配涉及到堆内存的管理，随着程序的运行，内存会被分配和释放。由于内存的分配和释放通常是不规则的，可能会导致内存碎片（外部碎片和内部碎片）。这些碎片会降低内存的使用效率，特别是在内存紧张的嵌入式系统中，可能导致系统无法满足内存需求，导致程序崩溃或性能急剧下降。

**外部碎片**

动态分配内存时，内存块会分散，造成大量不连续的小空闲内存块。这会导致系统无法满足较大内存块的请求，即使总空闲内存足够。

**内部碎片**

由于内存分配器通常会以固定的大小块来分配内存，可能会导致比实际需求更多的内存被分配，从而造成空闲内存浪费。

### 4.6.2 实时性问题

嵌入式系统通常要求满足严格的实时性要求，即在规定的时间内完成任务。动态内存分配是不可预期的，可能会引起如下问题：

- 不确定性：动态内存分配的延迟是不确定的，分配内存可能需要等待或在某些情况下花费较长时间，影响任务的执行时限。
- 优先级反转：在实时系统中，动态内存分配可能导致高优先级任务在等待低优先级任务释放内存时发生优先级反转，导致系统实时性失效。
- 内存分配失败：在内存紧张时，动态内存分配可能失败，这会直接影响实时任务的执行，导致系统崩溃或异常行为。

### 4.6.3 堆内存管理复杂性

堆内存的管理涉及复杂的分配和释放机制，这对于嵌入式系统来说可能是一种额外的负担。堆管理需要维护空闲内存的状态，可能增加系统的复杂性。此外，堆内存的管理在嵌入式系统中可能缺乏足够的保护，容易引发内存泄漏、悬挂指针、野指针等问题，增加了系统出错的风险。

### 4.6.4 内存泄漏问题

在动态内存分配过程中，内存释放的不当或遗漏会导致内存泄漏，长时间运行后，内存泄漏会导致系统内存耗尽，最终造成系统崩溃。嵌入式系统通常运行长时间，内存泄漏问题特别容易积累并导致系统崩溃。

### 4.6.5 系统资源的紧张

嵌入式系统的硬件资源通常是有限的（如内存、CPU 速度等），动态内存分配消耗额外的内存资源（如堆管理结构），占用了本可以用于程序执行的内存。这不仅降低了内存的利用效率，也可能导致系统在高负载或长时间运行时出现资源耗尽的问题。

### 4.6.6 调试和诊断困难

动态内存分配和释放使得程序的执行路径和内存状态更加难以预测和调试。嵌入式系统通常需要长期稳定运行，一旦出现错误，调试变得更加困难。内存问题（如内存泄漏、溢出等）可能在程序运行过程中逐渐暴露，导致难以复现和修复。

### 4.6.7 替代方案

由于嵌入式系统的资源有限，很多系统在设计时会避免使用动态内存分配，改为使用以下替代方案：

- 静态内存分配：在编译时分配固定大小的内存空间，并避免运行时的动态分配和释放。这样可以避免动态内存分配带来的问题，同时使系统更加可预测和稳定。
- 内存池（Memory Pool）：使用预分配的内存池来模拟动态内存分配。在内存池中，所有的内存块大小相同或固定，内存池管理比堆内存更简单和高效。
- 栈分配：通过栈来分配内存，这样的内存分配在函数返回时自动释放，减少了动态管理的复杂性。

### 4.6.8 总结

在嵌入式系统中尽量避免动态内存分配，主要是为了保证系统的实时性、稳定性和高效性。动态内存分配带来的内存碎片、实时性问题、堆内存管理复杂性、内存泄漏和调试难度等问题，都可能对嵌入式系统的长期稳定运行产生负面影响。因此，在嵌入式系统中，使用静态内存分配、内存池或栈内存等方案会是更加可控和安全的选择。

## 4.7 进程、线程及它们之间的区别

### 4.7.1 基本概念

**进程（Process）**

- **操作系统资源分配的基本单位**
- 拥有独立的：
    - 地址空间
    - 文件描述符
    - 堆、栈、全局变量
- 进程间相互隔离，安全性高

**线程（Thread）**

- **CPU 调度的基本单位**
- 线程属于进程
- 同一进程内的线程：
    - 共享地址空间和资源
    - 各自拥有独立的栈和寄存器

### 4.7.2 进程与线程的核心区别

| 维度 | 进程 | 线程 |
|---|---|---|
| 资源关系 | 资源分配和保护的基本单位 | 进程内的执行单元 |
| 地址空间 | 通常相互隔离 | 同一进程内共享代码、全局数据和堆 |
| 私有状态 | 独立页表、文件描述符表等（部分对象可共享） | 独立栈、寄存器上下文和线程局部存储 |
| 创建/切换成本 | 通常更高 | 通常更低，但仍取决于内核和工作集 |
| 故障影响 | 一个进程崩溃通常不直接破坏其他进程 | 未处理的致命信号可能终止整个进程 |
| 通信方式 | 需要 IPC，隔离强 | 共享内存直接通信，但必须同步 |

“线程是 CPU 调度的基本单位”是常用面试概括；Linux 内核实际调度的是可调度任务，进程和线程都可能对应一个 task。线程切换也不一定只保存寄存器，是否切换地址空间取决于线程是否属于同一进程。

### 4.7.3 调度与并发

- **进程调度**：跨地址空间时通常需要切换页表/地址空间状态，开销受 TLB、缓存和内核实现影响
- **线程调度**：同进程线程通常复用地址空间，但仍要保存寄存器、栈、TLS 和调度状态，不能简化成只切换寄存器和栈
- 多核 CPU 下：
    - 多进程并行
- **进程适合**：
    - 高可靠、强隔离场景
    - 服务之间解耦（浏览器多进程）
- **线程适合**：
    - 高频交互
    - 共享数据计算密集型任务

### 4.7.5 总结

> 进程是资源分配的基本单位，线程是 CPU 调度的基本单位，线程比进程更轻量但隔离性差。

> 进程管资源，线程跑任务；进程更安全，线程更高效。

## 4.8 父进程与子进程的关系及区别

### 4.8.1 基本关系

- **父进程（Parent Process）**
    - 调用系统调用 fork() 创建子进程
    - 负责管理子进程的生命周期
- **子进程（Child Process）**
    - 由父进程复制产生
    - 拥有**独立的地址空间**
    - 默认继承父进程的部分属性（如环境变量、打开的文件描述符）

### 4.8.2 父子进程的区别

| 项目 | 父进程 | 子进程 |
|---|---|---|
| 创建关系 | 调用 `fork()`，获得子进程 PID | 由 `fork()` 创建，`fork()` 返回 0 |
| 地址空间 | 保留自己的虚拟地址空间 | 获得父进程地址空间的逻辑副本，通常采用 COW |
| 文件描述符 | 原有描述符继续存在 | 继承描述符，父子描述符指向同一 open file description，文件偏移可能共享 |
| 生命周期 | 可以先于子进程退出 | 父进程退出后可能成为孤儿并被重新收养 |
| 回收责任 | 应通过 `wait()`/`waitpid()` 回收子进程 | 退出后暂时保留退出状态，等待父进程回收 |

父子进程不是“完全复制所有运行状态”：地址空间是逻辑复制，线程、锁的状态、打开文件对象等都有具体继承规则。调用 `fork()` 后，子进程通常应尽快执行 `execve()`，多线程程序还要遵守异步信号安全函数限制。

### 4.8.3 注意事项

1. **复制机制**
    - Linux fork() 采用**写时复制（Copy-On-Write）**
    - 子进程初始与父进程共享物理页，写时才拷贝
2. **僵尸进程（Zombie）**
    - 子进程结束，但父进程未调用 wait() 回收
    - 占用 PCB 结构

### 4.8.4 总结

> 父进程负责创建和管理子进程，子进程继承部分父进程资源但有独立地址空间，退出后需父进程回收。

> 父生子，资源部分共享，地址独立，生命周期可先后不同。

## 4.9 一个线程的内存一般多大？

线程本身并不是一个“固定大小”的实体，它占用的内存主要由 **线程栈 + 线程控制结构 + 少量TLS** 组成，大小与操作系统、配置密切相关。

### 4.9.1 线程内存组成

- **线程栈（主要部分）** 用于函数调用、局部变量、返回地址等；**占用最大、可配置**

常见默认值：

- **Linux（pthread）**：
    - 默认栈大小 ≈ **8 MB**
- **Windows**：
    - 默认栈大小 ≈ **1 MB**
- **嵌入式 RTOS（如 FreeRTOS）**：
    - 线程栈通常 **几百字节～几 KB**（如 512B、1KB、4KB）

**线程控制块（TCB）**

- 保存线程状态、寄存器上下文、调度信息等
- 大小通常为：
    - **几百字节 ～ 几 KB**
- 由操作系统内核或 RTOS 管理
- **线程局部存储（TLS）** 每个线程独立的全局变量副本；大小取决于程序中定义的 __thread / thread_local 变量；一般较小，可忽略不计（除非大量使用）

### 4.9.2 不同系统下的典型线程内存占用

**1. Linux / pthread**

```c
pthread_attr_setstacksize(&attr, 1 * 1024 * 1024); // 1MB
```

**2. 嵌入式 / RTOS**

- 精确评估函数调用深度
- 避免大数组、递归
- 使用栈水位检测（stack watermark）

### 4.9.3 为什么“线程多了容易 BOOM”

- 线程 共享堆和代码段
- 不共享栈
- 每创建一个线程，就至少消耗一块独立的线程栈

例如（Linux）：

- 1000 个线程 × 8MB ≈ 8GB 虚拟地址空间
- 即使没真正用到，也可能创建失败

### 4.9.4 如何控制线程内存占用

**1. Linux / pthread**

```c
pthread_attr_setstacksize(&attr, 1 * 1024 * 1024); // 1MB
```

**2. 嵌入式 / RTOS**

- 精确评估函数调用深度
- 避免大数组、递归
- 使用栈水位检测（stack watermark）

---

### 4.9.5 总结

- **线程占用的内存主要是线程栈**
- **Linux 默认约 8MB，Windows 约 1MB**
- **嵌入式线程通常只有几 KB**
- **线程过多，最先耗尽的是栈内存而不是堆**

## 4.10 GCC的编译过程

GCC 的编译过程其实可以分为 **四个主要阶段**：预处理、编译、汇编和链接。每一步都对应着源代码转化为可执行程序的过程。

1. 预处理（Preprocessing）
- 命令：gcc -E hello.c -o hello.i
- 主要任务：
    - 处理 **宏定义**（#define 展开）。
    - 处理 **头文件**（#include 替换为文件内容）。
    - 处理 **条件编译**（#ifdef、#ifndef、#if 等）。
    - 删除注释。
- 输出：.i 文件（纯粹的 C 代码，没有宏和注释）。
2. 编译（Compilation）
- 命令：gcc -S hello.i -o hello.s
- 主要任务：
    - 词法分析：把源代码拆分成 token。
    - 语法分析：根据 C 语言语法规则构建语法树（AST）。
    - 语义分析：类型检查、作用域检查。
    - 优化：循环展开、常量传播、死代码删除等。
    - 生成对应的 **汇编代码**。
- 输出：.s 文件（汇编源文件）。
3. 汇编（Assembly）
- 命令：gcc -c hello.s -o hello.o
- 主要任务：
    - 将汇编代码翻译为机器指令（二进制指令）。
    - 生成 **目标文件**（object file）。
- 输出：.o 文件（目标文件，二进制格式但不可独立运行）。
4. 链接（Linking）
- 命令：gcc hello.o -o hello
- 主要任务：
    - 把多个 .o 文件合并。
    - 解决函数、全局变量等符号的引用。
    - 把标准库（如 libc）和用户库链接进来。
    - 最终生成 **可执行文件**。
- 输出：**可执行文件**（hello）。

**总结流程**

```text
hello.c (源代码)
   ↓ 预处理 (-E)
hello.i
   ↓ 编译 (-S)
hello.s
   ↓ 汇编 (-c)
hello.o
   ↓ 链接
hello (可执行文件)
```

**查命令的小技巧**

你可以用下面命令观察每一步的结果：

```bash
gcc -E hello.c -o hello.i    # 预处理
gcc -S hello.i -o hello.s    # 编译
gcc -c hello.s -o hello.o    # 汇编
gcc hello.o -o hello         # 链接
```

## 4.11 进程状态 / 线程状态

### 4.11.1 进程的基本状态（以 Linux 为例）

1. **运行态（Running）**
    - 正在 CPU 上运行，或已就绪等待 CPU
2. **就绪态（Ready）**
    - 具备运行条件，等待 CPU 调度
3. **阻塞态（Blocked / Sleeping）**
    - 等待事件（I/O、锁、信号等）
4. **僵尸态（Zombie）**
    - 进程已退出
    - 父进程未回收其退出状态

### 4.11.2 Linux 常见进程状态标识

`ps` 的 `STAT` 字段和 `/proc/<pid>/stat` 的状态字段不是同一套完整状态图，常见主状态如下：

| 标识 | 含义 | 说明 |
|---|---|---|
| `R` | Running/Runnable | 正在运行或已在运行队列等待 CPU |
| `S` | Interruptible sleep | 可被信号唤醒的可中断睡眠 |
| `D` | Uninterruptible sleep | 通常等待不可中断的 I/O，不能简单理解为“死锁” |
| `T` | Stopped/Traced | 被作业控制信号停止或正在被跟踪 |
| `Z` | Zombie | 已退出但父进程尚未回收退出状态 |
| `X` | Dead | 进程已死亡，通常不会在正常 `ps` 输出中长期出现 |

`<`、`N`、`L`、`s`、`l`、`+` 等还可能作为附加标记，表示高优先级、低优先级、锁定内存、会话首进程、多线程或前台进程组。具体显示格式以所用 `ps` 实现为准。

### 4.11.3 线程的状态

> 线程状态与进程状态**基本一致**，但粒度更细

1. **新建（New）**
2. **就绪（Ready）**
3. **运行（Running）**
4. **阻塞 / 等待（Blocked / Waiting）**
5. **终止（Terminated）**

### 4.11.4 阻塞状态细分（线程常见）

- **I/O 阻塞**
- **互斥锁阻塞（Mutex）**
- **条件变量等待（Condition Variable）**
- **信号量等待（Semaphore）**

### 4.11.5 状态转换简图（文字描述）

```text
就绪 → 运行 → 阻塞
 ↑       ↓
 └───←───┘
```

- 阻塞解除后进入就绪态
- 调度器决定是否运行

### 4.11.6 总结

> 进程和线程都存在运行、就绪、阻塞等状态，僵尸态是进程独有的退出未回收状态。
> 状态本质是“是否能被调度以及在等什么资源”。

## 4.12 进程选用的时机 VS 线程选用的时机

### 4.12.1 使用进程的情况：

1. 需要独立的地址空间和系统资源
- 应用场景：当任务之间需要完全独立的环境，且需要较强的数据隔离时，应选择使用进程。每个进程有自己的内存空间和资源，不会直接影响其他进程。
- 例子：运行多个独立的应用程序或服务，如浏览器和数据库服务器，它们需要独立的内存和文件资源。
2. 需要更高的安全性和稳定性
- 应用场景：如果一个任务的崩溃不应该影响其他任务的正常运行，使用进程可以提高系统的稳定性。进程是独立的，进程崩溃时不会直接影响其他进程。
- 例子：在操作系统中，系统进程和用户进程应该分开，避免系统崩溃导致所有用户程序的崩溃。浏览器和操作系统的核心进程应该隔离，防止恶意网页或程序影响操作系统的稳定性。
3. 并行计算需求
- 应用场景：在多核处理器的情况下，进程可以充分利用多核的计算能力进行并行计算。每个进程可以在不同的 CPU 核心上独立执行，达到更高的计算效率。
- 例子：大规模的科学计算或数据处理任务，例如分布式数据库和视频编码任务。

### 4.12.2 使用线程的情况：

1. 共享数据和资源
- 应用场景：如果多个任务需要频繁共享数据和资源，并且需要较高效的通信，使用线程是更好的选择。线程之间可以直接访问同一个进程的地址空间，因此共享数据和资源变得更方便。
- 例子：在 Web 服务器中处理多个请求，多个线程可以共享数据库连接池，减少资源的占用和数据传输的开销。
2. 轻量级任务
- 应用场景：当任务较轻且需要频繁切换时，线程比进程更加轻量级。线程切换的开销远小于进程切换，因此当任务相对简单且需要快速调度时，线程更合适。
- 例子：一个图形界面程序中的按钮点击事件处理，每个事件可以通过一个线程来处理，线程切换快速且开销小。
3. 实时性要求
- 应用场景：如果任务对实时性有较高的要求，线程能够快速响应并处理任务。线程在同一进程内共享资源，因此线程之间的调度和通信速度较快，适合实时任务的处理。
- 例子：音视频处理、游戏开发等需要快速响应用户输入和数据处理的场景。多个线程可以在后台处理实时数据流，同时保持界面的响应性。

## 4.13 多进程内存共享可能存在的问题及处理方法

### 4.13.1 常见问题

**内存一致性问题**

多个进程访问共享内存时，如果它们都可以修改内存中的数据，就可能发生数据不一致的情况。例如，进程A修改了共享内存中的数据，但进程B读取时并没有及时看到A进程的修改，导致数据不一致。

**并发访问问题**

当多个进程同时访问共享内存中的数据时，可能会发生 **竞态条件**（race condition）。例如，如果两个进程同时修改共享变量，可能会导致数据竞争，造成不可预期的结果。

**同步问题**

由于进程之间的内存是相互独立的，它们之间并没有共享内存区域的原生同步机制。因此，必须采取额外的措施来保证共享数据的同步访问。

**死锁问题**

如果多个进程在访问共享内存时没有合理的同步机制，可能导致死锁。死锁是指多个进程相互等待对方释放资源，造成系统无法继续运行。

**内存泄漏与资源释放**

当进程结束后，未正确释放共享内存区域，或者在共享内存区域的使用中没有妥善清理，会导致内存泄漏。

### 4.13.2 处理方法

**使用进程间通信（IPC）机制**

IPC 是一种广泛用于多进程间数据共享和同步的方式。常见的 IPC 机制包括：

- **共享内存（Shared Memory）**：多个进程可以将数据存储在同一块内存区域，进行高效的交互。
- **信号量（Semaphore）**：用于进程间的同步，防止多个进程并发访问共享内存导致的冲突。
- **消息队列（Message Queue）**：进程可以通过发送和接收消息来进行通信。
- **管道（Pipe）**：一种简单的 IPC 机制，用于将一个进程的输出作为另一个进程的输入。

**使用锁机制（互斥锁）**

通过使用 **互斥锁**（Mutex）或 **读写锁**（RWLock）来保证进程在访问共享内存时的同步性。例如：

- **互斥锁（Mutex）**：确保同一时刻只有一个进程能够访问共享资源。
- **读写锁（RWLock）**：允许多个进程同时读取共享资源，但在写操作时，只有一个进程能访问资源。

**原子操作**

对于一些简单的操作（如加减法、比较并交换等），可以在目标平台和共享映射满足要求时使用 **原子操作**（Atomic Operations），使针对同一原子对象的读改写不可分割；跨进程还要确认共享内存布局、对齐、lock-free/进程共享属性和内存序，不能只凭“原子”二字保证整个数据结构没有竞态。

**内存屏障与同步**

在多核处理器中，共享内存访问仍需要定义可见性和顺序。内存屏障只能约束特定访问的顺序，不能替代互斥、原子读改写或条件同步；跨进程应使用 POSIX 进程共享锁、原子类型/平台指令和明确的内存序。

**使用共享内存时注意进程生命周期管理**

在创建共享内存时，确保 **资源的正确释放**。通过正确的管理机制，确保进程退出时清理所有资源。例如，在 POSIX 环境中，shm_unlink() 用于删除共享内存对象。

### 4.13.3 常用技术和方法

**POSIX 共享内存**

在 POSIX 系统中，常使用 shmget()、shmat() 等函数来创建和映射共享内存。在使用共享内存时，要确保多个进程同步访问。

- **创建和访问共享内存**：

```c

```

  使用信号量来控制多个进程对共享内存的访问：

## 4.14 FreeRTOS、linux、windows区别，什么时候用哪个

### 4.14.1 FreeRTOS、Linux、Windows 简介

- FreeRTOS：
    - 轻量级实时操作系统，设计用于嵌入式系统
    - 适用于资源受限的硬件，内存、处理能力有限
    - 支持实时任务调度，具备任务优先级、时间片等机制

- Linux：
    - 通用操作系统，支持多种硬件平台
    - 适用于服务器、桌面、嵌入式系统等
    - 支持进程管理、虚拟内存、文件系统等功能，开源自由

- Windows：
    - 主要用于桌面、工作站、服务器等
    - 提供强大的图形用户界面（GUI）和多任务处理功能
    - 支持多种硬件设备，具备完善的应用支持

### 4.14.2 区别

| 维度 | FreeRTOS | Linux | Windows |
|---|---|---|---|
| 定位 | 面向 MCU 的实时内核 | 通用/服务器/嵌入式操作系统 | 通用桌面和服务器操作系统 |
| 资源模型 | 通常无 MMU、资源固定、组件可裁剪 | 进程隔离、虚拟内存、丰富的驱动和文件系统 | 完整用户/内核隔离、GUI 和商业生态 |
| 调度 | 固定优先级抢占、可选时间片，具体由配置决定 | 普通调度与实时策略并存，受内核配置影响 | 调度器面向通用交互和服务负载 |
| 实时性 | 可提供较可预测的任务切换延迟，但 ISR 和配置仍重要 | 普通内核不是硬实时；可用 PREEMPT_RT 等增强 | 通用 Windows 不提供硬实时保证 |
| 内存 | 静态分配或可配置 heap，通常无完整虚拟内存 | 虚拟内存、页缓存、进程地址空间 | 虚拟内存、分页和完善的进程资源管理 |
| 选型 | 资源受限、控制环、低功耗 MCU | 复杂协议栈、网络、GUI、存储和多进程 | PC/服务器 GUI、办公和商业软件 |

FreeRTOS、Linux、Windows 不是简单的“性能高低”关系；应按内存、外设、实时期限、驱动生态、更新方式和团队工具链选择。Linux 也可以用于嵌入式，但通常需要 MPU/MMU、较大内存和启动存储。

### 4.14.3 适用场景和选择

**FreeRTOS 适用场景：**

- 嵌入式设备：例如家电、工业控制、传感器等，通常有严格的资源限制（如内存、处理能力有限）
- 实时要求高：对于实时性要求较高的应用（例如机器人、汽车电子等）
- 小型设备：如单片机、微控制器（MCU）等，适合开发低功耗、低资源消耗的系统

**Linux 适用场景：**

- 多任务系统：适用于资源充足的设备，如服务器、PC、智能手机等
- 复杂系统：需要支持虚拟内存、多进程管理和丰富的驱动的系统（例如桌面操作系统、云计算平台）
- 开发灵活性：支持多种编程语言和开发工具，适合需要开源生态和自定义的开发需求
- 嵌入式应用：如使用 Yocto、OpenEmbedded 等构建的嵌入式 Linux 系统，用于开发智能设备、网关等

**Windows 适用场景：**

- 桌面应用：如个人计算机、工作站等，适合 GUI 应用和日常办公环境
- 企业级应用：如企业服务器、商业软件等，Windows 提供广泛的商业软件支持
- Windows 嵌入式：如 Windows CE、Windows IoT 等，适用于嵌入式设备，适合复杂的用户界面和应用集成

### 4.14.4 总结

> FreeRTOS 适用于资源受限的嵌入式系统，Linux 适合多任务和功能复杂的环境，而 Windows 适用于桌面和商业应用。

> 选择操作系统时，FreeRTOS 适用于实时嵌入式，Linux 适合多任务复杂系统，Windows 适合桌面和商业环境。

## 4.15 CPU内核

### 4.15.1 ARM 内核

- **代表**：ARM7、ARM9、ARM11（早期），Cortex 系列（主流）
- **特点**：低功耗、高性能、指令集简单（RISC），生态庞大
- **应用**：
    - ARM7：早期手机、工业控制
    - ARM9/11：多媒体播放器、低端智能机
    - 现在多数嵌入式都已被 **Cortex 系列**替代

### 4.15.2 ARM Cortex 系列内核

ARM 把产品分成三大类：

- **Cortex-M 系列**（微控制器 MCU）
    - 面向低功耗嵌入式系统
    - **典型产品**：STM32（Cortex-M0/M3/M4/M7）、NXP LPC 系列、Nordic nRF（蓝牙芯片）
    - **应用**：智能家居、传感器、IoT、消费电子
- **Cortex-R 系列**（实时处理器）
    - 面向高可靠、实时性要求的场景
    - **典型产品**：TI Hercules、Renesas R 系列
    - **应用**：汽车 ECU、硬盘控制器、工业机器人
- **Cortex-A 系列**（应用处理器）
    - 高性能，支持操作系统（Linux/Android）
    - **典型产品**：高通 Snapdragon、三星 Exynos、树莓派的 Broadcom 芯片
    - **应用**：智能手机、平板、车机、边缘计算

### 4.15.3 x86 内核

- **代表**：Intel Core、AMD Ryzen、Atom
- **特点**：高性能，CISC 架构
- **应用**：个人电脑、服务器、工控机

### 4.15.4 RISC-V 内核

- **特点**：开源指令集，灵活可裁剪，低成本
- **应用**：
    - **低端 MCU**（如全志 D1、SiFive 芯片）
    - **高校/科研开发**（自研 CPU、国产替代）
    - **未来**：IoT、车载、AI 边缘计算

### 4.15.5 MIPS 内核

- **特点**：老牌 RISC 架构，简洁高效
- **应用**：曾用于路由器（早期的联发科）、机顶盒、网络交换机
- （逐渐被 ARM、RISC-V 替代）

### 4.15.6 PowerPC 内核

- **代表**：IBM、Freescale
- **特点**：高可靠性，嵌入式强
- **应用**：汽车 ECU（早期）、航空航天、工业控制

### 4.15.7 DSP 内核

- **代表**：TI C6000、ADI Blackfin
- **特点**：信号处理优化（乘加运算快）
- **应用**：音频处理、雷达、图像处理、通信基带

### 4.15.8 总结：什么时候用什么内核？

- **Cortex-M** → IoT、低功耗传感器、家电、STM32
- **Cortex-R** → 实时性要求高的（汽车 ECU、马达控制）
- **Cortex-A** → 高性能，需要操作系统的（手机、车机、边缘计算）
- **x86** → PC、服务器、大型工控机
- **RISC-V** → IoT、新兴领域、国产替代
- **DSP** → 专业音视频、雷达、通信

## 4.16 多进程的优缺点、多线程的优缺点

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/linux视觉感知面试题#Q06 OpenMP 与 Pthread 有什么区别？为什么采用 4 线程？|视觉项目 Q06：OpenMP 与 Pthread 有什么区别？为…]]

### 4.16.1 多进程的优缺点

**多进程的优点**

1. **高稳定性**
    - 单个进程崩溃不影响其他进程
2. **安全性好**
    - 地址空间隔离，数据不易被误操作
3. **易于模块解耦**
    - 适合服务化、模块化架构
4. **天然支持多核并行**

**多进程的缺点**

1. **创建和切换开销大**
    - 进程创建、上下文切换成本高
2. **进程间通信复杂**
    - 需要 IPC（管道、共享内存、消息队列等）
3. **资源占用多**
    - 每个进程都有独立资源

### 4.16.2 多线程的优缺点

**多线程的优点**

1. **创建和切换开销小**
    - 线程比进程轻量
2. **数据共享方便**
    - 同一进程内直接共享内存
3. **并发性能高**
    - 适合高并发、高性能场景
4. **资源利用率高**

**多线程的缺点**

1. **稳定性差**
    - 一个线程崩溃可能导致整个进程退出
2. **同步复杂**
    - 容易出现竞态、死锁
3. **调试困难**
    - 并发问题难复现、难定位

### 4.16.3 总结表

| 维度 | 多进程 | 多线程 |
|---|---|---|
| 隔离性 | 地址空间隔离，故障边界清晰 | 共享地址空间，故障可能影响整个进程 |
| 通信 | 管道、消息队列、共享内存、socket 等 IPC | 共享变量、条件变量、互斥锁、原子操作等 |
| 创建/切换 | 通常开销较大 | 通常开销较小，但仍有栈、调度和同步成本 |
| 并行能力 | 多核上可以并行 | 多核上也可以并行，不能把线程等同于串行 |
| 典型场景 | 服务隔离、插件沙箱、故障容错 | 同一服务内并发 I/O、流水线和共享缓存 |
| 主要风险 | IPC 复杂、资源复制或共享管理复杂 | 数据竞争、死锁、优先级反转和生命周期错误 |

选型不能只看“进程慢、线程快”。应同时考虑故障隔离、通信频率、实时约束、部署方式和安全边界。

### 4.16.4 总结

> 多进程稳定但开销大，多线程高效但复杂，工程中常结合使用。

> 多进程保安全，多线程拼性能。

## 4.17 线程崩溃的原因、影响与处理方式

### 4.17.1 线程崩溃的原因

- **内存访问错误**：访问非法内存（如空指针解引用、越界访问等）可能导致线程崩溃。
- **除零错误**：计算过程中发生除零操作。
- **栈溢出**：线程栈空间不足，通常由于递归深度过大等原因。
- **异常抛出**：未捕获的异常可能导致线程的崩溃。
- **资源耗尽**：线程执行过程中，如果无法获得需要的资源（如内存、文件句柄等），可能导致崩溃。
- **死锁**：死锁通常表现为线程永久等待或超时，不会因为“死锁”本身自动被操作系统杀死；监控程序、看门狗或外部信号可能另外终止进程。

### 4.17.2 线程崩溃的影响

**线程的独立性与进程边界**

- 普通线程函数正常返回、调用 `pthread_exit()` 或被取消时，通常只结束该线程；它仍可能留下未完成的共享状态或未释放的应用资源。
- 在 POSIX/Linux 中，非法内存访问、除零等致命信号的默认动作通常是终止整个进程，而不是只终止触发信号的线程；未捕获的 C++ 异常也会调用 `std::terminate`，通常结束整个进程。
- 只有显式安装信号处理、使用独立进程或运行时特定的故障隔离机制，才可能实现更细粒度的恢复；不能用“主线程/重要线程”作为通用判断。

**共享资源的影响**

- 如果线程崩溃发生在持有共享资源时（如文件句柄、锁、共享内存等），这些资源可能处于不一致的状态，导致其他线程无法正常工作。例如，持有互斥锁的线程崩溃，可能导致其他线程无法获得该锁，从而发生死锁。
- **资源泄漏**：崩溃的线程如果未能释放已分配的资源，可能会导致资源泄漏，如内存泄漏或文件句柄泄漏。

**线程之间的依赖性**

- 如果线程崩溃导致共享数据变得不一致，其他依赖于该数据的线程可能会受到影响。比如，线程 A 与线程 B 共享一个变量，线程 A 崩溃前没有更新该变量，线程 B 可能会错误地读取到过时的值。

### 4.17.3 如何处理线程崩溃

- **异常处理** 在线程函数中使用异常处理机制（如 try-catch）来捕获可能的异常，防止线程因未捕获异常而崩溃。这样做可以确保即使发生异常，程序也能继续运行。

**分离线程**

- `pthread_detach()` 或 `std::thread::detach()` 只改变 joinable 状态和线程结束后的资源回收方式，不会隔离地址空间，也不能防止致命信号终止整个进程。若需要故障隔离，应考虑进程边界、监督重启和清晰的取消/回收策略。
- **线程池管理** 线程池可复用线程、限制并发并集中处理任务；它不会自动隔离线程崩溃，若线程异常退出，是否创建替代线程要由线程池实现和监督逻辑负责。
- **资源保护** 使用互斥锁、读写锁、信号量等同步原语来保护共享资源，避免崩溃的线程持有锁而不释放，导致其他线程无法继续执行。

**崩溃检测和日志记录**

- 使用日志记录线程崩溃的情况，便于调试和排查问题。可以借助工具如 **core dump**、**gdb** 等来分析崩溃原因。
- 在崩溃发生时，捕获 **core dump** 文件或使用 **断言（assert）** 来进行事后分析。

**进程级故障的应对**

- 致命信号或未捕获异常可能终止整个进程，与触发故障的是主线程还是工作线程无关。`try-catch` 只能处理在线程栈上实际抛出的、可捕获的 C++ 异常，不能可靠地捕获 SIGSEGV 等硬件故障；应结合输入校验、资源清理、core dump、监督进程和重启策略处理。

### 4.17.4 线程崩溃与多核处理器

在多核处理器中，线程之间的调度是由操作系统进行管理的。虽然操作系统调度各个线程的执行，但线程之间仍然是相互独立的。

- **线程并行性**：多核只说明线程可以并行运行；一个线程发生普通退出与发生致命信号的后果不同，后者可能使整个进程退出，不能笼统地说“不会影响其他线程”。
- **线程同步**：如果多个线程需要共享数据，使用锁等同步机制来确保数据一致性，以防止崩溃线程对其他线程的数据产生负面影响。

### 4.17.5 总结

- 普通线程退出通常只结束该线程；共享状态、锁和资源仍可能影响其他线程。
- POSIX/Linux 中的致命信号和未捕获异常通常是进程级故障，可能终止所有线程；不能把 `detach` 或“非主线程”当作故障隔离手段。
- 健壮性依赖边界校验、异常/取消处理、资源回收、core dump、监督重启和必要的进程隔离。

## 4.18 进程上下文

### 4.18.1 定义

**进程上下文**是指：
**进程在执行时，CPU 为了能够在中断或切换后继续正确执行该进程，需要保存和恢复的全部运行环境信息**。

### 4.18.2 进程上下文包含的内容

1. **CPU 寄存器**
    - 程序计数器（PC）
    - 栈指针（SP）
    - 通用寄存器
    - 状态寄存器（PSW）
2. **虚拟内存信息**
    - 页表基址
    - 地址空间映射关系
3. **内核相关信息**
    - 内核栈
    - 进程控制块（PCB / task_struct）
4. **调度相关信息**
    - 进程状态
    - 优先级
    - 时间片信息

### 4.18.3 进程上下文切换（Context Switch）

**触发时机**

- 时间片用完
- 主动让出 CPU（sleep）
- 等待 I/O
- 高优先级进程抢占
- 系统调用 / 中断返回

**切换过程（简化）**

1. 保存当前进程上下文
2. 更新进程状态
3. 选择下一个可运行进程
4. 恢复新进程上下文
5. CPU 开始执行新进程

### 4.18.4 进程上下文 vs 线程上下文

| 维度 | 进程上下文 | 线程上下文 |
|---|---|---|
| 执行主体 | 进程中的当前执行流 | 某个线程的寄存器、栈和调度状态 |
| 地址空间 | 包含页表、地址空间和进程资源视图 | 同进程线程通常复用同一地址空间 |
| 私有数据 | 进程级资源和信号处理属性 | 线程栈、寄存器、TLS、线程调度参数 |
| 切换成本 | 可能需要切换页表和 TLB 相关状态 | 同进程线程切换通常不切换地址空间 |
| 关系 | 一个进程至少有一个线程 | 一个进程可包含多个线程 |

在 Linux 中，进程和线程都由内核任务结构表示，因此“进程上下文一定比线程上下文大”只是经验性说法；实际成本取决于是否跨地址空间、缓存/TLB 命中、寄存器扩展状态和调度路径。

### 4.18.5 总结

> 进程上下文是进程运行环境的集合，上下文切换涉及寄存器、页表等信息，开销较大。

> 进程上下文 = CPU 能“接着跑”一个进程所需的全部状态。

## 4.19 中断上下文

**中断上下文**是指系统在处理硬件或软件中断时，操作系统进入的执行环境。在中断上下文中，CPU会暂时停止当前正在执行的程序，转而执行与中断源相关的中断处理程序（通常称为**中断服务例程**，ISR）。这段时间被称为“中断上下文”。在此期间，操作系统不得进行任何阻塞操作，必须迅速响应和处理硬件事件。

### 4.19.1 中断上下文的特点

- **实时性强**：中断上下文中，系统会中断当前的任务，快速响应外部硬件事件或软件事件。因此，它要求执行的代码尽可能简短和高效，以便尽快恢复到正常程序流。
- **非阻塞**：在中断上下文中，不能进行任何形式的阻塞操作。例如，不能调用可能导致等待的系统调用（如获取锁、I/O操作等），因为阻塞操作会导致中断处理程序未能及时完成，影响系统的实时性和稳定性。
- **不能像线程一样直接睡眠/调度**：ISR 通常不能调用会阻塞或主动切换的线程 API；它可以唤醒任务或设置重调度请求，真正的任务切换通常在中断返回路径或端口规定的调度点发生。
- **嵌套取决于平台**：是否允许更高优先级中断嵌套由 CPU、中断控制器和屏蔽配置决定；ISR 应按目标平台规则编写，不能把“不可重入”当成所有系统的结论。

### 4.19.2 中断上下文的执行流程

1. **中断/异常发生**：硬件 IRQ、NMI、软件陷入或 CPU 异常按平台规则进入相应入口；系统调用入口不应笼统称为普通 IRQ。
2. **中断处理程序**：一旦中断被触发，操作系统会暂停当前正在执行的程序（如果需要），保存当前程序的状态，并转向执行与中断源相关的中断处理程序。
3. **中断处理程序执行**：中断处理程序（ISR）会执行中断事件的具体处理，比如读取设备数据、清除中断标志、调整硬件状态等。此时不能进行阻塞性操作，如等待某些资源或进行调度。
4. **恢复程序执行**：中断处理程序完成后，系统会恢复被中断的任务，并继续执行原来的程序。这个过程通常需要恢复先前保存的寄存器状态，并恢复到原先的执行流。

### 4.19.3 中断上下文与进程/线程上下文的区别

| 维度 | 进程/线程上下文 | 中断上下文 |
|---|---|---|
| 进入方式 | 被调度、系统调用或主动运行 | 硬件中断、异常或内核延后处理机制触发 |
| 是否可睡眠 | 满足条件时可以睡眠或阻塞 | 通常不能睡眠，不能调用可能阻塞的 API |
| 当前身份 | 有明确的进程/线程和用户地址空间 | 依附于被打断的执行流，不等同于一个线程 |
| 调度 | 可以触发调度 | ISR 通常先完成，返回路径再决定是否调度 |
| 适合工作 | 可执行较长任务和阻塞 I/O | 读取状态、清中断、搬运少量数据、唤醒下半部 |

“中断上下文不可重入”并非普适结论：更高优先级中断可能嵌套，是否允许取决于 CPU、中断控制器和屏蔽配置。常见做法是 ISR 做最少工作，把耗时处理交给线程化中断、软中断、tasklet 或工作队列。

### 4.19.4 中断上下文中的注意事项

**禁止阻塞操作**

在中断上下文中，由于不允许执行阻塞操作，以下操作通常不应在中断处理程序中执行：

- **动态内存分配**（如 malloc）
- **锁操作**（如互斥锁）
- **I/O操作**（如文件读取、网络发送等）
- **线程调度**（如 sleep 或 wait）

如果中断处理程序执行了阻塞操作，可能导致中断处理程序未能及时完成，系统无法及时响应其他事件，从而影响系统的实时性和稳定性。

**不能调用可能引起调度的函数**

在中断上下文中，不能调用那些会触发线程调度的操作。比如：

- **睡眠函数**：如 sleep、msleep，它们会使当前执行的任务被挂起，从而影响中断的实时性。
- **调度函数**：如 sched_yield、yield 等，会导致当前线程主动放弃CPU资源，进行线程调度。

**中断嵌套和优先级**

中断是否嵌套由目标 CPU、中断控制器和当前屏蔽位决定；支持嵌套的平台允许高优先级 ISR 打断低优先级 ISR。无论是否嵌套，都应保持 ISR 短小、可重入性和共享数据保护规则明确。

### 4.19.5 总结

**中断上下文**对于保证实时性至关重要。在设计中断服务例程时，必须确保中断处理程序尽可能简单、快速，并避免进行可能阻塞的操作。

## 4.20 中断和异常的区别

### 4.20.1 定义

- **中断（Interrupt）**：狭义通常指外设或其他硬件产生的异步 IRQ/NMI；部分教材也把软件中断指令称为 interrupt，因此回答时要说明分类口径。
- **异常（Exception）**：是由处理器在执行程序时内部产生的事件，通常是由于程序错误或不正常的操作所触发的。例如，除零错误、访问无效内存、指令错误等。

### 4.20.2 触发来源

- **硬件中断（IRQ/NMI）**：
    - **外部事件**：来自外设或硬件控制器的信号，通常与当前指令异步。常见来源包括定时器、网卡和 GPIO。
- **异常**：
    - **内部事件**：通常是由程序执行中的错误、无效操作或处理器内部状态引发的。异常通常反映程序本身的错误或者硬件故障。

### 4.20.3 处理机制

- **硬件中断**：
    - 中断会引发处理器暂停当前执行的任务，保存现场，去执行中断服务程序（ISR）。中断服务程序（ISR）一般会执行一个固定的响应操作，然后恢复之前的任务。
    - 硬件 IRQ 通常是异步的；软件陷入指令则与当前执行流同步，不能混用这两个结论。
- **异常**：
    - 异常发生时，处理器会立即停止当前执行的指令，并跳转到对应的异常处理程序。异常处理程序通常会对错误进行修复或终止程序执行。
    - 异常是同步的，即发生在程序的执行过程中，是在特定的程序操作上发生的。

### 4.20.4 响应时机

- **硬件中断**：
    - 硬件 IRQ 通常是**异步的**，不由当前指令直接产生；软件中断/系统调用属于另一类同步入口。
    - 例如，外部硬件设备向处理器发送中断信号，通知其处理某个事件（如I/O操作完成）。
- **异常**：
    - 异常是**同步的**，发生时是由程序中某个具体的指令或操作触发的。
    - 例如，当程序试图执行非法内存访问（如空指针解引用）时，处理器就会抛出异常。

### 4.20.5 例子

- **中断**：
    - **定时器中断**：定时器到期后，硬件发出中断信号，处理器暂停当前任务，去处理定时任务。
    - **外部设备中断**：例如，当外部硬盘完成数据传输时，硬盘会发出中断信号，通知CPU进行下一步操作。
- **异常**：
    - **除零异常**：当程序试图除以零时，处理器会触发异常，导致程序中断并进入异常处理流程。
- **段错误（Segmentation Fault）**：非法内存访问通常先触发处理器异常，再由 Linux 内核向进程投递 `SIGSEGV`；用户态看到的是信号，不应把它直接等同于“软中断”。

### 4.20.6 优先级与控制

- **中断**：
    - 中断通常由硬件设备发出，优先级通常由硬件或操作系统决定。某些中断可能是嵌套的，即处理器可以响应一个中断后再响应另一个中断。
    - 中断服务程序（ISR）执行完后，处理器会恢复中断之前的操作。
- **异常**：
    - 异常一般没有嵌套的概念，程序会在异常发生时立即中断当前执行，跳转到异常处理程序。异常通常是同步的，程序员需要对异常进行处理或捕捉。

### 4.20.7 是否可屏蔽

- **中断**：
    - 中断是可屏蔽的。操作系统可以通过禁用中断来避免某些中断的处理，或通过设置中断屏蔽字来控制中断的优先级和处理时机。
- **异常**：
    - 多数同步 CPU 异常不能像可屏蔽 IRQ 那样由通用中断屏蔽位忽略，但异常的可屏蔽性、优先级和处理方式由架构定义，不能把所有异常一概说成“不可屏蔽”。

### 4.20.8 是否可恢复

- **中断**：
    - 中断是可恢复的。当中断发生时，处理器执行完中断服务程序后会返回到中断前的执行状态。
- **异常**：
    - 异常的恢复通常依赖于异常类型。例如，某些异常可能导致程序终止（如除零错误、内存访问错误），而其他异常则可能通过异常处理机制（如 try/catch）进行恢复。

### 4.20.9 总结对比

- **中断** 主要是由外部硬件发出的请求，通常是异步的，目的是通知CPU处理外部事件。中断通常是可屏蔽的，处理完毕后会返回正常的程序执行。
- **异常** 则通常是由程序内部错误、显式陷阱或系统事件触发的，通常与当前指令同步。多数同步异常不能按普通 IRQ 方式屏蔽，但具体可屏蔽性、优先级和恢复方式由 CPU 架构及异常类型定义，处理不当可能导致程序终止。

## 4.21 中断处理函数中为什么不能做耗时操作？

中断处理函数（通常称为中断服务程序，**ISR**）是处理外部硬件事件的一段代码，其主要作用是尽快响应硬件中断并完成相应的任务。由于中断处理函数的特殊性质，在设计和编写中断处理函数时，必须避免进行耗时操作。原因如下：

### 4.21.1 阻塞系统其他中断的响应

- 中断是异步事件，当一个中断发生时，处理器会暂停当前任务，转而执行中断处理函数。如果中断处理函数执行时耗时过长，系统就无法及时响应其他的中断请求，可能会导致**中断丢失**或者**中断延迟**。
- 对于实时系统而言，实时性是非常重要的。中断处理函数如果执行耗时操作，可能导致某些实时任务无法在规定的时间内完成，从而影响系统的稳定性和可靠性。

### 4.21.2 影响主程序的执行

- 中断服务程序执行过程中，处理器暂停主程序的执行，直到ISR结束。如果ISR内有耗时操作（如等待、复杂计算、I/O操作等），则主程序的执行时间被延长，进而影响到系统的性能。
- 长时间的ISR执行也可能导致系统的响应时间变长，降低系统对外部事件的响应效率。

### 4.21.3 可能导致栈溢出或堆栈消耗过多

- 中断服务程序执行时会使用系统栈。如果ISR执行的代码过长或者堆栈消耗过大，可能导致**栈溢出**。嵌入式系统中的栈空间通常非常有限，栈溢出会导致系统崩溃或异常行为。
- 在ISR中进行耗时操作可能导致堆栈的深度增加，进一步加剧栈空间的压力。

### 4.21.4 中断嵌套和优先级反转问题

- 一些系统可能支持中断嵌套（即一个中断处理函数可以被更高优先级的中断打断）。如果当前ISR中存在耗时操作，可能会导致低优先级的ISR无法及时响应。长时间的ISR执行可能导致**优先级反转**问题，即高优先级中断被低优先级ISR阻塞，影响系统的实时性。
- 而且，有些嵌入式系统对中断优先级有严格的管理，长时间的中断处理会影响其他重要的高优先级中断处理，造成系统性能瓶颈。

### 4.21.5 调度延迟

- 中断服务程序执行完后，通常会恢复到中断前的程序状态。如果中断处理时间过长，会导致任务调度的延迟，降低整个系统的调度效率。尤其是实时操作系统（RTOS）中，这会影响任务的响应性，导致时序错误或任务超时。
- 例如，实时操作系统（RTOS）可能会在ISR返回后调度另一个任务，如果ISR执行了耗时操作，调度过程会受到影响，延迟其他任务的执行。

### 4.21.6 可能导致死锁或资源竞争

- 中断处理函数中进行耗时操作时，可能会访问和修改共享资源。若这些资源没有适当的同步机制，可能导致**竞态条件**和**死锁**问题。
- 如果ISR操作涉及到阻塞调用（例如访问文件系统或网络接口），这会导致系统状态的不可预测，影响程序的稳定性。

### 4.21.7 影响系统的可维护性和可扩展性

- 如果ISR内部的操作过于复杂或耗时，代码的可维护性会大大降低。长时间的ISR可能会影响系统设计的可扩展性，使得后续开发或调整变得更加困难。

### 4.21.8 避免耗时操作的建议

为了避免上述问题，编写中断处理程序时应遵循以下原则：

- **简短快速**：中断处理程序应尽量简短，快速完成必要的任务，并尽早返回主程序。
- **推迟复杂处理**：对于复杂的计算或耗时的操作（如数据处理、I/O操作等），应推迟到主程序中或其他线程中处理，而不是直接在ISR中进行。
- **使用标志量或信号量**：可以在ISR中设置标志位或发送信号量，主程序或其他任务可根据这些标志或信号进行相应的处理。
- **避免阻塞操作**：在ISR中避免使用会导致阻塞的操作，如sleep()、wait()、mutex等。
- **尽量避免内存分配**：避免在ISR中进行内存分配和释放操作，尤其是使用动态内存分配（如 malloc()），因为这些操作通常是耗时的，并且可能导致内存碎片问题。

### 4.21.9 总结

中断服务程序的设计应尽量简化，确保系统的实时性、稳定性和可维护性。避免耗时操作，快速响应中断，确保嵌入式系统的高效运作。

## 4.22 软中断和硬中断

### 4.22.1 硬中断（Hardware Interrupt）

- **定义**：硬中断是由外部硬件设备或外部信号发起的中断。通常由外设（如键盘、鼠标、网络接口、定时器等）向CPU发送中断请求（IRQ，Interrupt Request）。硬中断是异步的，即它可以在程序执行的任何时刻发生。
- **触发方式**：硬中断由硬件设备通过发送信号触发，通常是外部事件（如外设完成数据传输、I/O设备准备好数据等）引起的。
- **中断类型**：硬中断通常具有不同的优先级，可以通过中断控制器管理这些中断请求。中断服务程序（ISR）会被调用来处理中断。
- **特点**：
    - **异步**：硬中断的触发时机与程序执行无关，它是由外部设备或硬件触发的，处理器可以在程序的任何时刻响应硬中断。
    - **硬件驱动**：硬中断通常由硬件产生，CPU根据外部设备的请求进行响应。
    - **中断处理**：处理硬中断时，处理器会保存当前程序的上下文，执行对应的中断服务程序，然后恢复上下文继续执行。
- **示例**：
    - **定时器中断**：定时器周期性地生成中断信号，通知CPU执行定时任务。
    - **外部I/O设备中断**：例如，鼠标、键盘、网卡等外部设备产生的中断，用于处理设备的输入或数据传输。

### 4.22.2 软件触发入口与 Linux softirq

- **软件触发的陷入/异常**：x86 的 `int`、现代 `syscall` 以及 ARM 的 SVC 等，是用户或内核进入特定处理入口的机制；CPU 异常（如除零、缺页）则由处理器同步产生，不能简单归入“软中断”。
- **Linux `softirq`**：这是内核把硬中断后续工作延后执行的一种机制，由内核设置 pending 位并在合适时机运行；它不是用户程序执行 `int` 指令，也通常不能睡眠。
- **实时性与上下文**：软件陷入/异常通常与当前指令同步，Linux softirq 则是内核延后处理；具体能否睡眠、何时调度要看所处上下文和内核实现。

### 4.22.3 软中断与硬中断的比较

| 维度 | 硬件中断 | 软中断/延后处理 |
|---|---|---|
| 触发源 | 外部设备或片上外设的 IRQ | 内核或软件设置的待处理事件 |
| 时序 | 通常异步于当前代码 | 通常由内核在合适时机执行 |
| 典型用途 | 快速响应设备、读取状态、确认中断 | 网络协议栈、定时器和 ISR 的后续处理 |
| 能否睡眠 | 顶半部通常不能 | Linux softirq/tasklet 也不能睡眠；工作队列运行在线程上下文可睡眠 |
| 备注 | 需要保存/恢复被打断的上下文 | 不应把 `int` 指令、异常、系统调用和 Linux softirq 混为一类概念 |

在现代操作系统中，“软中断”有多种含义：x86 的软件中断指令、系统调用入口、CPU 异常与 Linux `softirq` 机制并不完全等价。回答时应先说明所指平台和机制。

### 4.22.4 总结

- **硬中断**由外部硬件触发，主要用于响应外部设备的事件，通常是异步且具有优先级，硬中断服务程序负责处理中断，并恢复主程序的执行。
- **软件触发入口/异常**可由指令或处理器内部条件产生；Linux `softirq` 则是内核延后处理机制。三者不能混为同一个“软中断”概念。

比较前应先说明平台和机制：硬件 IRQ 通常来自外设且相对异步，系统调用入口是受 ABI 约束的同步陷入，CPU 异常由当前指令触发，Linux `softirq` 是内核下半部处理。

## 4.23 中断嵌套的实现

### 4.23.1 中断嵌套的基本原理

在中断嵌套模式下，当一个中断服务程序执行时，如果发生了一个优先级更高的中断，当前的ISR可以被挂起并保存其上下文，执行更高优先级的ISR。当高优先级的ISR处理完毕后，控制权会返回到之前被挂起的ISR，恢复其执行。

**中断嵌套实现的基本流程：**

1. **硬件触发中断**：当一个中断事件发生时，中断控制器向CPU发出中断请求信号。
2. **保存当前上下文**：CPU响应中断时，首先会保存当前程序（主程序或上一个ISR）的上下文信息，以便稍后恢复。
3. **执行中断服务程序（ISR）**：CPU开始执行当前的ISR，完成对外设的处理。
4. **发生更高优先级的中断**：在当前ISR执行过程中，如果发生了一个更高优先级的中断，CPU将中断当前的ISR，保存其上下文，执行更高优先级的ISR。
5. **恢复原ISR执行**：高优先级ISR执行完毕后，控制返回到原ISR，恢复执行并最终返回到主程序。

### 4.23.2 硬件支持中断嵌套

大多数现代微处理器和微控制器都提供硬件支持来实现中断嵌套。以下是硬件如何支持中断嵌套的几个关键部分：

**中断控制器**

- **中断控制器（Interrupt Controller）**是硬件中负责管理中断请求的组件，它通常会决定哪些中断请求具有较高的优先级，以及何时处理这些请求。
- **优先级管理**：中断控制器会根据中断请求的优先级来决定中断的处理顺序。高优先级的中断会打断低优先级的中断处理程序。
- **中断屏蔽**：某些系统允许中断嵌套时暂时屏蔽低优先级中断，确保高优先级中断不会被打断。

**中断向量表**

- **中断向量表**包含了每个中断类型对应的ISR的地址。当CPU接收到一个中断请求时，它会通过查找中断向量表找到相应的ISR并跳转到该地址。
- **嵌套中断**时，CPU会根据中断控制器的优先级管理机制选择合适的ISR执行。

**保存和恢复上下文**

- **上下文保存**：在进入中断服务程序时，CPU会保存当前的上下文，包括程序计数器（PC）、寄存器内容、堆栈指针等。这样，当中断服务程序执行完成后，能够恢复到原来的状态。
- **嵌套上下文**：在发生更高优先级的中断时，CPU会再次保存当前上下文（即嵌套上下文），并在高优先级中断执行完成后，恢复较低优先级中断的上下文。

**中断嵌套标志和屏蔽**

- **中断屏蔽**：一些CPU架构提供中断嵌套时的屏蔽机制。在处理中断时，如果没有启用中断嵌套，CPU会屏蔽所有其他中断，直到当前ISR执行完毕。这可以通过设置中断屏蔽寄存器来控制。
- **中断嵌套标志**：某些系统提供标志位来管理中断嵌套的行为。系统可以配置是否允许嵌套中断以及嵌套的优先级。

### 4.23.3 软件支持中断嵌套

虽然硬件提供了基础支持，软件层面的中断嵌套管理同样至关重要。操作系统或固件需要通过以下方式来协调和控制中断嵌套：

**嵌套中断的启用与禁用**

- **禁用中断**：在一些情况下，程序可能需要禁用中断，以保证某些重要操作的原子性。这通常是通过全局禁用中断或禁止特定类型的中断来实现的。
- **启用中断**：允许系统响应中断。操作系统或驱动程序可能通过一些函数或中断管理器来配置是否允许中断嵌套。

**中断服务程序中的临界区**

- **临界区**：在中断服务程序中访问共享资源时，应使用架构/驱动允许的短临界区、原子操作或自旋锁等非睡眠机制；不能在 ISR 中获取会睡眠的普通互斥锁，任务与 ISR 的通信通常使用中断安全 API 或延后处理。
- **中断服务程序中的栈保护**：由于嵌套中断可能会导致栈的过深嵌套，操作系统可能需要在每个ISR入口和退出时维护堆栈保护，防止栈溢出。

### 4.23.4 中断嵌套的优缺点

**优点：**

- **提高实时性**：通过中断嵌套，优先级更高的中断可以迅速得到处理，增强系统的响应能力和实时性。
- **减少延迟**：高优先级中断的及时处理能够减少系统的延迟，尤其是在实时应用中非常重要。

**缺点：**

- **增加复杂度**：中断嵌套增加了系统的复杂性，特别是中断的管理、上下文切换和栈管理。
- **栈溢出的风险**：嵌套中断可能导致栈的深度不断增加，增加栈溢出的风险，特别是在ISR的栈空间有限的情况下。
- **调试困难**：中断嵌套增加了调试的难度，因为它可能使系统行为更加不可预测，尤其是当中断依赖于外部事件时。

### 4.23.5 总结

中断嵌套是通过硬件和软件的协调实现的，允许高优先级中断打断低优先级中断的处理。硬件通过中断控制器、优先级管理和上下文保存/恢复机制支持中断嵌套，而软件层则通过中断禁用和启用、栈管理等手段协调这些中断的处理。中断嵌套能够提高实时系统的响应能力，但也增加了系统的复杂性和栈溢出的风险。

## 4.24 实时进程和普通进程的区别

在操作系统中，进程根据其对时间要求的不同可以分为两类：**实时进程**和**普通进程**。这两类进程在调度策略、优先级、执行保证等方面有显著的区别。

### 4.24.1 实时进程（Real-Time Process）

实时进程是指那些对执行时间和响应时间有严格要求的进程。实时进程必须在规定的时间内完成任务，否则可能导致系统的不稳定或故障。实时进程通常出现在嵌入式系统、控制系统、工业自动化等需要及时响应的应用场景。

**实时进程的特点**

- **时间限制**：实时进程有明确的时间限制（Deadline），需要在规定的时间内完成任务，否则可能造成灾难性的后果。例如，飞行控制系统、汽车安全气囊等。
- **优先级**：实时进程通常具有比普通进程更高的优先级，调度器在执行时会优先考虑这些进程。
- **确定性**：实时进程要求有较好的确定性，调度行为必须是可预测的，不容忍延迟。

**实时进程的类型**

- **硬实时进程**：必须在严格的时间限制内完成任务，不能有任何超时。例如医疗设备的实时数据处理。
- **软实时进程**：尽管对时间的要求较高，但偶尔的超时是可以容忍的。例如视频流处理、音频播放等。

**实时进程调度策略**

- **SCHED_FIFO**：先到先服务策略；在满足权限、调度配置和可运行条件时，高优先级实时线程通常先于低优先级线程运行，但不等于应用 deadline 的硬保证。
- **SCHED_RR**：在同一实时优先级内轮询调度；时间片长度和具体行为由内核实现/配置决定，高优先级线程仍可抢占低优先级线程。
- **SCHED_DEADLINE**：按运行时间、周期和截止时间参数调度，并受带宽/准入控制约束；它提供调度目标，不等于脱离系统分析后的硬实时保证。

### 4.24.2 普通进程（Non-Real-Time Process）

普通进程是指那些没有严格时间限制的进程。它们可以在任何时间被操作系统调度执行，且没有像实时进程那样对执行时间有严格的要求。

**普通进程的特点**

- **无时间限制**：普通进程没有时间限制，只要进程能按时完成任务，系统会按照资源空闲的情况调度它们。
- **较低的优先级**：普通进程通常优先级较低，除非调度器设置了更高的优先级，否则在系统忙碌时可能会被延迟执行。
- **动态调度**：普通进程的调度不需要满足确定性要求，可以由操作系统根据系统负载和优先级等因素动态决定。

**普通进程调度策略**

- **SCHED_OTHER/SCHED_NORMAL**（默认策略）：普通进程的默认调度策略；传统内核主要由 CFS 实现，较新内核可能采用 EEVDF 等 fair-class 实现，按权重分配 CPU，不提供硬实时响应保证。
- **SCHED_BATCH**：适用于需要长时间运行但对响应时间不敏感的批处理任务。

### 4.24.3 实时进程与普通进程的主要区别

| 维度 | 实时进程 | 普通进程 |
|---|---|---|
| 目标 | 尽量满足优先级、周期或截止时间约束 | 在公平性和吞吐量之间取得平衡 |
| Linux 调度策略 | `SCHED_FIFO`、`SCHED_RR`、`SCHED_DEADLINE` 等 | `SCHED_OTHER`、`SCHED_BATCH`、`SCHED_IDLE` 等 |
| 抢占关系 | 高优先级实时任务可压过普通任务 | 由普通调度器按虚拟运行时间等因素选择 |
| 风险 | 可能长期占用 CPU，导致普通任务饥饿 | 不提供硬实时截止时间保证 |
| 适用场景 | 控制环、音视频时间约束、采集处理 | 后台服务、批处理、交互式一般任务 |

Linux 的实时调度策略只能提供调度层面的优先级和延迟改善，不等于整个应用具备硬实时保证；中断、锁、缺页、设备驱动和系统配置仍会影响最坏响应时间。

### 4.24.4 总结

实时调度策略能改善优先级和截止时间模型下的调度行为，但不自动提供硬实时保证；最终响应时间还取决于执行时间、阻塞、缺页、中断、驱动和系统配置。

## 4.25 线程之间的同步机制

### 4.25.1 为什么需要线程同步

- 多线程**共享同一进程地址空间**
- 并发访问共享资源会产生：
    - 数据竞争
    - 读写不一致
    - 崩溃或逻辑错误

**同步机制用于保证临界区访问的正确性和一致性。**

### 4.25.2 常见线程同步机制

**（1）互斥锁（Mutex）**

- 保证同一时刻只有一个线程访问临界区

```c
pthread_mutex_lock(&mutex);
/* 临界区 */
pthread_mutex_unlock(&mutex);
```

特点：

- 使用最广
- 适合保护共享资源

**（2）读写锁（Read-Write Lock）**

- 多个读者可并发
- 写者互斥

```c
pthread_rwlock_rdlock(&rwlock);
pthread_rwlock_wrlock(&rwlock);
```

适用场景：

- 读多写少

**（3）条件变量（Condition Variable）**

- 用于线程间**事件通知**
- 常与互斥锁配合使用

```c
pthread_cond_wait(&cond, &mutex);
pthread_cond_signal(&cond);
```

特点：

- 避免忙等
- 实现生产者-消费者模型

**（4）信号量（Semaphore）**

- 基于计数的同步机制

```c
sem_wait(&sem);
sem_post(&sem);
```

特点：

- 可实现互斥或资源计数
- 支持多线程/多进程

**（5）自旋锁（Spinlock）**

- 忙等锁，不让出 CPU

```c
pthread_spin_lock(&spin);
```

特点：

- 临界区极短
- 适合多核系统

**（6）原子操作（Atomic）**

- 硬件级别保证操作不可分割

```cpp
std::atomic<int> cnt;
cnt++;
```

特点：

- 无锁
- 适合简单变量操作

### 4.25.3 同步机制对比

| 机制 | 主要作用 | 是否带所有权 | 是否可能阻塞 | 适用场景 |
|---|---|---|---|---|
| 互斥锁 | 保护临界区和共享数据 | 通常有，持有者解锁 | 是 | 同一进程内的互斥访问 |
| 条件变量 | 等待某个共享条件变化 | 无，通常与互斥锁配合 | 是 | 生产者-消费者、状态等待 |
| 信号量 | 计数和同步资源数量 | 通常无 | 是 | 资源池、事件计数 |
| 读写锁 | 多读者或单写者 | 有读/写模式 | 是 | 读多写少的数据结构 |
| 原子操作 | 对单个变量执行不可分割操作 | 无 | 通常不阻塞 | 计数器、标志位和无锁算法 |
| 屏障 | 等待一组线程到达同一阶段 | 无 | 是 | 分阶段并行计算 |

同步不等于“把所有代码都加锁”。应缩短临界区，明确锁的顺序，并用 `while` 重新检查条件变量，防止虚假唤醒和条件变化导致的竞态。

### 4.25.4 总结

> 线程同步常用互斥锁、条件变量、信号量和原子操作，选择取决于临界区长度和并发需求。

> 同步的本质是控制对共享资源的访问顺序。

## 4.26 进程之间的通信IPC，Inter-Process Communication

### 4.26.1 为什么需要进程间通信

- 进程**地址空间相互隔离**
- 无法直接访问彼此内存
- 必须通过 **操作系统提供的 IPC 机制** 交换数据或同步

### 4.26.2 常见 IPC 通信方式

**（1）管道（Pipe）**

- **匿名管道** 通常按半双工使用；最常见是由 `fork()` 继承给有亲缘关系的进程，也可以通过 Unix 域 socket 等方式传递文件描述符给无亲缘关系进程

```c
pipe(fd);
```

特点：

- 简单
- 通信方向固定
- **命名管道（FIFO）** 有文件名；可用于无亲缘关系进程

```c
mkfifo("myfifo", 0666);
```

**（2）信号（Signal）**

- 用于**事件通知**
- 不能传递大量数据

```c
kill(pid, SIGUSR1);
```

**（3）消息队列（Message Queue）**

- 内核维护的消息链表
- 支持结构化消息

特点：

- 异步通信
- 消息有边界

**（4）共享内存（Shared Memory）**

- 多个进程映射同一块物理内存

```c
shmget();
shmat();
```

特点：

- **速度最快**
- 需要额外同步机制（信号量/互斥锁）

**（5）信号量（Semaphore）**

- 主要用于**进程同步**
- 常配合共享内存使用

**（6）Socket（套接字）**

- 最通用 IPC 方式
- 可跨主机通信

```c
socket();
bind();
send();
recv();
```

### 4.26.3 IPC 方式对比

| 机制 | 数据模型 | 性能/拷贝 | 适用场景 | 主要注意点 |
|---|---|---|---|---|
| 匿名管道 | 字节流，通常有亲缘关系 | 内核缓冲，简单可靠 | 父子进程流水线 | 单向、容量有限 |
| FIFO | 字节流，无需亲缘关系 | 内核缓冲 | 本机无亲缘进程通信 | 读写端打开时可能阻塞 |
| 消息队列 | 有边界的消息 | 内核管理消息 | 命令、事件、优先级消息 | 消息大小和队列上限 |
| 共享内存 | 共享地址区 | 大量数据可减少拷贝 | 高频大块数据 | 必须另配同步机制 |
| 信号 | 异步事件通知 | 不适合携带大量数据 | 终止、重载、简单通知 | 异步信号安全限制 |
| socket | 字节流或报文 | 本机/跨主机均可 | 服务间通信、网络服务 | 协议、缓冲和错误处理 |

共享内存通常吞吐最高，但并不自动保证一致性；socket 最通用，但本机 socket 也有系统调用、缓冲和协议开销。

### 4.26.4 总结

> 进程通信依赖 IPC 机制，包括管道、共享内存、消息队列、信号和 socket，各有性能与使用场景。

> 进程不共享内存，通信必须借助内核。

## 4.27 死锁与活锁

### 4.27.1 死锁（Deadlock）

- **定义：** **死锁**指的是在多线程或多进程环境中，多个进程或线程由于相互等待对方释放资源而永远不能继续执行的情况。

**死锁的四个必要条件**

1. **互斥条件**：至少有一个资源必须处于**非共享模式**，即每次只有一个线程/进程可以使用该资源。
2. **请求与保持条件**：一个线程已经持有某些资源，但又申请其他资源，这些资源被其他线程持有。
3. **不剥夺条件**：已经分配给线程的资源在没有使用完之前不能被强制剥夺。
4. **循环等待条件**：多个线程形成一个环形的资源请求链，每个线程都在等待下一个线程持有的资源。

**死锁的典型示例**

```c
// 进程A
lock(resource1);
lock(resource2);

// 进程B
lock(resource2);
lock(resource1);
```

此时，**进程A**持有resource1并请求resource2，**进程B**持有resource2并请求resource1，两者互相等待，造成死锁。

**死锁的解决方法**

- **预防死锁**：破坏死锁的一个或多个必要条件（如破坏循环等待）。
- **避免死锁**：采用资源分配算法（如银行家算法）动态决定是否分配资源。
- **检测与恢复**：定期检查系统中是否有死锁发生，并采取措施恢复（如强制终止一个进程）。

### 4.27.2 活锁（Livelock）

- **定义：** **活锁**是指线程或进程在不断地改变状态以响应其他线程的请求，但没有进展，系统中虽然没有死锁的“锁定”，但资源没有得到有效利用，程序无法继续执行。
- **活锁与死锁的区别**：**死锁**是执行流停在相互等待状态；**活锁**是执行流不断改变状态或重试，但没有完成有效工作。

**活锁的典型示例**

```c
// 进程A
while (resource_locked) {
    // 尝试释放资源并等待
    release(resource);
    wait(1);
}

// 进程B
while (resource_locked) {
    // 尝试释放资源并等待
    release(resource);
    wait(1);
}
```

进程A和进程B一直在释放资源并等待，但永远没有进展，造成活锁。

- **活锁的解决方法**：限制重试次数或设置超时；使用随机/指数退避打破同步重试；必要时记录进度并转入失败处理。

### 4.27.3 死锁与活锁的对比

| 维度 | 死锁 | 活锁 |
|---|---|---|
| 状态变化 | 线程/进程停在等待状态 | 不断运行、重试或让步 |
| 是否取得进展 | 没有 | 表面活跃但没有有效进展 |
| 典型原因 | 循环等待、持有并等待、资源不可抢占 | 同步退避策略相同、反复让步或冲突 |
| 常用检测 | 等待图、锁依赖分析、超时 | 进度指标、重试计数和吞吐监控 |
| 常用处理 | 固定加锁顺序、超时、避免嵌套锁 | 随机退避、指数退避、限制重试次数 |

死锁和活锁都不是“操作系统一定会自动杀掉”的错误。应在设计层面避免，并在运行时记录等待时间、持锁线程和重试次数。

### 4.27.4 总结

> 死锁是进程相互等待资源，无法继续执行；活锁是进程不断改变状态但没有进展，都会导致系统资源未被有效利用。

> 死锁导致资源永远无法释放，活锁则让进程在空转，二者都影响系统正常运行。

## 4.28 中断上下文中能否使用互斥锁？

**在中断上下文中使用互斥锁**通常是**不推荐**的，这会导致**死锁**、**不可预测的行为**以及**系统性能下降**。

### 4.28.1 中断上下文的特点

- **中断上下文**是指处理器在处理外部硬件中断时的执行环境。此时，CPU 中断当前正在执行的进程，并进入中断处理程序。
- 在中断上下文中，通常不允许执行 **阻塞操作**，因为中断处理程序必须尽快完成并返回，避免影响系统实时性。
- 中断处理程序通常是非常简洁和快速的，且执行期间不能被其他中断中断（除非中断被设置为更高优先级）。
- 在中断上下文中，线程的状态是 **不可切换的**，所以无法像普通任务上下文中那样进行线程调度。

### 4.28.2 互斥锁的工作原理

- **互斥锁**的设计目的是确保同一时刻只有一个线程能够访问临界区。
- 当一个线程尝试获取已被其他线程持有的互斥锁时，它会进入 **阻塞状态**，直到锁被释放。这意味着如果一个线程在持有锁时被中断，而另一个线程试图获取该锁，就会导致死锁或阻塞，造成系统停滞。

### 4.28.3 为什么中断上下文不能使用互斥锁

- **阻塞行为**：当中断服务程序尝试获取互斥锁时，如果锁已经被占用，当前中断会被 **阻塞**，等待锁的释放。这与中断的设计目标相悖。中断处理程序必须迅速完成，而互斥锁会引入不必要的延迟和阻塞。
- **死锁风险**：如果在中断上下文中使用互斥锁，而且该锁已经被一个线程持有，并且该线程也可能在处理中断时请求同一个锁，就可能导致 **死锁**。即线程和中断相互等待，永远无法继续执行。
- **不可重入**：许多操作系统内核会禁止在中断上下文中调用可能会导致调度的函数（如加锁）。因为中断上下文本身是 **非可重入** 的，一旦进入中断就不允许中断当前处理中断任务的执行。使用互斥锁可能会导致一些函数调用阻塞，从而破坏这个不重入的限制。

### 4.28.4 正确的做法

- **禁止在中断上下文中使用互斥锁**：为了避免阻塞和死锁风险，通常不在中断处理程序中使用互斥锁。如果需要保护共享资源，可以采用其他机制，如 **原子操作** 或 **中断禁用**。
- **原子操作**：对于一些简单的操作，可以使用硬件提供的 **原子操作**（如自增、自减、位运算等），这些操作通常不会引发阻塞，也不会影响中断的执行。
- **禁用中断**：在中断上下文中保护共享资源时，可以选择禁用中断来避免中断之间的竞争条件。这种方法通常用于 **短时间内** 防止其他中断打断当前处理逻辑，但要避免长时间禁用中断，以免影响系统的实时响应性。
- **中断上下文专用锁**：一些操作系统提供了专门用于中断上下文的锁（例如禁用和恢复中断的标志位），这种锁是设计来避免阻塞和死锁的。

### 4.28.5 总结

因此，在中断上下文中使用互斥锁是非常危险的，推荐使用不阻塞的同步机制如 **原子操作** 或 **中断禁用** 来避免中断上下文中的资源竞争问题。

## 4.29 互斥锁与自旋锁的区别(互斥锁优缺点、自旋锁优缺点)

### 4.29.1 基本概念

- **互斥锁（Mutex）** 线程获取不到锁时 **进入阻塞状态**；由操作系统调度唤醒；常用于用户态线程同步
- **自旋锁（Spinlock）** 获取不到锁时 **忙等（自旋）**；不会进入睡眠，不释放 CPU；常用于内核态或极短临界区

### 4.29.2 互斥锁 vs 自旋锁

| 维度 | 互斥锁 | 自旋锁 |
|---|---|---|
| 获取失败 | 线程睡眠并让出 CPU | 原地循环等待 |
| 临界区 | 可相对较长，但不能无限持有 | 应非常短 |
| 上下文 | 允许睡眠的线程上下文 | 常用于不能睡眠或极短临界区 |
| CPU 消耗 | 竞争时较低 | 竞争时持续占用 CPU |
| 中断关系 | 不能在会睡眠的中断路径使用 | 需使用平台提供的中断安全版本并正确保存标志 |
| 主要风险 | 睡眠/唤醒和优先级反转 | 忙等浪费 CPU、死锁和锁顺序错误 |

Linux 用户态 `pthread_mutex_t` 和内核 `spinlock_t` 不是同一 API。自旋锁并不天然“更快”，只有等待时间短且睡眠不可行时才有优势；多核系统还要考虑缓存一致性和内存序。

### 4.29.3 互斥锁的优缺点

**优点：**

1. **节省 CPU 资源**
2. 适合 **临界区较长** 的场景
3. 编程模型简单、易用

**缺点：**

1. **上下文切换开销**
2. 频繁加锁/解锁性能下降
3. 不适合短时间高频竞争

### 4.29.4 自旋锁的优缺点

**优点：**

1. **无上下文切换**
2. 加锁/解锁速度快
3. 适合 **短临界区**

**缺点：**

1. **浪费 CPU**
2. 单核系统意义不大
3. 临界区长会严重拖慢系统

### 4.29.5 使用建议（面试常问）

- **临界区短 + 多核 → 自旋锁**
- **临界区长 + 用户态 → 互斥锁**
- 不确定时，优先选择 **互斥锁**

### 4.29.6 总结

> 互斥锁阻塞等待，节省 CPU；自旋锁忙等不切换，适合短临界区。

> 时间换空间用自旋，空间换时间用互斥。

## 4.30 什么是临界区？

**临界区**（Critical Section）是指在多线程或多进程程序中，**多个线程或进程共享的资源**（如全局变量、文件、设备等）在同一时刻只允许**一个线程或进程**访问的代码区域。进入临界区的线程需要确保其他线程在此时不能同时访问共享资源，否则可能会导致数据竞争（Data Race）或资源的不一致性。

### 4.30.1 临界区的特点

- **共享资源**：临界区涉及的资源是多个线程或进程共享的，因此可能会被多个线程或进程同时访问。
- **互斥访问**：为了保证共享资源的一致性和正确性，临界区中的代码段必须保证在同一时刻只允许一个线程或进程访问。
- **线程安全**：在临界区内执行的代码必须是线程安全的，否则多个线程并发执行时可能会引发不确定的行为。

### 4.30.2 为什么需要临界区

在多线程或多进程编程中，多个线程或进程可能同时访问共享资源。如果多个线程在没有任何控制的情况下同时修改资源，会导致以下问题：

- **数据不一致性**：不同线程同时读写共享资源可能会导致数据不一致，最终结果无法预测。
- **竞态条件**：两个或更多线程并发执行时，操作的结果依赖于它们的执行顺序，若无法保证线程间的执行顺序，可能导致错误的结果。

通过使用临界区，可以保证在同一时刻只有一个线程访问共享资源，从而避免数据竞争和保证数据一致性。

### 4.30.3 如何保护临界区

为了防止多个线程同时访问临界区，通常会使用以下同步机制来保证互斥访问：

- **互斥锁（Mutex）**：通过加锁和解锁确保同一时刻只有一个线程访问临界区；进入前获取锁，退出后释放锁。示例：

```cpp
std::mutex mtx;  // 定义互斥锁

void thread_function() {
    std::lock_guard<std::mutex> lock(mtx);  // 自动加锁
    // 临界区：对共享资源的操作
}  // 离开作用域后自动释放锁
```

- **信号量（Semaphore）**：用计数控制可同时进入某类资源的执行流数量；它不表达资源所有权，因此不能直接等同于互斥锁。
- **读写锁（Read-Write Lock）**：允许多个线程并发读取，写入时通常要求独占；公平性和读写优先级由实现决定。
- **自旋锁（Spinlock）**：获取不到锁时忙等，不主动睡眠，适合极短临界区或不能睡眠的上下文；持锁过久会浪费 CPU。

### 4.30.4 临界区的常见问题

尽管临界区提供了对共享资源的保护，但不当使用会引发一些常见的同步问题：

**死锁（Deadlock）**

- **死锁**发生在多个线程或进程相互等待对方释放锁时，从而导致所有线程都无法继续执行。
- 死锁通常发生在程序的多个临界区中，线程在进入第一个临界区时获得了一个锁，然后试图进入第二个临界区并等待第二个锁，而此时另一个线程正持有第二个锁并等待第一个锁。
- **活锁（Livelock）** **活锁**是指两个或更多线程虽然不再死锁，但它们总是处于不断的状态变化中，无法完成实际的任务，导致资源无法得到有效利用。
- **优先级反转（Priority Inversion）**：低优先级线程持有锁时，高优先级线程因等待该锁而阻塞；若中优先级线程抢占持锁者，高优先级线程会被间接延迟。

**性能问题**

- **锁竞争**：多个线程竞争同一锁时，可能导致性能问题，特别是在高并发场景下。过多的锁操作可能会导致较高的上下文切换开销。
- **死锁检测和避免**：死锁的发生需要特殊的设计来避免和检测。过度复杂的同步设计可能增加调试和维护难度。

### 4.30.5 总结

临界区是多线程和多进程编程中保证共享资源安全性的重要概念。合理设计和使用临界区以及合适的同步机制，可以有效地避免并发问题，提高程序的稳定性和效率。

## 4.31 线程同步与互斥

### 4.31.1 基本概念

- **互斥（Mutual Exclusion）**：目的在于防止多个线程同时访问共享资源；关注谁能进入临界区，核心是避免数据竞争。
- **同步（Synchronization）**：目的在于控制线程执行的先后顺序；关注线程何时执行，核心是建立协作关系。

> **互斥是同步的一种，但同步不一定是互斥。**

### 4.31.2 互斥的典型方式

- 互斥锁（Mutex）
- 自旋锁（Spinlock）
- 原子操作（Atomic）

示例：

```c
pthread_mutex_lock(&mutex);
/* 访问共享资源 */
pthread_mutex_unlock(&mutex);
```

### 4.31.3 同步的典型方式

- 条件变量（Condition Variable）
- 信号量（Semaphore）
- 屏障（Barrier）

示例（条件变量）：

```c
pthread_mutex_lock(&mutex);
while (!ready) {
    pthread_cond_wait(&cond, &mutex);
}
pthread_mutex_unlock(&mutex);
```

### 4.31.4 同步 vs 互斥对比

| 概念 | 关注点 | 典型问题 | 常用工具 |
|---|---|---|---|
| 互斥 | 同一时刻谁能访问资源 | 多线程同时改同一数据 | 互斥锁、临界区、自旋锁 |
| 同步 | 不同执行流的先后顺序和条件 | 线程何时继续、何时等待 | 条件变量、信号量、屏障、事件 |

互斥可以是同步的一部分，但两者不是同义词。互斥锁保护“不能同时做”，条件变量表达“条件未满足先等待”；条件变量本身不保护共享数据，必须和互斥锁配合。

### 4.31.5 常见组合使用

- **互斥锁 + 条件变量**
    - 互斥：保护共享数据
    - 同步：等待条件满足

经典模型：

- 生产者-消费者

## 4.32 线程同步与阻塞的关系

线程同步和阻塞是两个独立但常常一起出现的概念，尤其是在多线程编程中。它们虽然相关，但有着不同的含义和应用场景。“同步一定阻塞吗？”和“阻塞一定同步吗？

### 4.32.1 线程同步

线程同步是指在多线程环境下，多个线程需要共享某些资源时，为了避免竞争条件（race conditions）和数据不一致性，需要采取措施确保 **同时只有一个线程能够访问共享资源**。同步机制的目标是确保 **不同线程之间的协作**，而不是阻止其他线程的执行。

**常见的线程同步机制：**

- **互斥锁（Mutex）**：保护共享资源，使得同一时刻只有一个线程可以访问。
- **读写锁（RWLock）**：允许多个线程并发读取，但写操作时只有一个线程可以访问。
- **条件变量（Condition Variable）**：用于线程间的通知机制，等待某些条件满足后才能继续执行。
- **信号量（Semaphore）**：控制多个线程对资源的访问，适用于限制访问数量。

### 4.32.2 线程阻塞

线程阻塞是指一个线程在某些条件下无法继续执行，通常是因为等待某个资源或条件变得可用。阻塞发生时，线程 **被挂起，直到特定条件满足**，之后才会恢复执行。阻塞是操作系统用来控制多线程行为的一种机制。

**常见的阻塞情况：**

- **等待锁**：一个线程在获取锁时，若该锁已被其他线程持有，当前线程会被阻塞，直到锁可用。
- **等待条件**：当线程通过条件变量等待某个条件满足时，它会被阻塞。
- **I/O 阻塞**：线程在执行 I/O 操作时（如读取文件、等待网络响应），如果数据尚未准备好，线程可能会被阻塞，直到 I/O 操作完成。

### 4.32.3 同步与阻塞的关系

- **同步可能会导致阻塞**：在同步的场景中，线程需要等待获取资源（如锁），因此可能会被阻塞。例如，如果多个线程都需要访问同一个共享资源，而只有一个线程能够访问该资源时，其他线程可能会被阻塞，直到当前线程释放资源。
- **阻塞不一定是同步**：阻塞和同步的目的不同。阻塞的目的是让线程等待某些条件（如等待I/O完成），而同步的目的是保证数据的一致性。在某些情况下，线程可能被阻塞，但不涉及任何同步机制。例如，当线程等待某些外部事件（如网络数据），它可能会被阻塞，但并没有涉及共享资源的同步。

### 4.32.4 同步一定阻塞吗？

**答案：** 不一定。

- **同步可能导致阻塞，但不一定**。线程同步的目的就是协调多个线程对共享资源的访问，保证资源的互斥性。虽然这通常会导致线程阻塞（例如，一个线程等待获取锁），但并不是所有同步操作都会导致阻塞。
    - **非阻塞同步**：有些同步机制允许线程在同步过程中不阻塞，例如使用 **自旋锁（Spinlock）**，即线程不断地尝试获取锁，而不进入阻塞状态。如果锁已经被占用，线程会一直轮询，而不是被挂起（阻塞）。这种方式虽然有同步，但没有阻塞。
- **异步执行和同步分开**：例如，通过 **条件变量** 和 **事件通知机制**，线程可以在等待同步条件时进入休眠状态，直到条件满足再继续执行，但这不一定意味着线程会一直阻塞，它们可以在同步完成之前进行其它操作。

### 4.32.5 阻塞一定同步吗？

**答案：** 不一定。

- **阻塞和同步是不同的概念**，阻塞不一定与同步有关。阻塞只是线程等待某个条件或资源可用的状态，而同步是确保多个线程正确访问共享资源的机制。阻塞并不总是为了同步目的而存在。
    - **无同步的阻塞**：线程也可能因为等待某些外部事件或I/O操作（例如，等待用户输入、读取文件等）而阻塞，但这些操作与线程之间的资源共享和同步无关。例如，线程在等待网络响应时被阻塞，虽然它处于阻塞状态，但并不涉及同步问题。
    - **同步的阻塞**：同步通常会涉及阻塞，尤其是当多个线程需要依次访问共享资源时。例如，当线程试图获取已经被其他线程占用的锁时，线程会被阻塞，直到锁可用，这就是同步导致的阻塞。

### 4.32.6 实际应用中的场景

1. **阻塞的同步**：
    - 线程在访问共享资源时通过互斥锁进行同步，若锁已被占用，线程会被阻塞，直到可以访问资源。
    - 使用条件变量进行线程同步，线程可能会因等待条件的满足而阻塞。
2. **非阻塞的同步**：
    - 使用自旋锁时，线程会不断地轮询获取锁，而不是被完全挂起。虽然这是一种同步机制，但线程不进入阻塞状态。
3. **无同步的阻塞**：
    - 线程等待外部事件（如网络响应或文件读取），这类阻塞不涉及线程之间的同步问题，只是等待外部事件的完成。

通过合理使用同步机制和阻塞策略，可以提高多线程程序的效率和可靠性。

### 4.32.7 总结

阻塞描述线程当前是否等待资源或事件，同步描述并发访问的顺序和可见性；二者可以同时出现，也可以分别出现。选择同步机制时应结合是否允许睡眠、临界区长度和实时性要求。

## 4.33 互斥量能否在进程中使用

### 4.33.1 背景

- **互斥量（Mutex）通常用于线程间互斥**，即同一进程内的多线程共享资源时使用
- **进程间默认互斥量不可共享**，因为每个进程有独立地址空间

### 4.33.2 进程间互斥量实现方式

**（1）POSIX 共享互斥量**

- 将互斥量放在**共享内存**中
- 使用 pthread_mutexattr_setpshared 属性设置可跨进程共享

示例：

```c
pthread_mutexattr_t attr;
pthread_mutex_t *mutex;

pthread_mutexattr_init(&attr);
pthread_mutexattr_setpshared(&attr, PTHREAD_PROCESS_SHARED);

mutex = mmap(NULL, sizeof(pthread_mutex_t),
             PROT_READ | PROT_WRITE,
             MAP_SHARED | MAP_ANONYMOUS, -1, 0);

pthread_mutex_init(mutex, &attr);
```

- **前提**：互斥量存放在共享内存区域
- **效果**：不同进程可以通过该互斥量同步访问共享资源

**（2）System V 机制**

- 使用 **信号量（Semaphore）** 实现进程间互斥
- 通常用在老系统或多进程同步

### 4.33.3 注意事项

1. **普通互斥量仅限同一进程线程**
2. **跨进程互斥量必须放共享内存**
3. **初始化属性必须设置 **PROCESS_SHARED

### 4.33.4 总结

> 互斥量默认线程内使用，进程间使用需要放在共享内存并设置 PROCESS_SHARED 属性。

> 进程间也能用互斥量，但必须显式声明为可共享并放在共享内存中。

## 4.34 并发、同步、异步、互斥、阻塞、非阻塞的理解

### 4.34.1 并发（Concurrency）

- **定义**：同一时间段内，有多个任务交替执行
- **特点**：
    - 多线程、多进程在单核上交替执行
    - 多核可同时运行
- **示例**：CPU 上同时跑多个线程处理不同请求

### 4.34.2 同步（Synchronous）

- **定义**：调用者必须等待任务完成后才能继续执行
- **特点**：
    - 顺序执行
    - 线程或进程等待结果
- **示例**：

```c
int result = read(fd, buf, size);  // 阻塞，等待完成
```

### 4.34.3 异步（Asynchronous）

- **定义**：调用者发起任务后无需等待，可继续执行其他操作
- **特点**：
    - 任务完成后通过回调、信号或事件通知
- **示例**：

```c
aio_read(...);  // 异步 I/O
```

### 4.34.4 互斥（Mutual Exclusion）

- **定义**：保护共享资源，防止多线程/进程同时访问
- **特点**：
    - 关注“能否同时访问”
    - 常用机制：互斥锁、信号量、自旋锁

### 4.34.5 阻塞（Blocking）

- **定义**：调用操作无法立即完成时，**调用线程被挂起，等待条件满足再继续**
- **特点**：
    - 会让出 CPU
    - 典型操作：阻塞 I/O、互斥锁等待

### 4.34.6 非阻塞（Non-blocking）

- **定义**：调用操作立即返回，不管任务是否完成
- **特点**：
    - 调用线程不会被挂起
    - 可能返回错误码表示未完成
- **示例**：

```c
fcntl(fd, F_SETFL, O_NONBLOCK);
read(fd, buf, size);  // 若无数据立即返回
```

### 4.34.8 总结

> 并发关注执行顺序，异步关注是否等待完成，互斥关注资源独占，阻塞会挂起，非阻塞立即返回。

> 并发是“同时做多件事”，同步/异步是“等不等”，互斥是“谁先用”，阻塞/非阻塞是“等不等 CPU”。

## 4.35 fork() 之后父子进程的内存变化

fork() 是一个系统调用，用于创建一个新的进程（子进程），该子进程是当前进程（父进程）的副本。虽然父子进程在 fork() 之后的内存内容初始时几乎相同，但在实现上，操作系统会进行一定的优化，特别是通过 **写时复制（Copy-On-Write, COW）** 技术，避免了对内存的完全复制。下面将详细讲解 fork() 之后父子进程的内存变化过程。

### 4.35.1 fork() 调用的内存变化

当调用 fork() 时，操作系统会为子进程分配新的地址空间，并将父进程的地址空间复制给子进程。但这并不意味着每个字节都被复制，而是通过 **写时复制** 技术优化了内存分配。

**写时复制（COW）**

- **COW（Copy-On-Write）** 技术是一种优化内存复制的方法。fork() 后，父子进程的地址空间最初是共享的。父进程和子进程都指向相同的物理内存页面，直到其中一个进程试图修改共享内存时，操作系统才会为该页面创建一个新的副本。
- 这种方式有效地减少了内存的开销，只有在写操作发生时，才会真正进行复制，这样就避免了不必要的内存开销。

**父子进程的内存映射**

- 在 fork() 后，父进程和子进程拥有相同的虚拟地址空间映射，但它们的物理内存页面最初是共享的。
- 这种共享是透明的，父进程和子进程的操作系统内核会在内部处理。
- 在写入操作之前，父子进程之间共享相同的物理页面。只有当父进程或子进程尝试修改内存中的数据时，操作系统才会为该页面创建新的副本（这就是 COW）。

### 4.35.2 内存分配和 COW 的流程

假设有如下的父进程和子进程创建过程：

1. **父进程调用 **fork()：
    - 操作系统为子进程分配一个新的进程表和内存页表，指向父进程的相同物理内存页面。
    - 子进程的栈、堆、数据段、BSS 段等最初与父进程共享。
    - 父子进程的地址空间是相同的，但父子进程的内存页面是共享的。
2. **父进程和子进程开始执行**：
    - 在子进程执行期间，它并不会立即修改父进程的内存，父进程和子进程共享同一块内存区域。
    - 只有当父进程或子进程尝试修改共享内存时，操作系统会为它们分配新的内存页面，并复制数据。
3. **修改时发生 COW**：
    - 例如，如果父进程修改了某个共享的内存页，操作系统就会为该内存页创建一份新的副本，父进程和子进程分别修改各自的副本。
    - 此时，父子进程的内存会发生“分离”，不再共享同一内存区域。

### 4.35.3 父子进程的内存空间差异

虽然父进程和子进程在 fork() 后的内存内容完全一致，但它们有一些重要的区别：

**文件描述符**

- `fork()` 后父子进程各自拥有描述符表副本，但表项通常指向同一个 open file description，因此文件偏移、状态标志等可能共享；管道/套接字也有相应的共享内核对象语义。
- 如果需要独立偏移，应重新 `open()` 或使用明确的定位/同步策略，不能笼统说父子有各自独立文件指针。

**内存内容**

- 在父进程和子进程的内存中，所有的代码段和只读数据段是共享的。
- 对于可写数据（堆、栈等），它们一开始是共享的，直到某一方修改该区域时，操作系统才会为该区域分配新的物理内存，保证父子进程的内存独立。

**子进程的栈和堆**

- 子进程拥有自己独立的栈和堆空间。
- 子进程的栈通常是从父进程的栈拷贝过来的，但它有自己的栈空间，可以独立修改。
- 子进程的堆空间和父进程的堆空间分离，尽管它们在初始时共享内存，直到进行写操作时才会发生复制。

**内存分配机制**

- **父进程**：父进程的内存独立于子进程，对子进程的修改不会影响父进程。
- **子进程**：子进程的内存最初共享父进程的内存。只有在进行写操作时，操作系统才会为子进程分配新的内存副本。

### 4.35.4 总结

fork() 创建的父子进程在内存中最初是共享的，采用了写时复制（COW）技术，只有在父子进程修改共享内存时，才会进行内存的实际复制。这种机制有效减少了内存开销，提高了性能。在子进程执行后，它拥有独立的内存空间，父子进程的资源逐渐分离。

## 4.36 fork()、vfork()、clone() 的区别

在 Linux 和其他类 Unix 系统中，fork()、vfork() 和 clone() 是用于创建新进程的系统调用。它们的作用相似，但在实现和性能方面有所不同。下面将详细比较这三个系统调用的区别。

### 4.36.1 fork()

fork() 是最常用的系统调用之一，用于 **创建一个新的进程**。调用 fork() 后，当前进程（父进程）会被复制一份，生成一个新的进程（子进程）。子进程是父进程的一个拷贝，除了进程ID和父进程ID之外，其余内容几乎相同。

**特点：**

- **新进程**：调用 fork() 时，操作系统为新进程分配了独立的地址空间（包括栈、堆等）。
- **内存复制**：父进程的内存会被复制到子进程中。操作系统使用 **写时复制（Copy-On-Write, COW）** 技术来优化这一过程：父子进程最初共享相同的内存，只有在父进程或子进程修改内存时才会发生实际的复制。
- **资源独立性**：子进程拥有自己的独立资源，包括文件描述符、堆栈、地址空间等。
- **返回值**：
    - 在父进程中，fork() 返回子进程的 PID（进程ID）。
    - 在子进程中，fork() 返回 0。

- **使用场景：** 用于创建新的进程，通常与 exec() 函数一起使用来启动新程序。

**示例：**

```c
pid_t pid = fork();
if (pid == 0) {
```

**磁盘I/O**

每次缺页中断导致的磁盘I/O操作都相对较慢，因此频繁的缺页中断会增加系统的负载，导致程序运行缓慢。

### 4.36.2 vfork()

`vfork()` 的语义是让父进程暂时挂起，子进程在 `execve()` 或 `_exit()` 前与父进程共享地址空间。子进程在此期间不能像普通 `fork()` 子进程一样任意修改栈、返回调用函数或调用可能破坏父进程状态的函数。现代 Linux 中应优先使用 `fork()` 或 `posix_spawn()`；只有明确理解平台语义、并且立即 `exec` 时才考虑 `vfork()`。

### 4.36.3 clone()

`clone()` 是 Linux 特有的、更细粒度的创建任务接口，可通过标志选择是否共享地址空间、文件系统信息、文件描述符表、信号处理表等。例如 `CLONE_VM` 共享地址空间，`CLONE_FILES` 共享文件描述符表，`CLONE_THREAD` 参与同一线程组。它是 pthread 和容器运行时等机制的底层基础之一，但直接调用时必须正确设置栈、TLS、退出信号和资源回收。

| 调用 | 地址空间 | 资源共享粒度 | 常见用途 |
|---|---|---|---|
| `fork()` | 逻辑复制，通常 COW | 按 POSIX/Linux 继承规则 | 创建独立子进程 |
| `vfork()` | 临时与父进程共享 | 受严格语义限制 | 立即 `exec` 的优化路径 |
| `clone()` | 由 flags 决定 | 可逐项选择 | 线程、容器和运行时 |

### 4.36.4 总结

`fork()` 适合创建具有独立地址空间的子进程，`vfork()` 只适用于严格受限的立即 `exec`/`_exit` 路径，`clone()` 则按 flags 选择共享粒度。实际使用应优先采用更高层的 POSIX/Linux 接口，并遵守各自的继承和资源回收规则。

## 4.37 什么时候不建议使用多线程 / 多进程？

1. **CPU 计算密集型任务**（如大规模数学运算、图像处理、加密解密）。线程太多可能会导致频繁切换，增加调度开销，降低效率。适用于单线程或使用**异步非阻塞**模式优化。
2. **线程/进程管理成本过高。**线程切换有**开销**，太多线程反而可能拖慢速度。进程之间的**通信（IPC）比线程通信成本高**，如果任务简单，单线程更高效。

## 4.38 进程创造的数量与什么有关系

### 4.38.1 操作系统限制

不同的操作系统对一个进程能够创建的线程数有不同的限制。操作系统通过以下几个参数来控制线程数量：

**线程栈大小**

- 每个线程都有一个栈，栈用于存储线程的局部变量、函数调用信息等。
- 在多线程应用中，线程的栈大小是影响最大线程数的主要因素之一。如果每个线程分配较大的栈空间，进程能创建的线程数就会减少。
- 操作系统通常会限制每个线程的栈大小；例如某些 Linux/glibc 配置的默认 pthread 栈约为 8MB，Windows 主线程/工作线程默认值也随链接器、版本和创建 API 变化，不能当作所有平台的固定常数。

**进程的虚拟内存空间**

- 进程可用虚拟地址空间取决于 32/64 位架构、内核配置、地址空间布局和资源限制；“2GB–4GB”只适合解释部分 32 位系统，不能作为现代系统的通用上限。
- 线程的栈、堆、以及线程控制块等信息会占用虚拟内存空间，因此线程数量的上限和可用的内存空间密切相关。
- **操作系统的线程调度限制** 操作系统的线程调度机制可能会限制线程的数量。例如，内核可能限制了系统中可调度的线程数量，以避免过多线程导致的资源争夺和过度上下文切换。

### 4.38.2 硬件资源

**CPU 核心数**

- 在多核处理器系统中，每个线程都可能在不同的 CPU 核心上并行运行。当线程数量大大超过核心数时，操作系统必须在多个线程之间进行上下文切换。
- 虽然线程的数量不直接由 CPU 核心数限制，但线程的数量和 CPU 性能（特别是上下文切换的开销）是有关系的。如果线程数量过多，系统可能会出现严重的性能问题。
- **内存**：每个线程会消耗一定的内存，特别是线程栈空间；当系统内存不足时，创建可能失败，系统也可能依据资源策略回收或终止进程。

### 4.38.3 系统配置

- **操作系统的内核限制**：操作系统可能会设置进程/用户任务数量限制，以保护系统稳定性；在 Linux 上可用 `ulimit` 和 `/proc` 等接口查询相关资源限制。

```bash
ulimit -a
ulimit -u <number> # 设置最大线程数
```

- **线程库限制** 线程库（如 pthread 库）也可能对线程数有所限制，尤其在嵌入式系统或轻量级线程库中，这些限制可能更为严格。

### 4.38.4 进程可创建线程数的实际限制

**栈大小与线程数量**

- 在现代操作系统中，默认的线程栈大小可能是 **8MB（Linux）** 或 **1MB（Windows）**，这就意味着，如果进程只分配栈空间而不使用其他内存资源，理论上，进程能创建的线程数约为进程总虚拟内存空间除以每个线程的栈大小。

举例：

- 假设一个进程的虚拟内存空间为 **2GB**，线程栈大小为 **8MB**，则理论上最多可以创建 2GB / 8MB = 256 个线程。
- **操作系统与硬件资源的平衡**：线程数越多，线程调度开销和内存开销可能越大，导致系统性能下降；实际创建线程的数量还受到操作系统、硬件、调度机制、内存管理等综合因素的影响。

### 4.38.5 实际应用中

- 在大规模多线程应用中，创建的线程数应根据硬件资源和操作系统的限制来优化。如果线程数量过多，可能会导致过度上下文切换、内存压力、性能下降等问题。
- 对于多核处理器，通常使用线程池或任务队列来有效管理线程，而不是直接创建大量线程。这可以避免过度使用线程和管理开销。

### 4.38.6 总结

- **操作系统限制**：操作系统对每个进程的线程数量有内核级的限制，通常由线程栈大小、虚拟内存、内核资源管理等因素决定。
- **硬件资源限制**：CPU 核心数、可用内存是影响线程数量的关键因素。
- **系统配置**：操作系统和线程库的配置可能限制可创建线程数。例如，Linux 中的 ulimit 可以设置最大线程数。

## 4.39 孤儿进程、僵尸进程、守护进程

### 4.39.1 孤儿进程（Orphan Process）

- **定义**：子进程在父进程终止后，成为孤儿进程，原父进程的任务由 init 进程接管。
- **处理方式**：
    - **init** 进程（PID 为 1）会自动成为孤儿进程的新父进程，并负责回收子进程的状态。
    - 孤儿进程的存在不会造成系统资源泄露。

- **特点：** 父进程退出后子进程未结束；由 init 进程（或 systemd）继续管理。

### 4.39.2 僵尸进程（Zombie Process）

- **定义**：子进程已结束，但父进程尚未调用 wait() 系统调用获取子进程的退出状态，从而没有释放其进程控制块（PCB）。
- **处理方式**：
    - 僵尸进程会占用系统的进程表项。
    - 父进程必须通过 wait() 或 waitpid() 收集子进程的退出信息。

- **特点：** 进程已结束，但进程控制块（PCB）未被回收；通过父进程或其他机制（如 init）清除。

### 4.39.3 守护进程（Daemon Process）

- **定义**：守护进程是一个在后台运行的进程，通常用于执行系统或服务的任务，**没有终端控制**。
- **特点**：
    - **独立性**：与用户交互较少，通常由系统启动。
    - **不受控制终端影响**：不依赖用户终端，即使用户退出，守护进程仍会继续运行。
    - **常驻后台**：在启动时由系统启动，并持续运行直到系统关闭。

**创建守护进程的步骤（典型）：**

1. 创建子进程并使父进程退出。
2. 在子进程中调用 setsid() 创建新的会话，并脱离终端。
3. 重定向标准输入输出（stdin、stdout、stderr）到 /dev/null。
4. 持续执行后台任务。

### 4.39.4 孤儿进程、僵尸进程、守护进程的区别

| 类型 | 形成原因 | 是否仍在运行 | 处理方式 |
|---|---|---|---|
| 孤儿进程 | 父进程先退出 | 通常仍在运行 | 被 PID 1 或子收割者重新收养 |
| 僵尸进程 | 子进程已退出，父进程尚未 `wait` | 不再运行，仅保留退出状态 | 父进程调用 `wait`/`waitpid`；必要时修复父进程 |
| 守护进程 | 以后台服务方式运行并脱离终端 | 通常持续运行 | 由服务管理器监督和停止 |

三者不是同一维度：孤儿/僵尸描述父子生命周期关系，守护进程描述服务运行方式。一个守护进程也可能产生孤儿或僵尸子进程。

### 4.39.5 总结

> 孤儿进程由 init 进程收养，僵尸进程需要父进程回收，守护进程常常在后台独立执行服务任务。

> 孤儿进程由 init 管理，僵尸进程等待回收，守护进程则在后台默默工作。

## 4.41 进程调度算法

### 4.41.1 调度的目的

- **合理分配 CPU 时间**给多个进程
- 提高**系统吞吐量、响应时间和公平性**
- 保证**多任务环境下的效率和用户体验**

### 4.41.2 调度类型

1. **非抢占式调度**
    - 进程一旦获得 CPU，运行完毕或主动阻塞才释放 CPU
    - 适合批处理系统
2. **抢占式调度**
    - CPU 可以被操作系统强制从运行中的进程收回，分配给更高优先级或等待时间过久的进程
    - 适合实时和多用户交互系统

### 4.41.3 常见进程调度算法

**（1）先来先服务（FCFS, First-Come, First-Served）**

- **非抢占式**
- 按进程到达顺序分配 CPU

特点：

- 简单易实现
- **缺点**：可能导致“短作业等待长作业”，即 **平均等待时间长（Convoy effect）**

**（2）短作业优先（SJF, Shortest Job First）**

- **非抢占式或抢占式（SRTF）**
- 优先执行预计运行时间最短的进程

特点：

- 最小化平均等待时间
- 需要预知进程运行时间
- 可能导致**长作业饥饿**

**（3）优先级调度（Priority Scheduling）**

- 每个进程分配一个**优先级**
- 高优先级先执行
- 可**抢占或非抢占**

缺点：

- 低优先级进程可能**饥饿**
- 可用 **老化（Aging）** 防止饥饿

**（4）时间片轮转（RR, Round Robin）**

- **抢占式**
- 每个进程分配固定时间片（Time Quantum）
- 时间片用完，进程被挂起，放入队列尾部

特点：

- 公平，响应时间短
- 时间片太短 → 频繁切换，开销大
- 时间片太长 → 接近 FCFS

**（5）多级队列调度（Multilevel Queue）**

- 将进程按类别分成多个队列
- 每个队列有独立调度策略
- 可实现优先级和响应性兼顾

### 4.41.4 调度策略选择原则

1. **批处理系统** → FCFS、SJF
2. **交互式系统** → RR、优先级
3. **实时系统** → 优先级调度、抢占式

### 4.41.5 总结

> 调度算法分为抢占式和非抢占式，常用有 FCFS、SJF、优先级、RR 和多级队列，各有优缺点，选择取决于系统目标。

> 调度算法决定进程获得 CPU 的顺序，目标是效率、响应和公平的平衡。

## 4.42 什么时候会用到进程调度算法

### 4.42.1 基本理解

- **进程调度算法**用于决定**哪个进程优先获得 CPU**
- 任何存在**多进程或多线程的操作系统**都会用到调度算法
- 目标：**提高系统效率、响应速度和资源利用率**

### 4.42.2 使用场景

1. **多任务操作系统**
    - CPU 同时存在多个可运行进程
    - 调度算法决定执行顺序
2. **交互式系统**
    - 如桌面操作系统、服务器
    - 需要响应用户请求，保证**响应时间短**
    - 常用算法：**时间片轮转（RR）、优先级调度**
3. **批处理系统**
    - 多个作业提交，执行顺序影响吞吐量
    - 常用算法：**先来先服务（FCFS）、短作业优先（SJF）**
4. **实时系统**
    - 对延迟和响应有严格要求
    - 调度算法保证高优先级任务及时执行
    - 常用算法：**抢占式优先级调度、最早截止时间优先（EDF）**
5. **多核/多 CPU 系统**
    - 需要调度算法分配进程到不同核心
    - 目标：负载均衡、提高吞吐量

### 4.42.3 总结

> 只要系统中有多个可运行进程或线程，需要共享 CPU，就会用到进程调度算法，以实现公平、高效和响应及时。

> 多任务环境、交互系统、批处理或实时系统都会用进程调度算法来分配 CPU 时间。

## 4.43 Linux 默认使用什么调度策略？

在 Linux 中，默认调度策略是 `SCHED_OTHER`（也称 `SCHED_NORMAL`），具体实现随内核版本演进。历史上的默认普通任务调度器是 **CFS（完全公平调度器）**；Linux 6.6 起正在逐步采用 **EEVDF**，因此不能把“默认策略”和某一个固定调度器名称混为一谈。

### 4.43.1 CFS/EEVDF（普通任务调度实现）

CFS 旨在提供公平且高效的调度机制；“公平”按 nice 权重分配 CPU，并不意味着所有进程获得完全相同的时间。传统 CFS 使用基于 vruntime 的运行队列；新内核的 EEVDF 使用 lag/虚拟截止时间选择任务，具体数据结构和实现以目标内核为准。

**CFS 的工作原理**

- **进程虚拟运行时间**：CFS 为每个进程分配一个虚拟运行时间（vruntime），该时间表示进程自上次运行以来的“权重”消耗。进程虚拟运行时间越小，意味着该进程优先获得 CPU 时间。
- **运行队列**：传统 CFS 以 vruntime 组织可运行任务并倾向选择 vruntime 较小者；采用 EEVDF 的内核则按 eligible/virtual deadline 规则选择，不能把红黑树和 vruntime 当作所有现代内核的固定实现。
- **公平性**：普通任务按权重和调度器规则获得 CPU；nice、cgroup、CPU 亲和性和实时任务都会影响结果，不应承诺绝对公平或固定响应时间。

**CFS 调度的优点**

- **公平性**：传统 CFS 通过 vruntime 按权重分配 CPU；这不是所有任务获得相同时间，也不代表固定响应上界。
- **响应性**：与传统的时间片轮询算法相比，CFS 在响应性方面表现更好，尤其是在有多个短时间运行的进程时。
- **效率**：传统实现使用红黑树等运行队列结构；具体开销和数据结构随内核版本、调度类与硬件而变。

### 4.43.2 其他调度策略

除了 CFS 外，Linux 还提供了其他几种调度策略，适用于不同的使用场景。

**实时调度策略（SCHED_FIFO 和 SCHED_RR）**

- SCHED_FIFO（先到先服务，First In First Out）：实时调度策略；同优先级任务通常按队列顺序运行，较高优先级任务仍可抢占当前任务，任务也可主动阻塞、让出或被信号影响。
- SCHED_RR（轮询调度，Round Robin）：与 SCHED_FIFO 类似，但是 SCHED_RR 为每个进程分配了固定的时间片，时间片用完后会轮流执行下一个进程。SCHED_RR 更适合需要公平分配 CPU 时间的实时任务。
- **基于时间片的调度（SCHED_BATCH）** SCHED_BATCH：该策略适用于需要大量计算但对响应时间不敏感的批处理作业。此策略会减少调度器的干预，让进程可以尽可能长时间地占用 CPU。
- **SCHED_IDLE 策略** SCHED_IDLE：这是最低优先级的调度策略，用于在系统负载很轻时运行的进程。该策略只有在其他所有高优先级进程都没有运行时才会运行。
- **SCHED_DEADLINE**：按 runtime/deadline/period 参数和内核带宽规则调度，适合需要截止时间模型的任务；是否满足硬实时仍需做最坏执行时间、资源和中断分析。

### 4.43.3 如何查看和修改调度策略

- **查看当前进程的调度策略** 可以使用 chrt 命令查看进程的调度策略：

```bash
chrt -p <PID>
```

- 这将显示指定进程的调度策略和优先级。
- **修改进程的调度策略** 使用 chrt 命令修改进程的调度策略：

```bash
chrt -f <priority> <PID>
```

- -f 表示使用 SCHED_FIFO 策略，<priority> 表示进程的优先级。
- 也可以通过 sched_setscheduler() 系统调用在程序中修改进程的调度策略。

### 4.43.4 总结

- **默认调度策略**：Linux 默认策略是 `SCHED_OTHER/SCHED_NORMAL`；传统版本主要由 CFS 实现，现代内核可能使用 EEVDF 等 fair 调度实现，按权重和调度规则分配 CPU，不提供硬实时保证。
- **实时调度策略**：Linux 提供 SCHED_FIFO、SCHED_RR 等策略来改善高优先级任务的响应；是否按时完成仍需结合执行时间、阻塞、中断和系统负载分析。
- **批处理和空闲任务**：SCHED_BATCH 和 SCHED_IDLE 策略适用于长时间运行的批处理任务或系统空闲时运行的进程。

## 4.44 优先级反转是什么？如何解决？

优先级反转（Priority Inversion）是一种在实时系统中可能出现的现象，通常发生在多线程或多进程的调度中。当一个高优先级的任务被低优先级的任务阻塞时，就会发生优先级反转。这样，高优先级任务的执行被不应当阻塞它的低优先级任务给阻塞了，导致系统不能按预期的时间完成任务，从而影响系统的实时性能。

### 4.44.1 优先级反转的情景

在一个多线程或多进程的实时系统中，任务是根据优先级来调度的。假设有以下三种任务：

- **高优先级任务**：需要尽快执行的任务，优先级最高。
- **低优先级任务**：优先级较低的任务，通常在空闲时执行。
- **中等优先级任务**：优先级介于高优先级和低优先级之间。

如果低优先级任务（Task C）先持有某个共享资源，高优先级任务（Task A）随后请求该资源而阻塞；此时中等优先级任务（Task B）又可以抢占 Task C，使 Task C 更晚释放资源，Task A 反而被间接延迟，这就是典型的优先级反转。

这种情况可能导致高优先级任务的响应时间变得不可预测，严重时会影响系统的实时性和稳定性。

### 4.44.2 优先级反转的例子

假设有三个任务，Task A（高优先级）、Task B（中等优先级）、Task C（低优先级）：

1. **Task C**（低优先级）先获得共享锁并执行临界区。
2. **Task A**（高优先级）请求该锁而阻塞。
3. **Task B**（中等优先级）变为就绪并抢占 Task C。
4. Task C 无法及时运行并释放锁，Task A 因而被 Task B 间接拖延。

最终，尽管 Task A 的优先级最高，它被 Task C（低优先级任务）的执行所阻塞，导致优先级反转。

### 4.44.3 优先级反转的影响

优先级反转的出现会导致以下问题：

- **实时任务的延迟**：高优先级任务无法在规定时间内完成，从而违背了系统的实时性要求。
- **响应时间不可预测**：优先级反转会使得高优先级任务的响应时间不可预测，降低系统的可预测性和可靠性。
- **任务调度不公平**：低优先级任务可能间接影响到高优先级任务的执行，导致资源分配不公平。

### 4.44.4 优先级反转的解决方案

为了解决优先级反转问题，操作系统和实时系统采用了多种策略：

**优先级继承协议（Priority Inheritance Protocol）**

- **优先级继承协议**的核心思想是：当低优先级任务占用了高优先级任务需要的资源时，低优先级任务的优先级会被临时提高到高优先级任务的优先级，直到低优先级任务释放资源为止。
- 这种机制可以缩短由中优先级任务造成的阻塞；实际效果取决于锁的使用、嵌套、调度和中断开销，不能单独保证 deadline。

**优先级天花板协议（Priority Ceiling Protocol）**

- **优先级天花板协议**规定每个资源都有一个“天花板优先级”，即资源的最高优先级。当一个任务获得该资源时，它的优先级会被提升到该资源的天花板优先级，直到任务释放资源。
- 这种方法通过限制任务获取资源的优先级来降低优先级反转；是否完全避免取决于协议实现和所有共享资源是否遵守规则。
- **禁止优先级反转的设计（Non-blocking Synchronization）** 采用无阻塞的同步机制，避免任务之间的互相阻塞。例如，使用无锁的数据结构、消息队列等，这样高优先级任务就不会因为低优先级任务的执行而被阻塞。

### 4.44.5 总结

优先级反转可能导致高优先级任务延迟和响应抖动。优先级继承/天花板等协议可在假设成立时降低或避免反转，但仍需结合最坏执行时间、锁粒度和中断负载验证实时性。

### 4.45.1 物理地址（Physical Address）

**定义：**
物理地址是由 MMU/总线使用的硬件地址空间中的地址，可指向 RAM，也可指向设备 MMIO 区域；它不是只指“内存条上的地址”。

- **特点：** 在给定地址空间和总线中有确定含义；CPU/设备最终通过它访问 RAM 或 MMIO；用户程序在现代 OS 中通常不能直接操作，内核和裸机代码可按平台规则访问

### 4.45.2 虚拟地址（Virtual Address）

**定义：**
虚拟地址是 **程序看到和使用的地址**，由操作系统提供的“假象地址”。

- **特点：** 每个进程都有独立的虚拟地址空间；同一个虚拟地址在不同进程中可能映射到不同物理地址；提供内存隔离与保护

### 4.45.3 虚拟地址 → 物理地址的转换（核心）

转换过程由 **MMU（内存管理单元）** 完成：

```text
虚拟地址 → 页表 → 物理地址
```

- 操作系统维护页表
- MMU 根据页表自动转换
- 程序无感知

### 4.45.4 为什么需要虚拟地址？

**（1）内存隔离（安全）**

- 防止进程互相访问内存
- 防止程序破坏系统

**（2）简化编程**

- 程序无需关心物理内存布局
- 每个程序“从 0x0 开始”

**（3）支持更大的地址空间**

- 虚拟内存 > 实际物理内存
- 支持换页（swap）

### 4.45.5 页（Page）与地址结构

常见页大小：**4KB**

虚拟地址结构：

```text
| 页号 | 页内偏移 |
```

- 页号 → 查页表
- 页内偏移 → 定位具体字节

### 4.45.8 嵌入式补充（加分）

- **无 MMU MCU**：直接使用物理地址
- **有 MMU（Linux）**：必须虚拟地址

**一句话总结：**
虚拟地址是给程序看的，物理地址是给硬件用的，中间由 MMU 翻译。

## 4.46 虚拟内存和物理内存

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/Linux物理内存碎片高频面试题#第 20 题：伙伴系统、order、zone、node/NUMA 分别是什么？它们和这个项目采集的指标如何对应？|内存项目 20：伙伴系统、order、zone、node/NUM…]]

### 4.46.1 物理内存（Physical Memory）

**定义：**
物理内存是计算机中实际存在的 **RAM 硬件资源**。

- **特点：** 真实存在、容量固定；访问速度快；所有进程共享；由硬件直接访问

### 4.46.2 虚拟内存（Virtual Memory）

**定义：**
虚拟内存是操作系统基于 **磁盘 + 物理内存** 提供的一种内存管理机制，对程序呈现出更大的“连续内存空间”。

- **特点：** 逻辑概念，不完全存在于 RAM；每个进程独立；可大于物理内存；由操作系统统一管理

### 4.46.3 虚拟内存的实现方式

- **分页机制（Paging）**
- 页表 + MMU 地址转换
- 页面置换（缺页中断）
- 交换区（swap / page file）

### 4.46.4 为什么需要虚拟内存？

1. **内存隔离**
    - 防止进程互相干扰
2. **提高内存利用率**
    - 只加载常用页面
3. **支持大程序运行**
    - 程序可使用超过物理内存的空间
4. **简化程序设计**
    - 进程拥有连续的地址空间

### 4.46.6 性能影响说明

- 命中 RAM：性能接近物理内存
- 频繁缺页：性能显著下降（抖动）
- 合理虚拟内存 ≠ 无限扩大 swap

### 4.46.7 嵌入式相关

- **无 OS / 无 MMU**：无虚拟内存概念
- **嵌入式 Linux**：完整虚拟内存机制
- **实时系统**：通常限制或关闭 swap
- 物理内存是真实的 RAM，虚拟内存是操作系统通过映射和换页机制提供的逻辑内存扩展与隔离手段。

## 4.47 页表

### 4.47.1 基本概念

- **页表（Page Table）是操作系统维护的虚拟地址到物理地址映射表**
- 用于**虚拟内存管理**
- 每个进程都有自己的页表

### 4.47.2 页表的作用

1. **地址映射**
    - 将进程的虚拟地址转换为物理地址
    - CPU 访问内存时，通过 MMU 查询页表完成转换
2. **内存隔离**
    - 不同进程的虚拟地址映射到不同物理页
    - 防止进程直接访问其他进程的内存
3. **按需分配与保护**
    - 只有访问的页才映射到物理内存（节省内存）
    - 可以设置页权限（读、写、执行）
4. **支持换页（Swap）**
    - 内存不足时，可将不常用页换到磁盘
    - 页表记录页是否在物理内存或磁盘

### 4.47.3 页表类型

1. **单级页表**
    - 简单，但占用内存大（虚拟地址空间大时）
2. **多级页表**（2级、3级、4级）
    - 减少页表占用
    - Linux x86_64 使用 4 级页表（PML4 → PDPT → PD → PT）
3. **反向页表（Inverted Page Table）**
    - 按物理页记录虚拟页
    - 节省内存，但查找较慢

### 4.47.4 页表项（PTE）内容

- **物理页号（Frame Number）**
- **有效位（Valid/Present）**
- **访问权限（读/写/执行）**
- **脏位、引用位**（用于换页算法）

### 4.47.5 页表意义总结

1. 实现**虚拟地址到物理地址的映射**
2. 提供**进程内存隔离与安全**
3. 支持**按需分配和内存扩展**
4. 为**换页和内存管理策略**提供基础

### 4.47.6 总结

> 页表是虚拟内存的核心，将虚拟地址映射到物理地址，同时提供隔离、权限控制和换页支持。

> 页表让 CPU 能用虚拟地址访问物理内存，并确保安全和灵活的内存管理。

## 4.48 什么是缺页中断？

**缺页中断**（Page Fault）是操作系统中一种常见的中断类型，通常发生在虚拟内存管理中。当程序访问的某个页面（Page）不在物理内存中时，CPU会触发缺页中断。操作系统通过缺页中断来处理虚拟地址与物理内存之间的映射，从而确保程序可以继续执行。

### 4.48.1 缺页中断的原因

缺页中断通常发生在以下几种情况下：

**访问的页面不在内存中**

虚拟内存允许程序使用比实际物理内存更大的内存空间。当程序访问一个虚拟地址时，操作系统会检查该地址对应的物理内存页面。如果该页面尚未加载到内存中（例如被交换出去或尚未分配），就会触发缺页中断。

**页面被换出到磁盘**

当系统内存不足时，操作系统会将某些不活跃的页面换出到硬盘上（通常称为**页面交换**或**页面调度**）。如果程序访问的页面已经被换出，操作系统会发生缺页中断，触发页面的重新加载。

**访问未分配的页面**

如果程序尝试访问一个未被分配的虚拟页面，操作系统会触发缺页中断，通常会引发访问异常，进而产生错误（如访问违规）。

**写入只读页面**

如果程序尝试修改一个只读页面，也会导致缺页中断。这通常会导致**访问违例**，如程序试图修改代码段等不允许写入的区域。

### 4.48.2 缺页中断的处理过程

当缺页中断发生时，CPU会中断当前的程序执行，并转而执行操作系统的**缺页中断处理程序**。该过程通常包括以下几个步骤：

**保存当前执行状态**

在处理中断时，操作系统首先保存当前正在执行的程序的状态，包括CPU寄存器、程序计数器（PC）等，以便在处理完中断后可以恢复执行。

**检查页面的状态**

操作系统会检查发生缺页的页面是否在物理内存中。如果该页面已经被交换到磁盘，操作系统会将其从磁盘加载回物理内存。

**页面加载或分配**

- **页面从磁盘加载**：如果页面在磁盘上，操作系统会选择一个空闲的内存页框，或者根据一定的页面替换算法（如 LRU）选择一个已加载的页面进行替换，将所需的页面从硬盘加载到内存中。
- **分配新页面**：如果页面从未分配过，操作系统会为该页面分配一个新的物理内存区域，并将该页面标记为已分配。

**更新页面表**

操作系统更新页表，将新的物理页框与相应的虚拟地址进行映射。页表中的相关项会被修改为指向新加载的页面。

**恢复执行**

中断处理程序完成后，操作系统会恢复之前保存的状态，并将程序执行流恢复到触发缺页中断的点，程序将继续执行。

### 4.48.3 缺页中断的类型

缺页中断的类型可以根据具体的访问行为有所不同：

**正常缺页中断**

这是最常见的缺页中断，表示程序访问的页面不在物理内存中。操作系统通过将页面加载到内存中来恢复程序执行。

**非法缺页中断**

如果程序访问的页面未被分配，或者程序尝试访问受保护的页面（例如只读页面），操作系统会触发非法缺页中断，这通常会导致程序崩溃或生成错误报告。

**写时复制缺页中断**

在实现写时复制（Copy-On-Write, COW）时，如果多个进程共享一个页面，当某个进程尝试写入该页面时，会触发缺页中断。操作系统会为该进程创建该页面的副本，以便修改，从而保持进程之间的数据独立性。

### 4.48.4 缺页中断的性能影响

虽然缺页中断使得程序能够使用更多的内存（通过虚拟内存），但频繁的缺页中断会严重影响系统性能。特别是在内存密集型应用中，如果程序频繁访问尚未加载到内存的页面，可能会导致大量的磁盘I/O操作，进而导致系统性能下降。

**页面抖动（Thrashing）**

当系统的物理内存不足时，操作系统可能会频繁地从磁盘中加载和交换页面，导致大量的缺页中断和磁盘I/O，这种现象称为**页面抖动**。页面抖动会极大地影响系统性能，甚至使程序几乎无法继续执行。

**磁盘I/O**

每次缺页中断导致的磁盘I/O操作都相对较慢，因此频繁的缺页中断会增加系统的负载，导致程序运行缓慢。

### 4.48.5 如何优化缺页中断的影响

为了减少缺页中断的负面影响，可以采取以下几种优化策略：

**增加物理内存**

增加系统的物理内存，可以减少页面交换的次数，从而减少缺页中断的频率。

**优化内存访问模式**

优化程序的内存访问模式，确保程序顺序访问内存，减少访问不连续页面的机会，从而降低缺页中断的频率。

**使用页面预取（Prefetching）**

操作系统或硬件可以使用预取技术，将程序可能会使用的页面提前加载到内存中，从而减少缺页中断的发生。

### 4.48.6 总结

缺页中断是虚拟内存管理的核心机制之一，它使得程序能够使用比物理内存更大的内存空间，但频繁的缺页中断可能会导致性能下降，需要通过优化内存管理和提高物理内存容量来减少其影响。

## 4.49 虚拟地址到物理地址的映射

### 4.49.1 背景

- **虚拟内存**为每个进程提供独立地址空间
- CPU最终访问的是物理内存，但CPU产生的是虚拟地址。
- **虚拟地址 → 物理地址** 的映射由 **操作系统 + MMU（内存管理单元）** 完成

### 4.49.2 映射过程

1. **虚拟地址分解**

假设虚拟地址长度为 32 位（简化示例）：

```text
| 虚拟页号（VPN） | 页内偏移（Offset） |
```

- **虚拟页号（VPN, Virtual Page Number）**：用来查页表
- **页内偏移（Offset）**：在物理页内的具体位置
2. **查页表（Page Table）**
- CPU 通过 **MMU** 查询页表
- 找到对应的物理页号（PFN, Physical Frame Number）
3. **计算物理地址**

```text
物理地址 = PFN * 页大小 + 页内偏移
```

### 4.49.3 举例

以 32 位虚拟地址、4 KiB 页为例，页内偏移占 12 位，虚拟页号占 20 位。若虚拟地址为 `0x12345ABC`，则页内偏移为低 12 位 `0xABC`，虚拟页号为 `0x12345`。页表将该虚拟页号映射到物理页框 `0x56789` 时，物理地址为：

```text
物理地址 = (0x56789 << 12) | 0xABC = 0x56789ABC
```

实际 x86-64、ARMv8 等平台通常使用多级页表和不同的地址位数，示例只用于说明“页号替换、页内偏移不变”。

### 4.49.4 映射特点

- **页内偏移保持不变**：地址转换只替换虚拟页号为物理页框号。
- **按页保护**：页表项可记录读写、执行、用户/内核、访问和脏等属性。
- **TLB 加速**：处理器缓存近期页表项，TLB 未命中时才需遍历页表。
- **缺页处理**：页表项无效或页面不在内存时触发缺页异常，内核可能从磁盘或文件装入页面。
- **共享映射**：不同进程的虚拟页可映射到同一物理页，用于共享库或共享内存。
- **地址空间隔离**：不同进程可使用相同虚拟地址而映射到不同物理页；内核还需校验权限，不能仅凭地址数值判断可访问性。

### 4.49.5 面试高频总结句

> 虚拟地址按页拆分为虚拟页号和页内偏移，MMU 通过页表或 TLB 将虚拟页号映射到物理页框，页内偏移保持不变；缺页、权限和缓存一致性由体系结构与内核共同处理。

## 4.50 段页式内存管理

### 4.50.1 背景

- **内存管理目标**：支持虚拟内存、进程隔离和高效利用物理内存
- **纯分页**：方便分配、易管理，但对逻辑结构不直观
- **纯分段**：支持逻辑分段，便于保护，但内存碎片多
- **段页式管理**：结合分页与分段优点

### 4.50.2 段页式内存管理概念

- **逻辑地址 = 段号 + 段内偏移（Segment Offset）**
- **段内再分页**：每个段被划分为固定大小的页（Page）
- **映射过程**：
    a. CPU 给出 **逻辑地址（段号 + 段内偏移）**
    b. **段表**：段号 → 段基址（段在虚拟内存中的起始页表） + 段界限
    c. **页表**：段内页号 → 物理页框
    d. **物理地址** = 物理页框 + 页内偏移

### 4.50.3 结构示意

```text
逻辑地址：
| 段号 (s) | 页号 (p) | 页内偏移 (d) |

段表：
段号 s → 段表项（段基址, 段界限）

页表：
段内页号 p → 页表项（物理页号 PFN）

物理地址：
PFN * 页大小 + 页内偏移 d
```

### 4.50.4 优势

1. **结合分段和分页优点**
    - 分段：便于程序逻辑结构（代码段、数据段、栈段）
    - 分页：解决内存碎片问题
2. **内存保护**
    - 段界限 + 页权限 → 细粒度保护
3. **支持大地址空间**
    - 分页解决连续内存不足问题
4. **灵活分配**
    - 段可按需增长（如栈段动态增长）

### 4.50.5 总结

> 段页式内存管理结合分段逻辑和分页物理，段表确定段起点与界限，页表完成页到物理页的映射，兼顾保护与内存利用率。

> 段页式管理：先按逻辑分段，再将段分页，映射到物理内存，实现灵活、高效、安全的内存管理。

## 4.51 栈溢出、堆溢出

在程序运行过程中，内存的分配通常分为 **栈** 和 **堆** 两个区域。栈和堆的溢出是常见的内存问题，它们的根本原因是内存空间的超出限制或不当使用。栈溢出和堆溢出具有不同的触发条件、影响范围和处理方式。

### 4.51.1 栈溢出（Stack Overflow）

栈溢出是指程序在调用函数时，栈的空间被用尽，从而导致栈区域超出分配的内存空间。栈主要用于存储局部变量、函数调用时的返回地址等信息。

**栈的特点**

- 栈的内存是由操作系统自动管理的。
- 栈是 **后进先出（LIFO）** 的数据结构，每次调用一个函数，函数的局部变量和返回地址会被压入栈中，函数返回时，这些数据会被弹出栈。
- 栈的大小是有限的（通常由操作系统或编译器设定），当栈的空间用尽时，发生栈溢出。

**栈溢出的常见原因**

- **递归调用过深**：当递归函数没有正确的终止条件，或者递归层数过多时，栈的空间会被大量消耗，最终导致栈溢出。
- **局部变量过多**：函数中的局部变量占用过多内存，导致栈空间不足。
- **过大的局部数组**：声明了很大的局部数组，这会消耗大量栈空间，特别是在嵌套函数调用时。

**栈溢出的后果**

- **程序崩溃**：当栈溢出发生时，操作系统会终止程序，并通常会生成一个崩溃报告。
- **栈指针损坏**：栈溢出可能导致栈指针（Stack Pointer）指向非法地址，导致数据丢失或程序错误。

**如何避免栈溢出**

- **避免深度递归**：递归深度过大时，应考虑改用迭代方法，或优化递归逻辑。
- **合理分配局部变量**：避免在函数中分配过多或过大的局部变量，尤其是大型数组等。
- **增加栈的大小**：在某些系统中，可以通过修改编译器选项或操作系统配置来增加栈的大小。

### 4.51.2 堆耗尽与堆缓冲区溢出

这两个概念要分开：**堆耗尽/分配失败**是可用堆空间不足，`malloc`/`new` 返回失败或触发异常；**堆缓冲区溢出**是写入超出某个已分配对象边界，可能破坏相邻对象和分配器元数据，属于内存安全错误。

**堆的特点**

- 堆是由程序员显式管理的内存区域，通过 malloc、calloc、realloc 等函数进行分配，使用 free 释放。
- 堆空间的大小可以动态调整，但它的大小也受到操作系统的限制。
- 堆的内存分配通常较慢，因为它是自由存取的，并且需要管理内存的碎片。

**堆耗尽或堆缓冲区溢出的常见原因**

- **未释放内存/内存泄漏**：长期占用堆空间，最终导致后续分配失败。
- **错误的内存分配**：请求的内存过大或碎片化严重，可能导致分配失败。
- **缓冲区溢出**：在堆上操作数据时未检查边界，向已分配对象之外写入数据。

**可能后果**

- **分配失败**：后续申请返回空指针或抛出异常，业务需要明确错误处理。
- **程序崩溃或数据损坏**：越界写可能破坏对象、堆元数据或控制流。
- **安全漏洞**：可利用的越界写可能造成信息泄露或代码执行风险。

**如何避免堆溢出**

- **正确管理内存**：使用智能指针（如 C++ 中的 std::unique_ptr 或 std::shared_ptr）来自动管理堆内存，避免忘记释放。
- **避免内存泄漏**：确保每次分配的内存都在不再使用时释放，避免内存泄漏。
- **检查内存分配**：在每次内存分配后，检查返回值是否为 NULL（在 C 中）或 nullptr（在 C++ 中），避免使用失败的分配。
- **使用内存池**：为了避免堆内存碎片，使用内存池来管理内存分配。

### 4.51.3 总结

- **栈溢出** 通常由深度递归、局部变量过多等原因引起，操作系统通过栈的空间限制和调用栈管理来避免。但如果栈空间不足，就会发生溢出。
- **堆耗尽**是可用堆空间不足导致分配失败；**堆缓冲区溢出**是对象边界检查缺失导致越界访问。二者原因和修复方式不同，不能都笼统称为“堆溢出”。

## 4.52 .so文件的基本理解

### 4.52.1 什么是 .so 文件

**.so（Shared Object）** 是 Linux/Unix 系统中的 **动态链接库文件**，相当于 Windows 下的 .dll。

### 4.52.2 .so 文件的作用

- **代码复用**：多个程序共享同一份库代码
- **减小可执行文件体积**
- **方便升级维护**：替换库无需重新编译程序
- **支持动态加载**（运行时加载）

### 4.52.3 .so 与可执行文件的关系

- 程序编译时 **只记录符号引用**
- 程序运行时由 **动态链接器（ld-linux）** 加载 .so
- 通过符号表完成函数地址绑定

### 4.52.4 .so 的链接方式

**（1）编译期动态链接（常见）**

```bash
gcc main.c -lmylib
```

- 程序启动时自动加载 .so

**（2）运行期动态加载**

```c
#include <dlfcn.h>

void* handle = dlopen("libtest.so", RTLD_LAZY);
void (*func)() = dlsym(handle, "func");
```

- 更灵活
- 常用于插件系统

### 4.52.5 .so 与 .a 的区别（重点）

| 项目 | `.a` 静态库 | `.so` 共享库 |
|---|---|---|
| 链接时机 | 链接阶段从归档中提取需要的目标文件 | 通常记录动态依赖，运行时由动态链接器装载 |
| 可执行文件 | 代码通常被复制进可执行文件 | 主要保存符号和依赖关系 |
| 运行时依赖 | 一般不需要同名库文件 | 需要目标系统存在兼容的共享库和动态链接器 |
| 更新方式 | 更新库通常需要重新链接程序 | 可独立更新，但必须维护 ABI 兼容 |
| 内存共享 | 不同进程各自拥有代码副本 | 多个进程可共享只读代码页 |
| 体积/启动 | 文件可能较大，启动依赖少 | 文件较小，装载和符号解析有开销 |

`gcc main.o -L. -lfoo` 选择哪一种还取决于搜索路径、链接选项和系统中实际存在的文件；不要把“用了 `-lfoo`”简单等同于静态或动态链接。

### 4.52.6 运行时查找 .so 的路径

运行时查找顺序由 ELF 的 `DT_RPATH`/`DT_RUNPATH`、`LD_LIBRARY_PATH`、`/etc/ld.so.cache`、默认目录以及安全模式等共同决定；`DT_RPATH` 与 `DT_RUNPATH` 的优先级不同，不能用一条脱离链接器和 libc 版本的固定顺序概括。部署时应使用 `readelf -d`、`ldd`（注意不要对不可信文件直接运行）和目标系统的动态链接器文档核对。

### 4.52.7 嵌入式 / Linux 开发注意点

- 交叉编译需匹配架构
- 注意 glibc / musl 版本
- 防止库版本冲突（ABI 不兼容）

### 4.52.8 常见问题

- **找不到 .so**：路径未配置
- **undefined symbol**：符号不匹配
- **版本冲突**：库 ABI 不一致

### 4.52.9 一句话总结

> .so 文件是 Linux 下的动态共享库，程序在运行时加载并共享代码，实现体积小、可维护性强的链接方式。

## 4.53 静态链接与动态链接

### 4.53.1 什么是静态链接

**定义：**
静态链接是在**编译 / 链接阶段**，将所需的库代码**完整拷贝进可执行文件**中。

**常见文件：**
.a（Linux）、.lib（Windows）

### 4.53.2 静态链接的特点

- 可执行文件体积大
- 不依赖外部库文件
- 运行时加载快
- 程序之间不共享库代码

### 4.53.3 什么是动态链接

**定义：**
动态链接是在**程序运行时**，由动态链接器加载共享库并完成符号解析。

**常见文件：**
.so（Linux）、.dll（Windows）

### 4.53.4 动态链接的特点

- 可执行文件体积小
- 多个程序共享同一份库
- 运行时有加载开销
- 依赖系统库环境

### 4.53.5 静态链接与动态链接对比（重点）

| 维度 | 静态链接 | 动态链接 |
|---|---|---|
| 依赖 | 依赖打包进可执行文件 | 运行时依赖共享库、动态链接器和 ABI |
| 升级 | 库更新需重新链接并发布程序 | 可替换共享库，但需兼容接口和版本 |
| 资源 | 多个进程可能重复占用代码空间 | 只读代码页可在进程间共享 |
| 启动 | 通常少一步动态装载 | 需要装载、重定位和符号解析 |
| 可移植性 | 仍受架构、libc、系统调用影响 | 还受库路径和 ABI 影响 |
| 嵌入式取舍 | 固件自包含、部署简单 | 节省存储并支持模块化升级 |

静态链接不等于“完全没有运行环境依赖”，例如仍可能依赖内核系统调用、设备节点和配置文件；动态链接也不必然更慢，装载后的共享代码可被多个进程复用。

### 4.53.6 编译示例

**静态链接**

```bash
gcc main.c -static -lmylib
```

**动态链接（默认）**

```bash
gcc main.c -lmylib
```

### 4.53.7 使用场景

- **静态链接适合：** 嵌入式裸机；独立部署程序；系统环境不可控
- **动态链接适合：** 桌面 / 服务器程序；多程序共享库；频繁升级的系统

### 4.53.8 嵌入式开发补充

- **无 OS / 裸机**：通常采用静态链接（也可由自定义运行时提供其他形式的库加载）
- **嵌入式 Linux**：多用动态链接节省资源
- **实时系统**：常用静态链接以减少运行时依赖；确定性还取决于调度、驱动和内存策略等整体设计

### 4.53.9 面试高频总结句

> 静态链接在编译期将库代码打包进程序，运行独立但体积大；动态链接在运行期加载共享库，节省内存但依赖环境。

### 4.53.10 静态链接与动态链接的优缺点？

**静态链接的优缺点**

- **优点：** 程序通常不依赖对应的外部共享库文件；少一次动态装载和符号解析，但启动速度仍取决于程序、文件系统和运行环境。
- **缺点：** 如果多个程序使用相同的库，每个程序都要包含一份相同的代码，可能浪费磁盘空间；更新库时通常需要重新链接所有依赖它的程序。

**动态链接的优缺点**

**优点：**

- 多个程序可以共享同一个动态链接库，节省了磁盘空间和内存。
- 如果库的版本更新，只需更新动态链接库，而不需要重新编译所有依赖库的程序。
- 支持插件机制，程序可以在运行时加载或卸载库。
- **缺点：** 程序在运行时依赖外部库文件，若库文件丢失、版本不匹配或 ABI 发生变化，可能无法正常运行；启动阶段还会增加装载、重定位和符号解析开销。

**总结**

·  **静态链接**将所有需要的库文件直接嵌入到最终的可执行文件中，生成的程序独立、较大，且对外部库没有依赖。

·  **动态链接**则推迟了库文件的链接，程序在运行时加载外部库文件，生成的程序较小，多个程序可以共享同一个库文件，但需要依赖运行时的库文件。

## 4.54 静态存储和动态存储

### 4.54.1 存储方式的基本概念

在 C/C++ 中，变量按照**生命周期和分配方式**可分为**静态存储**和**动态存储**。

### 4.54.2 静态存储（Static Storage）

**定义：**
在**程序编译或启动时**分配内存，整个程序运行期间一直存在。

**（1）包含的对象**

- 全局变量
- 静态全局变量（static 全局）
- 静态局部变量（static 局部）
- 常量字符串
- 静态成员变量（C++）

**（2）特点**

- 生命周期：程序开始 → 程序结束
- 内存位置：全局区 / 静态区
- 只初始化一次
- 访问速度快
- 不需要手动释放

### 4.54.3 动态存储（Dynamic Storage）

**定义：**
在**程序运行过程中**按需申请和释放的内存。

**（1）申请方式**

- C：malloc / calloc / realloc / free
- C++：new / delete

**（2）特点**

- 生命周期：由程序员控制
- 内存位置：堆（Heap）
- 空间大小灵活
- 易产生内存泄漏、碎片

### 4.54.4 栈存储的说明（易混点）

- **栈不是静态存储**
- 属于自动存储（Automatic Storage）
- 函数结束自动释放

### 4.54.5 静态存储 vs 动态存储对比

| 维度 | 静态存储期 | 动态存储期 |
|---|---|---|
| 生命周期 | 从程序启动到结束 | 由分配和释放操作决定 |
| 典型对象 | 全局变量、文件作用域 `static`、函数内 `static` | `malloc`/`new` 创建的对象 |
| 管理者 | 编译器/运行时自动安排 | 程序或分配器显式管理 |
| 优点 | 地址和生命周期稳定、可预测 | 大小灵活、可按需创建 |
| 风险 | 长期占用、固定容量 | 泄漏、悬挂指针、双重释放、碎片和失败 |
| 典型区域 | `.data`、`.bss`、只读数据等，具体由链接脚本决定 | 通常是堆或专用内存池 |

存储期、存储区域和作用域不是同一概念：局部 `static` 变量作用域仍在函数内，但存储期贯穿整个程序；动态对象不一定来自传统堆，也可能来自内存池或自定义分配器。

### 4.54.6 典型代码示例

```c
int g;              // 静态存储
static int s;       // 静态存储

void func() {
    static int x;   // 静态存储
    int y;          // 栈存储
    int *p = malloc(4); // 动态存储
}
```

### 4.54.7 使用场景总结

- **静态存储**：配置变量、全局状态、常驻数据
- **动态存储**：不确定大小的数据、运行期对象

### 4.54.8 面试高频总结句

> 静态存储的对象在程序整个生命周期内存在，而动态存储的对象由程序运行时申请和释放，生命周期由程序员控制。

### 4.54.9 总结

> 静态存储追求稳定和生命周期确定，动态存储追求灵活但需要严格管理。

## 4.55 Linux 内存的用户空间和内核空间如何划分？

在 Linux 操作系统中，内存的划分主要分为 **用户空间** 和 **内核空间** 两大部分。这样的划分不仅是为了操作系统的效率和安全性，也是为了确保用户程序与操作系统内核的隔离，从而避免用户程序误操作或损坏操作系统的核心功能。

### 4.55.1 用户空间和内核空间的基本概念

- **用户空间**：这是普通用户程序运行的区域。用户空间中运行着各类应用程序，操作系统的应用层组件（如图形界面、命令行工具等）。用户空间的程序通常不能直接访问硬件资源，也不能直接操作内核内存。
- **内核空间**：这是操作系统内核运行的区域。内核空间包含操作系统的内核代码、设备驱动程序和管理内存、进程、文件系统等的核心组件。内核空间是操作系统控制硬件和进行系统管理的地方，只有操作系统内核代码才能直接访问和修改内核空间中的数据。

### 4.55.2 用户空间和内核空间的地址划分

在 Linux 系统中，内存被虚拟化后，操作系统会划分一个独立的地址空间给用户程序，另一个独立的地址空间给内核。

**虚拟内存布局**

- **用户空间**：用户程序只能访问 **用户空间** 中的内存区域，无法直接访问内核空间；起止地址取决于架构、内核配置、地址位数和进程布局。
- **内核空间**：内核空间通常位于虚拟地址的受保护范围，起止地址和布局由架构、内核及硬件决定；内核代码、数据结构和驱动映射位于其中。

**32 位 x86 地址划分示例**

在启用常见 3G/1G 用户/内核划分的 **32 位 x86 Linux** 配置中，常见示例如下；具体比例可由内核配置改变：

- **用户空间**：从 0x00000000 到 0xBFFFFFFF（大约 3GB）。
- **内核空间**：从 0xC0000000 到 0xFFFFFFFF（大约 1GB）。

这种划分方式是为了保证用户空间和内核空间的分离，并且在大多数情况下，内核空间位于高地址，用户空间位于低地址。

**64 位系统**

在 64 位系统中，地址空间变得更加宽广，虚拟地址的范围大大增加。用户空间和内核空间的划分依然存在，但具体的大小会随着操作系统和硬件架构的不同有所变化。例如，在 Linux 的 64 位版本中：

- **用户空间**：在采用 48 位规范地址的常见配置中，示例为低地址到 `0x00007fffffffffff`（约 128 TiB）；实际上限随架构、内核和硬件变化。
- **内核空间**：通常位于高地址范围，起点和大小由架构、内核配置及硬件地址位数决定。

### 4.55.3 访问权限

- **用户空间的访问限制**：
    - 用户空间中的进程只能访问自己的内存区域。操作系统使用 **虚拟内存管理** 技术来实现对用户进程的内存隔离，确保一个进程无法直接访问或篡改另一个进程的内存。
    - 进程通过 **系统调用** 与内核进行交互，例如读取文件、创建进程、申请内存等。
- **内核空间的访问权限**：
    - 只有操作系统内核运行的代码（如内核态进程、设备驱动等）可以访问内核空间的内存。
    - 用户空间程序不能直接访问内核空间，这种保护机制可以防止恶意程序对系统核心的破坏。
    - 用户空间程序如果想要访问内核资源（如硬件、设备、系统信息等），必须通过 **系统调用** 机制，由内核来执行实际的操作。

### 4.55.4 用户空间与内核空间的切换

- **用户态到内核态的切换**：当用户程序需要请求内核服务时（如文件读写、内存分配等），会通过 **系统调用** 触发 **上下文切换**，使得 CPU 从 **用户态** 切换到 **内核态**，内核执行相应的操作后再切换回用户态。
- **内核态到用户态的切换**：内核执行完毕后，会通过 **系统调用返回** 的方式，将控制权交回到用户空间程序，恢复到用户态执行。

**中断与上下文切换**

- 当系统发生中断（如硬件中断、定时器中断等），操作系统会从用户空间切换到内核空间，进行中断处理。中断处理程序执行完毕后，会返回用户空间。
- 进程调度时，操作系统会进行上下文切换，保存当前进程的状态并加载下一个进程的状态。

### 4.55.5 虚拟内存和物理内存的关系

- **虚拟内存**：虚拟内存是由操作系统为每个进程提供的独立的地址空间，允许每个进程有自己独立的内存空间，不受其他进程的影响。
- **物理内存**：物理内存是计算机硬件上实际存在的内存（RAM）。操作系统通过 **页表** 将虚拟内存和物理内存进行映射。操作系统管理页表，确保每个进程的虚拟地址正确映射到物理内存。

内核空间和用户空间都属于虚拟内存的不同部分，操作系统使用 **虚拟内存管理机制** 来为每个进程提供独立的虚拟内存空间，并通过内存映射将其与物理内存关联。

### 4.55.6 总结

用户空间和内核空间的分离是操作系统设计中的重要安全机制，保证了进程之间的隔离和内核的稳定性。通过虚拟内存技术，操作系统为每个进程提供独立的地址空间，避免了进程之间的干扰。

## 4.56 LRU（Least Recently Used）

> [!tip] 🔗 项目关联

### 4.56.1 基本概念

- **LRU** 是一种 **页面置换算法**
- **原理**：当内存不足，需要置换页面时，选择**最近最久未使用的页面**进行淘汰
- 目标：**提高命中率，减少缺页中断**

### 4.56.2 工作机制

1. 每个页面记录**最近使用时间**
2. 当需要替换页面时：
    - 找到**最久未访问的页面**
    - 将其置换到磁盘或替换掉
3. 新页面加载到该位置

### 4.56.3 举例

假设内存只能存 3 页，访问序列：A B C A D

> 注意：淘汰的页面是**最近最少被访问的**

### 4.56.4 LRU 的实现方法

1. **链表法**
    - 每次访问页面，将其移到链表头
    - 链表尾部为最久未使用页面
2. **栈法**（栈模拟访问顺序）
3. **计数法**
    - 给每个页面一个时间戳或计数器，记录最后访问时间

### 4.56.5 优势

- **命中率高**：近似于最优置换（OPT）
- **局部性原理匹配**：最近使用的页面可能再次被访问

### 4.56.6 缺点

- **实现开销大**：每次访问需更新链表或计数
- **硬件支持复杂**：在嵌入式系统中可能成本高

### 4.56.7 总结

> LRU 淘汰策略总是选择最近最久未使用的页面置换，适用于具有局部性原理的场景。

> LRU = 最近不常用的页面先淘汰。

**实现思路**

**要求**

1. **O(1) 时间查找**（是否命中缓存）
2. **O(1) 时间更新使用记录**（最近访问的放前面）

**常见实现方式**

**C++ 代码示例（哈希表 + 双向链表）**

```cpp
    Node* head; // dummy head
    Node* tail; // dummy tail

    // 移动节点到链表头
    void moveToHead(Node* node) {
        removeNode(node);
        addToHead(node);
    }

    void removeNode(Node* node) {
        node->prev->next = node->next;
        node->next->prev = node->prev;
    }

    void addToHead(Node* node) {
        node->next = head->next;
        node->prev = head;
        head->next->prev = node;
        head->next = node;
    }

    Node* removeTail() {
        Node* node = tail->prev;
        removeNode(node);
        return node;
    }

public:
    LRUCache(int cap): capacity(cap) {
        head = new Node(0, 0);
        tail = new Node(0, 0);
        head->next = tail;
        tail->prev = head;
    }

    int get(int key) {
        if (map.find(key) == map.end()) return -1;
        Node* node = map[key];
        moveToHead(node);
        return node->value;
    }

    void put(int key, int value) {
        if (map.find(key) != map.end()) {
            Node* node = map[key];
            node->value = value;
            moveToHead(node);
        } else {
            Node* node = new Node(key, value);
            map[key] = node;
            addToHead(node);
            if (map.size() > capacity) {
                Node* tailNode = removeTail();
                map.erase(tailNode->key);
                delete tailNode;
            }
        }
    }
};

int main() {
```

**LRU 流程图**

```text
访问 key：
  命中：
    - 从链表中删除该节点
    - 插入到链表头
  未命中：
    - 创建新节点插到头部
    - 如果超容量，删除链表尾部节点
```

- **要点**：哈希表在平均情况下提供近似 O(1) 查找；双向链表可在已有节点指针的前提下 O(1) 更新访问顺序；头部是最新访问，尾部是最久未访问，淘汰时移除尾节点。

## 4.57 虚拟文件系统（VFS, Virtual File System）

### 4.57.1 基本概念

- **VFS** 是操作系统内核提供的一层**抽象接口**
- **作用**：为用户和应用程序提供统一的文件操作接口，而不关心底层具体文件系统（如 ext4、FAT、NTFS）
- 用户程序通过 VFS 调用标准接口，内核根据挂载的实际文件系统执行操作

### 4.57.2 VFS 的核心作用

1. **统一接口**
    - 提供统一的文件操作函数，如 open(), read(), write(), close()
    - 屏蔽底层文件系统差异
2. **支持多文件系统**
    - 内核可以同时挂载多种文件系统
    - VFS 通过抽象层管理不同文件系统的具体实现
3. **文件操作抽象**
    - VFS 定义了核心数据结构：
        - **inode**：文件元信息（大小、权限、时间戳）
        - **dentry**：目录项信息
        - **file**：打开文件的上下文（偏移量、状态）
4. **挂载机制**
    - 不同文件系统通过挂载（mount）统一到 VFS 树
    - 应用程序无需知道文件实际存储位置

### 4.57.3 工作流程示意

1. 用户程序调用 open("/home/test.txt")
2. 系统调用进入内核，VFS 接口处理请求
3. VFS 查找对应 inode 和 dentry
4. 根据挂载的底层文件系统（ext4 等）执行实际读写操作
5. 返回结果给用户程序

### 4.57.4 优势

- **跨文件系统透明性**：应用程序不依赖底层文件系统类型
- **统一管理**：简化内核文件管理逻辑
- **可扩展性**：支持多种文件系统挂载与卸载

### 4.57.5 总结

> VFS 是文件系统的抽象层，为不同底层文件系统提供统一接口，实现文件操作透明化和可扩展性。

> 虚拟文件系统让用户看到的是统一文件接口，而底层可挂载任意文件系统。
