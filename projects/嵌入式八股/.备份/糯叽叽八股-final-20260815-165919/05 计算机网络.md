## 1.1 OSI七层模型

### 1.1.1 概念

- **OSI（Open Systems Interconnection）七层模型**
- 由 **国际标准化组织（ISO）** 提出
- 目的是**实现不同厂商设备之间的互联和通信**
- 将网络通信划分为 **七个层次**，每层提供特定功能

OSI（Open Systems Interconnection）七层模型是一个**网络通信分层参考模型**，用于描述数据在网络中是如何从发送端传输到接收端的。每一层只关注特定功能，层与层之间相互独立、相互协作。

### 1.1.2 物理层（Physical Layer）

1. 负责比特流的传输
2. 定义电气特性、接口规范、信号电压、传输速率
3. 不关心数据含义，只负责 0 和 1

典型内容：

- 网线、光纤
- 电压、电流
- RJ45 接口

### 1.1.3 数据链路层（Data Link Layer）

1. 负责在相邻节点间传输数据帧
2. 提供错误检测和流量控制
3. 将物理层比特流组织成帧（Frame）

典型内容：

- MAC 地址
- 以太网协议（Ethernet）
- 交换机（Switch）
- VLAN
- PPP（点对点协议）

### 1.1.4 网络层（Network Layer）

1. 负责数据包的路由选择和转发
2. 提供逻辑寻址（IP 地址）
3. 处理数据包的分片和重组

典型内容：

- IP 地址
- IP 协议（IPv4 / IPv6）
- 路由协议（RIP、OSPF、BGP）
- 路由器（Router）
- ICMP（Ping 命令）

### 1.1.5 传输层（Transport Layer）

1. 提供端到端通信
2. 负责数据分段、重组
3. 保证或不保证数据可靠性

典型内容：

- TCP（可靠、有序）
- UDP（不可靠、高实时性）
- 端口号

### 1.1.6 会话层（Session Layer）

1. 负责建立、管理和终止会话
2. 控制通信过程中的会话状态
3. 支持会话同步和恢复

典型内容：

- 会话管理
- 断点续传控制（概念层面）

### 1.1.7 表示层（Presentation Layer）

1. 负责数据格式转换
2. 处理数据编码、加密、解密、压缩
3. 屏蔽不同系统的数据表示差异

典型内容：

- 字符编码（ASCII、UTF-8）
- 数据压缩
- SSL/TLS（概念上属于该层）

### 1.1.8 应用层（Application Layer）

1. 直接面向用户和应用程序
2. 提供网络服务接口
3. 定义具体应用协议

典型内容：

- HTTP / HTTPS
- FTP
- SMTP

## 1.2 TCP/IP四层模型

TCP/IP 模型是互联网协议族常用的分层方式，常见的四层划分如下。不同教材也会把“网络接口层”再拆成数据链路层和物理层，或把应用层对应到 OSI 的上三层；这是分层视角不同，不是协议功能重复。

| 层次 | 主要职责 | 常见协议/技术 | 典型数据单元 |
|---|---|---|---|
| 应用层 | 为应用提供语义、消息格式和服务接口 | HTTP、DNS、MQTT、SSH、SMTP | 消息/数据 |
| 传输层 | 进程到进程的复用、可靠性或低开销报文语义 | TCP、UDP、SCTP、QUIC（其可靠传输由 QUIC 实现） | TCP 段/UDP 数据报 |
| 网际层 | IP 寻址、路由和尽力而为的数据报转发 | IPv4、IPv6、ICMP | IP 数据报 |
| 网络接口层 | 在具体链路上封装帧并发送比特 | Ethernet、Wi‑Fi、PPP、驱动/网卡 | 帧/比特 |

TCP/IP 模型并不意味着每个应用都必须同时使用 TCP 和 IP：例如 DNS 可以使用 UDP 或 TCP，HTTP/3 使用 QUIC over UDP；可靠性、加密和拥塞控制由所选协议组合共同提供。

### 1.2.1 与 OSI 七层模型的对应关系

| TCP/IP 四层 | 常见 OSI 对应 | 说明 |
|---|---|---|
| 应用层 | 应用层、表示层、会话层 | TCP/IP 通常把应用语义、编码和会话管理合并描述 |
| 传输层 | 传输层 | TCP/UDP 等提供端到端传输语义 |
| 网际层 | 网络层 | IP 负责逻辑寻址和路由；ARP/ND 常作为链路邻接解析机制 |
| 网络接口层 | 数据链路层、物理层 | 具体链路的帧格式、介质访问和信号传输 |

### 1.2.2 总结

> TCP/IP 四层模型用应用层、传输层、网际层和网络接口层描述互联网通信；它是协议族的工程分层，和 OSI 七层模型不是一一对应的硬性实现边界。

## 1.3 CS模型与P2P模型

### 1.3.1 基本概念

- **CS（Client-Server，客户端-服务器）模型**
    - 典型的集中式网络通信模型
    - 客户端向服务器发送请求，服务器处理请求并返回结果
- **P2P（Peer-to-Peer，对等网络）模型**
    - 每个节点既是客户端又是服务器
    - 节点之间直接通信和共享资源

### 1.3.2 模型特点对比

| 维度 | CS（客户端/服务器） | P2P（对等网络） |
|---|---|---|
| 控制方式 | 服务器集中管理 | 节点之间分布式协作 |
| 数据位置 | 通常集中在服务器或服务集群 | 可分散在多个对等节点 |
| 访问方向 | 客户端请求、服务器响应 | 节点既可请求也可提供 |
| 易维护性 | 权限、版本和审计较集中 | 节点发现、数据一致性更复杂 |
| 扩展瓶颈 | 服务器和中心链路可能成为瓶颈 | 可通过增加节点扩展，但协调成本上升 |
| 典型场景 | Web、数据库、设备云端接入 | 文件分发、分布式账本、局域网直连 |

实际系统经常是混合模型：例如 P2P 节点通过中心服务器完成发现、认证和信令，而数据面在节点之间直连。

### 1.3.3 使用场景

**CS 模型**

- 适合集中控制、数据统一管理的应用
- 例子：
    - Web 服务（浏览器-服务器）
    - 企业内部数据库系统
    - 邮件服务

**P2P 模型**

- 适合资源分布广、节点数量多的应用
- 例子：
    - 文件共享（BitTorrent）
    - 区块链网络
    - 即时通信（部分去中心化系统）

### 1.3.4 总结

> CS 模型集中管理，客户端请求服务器处理；P2P 模型节点对等，资源共享直接通信，各自适用不同场景。

> CS 强调客户端-服务器集中控制，P2P 强调节点对等、分布式共享。

## 1.4 应用层、传输层、网络层分别解决什么问题？

### 1.4.1 应用层（Application Layer）

- **作用**：为用户和应用程序提供网络服务接口
- **解决的问题**：
    a. 定义应用数据格式（如 HTTP、FTP、MQTT）
    b. 提供不同应用间通信协议（文件传输、远程控制、消息传递）
    c. 数据表现和语义处理（编码、压缩、序列化等）
- **典型协议**：HTTP、HTTPS、FTP、SMTP、MQTT

### 1.4.2 传输层（Transport Layer）

- **作用**：实现端到端的通信，保证数据从源主机传到目标主机的应用进程
- **解决的问题**：
    a. **端口管理**：标识不同应用进程
    b. **可靠传输**（TCP）：顺序、重传、校验、流量控制
    c. **不可靠快速传输**（UDP）：低延迟、广播/组播
    d. **多路复用**：一个主机可同时处理多个连接
- **典型协议**：TCP、UDP

### 1.4.3 网络层（Network Layer）

- **作用**：实现不同网络间的数据转发与寻址
- **解决的问题**：
    a. **逻辑地址分配**：IP 地址标识设备位置
    b. **路由选择**：选择最优路径把数据从源传到目的
    c. **分片和重组**：跨网络大数据分片传输
    d. **拥塞控制**（部分）与差错检测（部分）
- **典型协议**：IP、ICMP、ARP（辅助映射 IP → MAC）

### 1.4.4 总结

- **应用层**：用户关心的数据内容
- **传输层**：保证数据正确、顺序到达对应应用
- **网络层**：确定数据怎么从一台主机送到另一台主机

**应用层解决应用通信问题，传输层提供端口复用以及 TCP 的可靠传输或 UDP 的尽力而为传输，网络层解决跨网络寻址和路由转发。**

## 1.5 数据在网络中是如何逐层封装和解封装的

### 1.5.1 数据封装过程（发送端）

- **应用层**：
    - 生成原始数据（消息、文件、请求等）
    - 添加应用层协议头（如 HTTP/FTP 协议头）
    - 输出 **应用数据（Application Data）**
- **传输层**：
    - 为应用数据加上 **传输层头（TCP/UDP Header）**
    - TCP 会增加序列号、端口号、校验和等信息
    - 输出 **段（Segment，TCP）或数据报（Datagram，UDP）**
- **网络层**：
    - 为段或数据报加上 **网络层头（IP Header）**
    - 包含源 IP、目标 IP、TTL 等信息
    - 输出 **数据包（Packet）**
- **数据链路层**：
    - 为数据包加上 **帧头和帧尾（MAC 地址、校验码等）**
    - 输出 **帧（Frame）**
    - 发送到物理介质（以太网、电信号或光信号）

### 1.5.2 数据解封装过程（接收端）

- **数据链路层**：
    - 接收帧，验证 MAC 地址和 CRC
    - 去掉帧头/帧尾，提取 **数据包**
- **网络层**：
    - 解析 IP 头，确认目标 IP 是否匹配
    - 去掉 IP 头，提取 **段/数据报**
- **传输层**：
    - 解析端口号，选择目标应用进程
    - TCP 按序号、校验和和连接状态处理字节流，再把数据交给目标套接字

### 1.5.3 总结

- **封装**：发送端从应用到物理层逐层加头（有时加尾），形成帧
- **解封装**：接收端从物理层到应用层逐层解析头，恢复原始数据
- **关键点**：
    a. 每层只关心自己的头信息
    b. 上层协议对下层透明
    c. 可靠性和安全性由具体协议提供：TCP 可可靠有序交付，UDP/IP 仍是尽力而为，TLS/应用层还要另行提供安全与业务确认

**数据从应用层开始封装，每层加上自己的协议头，经过物理层发送；接收端逐层解封装，最终恢复应用数据。**

## 1.6 什么是TCP/IP？

### 1.6.1 基本概念

- **TCP/IP（Transmission Control Protocol / Internet Protocol）**
    - 是一组**网络通信协议**，定义了计算机网络上设备如何进行数据交换
    - 支撑着全球互联网及大多数局域网的基础网络协议
    - 名称来自 TCP 与 IP，但 TCP/IP 是包含 UDP、ICMP、DNS、HTTP 等协议的协议族，不能只理解为两个协议

### 1.6.2 TCP 和 IP 协议

- **IP（Internet Protocol）**
    - 负责**地址分配**与**路由选择**
    - 将数据包从源主机传送到目标主机
    - **无连接**：不保证数据包的顺序或可靠性
    - 包括 **IPv4** 和 **IPv6** 两个版本
- **TCP（Transmission Control Protocol）**
    - 提供**可靠的端到端连接**
    - 确保数据在传输过程中的完整性和顺序
    - **面向连接**：通过三次握手建立连接状态；可靠交付还要依靠序号、ACK、重传、流量和拥塞控制
    - 支持流量控制、重传机制和拥塞控制

### 1.6.3 TCP/IP 四层模型

- **应用层**：为应用提供服务接口（如 HTTP, FTP）
- **传输层**：提供端到端的进程通信；TCP 提供可靠有序字节流，UDP 提供尽力而为的数据报语义
- **网络层**：实现数据包的路由与地址寻址（如 IP）
- **网络接口层**：管理物理传输（如 Ethernet）

### 1.6.4 工作流程

1. **IP** 协议将数据包从源地址发送到目标地址，负责寻址和路由选择
2. **TCP** 协议确保数据可靠到达，进行分段、重传和顺序控制
3. 数据从应用程序层进入传输层（TCP）并通过网络层（IP）到达目的地

### 1.6.5 总结

> TCP/IP 是全球互联网和局域网通信的基础协议，TCP 提供可靠传输，IP 负责地址路由，形成多层网络架构。

> TCP/IP 是一套网络协议族：TCP 提供一种可靠字节流传输，UDP 等协议提供其他传输语义，IP 负责网络层寻址和路由，是现代网络通信的基础。

## 1.7 子网掩码

### 1.7.1 基本概念

- **子网掩码（Subnet Mask）用于划分 IP 地址的网络部分和主机部分**
- 与 IP 地址配合使用，确定一台主机属于哪个子网
- **作用**：实现网络分段、提高网络管理效率、节省 IP 地址

### 1.7.2 原理

- **IP 地址** = **网络号 + 主机号**
- **子网掩码**由连续的 1 和连续的 0 组成：
    - **1** 对应网络位
    - **0** 对应主机位

**示例：**

IP 地址：192.168.1.10

子网掩码：255.255.255.0

- 二进制表示：
    - IP：11000000.10101000.00000001.00001010
    - 掩码：11111111.11111111.11111111.00000000
- 网络号 = IP & 子网掩码 = 192.168.1.0
- 主机号 = IP & (~子网掩码) = 0.0.0.10

### 1.7.3 功能

1. **区分网络和主机**
    - 网络号相同 → 属于同一子网
    - 网络号不同 → 不同子网
2. **划分子网**
    - 可以将大网络划分为多个小子网，提高网络管理灵活性
3. **确定广播地址**
    - 广播地址 = 网络号 + 全 1 的主机位
    - 用于子网内广播

### 1.7.4 常用子网掩码

> “/24” 表示子网掩码有 24 位 1

### 1.7.5 总结

> 子网掩码用来区分 IP 地址的网络部分和主机部分，实现子网划分和网络管理。

> 子网掩码通过 1 表示网络位、0 表示主机位，确定 IP 属于哪个子网。

## 1.8 MAC 地址和 IP 地址的区别

### 1.8.1 MAC 地址的概念

- **MAC（Media Access Control）地址**是网卡的**物理地址**
- 通常由厂家在出厂时写入
- 长度：**48 位（6 字节）**
- 表示形式：XX:XX:XX:XX:XX:XX
- 工作层次：**数据链路层（OSI 第二层）**
- 作用：**在同一局域网内唯一标识一台设备**

### 1.8.2 IP 地址的概念

- **IP 地址**是网络中的**逻辑地址**
- 由网络管理员或 DHCP 动态分配
- IPv4：**32 位**
- IPv6：**128 位**
- 工作层次：**网络层（OSI 第三层）**
- 作用：**标识设备在网络中的位置，实现跨网络通信**

### 1.8.3 核心区别对比

| 维度 | MAC 地址 | IP 地址 |
|---|---|---|
| 作用 | 在链路/局域网中标识接口 | 在网络层标识接口的逻辑位置 |
| 类型 | 链路层地址，常见以太网为 48 位 | IPv4 32 位或 IPv6 128 位 |
| 分配 | 可由厂商、软件或管理配置，不能简单视为永久不变 | 静态配置、DHCP、SLAAC 等 |
| 转发范围 | 通常只在一个二层广播域内有效 | 可跨路由器转发 |
| 改变时机 | 换网卡、虚拟网卡、MAC spoofing 或接口配置 | 换网络、租约变化、路由/地址配置变化 |
| 查找关系 | ARP（IPv4）或邻居发现（IPv6）把 IP 映射到链路层地址 | 路由表决定下一跳和出接口 |

MAC 地址不一定全球唯一，也不一定“写死在网卡上”；虚拟机、容器和软件可配置接口地址。跨网段发送时，帧的目标 MAC 通常是下一跳路由器，而不是最终主机的 MAC。

### 1.8.4 MAC 与 IP 在通信中的配合关系

- 实际通信流程：
    a. 应用层生成数据
    b. 网络层使用 **IP 地址** 确定目标网络
    c. 在 IPv4 中通过 **ARP**、在 IPv6 中通过 **邻居发现（ND）** 将下一跳 IP 解析为链路层地址
    d. 数据链路层使用 **MAC 地址**完成帧传输
- 总结一句话：
    - **IP 负责“去哪”，MAC 负责“送给谁”**

### 1.8.5 嵌入式系统中的实际应用

- 常见场景：
    - STM32 + LWIP
    - 工业以太网
- 常见面试追问：
        - 为什么换 IP 后通常仍可通信？
            - 需要重新进行地址配置、路由和邻居解析；MAC 不变只是同一链路接口仍可使用，并非 IP 改变后无需重新建立网络状态
    - 为什么不能只用 MAC？
        - MAC 无法实现跨网段路由

### 1.8.6 总结

**MAC 地址是数据链路层的物理地址，用于局域网通信；IP 地址是网络层的逻辑地址，用于跨网络路由，两者通过 ARP 协议协同完成通信。**

## 1.9 嵌入式常用 TCP/UDP 场景对照表

### 1.9.1 远程控制与指令下发

- **应用场景**：智能仪表、工业控制器接收上位机指令
- **协议选择**：TCP
- **理由**：TCP 提供可靠、有序字节流；命令是否真正执行成功仍应由应用层返回结果确认
- **注意事项**：
    a. 指令不能丢失，顺序敏感
    b. 可结合心跳机制监测设备在线状态

### 1.9.2 数据采集与上传

- **应用场景**：传感器数据上传到服务器或云端
- **协议选择**：TCP
- **理由**：TCP 可提供可靠、有序字节流；采集数据的业务落库和去重仍需应用层设计
- **典型场景**：
    a. 工业现场数据采集（温度、压力、流量）
    b. 智能电表/气表上报计量数据
    c. 车载传感器数据上报
- **注意事项**：
    - 数据量一般不大，TCP 性能开销可接受
    - 可考虑分批上传或压缩数据

### 1.9.3 远程日志与调试

- **应用场景**：嵌入式系统异常时发送日志到远程服务器
- **协议选择**：TCP
- **理由**：TCP 可提供可靠、有序字节流；日志系统仍需处理断线重连、缓冲和落盘策略
- **典型场景**：
    a. 工业网关、嵌入式 Linux 系统
    b. IoT 设备调试模式下日志回传
- **注意事项**：
    - 日志量大时注意缓冲和流量控制
    - 可异步发送，避免阻塞主任务

### 1.9.4 文件或固件传输（OTA）

- **应用场景**：固件升级或配置文件下载
- **协议选择**：TCP
- **理由**：保证文件完整性、顺序正确，支持丢包重传
- **注意事项**：
    a. 分片传输大文件，避免占用全部内存
    b. 可结合校验和或数字签名验证完整性

### 1.9.5 客户端/服务器模式的长连接

- **应用场景**：持续通信的工业网关或车载系统
- **协议选择**：TCP
- **理由**：支持长连接并提供可靠、有序字节流；心跳、重连和业务确认仍需应用层设计
- **典型场景**：
    a. 工业网关与云平台保持心跳
    b. 车载终端与调度系统实时通信
    c. 智能家居集中控制系统
- **注意事项**：
    - 定期发送心跳维持连接
    - 处理长连接断线重连机制

### 1.9.6 实时性极高、可容忍丢包场景

- **应用场景**：音视频传输、快速状态上报
- **协议选择**：UDP
- **理由**：低延迟，开销小，即使丢包也可接受
- **注意事项**：
    - 可在应用层增加简单重传或纠错机制
    - 避免频繁创建/关闭短连接

### 1.9.7 面试一句话总结

**TCP 用于可靠、顺序敏感的数据通信，如控制命令、数据采集、日志回传、OTA 升级和长连接实时通信；UDP 用于低延迟、可容忍丢包的场景，如音视频和快速状态上报。**

## 1.10 TCP的三次握手

### 1.10.1 基本概念

- 三次握手（Three-way Handshake）是 TCP 建立连接的过程
- 目的：
    a. 确认双方 **都能发送和接收数据**
    b. **同步序列号**（Sequence Number），保证可靠传输
- TCP 是 **面向连接、可靠传输** 协议，三次握手是其基础

### 1.10.2 三次握手过程

**TCP三次握手是建立可靠连接的过程，确保双方具备收发能力，并协商初始序列号。具体步骤如下：**

1. **客户端 → 服务器（SYN）**
    - **客户端** 发送一个 **SYN**（同步）标志的TCP报文，表示要建立连接，并携带一个**初始序列号（ISN，Initial Sequence Number）**。
    - 服务器收到后，知道客户端希望建立连接。
2. **服务器 → 客户端（SYN+ACK）**
    - **服务器** 返回一个 **SYN+ACK**（同步+确认）报文：
        - **SYN** 表示服务器也要建立连接，并发送自己的 **ISN**。
    - 客户端收到后，知道服务器同意建立连接，并且服务器也具备发送能力。
3. **客户端 → 服务器（ACK）**
    - **客户端** 再发送一个 **ACK**（确认）报文，确认收到服务器的 **SYN**，同时携带 **ACK = 服务器的 ISN + 1**。
    - **至此，连接建立成功，双方可以进行数据传输。**

### 1.10.3 关键点

1. **可靠性保证**
    - 确认双方都能收发数据
    - 确认初始序列号同步
2. **状态转换**
    - 客户端：CLOSED → SYN_SENT → ESTABLISHED
    - 服务器：LISTEN → SYN_RECEIVED → ESTABLISHED
3. **防止旧连接干扰**
    - TCP 序列号可防止旧重复报文被误识别

### 1.10.4 总结

> TCP 建立连接通过三次握手：客户端 SYN，服务器 SYN-ACK，客户端 ACK，确认双方序列号和收发能力，建立可靠传输的状态；它不等于应用业务已经成功。

> TCP 三次握手用 SYN 和 ACK 互相确认，完成连接状态和序列号同步；后续可靠交付还依赖 ACK、重传、流量及拥塞控制。

## 1.11 为什么 TCP 需要三次握手，而不是两次

### 1.11.1 背景

- TCP 是**面向连接、可靠传输**协议
- 建立连接的关键是：
    a. **双方确认能发送和接收数据**
    b. **序列号同步**（防止旧连接干扰）

### 1.11.2 两次握手的问题

假设只做两次握手（客户端 SYN → 服务器 SYN-ACK → 连接成功）：

1. **客户端向服务器发送 SYN**
2. **服务器收到 SYN 后发送 SYN-ACK**
3. 连接建立

**问题**：

- **客户端没有确认服务器的序列号是否收到**
- 如果网络中存在 **旧的 SYN-ACK 报文** 被误认为新连接：
    - 服务器可能认为客户端已经确认连接，但客户端实际上未收到
- 第三次握手 **客户端发送 ACK**：
    a. 确认服务器收到客户端的 SYN
    b. 确认双方的初始序列号同步
- 确保**连接双方都能发送与接收**，不会受到网络中旧报文影响

### 1.11.3 三次握手解决问题

- 第三次握手 客户端发送 ACK：
  a. 确认服务器收到客户端的 SYN
  b. 确认双方的初始序列号同步

- 确保连接双方都能发送与接收，不会受到网络中旧报文影响

---

### 1.11.4 可以优化的手段

- **TCP Fast Open（TFO）**：允许**减少三次握手的延迟**，在握手过程中**携带部分数据**，提高首包传输速度。
- **长连接（Keep-Alive）**：减少频繁建立TCP连接的开销，提高网络效率。

### 1.11.5 总结

> TCP 三次握手的第三次确认（客户端 ACK）用于完成双方序列号同步和连接状态确认，也有助于避免旧报文被当作新连接；机密性和身份认证需要 TLS 等其他协议。

> 两次握手无法让双方都确认对方已收到自己的序列号，三次握手完成 TCP 连接状态建立；“安全”仍需 TLS 等机制提供。

## 1.12 TCP的四次挥手

### 1.12.1 基本概念

- 四次挥手（Four-way Handshake）是 TCP 断开连接的典型过程；若 ACK 与 FIN 在时序上可以合并，报文数不一定严格为四个
- 目的是**保证双方的数据都传输完成后再关闭连接**
- TCP 是**全双工通信**，发送和接收可以独立关闭，因此需要四次挥手

### 1.12.2 四次挥手过程

假设 **客户端主动关闭连接**，服务器被动关闭。

**第一次挥手**

客户端发送 **FIN** 报文，表示客户端的数据已经发送完毕，请求关闭连接。

Client → Server : FIN

客户端进入状态：FIN_WAIT_1

**第二次挥手**

服务器收到 FIN 后，回复 **ACK**，表示已经收到关闭请求。

Server → Client : ACK

服务器进入：CLOSE_WAIT

客户端进入：FIN_WAIT_2

此时连接 **还没有完全关闭**，服务器仍然可以继续发送数据。

**第三次挥手**

当服务器数据发送完毕后，也发送 **FIN** 报文，表示服务器也准备关闭连接。

Server → Client : FIN

服务器进入：LAST_ACK

**第四次挥手**

客户端收到 FIN 后，发送 **ACK** 确认。

Client → Server : ACK

客户端进入：TIME_WAIT

服务器收到 ACK 后：连接关闭

### 1.12.3 关键点

1. **全双工通信**
    - 客户端和服务器发送、接收可以独立关闭
    - 由于双方发送方向可独立关闭，典型流程需要分别交换两个 FIN 和相应 ACK；具体报文数可能因合并 ACK/FIN 而变化
2. **连接状态**
    - FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
    - 服务器：CLOSE_WAIT → LAST_ACK → CLOSED
3. **TIME_WAIT 状态**
    - 客户端在发送最后 ACK 后会进入 TIME_WAIT
    - 目的是确保服务器收到 ACK，并防止旧报文干扰新连接

### 1.12.4 总结

> TCP 四次挥手通过 FIN 和 ACK 分别关闭客户端和服务器的发送方向，确保双方数据传输完成且连接可靠关闭。

> TCP 关闭通常按四次挥手描述，因为两个方向的 FIN/ACK 可以独立进行；实际抓包中 ACK 与 FIN 可能合并，不能把“四次”当作绝对报文数。

## 1.13 为什么 TCP 断开连接是四次挥手，而不是三次

### 1.13.1 背景

- TCP 是 **全双工通信**：
    - 客户端 → 服务器 可以发送数据
    - 服务器 → 客户端 也可以发送数据
- 断开连接需要保证 **双方数据发送完成后** 再关闭
- 与建立连接不同（SYN、ACK 是同步双向序列号），关闭连接需要分别确认双方的发送完成情况

### 1.13.2 两次或三次挥手的问题

- **如果只两次：** 客户端发送 FIN，服务器返回 ACK，连接就关闭；**问题**：服务器可能还有未发送的数据，直接关闭会丢失数据
- **如果只三次：** 客户端发送 FIN → 服务器 ACK → 服务器 FIN → 客户端 ACK？；有可能客户端还没确认服务器 FIN，就直接关闭，存在**数据丢失风险**

### 1.13.3 四次挥手的必要性

1. **第一次**：客户端发送 FIN，表示自己数据发送完毕
2. **第二次**：服务器 ACK，确认收到客户端 FIN
3. **第三次**：服务器发送 FIN，表示服务器数据也发送完毕
4. **第四次**：客户端 ACK，确认收到服务器 FIN，双方可以安全关闭

> 因为 TCP 是全双工，关闭需要客户端和服务器各自发送 FIN 并确认；典型情况下分成四个报文，但 ACK/FIN 可以合并。

### 1.13.4 总结

> TCP 关闭要分别处理两个发送方向，所以通常按四次挥手解释；具体报文数取决于 FIN 与 ACK 是否能合并。

> TCP 全双工关闭需要双方各自完成 FIN 和 ACK，典型为四次，但并非协议强制的固定报文数。

## 1.14 TCP的可靠机制体现在哪？

### 1.14.1 基本概念

TCP 是 **面向连接、可靠传输** 协议，其可靠性体现在数据从发送端到接收端**准确、完整、按序**传输。

### 1.14.2 TCP 可靠机制的主要体现

1. **序列号与确认号**：发送端给字节流编号，接收端用 ACK 表示按序接收的下一个字节；序号还用于乱序重排和重复数据识别。
2. **校验和**：检测端到端传输中的比特错误；校验失败的报文会被丢弃，通常依靠重传恢复。
3. **重传机制**：包括重传计时器、快速重传等。超时阈值由 RTT 和拥塞情况估算，不是固定常数。
4. **滑动窗口与流量控制**：接收窗口 `rwnd` 防止发送端超过接收缓存能力。
5. **拥塞控制**：拥塞窗口 `cwnd` 根据网络拥塞动态调整，慢启动、拥塞避免、快速重传/恢复等算法属于实现策略。
6. **连接状态管理**：通过握手、挥手和状态机维护连接，避免把不同连接或旧报文混在一起。

TCP 的“可靠”是字节流在连接语义下的可靠、有序交付，不保证消息边界、不保证永不超时，也不等于应用层业务一定成功。

### 1.14.3 核心特点总结

1. **数据完整性** → 序列号 + ACK + 校验和
2. **顺序传输** → 序列号保证数据按正确顺序重组
3. **可靠交付** → 超时重传机制
4. **流量与拥塞控制** → 保证接收方处理能力和网络负载平衡

### 1.14.4 总结

> TCP 的可靠性通过序列号、确认应答、超时重传、流量控制、拥塞控制和校验和保证数据准确、完整、按序传输。

> TCP 的可靠机制体现在序列号、ACK、重传、流量与拥塞控制以及校验和等手段上，确保数据可靠到达。

## 1.15 HTTPS和HTTP区别

### 1.15.1 基本概念

- **HTTP（HyperText Transfer Protocol）**：是 **超文本传输协议**，用于在客户端和服务器之间传输网页数据，数据传输过程是 **明文** 的。
- **HTTPS（HyperText Transfer Protocol Secure）**：是 **HTTP 的安全版本**，通过 **SSL/TLS** 协议对数据进行加密传输，保证数据的安全性和完整性。

### 1.15.2 HTTP 与 HTTPS 的主要区别

| 维度 | HTTP | HTTPS |
|---|---|---|
| 保护 | 默认明文，容易被窃听或篡改 | 通过 TLS 提供机密性、完整性和服务器认证 |
| 端口 | 常见 80 | 常见 443，但端口不是协议本质 |
| 握手 | TCP 建连后直接传 HTTP | TCP（或 QUIC）后建立 TLS 会话，再传 HTTP |
| 身份认证 | 协议本身不验证服务器身份 | 通常通过证书链验证服务器身份 |
| 性能 | 无 TLS 握手和加解密开销 | 有握手和加密开销，但连接复用、硬件加速可降低影响 |
| 数据内容 | 请求行、头部、正文均可被中间人读取 | TLS 保护应用数据，但域名、IP、流量特征等元数据未必全部隐藏 |

HTTPS 不是“把公钥加密整个 HTTP 数据”。现代 TLS 通常使用证书完成身份认证和密钥协商，再用对称 AEAD 算法保护数据；具体流程随 TLS 版本、密码套件和 HTTP/2/3 而变化。

### 1.15.3 工作原理

- **HTTP：** 客户端与服务器通过明文传输 HTTP 请求和响应；协议本身不提供机密性和完整性保护。

**HTTPS：**

1. 客户端发送 `ClientHello`，声明支持的 TLS 版本、密码套件、扩展和密钥分享等参数。
2. 服务器返回 `ServerHello`，选择参数并发送证书链；客户端按信任库验证证书、域名和有效期。TLS 1.3 通常还会交换密钥分享，TLS 1.2 的具体握手消息则可能不同。
3. 双方根据握手得到的共享秘密运行密钥派生，发送 `Finished` 校验握手完整性，随后使用对称 AEAD 密钥保护 HTTP 数据。现代 TLS 不把整个 HTTP 数据用公钥加密，也不必把会话密钥简单理解为“客户端生成后用公钥直接加密”。

### 1.15.4 总结

> HTTPS 是 HTTP 的加密版本，通过 SSL/TLS 协议对数据进行加密，确保数据传输的安全性、完整性以及防止中间人攻击。

> HTTPS 与 HTTP 的主要区别在于 HTTPS 提供加密保护，确保数据的安全传输，而 HTTP 是明文传输，易受攻击。

## 1.16 HTTPS 的三次握手

### 1.16.1 基本概念

- **HTTPS = HTTP + SSL/TLS**
- HTTPS 建立连接不仅包括 TCP 三次握手，还要完成 **SSL/TLS 握手**，确保数据加密传输
- 主要目的是：**验证服务器身份** + **协商加密算法和密钥**

> 注意：TLS 并没有一个跨版本固定为“三次”的握手名称；下面按面试常用的阶段简化说明，并与 TCP/QUIC 承载过程区分。

### 1.16.2 HTTPS/TLS 握手过程

HTTPS 需要先建立承载连接：传统 HTTP/1.1、HTTP/2 通常先完成 TCP 三次握手，HTTP/3 则运行在 QUIC 上，不应把 TCP 三次握手称为 TLS 握手。

以 TLS 1.3 的典型流程为例：

1. **ClientHello**：客户端发送支持的版本、密码套件、SNI/ALPN、随机数和密钥分享。
2. **ServerHello 与证书**：服务器选择参数并返回证书链、密钥分享和握手参数；客户端验证证书链、域名和有效期。
3. **密钥确认**：双方由密钥分享派生握手/应用流量密钥，交换 `Finished` 消息验证握手 transcript；之后 HTTP 请求和响应使用对称 AEAD 密钥保护。

TLS 1.2 的消息顺序和密钥交换可能不同，TLS 会话复用、0-RTT、HTTP/2/3 也会改变往返次数；“三次握手”只适合作为面试中的简化说法，必须先区分 TCP、QUIC 和 TLS。

### 1.16.3 总结

> HTTPS 的安全通道由 TLS 握手建立：ClientHello/ServerHello 协商参数，证书用于身份认证，密钥交换后派生对称流量密钥；它不等同于 TCP 三次握手。

> HTTPS 在 TCP 或 QUIC 承载之上运行 TLS，具体往返次数取决于 TLS 版本、会话复用和实现，不能固定称为“三次”。

## 1.17 DNS 解析过程（访问互联网过程、域名解析过程）

### 1.17.1 基本概念

- **DNS（Domain Name System）**：域名系统，将 **域名（如 **www.example.com**）** 转换为 **IP 地址（如 192.168.1.1）**
- 目的是让用户使用**易记的域名**访问互联网资源，而计算机通过 IP 通信

### 1.17.2 访问互联网的一般过程

1. 用户在浏览器输入域名（如 www.example.com）
2. **DNS 解析**：域名 → IP
3. 浏览器通过 IP 访问服务器
4. 建立 TCP / HTTPS 连接
5. 请求资源（HTTP/HTTPS）并接收响应

### 1.17.3 DNS 解析过程

**步骤示意（递归 + 迭代查询）**

1. **浏览器缓存查询**
    - 浏览器先检查本地 DNS 缓存，若有对应 IP，直接返回
2. **操作系统缓存查询**
    - 如果浏览器缓存没有，操作系统会查本地 Hosts 文件或 DNS 缓存
3. **递归 DNS 服务器查询**
    - 操作系统将请求发送给本地 DNS 服务器（ISP 提供）
    - 本地 DNS 服务器如果没有缓存，会代用户向根 DNS 查询
4. **根 DNS 查询**
    - 根 DNS 返回顶级域名（TLD）服务器地址（如 .com 服务器）
5. **顶级域名 DNS 查询**
    - 本地 DNS 向 TLD 服务器查询，得到负责具体域名的权威 DNS 服务器地址
6. **权威 DNS 查询**
    - 本地 DNS 向权威 DNS 查询域名对应 IP
    - 权威 DNS 返回域名对应的 **IP 地址**
7. **返回客户端**
    - 本地 DNS 缓存该 IP，并返回给客户端
    - 浏览器通过该 IP 发起 TCP/HTTPS 连接访问网站

### 1.17.4 缓存机制

- **浏览器缓存**：避免重复解析
- **操作系统缓存**：减轻 DNS 查询压力
- **DNS 服务器缓存**：提高解析速度和减少网络负载

### 1.17.5 总结

> DNS 解析过程是域名 → IP 的转换，经过浏览器/系统缓存、本地 DNS、根 DNS、TLD DNS 和权威 DNS 层层查询，最终获取访问服务器的 IP。

## 1.18 ARP（地址解析协议）的工作过程

### 1.18.1 基本概念

- ARP（Address Resolution Protocol）：地址解析协议，主要作用是将 IP 地址 转换为 MAC 地址
- 工作在 网络层 和 数据链路层之间，用于 局域网内 确定目标设备的硬件地址（MAC 地址）

### 1.18.2 ARP 的工作过程

1. 设备发送 ARP 请求
    - 当设备（如计算机）需要向另一个设备发送数据时，如果不知道目标设备的 MAC 地址，就会发送 ARP 请求。
    - ARP 请求是一个广播包，内容包含 目标 IP 地址，并请求对应的 MAC 地址。

2. 网络中的设备接收到 ARP 请求
    - 局域网中所有设备都会收到 ARP 请求，但只有 目标 IP 地址 对应的设备才会响应。

3. 目标设备返回 ARP 响应
    - 目标设备收到 ARP 请求后，使用自己的 MAC 地址 和 IP 地址 返回给请求设备一个 ARP 响应。
    - ARP 响应是 单播，即只发送给请求的设备。

4. 请求设备接收到 ARP 响应并缓存
    - 请求设备收到 ARP 响应后，解析出目标设备的 MAC 地址，并将该信息 缓存到 ARP 表 中，缓存时间一般为几分钟。

5. 数据发送
    - 设备获取了目标设备的 MAC 地址后，使用该地址进行数据帧的发送。
    - 以后若需要再次向同一设备发送数据，设备可以直接查询 ARP 表，无需再次发送 ARP 请求。

### 1.18.3 ARP 缓存与冲突

- ARP 缓存：存储设备 IP 地址和 MAC 地址的映射表
    - 一般会缓存一定时间（例如 2~10 分钟），避免频繁发送 ARP 请求。

- ARP 冲突：如果两个设备配置了相同的 IP 地址，它们会在 ARP 请求时同时回应，导致 ARP 冲突，并引起网络通信问题。

### 1.18.4 总结

> ARP 通过发送广播请求、获取目标设备的 MAC 地址并缓存，实现了 IP 地址到 MAC 地址的转换，使得局域网内的通信可以基于硬件地址进行。

> ARP 通过广播请求并获取响应，完成 IP 地址到 MAC 地址的转换，确保局域网内设备可以相互通信。

## 1.19 如何应对短连接、高并发的场景？

### 1.19.1 短连接与高并发的特点

- **短连接**：连接建立快、断开快（如 HTTP 短连接）
- **高并发**：同一时间有大量请求到达
- 主要问题：
    - 频繁建立/释放连接，系统开销大
    - 文件描述符、端口、内存资源容易耗尽
    - 线程/进程切换成本高
- 常见方式：
    - select：fd 数量有限，效率低
    - poll：无 fd 数量限制，但仍是轮询
    - epoll（Linux 常用）：
        - 事件驱动
        - 支持高并发
        - 等待阶段通常只返回就绪事件；具体复杂度取决于事件数量、内核版本和使用方式，不能笼统承诺严格 O(1)
- 适用场景：
    - Linux 服务器
    - 网络服务、嵌入式网关

### 1.19.2 使用 I/O 多路复用机制

- 核心思想：一个线程同时监听多个 socket
- 常见方式：
    - select：fd 数量有限，效率低
    - poll：无 fd 数量限制，但仍是轮询
    - epoll（Linux 常用）：
    - 事件驱动
    - 支持高并发
    - 等待阶段通常只返回就绪事件；具体复杂度取决于事件数量、内核版本和使用方式，不能笼统承诺严格 O(1)

- 适用场景：
    - Linux 服务器
    - 网络服务、嵌入式网关

---

### 1.19.3 采用线程池 / 任务队列

- 避免“来一个请求创建一个线程”
- 思路：
    - 主线程负责 accept
    - 工作线程从任务队列中取请求处理
- 优点：
    - 减少线程创建和销毁开销
    - 控制并发线程数量，防止系统被打爆
- 嵌入式中常见：
    - pthread + 任务队列
    - RTOS 中的任务池

### 1.19.4 使用连接复用或长连接（能用就别短）

- 能避免短连接就避免：
    - HTTP Keep-Alive
    - TCP 长连接
- 优点：
    - 减少三次握手/四次挥手
    - 降低 CPU 和网络开销
- 嵌入式场景：
    - MQTT
    - 私有 TCP 协议心跳机制

### 1.19.5 限流与背压机制

- 防止系统过载
- 常见手段：
    - 限制最大连接数
    - 限制请求速率（QPS）
    - 超出直接拒绝或丢弃
- 嵌入式系统尤为重要：
    - CPU、内存资源有限
    - 实时任务不能被拖死

### 1.19.6 减少单次请求的处理开销

- 优化点：
    - 减少动态内存分配（malloc/free）
    - 使用对象池、内存池
    - 避免阻塞操作（磁盘、网络）
- 原则：
    - 请求处理要“短、快、无阻塞”

### 1.19.7 总结

**通过 epoll + 线程池 + 限流机制，应对短连接和高并发，避免频繁创建线程和阻塞 I/O，提升系统吞吐和稳定性。**

## 1.20 说说 WebSocket与socket的区别

### 1.20.1 基本概念

- **Socket**：底层网络通信接口，提供进程间或者设备间的数据传输能力，支持 **TCP** 或 **UDP** 协议。
- **WebSocket**：通常在 TCP 上运行的应用层协议，专为 **浏览器和服务器之间的全双工通信**设计；也可通过 HTTP/2 或 HTTP/3 的相应扩展承载。

### 1.20.2 主要区别

| 维度 | Socket | WebSocket |
|---|---|---|
| 层次 | 编程接口/抽象端点，可承载 TCP、UDP 等 | 基于 HTTP Upgrade（或 HTTP/2/3 扩展）的应用层协议 |
| 通信对象 | 任意支持 socket 的进程、设备或主机 | 主要用于浏览器与服务器之间的持久双向通信 |
| 数据模型 | TCP 是字节流，UDP 是报文 | WebSocket 有消息帧、控制帧、掩码和关闭握手 |
| 建连方式 | 由应用选择 `socket`、`connect`、`bind` 等 | 先完成 HTTP 握手，再升级为 WebSocket |
| 浏览器支持 | 浏览器不能直接任意调用原始 TCP socket | 浏览器提供标准 WebSocket API |
| 适用场景 | 底层网络服务、设备通信、实时传输 | Web 实时推送、在线协作、浏览器控制通道 |

WebSocket 通常运行在 TCP 上，因此仍会受到 TCP 的有序字节流和断线问题影响；它不是“Socket 的另一种实现”，而是建立在传输连接之上的应用协议。

### 1.20.3 WebSocket 的优势

1. **全双工通信**：客户端和服务器可以随时发送和接收数据
2. **节省资源**：一次握手后保持连接，避免频繁 HTTP 请求的开销
3. **实时性高**：适合实时数据推送场景

### 1.20.4 总结

> Socket 是底层通信接口，可基于 TCP 或 UDP；WebSocket 是通常基于 TCP、也可通过 HTTP/2/3 承载的应用层协议，专为浏览器和服务器的实时全双工通信设计。

> WebSocket 是面向浏览器的应用层全双工协议，而 Socket 是更底层的网络通信接口；传统 WebSocket 多基于 TCP，现代扩展也可使用 HTTP/2/3 承载。

## 1.21 TCP的流量控制

### 1.21.1 基本概念

- **流量控制**：用于控制发送端的发送速率，以防止接收端处理不过来而丢失数据。
- **TCP 流量控制**是通过**窗口机制**来实现的，限制发送方在途数据量，避免接收方缓冲区被压垮；它是可靠传输的一部分，但不单独保证网络不丢包。

### 1.21.2 TCP 流量控制的实现机制

1. **接收窗口（Receive Window）**：
    - 接收方会在 ACK 等报文的 TCP 首部中通告 **接收窗口大小（Window Size）**，表示当前可接收的数据量；窗口更新的频率和是否携带在某个 ACK 中由实现及延迟 ACK 等策略决定。
    - 发送方根据接收窗口的大小决定每次发送的数据量，防止数据超过接收方的处理能力。
2. **滑动窗口机制**：
    - 在 TCP 连接中，发送方和接收方都会维护一个 **滑动窗口**，随着数据的确认，窗口会向前滑动。
    - 发送方可以在接收方窗口内发送数据，当接收方缓冲区空间不足时，接收方会通过调整接收窗口大小来告诉发送方**暂停发送**，直到缓冲区有空余空间。
3. **流量控制过程**：
    - 发送方根据接收到的窗口大小决定允许在途的数据量，可以连续发送多个段；ACK 会推进确认范围和窗口，而不是每个段都必须停下来等待。
    - 接收方通过调整窗口大小来控制流量，防止发送方发送过多的数据而导致溢出。

### 1.21.3 流量控制的特点

- **动态调整**：接收方会根据自己的缓冲区情况动态调整接收窗口大小。
- **可靠性边界**：流量控制可避免因接收方缓存不足而继续发送，但网络丢包仍由 TCP 的序号、ACK 和重传机制处理。
- **避免拥塞**：流量控制和拥塞控制结合使用，确保网络资源合理分配。

### 1.21.4 总结

> TCP 流量控制通过滑动窗口和接收方窗口限制在途数据，避免接收方缓存被压垮；它与序号、ACK、重传等机制共同构成可靠传输。

> TCP 流量控制通过动态调整接收窗口控制发送端速率，防止接收方缓冲区溢出；网络丢包的恢复仍由 TCP 重传等机制负责。

## 1.22 TCP的拥塞控制

### 1.22.1 基本概念

- **拥塞控制**：用于避免网络过载，防止过多的数据导致网络的性能下降，确保数据包的有效传输。
- TCP 的拥塞控制机制通过动态调整数据发送速率来控制网络的负载，从而避免网络拥塞。

### 1.22.2 拥塞控制的四种算法

1. **慢启动（Slow Start）**
    - 连接开始时，发送方以实现和标准允许的初始拥塞窗口（通常按若干 MSS 计算）开始发送，并在确认到达时增长；具体初值和增长细节受 TCP 版本、实现和配置影响。
    - 在未达到慢启动阈值且没有拥塞信号时，窗口通常按 RTT 呈指数级增长，但实际增长会受 ACK 聚合、接收窗口和实现算法影响。
2. **拥塞避免（Congestion Avoidance）**
    - 当拥塞窗口达到阈值（**慢启动阈值**）时，进入拥塞避免阶段，窗口每经过一个 RTT 只增加一个 MSS（线性增长），避免网络快速过载。
3. **快速重传（Fast Retransmit）**
    - 经典 Reno 规则是在收到三个重复 ACK 后快速重传；SACK、ACK 计数、RACK 等现代实现可能使用不同的丢包判定条件。
4. **快速恢复（Fast Recovery）**
    - 经典 Reno 会在快速重传后降低 `cwnd`（常见描述是减半）并进入恢复/拥塞避免；CUBIC、BBR 等算法的窗口调整和恢复过程不同，不能把“减半”当作所有 TCP 实现的固定规则。

### 1.22.3 拥塞控制过程

- **慢启动阶段**：初始拥塞窗口由标准、实现和配置共同决定，未出现拥塞时通常随 RTT 快速增长。
- **达到阈值后**：进入拥塞避免阶段，窗口线性增长，逐步增加网络吞吐量。
- **网络出现丢包**：经典 Reno 可由重复 ACK 触发快速重传和快速恢复；现代实现也可能依据 SACK/RACK 或其他信号采取不同动作。

### 1.22.4 总结

> TCP 拥塞控制通过慢启动、拥塞避免、丢包检测和恢复等机制动态调整发送速率；具体算法和参数取决于 TCP 实现、标准版本和配置，不能简单归结为固定的“四步”或固定减半规则。

> 面试中可以用 Reno 的慢启动、拥塞避免、快速重传/恢复作入门模型，同时说明现代 CUBIC、BBR 等实现的行为和参数可能不同。

## 1.23 TCP的粘包和拆包

### 1.23.1 基本概念

- **粘包**：由于 TCP 是 **流式协议**，它没有消息边界的概念，因此数据可能会被“粘”在一起，导致接收方无法正确区分多个包。
- **拆包**：指的是接收方从 TCP 数据流中无法正确分离消息，导致一个包被分割成多个部分接收。

### 1.23.2 粘包的原因

1. **TCP 是流式协议**：
    - TCP 传输数据时，数据以字节流的方式发送，不区分消息的边界。应用层将多个数据包一起发送，TCP 可能将这些包合并在一起发送。
2. **发送方发送过多数据**：
    - 当应用层连续发送多个小数据包时，TCP 会根据网络状况对数据进行打包，可能将多个小包合并成一个较大的包。
3. **网络延迟和缓冲区问题**：
    - 发送缓冲、Nagle/延迟 ACK 及调度时机可能改变分段和到达批次；网络延迟本身不改变 TCP 的消息边界。

### 1.23.3 拆包的原因

1. **传输分段与接收读取大小独立**：
    - TCP 会受 MSS、路径 MTU、拥塞窗口和实现策略影响分段；应用层一次 `send()` 的长度既不是必须的传输单位，也不对应接收端一次 `recv()` 的长度。
2. **TCP 分段机制**：
    - TCP 会根据网络状况动态调整发送的数据量，可能会将应用层发送的较大数据包拆分成多个小段进行传输。

### 1.23.4 解决粘包和拆包问题的常用方法

1. **固定长度包**：
    - 应用层协议可以规定每个数据包的长度是固定的，这样接收方就可以准确分割数据包。但是这限制了数据的灵活性，且不适用于动态数据量的场景。
2. **特殊分隔符**：
    - 在每个数据包的结尾加上特定的分隔符（如 \n 或 \r\n），接收方通过分隔符来区分包。这种方法适用于文本数据的传输。
3. **包头定义长度**：
    - 在每个包的头部添加 **包长度字段**，指明数据部分的长度。接收方读取包头的长度信息，来决定读取多少数据。常见于许多协议（如 HTTP、FTP）中。
4. **Nagle 算法**（避免小包过多）：
    - TCP 中的 Nagle 算法可能合并小段、减少小报文数量，但它不提供应用层消息边界，不能用来解决粘包/拆包；消息边界仍需由应用层协议定义。

### 1.23.5 总结

> TCP 的粘包和拆包问题源于它是流式协议，数据传输过程中可能会出现多个数据包合并（粘包）或拆分（拆包）。解决方法包括使用固定长度包、分隔符、包头长度字段等手段。

> TCP 的粘包和拆包问题是由于其流式特性导致的，应用层可以通过固定长度、分隔符、包头长度等方法来解决这一问题。

## 1.24 什么是socket?

### 1.24.1 Socket 的本质

- Socket 是 **操作系统提供的一种通信机制**
- 位于 **应用层与传输层（TCP / UDP）之间**
- 应用程序通过 Socket 使用网络，而不用直接操作底层协议

可以把它理解为：

> **程序访问网络的“插口”**

### 1.24.2 Socket 通信的基本要素

一个 Socket 通信至少需要以下信息：

1. **IP 地址**（定位主机）
2. **端口号**（定位进程）
3. **协议类型**
    - TCP（可靠、面向连接）
    - UDP（不可靠、无连接）

常说的 **五元组**：

```text
协议 + 源IP + 源端口 + 目的IP + 目的端口
```

### 1.24.3 Socket 的常见类型

**TCP Socket**

- 面向连接
- 可靠传输（确认、重传、排序）
- 典型应用：
    - HTTP / HTTPS
    - FTP

- **UDP Socket** 无连接；不保证可靠性；速度快、开销小

典型应用：

- 视频/语音
- DNS
- 实时通信

特点：

- 一次发送一个数据包
- 可能丢包、乱序

### 1.24.4 Socket 通信的基本流程（以 TCP 为例）

**服务器端：**

1. socket() —— 创建套接字
2. bind() —— 绑定 IP 和端口
3. listen() —— 监听
4. accept() —— 接收客户端连接
5. recv()/send() —— 数据通信

**客户端：**

1. socket()
2. connect() —— 连接服务器
3. send()/recv()

### 1.24.5 Socket 和嵌入式 / Linux 的关系

在 **嵌入式 Linux / RTOS + TCP/IP 协议栈** 中：

- Socket 是 **网络编程的统一接口**
- 底层可能是：
    - lwIP（STM32 + FreeRTOS）
    - Linux 内核网络栈

例如：

- 设备 ↔ 上位机通信
- 嵌入式设备联网
- OTA 升级

### 1.24.6 总结

> **Socket 是操作系统提供的网络通信接口，应用程序通过 Socket 使用 TCP/UDP 协议，实现进程间的网络数据通信。**

- **网络编程**：通过 **Socket API** 在应用程序中实现网络通信，通常用于构建客户端和服务器之间的通信。
- Socket 支持 **TCP**（面向连接）和 **UDP**（无连接）两种协议。

## 1.25 socket网络编程

### 1.25.1 基本概念

- Socket：是网络通信的端点，通过它，应用程序可以进行数据传输。
- 网络编程：通过 Socket API 在应用程序中实现网络通信，通常用于构建客户端和服务器之间的通信。
- Socket 支持 TCP（面向连接）和 UDP（无连接）两种协议。

### 1.25.2 Socket 编程的步骤

1. 创建套接字（socket）
    - 通过 socket() 函数创建套接字，指定通信协议（如 SOCK_STREAM 为 TCP，SOCK_DGRAM 为 UDP）。

```c
int sockfd = socket(AF_INET, SOCK_STREAM, 0);  // TCP socket
```

1. 绑定套接字（bind）
    - 对于服务器端，需要将套接字与具体的 IP 地址和端口号进行绑定，确保服务器监听指定端口。

```c
struct sockaddr_in server_addr;
server_addr.sin_family = AF_INET;
server_addr.sin_port = htons(8080);
server_addr.sin_addr.s_addr = INADDR_ANY; // 任意IP
bind(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));
```

2. 监听连接（listen）
    - 服务器使用 listen() 函数监听客户端的连接请求。

```c
listen(sockfd, 5);  // 监听最大 5 个连接
```

3. 接受连接（accept）
    - 服务器调用 accept() 函数接受来自客户端的连接请求，并返回一个新的套接字，用于与客户端进行通信。

```c
int client_sock = accept(sockfd, (struct sockaddr*)&client_addr, &client_len);
```

4. 连接服务器（connect）
    - 客户端使用 connect() 函数连接服务器，指定服务器的 IP 地址和端口号。

```c
struct sockaddr_in server_addr;
server_addr.sin_family = AF_INET;
server_addr.sin_port = htons(8080);
server_addr.sin_addr.s_addr = inet_addr("192.168.1.1");
connect(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));
```

5. 数据传输（send/recv 或 write/read）
    - 使用 send() 或 recv() 进行数据的发送与接收。客户端和服务器通过这些函数进行数据交换。

```c
send(sockfd, buffer, strlen(buffer), 0);
    ssize_t n = recv(sockfd, buffer, sizeof(buffer) - 1, 0);
    if (n > 0) {
        buffer[n] = '\0';       // 仅在把数据当作 C 字符串时添加终止符
    }
```

6. 关闭连接（close）
    - 数据传输完成后，客户端和服务器调用 close() 关闭套接字，释放资源。

```c
close(sockfd);
```

> 下面代码是教学示例，省略了 `bind`/`listen`/`connect`/`send` 的完整错误处理；生产代码还应处理短写、`EINTR`、超时以及 TCP 的应用层消息边界。

### 1.25.3 TCP 编程示例

**服务器端：**

```c
#include <stdio.h>
#include <string.h>
#include <arpa/inet.h>
#include <unistd.h>

int main() {
    int sockfd, client_sock;
    struct sockaddr_in server_addr, client_addr;
    char buffer[1024];
    socklen_t client_len = sizeof(client_addr);

    sockfd = socket(AF_INET, SOCK_STREAM, 0);
    if (sockfd == -1) {
        perror("Socket creation failed");
        return -1;
    }

    server_addr.sin_family = AF_INET;
    server_addr.sin_port = htons(8080);
    server_addr.sin_addr.s_addr = INADDR_ANY;

    bind(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));
    listen(sockfd, 5);

    printf("Server is listening on port 8080...\n");

    client_sock = accept(sockfd, (struct sockaddr*)&client_addr, &client_len);
    if (client_sock == -1) {
        perror("Client connection failed");
        return -1;
    }

    ssize_t n = recv(client_sock, buffer, sizeof(buffer) - 1, 0);
    if (n > 0) {
        buffer[n] = '\0';
        printf("Received message: %s\n", buffer);
    }

    close(client_sock);
    close(sockfd);

    return 0;
}
```

**客户端：**

```c
#include <stdio.h>
#include <string.h>
#include <arpa/inet.h>

}
```

#include <stdio.h>

    bind(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));

    printf("UDP Server is listening on port 8080...\n");

    ssize_t n = recvfrom(sockfd, buffer, sizeof(buffer) - 1, 0,

        buffer[n] = '\0';
        printf("Received message: %s\n", buffer);
    }

## 1.26 多线程socket编程中，如何避免线程安全问题？

### 1.26.1 基本概念

在多线程编程中，当多个线程共享同一资源（如同一个 Socket 连接）时，如果没有适当的同步机制，就可能导致**数据竞争**，引发**线程安全问题**。特别是在使用 Socket 进行网络通信时，线程安全问题可能会影响数据的完整性与可靠性。

### 1.26.2 常见的线程安全问题

1. **共享资源的竞争**：多个线程同时访问和修改同一资源（如同一个 Socket 连接）时，可能会导致资源状态不一致。
2. **数据错乱**：多个线程写入 Socket 时，如果没有同步机制，数据包可能会交叉或丢失。
3. **死锁**：如果不正确使用锁，可能导致线程相互等待，无法继续执行。

### 1.26.3 避免线程安全问题的方法

**1. 使用互斥锁（Mutex）**

- **互斥锁**（pthread_mutex_t）是最常用的同步机制之一，可以确保在同一时间只有一个线程能够访问 Socket。通过对 Socket 的每次访问加锁，避免多个线程同时操作 Socket，防止数据竞争。

```c
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void* thread_func(void* arg) {
    pthread_mutex_lock(&mutex);

    // 进行 Socket 数据发送或接收操作
    send(socket_fd, buffer, size, 0);

    pthread_mutex_unlock(&mutex);
    return NULL;
}
```

**2. 每个线程独立的 Socket**

- **线程间独立资源**：如果每个线程拥有独立的 Socket 连接，可以减少多个线程共享同一 Socket 状态的竞争；连接状态、协议数据和其他共享对象仍需明确所有权并做好同步。
- 例如，在服务端可以为每个客户端分配一个单独的 Socket 连接，每个线程负责处理一个客户端请求。这样，不同线程操作独立的 Socket，不会互相干扰。

**3. 线程池和工作队列**

- 通过**线程池**和**工作队列**管理线程和任务，将客户端请求任务添加到队列中，线程池中的工作线程从队列中获取任务并处理。
- 通过这种方式，可以控制线程的数量并避免创建过多线程，减少线程安全问题的复杂性。

```c
        task_t task = get_task_from_queue();

        // 处理任务
        process_socket_request(task.socket_fd);
    }
}
```

**4. 原子操作**

- 使用 **原子操作** 来避免线程竞争问题，尤其是当涉及到共享数据时，可以使用 **原子变量** 来保证操作的原子性。
- 例如，使用 atomic 库中的原子操作来修改共享变量，避免线程间的数据不一致问题。

```c
#include <stdatomic.h>

atomic_int shared_data;

void* thread_func(void* arg) {
    atomic_fetch_add(&shared_data, 1);  // 原子加操作
    return NULL;
}
```

**5. 无锁设计（Lock-Free）**

- 在一些高性能场景下，使用**无锁数据结构**来减少锁的开销。例如，可以使用**无锁队列**（lock-free queues）来存储待处理的网络请求。
- 无锁设计虽然能提升性能，但通常更复杂，需要特别注意设计的正确性。

### 1.26.4 避免死锁

1. **加锁顺序**：多个线程可能同时需要锁多个资源，为了避免死锁，所有线程应遵循相同的锁定顺序。
2. **超时机制**：对于互斥锁加锁操作，设置超时机制。如果在规定时间内无法获得锁，则放弃或重试，避免长期等待造成死锁。
3. **避免嵌套锁**：尽量避免在持有一个锁的情况下请求其他锁，减少死锁发生的可能性。

### 1.26.5 总结

> 在多线程 Socket 编程中，避免线程安全问题的常见方法包括使用互斥锁保护共享资源、为每个线程分配独立的 Socket 连接、利用线程池管理线程和任务、以及使用原子操作和无锁设计来减少线程竞争和提高效率。

> 为了避免多线程 Socket 编程中的线程安全问题，可以通过互斥锁、独立 Socket、线程池、原子操作等手段来实现线程安全和高效的资源管理。

## 1.27 以太网协议栈

### 1.27.1 基本概念

- **以太网**：是一种局域网（LAN）技术，广泛用于局域网中的数据通信。它工作在 OSI 模型的 **数据链路层** 和 **物理层**。
- **协议栈**：一组不同层次协议的集合，通常分为不同的层级，每一层负责不同的通信任务。

以太网协议栈是根据 **OSI 模型** 来分层的，下面我们将详细说明每个层的功能。

### 1.27.2 以太网协议栈的层次

- **功能**：定义了电缆的物理属性、信号的电气特性、传输速率、传输媒介等。它确保数据包在物理介质上进行正确的发送与接收。

**2. 数据链路层（Data Link Layer）**

- **协议**：以太网协议（Ethernet）、MAC（媒体访问控制）
- **功能**：
    - **MAC 地址**：传统以太网接口常使用 48 位 MAC 地址；地址应在接口/网络范围内可区分，但虚拟接口、随机地址、克隆或软件配置会使“全球唯一”不能作为绝对保证。
    - **帧结构**：在以太网中，数据被打包成“帧”进行传输。以太网帧包含源 MAC 地址、目的 MAC 地址、数据内容和校验码等。
    - **错误检测**：通过 CRC（循环冗余校验）来检测数据传输中的错误。
    - **介质访问控制**：控制不同设备在共享介质上如何进行通信，防止冲突。
- **以太网帧格式**：
    - **目的地址**（6 字节）：目标设备的 MAC 地址
    - **源地址**（6 字节）：发送设备的 MAC 地址
    - **类型**（2 字节）：指示上层协议（例如 IPv4、IPv6）
    - **数据**（46-1500 字节）：实际的网络数据
    - **校验和**（4 字节）：CRC 校验码

**3. 网络层（Network Layer）**

- **协议**：IP（Internet Protocol）
- **功能**：
    - **IP 地址**：网络层使用 **IP 地址** 来唯一标识网络中的每个主机。它支持不同网络间的路由，确保数据能够在广域网（WAN）上正确传递。
    - **路由功能**：路由器根据目标 IP 地址将数据包从源主机路由到目标主机。
    - **IP 数据包格式**：
        - **源地址**：发送方的 IP 地址
        - **目标地址**：接收方的 IP 地址
        - **数据**：传输的实际数据（例如，TCP 或 UDP 数据包）

**4. 传输层（Transport Layer）**

- **协议**：TCP、UDP
- **功能**：
    - **TCP**：面向连接，提供可靠的、按顺序的数据传输。它通过三次握手建立连接，并通过确认与重传机制确保数据可靠性。
    - **UDP**：无连接，不保证可靠性，但提供更高的效率，适用于实时数据传输（如视频流、语音）。

**5. 应用层（Application Layer）**

- **协议**：HTTP、FTP、SMTP、DNS 等
- **功能**：为用户提供应用服务和网络协议接口，例如浏览器访问网站时使用的 HTTP 协议。

### 1.27.3 以太网协议栈的流程

1. **数据生成**：应用层生成数据（如 HTTP 请求）。
2. **数据分段**：传输层（如 TCP）将数据拆分成适当的大小，并加入头部信息（如序号、确认信息）。
3. **封装数据包**：网络层（IP）将数据包封装成 IP 数据包，加入源和目标 IP 地址。
4. **数据链路层处理**：数据链路层将数据封装成以太网帧，加入源和目的 MAC 地址，使用 CRC 校验。
5. **物理层传输**：物理层将帧转换成电信号并通过电缆或无线信道传输到接收方。
6. **接收和解包**：接收方从物理层接收到信号，通过物理层解码，再按协议栈层次解析每一层的数据，直到到达应用层。

### 1.27.4 总结

> 以太网协议栈包括物理层、数据链路层、网络层、传输层和应用层，每层协议负责不同的通信任务。物理层和数据链路层负责链路传输与差错检测，网络层处理跨网络的数据报转发；端到端可靠性由 TCP 等上层协议提供，UDP/IP 本身只提供尽力而为语义。

> 以太网协议栈通过物理层、数据链路层、网络层、传输层和应用层的分层设计，实现了从应用层数据生成到物理层信号传输的完整通信过程。

## 1.28 网络通信中如何保证数据安全

### 1.28.1 机密性（Confidentiality）

- **目标**：防止数据被未授权方读取
- **方法**：
    a. **加密传输**：
        - 对称加密（AES、DES）— 高效，但密钥管理复杂
        - 非对称加密（RSA、ECC）— 用于密钥交换或签名
    b. **VPN 或 TLS/SSL**：
        - 建立安全隧道传输数据
        - 广泛用于 HTTP/HTTPS、MQTT over TLS

### 1.28.2 完整性（Integrity）

- **目标**：防止数据在传输过程中被篡改
- **方法**：
    a. **校验和**：简单检测传输错误（CRC、Checksum）
    b. **密码学哈希函数**（如 SHA-256）：配合可信基准值检测数据是否被修改；MD5 已不适合安全完整性或签名场景
    c. **数字签名**：保证数据完整性及来源可信

### 1.28.3 认证（Authentication）

- **目标**：确认通信双方身份
- **方法**：
    a. **用户名/密码**（基础认证）
    b. **证书认证**（X.509）— 配合 TLS/SSL 使用
    c. **Token 或密钥机制**（JWT、HMAC）— 轻量适合嵌入式

### 1.28.4 防重放攻击（Replay Attack）

- **目标**：防止被攻击者重复发送数据包
- **方法**：
    a. **时间戳** + **有效期**
    b. **随机数/Nonce**
    c. **序列号检测**

### 1.28.5 网络层安全策略

- **防火墙和访问控制**：限制不可信 IP 或端口访问
- **入侵检测与防护**（IDS/IPS）
- **网络分段**：隔离关键设备或服务

### 1.28.6 总结

**通过加密保证机密性、哈希/签名保证完整性、认证验证身份、序列号防重放，并辅以防火墙与访问控制，确保网络通信安全。**

## 1.29 嵌入式设备网络升级（OTA）涉及哪些网络问题？

### 1.29.1 网络可靠性问题

- **网络中断**：
    - 升级过程中网络掉线可能导致固件升级失败或设备不可用
- **丢包与错误**：
    - 无线网络尤其容易出现丢包
    - 需要校验机制保证传输完整性（如 CRC 用于偶发传输错误）；安全场景应使用 SHA-256 等哈希配合数字签名，不能把 MD5 当作抗碰撞安全校验

### 1.29.2 带宽与传输效率

- **大固件包**占用网络带宽，影响设备正常通信
- **传输速率慢**可能导致升级超时
- **优化策略**：
    - 分片传输（Chunk/Block）
    - 差分升级（只传输变化部分）
    - 压缩传输

### 1.29.3 安全性问题

- **固件篡改**：
    - OTA 更新包可能被中间人攻击篡改
- **解决措施**：
    - 数字签名验证
    - 加密传输（TLS/HTTPS）
- **认证与访问控制**：
    - 防止未授权设备或服务器进行升级

### 1.29.4 多设备并发升级问题

- **高并发升级**可能占用网关或服务器资源
- **可能导致**：
    - 网络拥塞
    - 升级失败或设备重启异常
- **优化策略**：
    - 分批升级（Batch Upgrade）
    - 限流策略（限制同时升级设备数）

### 1.29.5 网络层协议适配问题

- **不同网络环境**：
    - Wi-Fi、LTE、以太网、LoRa 等
    - 可能存在 MTU 限制或不同传输特性
- **解决方法**：
    - 自适应分片和重传机制
    - 选择可靠传输协议（TCP 或应用层 ACK 机制）

### 1.29.6 总结

**OTA 升级涉及网络可靠性、带宽占用、安全性、多设备并发及协议适配问题，需要分片传输、密码学哈希与签名校验、加密、断点续传和限流等策略提高成功率与可恢复性；不能仅靠 CRC 或 MD5 证明镜像可信。**
