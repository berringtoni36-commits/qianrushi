## 1.1 全局变量和局部变量的区别

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/RTOS高频面试题#A21. 全局变量、静态全局变量和局部变量的存储区域及生命周期有什么区别？|RTOS项目 A21：全局变量、静态全局变量和局部变量的存储区域及生命…]]

### 1.1.1 定义位置不同

1. **全局变量**
    - 定义在 **函数外部**，通常在文件顶部
    - 整个程序中都可以访问（受 extern / static 影响）
2. **局部变量**
    - 定义在 **函数内部或代码块内部**
    - 只能在定义它的作用域内使用

### 1.1.2 作用域不同

1. **全局变量**
    - 作用域：从定义处到文件结束
    - 可被多个函数访问
2. **局部变量**
    - 作用域：所在的函数或 {} 代码块
    - 离开作用域即不可访问

### 1.1.3 生命周期不同

1. **全局变量**
    - 生命周期：**整个程序运行期间**
    - 程序开始时分配，程序结束时释放
2. **局部变量**
    - 生命周期：**函数执行期间**
    - 函数调用时创建，函数返回时销毁

### 1.1.4 存储位置不同

1. **全局变量**
    - 存储在 **全局/静态存储区（.data / .bss）**
2. **局部变量**
    - 一般存储在 **栈区**
    - static 局部变量存储在静态区

### 1.1.5 初始化规则不同

1. **全局变量**
    - **默认初始化为 0**（未显式初始化）
2. **局部变量**
    - **不会自动初始化**，值为随机值

### 1.1.6 使用注意点

1. **全局变量**
    - 优点：使用方便、共享数据简单
    - 缺点：
        - 破坏模块封装
        - 容易引发命名冲突
        - 不利于多线程安全
2. **局部变量**
    - 优点：
        - 作用范围小，安全性高
        - 有利于代码维护和复用

### 1.1.7 总结

> 全局变量作用域大、生命周期长，存放在静态区；局部变量作用域小、生命周期短，通常存放在栈区，未初始化时值不确定。

## 1.2 内存分布模型

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/RTOS高频面试题#A3. 请说一下堆和栈的区别。|RTOS项目 A3：堆和栈的区别]]

![[assets/糯叽叽八股/内存分布模型-地址空间示意图.png|内存分布模型与地址空间示意图]]

### 1.2.1 先说结论

**1.代码段：**存放程序的机器指令（即二进制代码）。通常是只读的，因为程序的指令在执行过程中不应该被修改。

**2.数据段：**存放已初始化的**全局变量和静态变量**。这些变量在程序开始运行时已经赋予了初始值。

**3.BSS 段：**存放未初始化的**全局变量和静态变量**。它们在程序开始运行时会自动初始化为0或者空指针（初始化为0也是在这里）。

**4.堆区：**动态分配的内存空间，用于存放程序运行时动态申请的内存。（程序员可以通过函数（如 `malloc`、`calloc` 等）或者操作系统提供的接口来申请和释放堆内存；堆的增长方向取决于平台和分配器实现。）

**5.栈区：**存放函数的**局部变量**、函数参数值以及函数调用和返回时的相关信息。栈区通常按先进后出的方式管理，内存分配和释放由调用约定/运行时自动处理；增长方向和是否连续取决于平台实现。

**6.共享区：**也称为文件映射或共享内存，用于实现不同进程之间的内存共享。

**7. 只读数据段：**存放字符串字面量、只读全局/静态常量等数据（具体位置取决于编译器和链接脚本）。

### 1.2.2 代码区（Text Segment）

- **存放内容：** 可执行指令；只读常量字符串（部分系统）
- **特点：** 只读；多个进程可共享；防止程序被意外修改

### 1.2.3 只读数据区（RODATA）

- **存放内容：** 字符串常量；const 修饰的全局常量（可能）
- **特点：** 只读；编译期确定；位于代码区附近

### 1.2.4 全局/静态区（Data Segment）

**（1）已初始化全局区（.data）**

- **存放内容：** 已初始化的全局变量；已初始化的静态变量

**示例：**

```c
int g_val = 10;
static int s_val = 5;
```

**（2）未初始化全局区（.bss）**

- **存放内容：** 未初始化或初始化为 0 的全局变量；未初始化或初始化为 0 的静态变量
- **特点：** 程序启动时自动清零；不占可执行文件空间

### 1.2.5 堆区（Heap）

- **存放内容：** 动态分配的内存
- **管理方式：** 程序员手动申请和释放；容易产生内存泄漏

**示例：**

```c
int *p = (int *)malloc(sizeof(int));
```

- **特点：** 增长方向由平台/分配器决定；生命周期由程序员控制

### 1.2.6 栈区（Stack）

- **存放内容：** 局部变量；函数参数；返回地址
- **特点：** 自动分配和释放；空间有限；增长方向由平台/ABI 决定

**示例：**

```c
void func() {
    int a = 10;
}
```

### 1.2.7 内存分布示意（逻辑结构）

```text
高地址
 ┌────────────┐
 │   栈区     │
 ├────────────┤
 │   堆区     │
 ├────────────┤
 │  .bss      │
 ├────────────┤
 │  .data     │
 ├────────────┤
 │ rodata     │
 ├────────────┤
 │ 代码区     │
 └────────────┘
低地址
```

### 1.2.8 总结

- 全局变量和静态变量存放在全局/静态区
- 局部变量存放在栈区
- malloc/new 申请的内存在堆区
- const 变量位置与修饰方式、编译器有关
- 栈快、堆灵活，但栈空间有限
- 内存分布模型体现了程序中不同数据的生命周期和管理方式，是理解指针、作用域、内存泄漏和嵌入式底层开发的基础

## 1.3 初始化为 0 的全局变量存储位置：BSS 还是 Data？

> C 标准只规定具有静态存储期的对象在程序启动前完成零初始化，并不规定 `.bss` / `.data` 段。下文是 ELF 等常见工具链的典型布局，裸机系统则通常由启动代码和链接脚本完成复制/清零。

### 1.3.1 全局变量存储区概述

- **Data 段**：存储已初始化的全局变量和静态变量。
- **BSS 段**：存储未初始化的全局变量和静态变量，或者初始化为 0 的全局变量。

### 1.3.2 BSS 段和 Data 段的区别

- **BSS 段**：存储未显式初始化的变量或者初始化为零的变量。
    - 它在程序加载时会自动初始化为 0。
    - **不占用实际磁盘空间**，程序运行时由操作系统为它分配空间。
    - 优点是节省了程序文件的存储空间，程序文件中没有将所有零值写入磁盘，只记录了该变量的存在。
- **Data 段**：存储已显式初始化的全局变量。
    - 包括非零初始化的全局变量和静态变量。
    - 在程序加载时，操作系统会将这些值加载到内存中。

### 1.3.3 初始化为 0 的全局变量的存储位置

- **初始化为 0 的全局变量在常见工具链中通常放在 BSS 段**。
    - 这种做法是为了节省程序的存储空间，因为 BSS 段中的内存会被操作系统自动初始化为 0。

**示例：**

```c
int global_var = 0;  // 常见工具链通常放在 BSS 段
```

- **未初始化的全局变量也是存储在 BSS 段**，并且会默认初始化为 0。

**示例：**

```c
int uninitialized_global_var;  // 标准保证初始值为 0；常见工具链通常放在 BSS
```

### 1.3.4 存储位置总结表

| 变量类型 | 存储位置 | 说明 |
|---|---|---|
| 全局变量（未显式初始化） | 通常为 BSS | C 语义保证零初始化；宿主环境由 loader、裸机由启动代码等完成 |
| 全局变量（显式初始化为 0） | 通常为 BSS | 具体分段由编译器和链接脚本决定 |
| 全局变量（非零初始化） | 通常为 Data 段 | 初始值会占用可执行文件空间 |
| 静态变量（局部静态，未初始化） | 通常为 BSS | 未显式初始化时的常见布局 |
| 静态变量（局部静态，初始化为 0） | 通常为 BSS | 显式初始化为 0 时的常见布局 |
| 静态变量（局部静态，非零初始化） | 通常为 Data 段 | 初始值会占用可执行文件空间 |

### 1.3.5 为什么要把初始化为 0 的全局变量放在 BSS？

- **节省存储空间**：在可执行文件中，BSS 段的变量不会将 0 值存储到磁盘上，这样可以减少文件大小。程序加载时，操作系统会自动将这些变量初始化为 0，避免了程序需要在磁盘中存储零值。
- **高效加载**：BSS 段中的变量在程序加载时自动初始化为 0，这使得操作系统可以更高效地管理内存。

### 1.3.6 总结

> 在常见链接布局中，零初始化或未显式初始化的静态存储期对象通常放在 BSS，非零初始值通常放在 Data；真正结果应以 map 文件、目标文件和链接脚本为准。

## 1.4 字符数组初始化

### 1.4.1 使用字符串常量初始化（最常见）

```c
char str1[] = "hello";
```

- **本质**：字符数组
- **结尾**：自动添加 '\0'
- **数组大小**：6（h e l l o \0）

### 1.4.2 指定数组大小 + 字符串

```c
char str2[10] = "hello";
```

- 前 6 个元素："hello\0"
- 剩余元素：**自动补 0**
- 若数组长度不足以容纳字符串及结尾的 `\0`，编译器通常会诊断为错误

### 1.4.3 使用字符逐个初始化

```c
char str3[] = {'h', 'e', 'l', 'l', 'o', '\0'};
```

- **本质最明确**
- 不写 '\0' → **不是字符串**

### 1.4.4 部分初始化

```c
char str4[6] = {'h', 'e', 'l', 'l', 'o'};
```

- 编译器自动补 '\0'
- 等价于 "hello"

### 1.4.5 指针方式（对比易混）

```c
const char *str5 = "hello";
```

- **不是数组**，是指向字符串字面量的指针
- 通过该指针修改字面量是未定义行为
- 不能修改 str5[0]

**注意点：**

- "hello" ≠ {'h','e','l','l','o'}（少了 '\0'）
- sizeof(str)
    - 数组：返回**数组总字节数**
    - 指针：返回**指针大小**
- 字符数组可改，字符串常量不可改

## 1.5 数组的存储位置

### 1.5.1 按定义位置分类

1. **局部数组（函数内部定义）**
    - **存储位置**：栈区（Stack）
    - **生命周期**：随函数调用创建，函数返回销毁
    - **初始化**：未初始化内容为**随机值**（除 static 局部数组）
    - **示例**：

```c
void func() {
    int arr[10]; // 局部数组，存放在栈上
}
```

2. **全局数组（函数外定义）**
    - **存储位置**：静态区（BSS 段）
    - **生命周期**：整个程序运行期间
    - **初始化**：未显式初始化的数组元素自动初始化为 0
    - **示例**：

```c
int g_arr[10]; // 全局数组，存放在静态区
```

3. **静态局部数组（使用 **static** 修饰）**
    - **存储位置**：静态区（BSS 段）
    - **生命周期**：整个程序运行期间
    - **作用域**：仅限于定义它的函数内部
    - **示例**：

```c
void func() {
    static int arr[10]; // 静态局部数组，存放在静态区
}
```

4. **动态数组（通过 **malloc** / **calloc** 分配）**
    - **存储位置**：堆区（Heap）
    - **生命周期**：由程序控制，需手动释放
    - **示例**：

```c
int *arr = (int*)malloc(10 * sizeof(int)); // 堆上数组
free(arr); // 释放内存
```

### 1.5.2 总结表

|数组类型|存储位置|说明|
|---|---|---|
|全局数组（未显式初始化或初始化为 0）|BSS 段|编译器自动清零，程序启动时由 loader 初始化为 0|
|全局数组（非 0 初始化）|数据段（DATA）|编译器在程序加载时初始化为指定值|
|局部数组（非 static）|栈（Stack）|函数调用时分配，函数返回后释放|
|局部数组（static）|BSS / DATA 段|初始化为 0 放 BSS，非 0 初始化放 DATA，生命周期贯穿整个程序|
|常量数组（const）|只读数据段（RODATA）|存放不可修改的常量数组|

### 1.5.3 总结

> 数组的存储位置取决于定义方式：局部数组在栈上，静态和全局数组在静态区，动态数组在堆上，生命周期和初始化规则也随之不同。

## 1.6 静态数组和动态数组的生命周期区别？

### 1.6.1 静态数组（Static Array）

- **定义**：在编译时就确定大小的数组，例如：

```c
int arr[10];          // 全局或局部静态数组
static int arr2[5];   // 静态局部数组
```

- **存储位置**：
    - **全局数组**：存储在 **全局数据段（Data Segment 或 BSS 段）**
    - **局部静态数组**：存储在 **数据段**，不是栈
    - **普通局部数组**：存储在 **栈（Stack）**
- **生命周期**：
    - **全局数组**：程序运行期间一直存在，从程序开始到结束
    - **静态局部数组**：从程序开始到结束（即使在函数返回后也存在）
    - **普通局部数组**：函数调用时创建，函数返回时销毁
- **特点**：
    - 分配和释放由编译器自动管理
    - 局部数组可能占用栈空间，栈空间有限，过大数组会导致栈溢出
- 大小在编译时固定

### 1.6.2 动态数组（Dynamic Array）

- **定义**：在运行时通过 malloc、calloc 或 new 分配的数组，例如：

```c
int *arr = (int*)malloc(10 * sizeof(int));  // C 语言
int *arr_cpp = new int[10];                 // C++ 语言
```

- **存储位置**：**堆（Heap）**
- **生命周期**：
    - 从调用分配函数（malloc/new）开始，到显式调用 free/delete 结束
    - 如果没有释放，内存会一直存在，直到程序结束（可能导致内存泄漏）
- **特点**：
    - 大小在运行时决定，更灵活
    - 程序员必须手动管理内存
    - 可以分配比栈更大的内存，适合大数组或不确定大小的数组

### 1.6.3 对比总结

|特性|静态数组|动态数组|
|---|---|---|
|分配时机|编译/链接时确定，程序启动时分配|运行时分配（如 malloc / new[]）|
|生命周期|整个程序运行期间保持|从分配到显式释放之间有效（需 free / delete[]）|
|内存位置|数据段（全局/静态）或栈（局部数组）|堆（Heap）|
|大小|编译时固定|运行时可根据需求动态指定|
|示例|`int arr[10];`|`int* arr = new int[n];`|

### 1.6.4 总结

- **静态数组**：生命周期由编译器控制，自动分配和释放，大小固定，适合大小已知的数组。
- **动态数组**：生命周期由程序员控制，需要手动分配和释放，大小灵活，适合运行时大小不确定或需要较大内存的数组。

> 本质区别在于**分配位置和生命周期管理方式**：栈/数据段 vs 堆，以及编译器管理 vs 程序员管理。

## 1.7 二维数组的访问

### 1.7.1 定义二维数组

二维数组可以看作“数组的数组”，例如：

```c
int arr[3][4];  // 3 行 4 列
```

- arr 表示整个二维数组。
- arr[i] 表示第 i+1 行，是一个一维数组（长度为 4）。
- arr[i][j] 表示第 i+1 行第 j+1 列的元素。

### 1.7.2 通过下标访问

使用 **行列下标**访问元素：

```c
arr[0][0] = 1;  // 第一行第一列
arr[2][3] = 5;  // 第三行第四列
```

- 行下标 i：0 ~ 行数-1
- 列下标 j：0 ~ 列数-1

### 1.7.3 通过指针访问

二维数组在内存中是**按行连续存储**的，因此也可以用指针访问：

**方法 1：使用数组名 + 偏移量**

```c
*( *(arr + i) + j ) = 10;  // 等价于 arr[i][j]
```

- arr + i：第 i 行的首地址
- *(arr + i)：第 i 行的数组（一维数组）
- *( *(arr + i) + j )：第 i 行第 j 列元素

**方法 2：把二维数组看作一维数组**

```c
int *p = &arr[0][0];
p[i * 4 + j] = 20;  // 访问 arr[i][j]，假设列数为 4
```

- 适合在函数中把二维数组作为指针传递时使用。
- i * 列数 + j 是内存偏移公式。

### 1.7.4 总结

1. **最常用方式**：arr[i][j]
2. **指针方式**：*((arr + i) + j)
3. **一维化方式**：p[i * 列数 + j]

> 二维数组在内存中按行连续存储，所以指针和偏移都能准确访问元素。

## 1.8 extern关键字

### 1.8.1 基本作用

- extern 用于**声明一个在其他地方定义的变量或函数**
- 只做**声明**，不分配存储空间
- 用于实现**跨文件访问**

### 1.8.2 extern 修饰全局变量（最常见）

**文件 A：定义**

```c
int g_val = 10;
```

**文件 B：声明**（通常是头文件）

```c
extern int g_val;
```

- 编译通过，链接阶段找到定义
- 多文件工程的标准写法

### 1.8.3 extern 与头文件（规范用法）

**.h 文件**

```c
extern int g_val;
```

**.c 文件**

```c
int g_val = 10;
```

- 头文件只放 extern 声明
- 定义只出现一次

### 1.8.4 extern 与函数

```c
extern void func(void);
```

- 对函数来说：
    - 函数默认具有外部链接属性
- extern 可省略

### 1.8.5 extern 与 static 的关系（高频考点）

```c
static int x;   // 定义为当前翻译单元内部链接
extern int x;   // 同一翻译单元中可再次声明，仍沿用内部链接
```

- `static` 用于赋予文件作用域对象内部链接；`extern` 通常只声明对象定义在别处。
- 同一条声明不能同时写 `static extern`，但上例这种“先 `static` 定义、后 `extern` 再声明”是允许的。

### 1.8.6 extern 与 const（易错点）

```c
// file1.c
const int g_val = 10;

// file2.h
extern const int g_val;
```

- C 语言中：
    - 文件作用域的 `const` 对象默认仍是 **外部链接**，与普通全局变量一样。
    - 典型做法是在一个 `.c` 文件中定义，在头文件中用 `extern const int g_val;` 声明。
    - C++ 不同：命名空间作用域下非 `extern` 的非 `volatile const` 对象默认是内部链接。

### 1.8.7 常见错误示例

```c
// 头文件中
int g_val;   // 错误，导致多重定义
```

- 多个 .c 文件包含该头文件
- 链接错误：multiple definition

### 1.8.8 嵌入式开发中的典型用途

- 全局配置参数
- 外设句柄
- RTOS 任务句柄
- 跨模块共享状态

### 1.8.9 注意点

- `extern` 声明通常不是定义；但带初始化器的 `extern int x = 1;` 仍是定义。
- 链接错误的排查
- extern 与头文件规范
- **`extern` 主要用于跨文件声明变量或函数，让声明与其他位置的定义对应。**

## 1.9 数组大小

- 普通固定长度数组的大小由定义确定，定义后不能改变。
- C99 引入了块作用域的可变长度数组（VLA）；C11 起实现可选，很多嵌入式规范会禁用。文件作用域的数组长度仍必须是整型常量表达式。

### 1.9.1 数组大小在定义时必须确定

```c
int a[10];
```

- C90 中数组长度必须是整型常量表达式。
- C99 及支持 VLA 的后续实现中，块作用域可使用运行期长度，但需警惕栈空间和可移植性。

### 1.9.2 sizeof 获取数组大小

```c
int a[10];
sizeof(a);        // 40（假设 int 为 4 字节）
sizeof(a) / sizeof(a[0]);  // 元素个数
```

- sizeof(数组)：**整个数组占用字节数**
- 仅在**当前作用域**有效

### 1.9.3 数组名作为参数会退化为指针

```c
void func(int a[]) {
    sizeof(a);   // 指针大小，而非数组大小
}
```

- 数组传参本质是**指针传递**
- 无法在函数内获取原数组大小

### 1.9.4 字符数组的大小

```c
char s[] = "abc";
```

- 实际大小：4（包含 '\0'）
- sizeof(s) = 4
- strlen(s) = 3

### 1.9.5 多维数组大小规则

```c
int b[3][4];
```

- 必须指定**除第一维以外的所有维度**
- 内存连续存储（行优先）
- **注意点：** `sizeof` 是运算符，其结果通常可在编译期确定；操作数的类型为 VLA 时可在运行时求值。`sizeof(指针) ≠ sizeof(数组)`。

## 1.10 函数参数传递与调用约定

### 1.10.1 函数调用约定（Calling Conventions）简介

在 C/C++ 程序中，函数调用约定决定了函数参数如何传递、返回值如何传递，以及栈的清理方式。常见的调用约定有 __stdcall、__cdecl、__fastcall 等。不同的调用约定影响函数调用时的栈操作、参数传递和返回值处理。

> 下文关于“从右到左入栈”、EAX、栈清理和函数名修饰的对比，专指典型 **32 位 x86 Windows ABI**。x86-64 和 ARM ABI 通常先用寄存器传参，不能套用这些细节。

### 1.10.2 __cdecl 调用约定

1. **参数压栈顺序：**
    - **从右到左**：在函数调用时，参数是从右向左压栈。
2. **栈清理：**
    - **调用者清理栈**：函数调用完成后，调用者负责清理栈中传递的参数。
    - 这意味着调用者在函数执行后需要调整栈指针，移除压入栈中的参数。
3. **返回值处理：**
    - 在传统 x86 ABI 下整数返回值通常使用 EAX；具体方式由平台 ABI 决定。
4. **用途：**
    - __cdecl 是默认的调用约定，广泛用于 C/C++ 编译器，适合大多数函数调用。
5. **示例：**

```c
int __cdecl sum(int a, int b, int c) {
    return a + b + c;
}
```

### 1.10.3 __stdcall 调用约定

1. **参数压栈顺序：**
    - **从右到左**：和 __cdecl 一样，__stdcall 调用约定也是从右向左压栈传递参数。
2. **栈清理：**
    - **被调用者清理栈**：与 __cdecl 不同，__stdcall 中被调用的函数负责清理栈。
    - 这意味着在函数返回时，函数自身会调整栈指针，移除参数。
3. **返回值处理：**
    - 在传统 x86 ABI 下整数返回值通常使用 EAX；具体方式由平台 ABI 决定。
4. **用途：**
    - __stdcall 多用于 Windows API 调用，特别是在 Win32 API 中。

```c
int __stdcall multiply(int a, int b) {
    return a * b;
}
```

### 1.10.4 __cdecl 与 __stdcall 的区别

|特性|__cdecl|__stdcall|
|---|---|---|
|参数传递顺序|从右到左|从右到左|
|栈清理责任|调用者（Caller）|被调用者（Callee）|
|支持可变参数函数|支持（如 printf）|不支持|
|函数名修饰|前加 _，参数不修饰|前加 _，后加 @参数字节数|
|使用场景|C/C++ 默认调用约定|Windows API 函数常用调用约定|

### 1.10.5 为什么存在两种调用约定？

- __cdecl 适用于一般情况下的函数调用，特别是在 C/C++ 中较为常见。它允许传递可变参数（如 printf）。
- __stdcall 适用于 Windows 操作系统中 API 调用，它要求被调用者清理栈，减少调用者的负担，这对于大量的 API 调用是非常有用的，能够提高效率。

### 1.10.6 总结

> 在典型 32 位 x86 Windows ABI 下，`__cdecl` 由调用者清理参数栈，`__stdcall` 由被调用者清理，两者通常从右到左入栈。其他架构、操作系统和编译器必须以相应 ABI 文档为准。

## 1.11 C 语言的基本类型及常见字节数

C 标准不把整型和指针的大小与“32/64 位处理器”简单绑定，具体大小取决于 ABI 和编译器。下表是 `CHAR_BIT == 8`、IEEE 754 浮点数的常见实现：

| 数据类型 | 32 位 ILP32（字节） | 64 位 LP64（Linux/macOS） | 64 位 LLP64（Windows） |
| --- | --- | --- | --- |
| `_Bool` / `bool`（需 `<stdbool.h>`） | 1 | 1 | 1 |
| `char` / `unsigned char` | 1 | 1 | 1 |
| `short` | 2 | 2 | 2 |
| `int` / `unsigned int` | 4 | 4 | 4 |
| `long` / `unsigned long` | 4 | 8 | 4 |
| `long long` | 8 | 8 | 8 |
| `float` | 4 | 4 | 4 |
| `double` | 8 | 8 | 8 |
| 数据指针 | 4 | 8 | 8 |

> 必须以目标平台的 `sizeof` 结果和 ABI 文档为准；对精确位宽有要求时，优先使用 `<stdint.h>` 中实现支持的 `uint32_t` 等类型。

**位数和字节数**

日常平台通常 1 Byte = 8 bit，但 C 标准只保证一个字节至少 8 位，实际位数可由 `CHAR_BIT` 查询。处理器“32 位/64 位”也不能单独决定数据总线宽度或所有 C 类型的大小。

**字的定义**

“字（word）”是体系结构概念，具体宽度由目标架构定义，不是 C 语言的固定类型大小。

## 1.12 如何在 C 语言里实现位域映射寄存器？

位域是 C 语言中一种用于指定结构体中某些字段占用位数的特性。它使得我们能够直接在结构体中以更细粒度来控制数据的位表示，非常适合硬件寄存器的映射。

在嵌入式开发中，硬件寄存器通常是按位访问的，通过位域可以方便地模拟和访问硬件寄存器。

### 1.12.1 位域结构定义

首先，我们需要定义一个结构体，并使用位域来映射寄存器的不同字段。位域定义可以指定每个字段占用的比特数。

**示例：简单的寄存器映射**

假设有一个硬件寄存器如下所示：

```text
31             16 15        8 7         0
+---------------+-----------+-----------+
|   CONTROL     |  STATUS   |   DATA    |
+---------------+-----------+-----------+
     16 bits        8 bits      8 bits
```

- CONTROL 占 16 位。
- STATUS 占 8 位。
- DATA 占 8 位。

我们可以通过结构体和位域来映射这个寄存器。

**代码示例：**

```c
#include <stdio.h>

typedef struct {
    unsigned int data : 8;
    unsigned int status : 8;
    unsigned int control : 16;
} Register;

int main(void) {
    Register reg = {0};
    reg.control = 0x1234;
    reg.status = 0x56;
    reg.data = 0x78;

    // 打印各字段的值
    printf("Control: 0x%X\n", reg.control);
    printf("Status : 0x%X\n", reg.status);
    printf("Data   : 0x%X\n", reg.data);

    /*
     * ⚠ 注意（非常重要）：
     * 1. 位域不保证跨平台一致性（不同编译器可能布局不同）
     * 2. 不建议直接用于硬件寄存器映射（工程中更推荐位运算）
     * 3. 位域成员不能取地址（&reg.data 是非法的）
     * 4. 若赋值超过位宽，高位会被截断（例如 0x123 -> 只保留低 8 位）
     */

    return 0;
}
```

### 1.12.2 解释

- `#pragma pack(1)` 只能控制字节对齐，不能规定位域在寄存器中的位序；位域布局依赖编译器和 ABI。硬件寄存器映射通常更推荐显式位运算。
- **位域字段**：使用 unsigned int 类型，并通过 :n 指定字段的位宽度。例如，unsigned int control:16 表示 control 字段占用 16 位。这样我们就能将 C 结构体与硬件寄存器映射起来。

### 1.12.3 寄存器映射

假设硬件寄存器的地址是 0x40000000，我们可以通过指针直接操作该寄存器，模拟对硬件寄存器的访问。

**示例：寄存器映射地址**

```c
#define REGISTER_BASE_ADDRESS 0x40000000

typedef volatile Register* RegisterPtr;

int main() {
    RegisterPtr reg = (RegisterPtr)REGISTER_BASE_ADDRESS;

    // 读取寄存器
    unsigned int control_val = reg->control;
    unsigned int status_val = reg->status;
    unsigned int data_val = reg->data;

    // 写入寄存器
    reg->control = 0x1234;
    reg->status = 0x56;
    reg->data = 0x78;

    return 0;
}
```

- `volatile`：该限定告诉编译器这是可观察的访问，不得仅因为代码看似没用就省略或合并。它说的是编译器访问语义，不是 CPU cache 一致性。
- RegisterPtr：我们通过将寄存器的基地址转换为指向 Register 类型的指针来访问寄存器。

### 1.12.4 注意事项

- **对齐与布局**：`#pragma pack(1)` 只能在支持它的编译器中调整字节对齐，不保证位域的位序、基础存储单元大小或寄存器访问宽度。
- **位域和编译器**：位域的分配顺序由实现/ABI 定义，不能只根据大小端推断。在跨编译器、跨芯片代码中应优先使用掩码和移位。
- **volatile 关键字**：寄存器通常是硬件状态的一部分，使用 `volatile` 是为了告诉编译器不要省略或合并对寄存器的访问，因为它的值可能会由外部硬件改变。

### 1.12.5 总结

- 位域访问很直观，但只能在已确认目标编译器和 ABI 布局、并核对芯片手册后用于寄存器映射。
- `#pragma pack(1)` 不能解决位序和访问语义问题，对可移植寄存器代码优先使用定宽无符号类型、掩码与移位。
- 通过 volatile 关键字确保编译器不会优化对寄存器的访问。

## 1.13 数组名与指针的地址区别

### 1.13.1 数组名（array）

```c
int a[10];
```

- **含义**：`a` 是数组名，它本身不是指针对象。在大多数表达式中，数组名会转换为指向首元素的指针。
- **表达式中的关系**：

```c
a == &a[0]
```

- **转换后的类型**：

```c
int *        // 对于 int a[10]
```

- **特性**：
    - 不能被赋值、不能自增
- 在大多数表达式中会**转换为指针**，但作为 `sizeof`、`_Alignof`（C23 起）或一元 `&` 的操作数等情况例外。

### 1.13.2 &数组名（&array）

```c
&a
```

- **含义**：指向**整个数组的指针**
- **类型**：

```c
int (*)[10]   // 指向“含 10 个 int 的数组”的指针
```

- **指向范围**：整个数组内存块

### 1.13.3 地址数值 vs 地址类型

```c
printf("%p\n", (void *)a);
printf("%p\n", (void *)&a);
```

- **打印结果可能相同**
- **但指针类型不同，指针运算结果不同**

### 1.13.4 指针运算差异（重点考点）

```c
a + 1;    // 跳过 1 个 int      → sizeof(int)
&a + 1;   // 跳过整个数组      → sizeof(a)
```

假设：

```c
int a[10];  // int 占 4 字节
```

- a + 1 → 地址 + 4
- &a + 1 → 地址 + 40

### 1.13.5 典型使用场景

```c
int (*p)[10] = &a;
```

- 多用于**二维数组传参**
- 或精确控制数组整体边界
- **注意点：** 认为 a 和 &a 完全等价（错误）；忽略指针类型对指针运算的影响

## 1.14 指针函数与函数指针的区别

### 1.14.1 概念区分（最容易混的点）

1. **指针函数**
    - 本质：**函数**
    - 特点：函数的**返回值是指针**
    - 重点在「**函数**」
2. **函数指针**
    - 本质：**指针**
    - 特点：指针指向一个**函数**
    - 重点在「**指针**」
      **”函数名在前是指针函数，\* 靠近变量名是函数指针”**

### 1.14.2 指针函数（函数返回指针）

**示例：**

```c
int* func(int a) {
    static int x = 10;
    return &x;
}
```

- func 是一个函数
- 返回值类型是 int*
- 调用方式：

```c
int *p = func(5);
```

**使用场景**

```c
返回类型 *函数名(参数列表);
```

1. 返回数组地址
2. 返回动态申请的内存
3. 返回结构体指针

注意：
**不能返回局部变量地址（除非是 static）**

### 1.14.3 函数指针（指向函数的指针）

**定义形式**

```c
返回类型 (*指针名)(参数列表);
```

() 必须有，否则就变成指针函数了

**示例：**

```c
int add(int a, int b) {
    return a + b;
}

int (*pFunc)(int, int) = add;
```

**调用方式**

```c
int result = pFunc(2, 3);
// 或
int result = (*pFunc)(2, 3);
```

### 1.14.4 对比总结表

|名称|定义方式|功能/用途|返回值示例|
|---|---|---|---|
|指针函数|`type *func_name(params)`|返回指针的函数|`int *f()` 返回 int*|
|函数指针|`type (*ptr_name)(params)`|指向函数的指针|`int (*p)(int)` 指向的函数|

### 1.14.5 典型应用场景

1. **指针函数**
    - 返回缓冲区地址
    - 返回结构体对象
    - 底层库接口设计
2. **函数指针**
    - 回调函数（如中断、排序函数）
    - 多态思想（C语言实现）
    - 状态机、函数表（Jump Table）

### 1.14.6 易混写法对比

```c
int *func();        // 指针函数：返回 int*
int (*func)();      // 函数指针：指向函数
```

### 1.14.7 总结

> 指针函数是返回指针的函数，本质是函数；函数指针是指向函数的指针，本质是指针，常用于回调和函数封装。

## 1.15 形参与实参详解

### 1.15.1 基本定义

- **形参（形式参数，formal parameter）**
  函数定义时用于接收数据的变量，本质是**局部变量**
- **实参（实际参数，actual parameter）**
  函数调用时传递给函数的**具体数据**

```c
int add(int x, int y) {   // x、y：形参
    return x + y;
}
```

### 1.15.2 传值调用（C语言的本质）

- **C 语言只有传值调用**
- 实参的值 → 拷贝 → 形参
- 修改形参 **不会影响** 实参

```c
void func(int x) {
    x = 10;
}

int a = 5;
func(a);
// a 仍然是 5
```

### 1.15.3 指针作为形参（“间接修改”）

```c
void func(int *p) {
    *p = 10;
}

int a = 5;
func(&a);
// a 被修改为 10
```

- 仍然是**传值**
- 传的是**地址的副本**
- 通过地址间接修改实参

### 1.15.4 数组作为实参（重点考点）

```c
void fill_first(int a[]) {  // 调整后等价于 void fill_first(int *a)
    a[0] = 42;
}

int values[4] = {0};
fill_first(values);
```

- 数组名作为实参时：
    - **退化为指针**
    - 形参本质是 int *
- 无法在函数内获取数组大小

等价写法：

```c
void func(int *a);
```

### 1.15.5 多维数组作为实参

```c
void func(int a[][4]);
void func(int (*a)[4]);
```

- 必须指定**除第一维外的所有维度**
- 因为编译器需要计算地址偏移

### 1.15.6 结构体作为实参

```c
struct S s;
func(s);     // 结构体整体拷贝
```

- **值传递**，开销可能较大

推荐方式：

```c
func(&s);    // 指针传递
```

### 1.15.7 形参与实参个数和类型

- 对已有函数原型的普通非可变参函数，实参数量必须与形参一致，并且每个实参都要能按规则转换为形参类型，否则应诊断为编译错误。
- 可变参函数可多传实参，但被调函数必须按正确的数量和提升后类型读取，否则可能产生未定义行为。

- **注意点：** C 没有引用传递；“指针传参”不是引用，是值传递；数组传参一定会退化为指针；const 常用于保护形参不被修改

## 1.16 strcpy 与 memcpy 的区别

### 1.16.1 基本功能对比

|特性|strcpy|memcpy|
|---|---|---|
|功能|字符串拷贝，将源字符串拷贝到目标，遇 \0 结束|内存拷贝，将指定字节数从源地址拷贝到目标地址|
|参数|`(char *dest, const char *src)`|`(void *dest, const void *src, size_t n)`|

### 1.16.2 strcpy 的特点

```c
char dst[10];
strcpy(dst, "hello");
```

- 以 '\0' 作为结束标志
- 目标空间必须**足够大**
- 用于字符串拷贝

风险：

- 易发生**缓冲区溢出**

### 1.16.3 memcpy 的特点

```c
int a[5], b[5];
memcpy(a, b, sizeof(b));
```

- 按**字节**拷贝
- 不关心数据内容
- 可用于拷贝任意对象表示或二进制缓冲区

### 1.16.4 对内存重叠的处理（高频考点）

- strcpy：**未定义行为**
- memcpy：**未定义行为**

正确方式：

```c
memmove(dst, src, len);
```

### 1.16.5 性能与使用场景

- memcpy
    - 通常更快
    - 可用 DMA / 底层优化
- strcpy
    - 只适合字符串

### 1.16.6 常见错误示例

```c
char buf[5];
strcpy(buf, "hello");  // 溢出
```

```c
memcpy(dst, src, strlen(src)); // 少拷贝 '\0'
```

### 1.16.7 嵌入式开发中的建议

- 字符串操作：
    - 确保目标缓冲区足够大，并确认源数据以 `\0` 结尾
- 内存操作：
    - 明确长度再用 memcpy
- 通信协议、外设数据：
    - 按协议长度使用 `memcpy`；存在重叠时改用 `memmove`

**注意点：**

- 两者的拷贝终止条件
- 是否适合字符串
- 内存重叠问题
- **strcpy** 面向字符串，以 **'\0'** 结束；**memcpy** 面向内存，按字节拷贝，二者都不处理内存重叠。

## 1.17 在函数中申请堆内存的注意点

### 1.17.1 明确内存的所有权（最重要）

- 函数内申请的堆内存 **不会随函数结束自动释放**
- 必须明确：
    - 谁申请
    - 谁释放

- **常见方式：** 由调用者负责释放；在接口文档中明确说明

### 1.17.2 正确返回或传出指针

**（1）作为返回值**

```c
int *create_value(void) {
    int *p = malloc(sizeof *p);
    if (p != NULL) {
        *p = 0;
    }
    return p;  // 调用者负责 free
}
```

- 合法（堆内存）

**（2）通过二级指针传出**

```c
void func(int **p) {
    *p = malloc(sizeof(int));
}
```

### 1.17.3 不能返回局部变量地址

```c
int* func(void) {
    int a;
    return &a;   // 错误
}
```

- 局部变量位于栈区，函数结束即失效

### 1.17.4 必须检查 malloc 返回值

```c
int *p = malloc(100);
if (p == NULL) {
    return;
}
```

- 防止内存不足导致崩溃

### 1.17.5 避免内存泄漏

**常见错误：**

```c
p = malloc(100);
p = malloc(200);   // 原内存未释放
```

- **原则：** 新分配前，旧内存先释放

### 1.17.6 释放后避免悬空指针

```c
free(p);
p = NULL;
```

- 防止重复释放和非法访问

### 1.17.7 函数失败路径要释放内存

```c
p = malloc(100);
if (error) {
    free(p);
    return;
}
```

- 所有返回路径都要处理内存

### 1.17.8 注意作用域不等于生命周期

- 指针变量在函数内
- 堆内存生命周期独立于函数

### 1.17.9 嵌入式开发注意点

- 避免在中断中 malloc
- 避免频繁申请释放
- 优先使用静态内存或内存池
- 函数中申请堆内存的核心是：**能正确传出、有人释放、失败路径不泄漏、释放后不再使用**

## 1.18 如何交换两个整数不用临时变量（位运算）？

### 1.18.1 使用异或运算进行交换

异或运算 (^) 是一种按位操作，具有以下性质：

- a ^ a = 0（同一个数异或，结果是 0）
- a ^ 0 = a（任何数与 0 异或，结果是该数本身）
- **异或是交换律的**：a ^ b = b ^ a

通过利用这个性质，我们可以在不使用临时变量的情况下交换两个整数的值。以下是利用位运算交换两个整数的步骤：

### 1.18.2 位运算交换的步骤

假设有两个整数 a 和 b，我们要交换它们的值，步骤如下：

1. a = a ^ b：此时 a 存储的是 a 和 b 的异或结果。
2. b = a ^ b：由于 a 已经变为 a ^ b，所以 b 会变为原来的 a 值（因为 a ^ b ^ b = a）。
3. a = a ^ b：此时 a 会变为原来的 b 值（因为 a ^ b ^ a = b）。

### 1.18.3 代码实现

```c
#include <stdio.h>

void swap(int* a, int* b) {
    if (a == b) {
        return;  // 同一对象若执行 XOR 交换，会被清零
    }
    *a = *a ^ *b;  // 步骤1
    *b = *a ^ *b;  // 步骤2
    *a = *a ^ *b;  // 步骤3
}

int main() {
    int x = 10, y = 20;
    printf("Before swap: x = %d, y = %d\n", x, y);

    swap(&x, &y);

    printf("After swap: x = %d, y = %d\n", x, y);
    return 0;
}
```

### 1.18.4 执行结果

```text
Before swap: x = 10, y = 20
After swap: x = 20, y = 10
```

### 1.18.5 解释

1. **步骤1**：*a = *a ^ *b; 将 a 和 b 的异或结果赋值给 a。此时 a 存储的是 a ^ b 的值。
2. **步骤2**：*b = *a ^ *b; 通过再次与 b 异或，b 的值变为原来的 a。
3. **步骤3**：*a = *a ^ *b; 通过再次与 b 异或，a 的值变为原来的 b。

### 1.18.6 优缺点

**优点：**

- **无需临时变量**：完全不需要额外的内存空间，只使用原始的两个变量进行交换。
- **溢出问题**：如果使用加法和减法进行交换，可能会遇到溢出问题。而异或交换通常不会有此问题。
- **缺点：** 可读性差；两个指针指向同一对象时必须特别处理；现代编译器通常能将临时变量交换优化得更好，XOR 写法并不更快。

### 1.18.7 总结

异或运算可以在不引入临时变量的情况下交换两个不同对象的整数值，但它主要是位运算知识题。工程代码应优先使用临时变量，以避免别名陷阱并保持可读性。

```c
int main(int argc, char **argv)
```

```c
int main(int argc, char *argv[])
```

```c
argc == 4
```

```c
argv[0]  // 程序名
```

内存模型：

```text
argv -> | char* | char* | ... | NULL |
          ↓
        "app"
```

- argv 是：
    - 指向**指针数组**的指针

```c
argv[i][j] = 'x';
```

```c
int main(int argc, char *argv[])
```

- 常见环境中为什么 `argc` 通常至少为 1，以及标准为什么仍允许 0
- `char **argv` 与 `char *argv[]` 在 `main` 形参声明中的等价关系
- argv[argc] == NULL 的作用
- **`argc` 表示参数个数，`argv` 可按字符串指针数组使用；作为函数形参时，`char *argv[]` 会调整为 `char **argv`。**

## 1.20 malloc、free 使用时可能出现的问题？

### 1.20.1 内存泄漏 (Memory Leak)

- **问题描述**：内存泄漏是指动态分配的内存未被释放，导致程序运行时内存无法被回收，随着时间推移，程序占用的内存会不断增大，最终可能导致内存耗尽或程序崩溃。
- **原因**：每次使用 malloc 或 calloc 分配内存时，必须确保对应的 free 被调用来释放这块内存。如果忘记调用 free，就会导致内存泄漏。

**示例：**

```c
void memory_leak() {
    int *ptr = (int*)malloc(100 * sizeof(int));  // 分配内存
    // 忘记调用 free(ptr)，导致内存泄漏
}
```

- **解决方法**：确保每个 malloc 或 calloc 都有相应的 free 调用，及时释放不再使用的内存。

### 1.20.2 双重释放 (Double Free)

- **问题描述**：双重释放是指同一块内存被释放两次，这会导致程序出现未定义行为，可能引发崩溃或内存损坏。
- **原因**：free 后，指针仍然指向原内存位置，若再次调用 free，程序会尝试释放已被释放的内存。

**示例：**

```c
void double_free() {
    int *ptr = (int*)malloc(sizeof(int));
    free(ptr);
    free(ptr);  // 再次释放同一块内存，导致双重释放错误
}
```

- **解决方法**：释放内存后，可以将指针设为 NULL，防止再次错误地调用 free。

```c
free(ptr);
ptr = NULL;  // 防止双重释放
```

### 1.20.3 悬挂指针 (Dangling Pointer)

- **问题描述**：悬挂指针是指指向已释放内存的指针。悬挂指针可能导致程序读取无效内存或出现崩溃。
- **原因**：释放内存后，指针仍然指向原内存位置，如果程序继续使用该指针，会访问已释放的内存区域。

**示例：**

```c
void dangling_pointer() {
    int *ptr = (int*)malloc(sizeof(int));
    free(ptr);
    *ptr = 10;  // 使用已经释放的内存，导致悬挂指针错误
}
```

- **解决方法**：释放内存后，立即将指针置为 NULL，避免使用已释放的内存。

```c
free(ptr);
ptr = NULL;  // 防止悬挂指针
```

### 1.20.4 内存不足 (Out of Memory)

- **问题描述**：在系统内存不足时，malloc 或 calloc 可能返回 NULL，即内存分配失败。如果程序没有检查返回值为 NULL，就会发生访问无效内存的错误。
- **原因**：malloc 无法分配足够的内存时返回 NULL，如果程序没有判断返回值，可能会导致崩溃。

**示例：**

```c
void out_of_memory() {
    int *ptr = (int*)malloc(1000000000 * sizeof(int));  // 请求过多内存
    if (ptr == NULL) {
        // 忽略了错误处理，可能导致程序崩溃
    }
}
```

- **解决方法**：始终检查 malloc 或 calloc 的返回值，确保内存分配成功。

```c
int *ptr = (int*)malloc(1000000000 * sizeof(int));
if (ptr == NULL) {
    printf("Memory allocation failed\n");
    exit(1);  // 或者进行适当的错误处理
}
```

### 1.20.5 未初始化内存

- **问题描述**：通过 malloc 分配的内存没有初始化，可能会导致使用未定义的内存内容，进而引发错误。
- **原因**：malloc 分配的内存中的内容是未初始化的，因此内存中的数据可能是垃圾值。

**示例：**

```c
void uninitialized_memory() {
    int *ptr = (int*)malloc(sizeof(int));
    printf("%d\n", *ptr);  // 使用未初始化的内存，结果不可预期
    free(ptr);
}
```

- **解决方法**：
    - 使用 calloc 来分配并初始化内存。
    - 或者在 malloc 后手动初始化内存。

```c
int *ptr = (int*)malloc(sizeof(int));
if (ptr != NULL) {
    *ptr = 0;  // 手动初始化
}
```

### 1.20.6 内存访问越界 (Out-of-bounds Access)

- **问题描述**：如果 malloc 或 calloc 分配的内存被访问超出了其分配的范围，将导致内存访问错误。
- **原因**：数组或内存块大小计算错误，导致越界访问。

**示例：**

```c
void out_of_bounds_access() {
    int *ptr = (int*)malloc(10 * sizeof(int));
    ptr[10] = 5;  // 超出分配的内存范围，访问非法内存
    free(ptr);
}
```

- **解决方法**：确保每次访问内存时，都在合法范围内。

```c
int *ptr = (int*)malloc(10 * sizeof(int));
for (int i = 0; i < 10; i++) {
    ptr[i] = i;  // 确保不越界访问
}
free(ptr);
```

### 1.20.7 内存碎片化 (Memory Fragmentation)

- **问题描述**：在程序运行期间多次调用 malloc 和 free 可能导致内存碎片化，尤其是在长时间运行的大型程序中。
- **原因**：频繁的内存分配和释放可能导致空闲内存块不连续，从而影响性能或导致无法分配大块内存。
- **解决方法**：
    - 使用内存池（Memory Pool）来管理内存分配。
    - 在需要频繁分配/释放内存的程序中，优化内存使用模式。

### 1.20.8 总结

使用 malloc 和 free 时可能会出现以下问题：

1. **内存泄漏**：分配的内存未释放，导致内存占用增加。
2. **双重释放**：尝试释放已经释放的内存。
3. **悬挂指针**：指向已释放内存的指针。
4. **内存不足**：无法分配足够内存时，未检查返回值。
5. **未初始化内存**：malloc 分配的内存未初始化。
6. **内存访问越界**：访问超出已分配内存的区域。
7. **内存碎片化**：多次分配和释放内存导致的碎片问题。

**解决方法**：确保每次分配的内存都得到释放，检查 malloc 返回值，避免双重释放和悬挂指针，考虑内存池等优化策略。

## 1.21 static 关键字在 C 与 C++ 中的用法

### 1.21.1 static 在 C 语言中的用法

**1. 修饰局部变量（静态局部变量）**

```c
void func(void) {
    static int x = 0;
    x++;
}
```

- **作用域**：函数内部
- **生命周期**：整个程序运行期
- **存储位置**：静态区（.data / .bss）
- **初始化**：仅初始化一次，默认值为 0

**考点**：多次调用函数，变量值可保持

**2. 修饰全局变量（限制作用域）**

```c
static int g_var;
```

- **作用域**：仅限当前源文件
- **链接属性**：内部链接（internal linkage）
- **目的**：防止跨文件访问，避免命名冲突

**3. 修饰函数（文件内可见）**

```c
static void func(void);
```

- 函数只能在**本文件使用**
- 常用于模块化设计
- 嵌入式驱动中非常常见

### 1.21.2 static 在 C++ 中的用法（在 C 的基础上扩展）

**1. 修饰类的成员变量（静态成员变量）**

```cpp
class A {
public:
    static int cnt;
};
```

- **类级别共享**
- 不属于某个对象
- 必须在类外定义一次：

```cpp
int A::cnt = 0;
```

**2. 修饰类的成员函数（静态成员函数）**

```cpp
class A {
public:
    static void func();
};
```

- 无 this 指针
- 只能访问：
    - 静态成员
    - 其他静态函数
- 可通过：

```cpp
A::func();
```

**3. C++ 中的静态局部对象（构造一次）**

```cpp
void func() {
    static A a;
}
```

- **首次调用时构造**
- 程序结束时析构
- 常用于 **单例模式**

### 1.21.3 C vs C++ 对比总结

|特性|C|C++|
|---|---|---|
|编程范式|过程式（Procedural）|面向对象（Object-Oriented）、过程式|
|数据抽象|结构体（struct），无成员函数|类（class），支持封装、继承、多态|
|内存管理|手动管理（malloc/free）|支持 RAII、构造/析构函数，使用 new/delete|
|函数重载|不支持|支持函数重载和运算符重载|
|命名空间|全局命名，无命名空间|支持 namespace，避免命名冲突|
|标准库|标准 C 库（stdio.h、stdlib.h 等）|标准 C++ 库（STL、iostream 容器、算法等）|

### 1.21.4 嵌入式常见使用场景

- 限制变量/函数作用域（模块封装）
- 减少命名冲突
- 保存函数内部状态
- 单例外设驱动对象

### 1.21.5 注意点

- static 改变的是**作用域或生命周期**
- static ≠ const
- 静态变量默认初始化为 0
- **C 中的 `static` 用于控制作用域和生命周期，C++ 在此基础上扩展到类级别的共享成员。**

## 1.22 typedef 和 #define 的区别

### 1.22.1 区别

|特性|typedef|#define|
|---|---|---|
|类型|创建类型别名|宏替换文本，不创建类型|
|编译期/预处理期|编译期有效，受类型检查|预处理阶段，纯文本替换|
|类型检查|支持类型检查|不支持类型检查|
|可调试性|可在调试中看到类型名|调试时只看到替换后的文本|
|作用域|遵循 C/C++ 作用域规则|全局有效，除非使用 #undef|
|用途|简化复杂类型声明，如指针、结构体别名|定义常量、宏函数或条件编译|

### 1.22.2 基本用法对比

```c
typedef unsigned int uint32_t;
#define UINT32 unsigned int
```

- typedef：引入**新类型名**
- #define：**纯文本替换**

### 1.22.3 对指针的影响（必考）

```c
typedef char* PCHAR;
#define PCHAR2 char*
```

```c
PCHAR a, b;    // a、b 都是 char*
PCHAR2 c, d;   // c 是 char*，d 是 char
```

原因：

- typedef 作为一个整体
- #define 只是简单替换

### 1.22.4 对 const 的影响（高频易错）

```c
typedef int* PINT;
const PINT p;     // int* const p
```

- p 是**常指针**
- 指向内容可变

而：

```c
#define PINT2 int*
const PINT2 p;    // const int* p
```

### 1.22.5 调试与可读性

- `typedef`
    - 能被调试器识别
    - 提高代码可读性
- `#define`
    - 预处理后宏名通常不作为类型符号留给调试器

### 1.22.6 适用场景建议

- **使用 typedef** 定义复杂类型；提高可读性；跨平台类型适配；指针、函数指针
- **使用 #define** 常量定义；条件编译；宏函数（需谨慎）

### 1.22.7 注意点

- 为什么不用 #define 定义类型
- `typedef` 只引入类型别名，不创建新的不同类型，也不定义对象。
- 宏是文本替换，没有类型检查，需警惕优先级和重复求值。
- **`typedef` 是类型别名，参与编译；`#define` 是预处理阶段的文本替换，无类型概念。**

### 1.23.1 基本含义

- const 用于**限定变量为只读**
- 本质：**编译期语义约束**
- 并不一定放在 ROM，中断、指针场景尤为常考

### 1.23.2 修饰普通变量

```c
const int a = 10;
```

- a 不能被修改
- 必须在定义时初始化
- 具有变量的类型检查特性

### 1.23.3 修饰指针（重点必考）

**（1）指向常量的指针**

```c
const int *p;
int const *p;
```

- **不能通过 p 修改指向内容**
- 指针本身可以变

**（2）常指针**

```c
int * const p = &a;
```

- 指针不可变
- 指向内容可变

**（3）指向常量的常指针**

```c
const int * const p = &a;
```

- 指针和内容都不可变

### 1.23.4 const 与数组

```c
const char str[] = "hello";
```

- 数组元素不可修改
- 常用于字符串常量保护

### 1.23.5 const 与函数参数

```c
void print_value(const int *p);
```

- 防止函数内部误修改数据
- 提高接口安全性与可读性
- 嵌入式驱动中非常常见

### 1.23.6 const 与全局变量

```c
const int g_val = 10;
```

- 在 C 中，文件作用域 `const` 对象默认具有**外部链接**；可在头文件中使用 `extern const int g_val;` 声明。
- 在 C++ 中，命名空间作用域下非 `extern` 的非 `volatile const` 对象默认是内部链接。
- 常放在只读存储区（与编译器/链接脚本相关）

### 1.23.7 const 在 C++ 中的补充

- 可修饰成员函数
- 区分重载
- 与 C 语义不同，需注意

**注意点：**

- const 修饰的是**离它最近的对象**
- const ≠ #define
- C 中的普通 `const int` 不是整型常量表达式；在支持 VLA 的块作用域中可作为可变长度数组的长度
- const 可与指针、数组、函数参数组合使用
- **const** 用于提供只读语义约束，核心在于指针搭配规则和接口安全性。

## 1.24 引用、指针的定义

### 1.24.1 指针（Pointer）的定义

**概念：**
指针是一个**变量**，用于存储另一个变量的地址。

**定义方式：**

```c
int a = 10;
int *p = &a;
```

- **特点：** 本身占用内存；可以为空（NULL）；可以改变指向；需要显式解引用 *p

### 1.24.2 引用（Reference）的定义（C++）

**概念：**
引用是**已有变量的别名**，本质上是受限的指针。

**定义方式：**

```cpp
int a = 10;
int &r = a;
```

- **特点：** 必须初始化；不能为空；一旦绑定，不能再指向其他对象；使用方式与普通变量一致

### 1.24.3 指针与引用对比

| 特性 | 指针 | 引用 |
| --- | --- | --- |
| 初始化 | 可以延后赋值 | 必须在定义时绑定 |
| 空状态 | 可以是 `nullptr` / `NULL` | 语言层面不提供空引用 |
| 改变指向 | 可以 | 绑定后不能改绑其他对象 |
| 访问对象 | 通过 `*p` / `p->` | 像直接使用原对象一样 |

### 1.24.4 内存层面理解（常考）

- 指针：有独立存储空间
- 引用：通常通过指针实现，但对用户透明

- `sizeof(int*)` 是指针对象的大小。
- `sizeof(int&)` 按语言规则得到被引用类型 `int` 的大小，不能用它判断引用的底层实现或额外存储开销。

### 1.24.5 使用场景

- **指针适用场景** 动态内存管理；需要表示“无对象”；多态、复杂数据结构
- **引用适用场景** 函数参数传递（避免拷贝）；操作符重载；提高代码可读性

### 1.24.6 典型函数参数对比

```cpp
void func1(int *p);
void func2(int &r);
```

- 指针：需判空
- 引用：更安全、语义更清晰

### 1.24.7 指针注意点

**初始化指针**：未指向时将指针初始化为NULL，避免指向随机地址。

**类型匹配**：确保指针类型与其指向的数据类型匹配。

**释放内存后将指针置空**：避免使用悬挂指针。

**检查内存分配成功**：分配内存后，检查分配是否成功，并确保不越界使用内存。

## 1.25 可变参数函数 (...) 的实现

### 1.25.1 可变参数函数简介

可变参数函数是指参数数量不固定的函数。在 C 和 C++ 中，使用 ... 来表示一个函数可以接受多个可选参数，常见的例子包括 printf 函数。可变参数函数的实现依赖于特定的机制来处理不定数量的参数，C 语言提供了标准库 <stdarg.h> 来帮助管理这些参数。

### 1.25.2 实现原理

可变参函数的底层传参方式由平台 ABI 决定，参数可能位于寄存器、寄存器保存区或栈中。C 通过 `<stdarg.h>` 中的 `va_list`、`va_start`、`va_arg`、`va_copy` 和 `va_end` 屏蔽这些差异，代码不应自行按栈布局读取参数。

### 1.25.3 实现步骤

**1. 函数定义**

函数的参数列表以 ... 结尾，表示可以接受不定数量的参数。

```c
#include <stdarg.h>

void my_func(int count, ...) {
    // 通过 va_list 来访问可变参数
}
```

- count 是已知的参数，表示参数的个数或其他信息（用于确定如何处理后续参数）。

**2. 定义 va_list 类型变量**

va_list 是在 <stdarg.h> 中定义的类型，用于访问可变参数。

```c
va_list args;
```

**3. 初始化 va_list**

使用 va_start 宏来初始化 va_list 变量，它的第一个参数是 va_list 变量，第二个参数是可变参数函数的最后一个固定参数。

```c
va_start(args, count);
```

- args 用来访问后续的参数。
- `count` 是最后一个固定参数；`va_start` 使用它来按当前 ABI 初始化遍历状态。

**4. 访问可变参数**

通过 va_arg 宏来访问每一个可变参数。va_arg 宏返回下一个参数，并自动移动到下一个参数。

```c
int param = va_arg(args, int);  // 获取下一个 int 类型的参数
```

- va_arg(args, type)：从 args 中获取一个指定类型的参数。
- 类型必须正确匹配，确保读取的参数类型和传入的类型一致。

**5. 清理 va_list**

完成后，需要通过 va_end 宏来清理 va_list 变量。

```c
va_end(args);
```

### 1.25.4 完整示例

```c
#include <stdio.h>
#include <stdarg.h>

void print_numbers(int count, ...) {
    va_list args;
    va_start(args, count);  // 初始化 va_list

    for (int i = 0; i < count; i++) {
        int num = va_arg(args, int);  // 获取每个 int 类型的参数
        printf("%d ", num);
    }

    va_end(args);  // 清理 va_list
    printf("\n");
}

int main() {
    print_numbers(3, 1, 2, 3);  // 打印 1 2 3
    print_numbers(5, 10, 20, 30, 40, 50);  // 打印 10 20 30 40 50
    return 0;
}
```

**输出**：

```text
1 2 3
10 20 30 40 50
```

### 1.25.5 总结

可变参函数按平台 ABI 传递参数，程序必须使用 `va_list` 和 `va_*` 宏以可移植方式访问。具体步骤包括：

- 使用 va_start 初始化 va_list 变量。
- 使用 va_arg 访问每个参数，类型需要与传入的参数类型匹配。
- 使用 va_end 清理 va_list 变量。

这种机制使得函数能够灵活处理不同数量的参数，像 printf 就是一个典型的使用可变参数函数的例子。

## 1.26 const 和 #define的区别

### 1.26.1 定义与功能

- const：
    - const 是 C/C++ 中的关键字，用来定义常量。它告诉编译器该变量的值不能改变，并且它的类型是已知的。
    - **作用**：const 常量是在编译时就能知道其类型和大小，且可以进行类型检查。
- #define：
    - #define 是预处理器指令，用来进行宏定义。它可以定义常量、宏函数或者条件编译代码块。
    - **作用**：#define 在预处理阶段进行文本替换，它会在编译之前替换代码中的宏定义，因此编译器并不知道宏的类型。

### 1.26.2 语法对比

- const：
  定义常量时要指定类型。

```c
const int MAX_SIZE = 100;
```

- #define：
  宏常量没有类型，直接进行文本替换。

```c
#define MAX_SIZE 100
```

### 1.26.3 类型检查

- const：
  const 定义的常量有类型，编译器可以对其进行类型检查。
    - 例如，const int MAX_SIZE = 100; 可以保证 MAX_SIZE 是一个整数，并且在使用时会进行类型检查。
- #define：
  #define 定义的宏常量没有类型信息，编译器不会进行类型检查。它仅仅是将 MAX_SIZE 替换为 100，可能导致一些类型错误。
    - 例如，#define MAX_SIZE 100 后，MAX_SIZE 在代码中只是一个数字，编译器无法验证其类型。

### 1.26.4 作用域

- const：
  const 常量的作用域是其定义的范围。例如，如果在函数内部定义了 const 常量，它的作用域就仅限于该函数。

```c
void func() {
    const int MAX_SIZE = 100;  // 仅在 func 函数中有效
```

- #define：
  #define 宏常量的作用域通常是从定义开始直到文件末尾，除非通过条件编译指令 #undef 来取消宏定义。

```c
#define MAX_SIZE 100
// MAX_SIZE 在整个文件中都有效
```

### 1.26.5 调试和优化

- const：
    - const 常量在调试时通常可以显示其名字。
    - 编译器在优化时也会将 const 常量当作固定值进行优化。
- #define：
    - #define 的常量在调试时无法直接看到其名称，因为它们只是文本替换。
    - 编译器不会知道 #define 定义的宏常量的类型，因此可能会导致调试时的问题。

### 1.26.6 内存分配

- const：
    - const 常量通常会占用内存空间（取决于编译器实现）。它的值会被存储在数据段中，并且在程序运行时可以访问。
- #define：
    - #define 宏常量不会占用内存空间。它只是代码替换，编译时会将所有 MAX_SIZE 替换成 100，所以没有实际的内存开销。

### 1.26.7 预处理和编译时行为

- const：
    - const 常量在编译时被处理。它在编译后生成机器代码的一部分，且可以在调试时被检查。
- #define：
    1. #define 是预处理器指令，在编译之前执行文本替换。它在源代码中被简单替换成文本，所以没有类型信息，编译器无法进行类型检查。
- #define 是预处理器指令，在编译之前执行文本替换。它在源代码中被简单替换成文本，所以没有类型信息，编译器无法进行类型检查。

### 1.26.8 示例对比

**const 示例：**

```c
const int MAX_SIZE = 100;  // 常量有类型，编译器会进行类型检查
void func() {
    int arr[MAX_SIZE];  // 使用 const 常量
}
```

**#define 示例：**

```c
#define MAX_SIZE 100  // 宏常量没有类型，编译器不检查类型
void func() {
    int arr[MAX_SIZE];  // 使用宏常量
}
```

### 1.26.9 总结表

|特性|const|#define|
|---|---|---|
|类型检查|有类型检查|无类型检查（仅文本替换）|
|编译期/运行期|可在编译期或运行期|仅在预处理阶段文本替换|
|存储|可能占内存或放入寄存器|不占内存，仅做宏替换|
|可调试性|可以在调试中看到符号|调试时只看到替换后的值|
|作用域|遵循 C/C++ 作用域规则|宏全局有效，除非用 #undef|
|表达式|可以是复杂表达式|可以是复杂表达式，但仅文本替换|

### 1.26.10 结论

- const 用于定义带类型的常量，具有作用域、类型检查和内存分配特性。它适用于需要确保类型安全、调试和优化的场景。
- #define 用于进行文本替换，不具有类型，适合用于宏定义、条件编译等场景，但不适用于需要类型安全和调试的常量。

## 1.27 多重包含保护（Include Guard）的实现

### 1.27.1 概念

多重包含保护是为了防止同一个头文件被多次 #include 导致重复定义的问题。重复包含头文件会引发编译错误，例如类型或函数重复定义。

### 1.27.2 实现方式

主要有两种方式：

- **方式一：#ifndef / #define / #endif（最常用）** **原理**：通过预处理宏判断头文件是否已被包含，如果没有定义宏就定义它，并包含头文件内容；如果宏已定义，则跳过头文件内容。

**语法：**

```c
#ifndef HEADER_NAME_H
#define HEADER_NAME_H

// 头文件内容，例如函数声明、结构体定义等

#endif  // HEADER_NAME_H
```

**示例：**

```c
#ifndef MY_HEADER_H
#define MY_HEADER_H

void my_function();
struct MyStruct {
    int value;
};

#endif  // MY_HEADER_H
```

- **说明**：
    - MY_HEADER_H 是一个唯一宏名，通常使用头文件名全大写并加 _H 后缀。
    - 预处理器会在第一次包含时定义宏，之后再包含该头文件时会检测到宏已定义，从而跳过重复内容。

- **方式二：`#pragma once`**：指示编译器只包含一次该头文件，无需手动定义宏。使用方式：

```c
#pragma once

// 头文件内容
```

- **优点**：
    - 简洁，无需宏定义
    - 可以避免宏名冲突
- **缺点**：
    - 虽然大多数现代编译器支持，但不是 C/C++ 标准的一部分，可能在极少数老旧编译器上不兼容。

### 1.27.3 头文件多重包含保护流程示意

```text
第一次包含：
    #ifndef MY_HEADER_H  → 条件成立
        #define MY_HEADER_H
        // 包含头文件内容
    #endif

第二次包含：
    #ifndef MY_HEADER_H  → 条件不成立，跳过头文件内容
```

### 1.27.4 总结

- **为什么需要**：防止头文件被多次包含导致重复定义错误。
- **实现方式**：
    a. **经典方式**：#ifndef / #define / #endif，兼容性好。
    b. **现代方式**：#pragma once，更简洁，但非标准。
- **实践建议**：
    - 对于跨平台或兼容性要求高的项目，使用 #ifndef / #define / #endif。
    - 对于内部或现代编译器项目，可以使用 #pragma once 简化代码。

## 1.28 内存泄漏

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/RTOS高频面试题#A22. 请说一下内存泄漏的原因。|RTOS项目 A22：内存泄漏的原因]]

### 1.28.1 什么是内存泄漏

**定义：**
程序中动态申请的内存，在**不再使用后未被释放**，导致这块内存无法再次利用。

```c
void func() {
    int *p = malloc(100);
    // 未 free(p)
}
```

### 1.28.2 内存泄漏的危害

- 程序占用内存持续增长
- 性能下降
- 系统资源耗尽
- 嵌入式系统中可能导致死机或重启

### 1.28.3 常见产生原因（高频）

1. 忘记 free
2. 指针被重新赋值，原地址丢失
3. 函数提前 return，未释放内存
4. 异常路径未处理
5. 循环中反复 malloc 不 free

### 1.28.4 如何检测内存泄漏

**（1）代码层面检查**

- malloc 与 free 是否成对
- 是否所有返回路径都释放内存

**（2）工具检测（工程常用）**

- **Valgrind（Linux）**
- AddressSanitizer（ASan）
- Visual Leak Detector（Windows）

**（3）统计法（嵌入式常用）**

- 申请/释放计数
- 剩余堆空间监控

### 1.28.5 如何避免内存泄漏（重点）

**（1）明确内存所有权**

- 谁申请，谁释放
- 接口文档说明清楚

**（2）规范释放流程**

```c
free(p);
p = NULL;
```

**（3）失败路径统一释放**

```c
p = malloc(100);
if (error) {
    free(p);
    return;
}
```

**（4）减少动态内存使用**

- 使用栈
- 使用静态内存
- 使用内存池

**（5）C++ 中使用 RAII**

- std::vector
- std::unique_ptr
- std::shared_ptr

### 1.28.6 注意点

- 尽量避免频繁 malloc/free
- 不在中断中申请内存
- 长期运行系统必须做内存监控
- 内存泄漏的本质是**申请了却没释放**，解决的关键在于**成对管理、路径完整、减少动态内存依赖**。

## 1.29 内存碎片的概述与解决方法

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/RTOS高频面试题#A20. 什么是内存碎片？|RTOS项目 A20：内存碎片]]
> - [[projects/嵌入式八股/1. 项目八股/Linux物理内存碎片高频面试题#第 21 题：外部碎片、内部碎片、伙伴系统、SLAB/SLUB 之间是什么关系？这个项目主要观测哪一类碎片问题？|内存项目 21：外部碎片、内部碎片、伙伴系统、SLAB/SLUB…]]

### 1.29.1 什么是内存碎片

**定义：**
由于频繁、大小不一的内存申请与释放，导致内存空间被分割成大量**不连续的小块**，虽然总剩余内存足够，但无法满足较大的连续申请。

### 1.29.2 内存碎片的类型

**（1）内部碎片**

- 已分配内存中**未被使用的部分**
- 由于内存对齐或分配粒度造成

**（2）外部碎片（重点）**

- 空闲内存分散，无法形成大块连续空间
- 常见于堆内存

### 1.29.3 产生原因（高频）

- 频繁 malloc / free
- 申请大小不固定
- 长时间运行程序
- 动态内存管理算法不合理

### 1.29.4 内存碎片的危害

- 大块内存申请失败
- 系统性能下降
- 嵌入式系统中可能导致异常或死机

### 1.29.5 如何检测内存碎片

- 动态内存分配失败但剩余内存充足
- 堆空间监控
- 内存使用曲线异常

### 1.29.6 解决与规避方法（重点）

**（1）减少动态内存使用**

- 使用栈
- 使用全局/静态内存

**（2）固定大小内存分配**

- 统一申请相同大小内存块
- 减少外部碎片

**（3）使用内存池（嵌入式常用）**

- 预先分配大块内存
- 按固定块管理
- 不直接使用 malloc

**（4）集中释放策略**

- 在确定时机统一释放
- 避免交叉申请/释放

**（5）避免在中断和实时任务中动态分配**

### 1.29.7 C++ 的改进手段

- 使用 STL 容器
- 自定义 allocator
- 对象池技术

### 1.29.8 注意点

- 内存碎片并非内存不足，而是**内存被用“碎”了**，长期运行系统必须主动规避
- 内存碎片是由于动态内存反复分配释放导致的非连续空闲空间问题，解决关键在于**减少动态分配、统一分配粒度、使用内存池**。

## 1.30 什么是内存池（Memory Pool），为什么需要内存池

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/RTOS高频面试题#A27. RTOS 的内存池机制如何优化内存分配？|RTOS项目 A27：RTOS 的内存池机制如何优化内存分配]]

- 从池中分配、归还小块内存

**本质：**

> 用“自己管理内存”，替代系统的动态内存分配器

### 1.30.1 什么是内存池（Memory Pool）

**内存池**是一种**预先分配一大块内存，并按固定规则进行管理和复用**的内存管理机制。

- 程序启动时一次性申请内存
- 运行过程中不再频繁调用 malloc/free
- 从池中分配、归还小块内存

**本质：**

> 用“自己管理内存”，替代系统的动态内存分配器

### 1.30.2 内存池的基本工作方式

1. 启动时申请一块大内存
2. 切分为多个固定大小的内存块
3. 使用链表或位图管理空闲块
4. 分配：取一块
5. 释放：归还到池中

### 1.30.3 为什么需要内存池（核心原因）

**（1）避免内存碎片（最重要）**

- malloc/free 反复使用会产生外部碎片
- 内存池使用固定大小块，不产生碎片

**（2）提高分配/释放速度**

- 内存池分配本质是取链表节点
- 时间复杂度接近 O(1)
- 比系统 malloc 快且稳定

**（3）提高系统稳定性**

- 不依赖堆管理器状态
- 避免运行一段时间后分配失败
- 特别适合长期运行系统

**（4）满足实时性要求**

- malloc/free 时间不确定
- 内存池分配时间可预测
- 符合实时系统要求

**（5）适合嵌入式系统**

- 堆空间小
- 无 MMU
- 动态分配风险高

### 1.30.4 内存池适用场景

- 嵌入式系统

### 1.30.5 内存池 vs malloc/free 对比

|特性|内存池（Memory Pool）|malloc / free|
|---|---|---|
|分配方式|预先分配固定大小的内存块|按需动态分配大小可变的内存|
|分配速度|快，常数时间 O(1)|较慢，需在堆上搜索合适的内存块|
|内存碎片|几乎无碎片|容易产生内存碎片|
|内存回收|通常快速，可直接归还到池中|依赖系统堆管理，可能延迟或产生碎片|
|生命周期管理|由应用控制，可循环使用|系统管理，需手动 free|
|适用场景|高频分配/释放、嵌入式系统、实时系统|通用应用程序、大小不固定的内存需求|

### 1.30.6 内存池的缺点

- 实现复杂
- 内存利用率可能降低
- 不适合大小差异很大的对象

### 1.30.7 注意点

- 内存池的核心价值在于**稳定、可控、无碎片、可预测**，是对 malloc/free 的工程级替代方案。
- 内存池通过预分配和固定块管理，避免内存碎片，提高分配效率和系统稳定性，尤其适用于嵌入式和实时系统。

## 1.31 递归函数可能会导致什么问题？

### 1.31.1 栈溢出 (Stack Overflow)

- **问题**：递归函数每调用一次，都会将当前函数的状态（局部变量、返回地址等）压入调用栈。如果递归深度过大，栈空间可能被耗尽，导致栈溢出。
- **表现**：程序异常终止，通常会出现类似“Stack Overflow”或“Segmentation Fault”的错误。
- **解决方法**：
    - 考虑转换为循环。

**示例：**

```c
void recursive_function() {
    recursive_function();  // 无限递归
}
```

### 1.31.2 性能问题

- **问题**：递归函数通常涉及多次函数调用，尤其是对于复杂的递归，可能会重复计算相同的子问题，导致性能低下。
- **表现**：如果递归没有优化，可能导致时间复杂度极高，甚至出现指数级增长。
- **解决方法**：
    - 使用**动态规划**（DP）或**记忆化递归**来缓存已计算的结果，避免重复计算。
    - 如果可能，改用**迭代算法**。

**示例（重复计算）：**

```c
int fib(int n) {
    if (n <= 1) return n;
    return fib(n-1) + fib(n-2);  // 重复计算 fib(n-1) 和 fib(n-2)
}
```

### 1.31.3 过深的递归树

- **问题**：递归树的深度过大时，可能会导致空间占用过多，尤其是递归树每一层都生成新的函数调用栈帧。
- **表现**：内存消耗过大，可能会导致堆栈溢出，或者程序性能严重下降。
- **解决方法**：
    - 在设计递归时，尽量使递归树保持平衡。
    - 采用更高效的算法，例如分治法的改进，避免不必要的递归。

**示例：**

```c
void deep_recursion(int n) {
    if (n == 0) return;
    deep_recursion(n - 1);  // 如果 n 很大，会导致深递归
}
```

### 1.31.4 递归基准条件不明确

- **问题**：递归函数必须有清晰的**基准条件**（终止条件），如果没有正确处理，递归可能永远不会终止，导致无限递归。
- **表现**：程序陷入无限递归，最终导致栈溢出或程序崩溃。
- **解决方法**：
    - 确保递归函数有明确的基准条件，并且每次递归都朝着基准条件前进。
- 限制递归深度。

**示例：**

```c
void infinite_recursion(int n) {
    // 没有终止条件，导致无限递归
    infinite_recursion(n);
}
```

### 1.31.5 代码可读性与调试困难

- **问题**：递归算法在逻辑上有时比较难理解，特别是在递归深度较大时，调试和追踪每一层的函数调用也变得复杂。
- **表现**：递归函数的调用栈较深，调试时难以追踪每次调用的状态，特别是在多次调用和中断的情况下。
- **解决方法**：
- 使用尾递归优化（一些编译器支持自动优化）。

### 1.31.6 总结

递归函数可能带来以下问题：

- **栈溢出**：递归过深导致栈空间不足。
- **性能问题**：重复计算相同的子问题导致效率低下。
- **过深的递归树**：消耗过多的内存和处理能力。
- **缺乏终止条件**：没有正确的基准条件导致无限递归。
- **调试困难**：递归逻辑可能导致代码较难理解和调试。

解决方案包括优化递归结构、使用动态规划、限制递归深度以及确保基准条件的正确性。

## 1.32 常见的变量定义

### 1.32.1 按作用域划分

1. **全局变量**

```c
int g_var = 10;
```

- 定义在函数外
- 整个程序可见（受 static 限制）
- 默认初始化为 0
2. **局部变量**

```c
void func() {
    int local_var = 5;
}
```

- 定义在函数或代码块内
- 只在当前作用域有效
- 不会自动初始化

### 1.32.2 按存储类型划分

1. **普通变量（auto，默认）**

```c
int a;
```

- 默认存储在栈区
- 生命周期为函数执行期间
2. **static 变量**

```c
static int s_var;
```

- 存储在静态区
- 生命周期为整个程序运行期间
3. **extern 变量**

```c
extern int g_var;
```

- 普通无初始化器的 `extern` 声明用来引用其他位置的对象定义，本身通常不是定义。
- `extern int g_var = 1;` 带有初始化器，仍然是一个定义。
4. **register 变量**

```c
register int r;
```

- 建议编译器将变量放入寄存器
- 不能对其取地址

### 1.32.3 按修饰符划分

1. **const 变量**

```c
const int x = 10;
```

- 只读变量
- 编译期或运行期不可修改
2. **volatile 变量**

```c
volatile int flag;
```

- 防止编译器优化
- 常用于硬件寄存器、中断共享变量
3. **const volatile 变量**

```c
const volatile int status;
```

- 只读，但值可能被外部硬件或中断修改

### 1.32.4 按数据类型划分

1. **基本类型变量**

```c
int a;
char c;
float f;
double d;
```

2. **数组**

```c
int arr[10];
char buf[32];
```

3. **指针**

```c
int *p;
char *str;
```

4. **结构体变量**

```c
struct Node {
    int val;
};
struct Node n;
```

5. **联合体变量**

```c
union Data {
    int i;
    char c;
};
union Data d;
```

6. **枚举变量**

```c
enum Color { RED, GREEN, BLUE };
enum Color color;
```

### 1.32.5 常见组合定义

1. **指向常量的指针**

```c
const int *p;
```

2. **常量指针**

```c
int * const p = &a;
```

3. **静态常量**

```c
static const int MAX = 100;
```

### 1.32.6 总结

> C 语言中变量可按作用域、存储类型、修饰符和数据类型进行定义，常见包括全局变量、局部变量、static、extern、const、volatile 以及指针、数组和结构体变量。

## 1.33 #include<> 和 #include""的区别

### 1.33.1 #include <filename>

- **用途**：包含**系统头文件**或标准库头文件。
- **搜索顺序**：
    a. 编译器预定义的系统目录（如 /usr/include 或编译器自带库路径）
    b. 系统环境中指定的额外头文件路径（如通过 -I 选项添加）
- **特点**：
    - 通常从实现配置的系统/包含路径查找；确切搜索顺序由编译器实现和命令行选项决定。
    - 常用于标准库（如 #include <stdio.h>）。

### 1.33.2 #include "filename"

- **用途**：包含**用户自定义头文件**。
- **搜索顺序**：
    a. 当前源文件所在目录
    b. 如果未找到，再按实现规定的后续包含路径查找。
- **特点**：
    - 优先搜索当前目录，便于引用项目内自定义头文件
    - 如果头文件在其他路径，需要通过 -I 选项添加搜索路径。

### 1.33.3 总结对比表

|用法|搜索路径顺序|说明|
|---|---|---|
|#include <file>|优先搜索系统头文件目录（如 /usr/include）|通常用于包含标准库或第三方库的头文件|
|#include "file"|先搜索当前源文件所在目录，再搜索系统头文件目录|通常用于包含自定义的项目头文件|

### 1.33.4 总结

> `#include <...>` 一般用于系统或标准库头文件，`#include "..."` 一般优先查找引用文件附近的项目头文件；完整搜索顺序由具体实现决定。

## 1.34 头文件#ifndef/#define/#endif的作用

### 1.34.1 基本作用

- 用于**防止头文件被重复包含**
- 避免：
    - 重复定义
    - 编译错误
- 又称 **头文件保护（Header Guard）**

### 1.34.2 典型写法

```c
#ifndef DRIVER_UART_H
#define DRIVER_UART_H

/* 头文件内容 */

#endif  // DRIVER_UART_H
```

- 第一次包含：宏未定义 → 编译内容
- 再次包含：宏已定义 → 直接跳过

### 1.34.3 为什么会重复包含

- 同一个 .c 文件里 include 了同一个头文件多次
- 头文件相互嵌套包含

```c
A.h -> B.h
B.h -> A.h
```

### 1.34.4 不加保护的后果

- 结构体重复定义
- 枚举、宏、全局变量重定义
- 编译直接报错

### 1.34.5 宏名命名规范（工程常考）

- 全大写
- 唯一、不冲突
- 通常包含路径信息

```c
#ifndef DRIVER_UART_H
```

### 1.34.6 头文件应放什么（高频面试）

- 函数声明
- 类型定义（struct / enum / typedef）
- 宏定义
- extern 声明

不应放：

- 具有外部链接的对象定义。
- 普通非 `inline` 函数定义（应放在 `.c` 文件）。

**注意点：** 头文件保护解决单个翻译单元中的重复包含，不自动解决类型不完整或循环依赖问题。保护宏应唯一，且避免使用双下划线或下划线加大写字母开头的实现保留标识符。

## 1.35 #error的目的是什么？

### 1.35.1 #error 的作用

#error 是 C/C++ 预处理器指令之一，主要用于在预处理阶段检测到某些条件时，**生成编译错误**并终止编译过程。

- 当编译器遇到 #error 指令时，编译过程会立即终止，并在编译器输出中显示 #error 后面的错误消息。

### 1.35.2 语法

```c
#error 错误信息
```

- **错误信息**：可以自定义一个字符串消息，编译器会将此消息输出到错误日志中。

### 1.35.3 典型用途

#error 常用于以下场景：

1. **条件编译检测**
    - 在复杂的条件编译中，如果某些预期的条件不满足，可以使用 #error 生成编译错误，提醒开发者某个条件必须满足，否则无法继续编译。
2. **编译器或平台的特定要求**
    - 如果代码依赖于特定的编译器或平台功能，可以通过 #error 确保代码只在支持的环境中编译。
3. **编译时配置检查**
    - 在构建系统中，通过 #error 提醒开发者某些编译配置或选项不正确。

### 1.35.4 示例代码

**1. 条件编译检测**

假设我们希望检查是否定义了某个宏，如果没有定义，编译器就会报错：

```c
#ifndef MY_MACRO
#error "MY_MACRO is not defined!"
#endif
```

如果 MY_MACRO 没有定义，编译器会输出以下错误信息：

```text
error: "MY_MACRO is not defined!"
```

**2. 平台特定要求**

假设代码只能在 64 位系统上编译，如果是 32 位系统，则强制编译失败：

```c
#if defined(_WIN32) && !defined(_WIN64)
#error "This code requires a 64-bit system."
#endif
```

如果在 32 位 Windows 系统上编译，编译器会显示如下错误：

```text
error: This code requires a 64-bit system.
```

**3. 编译配置检查**

假设我们需要确保在编译时开启了某些特定的编译选项：

```c
#if !defined(_DEBUG)
#error "This code must be compiled in Debug mode."
#endif
```

如果没有定义 _DEBUG，编译器会报错：

```text
error: This code must be compiled in Debug mode.
```

### 1.35.5 总结

#error 指令用于在编译阶段强制终止编译，并输出自定义的错误信息。它常用于条件编译时，确保某些预编译条件得到满足，或者确保代码只在特定环境下编译。

## 1.36 #ifdef、#ifndef、#error 的使用场景？

### 1.36.1 #ifdef（如果已定义）

- **用途**：用于判断一个宏是否已定义。如果已定义该宏，则编译器会包含宏后的代码；如果未定义，则跳过该段代码。
- **常见场景**：
    - 防止重复定义宏。
    - 条件编译不同平台的代码。
    - 控制某些功能是否启用。

**语法：**

```c
#ifdef MACRO_NAME
    // 如果 MACRO_NAME 已定义，执行这部分代码
#endif
```

**示例：**

```c
#define DEBUG  // 定义调试宏

#ifdef DEBUG
    printf("debug mode\n");
#endif
```

### 1.36.2 #ifndef（如果未定义）

- **用途**：用于判断一个宏是否未定义。如果未定义该宏，则编译器会包含宏后的代码；如果已定义，则跳过该段代码。
- **常见场景**：
    - 防止头文件的多重包含（常用于头文件保护）。
    - 条件编译不同的实现或功能。

**语法：**

```c
#ifndef MACRO_NAME
    // 如果 MACRO_NAME 未定义，执行这部分代码
#endif
```

**示例：**

```c
// 未定义 MY_HEADER_H 时，编译器会处理以下内容
#ifndef MY_HEADER_H
#define MY_HEADER_H
int value;
#endif
```

> **防止头文件重复包含**：

```c
#ifndef MY_HEADER_H
#define MY_HEADER_H

// 头文件内容

#endif  // MY_HEADER_H
```

### 1.36.3 #error（生成编译错误）

- **用途**：在编译过程中触发一个编译错误，并可以附带自定义的错误信息。
- **常见场景**：
    - 当某些条件不满足时，强制停止编译并给出错误提示。
    - 用于在特定条件下生成编译时错误（例如：缺少宏定义或不支持的编译环境）。

**语法：**

```c
#error "Error message"
```

**示例：**

```c
#ifndef PLATFORM
    #error "Platform is not defined!"  // 如果没有定义 PLATFORM，则生成编译错误
#endif
```

> **应用场景**：

- 在平台间的代码编译中，强制要求定义特定的宏：

```c
#if defined(__linux__)
    // Linux-specific code
#else
    #error "Unsupported platform"
#endif
```

### 1.36.4 总结

- **`#ifdef` 和 `#ifndef`：** 控制条件编译，帮助针对不同配置或平台选择代码。
- **`#error`：** 在指定条件下产生编译诊断，用于尽早报告不支持的配置。

## 1.37 volatile声明的作用

### 1.37.1 基本含义

- volatile 告诉编译器：
  **该变量的值可能在程序控制之外被改变**
- 使对该 `volatile` 对象的访问成为可观察行为，编译器不得任意省略或合并这些访问。

### 1.37.2 为什么需要 volatile

在没有 volatile 的情况下，编译器可能会：

- 将变量缓存到寄存器
- 消除“看似无用”的重复读取
- 对普通访问做不影响单线程可观察结果的重排。`volatile` 不是通用编译器/CPU 内存屏障，不保护其他普通内存访问。

```c
while(flag == 0);   // 若 flag 非 volatile，可能被优化为死循环
```

### 1.37.3 volatile 的典型使用场景（嵌入式必考）

**（1）中断与主程序共享变量**

```c
volatile int flag;
```

- 中断中修改
- 主循环中读取

**（2）硬件寄存器映射**

```c
#define GPIO_ODR (*(volatile unsigned int *)0x4001080C)
```

- 每次访问都必须真实读写硬件

**（3）不应单独用于线程/RTOS 同步**

- 在 C 抽象机中，`volatile` 不提供原子性、线程间顺序或互斥。
- 多线程共享可变数据应使用 C11 `_Atomic`、RTOS 同步原语或互斥/临界区。
- 中断与主程序共享时，除 `volatile` 外还要确认目标平台的访问宽度和原子性，必要时使用临界区。

### 1.37.4 volatile 与 const 组合

```c
volatile const int reg;
```

- 程序不能修改
- 硬件可能修改

典型：**只读状态寄存器**

### 1.37.5 volatile 不能做什么（易错点）

- 不能保证**原子性**
- 不能保证**线程安全**
- 不能替代：
    - 临界区
    - 互斥锁
    - 内存屏障

### 1.37.6 volatile 与 static 搭配

```c
static volatile int tick;
```

- 文件内可见
- 中断/定时器计数常用写法

**注意点：**

- volatile 防止的是**编译器优化**，不是 CPU 缓存
- 与多核一致性无直接关系
- 哪些变量必须加 volatile
- **volatile** 用于禁止编译器对变量的优化假设，确保每次访问都真实发生，常用于中断和硬件寄存器场景；它本身不提供线程同步或原子性。

## 1.38 register 关键字

### 1.38.1 基本作用

- 建议编译器：
  **将变量存放在寄存器中以提高访问速度**
- 属于**优化提示（hint）**
- 编译器**可以忽略**

```c
register int i;
```

### 1.38.2 register 的特性

- 可能存放在 CPU 寄存器或普通内存中，由编译器决定。
- **无法获取地址**

```c
register int x;
int *p = &x;   // 编译错误
```

### 1.38.3 使用限制

- 只能修饰：
    - 局部变量
    - 函数形参
- 不能修饰：
    - 全局变量
    - 静态变量

### 1.38.4 实际效果（现代编译器）

- 现代编译器：
    - 自动进行寄存器分配
    - 优化能力远强于人工指定
- register 基本**已失去实际意义**

### 1.38.5 与 volatile 的关系

- `register`：存储类说明符，不允许对所声明对象取地址，但不保证真的分配到寄存器。
- `volatile`：类型限定符，约束对该对象的可观察访问。

```c
register volatile int x;   // 合法 C：不可取地址，访问仍具有 volatile 语义
```

- 两者不冲突，只是这种组合在现代工程中很少有必要。

### 1.38.6 在 C / C++ 标准中的现状

- C：
    - C11 仍保留
    - 但不推荐使用
- C++：
    - C++11 起被弃用
    - C++17 起不再是存储类说明符，不能继续作为普通编程用法

### 1.38.7 嵌入式中的说明

- 早期 MCU / 老编译器中有意义
- 现代 ARM-GCC / Clang：
    - 使用 -O2 / -O3 更有效
- 面试中重点在**理解语义而非使用**
- **常见考点** 为什么不能取地址；register 是否一定在寄存器中；为什么逐渐被淘汰；register** 是给编译器的寄存器优化建议，不能取地址，现代编译器中基本不再需要**

## 1.39 一个变量既可以是 const 又可以是 volatile 吗

### 1.39.1 先说结论

**可以，同时存在，而且有明确使用场景。**

```c
volatile const int reg;
```

### 1.39.2 各自含义回顾

- const
    - **程序不可修改**
    - 编译期语义约束
- volatile
    - **值可能被外部修改**
    - 禁止编译器优化

### 1.39.3 同时使用时的语义（重点）

```c
volatile const int reg;
```

含义是：

- 程序代码 **不能写 reg**
- reg 的值 **可能随时变化**
- 每次访问都必须**从真实内存读取**

### 1.39.4 典型应用场景（嵌入式必考）

**（1）硬件只读寄存器**

```c
#define STATUS_REG (*(volatile const uint32_t *)0x40000000)
```

- MCU 状态寄存器
- 硬件更新
- 软件只读

**（2）中断/硬件更新的状态量**

- 主程序只读
- 外设或中断修改

### 1.39.5 指针形式对比（易混点）

```c
const volatile int *p;
volatile const int *p;
```

- 二者**完全等价**
- 修饰的是 *p 指向的对象

### 1.39.6 常见误解

- 认为 const 和 volatile 冲突（错误）
- 认为 volatile 能保证线程安全（错误）
- 认为 const 一定放在 ROM（错误）

### 1.39.7 面试常问追问

- 为什么硬件寄存器要加 volatile
- 为什么状态寄存器还要加 const
- 如果少一个会有什么问题
- **const** 约束程序写入，**volatile** 约束编译器优化，二者可同时使用，典型场景是硬件只读寄存器。

## 1.40 指针与 const 的组合使用区别（const int*、int* const、const int* const）？

### 1.40.1 const int\* 或 int const\*

- **含义**：指向常量 int 的指针。
- **解释**：const 修饰的是 int 类型，意味着通过该指针不能修改所指向的 int 值，但指针本身可以改变指向不同的地址。
- **使用场景**：当你需要一个指针指向一个常量，且不打算通过这个指针修改其值时使用。

**示例：**

```c
const int* ptr;
int a = 10;
int b = 20;
ptr = &a;  // 合法
*ptr = 15; // 错误：不能通过指针修改值
ptr = &b;  // 合法
```

- **重点**：指向的内容是常量，但指针本身可以改变。

### 1.40.2 int* const

- **含义**：常量指针，指向 int 类型的指针。
- **解释**：const 修饰的是指针本身，意味着指针不能指向其他地址，但可以通过该指针修改所指向的 int 值。
- **使用场景**：当你希望指针指向一个固定的地址，但允许修改地址所指向的值时使用。

**示例：**

```c
int* const ptr;
int a = 10;
int b = 20;
ptr = &a;  // 合法
*ptr = 15; // 合法：可以修改值
ptr = &b;  // 错误：指针不能改变指向
```

- **重点**：指针本身是常量，不能改变指向，但指向的内容可以修改。

### 1.40.3 const int* const 或 int const* const

- **含义**：常量指针，指向常量 int 类型的指针。
- **解释**：const 修饰的是指针和所指向的内容，意味着既不能通过指针修改所指向的 int 值，也不能改变指针指向的地址。
- **使用场景**：当你希望指针和所指向的内容都不允许修改时使用。

**示例：**

```c
const int* const ptr;
int a = 10;
int b = 20;
ptr = &a;  // 合法
*ptr = 15; // 错误：不能通过指针修改值
ptr = &b;  // 错误：指针不能改变指向
```

- **重点**：指针和它指向的内容都是常量，既不能修改指针的值，也不能修改指针指向的数据。

### 1.40.4 总结对比

- const int\* / int const\*：指向常量，指针可变。
- int* const：常量指针，指向的数据可变。
- const int* const：指向常量的常量指针，既不可修改指向的数据，也不可修改指针本身。

### 1.40.5 应用场景

- const int*：当你不希望通过指针修改数据，但允许指针指向其他地址时使用。例如，传递数组给函数时，表示函数不能修改数组元素。
- int* const：当你希望指针始终指向相同的地址，但可以修改该地址上的数据时使用。例如，常用在某些硬件寄存器的指针定义中。
- const int* const：当你需要指针和数据都不被修改时使用。例如，定义一个函数参数时，既不希望函数改变指针的地址，也不希望修改数据。

## 1.41 整型溢出和浮点精度丢失的情况及其影响

### 1.41.1 整型溢出

当整数运算的数学结果超出类型可表示范围时，无符号和有符号类型的规则不同：

- **无符号整数**：按模 `2^N` 算术运算，超过范围时会按标准规则回绕。
- **有符号整数**：结果无法表示时是**未定义行为**，程序不能依赖于“从最大值回绕到最小值”。
- **溢出的常见场景** **无符号整数溢出**：

```c
#include <stdio.h>
#include <limits.h>

int main(void) {
    unsigned int a = UINT_MAX;
    printf("a = %u\n", a);
    a += 1;  // 发生溢出
    printf("a after overflow = %u\n", a);  // 输出 a = 0
    return 0;
}
```

- **结果**：无符号整数溢出后会回绕至 0。
- **有符号整数溢出**：

```c
#include <limits.h>

int a = INT_MAX;
// a += 1;  // 不要这样做：有符号溢出是未定义行为
```

- **结果**：标准没有规定运行结果，编译器可以基于“有符号溢出不会发生”进行优化。

**溢出影响**

- **未定义行为**：有符号溢出没有可依赖的结果；无符号回绕则是定义良好的，但仍可能造成逻辑错误。
- **安全漏洞**：整数范围检查失败可能进一步导致缓冲区大小计算错误、越界等安全问题。
- **逻辑错误**：程序逻辑可能错误地处理溢出的值，导致计算结果不正确，可能产生异常或错误结果。

**预防方法**

- 使用适当的类型来防止溢出，例如使用 long long 或 uint64_t。
- 对数据进行边界检查，在进行运算前确认是否可能发生溢出。
- 使用编译器提供的检查机制（例如 GCC/Clang 的 `__builtin_add_overflow`）或工程封装的 checked arithmetic，并明确其可移植性。

### 1.41.2 浮点精度丢失

浮点数在表示大多数实数时并不精确，因为它们只能表示有限的精度。浮点数的表示基于科学记数法，通常包含一个尾数和一个指数，精度受限于尾数的位数。在进行浮点数计算时，可能会出现精度丢失的问题。

**浮点精度丢失的原因**

- **有限精度**：浮点数的尾数位数有限，不能表示所有的小数值。例如，0.1 在二进制浮点表示中无法精确表示。
- **舍入误差**：计算时，浮点数可能会被舍入或截断，导致丢失精度。
- **表示范围**：浮点数可以表示的数值范围有限，超出范围的数值会丢失。
- **浮点数精度丢失的示例** **例1：浮点表示的舍入误差**

```c
#include <stdio.h>

int main() {
    double x = 0.1;
    double sum = 0.0;

    for (int i = 0; i < 10; i++) {
        sum += x;
    }

    printf("Sum = %f\n", sum);  // 预期应该输出 1.0，但实际输出可能是 0.999999
    return 0;
}
```

- **结果**：因为浮点数的精度限制，0.1 无法精确表示，导致多次加法后的误差累积。
- **例2：超出表示范围**

```c
int main() {
    double x = 1.0e308;  // 近乎最大的 double 值
    double y = 1.0e308;

    double result = x * y;  // 超出 double 的表示范围，导致溢出为 inf

    printf("Result = %f\n", result);  // 输出 inf
    return 0;
}
```

- **结果**：由于超出了浮点数的表示范围，计算结果会变为无穷大（inf）。

**浮点精度丢失的影响**

- **数值误差**：可能导致计算结果与实际结果之间有微小的误差，影响程序的正确性。
- **不准确的比较**：浮点数之间的比较可能不精确，导致逻辑错误（例如在判断浮点数是否相等时）。
- **累积误差**：在多次浮点运算中，误差可能累积，导致最终结果严重偏离预期。
- **避免浮点精度丢失的建议** **避免直接比较浮点数**：使用一个精度容忍度（例如 epsilon）进行浮点数比较，而不是直接比较相等性。

```c
#include <stdio.h>
#include <math.h>

int main() {
    double a = 0.1 * 10;
    double b = 1.0;
    double epsilon = 1e-9;

    if (fabs(a - b) < epsilon) {
        printf("a and b are considered equal.\n");
    }

    return 0;
}
```

- **使用高精度类型**：如果需要更高精度的计算，可以使用 long double 或库提供的高精度类型（如 GMP 库）。
- **合理的数值缩放**：在处理浮点数时，尽量避免数值过大或过小，保持数值在合理范围内。

## 1.42 结构体与共用体的区别

### 1.42.1 基本概念

1. **结构体（struct）**
    - 结构体是将不同类型的数据组合成一个单元的聚合数据类型。
    - 每个成员有独立的内存空间，成员之间的数据是并行存储的。
2. **共用体（union）**
    - 共用体是将多个不同类型的数据存储在同一内存空间中。
    - 所有成员共享同一块内存，因此每次只能存储一个成员的值。

### 1.42.2 内存分配

1. **结构体**
    - 成员按声明顺序存储，中间和末尾可有对齐填充；因此 `sizeof(struct)` 通常大于或等于各成员大小之和。
2. **共用体**
    - 所有成员共享起始存储位置；`sizeof(union)` 至少能容纳最大成员，并满足所有成员的对齐要求，因而可能包含尾部填充。

### 1.42.3 存储和访问

1. **结构体**
    - 结构体成员的数据是并行存储的，修改一个成员的值不会影响其他成员的值。
    - 例如：

```c
struct Student {
    int age;
    float height;
};
struct Student s1;
s1.age = 20;     // 设置 age 为 20
s1.height = 1.75; // 设置 height 为 1.75
```

2. **共用体**
    - 共用体成员共享同一块内存，修改一个成员会影响其他成员的值。
    - 例如：

```c
union Value {
    int i;
    float f;
};

union Value value = {.i = 42};
```

### 1.42.4 使用场景

1. **结构体**
    - 当需要存储多个不同类型的数据，并且每个数据都需要独立存储时，使用结构体。
    - 常见场景：学生信息、员工数据、矩阵等。
2. **共用体**
    - 当多个数据类型需要共用同一块内存时，使用共用体。适用于存储互斥的数据类型。
    - 常见场景：协议解析、内存池、共享内存区域等。

### 1.42.5 内存对比示例

假设有以下结构体和共用体：

```c
struct DataStruct {
    int i;
    float f;
};

union DataUnion {
    int i;
    float f;
};
```

- **结构体大小**：
  假设 int 占 4 字节，float 占 4 字节，结构体的大小为 4 + 4 = 8 字节。
- **共用体大小**：
  在常见 ABI 中，若 `int` 和 `float` 都占 4 字节且对齐要求一致，该共用体通常为 4 字节；仍应以目标平台的 `sizeof` 为准。

### 1.42.6 总结

> 结构体中的每个成员拥有独立的内存空间，适用于存储多个不同类型的相关数据；而共用体中的所有成员共享同一内存空间，每次只能存储一个成员的值，适用于需要节省内存或互斥使用数据的场景。

> 结构体每个成员独立存储，适用于多个数据并行存储；共用体所有成员共享同一内存，适用于互斥使用的数据。

## 1.43 指针类型转换的风险

### 1.43.1 常见的指针类型转换方式

1. **隐式转换**：某些情况下，编译器会自动将指针类型进行兼容转换，例如 void* 与其他指针类型之间。
2. **显式转换**（强制类型转换）：C 使用 `(type *)` 形式；C++ 另提供 `static_cast`、`reinterpret_cast` 等分类更明确的转换。
3. **const 修饰符转换**：去掉或增加 `const` 的转换，如 `(int *)const_ptr`。

### 1.43.2 指针类型转换的风险

- **指针所指对象类型不匹配：** 将指针强制转换为不兼容的类型，再通过转换后的指针访问对象，可能违反有效类型/别名规则并导致未定义行为。例如：

```c
float f = 3.14;
int* p = (int*)&f;   // 强制类型转换
int val = *p;        // 未定义行为，可能得到错误的值
```

- **原因**：浮点数和整数的内存表示不同，直接按整数读取浮点数，会得到错误的数据。
- **对齐要求不满足：** 指针转换后访问未对齐的内存是未定义行为，在某些嵌入式平台上可能引发总线异常，在其他平台上也可能降低性能。例如：

```c
char buffer[8];
int* p = (int*)(buffer + 1); // 未对齐访问
*p = 10;                     // 在某些嵌入式平台可能导致崩溃
```

- **原因**：int 通常要求 4 字节对齐，如果指针未按要求对齐，CPU 可能抛出异常。
- **丢失 `const` 限定：** 可以转换掉限定，但若原对象本身定义为 `const`，通过转换后指针写入是未定义行为。例如：

```c
const int value = 10;
const int *p = &value;
/* 不要把 p 强制转换为 int* 后写入。 */
```

- **原因**：某些常量可能存储在只读存储区，强行修改可能导致程序崩溃。
- **野指针与越界访问：** 类型转换会改变指针算术的步长，若忽略实际对象边界，容易越界。例如：

```c
char buf[8];
int* p = (int*)buf;  // 将字节数组当作 int 数组
p[2] = 100;          // 越界访问，buf 只有 8 字节
```

- **影响**：破坏内存数据、引起崩溃或不可预期的行为。
- **非法释放：** 转换指针类型本身不改变动态分配块的起始地址，但只能将分配函数返回的原始地址（或空指针）传给 `free`。例如：

```c
void* p = malloc(10);
int* ip = (int*)p;
free(ip);  // 正确，但如果 ip 指向内存偏移位置，可能导致非法释放
```

- **原因**：释放内存时必须使用原始分配指针，否则可能破坏内存管理结构。

### 1.43.3 避免风险的建议

1. **尽量避免不必要的指针类型转换**。
2. **使用 void\* 进行通用传参时，要谨慎转换为正确类型**。
3. **保持类型匹配**：确保指针类型和所指对象类型一致。
4. **注意对齐要求**：在嵌入式平台尤其重要。
5. **不要去掉 `const` 后修改只读数据**。
6. **结构体和数组转换时保证大小和偏移安全**。
7. **调试和静态分析**：使用工具检测潜在未定义行为和越界访问。

## 1.44 sizeof与strlen的区别

### 1.44.1 先说结论

|特性|sizeof|strlen|
|---|---|---|
|功能|返回类型或变量所占内存字节数|返回字符串实际长度（不包括末尾 \0）|
|计算方式|通常在编译时确定；操作数类型为 VLA 时可在运行时求值|运行时遍历字符串直到 `\0`|
|参数类型|类型或变量|字符串指针|
|返回值类型|size_t|size_t|
|注意事项|对数组返回整个内存大小，对指针返回指针大小|必须是以 \0 结尾的字符串，否则结果未定义|

### 1.44.2 基本用法对比

```c
char s[] = "hello";

sizeof(s);   // 6
strlen(s);   // 5
```

原因：

- sizeof：数组真实大小
- strlen：遇到 '\0' 停止

### 1.44.3 数组与指针场景（高频考点）

```c
char s1[] = "abc";
const char *s2 = "abc";
```

### 1.44.4 函数参数中的区别（必考）

```c
void func(char s[]) {
    sizeof(s);   // 指针大小
    strlen(s);   // 正确
}
```

- 数组传参会**退化为指针**
- `sizeof(s)` 在此只能得到调整后的指针大小，不能得到调用方数组容量。

### 1.44.5 安全性差异

- `sizeof`
    - 通常不求值其操作数，但 VLA 相关表达式可能在运行时求值。
    - 对指针只返回指针本身大小，无法获知 `malloc` 分配块的大小。
- `strlen`
    - 依赖 '\0'
    - 若无结尾，可能越界

### 1.44.6 嵌入式中的使用建议

- 缓冲区大小：sizeof
- 字符串长度：strlen
- 协议、DMA、结构体：sizeof

**常见错误：**

- 用 `sizeof` 代替 `strlen` 求指针所指字符串的长度。
- 用 `strlen` 代替 `sizeof` 求数组容量。
- 忽略结尾 `\0` 在字符数组占用空间和字符串逻辑长度中的差异。

> `sizeof` 计算对象或类型的字节大小；`strlen` 计算以 `\0` 结尾字符串的长度，不包括结尾 `\0`。

## 1.45 按位与、或、异或在嵌入式控制中常用场景？

在嵌入式开发中，位运算（按位与、按位或、按位异或）广泛应用于硬件控制、协议处理、寄存器配置、状态位操作等方面。位运算操作符能在硬件上直接执行，并且通常非常高效，因此特别适用于需要对硬件寄存器进行精细控制的场景。

### 1.45.1 按位与（AND） &

按位与操作用于清除指定的位或检测某些位的状态。它通常用于：

- **清除某些特定位**
- **掩码操作**（masking）
- **位检测**
- **常用场景：** **清除指定的位**：在控制硬件设备时，我们可能需要清除某个寄存器的某些位，而不影响其他位。可以通过按位与操作与一个掩码（mask）进行运算。

```c
#define FLAG_MASK 0x0F   // 清除高 4 位
unsigned char reg = 0xFF;  // 假设寄存器的初始值为 0xFF
reg &= FLAG_MASK;  // 高 4 位清零，reg 变为 0x0F
```

- **检测某些位的状态**：通过按位与操作和掩码一起使用，可以检查特定位是否为 1。

```c
unsigned char reg = 0xAA;  // 1010 1010
if (reg & 0x04) {  // 检查第 3 位是否为 1
    // 执行某些操作
}
```

**示例：清除状态寄存器的某些标志位**

```c
#define FLAG_REGISTER 0xFF  // 假设寄存器的初始值为 0xFF
#define STATUS_MASK 0xF0    // 我们只想保留高 4 位

unsigned char reg = FLAG_REGISTER;
reg &= STATUS_MASK;  // 只保留高 4 位，低 4 位清零
```

### 1.45.2 按位或（OR） |

按位或操作用于设置指定的位。它常用于：

- **设置某些位**
- **组合多个状态位**
- **常用场景：** **设置某些位**：有时我们需要将某些位设置为 1，而不改变其他位。通过按位或操作，可以在不修改其他位的情况下，设置特定位置为 1。

```c
unsigned char reg = 0x0F;  // 初始值 00001111
reg |= 0x10;               // 设置第 5 位为 1，reg 变为 0x1F
```

- **组合多个标志位**：在协议或控制指令中，常常需要将多个标志位组合成一个完整的控制命令。可以通过按位或操作将多个标志位合并。

```c
unsigned char cmd = 0x00;  // 假设命令初始值为 0
cmd |= 0x01;  // 设置第 0 位为 1，表示启动
cmd |= 0x02;  // 设置第 1 位为 1，表示启用某个功能
```

**示例：设置设备的控制位**

```c
#define CONTROL_REGISTER 0x00   // 假设控制寄存器初始值为 0x00
#define DEVICE_ENABLE_MASK 0x01  // 启动设备的控制位掩码

unsigned char reg = CONTROL_REGISTER;
reg |= DEVICE_ENABLE_MASK;  // 设置第 0 位，启动设备
```

### 1.45.3 按位异或（XOR） ^

按位异或操作常用于：

- **切换位的状态**
- **校验和**
- **奇偶校验**
- **常用场景：** **切换位的状态**：按位异或是非常有效的切换位的方式。通过异或操作，可以将某个特定的位从 0 切换为 1，或者从 1 切换为 0。

```c
unsigned char reg = 0x01;  // 初始值 00000001
reg ^= 0x01;               // 切换第 0 位，reg 变为 0x00
reg ^= 0x01;               // 再次切换第 0 位，reg 变为 0x01
```

- **校验和与错误检测**：在数据传输中，按位异或常用于生成简单的校验和，帮助检查传输错误。

```c
unsigned char data1 = 0xFF;
unsigned char data2 = 0xA5;
unsigned char checksum = data1 ^ data2;  // 计算校验和
```

- **奇偶校验**：在一些嵌入式通信协议中，使用异或操作来实现奇偶校验。

**示例：切换控制寄存器的某个标志位**

```c
#define CONTROL_REGISTER 0x01   // 初始值为 00000001
#define BIT_TO_TOGGLE 0x01      // 第 0 位需要切换

unsigned char reg = CONTROL_REGISTER;
reg ^= BIT_TO_TOGGLE;  // 切换第 0 位，reg 变为 0x00
reg ^= BIT_TO_TOGGLE;  // 切换第 0 位，reg 变为 0x01
```

## 1.46 数组名与指针的区别

### 1.46.1 本质区别

> **数组名不是指针，而是在表达式中会退化为指针**

### 1.46.2 定义方式不同

```c
int a[10];
int *p;
```

- a：**数组**
- p：**指针变量**

### 1.46.3 内存分配差异

- **数组名**
    - 在定义时分配**连续内存**
    - 大小固定，不可改变
- **指针**
    - 只分配**指针本身大小**
    - 可指向任意地址

### 1.46.4 sizeof 行为不同（高频考点）

```c
sizeof(a);   // 整个数组大小
sizeof(p);   // 指针大小
```

- 数组名不会退化为指针参与 sizeof

### 1.46.5 可修改性差异

```c
a = p;   // 错误
p = a;   // 正确
```

- 数组不是可修改左值，不能整体赋值；这不意味着数组名是一个“常量指针”。
- 指针是变量

### 1.46.6 指针算术的差异

```c
a + 1;   // 指向 a[1]
p + 1;   // 指向下一个元素（若已指向数组）
```

- 表达式结果类似
- **语义来源不同**

### 1.46.7 传参行为（重点）

```c
void func(int a[]);
```

- 数组名作为实参时：
    - **退化为指针**
    - 函数内无法区分数组或指针

### 1.46.8 适用场景

- 使用数组：
    - 固定大小缓冲区
    - 静态数据结构
- 使用指针：
    - 动态内存
    - 灵活访问

**注意点：**

- 认为数组名就是指针
- 认为 sizeof(a) 等于 sizeof(p)
- 忽略数组不可赋值的特性
- **数组名代表一块连续内存，大小固定不可改；指针是变量可变，二者只是在表达式中表现相似**

## 1.47 数组指针与指针数组的区别

### 1.47.1 基本概念

> **数组指针是“指向数组的指针”，指针数组是“装指针的数组”**

### 1.47.2 定义方式对比（核心考点）

**（1）数组指针（pointer to array）**

```c
int a[10];
int (*p)[10] = &a;
```

- p 是**指针**
- 指向一个 **含 10 个 int 的数组**
- 类型：

```c
int (*)[10]
```

**（2）指针数组（array of pointers）**

```c
int *p[10];
```

- p 是**数组**
- 每个元素都是 int *
- 类型：

```c
int *[10]
```

### 1.47.3 sizeof 行为差异（高频）

```c
sizeof(p);
```

- 数组指针：
    - sizeof(p) → 指针大小
- 指针数组：
    - sizeof(p) → 10 × 指针大小

### 1.47.4 内存布局区别

- **数组指针**
    - 一个指针变量
    - 指向一整块连续数组
- **指针数组**
    - 连续存放多个指针
    - 每个指针可指向不同地址

### 1.47.5 指针运算差异

```c
p + 1;
```

- 数组指针：
    - 跨过整个数组
- 指针数组：
    - 跨过一个指针元素

### 1.47.6 常见使用场景

- **数组指针** 二维数组传参；精确描述数组边界

```c
void process(int (*rows)[10]);
```

- **指针数组** 字符串数组；命令行参数

```c
char *argv[];
```

### 1.47.7 记忆技巧（面试常用）

> **先看 []，再看 \***

- *p[10] → 指针数组
- (*p)[10] → 数组指针
- **注意点：** 混淆定义顺序；忽略括号优先级；误用在函数参数中；**数组指针指向整个数组，指针数组本身就是数组，核心区别在于“谁是数组、谁是指针”**

## 1.48 指针函数与函数指针的区别

### 1.48.1 基本概念

> **指针函数是“返回指针的函数”，函数指针是“指向函数的指针”**

### 1.48.2 定义方式对比（核心考点）

**（1）指针函数（Pointer Function）**

```c
int* func(void);
```

- func 是**函数**
- 返回值类型是 **指针**
- 本质：普通函数

常见示例：

```c
char* my_strcpy(char *dst, const char *src);
```

**（2）函数指针（Function Pointer）**

```c
int (*pfunc)(int, int);
```

- pfunc 是**指针**
- 指向一个函数
- 可通过指针调用函数

```c
pfunc = add;
pfunc(1, 2);
```

### 1.48.3 括号优先级区别（必考）

- int* func();
  → 函数，返回 int*
- int (*func)();
  → 指针，指向函数

**括号决定本质**

### 1.48.4 对比

|特性|指针函数（Pointer to Function Return）|函数指针（Function Pointer）|
|---|---|---|
|定义含义|函数返回一个指针|一个指针变量，指向函数|
|典型声明|`int* func();`|`int (*funcPtr)(int);`|
|使用方式|调用函数后返回指针|通过指针调用函数，例如 `funcPtr(10);`|
|主要用途|获取动态分配或全局/静态对象的地址|用于回调、策略模式、动态选择函数|
|调用结果|得到指针，可以操作指向的数据|执行指针指向的函数，返回函数返回值|

## 1.49 指针使用场景

### 1.49.1 作为函数参数（传地址）

- **作用：** 在函数内部修改实参；避免大对象的值拷贝，提高效率

**示例：**

```c
void swap(int *a, int *b);
```

### 1.49.2 动态内存管理

- **作用：** 在运行时申请和释放内存；解决栈空间不足问题
- **相关接口：** C：malloc / free；C++：new / delete

**示例：**

```c
int *p = (int *)malloc(sizeof(int) * n);
```

### 1.49.3 数组与字符串操作

- **作用：** 数组名在表达式中退化为指向首元素的指针；高效遍历数组和字符串

**常见形式：**

```c
void func(int *arr);
char *str;
```

### 1.49.4 构建复杂数据结构

- **作用：** 实现非连续存储结构
- **典型应用：** 链表；树；图；队列

**示例：**

```c
struct Node {
    int data;
    struct Node *next;
};
```

### 1.49.5 函数指针（回调机制）

- **作用：** 实现回调函数；提高程序扩展性和灵活性

**示例：**

```c
void (*func)(int);
```

- **应用场景：** qsort 比较函数；状态机设计；中断或事件回调

### 1.49.6 访问硬件或特殊内存（嵌入式开发）

- **作用：** 直接访问寄存器或指定内存地址

**示例：**

```c
#include <stdint.h>

volatile uint32_t *reg = (volatile uint32_t *)(uintptr_t)0x40021000u;
```

- **说明：** 地址、访问宽度、对齐和整数到指针的转换都由目标平台定义，必须以芯片手册、链接脚本和厂商头文件为准。

### 1.49.7 多级指针（指针的指针）

- **作用：** 修改指针本身；表示二维数组或动态数组；处理命令行参数

**示例：**

```c
void func(int **p);
int main(int argc, char **argv);
```

### 1.49.8 面向对象中的多态（C++）

- **作用：** 使用基类指针指向派生类对象；实现运行时多态

**示例：**

```cpp
Base *p = new Derived();
p->func();
```

### 1.49.9 与 const / volatile 结合使用

- **作用：** 提高接口安全性；防止误修改；支持并发或硬件访问

**常见形式：**

```c
const int *p;
int * const p;
volatile int *p;
```

**总结：**
指针是 C/C++ 中实现高效内存管理、灵活接口设计、底层控制以及复杂数据结构的核心工具，也是区分初级与中高级程序员的重要知识点。

## 1.50 malloc

malloc 是 C 语言中最常用的**动态内存分配函数**，用于在**堆区**申请一块连续内存。

### 1.50.1 基本原型

```c
void *malloc(size_t size);
```

- size：申请的字节数
- 返回值：
    - 成功：返回指向申请内存的首地址（void*）
    - 失败：返回 NULL

### 1.50.2 基本用法

```c
int *p = (int *)malloc(sizeof(int));
```

- 申请内存大小必须用 sizeof
- C 语言中**不强制类型转换**（C++ 必须）

### 1.50.3 内存特点（必考）

- 分配在 **堆区**
- 内存内容**未初始化**，包含不确定的字节内容；不要在写入前将其当作已初始化对象值读取。
- 生命周期由程序员控制
- 必须配合 free 使用

### 1.50.4 常见使用场景

**（1）动态数组**

```c
int *arr = (int *)malloc(sizeof(int) * n);
```

**（2）动态结构体**

```c
struct Node *p = malloc(sizeof(struct Node));
```

### 1.50.5 malloc 与 free 配对原则

```c
int *p = malloc(sizeof(int));
if (p != NULL) {
    /* 使用 */
    free(p);
    p = NULL;
}
```

- **原则：** 申请一次，释放一次；释放后指针置空，防止悬垂指针

### 1.50.6 常见错误（面试高频）

**（1）忘记判断返回值**

```c
p = malloc(100);   // 可能返回 NULL
```

**（2）内存越界访问**

```c
p = malloc(4);
p[1] = 10;
```

**（3）内存泄漏**

```c
p = malloc(100);
p = malloc(200);   // 原内存丢失
```

**（4）重复释放**

```c
free(p);
free(p);
```

### 1.50.7 malloc vs calloc vs realloc

|特性|malloc|calloc|realloc|
|---|---|---|---|
|功能|分配指定字节数的内存|分配指定数量的元素，每个元素初始化为 0|调整已分配内存块|
|初始化|未初始化，内存内容不确定|自动初始化为 0|原内存内容保持不变，扩展的部分未初始化|
|参数|size_t size|size_t num, size_t size|void *ptr, size_t new_size|
|返回值|指向分配内存的指针|指向分配内存的指针|指向调整后内存的指针（可能改变地址）|
