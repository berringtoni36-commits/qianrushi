大家好，我是蟹老板~

这么多年下来，我发现时钟是 STM32 最容易被低估的模块。

时钟树看着是最简单的底层配置，实则是 STM32 所有外设运行的根基。**所有外设的精度、稳定性、响应速度、功耗表现，全绑在时钟树上**。

## 一、时钟基础（嵌入式硬件视角）

### 1.1 数字电路时钟核心定义——频率、周期、抖动

数字电路里的时钟，本质上是一串周期性变化的电平信号。

高、低、高、低。

看着挺朴素。实际上 MCU 里几乎所有同步逻辑都得听它指挥。

频率表示一秒钟出现多少个完整周期，单位是 Hz。周期表示完成一次高低变化需要多长时间，两者互为倒数。T=f1

72MHz 时钟的周期大约是 13.89ns。

这意味着在理想情况下，内核每隔 13.89ns 就能获得一次新的节拍。注意，我说的是“获得节拍”，不是每条 C 语句都能在一个周期里执行完。指令流水线、总线等待、Flash 延迟、缓存命中情况，全都在里面掺和。

除了频率和周期，还有一个很容易被忽略的东西——抖动。

理想时钟的每个边沿都应该准时出现，可现实世界没这么讲武德。电源噪声、晶振相位噪声、PLL 环路噪声、PCB 串扰，都会让某个边沿早一点或者晚一点。

假设一个 10MHz 时钟，理想周期是 100ns。

实际测量可能出现 99.8ns、100.1ns、100.3ns。

这些时间偏移就是抖动的一种表现。

普通 GPIO 翻转可能根本不在乎这点变化。高速 USB、精密 ADC、音频采样、以太网接口却很敏感。频率平均值看起来正确，不代表时钟质量就一定好。

还有占空比。

很多数字模块只关心上升沿，但某些高速外设、外部存储器接口或者需要双边沿采样的电路，会对高电平和低电平的持续时间提出要求。

所以别把时钟理解成一个单纯的数字。

它其实有频率、相位、占空比、抖动、启动时间、温漂等一整套脾气。像个表面老实、实际上需求一堆的甲方。

### 1.2 MCU 时钟存在的意义（内核、总线、外设同步驱动）

MCU 为什么必须有时钟？

因为绝大多数 MCU 内部电路都是同步数字电路。内部触发器不会凭空知道什么时候更新状态，大家需要一个统一的节拍。

CPU 内核需要时钟，才能取指、译码、执行。

AHB、APB 总线需要时钟，才能搬运地址和数据。

GPIO 外设虽然看起来只是拉高拉低，但它背后的寄存器访问仍然走总线。总线没时钟，你写再多次 `GPIOx->ODR` 都像往黑洞里扔纸条。

定时器更直接。它靠时钟脉冲递增计数器，没有输入时钟，CNT 就永远停在那里装死。

USART 根据外设时钟计算位宽。ADC 根据采样时钟决定采样保持时间和转换速度。SPI 根据时钟分频产生 SCK。I2C 的时序寄存器也依赖 APB 时钟。

所以 MCU 不是只有一个时钟。

它更像一个公司。SYSCLK 是老板定的大方向，AHB 和 APB 是各级部门，外设时钟是每个员工的工位电源。老板来上班了，不代表每个员工的电脑都自动开机。

### 1.3 时钟异常引发的典型工程问题

时钟问题最烦人的地方，在于它经常伪装成别的问题。

串口乱码时，你会先怀疑接线、波特率、校验位。

ADC 波动时，你会先怀疑参考电压、传感器、运放。

定时器周期不对时，你会先怀疑 PSC 和 ARR。

程序跑飞时，你会先怀疑数组越界和野指针。

这些怀疑都合理，可时钟一旦错了，上层所有计算都会跟着歪。

说几个比较典型的坑：

系统以为自己跑在 72MHz，实际仍然跑在 8MHz，导致 `SystemCoreClock` 和真实频率不一致。

APB1 设置了二分频，却忘了定时器时钟会自动变成两倍，于是 PWM 频率整整高了一倍。

ADC 时钟超过芯片允许上限，室温下勉强工作，高温环境里数据开始抽风。

提高主频前没有增加 Flash 等待周期，CPU 一加速，取指开始失败。

HSE 起振失败后程序永远卡在等待标志位的 `while` 循环里，量产时偶发“开不了机”。

PLL 参数算出来的结果看似正确，可 VCO 输入或输出范围越界，芯片就是不锁定。

低功耗模式唤醒后时钟源变了，串口初始化参数却没重新计算，第一包数据直接乱码。

这些问题没有哪个特别高深，但组合到一起，真的能让人锈逗。

## 二、STM32 时钟树整体框架

### 2.1 时钟树整体架构逻辑（多级层级分发体系）

STM32 的时钟树，看起来像一张地铁线路图。

左边是一堆时钟源。

中间是选择器、倍频器和分频器。

右边是内核、总线和各类外设。

信号从左往右流动，大致会经历下面这条路径。

```
HSI / HSE / MSI        │        ▼   时钟源选择        │        ├──────────────► 直接作为 SYSCLK        │        ▼       PLL        │        ▼     SYSCLK        │        ▼   AHB 预分频器        │        ├──────────────► HCLK / CPU / DMA / SRAM        │        ▼ APB1 与 APB2 预分频器        │        ├──────────────► 通用外设        └──────────────► 定时器时钟
```

另外还有一些不完全服从这条主干的独立时钟。

RTC 可以选择 LSE、LSI，某些系列还能使用 HSE 分频。

USB 往往要求精确的 48MHz，可能来自专用 PLL 输出。

ADC 在部分系列中有独立异步时钟。

SAI、I2S、SDMMC、FDCAN、RNG 也可能有自己的内核时钟选择器。

这就是时钟树设计的核心思路。

不是拿一个超高频时钟怼遍全芯片，而是根据模块需求逐级分发。需要高性能的跑快，需要低功耗的跑慢，不用的直接关掉。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-008.jpg]]

### 2.2 两大时钟体系——高速系统主时钟树与 RTC 低速独立支路

把复杂细节先放一边，STM32 时钟大体可以看成两个世界。

一个世界负责运行程序。

它包含 HSI、HSE、MSI、PLL、SYSCLK、HCLK、PCLK，以及各种高速外设时钟。

另一个世界负责慢慢计时。

它主要包含 LSI、LSE、RTC 和独立看门狗。

高速时钟关注性能，单位经常是 MHz。

低速时钟关注功耗和长期稳定性，典型频率只有几十 kHz。

两者之所以要分开，是因为 RTC 希望在主系统睡眠、停机甚至主电源部分关闭时仍然继续运行。

比如设备进入 Standby，CPU 和大部分 SRAM 都停了，LSE 仍然可以在备份域里慢悠悠地振荡。RTC 继续计时，闹钟到了再把系统叫醒。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-009.jpg]]

### 2.3 主流 STM32 系列时钟树差异（F1/F0/F4/L4/H7 核心区别）

STM32 系列多得有点离谱。同样叫 RCC，不同系列的复杂度差别很大。

F0 和 F1 的时钟树相对简单，特别适合拿来学底层逻辑。

STM32F1 常见的系统时钟源是 HSI、HSE 和 PLL。经典 F103 最高主频 72MHz。PLL 结构简单，主要就是选择输入源和倍频系数。简单是简单，但灵活性也有限。

例如 HSI 进入 PLL 前固定除以 2。8MHz HSI 经过二分频只剩 4MHz，即使使用最大 16 倍频，也只能得到 64MHz。想跑 72MHz，一般得上 8MHz HSE，再乘 9。

F0 的主频通常更低，很多型号运行在 48MHz 左右。有些器件自带 HSI48，做 USB 时会方便很多。它不像 F1 那么执着于“外置 8MHz 加九倍频”这套经典组合。

F4 的 PLL 明显复杂起来。

它有 PLLM、PLLN、PLLP、PLLQ 等参数。一个 PLL 不仅要给系统提供主时钟，还可能同时给 USB、SDIO、随机数发生器提供 48MHz 域。

公式如下：

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-010.jpg]]

你会发现它不再是“输入乘几倍”这么简单了。参数组合多，约束也多。

L4 的特性是低功耗。

它支持多档 MSI，可以在非常低的频率下运行，也可以把频率拉到几十 MHz。某些型号还能让 MSI 借助 LSE 自动校准，兼顾功耗和精度。

对于电池设备，这套机制很香。

设备平时用低频 MSI 摸鱼，需要处理任务时再升频，处理完马上降回去。老板看了都想把这套管理方式搬进公司。

H7 则是另一个画风。

多个电源域、多个总线域、多个 PLL、内核时钟、AXI 时钟、AHB 时钟、APB 时钟，全凑齐了。部分 H7 还有 D1、D2、D3 等时钟域，不同外设可能位于不同域里。

H7 配时钟时，除了频率，还得关心电压档位、供电模式、Flash 延迟、域间分频和内核时钟比例。

在 F1 上配错时钟，可能串口乱码。

在 H7 上配错时钟，调试器可能刚连上，芯片就原地失联。

所以学时钟树时，我一直建议先拿 F1 或 F0 建立完整认知，再去看 F4、L4、H7。别一上来挑战满配 H7，容易把学习嵌入式变成心理健康测试。

## 三、时钟树核心硬件模块底层原理

### 3.1 多路复用器 MUX——时钟切换逻辑与毛刺风险

多路复用器就是时钟选择开关。

多个输入，只允许其中一路连接到输出。

```
HSI ─┐HSE ─┼──► MUX ───► SYSCLKPLL ─┘
```

软件通过 RCC 配置位选择目标时钟源。可时钟不是静态电平，它一直在跳变。

如果硬件粗暴地在某个随机时刻切换，旧时钟刚拉高，新时钟正好也在变化，中间可能产生一个特别窄的脉冲。

这个窄脉冲就是毛刺。

对组合逻辑来说，它可能只是一闪而过。对时序逻辑来说，它可能被当成一个合法边沿，让某些触发器提前更新。

STM32 内部的系统时钟切换通常带有硬件同步和无毛刺处理，但软件仍然必须遵守顺序。

新时钟没有稳定之前，别切。

切换命令写入以后，别立刻假设已经完成。

应该读取状态位，确认当前系统时钟来源真的发生了变化。

F1 上的 `SW` 位负责发出选择请求，`SWS` 位表示当前实际使用的时钟源。两者不是同一个概念。

```
RCC->CFGR &= ~RCC_CFGR_SW;RCC->CFGR |= RCC_CFGR_SW_PLL;while ((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_PLL){    /* 等待硬件完成切换 */}
```

只写 `SW` 不看 `SWS`，多少有点像给同事发了消息，没看到回复就默认他已经干完了。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-012.jpg]]

### 3.2 分频器 Divider——预分频、后分频硬件规则

分频器会对输入时钟脉冲进行计数，每累计若干个脉冲再输出一次。

二分频意味着输入两个周期，输出一个周期。

四分频意味着输入四个周期，输出一个周期。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-013.jpg]]

STM32 时钟树里常见 AHB 预分频、APB1 预分频、APB2 预分频、ADC 预分频和 USB 分频。

“预分频”和“后分频”只是相对于某个模块的位置。

时钟进入 PLL 前的分频叫前级分频。

从 PLL 的 VCO 输出再分下来，叫后级分频。

在复杂系列中，合理的前后分频不只是为了得到目标频率，还要确保中间节点处于合法范围。

比如最后输出 100MHz，不代表中间 VCO 频率随便多少都行。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-014.jpg]]

### 3.3 锁相环 PLL——倍频原理、VCO 约束、锁定稳定时间与失锁机制

PLL 的中文叫锁相环。

很多教程一句话带过，说它负责倍频。这个说法没错，但太扁平了。

PLL 内部通常包含相位比较器、环路滤波器、压控振荡器，也就是 VCO，以及反馈分频器。

它会不断比较参考时钟与反馈时钟之间的相位差，再调整 VCO，使两者逐渐同步。

锁定以后，输出频率与输入频率保持确定比例。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-015.jpg]]

具体公式会随系列变化，但思路差不多。

PLL 有几个工程上绕不开的限制。

输入频率不能太低，也不能太高。

VCO 输入必须处于指定范围。

VCO 输出也必须处于指定范围。

倍频和分频系数只能取芯片允许的离散值。

启用 PLL 后需要等待锁定，不能刚打开就切过去。

参考时钟如果消失，PLL 可能失锁。

环境温度、电源噪声和时钟源质量也会影响锁定稳定性。

有些人算 PLL，只看最后结果。

比如输入 8MHz，想输出 72MHz，直接说乘 9，完事。

在 F1 上这样算问题不大，因为结构简单。

到了 F4、H7，这么算很容易漏掉 VCO 范围。最终结果看着正确，中间节点却违规，PLL 就会摆烂。

### 3.4 时钟就绪标志与启动超时等待机制

STM32 上电后通常不会直接使用外部晶振。

因为外部晶振需要起振时间。这个时间受晶体参数、负载电容、温度、供电上升速度和 PCB 条件影响。

内部 RC 时钟启动更快，所以芯片往往先从 HSI 或 MSI 启动。

接下来软件打开 HSE，再等待 `HSERDY`。

PLL 打开后等待 `PLLRDY`。

LSE 打开后等待 `LSERDY`。

正确代码一定要带超时。

```
static int RCC_WaitFlag(volatile uint32_t *reg,                        uint32_t mask,                        uint32_t expected,                        uint32_t timeout){    while (((*reg) & mask) != expected)    {        if (timeout-- == 0U)        {            return -1;        }    }    return 0;}
```

调用时可以这样写。

```
RCC->CR |= RCC_CR_HSEON;if (RCC_WaitFlag(&RCC->CR,                 RCC_CR_HSERDY,                 RCC_CR_HSERDY,                 1000000U) != 0){    /* HSE 启动失败，进入降级流程 */}
```

不加超时会怎样？

实验室里可能一切正常。

量产一万台后，某块板子的晶体参数稍微偏一点，上电时 HSE 没起来，程序就永远卡在启动阶段。

设备不复位，不报错，也不继续运行。

它就在那里等。

等一个永远不会来的 `HSERDY`。

## 四、五大时钟源（树根，硬件底层）

### 4.1 高速内部时钟 HSI

HSI 是高速内部 RC 振荡器。

它集成在 MCU 内部，不需要外部晶体和负载电容。启动快、成本低、布板省心，是绝大多数 STM32 上电后的默认时钟来源。

F103 的 HSI 典型频率为 8MHz。

不同系列的 HSI 频率不完全一样，有些是 16MHz，有些还提供 48MHz 内部振荡器。看具体型号手册，别拿 F1 的经验硬套所有系列。

HSI 省钱、省引脚、启动快，外部晶振坏了还能拿来兜底。

缺点的话，精度和温漂通常不如外部晶体。

电压和温度变化会让频率发生漂移。

芯片一般会在出厂时对 HSI 做校准，并提供微调寄存器。但它终究还是 RC 振荡器，别指望它天然拥有晶体级稳定性。

普通 UART、定时任务、低成本控制应用，HSI 往往够用。

要求严格的 USB、精准音频采样、长期计时或者高精度通信，就要慎重。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-017.jpg]]

### 4.2 高速外部晶振 HSE

HSE 来自芯片外部。

常见形式有两种。

一种是无源晶体加两颗负载电容。

另一种是外部有源时钟直接送入 OSC_IN，引脚配置为旁路模式。

无源晶体本身不是一个“主动输出时钟”的器件。它与 MCU 内部的反相放大器、偏置电路和外部电容共同组成振荡回路。

HSE 的优点是精度高、温漂相对小、长期稳定性好。

代价是多占两个引脚，需要晶体和电容，PCB 布局也得认真。

F103 开发板最常见的是 8MHz HSE。

8MHz 进入 PLL 乘 9，刚好得到 72MHz。USB 时钟再从 72MHz 除以 1.5 得到 48MHz，组合很舒服。

这也是为什么 8MHz 晶体在 F1 项目里特别常见。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-018.jpg]]

### 4.3 多速内部时钟 MSI、MSIS 与 MSIK

MSI 主要出现在强调低功耗的 STM32 系列中。

它不是一个固定频率振荡器，而是可以选择多个频率档位。系统轻载时使用较低档位，任务变重时再升高。

这套思路很适合电池设备。

比如传感器节点大部分时间只需要维护状态，几百 kHz 或几 MHz 就够了。等到采样、运算和通信时，再把频率拉上去。

部分新一代低功耗系列把 MSI 相关时钟进一步拆成 MSIS 和 MSIK。

MSIS 更偏向系统时钟域。

MSIK 更偏向部分内核外设时钟域。

这样做可以让 CPU 和某些外设使用不同节奏，不必全芯片绑在一个频率上。

具体频率档位和可连接外设会因芯片而变，这一块必须看对应型号的 RCC 章节。不要看到名字相似，就默认寄存器也一样。

MSI 还有一个很有点东西的能力。

部分系列支持借助 LSE 对 MSI 自动校准。

LSE 是 32.768kHz 晶体，精度通常比内部 RC 更高。硬件可以拿 LSE 当参考，持续修正 MSI 偏差。

于是系统获得一种折中方案。

主时钟不用一直依赖高功耗外部高速晶体，却能通过低功耗 LSE 提升内部时钟精度。

这套设计在低功耗产品里真的很香，不是 PPT 香，是电流表上能看见的那种香。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-019.jpg]]

### 4.4 低速内部时钟 LSI

LSI 是低速内部 RC 振荡器，频率通常在几十 kHz 附近。

它启动快，不需要外部器件，常被用于独立看门狗，也可以作为 RTC 的时钟源。

LSI 的主要问题是精度一般。

如果拿它跑 RTC，设备短时间看起来没事。运行几天、几周以后，累计误差可能逐渐明显。

对“每天差几分钟也无所谓”的设备，LSI 足够。

对电表、门锁、数据记录器、日历时钟这类长期计时设备，我更愿意用 LSE。

看门狗的目标是救命，独立看门狗使用 LSI 倒是很合理。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-020.jpg]]

### 4.5 低速外部晶振 LSE

LSE 通常使用 32.768kHz 晶体。

这个数字看起来有点怪，其实它是 (2^{15})。

经过 15 次二分频就能得到 1Hz，特别适合 RTC。

LSE 的优点是功耗低、长期稳定性好、计时精度高。

它的缺点就是起振慢，信号幅度小。对 PCB 泄漏、污染、寄生电容和干扰比较敏感。

高速晶振不起振，很多时候还能拿探头看看。

LSE 的信号非常脆弱，普通示波器探头一怼上去，探头电容本身都可能把振荡回路压死。

这时候真别逞强。优先用 MCO、RTC 校准输出或者内部状态位间接判断。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-021.jpg]]

### 4.7 晶振起振失败常见硬件问题排查

晶振不起振时，别上来就换代码。

我通常先确认芯片到底配置成晶体模式还是旁路模式。

如果外部接的是有源振荡器，却没有打开 bypass，配置就不对。

如果接的是无源晶体，却开了 bypass，也不可能正常工作。

接着看器件。

晶体频率是否符合芯片范围。

负载电容是否匹配。

晶体等效串联电阻 ESR 是否过大。

驱动功率是否超过晶体限制。

焊接方向虽然对普通无源晶体通常不敏感，但封装引脚定义仍然得确认。

然后看布局。

走线是不是太长。

旁边是不是有 DC-DC 开关节点。

地平面是否被割裂。

是否放了大电容，把振荡回路压得太重。

是否存在助焊剂残留、潮气和漏电。

更深一层会涉及负阻分析。

振荡器要稳定起振，MCU 内部振荡放大器提供的负阻绝对值必须明显大于晶体等效串联电阻。

工程上常用的经验是留出数倍裕量。

若负阻裕量太小，室温样机也许能启动，低温、高温、低电压或批量参数离散时就会暴露问题。

测负阻通常需要串联测试电阻，逐步增加阻值并观察振荡何时停止，再结合晶体 ESR 做估算。这是偏硬件验证的活，不建议拿普通示波器探头直接怼晶体两端。

探头电容可能改变负载条件，导致原本正常的晶振被你测到停振。

最离谱的是，你一拿开探头，它又好了。

## 五、系统主时钟 SYSCLK（树干，内核核心频率）

### 5.1 SYSCLK 三种可选输入源

以经典 STM32F103 为基准，SYSCLK 可以选择 HSI、HSE 或 PLL 输出。

不同系列可能增加 MSI、CSI 或其他来源，但底层选择逻辑相似。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-027.jpg]]

#### 5.1.1 直连 HSI

HSI 直连是最省事的配置。

F103 上电默认通常就在这个状态，系统以 8MHz 运行。

它适合启动阶段、故障降级、低成本设计和对频率要求不高的应用。

直连 HSI 不需要等待外部晶体，也不需要等待 PLL 锁定，启动速度非常快。

#### 5.1.2 直连 HSE

HSE 也可以不经过 PLL，直接作为 SYSCLK。

如果板上使用 8MHz 晶体，那么系统就以 8MHz 运行。

与 HSI 直连相比，HSE 直连频率未必更高，但精度通常更好。

某些对频率精度敏感、性能要求不高的应用，会选择这种方案。

#### 5.1.3 PLL 倍频输出

想让 F103 跑到 72MHz，通常要使用 PLL。

最经典的组合如下。

```
HSE = 8MHzPLL 输入 = 8MHzPLL 倍频 = 9PLL 输出 = 72MHzSYSCLK = 72MHz
```

性能上去了，配置步骤也变多。

Flash 延迟要提前设置。

总线分频要保证不超限。

PLL 输入必须合法。

PLL 开启后要等待锁定。

切换完成后还要更新 `SystemCoreClock` 和 SysTick。

少一步，都可能埋雷。

### 5.2 PLL 完整频率计算公式、VCO 范围约束与合法取值

F1 的主 PLL 相对简单。

使用 HSE 时，可选择 HSE 直接输入，或者先除以 2。

如果倍频系数为 5，输出就是 20MHz。

### 5.3 时钟安全系统 CSS

CSS 是 Clock Security System，也就是时钟安全系统。

它可以监测 HSE。

当 HSE 失效时，硬件会自动把系统时钟切换到 HSI，避免 CPU 因主时钟消失而直接停摆。

部分系列还会触发不可屏蔽中断 NMI，让软件执行故障处理。

CSS 很像备用发电机。

外部电网突然断了，系统先切到内部电源保命。性能和精度可能下降，但总比当场躺平强。

F1 上启用 CSS 很简单。

```
RCC->CR |= RCC_CR_CSSON;
```

真正麻烦的是故障后的软件策略。

系统切到 HSI 后，CPU 频率变了。

串口波特率可能不准。

USB 可能无法继续运行。

定时器周期会变化。

SysTick 节拍也可能变化。

所以 NMI 处理函数里不能只清个标志就完事。你需要决定设备进入安全模式、重新初始化通信、记录错误，还是尝试恢复 HSE。

```
void NMI_Handler(void){    if ((RCC->CIR & RCC_CIR_CSSF) != 0U)    {        RCC->CIR |= RCC_CIR_CSSC;        /*         * 此时系统可能已经切换到 HSI。         * 应进入降级状态，停止对时钟精度敏感的业务。         */        Clock_FaultCallback();    }}
```

有时高频快速算完再睡，比低频慢慢磨更省电。这个得拿电流表测，嘴上争没意义。

#### 5.4.2 20MHz 中速平衡配置（无外置晶振、轻量级应用）

### 5.5 Flash 访问延时配置

CPU 频率提高以后，Flash 不一定跟得上。

F103 在常见供电条件下，Flash 等待周期大致可按下面思路配置。

| HCLK 范围 | Flash 等待周期 |
| --- | --- |
| 不高于 24MHz | 0 |
| 24MHz 到 48MHz | 1 |
| 48MHz 到 72MHz | 2 |

提高主频前，要先增加 Flash 等待周期。

降低主频后，才可以减少等待周期。

顺序不能反。

从 8MHz 升到 72MHz 时，推荐流程如下。

```
先配置 Flash 为 2 个等待周期再配置总线分频再启动 HSE 和 PLL再切换 SYSCLK 到 PLL
```

从 72MHz 降回 8MHz时，顺序反过来。

```
先切换 SYSCLK 到 HSI确认切换成功再降低 Flash 等待周期
```

如果先把 Flash 延迟从 2 降到 0，而 CPU 还在 72MHz 跑，接下来一次取指就可能翻车。

这种错误有时不会稳定复现。Debug 模式能跑，Release 模式崩。加一句日志后又好了。

特别折磨人。

## 六、总线与外设时钟分支（树枝）

### 6.1 三层总线架构——AHB、APB1 与 APB2

F1 的主干可以简化为三层。

AHB 是高速总线。

CPU、DMA、SRAM、Flash 接口和部分高速模块都与它相关。HCLK 通常就是 AHB 时钟，也是内核主要工作节拍。

APB1 是低速外设总线。

USART2、USART3、I2C、SPI2、USB、CAN、部分定时器等常挂在 APB1。

APB2 是高速外设总线。

GPIO、AFIO、USART1、SPI1、ADC、部分高级定时器常挂在 APB2。

这里的“低速”和“高速”是相对称呼，不代表 APB1 上的外设都很慢。

F103 满频运行时，一般这样配置。

```
SYSCLK = 72MHzHCLK   = 72MHzPCLK1  = 36MHzPCLK2  = 72MHz
```

为什么 APB1 要减半？

因为它的额定上限低于系统主频。

时钟树不是为了把所有地方都跑到最快，而是为了保证每个模块运行在自己的安全范围内。

### 6.2 APB 预分频特殊规则——定时器时钟自动乘 2

这条规则很多人记住了现象，却没理解原因。

当 APB 预分频为 1 时，定时器时钟等于 PCLK。

当 APB 预分频大于 1 时，定时器时钟通常等于 2 倍 PCLK。

```
APB 分频 = 1TIMCLK = PCLKAPB 分频 = 2、4、8 或 16TIMCLK = 2 × PCLK
```

这不是定时器内部突然多了一个 PLL。

硬件只是从分频链上选择了一个更高频的节点，让 APB 总线可以降频省功耗，同时保留定时器的时间分辨率。

假设 SYSCLK 为 72MHz。

APB1 设置二分频，PCLK1 为 36MHz。

TIM2 的时钟仍然可以是 72MHz。

这设计挺聪明。

总线不用一直高速翻转，定时器又不会因为总线降频损失一半精度。

算定时器参数时，建议统一写一个函数，不要到处手算。

```
uint32_t GetAPB1TimerClock(void){    uint32_t pclk1 = HAL_RCC_GetPCLK1Freq();    uint32_t ppre1 = RCC->CFGR & RCC_CFGR_PPRE1;    if (ppre1 == RCC_CFGR_PPRE1_DIV1)    {        return pclk1;    }    return pclk1 * 2U;}
```

#### 6.3.1 USB 专用 PLL 时钟

USB Full Speed 要求 48MHz 时钟，而且精度要求不低。

F103 的常见方案是 PLL 输出 72MHz，再除以 1.5 得到 48MHz。

如果系统只跑 64MHz，就没法通过这个固定分频得到 48MHz。

这也是 F103 使用 HSI 做 PLL 时很难兼顾满速 USB 的原因之一。

新系列通常会提供 PLLQ、HSI48 或 CRS 自动校准等更灵活的方案。

做 USB 时别只看 CPU 主频。

真正关键的是 48MHz 域是否准确、稳定并且满足规格。

#### 6.3.2 ADC 独立时钟分频

F103 的 ADC 时钟来自 PCLK2 分频。

常见分频系数包括 2、4、6、8。

系统为 72MHz 时，我通常选 6 分频得到 12MHz。

```
RCC->CFGR &= ~RCC_CFGR_ADCPRE;RCC->CFGR |= RCC_CFGR_ADCPRE_DIV6;
```

ADC 时钟越高，转换越快。

可采样质量不只取决于 ADC 时钟，还取决于采样时间、信号源阻抗、前端驱动能力和内部采样电容充电时间。

高阻传感器接入 ADC 时，采样时间太短，采样电容根本充不满。

结果看起来像时钟不稳，其实是模拟前端带不动。

嵌入式就这样。模拟和数字天天互相甩锅，工程师站中间挨打。

### 6.4 外设时钟门控与 RCC 总线位宽

STM32 不会默认打开所有外设时钟。

原因很现实。

省电。

减少无意义的总线翻转。

避免未使用模块工作。

F1 上常见时钟使能寄存器包括 `AHBENR`、`APB1ENR` 和 `APB2ENR`。

例如打开 GPIOA。

```
RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;
```

打开 USART2。

```
RCC->APB1ENR |= RCC_APB1ENR_USART2EN;
```

打开 DMA1。

```
RCC->AHBENR |= RCC_AHBENR_DMA1EN;
```

某些系列在时钟使能后，需要等待若干总线周期再访问外设。

最稳妥的写法是做一次读回。

```
RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;(void)RCC->APB2ENR;
```

读回可以确保写操作已经到达外设桥。

HAL 和 LL 宏内部在某些系列中已经处理了类似细节，但写纯寄存器代码时最好有这个意识。

#### 6.5.1 低功耗 8MHz 全系统配置（HSI 直连）

```

```

这套配置里，SYSCLK 使用 HSE 加 PLL，RTC 使用 LSE。

系统主频怎么变，不影响 RTC 的基础计时源。

设备进入低功耗模式以后，主时钟可以停，LSE 和 RTC 仍能继续工作。

### 6.6 经典踩坑——未开启外设时钟导致寄存器操作无响应

这是每个嵌入式新人都会踩的坑。

GPIO 配置写得特别认真。

模式、上下拉、输出速度全对。

结果引脚一动不动。

原因只是没开 GPIO 时钟。

```
GPIOA->CRL &= ~(0xFU << 0);GPIOA->CRL |=  (0x2U << 0);
```

这段代码在 GPIOA 时钟关闭时，可能完全不起作用。

正确顺序应该是

```
RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;(void)RCC->APB2ENR;GPIOA->CRL &= ~(0xFU << 0);GPIOA->CRL |=  (0x2U << 0);
```

有些外设在时钟关闭时读取寄存器，会返回零或固定值。

有些写入会被忽略。

某些架构和访问场景下，还可能触发总线错误。

更常见的是程序卡在等待状态位。

```
while ((USART1->SR & USART_SR_TXE) == 0U){}
```

若 USART1 根本没有时钟，状态机不运行，`TXE` 也可能不会按预期变化。

程序就死等。

看起来像串口坏了，其实串口连上班卡都没打。

### 7.2 三大配置策略——高性能、低功耗与平衡模式

高性能模式会尽量拉高 SYSCLK 和关键总线频率。

适合控制算法、高速通信、图像处理、大量浮点运算和短时间高负载任务。

代价是功耗上升、EMI 增强、供电要求提高，Flash 延迟和散热也更敏感。

低功耗模式会使用 HSI、MSI 或低频分频，关闭不需要的 PLL 和外设时钟。

适合电池供电、长期待机和间歇唤醒设备。

代价是任务执行时间变长，通信带宽下降，部分高速外设无法使用。

平衡模式是我在实际项目里用得最多的。

系统不追求满频常驻，而是按任务动态调整。

空闲时低频。

处理数据时升频。

通信结束后关外设。

任务完成后进入 Sleep 或 Stop。

性能和功耗不是二选一，很多时候可以靠时钟动态管理获得不错的平衡。

当然，动态切换也会增加软件复杂度。

想省下硬件电流，就得多付一点软件脑细胞。能量守恒嘛，痛苦也守恒。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-062.jpg]]

### 7.3 低功耗场景时钟裁剪

Sleep 模式通常停止 CPU 内核执行，但大部分外设时钟仍可继续运行。

定时器、串口、DMA 可以继续工作，并通过中断唤醒 CPU。

Stop 模式会关闭更多高速时钟和 PLL，保留部分低速域和 SRAM 内容。

唤醒后，系统经常先回到 HSI 或 MSI，而不是自动恢复到原来的高性能配置。

这意味着唤醒代码里可能需要重新启动 HSE、等待 PLL 锁定，再切回目标时钟。

Standby 模式更激进。

大部分上下文会丢失，唤醒行为接近一次复位。备份域、RTC 和少量寄存器可以继续保留。

做低功耗时，不要只调用一个 `HAL_PWR_EnterSTOPMode()` 就觉得完成了。

真正要检查的是这些东西：

哪些外设还在运行。

哪些 GPIO 存在漏电。

调试接口是否仍保持。

唤醒后 SYSCLK 来自哪里。

SysTick 是否需要恢复。

UART、SPI、I2C 的时钟参数是否需要重配。

PLL 和 HSE 是否重新启动。

低功耗最容易出现的假象是 MCU 睡了，外围却没睡。

CPU 电流只剩几十微安，板子整体还有十几毫安。

查了半天，发现某颗传感器一直开着，或者 GPIO 把外部电路顶在半导通状态。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-063.jpg]]

### 7.5 量产稳定性配置要点

实验室能跑，不等于量产能跑。

样机只有三块板，晶体还是手工挑的。

量产可能是一万块，晶体 ESR 有离散，电容有误差，焊接有偏差，PCB 材料也会变化。

温度也是一个大坑。

室温二十五度正常，不代表零下二十度还能快速起振。

供电条件也要留余量。

芯片最高频率往往与电压范围、电源模式有关。电源刚上升时若电压还没稳定，软件就急着拉高主频，系统可能表现得特别玄学。

EMC 环境同样会影响时钟。

高速边沿会产生辐射。

外部强干扰也可能耦合进晶振或复位网络。

量产设计里，我一般会做这些事。

晶体和负载电容不贴极限选型。

PLL 参数落在推荐范围中部，而不是边界上蹦迪。

HSE 和 PLL 等待流程带超时。

HSE 失败后允许切 HSI 降级启动。

开启 CSS，并记录失效事件。

高低温测试覆盖冷启动，而不是只测运行状态。

电压跌落测试观察 PLL、Flash 和复位行为。

用示波器测 MCO，不只相信软件变量。

给关键通信留频偏余量。

时钟走线和开关电源区域保持距离。

量产稳定性很多时候不是靠一个“神参数”，而是靠每个环节都不贪那最后一点极限。

### 7.6 时钟类故障完整排查流程

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-065.jpg]]

#### 7.6.1 晶振不起振

先读 `HSERDY` 或 `LSERDY`。

如果就绪位一直不置位，检查软件模式。

晶体模式和旁路模式是否搞反。

驱动能力档位是否合适。

启动超时是否太短。

软件确认后再看硬件。

晶体型号、频率、ESR、负载电容、焊接和走线。

HSE 失败时，可以临时切到 HSI，让系统继续运行，再通过串口输出故障码。

这招在量产测试中特别有用。

板子至少能说话，不至于直接变砖。

#### 7.6.2 PLL 频繁失锁

先重新计算所有中间频率。

别只算输出。

确认 PLL 输入范围、VCO 输入范围、VCO 输出范围和最终分频输出。

再检查参考时钟。

HSE 本身是否稳定。

电源噪声是否过大。

旁路时钟占空比和幅度是否合规。

如果芯片只在高温或高负载时失锁，电源完整性很可疑。

CPU、DMA 和外设同时工作时，瞬态电流增大，电压纹波可能把时钟系统一起带崩。

#### 7.6.3 串口乱码与 ADC 采样波动

串口先算实际波特率误差。

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-066.jpg]]

把发送端和接收端误差叠加考虑。

再确认 `SystemCoreClock`、PCLK 和 BRR 是否匹配。

别光看代码配置，最好直接测 TX 位宽。

115200 波特率下，单个位宽约为

![[assets/embedded-interview/嵌入式 STM32 时钟体系全解：从硬件底层到量产实战/img-067.jpg]]

示波器一量，很快就知道实际波特率偏到哪去了。

ADC 波动则要同时检查 ADC 时钟和模拟前端。

ADC 时钟是否超限。

采样周期是否过短。

信号源阻抗是否太高。

VDDA 和 VREF 是否干净。

数字时钟是否通过电源或地耦合到模拟域。

很多人一看到 ADC 数据抖，就疯狂加平均滤波。

滤波当然有用，但别让滤波替硬件背锅。

#### 7.6.4 程序超频死机

主频升高后立刻崩溃，优先检查 Flash 延迟。

然后检查供电电压和电压档位。

再检查 AHB、APB、ADC、USB 等分支是否超频。

某些外设不会因为总线超频马上报错，而是以一种很阴间的方式偶发异常。

Debug 可运行、脱机不运行，也可能与时钟启动时序有关。

调试器连接会改变复位和启动节奏，甚至影响低功耗行为。

别把“连着调试器能跑”当成稳定性证明。

那只是芯片当着老师的面比较乖。

## 八、拓展实战

### 8.1 寄存器版纯底层时钟初始化

下面给一份更精简的 F103 纯寄存器 72MHz 初始化。

它不依赖 HAL，但仍建议在正式项目中补上超时和错误回调。

```
#include "stm32f10x.h"void RCC_Config72MHz_Register(void){    RCC->CR |= RCC_CR_HSION;    while ((RCC->CR & RCC_CR_HSIRDY) == 0U)    {    }    RCC->CFGR &= ~RCC_CFGR_SW;    RCC->CFGR |= RCC_CFGR_SW_HSI;    while ((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_HSI)    {    }    RCC->CR &= ~RCC_CR_PLLON;    while ((RCC->CR & RCC_CR_PLLRDY) != 0U)    {    }    FLASH->ACR = FLASH_ACR_PRFTBE |                 FLASH_ACR_LATENCY_2;    RCC->CFGR &=        ~(RCC_CFGR_HPRE   |          RCC_CFGR_PPRE1  |          RCC_CFGR_PPRE2  |          RCC_CFGR_ADCPRE |          RCC_CFGR_PLLSRC |          RCC_CFGR_PLLXTPRE |          RCC_CFGR_PLLMULL);    RCC->CFGR |=        RCC_CFGR_HPRE_DIV1   |        RCC_CFGR_PPRE1_DIV2  |        RCC_CFGR_PPRE2_DIV1  |        RCC_CFGR_ADCPRE_DIV6;    RCC->CR |= RCC_CR_HSEON;    while ((RCC->CR & RCC_CR_HSERDY) == 0U)    {    }    RCC->CFGR |= RCC_CFGR_PLLSRC |                 RCC_CFGR_PLLMULL9;    RCC->CR |= RCC_CR_PLLON;    while ((RCC->CR & RCC_CR_PLLRDY) == 0U)    {    }    RCC->CFGR &= ~RCC_CFGR_SW;    RCC->CFGR |= RCC_CFGR_SW_PLL;    while ((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_PLL)    {    }    SystemCoreClockUpdate();    SysTick_Config(SystemCoreClock / 1000U);}
```

看寄存器代码有个好处。

你会真正看见时钟初始化的顺序。

先保证安全时钟存在。

再退出旧 PLL。

再设置 Flash 和分频。

再启动 HSE。

再配置 PLL。

再等待锁定。

再切换系统时钟。

HAL 把这些细节包起来了，但硬件顺序并没有消失。

### 8.2 HAL 库与 LL 库时钟配置对比

HAL 的优点是可读性强、跨项目迁移方便、错误返回机制相对完整。

缺点是代码体积较大，调用层级深，想追到底层时要翻不少文件。

LL 更接近寄存器。

代码轻，执行路径短，寄存器意图清晰。

缺点是使用者要自己承担更多顺序和异常处理责任。

用 LL 配置 F103 时钟，大致会是这种风格。

```
#include "stm32f1xx_ll_rcc.h"#include "stm32f1xx_ll_flash.h"#include "stm32f1xx_ll_system.h"void SystemClock_Config_LL_72MHz(void){    LL_FLASH_SetLatency(LL_FLASH_LATENCY_2);    LL_RCC_HSE_Enable();    while (LL_RCC_HSE_IsReady() != 1)    {    }    LL_RCC_PLL_ConfigDomain_SYS(        LL_RCC_PLLSOURCE_HSE_DIV_1,        LL_RCC_PLL_MUL_9);    LL_RCC_PLL_Enable();    while (LL_RCC_PLL_IsReady() != 1)    {    }    LL_RCC_SetAHBPrescaler(LL_RCC_SYSCLK_DIV_1);    LL_RCC_SetAPB1Prescaler(LL_RCC_APB1_DIV_2);    LL_RCC_SetAPB2Prescaler(LL_RCC_APB2_DIV_1);    LL_RCC_SetSysClkSource(LL_RCC_SYS_CLKSOURCE_PLL);    while (LL_RCC_GetSysClkSource() !=           LL_RCC_SYS_CLKSOURCE_STATUS_PLL)    {    }    LL_SetSystemCoreClock(72000000U);    SysTick_Config(72000000U / 1000U);}
```

我的习惯是这样。

业务项目优先 HAL。

性能敏感、启动时间敏感、Bootloader 或基础驱动层会考虑 LL 和寄存器。

不是因为寄存器版更“高级”。

能稳定交付才高级。

写了两百行神仙位操作，三个月后自己都看不懂，那不叫底层，那叫给未来的自己埋雷。

### 8.3 调试观测时钟频率方法

软件认为自己跑在 72MHz，不代表硬件真的跑在 72MHz。

最直接的验证方法是把时钟输出到 MCO 引脚。

F103 可以通过 MCO 输出 SYSCLK、HSI、HSE 或 PLL 分频时钟。

```
RCC->APB2ENR |= RCC_APB2ENR_IOPAEN;GPIOA->CRH &= ~(GPIO_CRH_MODE8 |                GPIO_CRH_CNF8);GPIOA->CRH |= GPIO_CRH_MODE8_1 |              GPIO_CRH_MODE8_0 |              GPIO_CRH_CNF8_1;RCC->CFGR &= ~RCC_CFGR_MCO;RCC->CFGR |= RCC_CFGR_MCO_SYSCLK;
```

然后用示波器或频率计测 PA8。

注意输出频率过高时，GPIO 速度、探头带宽、走线和负载都会影响波形。

你可能看到的不是漂亮方波，而是一坨边沿发圆的东西。

频率计数通常仍然能用。

除了 MCO，还可以通过定时器输出固定频率 PWM，再反推时钟。

也可以在调试器里读取 RCC 寄存器。

重点看这些状态。

HSE 是否就绪。

PLL 是否锁定。

SYSCLK 当前来源。

AHB 和 APB 分频值。

外设时钟选择器状态。

`SystemCoreClock` 只是一个软件变量。

寄存器和示波器才是更接近真相的证据链。

### 8.4 RTC 低速时钟独立配置实操

RTC 可以使用 LSE，也可以使用 LSI。

LSE 精度高，适合长期计时。

LSI 无需外部晶体，适合成本敏感或对时间精度要求不高的场景。

切换 RTC 时钟源通常涉及备份域。

备份域有个很重要的特点。

RTC 时钟源选择一旦建立，普通 RCC 复位不一定会清除。想重新选择时钟源，可能需要复位备份域。

而复位备份域会清除 RTC 配置和备份寄存器内容。

这事不能随便干。

```
__HAL_RCC_PWR_CLK_ENABLE();HAL_PWR_EnableBkUpAccess();if (NeedResetBackupDomain()){    __HAL_RCC_BACKUPRESET_FORCE();    __HAL_RCC_BACKUPRESET_RELEASE();}
```

设备使用后备电池时，主电源掉电，VBAT 可以继续给备份域和 LSE 供电。

RTC 继续走。

主电源恢复后，软件应该先判断备份域是否已经初始化，而不是每次启动都重新设置时间。

常见做法是在备份寄存器写入魔数。

```
#define RTC_INIT_MAGIC 0x5AA5Uif (HAL_RTCEx_BKUPRead(&hrtc, RTC_BKP_DR1) != RTC_INIT_MAGIC){    RTC_FirstInitialize();    HAL_RTCEx_BKUPWrite(&hrtc,                        RTC_BKP_DR1,                        RTC_INIT_MAGIC);}else{    RTC_RestoreRuntimeState();}
```

否则设备每次重启都把 RTC 重置到默认时间。

后备电池焊得再漂亮也白搭。

### 8.5 运行中动态切换时钟源

动态切换时钟不是简单改一个 RCC 位。

因为 CPU 频率变化会影响一大票东西。

SysTick。

RTOS Tick。

串口波特率。

SPI 速率。

I2C 时序。

定时器周期。

ADC 时钟。

Flash 等待周期。

正在运行的 DMA 和通信外设也可能受到影响。

所以切换时需要临界区保护。

比较稳妥的思路是先暂停对时钟敏感的业务，进入临界区，完成切换，更新软件频率变量和外设参数，再恢复业务。

下面是一段从 72MHz 降到 8MHz 的示意代码。

```
void Clock_Switch72MHzTo8MHz(void){    uint32_t primask = __get_PRIMASK();    __disable_irq();    Communication_Suspend();    HAL_SuspendTick();    RCC->CR |= RCC_CR_HSION;    while ((RCC->CR & RCC_CR_HSIRDY) == 0U)    {    }    RCC->CFGR &= ~RCC_CFGR_SW;    RCC->CFGR |= RCC_CFGR_SW_HSI;    while ((RCC->CFGR & RCC_CFGR_SWS) !=           RCC_CFGR_SWS_HSI)    {    }    RCC->CR &= ~RCC_CR_PLLON;    while ((RCC->CR & RCC_CR_PLLRDY) != 0U)    {    }    RCC->CR &= ~RCC_CR_HSEON;    RCC->CFGR &= ~(RCC_CFGR_HPRE |                   RCC_CFGR_PPRE1 |                   RCC_CFGR_PPRE2);    RCC->CFGR |= RCC_CFGR_HPRE_DIV1 |                 RCC_CFGR_PPRE1_DIV1 |                 RCC_CFGR_PPRE2_DIV1;    FLASH->ACR &= ~FLASH_ACR_LATENCY;    FLASH->ACR |= FLASH_ACR_LATENCY_0;    SystemCoreClockUpdate();    HAL_SYSTICK_Config(SystemCoreClock / 1000U);    HAL_ResumeTick();    PeripheralClock_Reconfigure();    Communication_Resume();    if (primask == 0U)    {        __enable_irq();    }}
```

从低频升到高频时，顺序要特别注意。

先提高 Flash 等待周期。

再设置安全的总线分频。

再启动高速时钟和 PLL。

确认锁定。

最后切换 SYSCLK。

```
void Clock_Switch8MHzTo72MHz(void){    uint32_t primask = __get_PRIMASK();    __disable_irq();    Communication_Suspend();    HAL_SuspendTick();    FLASH->ACR = FLASH_ACR_PRFTBE |                 FLASH_ACR_LATENCY_2;    RCC->CFGR &= ~(RCC_CFGR_HPRE |                   RCC_CFGR_PPRE1 |                   RCC_CFGR_PPRE2);    RCC->CFGR |= RCC_CFGR_HPRE_DIV1 |                 RCC_CFGR_PPRE1_DIV2 |                 RCC_CFGR_PPRE2_DIV1;    RCC->CR |= RCC_CR_HSEON;    if (WaitMask(&RCC->CR,                 RCC_CR_HSERDY,                 RCC_CR_HSERDY,                 1000000U) != 0)    {        goto switch_failed;    }    RCC->CFGR &= ~(RCC_CFGR_PLLSRC |                   RCC_CFGR_PLLXTPRE |                   RCC_CFGR_PLLMULL);    RCC->CFGR |= RCC_CFGR_PLLSRC |                 RCC_CFGR_PLLMULL9;    RCC->CR |= RCC_CR_PLLON;    if (WaitMask(&RCC->CR,                 RCC_CR_PLLRDY,                 RCC_CR_PLLRDY,                 1000000U) != 0)    {        goto switch_failed;    }    RCC->CFGR &= ~RCC_CFGR_SW;    RCC->CFGR |= RCC_CFGR_SW_PLL;    if (WaitMask(&RCC->CFGR,                 RCC_CFGR_SWS,                 RCC_CFGR_SWS_PLL,                 100000U) != 0)    {        goto switch_failed;    }    SystemCoreClockUpdate();    HAL_SYSTICK_Config(SystemCoreClock / 1000U);    HAL_ResumeTick();    PeripheralClock_Reconfigure();    Communication_Resume();    if (primask == 0U)    {        __enable_irq();    }    return;switch_failed:    ClockFallbackToHSI();    SystemCoreClockUpdate();    HAL_SYSTICK_Config(SystemCoreClock / 1000U);    HAL_ResumeTick();    PeripheralClock_Reconfigure();    Application_EnterDegradedMode();    if (primask == 0U)    {        __enable_irq();    }}
```

正在发送串口数据时，不建议直接切换 PCLK。

正在进行 SPI 事务时，也别突然改 SPI 内核时钟。

RTOS 项目还要考虑调度器 Tick 和时间基准连续性。

有些系统会用独立低速定时器维护单调时间，再允许主时钟动态变化。这样上层超时计算不会因为主频切换突然抽风。

说到底，Runtime 动态切时钟不是不能做。

它只是需要你把时钟当成一种系统资源，而不是一个启动时设置完就永远不管的常量。
