### 第71题：UART 的基本通信原理是什么？

> **UART 是异步串行通信，靠约定好的波特率逐位收发，帧格式为：起始位 + 数据位 + 校验位 + 停止位。**

#### ① UART 物理层

| 项目 | 说明 |
|------|------|
| 信号线 | TX（发送）+ RX（接收），交叉连接 |
| 通信方式 | 异步（无时钟线）、全双工、点对点 |
| 电平 | TTL（0/3.3V）或 RS232（±12V） |
| 波特率 | 常见 9600 / 115200，双方必须一致 |

#### ② 一帧数据格式

```text
空闲(高)  起始位  D0 D1 D2 D3 D4 D5 D6 D7  校验位  停止位  空闲(高)
  ----┐  ┌──────────────────────────────┐  ┌──┐  ┌──┐  ┌----
      └──┘                              └──┘  └──┘  └──
      起始(低)    8bit 数据（LSB先发）        停止(高)
```

| 字段 | 作用 |
|------|------|
| 起始位 | 1bit 低电平，通知接收方"数据来了" |
| 数据位 | 5~9bit，最常见 8bit |
| 校验位 | 可选，奇校验/偶校验，用于简单检错 |
| 停止位 | 1/1.5/2bit 高电平，标志一帧结束 |

#### ③ 关键点速记

- **异步 = 无时钟线**，靠双方约定相同波特率
- UART 是**字节流**协议，不自带帧边界，应用层要自己设计协议帧（帧头+长度+校验）
- 常见用途：调试串口、蓝牙模块（HC-05）、GPS 模块、上位机通信

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **波特率和比特率有什么区别？** | UART 中二者数值相同，因为 1 个符号 = 1 个 bit |
| **UART 怎么判断一帧数据接收完了？** | 接收到停止位（高电平）表示一帧结束；如果需要判断应用层一帧，用 IDLE 空闲中断 |
| **UART 通信距离多远？** | TTL 电平通常 <1m，RS232 <15m，RS485 <1200m |

### 第72题：UART 和 RS485 有什么区别？

> **UART 是协议层概念（怎么收发数据），RS485 是物理层标准（怎么传电信号），项目中 MCU 串口通过 RS485 收发器连到总线。**

#### ① 本质区别

| 对比项 | UART | RS485 |
|--------|------|-------|
| 层次 | 协议/接口层 | 物理层电气标准 |
| 电平 | TTL（0/3.3V）单端 | 差分信号（A-B 两线） |
| 通信方式 | 全双工（TX+RX） | 半双工（共用 A/B 线） |
| 距离 | <1m（TTL） | <1200m |
| 节点数 | 点对点（1对1） | 多节点总线（1主多从） |
| 抗干扰 | 弱 | 强（差分抑制共模干扰） |

#### ② 项目中的典型用法

```text
MCU                    RS485收发器              总线（A/B）
  │                    (如 MAX485)               │
  ├── TX -----------> DI -----------> A --- 从机1
  ├── RX <----------- RO               B --- 从机2
  ├── DE/RE (方向控制)                      └── 从机3
  │
  软件发数据前拉高 DE，发完后拉低 DE 切回接收
```

#### ③ 工程注意事项

| 要点 | 说明 |
|------|------|
| **方向控制** | RS485 半双工，发完数据要手动切回接收模式 |
| **终端电阻** | 总线两端各接 120Ω 匹配电阻 |
| **地址机制** | RS485 本身无地址，靠协议层（如 Modbus）区分设备 |
| **冲突避免** | 需要主从轮询，不能两个设备同时发 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **RS485 收发器怎么切换方向？** | DE/RE 引脚控制：DE=高为发送，RE=低为接收，通常连同一个 GPIO |
| **为什么不直接用 UART？** | TTL 电平抗干扰差、距离短、只支持点对点，工业场景需要 RS485 |
| **RS485 和 RS232 有什么区别？** | RS232 是单端信号、点对点、±12V 电平；RS485 是差分信号、多节点、抗干扰更强 |

### 第73题：Modbus RTU 的基本特点是什么？

> **Modbus RTU 是 RS485 总线上最常见的主从协议，帧简单（地址+功能码+数据+CRC），靠帧间隔区分帧边界。**

#### ① Modbus RTU 帧格式

| 字段 | 字节数 | 说明 |
|------|--------|------|
| 从机地址 | 1 | 1~247，0 为广播 |
| 功能码 | 1 | 03=读保持寄存器，06=写单个寄存器，10=写多个寄存器 |
| 数据 | N | 寄存器地址、数量、数值等 |
| CRC16 | 2 | 低字节在前，Modbus 专用多项式 |

#### ② 帧边界识别

```text
|<----- 帧间隔 >= 3.5 字符时间 ----->|
                                    |<- 地址 ->|<- 功能码 ->|<- 数据 ->|<- CRC ->|
|<----- 帧间隔 >= 3.5 字符时间 ----->|
                                    <- 下一帧开始 ->

关键：Modbus RTU 没有帧头帧尾，靠"帧间隔"（3.5 字符时间的总线空闲）来区分帧边界
```

#### ③ 常用功能码速查

| 功能码 | 含义 | 数据域 |
|--------|------|--------|
| 0x03 | 读保持寄存器 | 起始地址 + 寄存器数量 |
| 0x04 | 读输入寄存器 | 起始地址 + 寄存器数量 |
| 0x06 | 写单个寄存器 | 寄存器地址 + 写入值 |
| 0x10 | 写多个寄存器 | 起始地址 + 数量 + 字节数 + 数据 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **Modbus RTU 和 Modbus ASCII 有什么区别？** | RTU 用二进制传输、效率高；ASCII 用 ASCII 字符、可读性好但效率低 |
| **3.5 字符时间怎么算？** | 以 9600bps 为例：1 字符 = 11bit，3.5 × 11 / 9600 ≈ 4ms |
| **CRC 怎么校验？** | 发送端算 CRC 附在帧尾，接收端对整帧（含 CRC）重算，结果应为 0 |

### 第74题：自定义通信协议帧一般怎么设计？

> **可靠协议帧 = 帧头 + 长度 + 命令字 + 数据区 + 校验 + 帧尾，解析用状态机逐字节接收。**

#### ① 协议帧结构

| 字段 | 字节数 | 说明 |
|------|--------|------|
| 帧头 | 2 | 固定值，如 0xAA 0x55，用于快速同步 |
| 版本/类型 | 1 | 协议版本或帧类型 |
| 命令字 | 1 | 区分业务类型（读/写/配置/上报等） |
| 序号 | 1~2 | 防重复、匹配应答 |
| 长度 | 1~2 | 数据区字节数 |
| 数据区 | N | 实际业务数据 |
| 校验 | 2 | CRC16 或累加和 |
| 帧尾（可选） | 1~2 | 固定值，辅助帧完整性判断 |

#### ② 状态机解析流程

```text
         ---- 收到0xAA ----
         |                  |
      WAIT_HEAD             | (丢弃，继续等)
         |                  |
    收到0x55                |
         |                  |
      READ_LEN -------------+
         |
    读取长度字段
         |
      READ_LEN  -- 收满 N 字节 --> CHECK_CRC
         |                              |
    超时未收满                         CRC 正确
         |                              |
         +------------------->  交给业务层处理
                     (丢弃异常帧，重新同步)
```

#### ③ 防粘包和转义

| 问题 | 解决方案 |
|------|----------|
| **粘包** | 靠长度字段定界，不要假设一包 = 一次接收 |
| **数据区含帧头字节** | 方案一：以长度字段为主，不依赖帧尾；方案二：转义机制（类似 SLIP） |
| **丢包/错包** | CRC 校验 + 超时丢弃 + 序号匹配 |
| **重复包** | 序号去重，相同序号的包只处理一次 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么用状态机而不是直接 memcpy？** | 串口是字节流，不能假设一次中断就收完整帧，状态机逐字节解析更可靠 |
| **帧头选什么值好？** | 避免和常见数据冲突，选不常用的组合如 0xAA 0x55 |
| **CRC 和累加和哪个好？** | CRC 检错能力更强，能发现位翻转和突发错误；累加和实现简单但漏检率高 |

### 第75题：CRC 校验和普通累加和有什么区别？

> **CRC 基于多项式除法，检错能力远强于累加和，能发现位翻转和突发错误，是工业协议的标配。**

#### ① 累加和 vs CRC 对比

| 对比项 | 累加和 | CRC |
|--------|--------|-----|
| 算法 | 字节累加取低位 | 多项式除法取余数 |
| 检错能力 | 弱，容易漏检 | 强，能检测位翻转和突发错误 |
| 计算速度 | 极快（加法） | 较快（可查表优化） |
| 实现难度 | 极简单 | 中等（查表法 256 字节） |
| 典型应用 | 简单内部校验 | Modbus、XMODEM、CAN、以太网 |

#### ② CRC16 计算流程（简化）

```text
1. 初始化 CRC 寄存器 = 0xFFFF（初始值）
2. 对每个数据字节：
   CRC = CRC XOR 当前字节
   对 bit0~bit7 循环：
     if CRC & 1:  CRC = (CRC >> 1) XOR 0xA001（多项式）
     else:        CRC = CRC >> 1
3. 最终 CRC 即为校验值（低字节在前发送）
```

#### ③ CRC 参数说明

| 参数 | 含义 | Modbus CRC16 值 |
|------|------|-----------------|
| 多项式 | 除法用的固定除数 | 0xA001 |
| 初始值 | CRC 寄存器起始值 | 0xFFFF |
| 输入反转 | 每字节是否 bit 反转 | 是 |
| 输出反转 | 最终结果是否 bit 反转 | 是 |
| 最终异或 | 结果再 XOR | 0x0000 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **CRC 能纠错吗？** | 不能，CRC 只能检错，不能定位和纠正错误位 |
| **CRC8、CRC16、CRC32 怎么选？** | 数据短、要求低用 CRC8；串口协议常用 CRC16；以太网/文件校验用 CRC32 |
| **为什么 CRC 比累加和更可靠？** | 累加和只看总和，交换两个字节结果不变；CRC 基于多项式除法，对位顺序敏感，检错率更高 |

### 第76题：I2C 的基本通信过程是什么？

> **I2C 是两线制同步串行总线，通信靠主机发时钟 + 起始/停止信号，从机靠地址匹配 + ACK 应答。**

#### ① I2C 物理层

| 项目 | 说明 |
|------|------|
| 信号线 | SCL（时钟）+ SDA（数据），都由上拉电阻拉高 |
| 主从关系 | 主机产生时钟，从机被动响应 |
| 电平 | 开漏输出，只能拉低，不能主动拉高 |
| 速率 | 标准模式 100kHz / 快速模式 400kHz / 高速 3.4MHz |

#### ② 一次完整传输流程

```text
主机                          从机
  |---- S(起始位) ------------->|
  |---- 7bit 地址 + R/W 位 ----->|
  |<--- ACK（地址匹配） ---------|
  |---- 8bit 数据 ------------->|
  |<--- ACK/NACK ---------------|
  |---- ...（继续发/收） ------->|
  |---- P(停止位) ------------->|
```

| 步骤 | 信号 | 含义 |
|------|------|------|
| 1 | S（Start） | SCL=1 时 SDA 从高→低 |
| 2 | 7bit 地址 + R/W | 寻址从机，R/W=0 写 / 1 读 |
| 3 | ACK | 第 9 个时钟，从机拉低 SDA 确认 |
| 4 | 数据传输 | 每 8bit 后跟 1bit ACK/NACK |
| 5 | P（Stop） | SCL=1 时 SDA 从低→高 |

#### ③ I2C vs SPI vs UART 速查

| 对比项 | I2C | SPI | UART |
|--------|-----|-----|------|
| 线数 | 2（SCL+SDA） | 4（SCK/MOSI/MISO/CS） | 2（TX+RX） |
| 通信方式 | 半双工、同步 | 全双工、同步 | 全双工、异步 |
| 多从机 | 地址寻址，天然支持 | 每个从机需要独立 CS | 点对点 |
| 速率 | 100k~3.4MHz | 可达几十 MHz | 通常 ≤1Mbps |
| 典型场景 | EEPROM、传感器、IMU | Flash、LCD、高速 ADC | 调试口、蓝牙模块 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **起始和停止信号怎么产生的？** | 起始：SCL=1 时 SDA 由高→低；停止：SCL=1 时 SDA 由低→高。都是主机产生 |
| **ACK 和 NACK 分别什么含义？** | ACK：第 9 个时钟接收方拉低 SDA，表示"收到，继续"；NACK：SDA 保持高，表示"不认/结束" |
| **I2C 为什么是半双工？** | 只有一根数据线 SDA，发送和接收不能同时进行 |

### 第77题：I2C 为什么需要上拉电阻？

> **I2C 用开漏输出只能拉低不能拉高，上拉电阻是总线恢复高电平的唯一手段，也是线与逻辑的基础。**

#### ① 开漏输出原理

```text
           VCC
            |
          [Rp]  <-- 上拉电阻
            |
SDA/SCL ----|
            |
        +---+---+
        | MOSFET |  <-- 开漏管
        +---+---+
            |
           GND

导通时 -> 总线拉低（低电平）
截止时 -> 总线通过 Rp 拉到 VCC（高电平）
```

#### ② 为什么必须用开漏？

| 原因 | 说明 |
|------|------|
| **线与逻辑** | 多设备共享总线，任一拉低则总线为低，避免推挽输出互相短路 |
| **支持仲裁** | 一个发高一个发低时，发低的优先，不会烧总线 |
| **电平兼容** | 不同电压设备可共存（3.3V/5V 通过上拉到不同电压） |

#### ③ 上拉电阻怎么选？

| 阻值 | 效果 |
|------|------|
| **太大（>10kΩ）** | 上升沿慢，高速通信出错 |
| **太小（<1kΩ）** | 拉低时电流大，功耗高 |
| **常用** | 标准模式 4.7kΩ，快速模式 2.2kΩ |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **不接上拉电阻会怎样？** | 总线无法恢复高电平，SDA/SCL 始终低电平，通信完全失败 |
| **能用 MCU 内部上拉代替吗？** | 内部上拉 40kΩ~100kΩ 阻值太大，只能用于极低速，不推荐 |
| **上拉电阻接哪？** | 接 I2C 逻辑电平对应的电源，3.3V 系统接 3.3V |

### 第78题：I2C 仲裁机制是什么？

> **多主机同时抢总线时，靠"边发边读、线与比较"实现无损仲裁，发高读低的一方自动退出。**

#### ① 仲裁过程

```text
时序线：  bit7  bit6  bit5  bit4  bit3  ...
主机A发：  1     0     1     1     0
主机B发：  1     0     1     0     1
SDA实际：  1     0     1     0     ...   <-- 线与结果

                  bit4: A发1(高)，B发0(低)
                  线与=0
                  A读到0≠自己发的1 -> A 失去仲裁，退出
                  B 继续通信
```

| 阶段 | 主机A | 主机B | 总线 |
|------|-------|-------|------|
| bit7 | 发1 | 发1 | 1，都继续 |
| bit4 | 发**1** | 发**0** | **0**（线与） |
| 结果 | 读到0≠1，**退出** | 读到0=0，**赢** | B独占 |

#### ② 关键特性

- **无损仲裁**：退出的主机数据不被破坏，等总线空闲后重试
- **依赖线与**：只有开漏结构才能实现
- **边发边读**：每个 bit 同时发送和采样 SDA

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **仲裁失败怎么办？** | 停止发送，等总线空闲（SDA+SCL 都为高）后重试 |
| **实际项目会用到吗？** | 单主系统很少用，但理解它有助于理解开漏输出和上拉电阻的设计原因 |
| **SPI 有仲裁吗？** | 没有，SPI 用 CS 片选区分从机，不存在多主冲突 |

### 第79题：I2C 时钟延展是什么？

> **从机来不及处理时把 SCL 拉低"卡住"时钟线，让主机等一等再继续，本质是慢从机控快主机。**

#### ① 工作机制

```text
正常：SCL: -|-|-|-|-   （主机自由产生时钟）

延展：SCL: -|-|-|--------|-|-|
                  从机拉低
                   |
              主机在此等待
```

| 步骤 | 说明 |
|------|------|
| 1 | 主机发完字节，等 ACK |
| 2 | 从机需要处理（ADC转换/读Flash），拉低 SCL |
| 3 | 主机检测 SCL 低，停止时钟，等待 |
| 4 | 从机处理完，释放 SCL |
| 5 | 主机继续后续传输 |

#### ② 典型场景

| 场景 | 说明 |
|------|------|
| ADC 转换 | 正在转换，数据没好 |
| EEPROM 写入 | 内部写周期 5~10ms |
| 缓冲区满 | FIFO 满了需要消化 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **主机不支持时钟延展会怎样？** | 不检测 SCL 电平直接继续，导致从机数据丢失或 NACK |
| **总线卡住怎么排查？** | 示波器看 SCL 是否被某设备一直拉低 |
| **SPI 有时钟延展吗？** | 没有，SPI 时钟完全由主机控制，从机无法暂停 |

### 第80题：I2C 总线上两个从设备地址冲突会发生什么？

> **两个从机都会 ACK，写操作双写错乱，读操作线与导致数据混乱，解决靠改地址脚或加多路复用器。**

#### ① 写操作冲突

```text
主机发地址 + 写位 -> 两个从机都 ACK
    |
两个从机同时接收同一份数据 -> 双方状态都乱了
```

#### ② 读操作冲突

```text
主机发地址 + 读位 -> 两个从机都 ACK -> 都开始发数据
    |
从机A输出 0xAA，从机B输出 0x55
    |
SDA 线与结果 ≠ 任何一个的真实数据 -> 主机读到的数据不可预测
```

#### ③ 解决方案

| 方案 | 适用场景 |
|------|----------|
| 改硬件地址脚 | 芯片有 ADDR 引脚（如 AT24C02 的 A0~A2） |
| 选不同地址版本 | 同系列芯片有多个地址版本 |
| I2C 多路复用器 | TCA9548A，相同设备挂不同通道 |
| 不同 I2C 控制器 | 分到 MCU 的不同 I2C 总线 |
| 片选/电源控制 | 同一时刻只使能一个设备 |

#### 面试常问追问

| 追问                    | 回答                              |
| --------------------- | ------------------------------- |
| **怎么检测地址冲突？**         | 初始化遍历 7bit 地址，同一地址收到多个 ACK 就有冲突 |
| **I2C 支持 10bit 地址吗？** | 支持，1024 个地址，能缓解冲突但实际用得不多        |
| **SPI 有地址冲突吗？**       | 不会，SPI 靠 CS 片选，每根 CS 对应一个设备     |

### 第81题：SPI 的基本通信原理是什么？

> **SPI 是四线制同步全双工总线，靠 CS 片选选设备、SCLK 驱动时序、MOSI/MISO 双向传数据，速度快协议简单。**

#### ① SPI 物理层

| 信号线   | 全称                  | 作用              |
| ----- | ------------------- | --------------- |
| SCLK  | Serial Clock        | 主机产生的时钟信号       |
| MOSI  | Master Out Slave In | 主机发、从机收         |
| MISO  | Master In Slave Out | 从机发、主机收         |
| CS/SS | Chip Select         | 片选，低电平有效，每个从机一根 |

#### ② 通信过程

```text
主机                    从机
  |--- CS 拉低（选中从机）--->|
  |--- SCLK 时钟启动 ------->|
  |--- MOSI 发送数据 ------->|
  |<-- MISO 同时返回数据 -----|
  |--- CS 拉高（释放从机）--->|
```

- **全双工**：发送和接收同时进行，主机发 8bit 的同时从机也在移出 8bit
- **只读不发也要产生时钟**：主机想读从机数据，必须发 dummy 字节（如 0xFF）驱动时钟

#### ③ SPI vs I2C vs UART 速查

| 对比项 | SPI | I2C | UART |
|--------|-----|-----|------|
| 线数 | 4 | 2 | 2 |
| 通信方式 | 全双工、同步 | 半双工、同步 | 全双工、异步 |
| 速率 | 可达几十 MHz | 100k~3.4MHz | 通常 ≤1Mbps |
| 多从机 | 每个需独立 CS | 地址寻址 | 点对点 |
| 典型场景 | Flash、LCD、高速 ADC | EEPROM、传感器 | 调试口、蓝牙 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **SPI 没有 ACK 怎么保证可靠？** | 靠应用层校验（CRC/状态寄存器）或重发 |
| **CS 片选时序要注意什么？** | 传输前拉低、传输后拉高；有些设备要求 CS 拉高才触发命令 |
| **SPI 为什么比 I2C 快？** | 全双工无地址/ACK 开销，推挽输出驱动强，时钟可达几十 MHz |

### 第82题：SPI 的 CPOL 和 CPHA 是什么？

> **CPOL 决定时钟空闲电平，CPHA 决定数据在哪边沿采样，两者组合成 4 种 SPI 模式，主从必须一致。**

#### ① CPOL 和 CPHA 定义

| 参数 | 值 | 含义 |
|------|------|------|
| CPOL | 0 | SCLK 空闲时为**低电平** |
| CPOL | 1 | SCLK 空闲时为**高电平** |
| CPHA | 0 | 在**第一个**边沿采样数据 |
| CPHA | 1 | 在**第二个**边沿采样数据 |

#### ② 四种 SPI 模式

| 模式 | CPOL | CPHA | 空闲电平 | 采样边沿 | 常见设备 |
|------|------|------|----------|----------|----------|
| Mode 0 | 0 | 0 | 低 | 上升沿 | 大多数 SPI Flash、传感器 |
| Mode 1 | 0 | 1 | 低 | 下降沿 | 部分 ADC |
| Mode 2 | 1 | 0 | 高 | 下降沿 | 较少使用 |
| Mode 3 | 1 | 1 | 高 | 上升沿 | 部分传感器、LCD |

#### ③ 时序图示例

```text
Mode 0 (CPOL=0, CPHA=0):
SCLK: ____┌──┐  ┌──┐  ┌──┐  ┌──┐____
           采样  采样  采样  采样
MOSI: ----< D7 >< D6 >< D5 >< D4 >----

Mode 3 (CPOL=1, CPHA=1):
SCLK: ────┐  ┌──┐  ┌──┐  ┌──┐  ┌────
             采样  采样  采样  采样
MOSI: ----< D7 >< D6 >< D5 >< D4 >----
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **主从 CPOL/CPHA 不一致会怎样？** | 数据错位或完全读错 |
| **怎么确定设备用哪种模式？** | 查芯片手册的 SPI 时序图 |
| **调试 SPI 数据异常先查什么？** | 先查 CPOL/CPHA 是否匹配，再查时钟频率和位序 |

### 第83题：SPI 和 I2C 有什么区别？

> **SPI 快、全双工、线多；I2C 慢、半双工、线少支持多设备寻址。选型看速度和引脚资源。**

#### ① 核心对比

| 对比项  | SPI                  | I2C           |
| ---- | -------------------- | ------------- |
| 线数   | 4（SCLK/MOSI/MISO/CS） | 2（SCL/SDA）    |
| 通信方式 | 全双工                  | 半双工           |
| 速率   | 可达几十 MHz             | 100k~3.4MHz   |
| 多从机  | 每个需独立 CS             | 地址寻址共用总线      |
| 寻址   | 无（靠 CS）              | 7bit/10bit 地址 |
| 应答   | 无 ACK                | 有 ACK/NACK    |
| 仲裁   | 无                    | 有（多主机）        |
| 时钟延展 | 无                    | 有             |

#### ② 选型建议

| 场景               | 推荐  | 原因           |
| ---------------- | --- | ------------ |
| 高速数据传输           | SPI | 速率高，全双工      |
| 引脚资源紧张           | I2C | 只需 2 根线      |
| 多设备挂总线           | I2C | 地址寻址，无需额外 CS |
| Flash/LCD/高速 ADC | SPI | 大数据量，时序要求高   |
| EEPROM/IMU/传感器   | I2C | 低速配置类，线少     |
| 实时性要求高           | SPI | 无协议开销，延迟低    |

#### ③ 典型接线对比

```text
SPI（3个从机需要 6 根线）:
  主机 --SCLK/MOSI/MISO--> 从机1/2/3
  主机 --CS1/CS2/CS3-----> 从机1/2/3

I2C（3个从机只需 2 根线）:
  主机 --SCL/SDA--> 从机1/2/3（靠地址区分）
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **I2C 和 SPI 能同时用吗？** | 能，独立外设，互不影响 |
| **SPI 能接很多从机吗？** | 能，但每个需独立 CS；可用译码器扩展 |
| **Flash 为什么用 SPI 不用 I2C？** | Flash 数据量大，SPI 速率高得多 |

### 第84题：CAN 总线有什么特点？

> **CAN 是多主、差分、面向消息的工业总线，靠报文 ID 区分内容和优先级，抗干扰强、可靠性高。**

#### ① CAN 核心特性

| 特性 | 说明 |
|------|------|
| 多主通信 | 任何节点都可以主动发送 |
| 差分信号 | CAN_H 和 CAN_L，抗干扰强 |
| 面向消息 | 按报文 ID 寻址，不是设备地址 |
| 非破坏性仲裁 | 高优先级报文不被打断 |
| 错误检测 | CRC + 位填充 + 帧检查 + ACK |
| 自动重发 | 仲裁失败或出错自动重发 |

#### ② CAN 数据帧结构

```text
| 帧头 | 仲裁段 | 控制段 | 数据段 | CRC段 | ACK段 | 帧尾 |
| SOF  |11bit ID + RTR | DLC | 0~8字节 | CRC15 | ACK | EOF |
```

#### ③ CAN vs RS485

| 对比项  | CAN          | RS485   |
| ---- | ------------ | ------- |
| 仲裁机制 | 有（非破坏性）      | 无（靠协议层） |
| 错误检测 | 硬件级（CRC+位填充） | 无，靠软件   |
| 通信方式 | 多主           | 主从      |
| 自动重发 | 有            | 无       |
| 抗干扰  | 差分 + 协议级     | 差分      |
| 典型场景 | 汽车、工业        | 工业仪表、楼宇 |

#### 面试常问追问

| 追问                         | 回答                                  |
| -------------------------- | ----------------------------------- |
| **CAN 总线最大节点数？**           | 理论上无限制，实际受总线负载和收发器驱动能力限制，通常 <110 个  |
| **CAN 报文 ID 越小优先级越高吗？？**   | 是的，ID 数值越小，二进制中越早出现显性位 0，仲裁越早胜出     |
| **CAN 2.0A 和 2.0B 有什么区别？** | 2.0A 标准帧 11bit ID；2.0B 扩展帧 29bit ID |

### 第85题：CAN 仲裁机制是怎么实现的？

> **CAN 用"显性覆盖隐性"的非破坏性位仲裁，发送同时监听总线，发隐性读到显性的一方自动退出。**

#### ① 显性与隐性

|电平|CAN 值|含义|
|---|---|---|
|显性（Dominant）|0|差分电压大，**可以覆盖隐性**|
|隐性（Recessive）|1|差分电压小，被显性覆盖|

关键：**总线上只要有一个节点发显性（0），总线就是显性**——这和 I2C 的"线与"逻辑类似。

#### ② 仲裁过程

```text
节点A 发送 ID: 0x100 = 0001 0000 0000
节点B 发送 ID: 0x200 = 0010 0000 0000
                  ↑
           bit8: A发0(显性)，B发0(显性) → 都继续
           bit7: A发0(显性)，B发1(隐性) → A赢
                  B读到总线是0≠自己发的1 → B退出仲裁

仲裁结果：A 继续发送，B 等 A 发完后重试
```

|bit 位|节点A|节点B|总线|结果|
|---|---|---|---|---|
|bit9|0（显性）|0（显性）|0|都继续|
|bit8|0（显性）|0（显性）|0|都继续|
|bit7|**0（显性）**|**1（隐性）**|**0**|**A 赢，B 退出**|

#### ③ 非破坏性仲裁的关键

|特性|说明|
|---|---|
|非破坏性|退出的节点不破坏总线上正在传输的数据|
|边发边听|每个 bit 都在监听总线电平|
|自动重发|退出的节点等总线空闲后自动重试|
|ID 越小优先级越高|ID 数值小 → 更早出现显性位 0 → 仲裁胜出|

#### ④ CAN 仲裁 vs I2C 仲裁

|对比项|CAN|I2C|
|---|---|---|
|原理|显性覆盖隐性|线与（开漏）|
|仲裁字段|报文 ID（11/29bit）|地址+数据|
|退出后|自动重发|等总线空闲重试|
|破坏性|非破坏性|非破坏性|
|多主支持|天然多主|支持但少用|

#### 面试常问追问

| 追问                        | 回答                                    |
| ------------------------- | ------------------------------------- |
| **CAN 仲裁失败会丢数据吗？**        | 不会，低优先级节点只是延后发送，数据不会丢失                |
| **为什么 CAN 适合汽车？**         | 多主通信、抗干扰强、错误检测完善、自动重发，适合恶劣电磁环境        |
| **CAN FD 和经典 CAN 有什么区别？** | CAN FD 数据段可达 64 字节，速率可达 8Mbps，仲裁段速率不变 |

### 第86题：CAN 如何进行错误检测和处理？

> **CAN 内置 5 种错误检测机制 + 3 级错误状态，轻错误自动恢复，重错误主动脱离总线保护系统。**

#### ① 五种错误类型

|错误类型|检测时机|说明|
|---|---|---|
|位错误|发送时|发送节点监听总线，发现实际电平≠预期|
|填充错误|收发时|位填充区间出现 6 个连续相同电平|
|CRC 错误|接收时|接收方计算 CRC 与帧中 CRC 不一致|
|格式错误|接收时|固定格式段（如 EOF）出现非法位|
|ACK 错误|发送时|发送方在 ACK 段没检测到显性位|

#### ② 错误帧

```text
正常报文: [SOF] [ID] [控制] [数据] [CRC] [ACK] [EOF]
                                                |
                                          检测到错误
                                                |
错误帧:   6个显性位 + 8个隐性位（错误界定符）
          通知总线所有节点：当前报文无效
```

#### ③ 三级错误状态

```text
错误计数 < 96:  Error Active（正常，可发错误帧）
错误计数 96~127: Error Passive（被动，不能发错误帧）
错误计数 > 127:  BusOff（脱离总线，停止通信）
```

|状态|发送错误计数|接收错误计数|行为|
|---|---|---|---|
|Error Active|<96|<96|正常通信，可发主动错误帧|
|Error Passive|96~127|96~127|可通信但只发被动错误帧|
|BusOff|>127|-|脱离总线，不参与通信|

#### ④ BusOff 恢复

- 自动恢复：等待 128 组 11 个隐性位后自动回到 Error Passive
- 软件恢复：MCU 检测到 BusOff 后重新初始化 CAN 控制器
- 工程建议：BusOff 往往是硬件问题（波特率不匹配、终端电阻、总线电平），不要只靠软件恢复

#### 面试常问追问

| 追问                          | 回答                                        |
| --------------------------- | ----------------------------------------- |
| **CAN 总线一直报错误帧怎么办？**        | 先用示波器看 CAN_H/CAN_L 电平，检查波特率、终端电阻、共地       |
| **错误计数器怎么清零？**              | 每成功收发一帧，相应计数器减 1；发送成功减 1，接收成功减 1          |
| **CAN 和 CAN FD 的错误处理有区别吗？** | 基本机制相同，但 CAN FD 的 CRC 更长（17/21bit），检错能力更强 |

### 第87题：TCP 和 UDP 有什么区别？

> **TCP 可靠有序但开销大，UDP 快但不保证可靠。选型看业务对可靠性和延迟的取舍。**

#### ① 核心对比

|对比项|TCP|UDP|
|---|---|---|
|连接方式|面向连接（三次握手）|无连接|
|可靠性|可靠（确认+重传+排序）|不可靠（尽力而为）|
|数据形式|字节流|数据报|
|顺序保证|有|无|
|流量控制|有（滑动窗口）|无|
|拥塞控制|有|无|
|首部开销|20 字节|8 字节|
|传输效率|较低|高|

#### ② 典型应用场景

|场景|推荐|原因|
|---|---|---|
|HTTP/HTTPS|TCP|必须可靠|
|文件传输|TCP|数据完整性|
|远程登录 SSH|TCP|可靠+有序|
|实时音视频|UDP|低延迟，可容忍丢包|
|DNS 查询|UDP|简单快速|
|广播/组播|UDP|TCP 不支持广播|
|MQTT over TCP|TCP|物联网消息可靠|

#### ③ 嵌入式选型

```text
可靠性优先 → TCP（省去应用层重传设计）
延迟优先   → UDP（自己加应用层校验）
资源受限   → UDP（协议栈开销小）
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **UDP 怎么实现可靠传输？** | 应用层自己设计：序号+ACK+重传+超时（如 QUIC） |
| **TCP 和 UDP 能用同一个端口吗？** | 能，端口号在 TCP 和 UDP 是独立的 |
| **嵌入式用 TCP 还是 UDP 多？** | MQTT/HTTP 用 TCP；传感器上报可能用 UDP |

### 第88题：TCP 三次握手和四次挥手是什么？

> **三次握手：确认双方收发能力正常并同步序列号；四次挥手：分别关闭双向数据通道。**

#### ① 三次握手

```text
客户端                              服务端
  |--- SYN (seq=x) ----------------->|  ① 请求连接
  |<-- SYN+ACK (seq=y, ack=x+1) ----|  ② 确认并回复
  |--- ACK (ack=y+1) --------------->|  ③ 客户端确认
  连接建立                            连接建立
```

| 步骤 | 发送内容 | 确认了什么 |
|------|----------|------------|
| 第1次 | SYN, seq=x | 客户端→服务端方向正常 |
| 第2次 | SYN+ACK, seq=y, ack=x+1 | 服务端→客户端方向正常 |
| 第3次 | ACK, ack=y+1 | 再次确认客户端→服务端 |

#### ② 四次挥手

```text
客户端                              服务端
  |--- FIN (seq=u) ----------------->|  ① 客户端不发了
  |<-- ACK (ack=u+1) ----------------|  ② 服务端确认
  |         ...服务端可能还有数据...    |
  |<-- FIN (seq=w) ------------------|  ③ 服务端也关闭
  |--- ACK (ack=w+1) --------------->|  ④ 客户端确认
  TIME_WAIT (2MSL)                   关闭
```

#### ③ TIME_WAIT 作用

| 作用 | 说明 |
|------|------|
| 处理重传 FIN | 最后 ACK 丢失时，等待对端重发 FIN |
| 消除旧报文 | 等待 2MSL 让旧连接残留报文过期 |
| 持续时间 | 2×MSL（通常 120 秒） |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么三次不是两次？** | 两次无法确认客户端接收能力，可能收到过期 SYN 建立无效连接 |
| **为什么四次不是三次？** | TCP 全双工，每个方向需独立 FIN+ACK；服务端可能还有数据没发完 |
| **SYN Flood 是什么？** | 伪造大量 SYN 不完成握手，耗尽服务端连接资源 |

### 第89题：TCP 粘包是什么？如何解决？

> **TCP 是字节流没有消息边界，多次 write 可能被一次 read 读到。解决靠应用层协议定界。**

#### ① 粘包原因

```text
发送端:  write("HELLO")  write("WORLD")
TCP层:   [HELLOWORLD]  ← 合并
接收端:  read() → "HELLOWORLD"  ← 一次读到两包

或者:
发送端:  write("HELLOWORLD")
TCP层:   [HELLO] [WORLD]  ← 拆分
接收端:  read() → "HELLO"  ← 只读到半包
```

#### ② 四种解决方案

| 方案 | 原理 | 适用场景 |
|------|------|----------|
| 固定长度 | 每包固定 N 字节 | 简单但浪费带宽 |
| 分隔符 | 特殊字符结尾（如 \n） | 文本协议（HTTP） |
| 长度字段 | 帧头包含数据长度 | 最常用，推荐 |
| TLV 格式 | Type-Length-Value | 灵活可扩展 |

#### ③ 嵌入式推荐方案（长度字段）

```text
帧格式: [帧头 2B] [长度 2B] [数据 NB] [CRC 2B]

接收状态机:
WAIT_HEAD → READ_LEN → READ_DATA → CHECK_CRC → 处理
```

|步骤|操作|
|---|---|
|1|缓冲区累积数据|
|2|检查是否收到完整帧头+长度|
|3|长度字段判断数据是否收够|
|4|收够后做 CRC 校验|
|5|校验通过才交给业务层|

#### 面试常问追问

| 追问               | 回答                                                    |
| ---------------- | ----------------------------------------------------- |
| **UDP 有粘包问题吗？**  | 没有，UDP 是数据报协议，每次 recv 就是一次 send 的数据                   |
| **HTTP 怎么解决粘包？** | Content-Length 字段定界，或 Transfer-Encoding: chunked 分块传输 |
| **和串口粘包有什么区别？**  | 本质相同——都是字节流，解决思路也一样（长度字段+状态机）                         |

### 第90题：MQTT 的基本原理是什么？

> **MQTT 是轻量级发布/订阅协议，设备通过 Broker 的 topic 解耦通信，适合物联网低带宽场景。**

#### ① 发布/订阅模型

```text
传统点对点:
  设备A ──直接──> 设备B   (A 必须知道 B 的地址)

MQTT 发布/订阅:
  设备A ──publish──> Broker ──forward──> 设备B
  设备B ──subscribe "sensor/temp"──> Broker
  设备A ──publish "sensor/temp" 25.5──> Broker

  设备A 不需要知道谁在订阅，只管往 topic 发
  设备B 不需要知道谁在发布，只管订阅 topic
```

#### ② 核心概念

| 概念           | 说明                        |
| ------------ | ------------------------- |
| Broker       | 消息代理服务器，负责转发消息            |
| Topic        | 消息主题，如 `home/sensor/temp` |
| Publish      | 发布消息到指定 topic             |
| Subscribe    | 订阅 topic，接收对应消息           |
| QoS          | 消息质量等级（0/1/2）             |
| Will Message | 遗嘱消息，设备异常断开时自动发布          |
| Keep Alive   | 心跳保活，检测连接是否存活             |

#### ③ QoS 等级

| QoS | 含义   | 保证        | 开销  |
| --- | ---- | --------- | --- |
| 0   | 最多一次 | 不保证送达     | 最低  |
| 1   | 至少一次 | 保证送达，可能重复 | 中   |
| 2   | 恰好一次 | 不重复不丢失    | 最高  |

#### ④ MQTT vs HTTP（物联网场景）

|对比项|MQTT|HTTP|
|---|---|---|
|模式|发布/订阅，长连接|请求/响应，短连接|
|开销|极小（2字节固定头）|大（文本头）|
|双向通信|天然支持|需要轮询或 WebSocket|
|适用场景|传感器上报、远程控制|Web API、固件下载|
|嵌入式资源|低|较高|

#### 面试常问追问

| 追问                   | 回答                                            |
| -------------------- | --------------------------------------------- |
| **MQTT 断线重连怎么处理？**   | 设备端检测心跳超时后重连 Broker，可设置 Clean Session 和消息缓存   |
| **MQTT 适合实时控制吗？**    | QoS 0/1 延迟较低，适合一般控制；强实时闭环建议用 CAN/Modbus 等现场总线 |
| **MQTT Broker 有哪些？** | Mosquitto（轻量）、EMQX（企业级）、阿里云/华为云 IoT 平台自带      |
