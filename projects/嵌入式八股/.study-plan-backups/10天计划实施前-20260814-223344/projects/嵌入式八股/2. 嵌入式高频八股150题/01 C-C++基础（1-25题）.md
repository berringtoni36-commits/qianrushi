### 第1题：static 关键字有哪些作用？

> **static 有三大作用——延长局部变量生命周期、限制全局变量/函数的作用域为当前文件、C++ 中修饰类成员为所有对象共享。**

#### ① 修饰局部变量：生命周期延长，作用域不变

| 特性 | 普通局部变量 | static 局部变量 |
|------|-------------|----------------|
| 存储位置 | 栈区 | 静态存储区（.data/.bss） |
| 生命周期 | 函数调用结束即销毁 | 程序运行期间一直存在 |
| 初始化时机 | 每次进入函数都重新初始化 | 只在第一次调用时初始化 |
| 作用域 | 仅函数内部 | 仅函数内部（不变） |

```c
void counter(void) {
    static int cnt = 0; // 只初始化一次，之后值保留
    cnt++;              // 每次调用 cnt 都在上一次基础上累加
    printf("%d\n", cnt);
}
// 连续调用3次输出：1, 2, 3
```

#### ② 修饰全局变量/函数：限制作用域为当前文件

| 特性 | 普通全局变量 | static 全局变量 |
|------|-------------|----------------|
| 作用域 | 整个工程（其他文件 extern 可用） | 仅当前 .c 文件 |
| 链接属性 | 外部链接 | 内部链接 |
| 用途 | 跨文件共享 | 模块内部封装，避免命名冲突 |

```c
// module.c
static int g_state = 0;           // 只有 module.c 内能访问
static void parse_frame(void) {}  // 只有 module.c 内能调用
```

#### ③ C++ 中修饰类成员：所有对象共享

```cpp
class Device {
    static int count;  // 所有 Device 对象共享同一份
public:
    Device() { count++; }
    ~Device() { count--; }
    static int getCount() { return count; } // 可通过类名直接调用
};
```

#### ④ 存储位置总结（ASCII 图）

```text
程序内存布局（静态区部分）：
┌──────────────────────────┐ 高地址
│         栈区（向下增长）    │ ← 普通局部变量
├──────────────────────────┤
│         堆区（向上增长）    │ ← malloc/new
├──────────────────────────┤
│   .bss 段（未初始化/置零） │ ← static int x;
│   .data 段（已初始化）     │ ← static int x = 10;
├──────────────────────────┤
│      代码段 .text         │
└──────────────────────────┘ 低地址
```

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **static 局部变量存放在哪里？** | 静态存储区，不在栈上，函数结束后值仍保留 |
| **static 全局变量为什么只文件可见？** | 链接属性为内部链接，链接器不会把它导出给其他编译单元 |
| **static 变量是否线程安全？** | 不保证，多线程访问需要加锁或临界区保护 |
| **static 成员变量能在类内初始化吗？** | 只有 const 整型/枚举可以在类内初始化，其余必须类外定义 |

### 第2题：const 关键字有什么作用？

> **const 核心是表达"只读语义"，约束数据不被修改，让接口意图更清晰，编译器帮你检查。**

#### ① const 修饰变量：不可修改

```c
const int MAX = 100;  // MAX 的值不能被修改
// MAX = 200;         // 编译报错
```

#### ② const 与指针组合（高频考点）

判断口诀：**const 在 * 左边 → 内容只读；const 在 * 右边 → 指针只读**

| **声明** | 含义 | 能改指向？ | 能改内容？ |
|------|------|-----------|-----------|
| **`const int *p`** | 指向常量的指针 | ✅ | ❌ |
| **`int * const p`** | 常量指针 | ❌ | ✅ |
| **`const int * const p`** | 都不能改 | ❌ | ❌ |

```c
int a = 10, b = 20;
const int *p = &a;  // p 可以改指向，但不能通过 p 修改 *p
p = &b;             // ✅ 合法
// *p = 30;         // ❌ 编译报错
```

#### ③ 嵌入式中的典型用法

| **场景** | 示例 | 目的 |
|------|------|------|
| **查表数组** | const uint16_t sin_table[] | 数据可能放 Flash，防误写 |
| **函数参数** | `void read(const uint8_t *buf, int len)` | 表示函数不会修改调用方数据 |
| **固定配置** | const uint32_t BAUD_RATE = 115200 | 语义明确，防意外修改 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **const 和 #define 有什么区别？** | const 有类型检查、有作用域、可调试；#define 是纯文本替换 |
| **const 变量能不能绕过修改？** | 可以通过指针强转绕过，但属于未定义行为，嵌入式中不应这么做 |
| **const 修饰成员函数有什么用？** | 表示该函数不修改对象状态，const 对象只能调用 const 成员函数 |
| **函数参数加 const 的意义？** | 接口约束：告诉调用者"我只读不改"，也方便编译器检查 |

### 第3题：volatile 关键字在嵌入式开发中有什么作用？

> **volatile 告诉编译器"这个变量可能被意外改变，每次访问都老老实实从内存读"，防止编译器优化掉必要的读写操作。**

#### ① volatile 解决什么问题？

编译器优化时，如果发现某变量在当前代码流程中没有被修改，可能把它缓存到寄存器，不再每次从内存读取。但在嵌入式中，变量的值可能被中断、硬件、DMA 等外部因素改变，优化会导致读到"旧值"。

```c
volatile uint8_t rx_done = 0;  // 可能在中断中被置 1

while (!rx_done) {   // 如果没有 volatile，编译器可能优化为只读一次
    // 等待接收完成
}
// 加了 volatile：每次都从内存重新读取 rx_done 的值
```

#### ② 必须使用 volatile 的三大场景

| **场景** | 原因 | 示例 |
|------|------|------|
| **中断与主循环共享变量** | 中断随时可能改变变量值 | `volatile uint8_t flag;` |
| **硬件寄存器映射** | 外设随时可能改变寄存器值 | `*(volatile uint32_t *)0x40021000` |
| **多线程/RTOS 共享标志** | 其他任务随时可能修改变量 | `volatile int state;` |

#### ③ volatile 的局限性

| **能解决** | 不能解决 |
|--------|---------|
| **编译器优化可见性问题** | 原子性问题（读-改-写不是原子的） |
| **确保每次都从内存读写** | 竞态条件（多任务同时修改） |

> volatile + 互斥锁/临界区/原子操作 = 完整的多任务共享保护

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **volatile 能替代锁吗？** | 不能，volatile 只保证读写不被优化，不保证原子性和同步 |
| **什么场景必须加 volatile？** | 中断共享变量、硬件寄存器、RTOS 多任务共享标志位 |
| **volatile 和 const 能同时用吗？** | 可以，const volatile 表示"我不改，但别人可能改"，常见于只读硬件寄存器 |
| **缺少 volatile 会导致什么现象？** | 程序可能一直卡在循环中等待一个"永远不会变"的变量 |

### 第4题：extern 关键字有什么作用？

> **extern 用于声明"这个变量/函数定义在别的文件中"，是多文件工程中实现跨文件共享符号的关键手段。**

#### ① extern 的核心作用：声明 vs 定义

| **概念** | 定义 | 声明 |
|------|------|------|
| **含义** | 分配存储空间，创建实体 | 告诉编译器"存在这个符号" |
| **写法** | int g_count = 0; | extern int g_count; |
| **出现次数** | 整个工程只能有一次 | 可以出现多次 |
| **存储空间** | 分配 | 不分配 |

#### ② 多文件工程的标准用法

```c
// sensor.c —— 定义全局变量
int g_temp_value = 0;          // 定义，分配空间

// sensor.h —— 头文件中声明
extern int g_temp_value;       // 声明，不分配空间

// main.c —— 包含头文件后使用
#include "sensor.h"
void main() { g_temp_value = 25; }  // 合法访问
```

#### ③ 常见错误

| **错误写法** | 后果 |
|---------|------|
| **头文件中 int g_count = 0;（直接定义）** | 多文件包含后链接报"重复定义" |
| **只写 extern int g_count; 但没有在任何 .c 中定义** | 链接报"未定义符号" |
| **两个 .c 文件各自定义 int g_count;** | 链接报"重复定义"（C++ 中，C 中可能为暂定定义） |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **extern "C" 是干什么的？** | 告诉 C++ 编译器用 C 的链接约定编译，使 C 函数能被 C++ 代码调用 |
| **声明和定义有什么区别？** | 声明不分配存储空间，定义会分配；extern 是声明，不是定义 |
| **extern 能用在函数上吗？** | 可以但通常省略，函数声明默认就是 extern 的 |
| **为什么不推荐大量用全局变量？** | 增加模块耦合、难以追踪修改、不利于维护，推荐用接口封装 |

### 第5题：指针和数组有什么区别？

> **数组是一段连续内存块，指针是一个存储地址的变量；数组名会"退化"为指针，但本质不同。**

#### ① 核心区别对比

| **对比项** | 数组 | 指针 |
|--------|------|------|
| **本质** | 连续内存块 | 存储地址的变量 |
| **sizeof 结果** | 整个数组的字节数 | 指针变量大小（32位4字节，64位8字节） |
| **赋值** | 不能整体赋值 | 可以随时指向别的地址 |
| **存储** | 有自己的存储空间 | 变量本身只存一个地址 |

#### ② sizeof 陷阱（最常考）

```c
int arr[10] = {0};
int *p = arr;

sizeof(arr);  // 40（10个int，每个4字节）
sizeof(p);    // 4（32位系统）或 8（64位系统）
```

#### ③ 函数传参时数组退化为指针

```c
void func(int buf[]) {
    // 这里 buf 已经退化为 int*，sizeof(buf) = 4 或 8
    // 无法得知原数组大小！
}
// 正确做法：额外传长度参数
void func2(int *buf, int len) { /* ... */ }
```

```text
数组退化示意：
int arr[5];          sizeof(arr) = 20
        │
        ▼ 传入函数
void f(int buf[])    sizeof(buf) = 4   ← 已退化为指针！
```

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **数组名是常量指针吗？** | 可以这么理解，数组名不能被赋值，但会在大部分表达式中退化为指向首元素的指针 |
| **函数参数中数组为什么退化？** | C 语言数组不能按值传递，编译器自动将数组参数转换为指针参数 |
| **指针数组和数组指针区别？** | `int *p[5]` 是指针数组（5 个 `int*`），`int (*p)[5]` 是数组指针（指向含 5 个 `int` 的数组） |
| **嵌入式中怎么安全传缓冲区？** | 指针 + 长度一起传：`func(buf, sizeof(buf))` |

### 第6题：指针和引用有什么区别？

> **指针是存地址的变量（可为空、可改指向），引用是对象的别名（必须初始化、不可更换绑定）。**

#### ① 核心区别对比

| **对比项** | 指针 | 引用 |
|--------|------|------|
| **本质** | 存储地址的变量 | 对象的别名 |
| **是否可为空** | 可以为 NULL/nullptr | 不能为空，必须绑定有效对象 |
| **初始化** | 可以先声明后初始化 | 定义时必须初始化 |
| **能否改指向** | 可以随时改变指向 | 绑定后不能更换对象 |
| **是否占内存** | 占内存（存一个地址） | 理论上不额外占空间（编译器实现相关） |
| **访问方式** | 需要 *p 解引用 | 直接使用，和原变量一样 |

#### ② 代码对比

```cpp
int a = 10, b = 20;
int *p = &a;   // 指针指向 a
p = &b;        // 可以改指向 b
*p = 30;       // 通过指针修改 b 的值

int &r = a;    // 引用绑定 a
r = 40;        // 直接修改 a 的值
// r = b;      // ❌ 不是改绑定，而是把 b 的值赋给 a
```

#### ③ 使用场景选择

| **场景** | 推荐 | 原因 |
|------|------|------|
| **函数参数避免拷贝，且不会为空** | const T& | 更安全、更简洁 |
| **参数可能为空** | 指针 T* | 引用不能表达"空"的语义 |
| **寄存器映射/DMA/内存操作** | 指针 | 需要直接操作地址 |
| **C++ 运算符重载/STL** | 引用 | 语法要求 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **引用底层怎么实现？** | 大多数编译器用指针实现，但语言层面不能取引用本身的地址 |
| **C 为什么没有引用？** | 引用是 C++ 引入的语法糖，C 用指针完成类似功能 |
| **为什么 C++ 有了指针还要引用？** | 引用更安全（不为空、不改绑定），接口语义更清晰 |
| **引用能替代指针吗？** | 不能，底层地址操作、可空语义、动态绑定等场景仍需指针 |

### 第7题：sizeof 和 strlen 有什么区别？

> **sizeof 是编译期运算符，算的是"占多大内存"；strlen 是运行时函数，算的是"字符串多长"。**

#### ① 核心区别对比

| **对比项** | sizeof | strlen |
|--------|--------|--------|
| **本质** | 编译器运算符 | C 标准库函数 <string.h> |
| **计算内容** | 类型/对象占用的字节数 | \0 之前的字符个数 |
| **计算时机** | 编译期确定（大部分情况） | 运行时逐字节扫描 |
| **是否包含 \0** | 包含 | 不包含 |
| **参数** | 类型或变量 | 只能是 char* 字符串 |

#### ② 代码示例

```c
char str[] = "abc";

sizeof(str);   // 4（'a','b','c','\0' 共4字节）
strlen(str);   // 3（'\0' 之前有3个字符）

char *p = str;
sizeof(p);     // 4（32位）或 8（64位）——指针本身大小，不是字符串长度！
strlen(p);     // 3
```

#### ③ 嵌入式中的典型坑

| **场景** | 错误做法 | 正确做法 |
|------|---------|---------|
| **发送二进制数据（含0字节）** | strlen(buf) 会提前截断 | 用协议中的 length 字段 |
| **函数内求数组大小** | sizeof(buf) 已退化为指针 | 传参时同时传 len |
| **判断 DMA 接收长度** | strlen 扫描不到有效数据 | 用 DMA 计数器或协议帧长 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **sizeof 是在编译期还是运行时？** | 大部分情况下编译期确定，变长数组（VLA）在运行时计算 |
| **sizeof 一个空结构体是多少？** | C 中为 0，C++ 中为 1（保证不同对象地址不同） |
| **字符数组和字符指针的 sizeof 区别？** | 数组 = 元素个数 × 元素大小；指针 = 指针变量大小 |
| **为什么嵌入式中不能随便用 strlen？** | 二进制数据中间可能有 0x00，strlen 遇到就停止计数 |

### 第8题：堆和栈有什么区别？

> **栈由编译器自动管理（函数进出），速度快但空间小；堆由程序员手动管理（malloc/free），灵活但风险大。**

#### ① 核心区别对比

| **对比项** | 栈（Stack） | 堆（Heap） |
|--------|------------|-----------|
| **管理方式** | 编译器自动分配释放 | 程序员手动 malloc/free |
| **速度** | 快（直接移动栈指针） | 慢（需要查找空闲块） |
| **空间大小** | 较小（通常几KB~几MB） | 较大（取决于系统可用内存） |
| **生存期** | 函数结束自动释放 | 由程序员控制 |
| **碎片问题** | 无（后进先出） | 有（频繁分配释放产生碎片） |
| **生长方向** | 向低地址增长（多数平台） | 向高地址增长（多数平台） |

#### ② 内存布局图

```text
┌───────────────┐ 高地址
│   栈 Stack     │ ← 局部变量、函数参数、返回地址（向下增长 ↓）
├───────────────┤
│       ↓       │
│   空闲区域     │
│       ↑       │
├───────────────┤
│   堆 Heap      │ ← malloc/new 分配（向上增长 ↑）
├───────────────┤
│ .bss / .data   │ ← 全局变量、静态变量
├───────────────┤
│ .text（代码段） │ ← 程序指令
└───────────────┘ 低地址
```

#### ③ 嵌入式中的注意事项

| **问题** | 后果 | 建议 |
|------|------|------|
| **栈上放大型数组** | 栈溢出 → 系统崩溃 | 大数组放全局/静态区 |
| **深递归** | 栈溢出 | 改用循环或限制递归深度 |
| **频繁 malloc/free** | 内存碎片 → 运行久了分配失败 | 用静态分配或内存池 |
| **忘记 free** | 内存泄漏 | RAII 或成对管理 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **栈溢出会怎样？** | 覆盖相邻内存，导致数据破坏或 HardFault（MCU）/段错误（Linux） |
| **栈的默认大小是多少？** | MCU 由链接脚本/RTOS配置，Linux 线程默认 8MB |
| **堆内存是物理地址吗？** | malloc 返回的是虚拟地址，需要页表映射到物理地址 |
| **为什么嵌入式慎用堆？** | RAM 有限、碎片不可控、分配时间不确定、长期运行稳定性差 |

### 第9题：全局变量、局部变量和静态变量分别存放在哪里？

> **局部变量在栈上，全局变量和静态变量在静态存储区（.data/.bss），static 局部变量虽然写在函数里但不在栈上。**

#### ① 存储位置总结

| **变量类型** | 存储区域 | 生命周期 | 初始化值 |
|---------|---------|---------|---------|
| **普通局部变量** | 栈区 | 函数调用期间 | 随机值（未初始化） |
| **static 局部变量** | 静态存储区 | 整个程序运行期 | 0（默认） |
| **全局变量（已初始化）** | .data 段 | 整个程序运行期 | 指定初值 |
| **全局变量（未初始化）** | .bss 段 | 整个程序运行期 | 0 |
| **static 全局变量** | .data / .bss 段 | 整个程序运行期 | 同全局变量 |

#### ② 程序段分布图

```text
Flash 中存储：
┌─────────────────┐
│  .text（代码段）  │  ← 程序指令
│  .rodata        │  ← const 常量、字符串字面量
│  .data 初值      │  ← 已初始化全局/静态变量的"模板"
└─────────────────┘

RAM 中运行：
┌─────────────────┐
│  栈 Stack        │  ← 局部变量
├─────────────────┤
│  堆 Heap         │  ← malloc
├─────────────────┤
│  .bss 段         │  ← 未初始化全局/静态变量（启动时清零）
│  .data 段        │  ← 已初始化全局/静态变量（启动时从Flash拷贝）
└─────────────────┘
```

#### ③ 启动流程中的初始化

| **步骤** | 操作 | 原因 |
|------|------|------|
| **1** | .bss 段清零 | 未初始化全局变量默认为 0 |
| **2** | .data 段从 Flash 拷贝到 RAM | 已初始化全局变量需要有初值 |
| **3** | 跳转到 main | 初始化完成，开始执行用户代码 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **未初始化的全局变量为什么是 0？** | 启动代码在 main 之前将 .bss 段清零 |
| **static 局部变量为什么不在栈上？** | 编译器把它放在静态存储区，函数返回后值仍保留 |
| **.data 和 .bss 有什么区别？** | .data 存已初始化变量（占 Flash + RAM），.bss 存未初始化变量（只占 RAM，Flash 不存内容） |
| **局部变量不初始化的值是什么？** | 栈上的残留数据，是不确定的随机值 |

### 第10题：malloc/free 和 new/delete 有什么区别？

> **malloc/free 只管分配/释放原始内存；new/delete 在此基础上还会调用构造函数/析构函数，是面向对象的完整方案。**

#### ① 核心区别对比

| **对比项** | malloc / free | new / delete |
|--------|--------------|-------------|
| **本质** | C 标准库函数 | C++ 运算符 |
| **构造/析构** | ❌ 不调用 | ✅ 自动调用 |
| **返回类型** | void*（需强转） | 具体类型指针 |
| **失败处理** | 返回 NULL | 默认抛异常（可用 nothrow） |
| **大小计算** | 需手动算字节数 | 自动计算类型大小 |
| **能否重载** | ❌ | ✅ 可重载 operator new |

#### ② 代码对比

```cpp
// C 风格
int *p1 = (int *)malloc(10 * sizeof(int));  // 分配10个int
free(p1);                                    // 释放

// C++ 风格
int *p2 = new int[10];    // 分配 + 默认初始化
delete[] p2;              // 释放（数组用 delete[]）

// C++ 对象
Device *dev = new Device();  // 分配 + 调用构造函数
delete dev;                  // 调用析构函数 + 释放
```

#### ③ 绝对不能混用的配对

```text
malloc  → free      ✅
new     → delete    ✅
new[]   → delete[]  ✅

malloc  → delete    ❌ 未定义行为
new     → free      ❌ 析构函数不会被调用！
new[]   → delete    ❌ 可能只析构第一个元素
```

#### ④ 嵌入式中的建议

| **建议** | 原因 |
|------|------|
| **优先静态分配** | RAM 有限，避免碎片 |
| **如果用 C++，用 new/delete 或智能指针** | 自动管理构造/析构和生命周期 |
| **限制动态分配时机** | 启动阶段一次性分配，运行阶段尽量不频繁申请释放 |
| **检查返回值/异常** | 分配失败时做明确处理，不能忽略 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-----------|
| **new 的底层调用了什么？** | 底层调用 operator new（通常封装 malloc），然后调用构造函数 |
| **new 出来的内存能用 free 释放吗？** | 不推荐，析构函数不会被调用，属于未定义行为 |
| **delete 和 delete[] 有什么区别？** | delete 释放单个对象，delete[] 释放数组并逐个调用析构函数 |
| **为什么嵌入式中慎用动态内存？** | 内存碎片、分配时间不确定、泄漏风险、长期运行稳定性差 |

### 第11题：delete 和 delete[] 有什么区别？

> **delete 释放单个对象，delete[] 释放数组，混用是未定义行为。**

#### ① 核心区别

| **对比项** | `delete` | `delete[]` |
|---|---|---|
| **适用场景** | 释放 `new` 创建的单个对象 | 释放 `new[]` 创建的对象数组 |
| **析构调用** | 只调用 1 次析构函数 | 对**每个元素**都调用析构函数 |
| **混用后果** | 未定义行为，可能少析构/内存泄漏 | 未定义行为，可能多析构/崩溃 |

#### ② 代码示例

```cpp
int *a = new int[10];       // 分配数组
delete[] a;                 // ✅ 正确：释放整个数组

MyClass *obj = new MyClass(); // 分配单个对象
delete obj;                   // ✅ 正确：释放单个对象
```

#### ③ 基本类型 vs 类对象

| **类型** | 混用是否立即崩溃 | 风险 |
|------|------------------|------|
| **int[]/char[] 等基本类型** | 通常不会立即崩 | 但仍属未定义行为，不保证安全 |
| **带析构函数的类对象数组** | 很可能崩溃 | 析构次数不对，资源释放不完整 |

#### ④ 记住什么

- **配对原则**：
new → delete，
new[] → delete[]，绝不混用

- 基本类型混用"看起来没事"只是运气好，换编译器/平台就可能崩
- 嵌入式中资源有限，析构不完整可能导致外设未关闭、DMA 未停止等严重后果

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **`new` 和 `malloc` 有什么区别？** | `new` 调构造函数、返回类型安全指针；`malloc` 只分配原始内存、返回 `void*` |
| **`delete` 后指针变什么？** | 指针值不变（悬空指针），建议释放后立即置为 `nullptr` |
| **嵌入式中一般怎么管理内存？** | 静态分配为主，避免频繁 `new/delete`，必要时用内存池 |
| **RAII 是什么？** | 把资源绑定到对象生命周期，对象销毁时自动释放资源 |

### 第12题：什么是内存泄漏？如何避免？

> **申请了内存没释放，就叫内存泄漏——长时间运行的嵌入式设备会逐渐死机。**

#### ① 什么是内存泄漏

```text
程序 malloc/new → 获得内存块 → 忘记 free/delete → 内存永远回不来
                                              ↓
                               系统可用内存越来越少 → 最终 OOM/死机
```

#### ② 常见泄漏场景

| **场景** | **说明** |
|------|------|
| **提前 `return` 跳过释放** | 函数中间 `return`，后面的 `free` 被跳过 |
| **异常/错误分支遗漏** | `if (err) return;` 但没释放已分配的内存 |
| **容器只增不删** | 链表/数组不断 `push` 但不 `pop` |
| **循环引用** | `shared_ptr` 互相引用导致引用计数永远不归零 |

#### ③ 如何避免

```cpp
// 方法1：RAII——用智能指针自动管理
std::unique_ptr<int> p(new int(42)); // 离开作用域自动释放

// 方法2：成对出现，所有分支都释放
int *buf = malloc(256);
if (!buf) return -1;
if (err) { free(buf); return -1; }  // 异常分支也要释放
free(buf);                            // 正常分支释放
```

#### ④ 排查工具

| **平台** | 工具 |
|------|------|
| **Linux** | Valgrind、AddressSanitizer（ASan）、mtrace |
| **FreeRTOS** | xPortGetFreeHeapSize() 监控堆变化 |
| **通用** | 代码审查、堆剩余空间日志监控 |

#### ⑤ 记住什么

- 核心原则：**谁申请谁释放，每条路径都要释放**
- C++ 优先用 RAII（unique_ptr/shared_ptr）
- 嵌入式中更推荐**静态分配**，从根源上杜绝泄漏

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **shared_ptr 循环引用怎么办？** | 用 weak_ptr 打破循环 |
| **valgrind 怎么用？** | `valgrind --leak-check=full ./program` |
| **FreeRTOS 怎么监控堆？** | 定时调用 xPortGetFreeHeapSize 记录日志 |
| **嵌入式为什么更怕内存泄漏？** | 设备长期运行，泄漏累积导致系统不可用 |

### 第13题：栈溢出是什么？如何避免？

> **栈空间用超了就是栈溢出——深递归、大局部数组、调用链太深都是元凶。**

#### ① 栈溢出原理

```text
栈空间（有限大小）
┌─────────────────┐ 高地址
│   main() 栈帧    │
│   funcA() 栈帧   │
│   funcB() 栈帧   │  ← 每调一层函数就压一帧
│   funcC() 栈帧   │
│   ...不断深入... │
│   💥 栈溢出！    │  ← 超出栈边界，覆盖其他内存
└─────────────────┘ 低地址
```

#### ② 常见原因

| **原因** | 说明 |
|------|------|
| **递归没有终止条件** | 无限递归，栈帧不断压入 |
| **局部数组过大** | 函数内定义 char buf[65536] 直接吃掉栈空间 |
| **调用链太深** | 中间件/回调层层嵌套 |
| **FreeRTOS 任务栈太小** | 任务栈分配不足，运行时溢出 |

#### ③ 如何避免

| **方法** | 说明 |
|------|------|
| **大数组放静态区/堆上** | static char buf[N] 或 malloc |
| **限制递归深度** | 加深度计数器或改用迭代 |
| **合理设置任务栈** | FreeRTOS 用 uxTaskGetStackHighWaterMark 监控 |
| **开启栈溢出检测** | configCHECK_FOR_STACK_OVERFLOW |

```cpp
// 错误：大数组放栈上
void bad() { char buf[4096]; }  // 💥 栈上吃掉 4KB

// 正确：大数组放静态区
void good() { static char buf[4096]; }  // ✅ 放在 BSS 段
```

#### ④ 记住什么

- 栈溢出 ≠ 段错误，但栈溢出**常常导致**段错误或数据破坏
- 嵌入式 MCU 栈通常只有几 KB，比 Linux 小得多，更要注意
- FreeRTOS 每个任务独立栈，任务多时总栈空间可能超过 RAM

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **栈溢出会怎样？** | 数据被覆盖、HardFault、程序跑飞、偶发崩溃 |
| **FreeRTOS 怎么检测栈溢出？** | 水位线 uxTaskGetStackHighWaterMark + 溢出钩子 |
| **栈和堆哪个在高地址？** | 取决于平台，ARM Cortex-M 通常栈在高地址向下增长 |
| **printf 会吃栈吗？** | 会，printf 内部缓冲区可能占数百字节到 1KB+ |

### 第14题：段错误是什么？常见原因有哪些？

> **段错误（Segmentation Fault）就是程序访问了不该访问的内存，操作系统直接杀掉进程。**

#### ① 段错误是什么

```text
程序试图访问非法内存地址
        ↓
操作系统检测到越权/非法访问
        ↓
向进程发送 SIGSEGV 信号
        ↓
进程被终止（core dumped）
```

#### ② 常见原因

| **原因** | 代码示例 |
|------|----------|
| **空指针解引用** | int *p = NULL; *p = 1; |
| **访问已释放内存** | free(p); *p = 5;（use-after-free） |
| **数组越界** | int a[10]; a[100] = 0; |
| **栈溢出** | 无限递归或局部数组过大 |
| **写只读内存** | char *s = "hello"; s[0] = 'H'; |
| **错误的函数指针** | 调用未初始化/已失效的函数指针 |

#### ③ 嵌入式中的段错误

| **平台** | 表现 |
|------|------|
| **Linux 嵌入式** | 进程收到 SIGSEGV 被杀，可生成 core dump |
| **MCU（Cortex-M）** | HardFault 异常，进入 HardFault_Handler |
| **裸机** | 可能不报错直接跑飞，结果不可预测 |

#### ④ 排查方法

```bash
# Linux 下用 GDB + core dump
gcc -g main.c -o main          # 编译带调试信息
ulimit -c unlimited            # 允许生成 core 文件
./main                         # 复现崩溃
gdb ./main core                # 加载 core 文件
(gdb) bt                       # 查看崩溃调用栈
```

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **SIGSEGV 是什么？** | 段错误信号，表示访问非法内存 |
| **core dump 怎么开启？** | ulimit -c unlimited，编译加 -g |
| **MCU 的 HardFault 怎么排查？** | 查 PC/LR/SP 寄存器，结合 map 文件反查地址 |
| **段错误和栈溢出什么关系？** | 栈溢出是段错误的常见原因之一 |

### 第15题：大端和小端是什么？如何判断？

> **大端高位字节在低地址，小端低位字节在低地址；网络字节序是大端，x86/多数ARM是小端。**

#### ① 大端 vs 小端

```text
数值 0x12345678 在内存中的存放：

大端模式（Big-Endian）：        小端模式（Little-Endian）：
低地址 ──────────► 高地址       低地址 ──────────► 高地址
┌────┬────┬────┬────┐          ┌────┬────┬────┬────┐
│ 12 │ 34 │ 56 │ 78 │          │ 78 │ 56 │ 34 │ 12 │
└────┴────┴────┴────┘          └────┴────┴────┴────┘
高位字节在前（低地址）          低位字节在前（低地址）
```

| **对比项** | 大端 Big-Endian | 小端 Little-Endian |
|--------|----------------|-------------------|
| **存放顺序** | 高位字节在低地址 | 低位字节在低地址 |
| **直觉** | 符合人类阅读习惯 | 符合计算机运算习惯 |
| **代表平台** | 网络字节序、PowerPC、部分MIPS | x86、STM32、多数ARM |

#### ② 代码判断方法

```c
#include <stdint.h>

int is_little_endian(void) {
    uint32_t x = 0x12345678;
    uint8_t *p = (uint8_t *)&x;  // 取最低地址的1字节
    return (*p == 0x78);          // 0x78=小端，0x12=大端
}
```

#### ③ 嵌入式中什么时候要关注大小端？

| **场景** | 说明 |
|------|------|
| **网络通信** | 网络字节序是大端，发送前用 htonl() 转换 |
| **通信协议解析** | 不同MCU可能大小端不同，按协议文档逐字节解析 |
| **Flash 存储** | 多字节数据写入后再读出，跨平台可能解析错误 |
| **寄存器访问** | 某些外设寄存器有字节序要求 |

#### ④ 常用字节序转换函数

| **函数** | 作用 |
|------|------|
| **htonl() / ntohl()** | 32位：主机序 ↔ 网络序（大端） |
| **htons() / ntohs()** | 16位：主机序 ↔ 网络序（大端） |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么网络用大端？** | 历史约定（RFC），大端符合人类阅读习惯，便于抓包分析 |
| **STM32 是大端还是小端？** | 小端，Cortex-M 内核默认小端，但可配置为大端（通常不用） |
| **大小端对编程有什么影响？** | 单机开发无感，跨平台通信/存储必须统一字节序，否则数据解析错误 |
| **union 可以判断大小端吗？** | 可以，union 共享内存，写入多字节成员后读取单字节成员即可判断 |

### 第16题：内存对齐是什么？为什么要内存对齐？

> **编译器在成员间插入 padding 让地址对齐到特定边界，为了 CPU 访问效率和硬件兼容性。**

#### ① 什么是内存对齐

```c
struct Example {
    char a;    // 1字节，偏移 0
    // 3字节 padding（对齐到4字节边界）
    int b;     // 4字节，偏移 4
    char c;    // 1字节，偏移 8
    // 3字节 padding（结构体总大小对齐到最大成员=4的倍数）
};
// 总大小 = 12 字节（不是 6 字节！）
```

#### ② 对齐规则

| **规则** | 说明 |
|------|------|
| **成员对齐** | 每个成员的起始地址必须是其大小的整数倍 |
| **结构体对齐** | 结构体总大小必须是最大成员对齐值的整数倍 |
| **嵌套结构体** | 嵌套的结构体按其最大成员对齐 |

#### ③ 成员顺序影响大小

```cpp
struct A { char a; int b; char c; };  // 12 字节（有 padding）
struct B { int b; char a; char c; };  // 8 字节（紧凑排列）
```

#### ④ 为什么要对齐

| **原因** | 说明 |
|------|------|
| **CPU 访问效率** | 对齐的数据一次总线事务读完，不对齐可能要两次 |
| **硬件要求** | 部分 ARM/RISC 处理器**不支持**非对齐访问，直接触发异常 |
| **DMA/外设通信** | 外设寄存器和 DMA 通常要求对齐地址 |

#### ⑤ 嵌入式注意事项

| **场景** | 建议 |
|------|------|
| **通信协议帧解析** | 不要直接 struct 映射，按字段手动解析 |
| **跨平台数据传输** | 用 #pragma pack(1) 或按字节序列化 |
| **Flash 存储布局** | 注意不同编译器对齐方式可能不同 |

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **#pragma pack(1) 是什么？** | 关闭对齐，结构体成员紧密排列 |
| **pack 后有什么代价？** | CPU 访问变慢，某些平台可能触发异常 |
| **怎么查看结构体大小？** | sizeof() + 打印每个成员的 offsetof() |
| **结构体成员顺序怎么优化？** | 按对齐值从大到小排列，减少 padding |

### 第17题：#define 和 typedef 有什么区别？

> **#define 是预处理阶段的文本替换， typedef 是编译阶段的类型别名——本质完全不同。**

#### ① 核心区别

| **对比项** | #define |  typedef |
|--------|-----------|-----------|
| **处理阶段** | 预处理（编译前） | 编译阶段 |
| **本质** | 纯文本替换 | 类型别名，有类型语义 |
| **作用域** | 从定义处到文件末尾，不受 {} 限制 | 遵循正常的作用域规则 |
| **调试** | 宏替换后符号消失，不好调试 | 类型别名保留在符号表中 |
| **指针陷阱** | 多变量声明有坑 | 正确处理类型语义 |

#### ② 指针声明的经典坑

```cpp
#define INT_PTR int*
typedef int* IntPtr;

INT_PTR a, b;    // 展开为 int* a, b; → a 是指针，b 是 int！
IntPtr c, d;     // c 和 d 都是 int* 类型 ✅
```

#### ③ 各自适用场景

| **场景** | 推荐用 | 原因 |
|------|--------|------|
| **定义简单常量** | #define 或 const/constexpr | 宏简单直接 |
| **给类型起别名** | typedef | 有类型检查，安全 |
| **简化复杂类型声明** | typedef | 如函数指针、结构体别名 |
| **条件编译开关** | #define |  typedef 做不到 |

```cpp
// typedef 简化函数指针
typedef int (*MathFunc)(int, int);  // 函数指针类型别名
MathFunc fp = add;                  // 使用时更清晰
```

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **#define 和 const 有什么区别？** | const 有类型检查和作用域，#define 只是文本替换 |
| **C++ 中 using 和  typedef 区别？** | using 语法更清晰，支持模板别名，功能是超集 |
| **宏定义常量有什么缺点？** | 没有类型检查、没有作用域、调试时符号消失 |
| **typedef 在嵌入式中常用场景？** | 给 uint32_t 等固定宽度类型起项目别名 |

### 第18题：宏定义和 inline 函数有什么区别？

> **宏是文本替换，inline 是真正的函数，只是建议展开——类型安全和可调试性差距巨大。**

#### ① 核心区别

| **对比项** | #define 宏 | inline 函数 |
|--------|--------------|---------------|
| **处理阶段** | 预处理（文本替换） | 编译阶段（函数语义） |
| **类型检查** | ❌ 没有 | ✅ 有完整的参数/返回值类型检查 |
| **作用域** | 无作用域概念 | 遵循函数作用域规则 |
| **调试** | 替换后无法断点调试 | 可以正常断点、单步 |
| **副作用** | 参数可能被多次求值 | 参数只求值一次 |
| **是否一定展开** | 必定替换 | 只是**建议**，编译器可拒绝 |

#### ② 宏的经典副作用

```cpp
#define SQUARE(x) ((x) * (x))

int a = 3;
int r = SQUARE(a++);
// 展开为 ((a++) * (a++)) → a 被自增两次！结果未定义

// inline 版本——安全
inline int square(int x) { return x * x; }
int r2 = square(a++);   // a++ 只求值一次 ✅
```

#### ③ inline 什么时候不展开

| **情况** | 说明 |
|------|------|
| **函数体太大** | 编译器认为展开不如调用 |
| **包含递归** | 无法展开递归函数 |
| **取了函数地址** | 必须生成真正函数实体 |
| **编译优化等级低** | -O0 通常不展开 |

#### ④ 嵌入式中的最佳实践

| **场景** | 推荐方式 |
|------|----------|
| **寄存器位操作** | #define（如 #define BIT(n) (1U << (n))） |
| **短小工具函数** | static inline |
| **常量定义** | const/constexpr 优先 |
| **条件编译开关** | 只能用 #define |

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **static inline 为什么放头文件？** | static 避免多重定义，inline 建议展开 |
| **宏定义要不要加大括号？** | 要，整个表达式加 ()，每个参数也加 () |
| **inline 和 __attribute__((always_inline)) 区别？** | 前者是建议，后者是强制展开（GCC 扩展） |
| **C++ 中宏还有什么不可替代的用途？** | 条件编译、文件/行号宏 __FILE__/__LINE__ |

### 第19题：条件编译有什么作用？

> **条件编译让同一份源码在不同条件下编译出不同代码——平台适配、调试开关、头文件防重复包含都靠它。**

#### ① 条件编译的本质

```text
源代码中：
#if 条件
    代码A    ← 条件为真时编译
#else
    代码B    ← 条件为假时编译
#endif

不满足条件的代码在预处理阶段就被丢弃，不会进入编译
```

#### ② 常见用法

| **用途** | 示例 |
|------|------|
| **头文件防重复包含** | #ifndef __XXX_H / #define __XXX_H / #endif |
| **平台适配** | #ifdef __linux__ ... #elif defined(STM32F4) |
| **调试开关** | #ifdef DEBUG 打印日志，Release 版不编译 |
| **功能裁剪** | #if ENABLE_FEATURE_A 选择性编译功能模块 |
| **编译器区分** | #if defined(__GNUC__) 针对 GCC 特殊处理 |

#### ③ 头文件守卫示例

```cpp
#ifndef MY_DRIVER_H       // 如果没定义过
#define MY_DRIVER_H       // 就定义，防止重复包含

// 头文件内容...

#endif                    // 结束守卫
```

#### ④ 嵌入式中的典型应用

| **场景** | 说明 |
|------|------|
| **多型号硬件适配** | 同一份代码通过宏切换不同 MCU 的寄存器地址 |
| **日志分级** | LOG_LEVEL 宏控制哪些级别的日志被编译 |
| **外设裁剪** | 裁掉不用的驱动模块，减小固件体积 |
| **C/C++ 混合编译** | #ifdef __cplusplus + extern "C" |

```cpp
#ifdef __cplusplus
extern "C" {           // C++ 调用 C 函数时防止名字修饰
#endif
void my_c_func(void);
#ifdef __cplusplus
}
#endif
```

#### ⑤ 记住什么

- 条件编译是**预处理阶段**的行为，不产生运行时开销
- #ifdef 只判断"是否定义过"，#if 可以判断值
- 嵌入式项目中条件编译无处不在：平台适配、调试、裁剪

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **#ifdef 和 #if defined() 区别？** | `#if defined()` 支持逻辑组合（`&&`、`\|\|`、`!`） |
| **extern "C" 是干什么的？** | 防止 C++ 编译器对 C 函数做名字修饰（name mangling） |
| **头文件不加守卫会怎样？** | 重复包含导致类型/函数重复定义，链接报错 |
| **条件编译有什么缺点？** | 代码可读性差，不同分支难以同时测试和维护 |

### 第20题：为什么嵌入式系统中通常不建议频繁使用动态内存？

> **RAM 有限 + 内存碎片 + 实时性要求 + 可靠性要求 → 嵌入式更偏向静态分配。**

#### ① 动态内存在嵌入式中的问题

| **问题** | 说明 |
|------|------|
| **内存碎片** | 反复 malloc/free 产生碎片，总内存够但找不到连续块 |
| **分配时间不确定** | malloc 可能触发内存整理，执行时间不可预测 |
| **泄漏风险** | 遗忘释放/异常路径遗漏，长时间运行逐渐 OOM |
| **重复释放/悬空指针** | 释放后继续访问，破坏数据甚至外设寄存器 |
| **RAM 资源有限** | MCU 可能只有几 KB 到几百 KB RAM |

#### ② 内存碎片示意

```text
初始状态：[     可用 256 字节     ]

分配释放多次后：
[已用][空40B][已用][空80B][已用][空60B][已用]
         ↑ 总空闲 180B，但无法分配 100B 的连续块！
```

#### ③ 嵌入式推荐的替代方案

| **方案** | 说明 | 适用场景 |
|------|------|----------|
| **静态分配** | 编译时确定大小 | 绝大多数场景优先考虑 |
| **固定大小内存池** | 预分配 N 个固定大小块 | 需要动态但大小固定 |
| **对象池** | 预创建 N 个对象实例 | 任务/连接/消息对象 |
| **启动时一次分配** | 运行时不 malloc/free | 配置缓冲区等 |

```cpp
// 内存池示例：固定块大小，无碎片
static uint8_t pool[16][64];  // 16 个 64 字节块
static uint8_t used[16] = {0}; // 使用标记
```

#### ④ 如果必须用动态内存

| **建议** | 说明 |
|------|------|
| **启动阶段分配** | 初始化时一次性 malloc，运行阶段不再分配 |
| **限制使用范围** | 仅在非实时、可重试的路径中使用 |
| **检查返回值** | malloc 返回 NULL 时必须处理 |
| **监控堆状态** | 定时检查剩余堆空间 |
| **使用安全分配器** | FreeRTOS 的 `pvPortMalloc`/`vPortFree` 可追踪 |

#### ⑤ 记住什么

- 核心原则：**不是绝对不能用，而是要可控**
- 可控 = 生命周期清晰 + 最大占用可预期 + 失败可处理
- 嵌入式面试的黄金回答：静态分配为主，内存池为辅，动态分配尽量避免

#### 面试常问追问

| 追问 | 回答 |
|------|-------------|
| **malloc(0) 返回什么？** | 实现定义，可能返回 NULL 或有效指针（不能解引用） |
| **FreeRTOS 有几种堆实现？** | heap_1 到 heap_5，heap_1 只分配不释放，heap_4 有合并 |
| **内存碎片怎么解决？** | 定期整理（如果支持）或使用固定大小内存池 |
| **嵌入式 Linux 也要避免动态内存吗？** | 用户态程序可以用，内核驱动要谨慎（GFP 标志、内存池） |

### 第21题：什么是可重入函数？

> **可重入函数 = 多次并发调用时不会互相破坏执行结果，核心是不依赖共享的全局/静态状态。**

#### ① 什么是可重入函数

可重入函数是指函数在执行过程中，即使被再次调用（比如被中断打断后重入），也能安全执行，不会因为共享状态被破坏而产生错误。

| **特征** | 可重入函数 | 不可重入函数 |
|------|-----------|-------------|
| **全局变量** | 不使用或加锁保护 | 直接读写全局变量 |
| **静态局部变量** | 不使用 | 依赖 static 缓冲区 |
| **返回值** | 返回值类型或调用方传入缓冲区 | 返回内部 static 缓冲区地址 |
| **中断安全** | ✅ 可在中断中调用 | ❌ 中断调用可能数据错乱 |

#### ② 不可重入的典型例子

```c
// 不可重入：内部使用 static 缓冲区
char* int_to_str(int val) {
    static char buf[16];          // static 共享缓冲区
    sprintf(buf, "%d", val);      // 写入 static 区域
    return buf;                   // 返回 static 地址
}

// 如果中断里也调用了这个函数，上一次的结果会被覆盖
```

#### ③ 嵌入式中的可重入问题

嵌入式场景下，中断 + 主循环/RTOS 多任务最容易触发可重入问题：

```text
主循环调用 int_to_str(123)
        │
        ▼  中断来了 ──→ 中断里也调用 int_to_str(456) ──→ buf 被覆盖为 "456"
        │
        ▼  中断返回 ──→ 主循环读到的是 "456"，结果出错！
```

#### ④ 如何保证安全

| **方法** | 适用场景 |
|------|---------|
| **不使用全局/static 变量** | 最根本的方法，函数只用局部变量 |
| **互斥锁保护** | 多任务共享资源时 |
| **临界区开关中断** | 中断与主循环共享时 |
| **调用方传入缓冲区** | 避免函数内部 static 缓冲区 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-------------|
| **可重入和线程安全的区别？** | 可重入强调不依赖共享状态，天然线程安全；线程安全可以通过锁实现，但不一定可重入 |
| **中断里能用 malloc 吗？** | 不能，malloc 内部通常有锁/全局状态，不可重入 |
| **printf 是可重入的吗？** | 不是，printf 内部有 static 缓冲区和全局锁 |
| **怎么把不可重入函数变安全？** | 用互斥锁保护、开关中断、或改为调用方传入缓冲区的版本 |

### 第22题：const int *p、int * const p 和 const int * const p 有什么区别？

> **看 const 在 `*` 的左边还是右边——左边修饰指向内容（只读数据），右边修饰指针本身（固定指向）。**

#### ① 三种形式对比

| **声明** | 含义 | 能改 `*p` 吗 | 能改 `p` 吗 | 记忆口诀 |
|------|------|-----------|----------|---------|
| **`const int *p`** | 指向常量的指针 | ❌ 不能 | ✅ 可以 | const 在 `*` 左 → 数据只读 |
| **`int * const p`** | 常量指针 | ✅ 可以 | ❌ 不能 | const 在 `*` 右 → 指针只读 |
| **`const int * const p`** | 指向常量的常量指针 | ❌ 不能 | ❌ 不能 | 两边都 const → 都不能改 |

#### ② 代码示例

```c
int a = 10, b = 20;

const int *p1 = &a;       // p1 指向的内容不能通过 p1 修改
// *p1 = 30;              // ❌ 编译报错：不能修改只读内容
p1 = &b;                  // ✅ 可以改指向

int * const p2 = &a;      // p2 本身不能改指向
*p2 = 30;                 // ✅ 可以修改指向的内容
// p2 = &b;              // ❌ 编译报错：不能修改常量指针

const int * const p3 = &a; // 两个都不能改
// *p3 = 40;              // ❌
// p3 = &b;              // ❌
```

#### ③ 工程中的实际用法

嵌入式开发中非常常见的写法：

| **写法** | 含义 | 典型场景 |
|------|------|---------|
| **`const uint8_t *buf`** | 函数只读取 buf，不修改 | 读取传感器数据、发送缓冲区 |
| **`uint8_t * const reg`** | 固定指向某个寄存器地址 | 外设寄存器映射 |
| **`const uint8_t * const table`** | 固定的只读查找表 | Flash 中的常量表 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-------------|
| **const 在 `*` 左边和右边怎么快速判断？** | const 在 `*` 左边 → 修饰数据（只读）；在 `*` 右边 → 修饰指针（固定指向） |
| **`int const *p` 和 `const int *p` 一样吗？** | 一样，都是指向常量的指针，const 位置可以互换 |
| **为什么函数参数常用 const 指针？** | 表示函数承诺不修改数据，接口语义更清晰，编译器也能帮忙检查 |
| **const 变量一定在 ROM 吗？** | 不一定，const 只是编译期约束，不一定放到只读存储区 |

### 第23题：C 语言中的 struct 和 C++ 中的 class 有什么区别？

> **C 的 struct 只能打包数据；C++ 的 struct 和 class 几乎等价，唯一区别是默认访问权限和默认继承权限不同。**

#### ① C struct vs C++ class vs C++ struct

| **特性** | C struct | C++ struct | C++ class |
|------|----------|-----------|-----------|
| **成员变量** | ✅ | ✅ | ✅ |
| **成员函数** | ❌ | ✅ | ✅ |
| **构造/析构函数** | ❌ | ✅ | ✅ |
| **访问控制 (public/private)** | ❌ | ✅ | ✅ |
| **继承** | ❌ | ✅ | ✅ |
| **虚函数/多态** | ❌ | ✅ | ✅ |
| **默认访问权限** | 无 | **public** | **private** |
| **默认继承权限** | 无 | **public** | **private** |

#### ② 关键区别：默认权限

```cpp
// C++ struct：默认 public
struct Point {
    int x;           // 默认 public
    int y;           // 默认 public
};

// C++ class：默认 private
class Sensor {
    int value;        // 默认 private
public:
    int read();       // 显式声明 public
};

// 默认继承权限
struct Child : Base { };   // 默认 public 继承
class Child : Base { };    // 默认 private 继承
```

#### ③ 工程使用习惯

| **场景** | 推荐用 | 原因 |
|------|--------|------|
| **纯数据聚合（配置、协议帧、坐标）** | struct | 语义明确，所有成员公开 |
| **有封装、有行为的对象** | class | 强调封装，控制访问权限 |
| **C 语言项目的数据结构** | struct | C 没有 class |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-------------|
| **C++ 的 struct 能有成员函数吗？** | 能，C++ struct 和 class 能力基本一致 |
| **struct 和 class 唯一区别是什么？** | 默认访问权限：struct 是 public，class 是 private |
| **什么时候用 struct 什么时候用 class？** | 纯数据用 struct，有封装行为用 class |
| **C 的 struct 能定义函数吗？** | 不能，C struct 只能包含数据成员 |

### 第24题：C 和 C++ 的主要区别是什么？

> **C 是过程式，贴近硬件、直接可控；C++ 在 C 基础上加了面向对象、泛型编程、RAII 等机制，封装能力更强但要注意抽象成本。**

#### ① 核心区别对比

| **特性** | C | C++ |
|------|---|-----|
| **编程范式** | 过程式 | 面向对象 + 泛型 + 过程式 |
| **struct** | 只能包含数据 | 可以有函数、继承、多态 |
| **内存管理** | malloc / free | new / delete + RAII |
| **异常处理** | 无（靠返回值/errno） | try / catch / throw |
| **函数重载** | ❌ | ✅ |
| **模板** | ❌ | ✅（泛型编程） |
| **标准库** | 较少（libc） | 丰富（STL：vector、map 等） |
| **引用 (&)** | ❌ | ✅ |
| **bool 类型** | C99 起有 _Bool | 原生 bool |
| **命名空间** | ❌ | ✅（namespace） |

#### ② 嵌入式中的选择

```text
┌─────────────────────────────────────┐
│           嵌入式项目分层              │
├─────────────────────────────────────┤
│  上层应用 / 业务逻辑  → C++ 封装模块   │
│  算法 / 状态机        → C++ 类管理     │
│  RTOS 任务封装        → C++ 对象       │
├─────────────────────────────────────┤
│  驱动层 / 寄存器操作   → C 直接可控     │
│  启动代码 / 中断向量   → C 贴近硬件     │
│  内核 / Bootloader    → C 简单可预测   │
└─────────────────────────────────────┘
```

#### ③ 回答时的注意事项

| **说法** | ❌ 错误 | ✅ 正确 |
|------|--------|--------|
| **C++ 比 C 高级** | 贬低 C | 两者定位不同，C 更直接可控 |
| **C++ 不能做底层** | 错误 | 可以，但要注意虚函数等开销 |
| **C 不能面向对象** | 不完全对 | 可以用函数指针模拟，只是没语法支持 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-------------|

### 第25题：在 32 位和 64 位系统中，常见类型大小有什么变化？

> **基本整型大小不变，变化最大的是指针——32 位 4 字节，64 位 8 字节；long 大小跟平台有关，不能一概而论。**

#### ① 32 位 vs 64 位类型大小对比

| **类型** | 32 位 (Win/Linux) | 64 位 Windows | 64 位 Linux | 备注 |
|------|-------------------|--------------|-------------|------|
| **char** | 1 | 1 | 1 | 不变 |
| **short** | 2 | 2 | 2 | 不变 |
| **int** | 4 | 4 | 4 | 不变 |
| **long** | **4** | **4** | **8** | ⚠️ 平台相关 |
| **long long** | 8 | 8 | 8 | 通常不变 |
| **float** | 4 | 4 | 4 | 不变 |
| **double** | 8 | 8 | 8 | 不变 |
| **指针** | **4** | **8** | **8** | ⚠️ 变化最大 |

#### ② 最容易踩的坑

```c
// ❌ 错误：64 位系统中指针 8 字节，int 只有 4 字节，地址会截断！
int ptr_val = (int)some_pointer;

// ✅ 正确：用 uintptr_t 保存指针的整数表示
#include <stdint.h>
uintptr_t ptr_val = (uintptr_t)some_pointer;

// ✅ 正确：用 size_t 表示内存大小/长度
size_t len = sizeof(buffer);
```

#### ③ 嵌入式推荐做法

| **做法** | 推荐 | 原因 |
|------|------|------|
| **用 `uint8_t` / `uint16_t` / `uint32_t`** | ✅ 强烈推荐 | 大小固定，跨平台一致 |
| **直接用 int / long** | ❌ 避免 | 大小随平台变化，协议解析可能出错 |
| **指针强转为 int** | ❌ 绝对禁止 | 64 位系统会截断地址 |
| **用 uintptr_t / size_t** | ✅ 推荐 | 大小与指针匹配 |

#### 面试常问追问

| 追问 | 回答 |
|-------------|-------------|
| **64 位系统中 long 一定是 8 字节吗？** | 不是，Windows 64 位下 long 仍是 4 字节，Linux 64 位下是 8 字节 |
| **为什么嵌入式推荐 stdint.h 类型？** | 固定宽度，跨平台一致，避免依赖编译器默认大小 |
| **指针能强转成 int 吗？** | 32 位可以但不推荐，64 位绝对不行——会截断，应用 uintptr_t |
| **size_t 和 int 有什么区别？** | size_t 是无符号的，大小与平台指针宽度一致，int 固定 4 字节 |
