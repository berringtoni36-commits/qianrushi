### 第106题：进程和线程有什么区别？

> **进程是资源分配单位（隔离强），线程是CPU调度单位（共享多）；选型看隔离性和通信需求。**

#### ① 核心对比

| 对比项  | 进程                | 线程                     |
| ---- | ----------------- | ---------------------- |
| 资源分配 | 独立地址空间、文件描述符表     | 共享进程地址空间和大部分资源         |
| 调度单位 | CPU调度的基本单位（传统）    | CPU调度的现代基本单位           |
| 隔离性  | 强（一个进程崩溃不影响其他进程）  | 弱（共享内存，一个线程崩溃可能拖垮整个进程） |
| 通信开销 | 大（需IPC机制如管道、共享内存） | 小（直接读写共享变量）            |
| 切换开销 | 大（需切换页表、TLB刷新）    | 小（同进程内只需切换栈和寄存器）       |
| 典型应用 | 关键服务隔离、嵌入式模块化     | 同进程内并发、数据处理、IO并发       |

#### ② 选型原则

```text
需要隔离性高、一个模块崩溃不影响其他 → 多进程
需要共享数据多、通信频繁、切换开销小 → 多线程
嵌入式Linux：关键服务用多进程，进程内用多线程
```

#### ③ Linux中的特殊点

| 概念              | 说明                              |
| --------------- | ------------------------------- |
| 轻量级进程           | Linux中线程本质是轻量级进程（LWP），共享进程资源    |
| clone()         | 创建线程时用clone()并指定共享标志（CLONE_VM等） |
| /proc/pid/task/ | 每个线程在该目录下有独立子目录                 |

#### 面试常问追问

| 追问                | 回答                                      |
| ----------------- | --------------------------------------- |
| **线程比进程快吗？**      | 创建和切换通常更快（无需切换页表），但不绝对——频繁竞争共享资源时线程可能更慢 |
| **嵌入式用多进程还是多线程？** | 关键服务用多进程隔离（如摄像头、通信模块分离），进程内用多线程处理并发     |
| **线程崩溃会怎样？**      | 默认会拖垮整个进程（收到信号后整个进程退出），除非用信号处理捕获        |

### 第107题：进程间通信方式有哪些？

> **管道适合简单流、消息队列适合结构化消息、共享内存效率最高但需同步、Socket适合跨主机。**

#### ① IPC方式对比

| IPC方式              | 特点             | 适用场景           | 数据拷贝      |
| ------------------ | -------------- | -------------- | --------- |
| 管道（pipe）           | 半双工、字节流、需亲缘关系  | 父子进程简单通信       | 内核缓冲区拷贝   |
| FIFO（有名管道）         | 半双工、有路径名、无亲缘要求 | 无亲缘进程简单通信      | 内核缓冲区拷贝   |
| 消息队列               | 结构化消息、有类型      | 异步消息传递         | 内核消息拷贝    |
| 共享内存               | 效率最高、需同步       | 大数据块（图像、点云）    | 零拷贝（直接映射） |
| 信号                 | 异步通知、信息量少      | 事件通知（SIGCHLD等） | 无数据拷贝     |
| 信号量                | 同步原语、计数器       | 资源计数、互斥        | 无数据拷贝     |
| Socket             | 跨主机、双向         | 网络通信、本机复杂IPC   | 内核缓冲区拷贝   |
| Unix Domain Socket | 本机socket、高效    | 本机复杂IPC、传递fd   | 内核缓冲区拷贝   |
| eventfd            | 事件通知、轻量        | 线程/进程事件通知      | 8字节计数器    |

#### ② 选型决策树

```text
需要跨主机？ → Socket
数据量大（图像/点云）？ → 共享内存 + 互斥锁/信号量
简单父子进程通信？ → 管道
无亲缘进程通信？ → FIFO 或 Unix Domain Socket
异步事件通知？ → 信号 或 eventfd
```

#### 面试常问追问

| 追问              | 回答                               |
| --------------- | -------------------------------- |
| **管道和消息队列的区别？** | 管道是字节流（无消息边界），消息队列有消息边界和类型       |
| **共享内存需要同步吗？**  | 必须！共享内存只解决数据共享，不解决并发同步问题         |
| **信号和信号量的区别？**  | 信号是异步通知机制（如SIGINT），信号量是同步原语（计数器） |

### 第108题：共享内存为什么效率高？需要注意什么？

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/Linux物理内存碎片高频面试题#第 11 题：BPF Map 在这个项目里如何实现内核态 eBPF 和用户态 Python 的数据共享？|内存项目 11：BPF Map 在这个项目里如何实现内核态 eB…]]

> **共享内存快在少拷贝（直接映射物理页），但难在同步和一致性管理。**

#### ① 效率高的原因

```text
传统IPC（管道/消息队列）：
用户空间A → 内核缓冲区 → 用户空间B  （两次拷贝）

共享内存：
用户空间A ←→ 物理内存页 ←→ 用户空间B  （零拷贝，直接映射）
```

| 对比项   | 管道/消息队列      | 共享内存            |
| ----- | ------------ | --------------- |
| 数据拷贝  | 2次（用户→内核→用户） | 0次（直接映射物理页）     |
| 系统调用  | 每次read/write | mmap一次，后续直接读写   |
| 适用数据量 | 小数据          | 大数据块（图像、点云、音视频） |

#### ② 需要注意的问题

| 问题   | 说明                       |
| ---- | ------------------------ |
| 并发同步 | 多进程同时读写会导致数据覆盖、读到半包数据    |
| 一致性  | 写入后需确保其他进程能看到最新数据（缓存一致性） |
| 生命周期 | 共享内存段的创建、销毁、进程异常退出的清理    |
| 数据结构 | 设计好缓冲区长度、读写索引、数据有效标志     |

#### ③ 同步方案

```c
// 共享内存 + 互斥锁典型用法
pthread_mutex_t *mutex = (pthread_mutex_t *)shm_ptr;
char *data = shm_ptr + sizeof(pthread_mutex_t);

pthread_mutex_lock(mutex);    // 加锁
// 读写共享数据
memcpy(data, src, len);
pthread_mutex_unlock(mutex);  // 解锁
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **共享内存为什么还需要同步？** | 共享内存只解决"数据在哪"的问题，不解决"谁能访问"的问题 |
| **嵌入式中共享内存适合什么场景？** | 图像帧、点云、传感器大块数据、音视频缓存等高吞吐场景 |
| **共享内存用什么同步？** | 互斥锁、信号量、原子操作、futex、读写指针+内存屏障 |

### 第109题：互斥锁和自旋锁有什么区别？

> **互斥锁拿不到就睡眠让CPU，自旋锁拿不到就忙等；选型看临界区长短和能否睡眠。**

#### ① 核心对比

| 对比项 | 互斥锁（Mutex） | 自旋锁（Spinlock） |
|--------|----------------|-------------------|
| 拿不到锁时 | 线程睡眠，让出CPU | 忙等（循环检查锁状态） |
| CPU占用 | 睡眠时不占CPU | 等待时一直占CPU |
| 调度开销 | 有（睡眠+唤醒上下文切换） | 无（无上下文切换） |
| 适用临界区 | 长临界区（>1μs） | 短临界区（<1μs） |
| 适用上下文 | 用户态、可睡眠上下文 | 内核态、不可睡眠上下文（如中断） |
| 典型应用 | 用户态多线程、长操作 | 内核短临界区、中断保护 |

#### ② 选型决策

```text
临界区很长（可能阻塞）？ → 互斥锁
临界区很短（几条指令）？ → 自旋锁
当前上下文不能睡眠（中断/内核原子上下文）？ → 自旋锁
用户态应用？ → 通常用互斥锁
```

#### ③ Linux内核中的特殊点

| 场景 | 说明 |
|------|------|
| 中断上下文 | 不能用互斥锁（会睡眠），必须用自旋锁 |
| 自旋锁+中断 | 需要spin_lock_irqsave()禁中断，防止中断中再次获取同一锁 |
| 用户态自旋锁 | futex机制：无竞争时用户态原子操作，有竞争时才进入内核睡眠 |

#### 面试常问追问

| 追问             | 回答                                      |
| -------------- | --------------------------------------- |
| **自旋锁浪费CPU吗？** | 是的，等待期间一直占CPU；但短临界区时比互斥锁的睡眠/唤醒开销小       |
| **用户态能用自旋锁吗？** | 可以（如pthread_spin_lock），但通常用互斥锁+futex更高效 |
| **中断里能用互斥锁吗？** | 不能！互斥锁会睡眠，中断上下文不能睡眠，必须用自旋锁              |

### 第110题：信号量和条件变量有什么区别？

> **信号量自带计数（适合资源池），条件变量只负责等待条件变化（需配合互斥锁和共享变量）。**

#### ① 核心对比

| 对比项  | 信号量（Semaphore）    | 条件变量（Condition Variable） |
| ---- | ----------------- | ------------------------ |
| 内部状态 | 维护计数值             | 无内部状态                    |
| 同步语义 | 资源计数或事件计数         | 等待某个条件变为真                |
| 配合使用 | 独立使用              | 必须配合互斥锁                  |
| 典型场景 | 资源池、生产者消费者、并发限制   | 队列非空、缓冲区不满、状态初始化完成       |
| 唤醒机制 | post增加计数，wait减少计数 | signal/broadcast唤醒等待线程   |
| 虚假唤醒 | 无（计数器明确）          | 有（需用while循环检查条件）         |

#### ② 典型代码对比

```c
// 信号量：生产者消费者
sem_t sem;
sem_init(&sem, 0, 0);      // 初始0个资源
sem_post(&sem);             // 生产者：资源+1
sem_wait(&sem);             // 消费者：资源-1，无资源则阻塞

// 条件变量：队列非空
pthread_mutex_lock(&mutex);
while (queue_empty()) {     // 必须用while，防止虚假唤醒
    pthread_cond_wait(&cond, &mutex);  // 释放锁+睡眠+醒来后重新获取锁
}
// 取数据
pthread_mutex_unlock(&mutex);
```

#### ③ 选型决策

```text
资源池、并发数量限制？ → 信号量（自带计数）
等待某个条件成立（队列非空、状态变化）？ → 条件变量 + 互斥锁
事件通知（发生了几次）？ → 计数信号量
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么条件变量要用while而不是if？** | 可能存在虚假唤醒，也可能多个线程被唤醒后竞争同一个资源 |
| **信号量和互斥量的区别？** | 互斥量是二值的（只有锁/解锁），信号量可以是计数的；互斥量有优先级继承 |
| **条件变量signal和broadcast的区别？** | signal唤醒一个等待线程，broadcast唤醒所有等待线程 |

### 第111题：死锁发生的四个必要条件是什么？如何避免？

> **死锁四条件：互斥、占有且等待、不可抢占、循环等待；避免靠统一加锁顺序和减少锁嵌套。**

#### ① 死锁四条件

| 条件 | 含义 | 示例 |
|------|------|------|
| 互斥 | 资源同一时刻只能被一个线程占用 | 锁被一个线程持有 |
| 占有且等待 | 已持有资源的同时还在等待其他资源 | 线程A持有锁1，等待锁2 |
| 不可抢占 | 资源不能被强制拿走 | 锁只能由持有者主动释放 |
| 循环等待 | 多个线程形成首尾相接的等待关系 | A等B，B等C，C等A |

#### ② 典型死锁场景

```c
// 线程A：先锁1，再锁2
pthread_mutex_lock(&mutex1);
pthread_mutex_lock(&mutex2);  // 死锁！

// 线程B：先锁2，再锁1
pthread_mutex_lock(&mutex2);
pthread_mutex_lock(&mutex1);  // 死锁！
```

#### ③ 避免方法

| 方法 | 说明 |
|------|------|
| 统一加锁顺序 | 所有线程按相同顺序获取多个锁 |
| 减少锁嵌套 | 尽量不同时持有多个锁 |
| 缩小临界区 | 减少持锁时间 |
| trylock | 获取失败时释放已持有的锁后重试 |
| 超时机制 | 设置等待超时，超时后放弃并重试 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **死锁四条件缺一会怎样？** | 缺任何一个条件都不会发生死锁 |
| **嵌入式中死锁常见原因？** | 多个锁获取顺序不一致、中断和任务竞争同一资源 |
| **FreeRTOS如何避免优先级反转导致的死锁？** | 使用互斥量的优先级继承机制 |

### 第112题：虚拟内存和物理内存有什么区别？

> **虚拟内存是进程看到的隔离地址空间（MMU+页表转换），物理内存是真实RAM。**

#### ① 核心对比

| 对比项 | 虚拟内存 | 物理内存 |
|--------|----------|----------|
| 本质 | 操作系统给进程的"假地址" | 真实存在的RAM硬件 |
| 地址空间 | 每个进程独立（4GB/32位） | 所有进程共享 |
| 访问方式 | 通过指针直接访问 | 通过MMU+页表转换 |
| 隔离性 | 强（进程间互不干扰） | 无（共享） |
| 典型应用 | 用户程序malloc、指针操作 | DMA缓冲区、驱动开发 |

#### ② 地址转换流程

```text
用户程序：指针p = 0x12345678（虚拟地址）
    ↓
MMU查页表：虚拟地址 → 物理地址
    ↓
物理RAM：0x87654321（真实地址）
```

#### ③ 嵌入式Linux注意事项

| 场景 | 说明 |
|------|------|
| malloc返回 | 虚拟地址，不是物理地址 |
| DMA缓冲区 | 必须用物理地址或总线地址 |
| mmap映射 | 把设备物理内存映射到用户虚拟空间 |
| 用户态程序 | 不能直接访问物理地址 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么需要虚拟内存？** | 隔离进程、简化内存管理、支持按需分配和换页 |
| **嵌入式中malloc能给DMA用吗？** | 不能！malloc返回虚拟地址，DMA需要物理地址 |
| **如何获取物理地址？** | 内核中用virt_to_phys()，用户态需通过mmap映射 |

### 第113题：malloc返回的是虚拟地址还是物理地址？会立即分配物理页吗？

> **malloc返回虚拟地址，物理页通常在实际访问时才按需分配（惰性分配+COW）。**

#### ① malloc返回什么

```c
void *p = malloc(1024);  // p是虚拟地址，不是物理地址
// CPU访问p时，MMU通过页表转换成物理地址
```

#### ② 惰性分配机制

```text
malloc(1MB) → 只分配虚拟地址范围，不分配物理内存
    ↓
程序访问p[0] → 触发缺页异常
    ↓
内核分配物理页 → 建立页表映射 → 程序继续执行
```

| 阶段 | 说明 |
|------|------|
| malloc时 | 只分配虚拟地址范围（或调整堆管理结构） |
| 首次访问 | 触发缺页异常，内核分配物理页 |
| 物理页分配 | 按需分配，不访问就不分配 |

#### ③ 为什么这样设计

| 原因 | 说明 |
|------|------|
| 节省内存 | 申请但不访问的内存不占物理空间 |
| 提高效率 | 大块内存分配几乎瞬间完成 |
| 支持超额提交 | 进程可申请超过物理内存的虚拟空间 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **malloc返回NULL是什么意思？** | 虚拟地址空间不足或达到限制，不是物理内存不足 |
| **物理内存不足会怎样？** | 访问时触发OOM，进程可能被杀死 |
| **如何避免惰性分配的坑？** | 申请后立即访问（如memset）确保物理页已分配 |

### 第114题：fork和exec有什么区别？

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/linux视觉感知面试题#Q15 Qt、QProcess 和资源监控分别怎么工作？|视觉项目 Q15：Qt、QProcess 和资源监控分别怎么工作]]

> **fork创建新进程（复制地址空间），exec替换当前进程为新程序（PID不变）。**

#### ① 核心对比

| 对比项 | fork | exec |
|--------|------|------|
| 作用 | 创建新进程 | 替换当前进程为新程序 |
| 地址空间 | 复制父进程（写时复制） | 完全替换为新程序 |
| 返回值 | 父进程返回子PID，子进程返回0 | 成功不返回，失败返回-1 |
| PID | 子进程有新PID | PID不变 |
| 典型应用 | shell创建子进程 | 子进程加载并执行新程序 |

#### ② 典型流程

```c
pid_t pid = fork();
if (pid == 0) {
    // 子进程：执行新程序
    execl("/bin/ls", "ls", "-l", NULL);  // 替换为ls命令
    perror("exec failed");  // exec失败才会执行
    exit(1);
} else if (pid > 0) {
    // 父进程：等待子进程
    wait(NULL);
} else {
    perror("fork failed");
}
```

#### ③ 写时复制（COW）

```text
fork后：父子进程共享物理页（只读）
    ↓
某一方写入：触发缺页异常
    ↓
内核复制该物理页：各自拥有独立副本
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **fork后父子进程共享什么？** | 地址空间逻辑独立（COW），文件描述符可能共享内核对象 |
| **exec后原来打开的文件还在吗？** | 默认保留（除非设置FD_CLOEXEC标志） |
| **为什么fork+exec是经典组合？** | fork创建子进程环境，exec加载新程序，shell就是这么工作的 |

### 第115题：用户态和内核态有什么区别？为什么要区分？

> **用户态权限受限（安全隔离），内核态管理硬件资源；系统调用是受控入口。**

#### ① 核心对比

| 对比项 | 用户态 | 内核态 |
|--------|--------|--------|
| 权限级别 | 低（受限） | 高（完整权限） |
| 能访问什么 | 只能访问自己的虚拟空间 | 可以访问所有内存和硬件 |
| 能做什么 | 计算、调用库函数 | 管理进程、内存、文件、设备 |
| 典型代码 | 应用程序（main函数） | 内核代码、驱动、中断处理 |
| 崩溃影响 | 只影响自身进程 | 可能导致系统崩溃 |

#### ② 为什么要区分

```text
如果应用能直接访问硬件：
    一个bug可能破坏整个系统
    ↓
区分用户态/内核态：
    应用出错只影响自身，系统保持稳定
```

| 原因 | 说明 |
|------|------|
| 安全性 | 防止恶意程序破坏系统 |
| 稳定性 | 用户程序崩溃不拖垮内核 |
| 隔离性 | 进程间互不干扰 |

#### ③ 用户态如何进入内核态

| 方式 | 说明 |
|------|------|
| 系统调用 | open、read、write、fork等 |
| 异常 | 缺页异常、除零错误 |
| 中断 | 硬件中断（定时器、网卡等） |

```c
// 系统调用示例
int fd = open("/dev/tty", O_RDWR);  // 用户态 → 内核态
read(fd, buf, 100);                 // 用户态 → 内核态
close(fd);                          // 用户态 → 内核态
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **系统调用和库函数的区别？** | 系统调用进入内核（如read），库函数在用户态（如printf可能内部调用write） |
| **嵌入式中用户态/内核态重要吗？** | 非常重要！应用层和驱动层的边界就是围绕这个机制建立的 |
| **如何减少系统调用次数？** | 使用缓冲（如stdio的缓冲机制）、批量操作 |

### 第116题：select、poll 和 epoll 有什么区别？

> **select/poll/epoll 都是IO多路复用机制，让一个线程同时监听多个fd；select有fd数量限制，poll突破限制但仍线性扫描，epoll注册一次可重复使用适合高并发。**

#### ① 三种机制对比

| 对比项 | select | poll | epoll |
|--------|--------|------|-------|
| fd存储 | 固定大小fd_set（通常1024） | 数组（无固定限制） | 内核红黑树+就绪链表 |
| fd传递 | 每次调用都传入全部fd | 每次调用都传入全部fd | 注册一次，后续只等就绪事件 |
| 就绪检测 | 线性扫描O(n) | 线性扫描O(n) | 回调通知O(1) |
| fd数量限制 | 有（FD_SETSIZE） | 无 | 无 |
| 适用场景 | 少量fd、简单场景 | 少量fd、突破select限制 | 大量fd、高并发 |
| 代码复杂度 | 低 | 低 | 较高 |

#### ② 工作原理

```text
select/poll：
用户态传入fd集合 → 内核遍历检查 → 返回就绪fd → 用户态再遍历找就绪fd

epoll：
epoll_create创建实例
epoll_ctl注册fd（只注册一次）
epoll_wait等待事件 → 直接返回就绪fd列表
```

#### ③ 选型决策

```text
fd数量少（<100）且简单？ → select/poll足够
fd数量多（>1000）或高并发？ → epoll
跨平台兼容性要求？ → select（Windows也支持）
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **epoll一定比select快吗？** | 不一定！少量fd时select可能更快（无注册开销） |
| **epoll的LT和ET模式？** | LT：只要可读就持续通知；ET：只通知一次，需一次性读完 |
| **select为什么有fd数量限制？** | fd_set是位图，FD_SETSIZE通常定义为1024 |

### 第117题：TCP 服务端建立连接需要哪些 socket API？

> **TCP服务端流程：socket()创建套接字 → bind()绑定IP端口 → listen()开始监听 → accept()接受连接返回新套接字。**

#### ① 核心API流程

```c
int sockfd = socket(AF_INET, SOCK_STREAM, 0);  // 创建套接字
bind(sockfd, (struct sockaddr*)&addr, len);      // 绑定地址
listen(sockfd, backlog);                         // 开始监听
int connfd = accept(sockfd, ...);                // 接受连接，返回新套接字
read(connfd, buf, sizeof(buf));                  // 用新套接字收发数据
close(connfd);                                   // 关闭连接套接字
close(sockfd);                                   // 关闭监听套接字
```

#### ② 监听套接字 vs 连接套接字

| 对比项 | 监听套接字(sockfd) | 连接套接字(connfd) |
|--------|-------------------|-------------------|
| 作用 | 只负责accept新连接 | 负责和客户端收发数据 |
| 数量 | 一个 | 每个客户端一个 |
| 何时创建 | socket()时创建 | accept()时创建 |
| 能否收发数据 | 不能 | 能 |

#### ③ 工程注意事项

| 问题 | 说明 |
|------|------|
| SO_REUSEADDR | 服务器重启时避免"Address already in use" |
| backlog | listen的第二个参数，半连接队列大小 |
| 阻塞/非阻塞 | accept默认阻塞，可设为非阻塞配合epoll |
| 多客户端 | 多线程/多进程/IO多路复用 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **listen的backlog是什么？** | 半连接队列大小，内核维护已完成三次握手但未被accept的连接 |
| **accept返回什么？** | 返回新的文件描述符（连接套接字），用于和该客户端通信 |
| **为什么需要两个套接字？** | 监听套接字负责"门卫"，连接套接字负责"服务员"，分离职责 |

### 第118题：阻塞 IO 和非阻塞 IO 有什么区别？

> **阻塞IO：没数据就一直等；非阻塞IO：没数据立即返回EAGAIN。选型看并发量和实时性要求。**

#### ① 核心对比

| 对比项 | 阻塞IO | 非阻塞IO |
|--------|--------|----------|
| 没数据时 | 线程睡眠等待 | 立即返回错误码(EAGAIN) |
| 有数据时 | 返回数据 | 返回数据 |
| 编程模型 | 简单（同步逻辑） | 复杂（需轮询或配合epoll） |
| 适用场景 | 少量连接、简单业务 | 高并发、不能阻塞的场景 |
| CPU占用 | 等待时不占CPU | 轮询时占CPU（配合epoll则不占） |

#### ② 典型代码对比

```c
// 阻塞IO
int n = read(fd, buf, sizeof(buf));  // 没数据时阻塞在这里
if (n > 0) { /* 处理数据 */ }

// 非阻塞IO
int n = read(fd, buf, sizeof(buf));
if (n < 0 && errno == EAGAIN) {
    // 没数据，可以做其他事
} else if (n > 0) {
    // 处理数据
}
```

#### ③ 选型决策

```text
连接数少、业务简单？ → 阻塞IO（多线程处理）
连接数多、高并发？ → 非阻塞IO + epoll
实时性要求高、不能阻塞？ → 非阻塞IO
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **非阻塞IO一定更快吗？** | 不一定！只是避免线程阻塞，真正快靠epoll批量处理 |
| **非阻塞IO怎么知道有数据？** | 配合select/poll/epoll检测fd可读状态 |
| **嵌入式用哪种？** | 通常阻塞IO + 多线程够用；高并发场景才用非阻塞+epoll |

### 第119题：core dump 如何用 GDB 调试？

> **core dump是崩溃时的内存快照，用gdb加载可执行文件和core文件，bt查看调用栈定位崩溃位置。**

#### ① 调试流程

```bash
# 1. 开启core dump
ulimit -c unlimited

# 2. 运行程序，崩溃后生成core文件
./my_program
Segmentation fault (core dumped)

# 3. 用GDB加载
gdb ./my_program core

# 4. 常用命令
(gdb) bt              # 查看调用栈
(gdb) frame 2         # 切换到第2帧
(gdb) info locals     # 查看局部变量
(gdb) p variable      # 打印变量值
(gdb) info threads    # 查看线程列表
(gdb) thread 3        # 切换到线程3
```

#### ② 常用GDB命令

| 命令 | 作用 |
|------|------|
| `bt` | 查看当前调用栈（backtrace） |
| `frame N` | 切换到第N帧 |
| `info locals` | 查看当前帧的局部变量 |
| `p expr` | 打印表达式值 |
| `info threads` | 查看所有线程 |
| `thread N` | 切换到线程N |
| `info registers` | 查看寄存器 |

#### ③ 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 出现大量问号`??` | 缺少调试符号 | 编译时加`-g`，不要strip |
| core文件不匹配 | 可执行文件版本不对 | 保留崩溃时的可执行文件 |
| 没有core文件 | core dump未开启 | `ulimit -c unlimited` |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **core文件太大怎么办？** | 可设置`/proc/sys/kernel/core_pattern`限制大小或路径 |
| **嵌入式设备怎么调试core？** | 把core文件、可执行文件、库拉回开发机，用交叉编译的GDB调试 |
| **段错误一定是空指针吗？** | 不一定！也可能是越界访问、use-after-free、栈溢出 |

### 第120题：Linux 启动流程大致是什么？设备树有什么作用？

> **Linux启动：BootROM → Bootloader → 加载内核+设备树 → 内核初始化 → 挂载根文件系统 → 启动init/systemd。**

#### ① 启动流程

```text
BootROM（芯片固化代码）
    ↓
Bootloader（U-Boot等）
    ├── 初始化DDR、时钟、串口
    ├── 加载内核镜像到内存
    ├── 加载设备树到内存
    └── 跳转到内核入口
    ↓
Linux内核
    ├── 解压内核（如果是压缩镜像）
    ├── 初始化内存管理、调度器、中断
    ├── 解析设备树，初始化驱动
    ├── 挂载根文件系统
    └── 启动init/systemd（PID=1）
    ↓
用户空间
    └── 启动各种服务
```

#### ② 设备树的作用

| 作用 | 说明 |
|------|------|
| 描述硬件 | CPU、内存、GPIO、I2C、SPI、UART、中断、时钟等 |
| 驱动解耦 | 驱动代码不写死板级信息，从设备树读取 |
| 一套驱动多块板 | 不同板子只需不同设备树，驱动代码复用 |

#### ③ 设备树关键属性

| 属性 | 说明 |
|------|------|
| compatible | 驱动匹配依据（"厂商,设备名"） |
| reg | 寄存器地址和大小 |
| interrupts | 中断号 |
| clocks | 时钟引用 |
| pinctrl | 引脚复用配置 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **设备树和驱动怎么匹配？** | 驱动的of_match_table和设备树节点的compatible字符串匹配 |
| **probe函数什么时候调用？** | 设备树节点和驱动匹配成功后，内核自动调用probe |
| **没有设备树会怎样？** | 早期ARM要把板级信息写死在内核代码里，维护困难 |

### 第121题：Linux 进程地址空间通常包含哪些区域？

> **进程地址空间从低到高：代码段 → 数据段 → BSS → 堆 ↑ → 共享库映射 ↓ ← 栈。**

#### ① 地址空间布局

```text
高地址
┌─────────────────┐
│   内核空间        │ ← 用户态不可访问
├─────────────────┤
│   栈（Stack）     │ ← 向下增长，局部变量、返回地址
├─────────────────┤
│   ↓ 空闲区域      │
├─────────────────┤
│   共享库映射      │ ← mmap映射的动态库
├─────────────────┤
│   ↑ 空闲区域      │
├─────────────────┤
│   堆（Heap）      │ ← 向上增长，malloc/new分配
├─────────────────┤
│   BSS段          │ ← 未初始化全局变量（清零）
├─────────────────┤
│   数据段          │ ← 已初始化全局变量
├─────────────────┤
│   代码段(.text)   │ ← 程序指令，只读
└─────────────────┘
低地址
```

#### ② 各区域说明

| 区域 | 存放内容 | 生命周期 | 读写权限 |
|------|----------|----------|----------|
| 代码段 | 程序指令 | 进程生命期 | 只读+执行 |
| 数据段 | 已初始化全局/static变量 | 进程生命期 | 可读写 |
| BSS段 | 未初始化全局/static变量 | 进程生命期 | 可读写 |
| 堆 | malloc/new分配 | 程序员管理 | 可读写 |
| 栈 | 局部变量、返回地址 | 函数调用期 | 可读写 |
| 共享库 | 动态链接库 | 进程生命期 | 只读+执行 |

#### ③ 常见问题

| 问题 | 原因 |
|------|------|
| 段错误(SIGSEGV) | 访问非法地址、空指针、越界 |
| 栈溢出 | 递归太深、局部数组太大 |
| 内存泄漏 | 堆内存未释放 |
| 野指针 | 指向已释放的堆内存 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **栈和堆的区别？** | 栈：系统管理、自动释放、速度快、空间小；堆：手动管理、灵活、速度慢 |
| **BSS和数据段的区别？** | BSS存未初始化变量（不占文件空间），数据段存已初始化变量 |
| **为什么栈向下增长、堆向上增长？** | 历史设计，中间是空闲区域，两边相向增长可最大化利用空间 |

### 第122题：Linux 线程共享哪些资源？哪些资源是私有的？

> [!tip] 🔗 项目关联
> - [[projects/嵌入式八股/1. 项目八股/linux视觉感知面试题#Q06 OpenMP 与 Pthread 有什么区别？为什么采用 4 线程？|视觉项目 Q06：OpenMP 与 Pthread 有什么区别？为…]]

> **线程共享：地址空间、全局变量、堆、文件描述符、信号处理；私有：栈、寄存器、线程ID、errno。**

#### ① 共享 vs 私有

| 共享资源 | 私有资源 |
|----------|----------|
| 虚拟地址空间 | 线程ID |
| 全局变量 | 栈空间 |
| 堆内存 | 寄存器上下文 |
| 文件描述符表 | 程序计数器(PC) |
| 信号处理方式 | 调度状态 |
| 当前工作目录 | errno副本 |
| 用户ID/组ID | 线程局部存储(TLS) |

#### ② 为什么这样设计

```text
共享地址空间 → 线程间通信方便（直接读写共享变量）
共享文件描述符 → 多线程可同时操作同一文件/socket
私有栈 → 每个线程独立的函数调用链
私有寄存器 → 线程切换时保存/恢复上下文
```

#### ③ 工程注意事项

| 问题 | 说明 |
|------|------|
| 数据竞争 | 多线程同时读写共享变量，需互斥锁保护 |
| 线程安全 | 全局变量、静态变量、标准库函数可能不安全 |
| 线程栈大小 | 默认通常8MB，可通过pthread_attr_setstacksize调整 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **线程共享文件描述符有什么风险？** | 多线程同时read/write同一个fd可能数据混乱 |
| **errno为什么是私有的？** | 每个线程可能有不同的系统调用错误，不能互相覆盖 |
| **怎么让变量线程私有？** | 用`__thread`或`pthread_key_create`创建线程局部存储 |

### 第123题：fork 之后父子进程共享哪些内容？哪些内容是独立的？

> **fork后地址空间逻辑独立（COW），文件描述符可能共享内核对象；代码/数据/堆/栈各自独立。**

#### ① 共享 vs 独立

| 独立的 | 可能共享的 |
|--------|-----------|
| 虚拟地址空间（逻辑独立） | 文件描述符→内核打开文件对象 |
| 全局变量（各自副本） | 文件偏移量（共享同一struct file） |
| 堆内存（各自副本） | 内存映射（MAP_SHARED） |
| 栈（各自副本） | |
| 进程ID | |

#### ② 写时复制(COW)

```text
fork后：
父子进程共享物理页（只读）
    ↓
某一方写入：触发缺页异常
    ↓
内核复制该物理页：各自独立
```

#### ③ 文件描述符的特殊性

```c
// fork后文件描述符共享示例
int fd = open("test.txt", O_RDWR);
pid_t pid = fork();
if (pid == 0) {
    write(fd, "hello", 5);  // 子进程写入，偏移量变化
} else {
    wait(NULL);
    // 父进程的fd偏移量也变了！（共享struct file）
    char buf[10];
    read(fd, buf, 10);  // 读不到"hello"，因为偏移量已移动
}
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **fork后父子进程怎么通信？** | 管道、共享内存、socket等IPC机制 |
| **fork后子进程能访问父进程的变量吗？** | 不能！地址空间独立，只能读到fork时刻的值 |
| **为什么fork要COW？** | 避免复制大量内存（子进程可能马上exec加载新程序） |

### 第124题：写时复制 COW 是什么？它解决了什么问题？

> **COW：fork时不立即复制物理页，先共享只读；写入时才触发缺页异常复制。节省内存和时间。**

#### ① COW工作流程

```text
1. fork时：父子进程共享物理页，页表标记为只读
2. 读操作：直接读共享页，无额外开销
3. 写操作：触发缺页异常
   ├── 内核分配新物理页
   ├── 复制原页内容到新页
   ├── 更新页表指向新页（可写）
   └── 程序继续执行
```

#### ② 解决的问题

| 问题 | 没有COW | 有COW |
|------|---------|-------|
| fork开销 | 复制整个地址空间（慢） | 只复制页表（快） |
| 内存占用 | 立即翻倍 | 只在写入时增加 |
| fork+exec | 复制的内存全浪费 | 只复制被修改的页 |

#### ③ 依赖的内核机制

| 机制 | 作用 |
|------|------|
| 页表权限 | 标记只读，写入时触发异常 |
| 物理页引用计数 | 多个进程共享同一物理页 |
| 缺页异常处理 | 检测写只读页，执行复制 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **COW只用于fork吗？** | 主要用于fork，也可用于其他需要延迟复制的场景 |
| **COW有什么缺点？** | 如果fork后父子进程都大量写入，可能触发很多缺页异常 |
| **mmap的MAP_PRIVATE也用COW吗？** | 是的，私有映射修改时也会触发COW |

### 第125题：缺页中断是什么？常见触发场景有哪些？

> **缺页中断是CPU访问虚拟地址时页表无有效映射，触发内核处理。可能是正常按需分配，也可能是非法访问。**

#### ① 缺页中断本质

```text
CPU访问虚拟地址
    ↓
MMU查页表：无有效物理页映射 或 权限不足
    ↓
触发缺页异常（同步异常）
    ↓
内核处理
    ├── 能处理：分配物理页/加载文件页/COW复制 → 程序继续
    └── 不能处理：发送SIGSEGV/SIGBUS → 程序崩溃
```

#### ② 常见触发场景

| 场景 | 说明 | 是否正常 |
|------|------|----------|
| 惰性分配 | malloc后首次访问 | 正常 |
| 文件映射 | mmap后访问未加载的页 | 正常 |
| 写时复制 | fork后写共享页 | 正常 |
| 访问空指针 | 解引用NULL | 异常 |
| 越界访问 | 数组越界 | 异常 |
| 写只读页 | 修改代码段或const变量 | 异常 |
| 栈溢出 | 递归太深触碰栈边界 | 异常 |

#### ③ 内核处理流程

```c
// 伪代码：缺页异常处理
void handle_page_fault(unsigned long addr) {
    // 1. 查找VMA（虚拟内存区域）
    struct vm_area_struct *vma = find_vma(addr);
    if (!vma) goto error;  // 访问非法地址

    // 2. 检查权限
    if (vma权限不足) goto error;

    // 3. 根据VMA类型处理
    if (匿名页) {
        分配物理页，建立映射
    } else if (文件映射) {
        从文件加载页
    } else if (COW) {
        复制物理页，更新页表
    }
    return;

error:
    发送SIGSEGV给进程
}
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **缺页中断是中断吗？** | 更准确说是"同步异常"，由当前指令直接引发 |
| **怎么减少缺页中断？** | 预分配（malloc后立即访问）、mmap预读、大页 |
| **嵌入式有缺页中断吗？** | 有MMU的Linux系统有；无MMU的RTOS通常没有虚拟内存 |

### 第126题：mmap 有什么作用？和 read/write 有什么区别？

> **mmap是地址空间映射接口（直接访问文件页），read/write是流式拷贝接口（经过内核缓冲区）；mmap适合大文件随机访问和共享内存，read/write适合顺序IO。**

#### ① 核心对比

| 对比项 | read/write | mmap |
|--------|------------|------|
| 数据拷贝 | 用户缓冲区 ↔ 内核页缓存（2次拷贝） | 直接访问内核页缓存（0次显式拷贝） |
| 系统调用 | 每次read/write都要系统调用 | 只需mmap一次，后续直接访问内存 |
| 适用场景 | 顺序IO、小数据 | 大文件随机访问、共享内存、设备映射 |
| 编程模型 | 显式read/write | 像访问内存一样读写 |
| 同步机制 | 无（每次调用即完成） | 需要msync刷新脏页 |

#### ② 工作原理

```text
read/write：
文件 → 内核页缓存 → 用户缓冲区（拷贝）
用户缓冲区 → 内核页缓存 → 文件（拷贝）

mmap：
文件 → 内核页缓存 ←→ 用户虚拟地址空间（直接映射）
访问时触发缺页异常，按需加载页面
```

#### ③ 嵌入式Linux应用场景

| 场景 | 推荐方式 |
|------|----------|
| 读写配置文件 | read/write（简单） |
| 大文件随机访问 | mmap（避免重复拷贝） |
| 设备寄存器映射 | mmap（直接访问硬件） |
| 进程间共享内存 | mmap + MAP_SHARED |
| DMA缓冲区映射 | mmap（把内核缓冲区映射到用户态） |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **mmap比read快吗？** | 不一定！顺序读时read可能更高效（预读优化），随机读时mmap优势明显 |
| **mmap的MAP_PRIVATE和MAP_SHARED区别？** | PRIVATE：写时复制（COW），修改不影响文件；SHARED：修改直接写回文件 |
| **mmap需要手动释放吗？** | 需要munmap释放映射，否则进程退出时自动释放 |

### 第127题：管道、有名管道和 Unix Domain Socket 有什么区别？

> **管道：亲缘进程、半双工、字节流；FIFO：无亲缘要求、有路径名；UDS：功能最强、支持双向和传递fd。**

#### ① 核心对比

| 对比项 | 管道(pipe) | 有名管道(FIFO) | Unix Domain Socket |
|--------|------------|----------------|-------------------|
| 亲缘关系 | 必须有（父子进程） | 不需要 | 不需要 |
| 文件系统路径 | 无 | 有（/tmp/fifo） | 有（/tmp/sock） |
| 通信方式 | 半双工（一端读一端写） | 半双工 | 全双工 |
| 数据格式 | 字节流 | 字节流 | 字节流或数据报 |
| 传递fd | 不支持 | 不支持 | 支持 |
| 适用场景 | 父子进程简单通信 | 无亲缘进程简单通信 | 复杂本机IPC |

#### ② 典型用法

```c
// 管道（父子进程）
int pipefd[2];
pipe(pipefd);
if (fork() == 0) {
    write(pipefd[1], "hello", 5);  // 子进程写
} else {
    read(pipefd[0], buf, 5);       // 父进程读
}

// 有名管道
mkfifo("/tmp/myfifo", 0666);
int fd = open("/tmp/myfifo", O_WRONLY);
write(fd, "hello", 5);

// Unix Domain Socket
int fd = socket(AF_UNIX, SOCK_STREAM, 0);
connect(fd, ...);
send(fd, "hello", 5, 0);
```

#### ③ 选型决策

```text
父子进程简单通信？ → pipe
无亲缘进程简单通信？ → FIFO
需要双向通信或传递fd？ → Unix Domain Socket
需要跨主机？ → TCP/UDP Socket
```

#### 面试常问追问

| 追问                   | 回答                                   |
| -------------------- | ------------------------------------ |
| **管道缓冲区多大？**         | 通常64KB（PIPE_BUF），内核维护                |
| **FIFO和管道的读写语义一样吗？** | 一样，都是字节流，没有消息边界                      |
| **UDS为什么能传递fd？**     | 通过sendmsg/recvmsg的辅助数据（SCM_RIGHTS）传递 |

### 第128题：Linux 信号机制是什么？常见信号有哪些？

> **信号是异步通知机制，用于通知进程发生了某类事件；常见信号：SIGINT(Ctrl+C)、SIGTERM(请求退出)、SIGKILL(强制杀死)、SIGSEGV(段错误)。**

#### ① 信号本质

```text
信号是进程间异步通信的一种方式
信号本身只携带信号编号，不携带数据
适合做事件通知，不适合做数据传输
```

#### ② 常见信号

| 信号 | 编号 | 默认动作 | 说明 |
|------|------|----------|------|
| SIGINT | 2 | 终止 | Ctrl+C发送 |
| SIGTERM | 15 | 终止 | kill默认信号，可捕获 |
| SIGKILL | 9 | 终止 | 强制杀死，不可捕获 |
| SIGSEGV | 11 | 终止+core | 段错误（访问非法内存） |
| SIGPIPE | 13 | 终止 | 向已关闭管道/socket写数据 |
| SIGCHLD | 17 | 忽略 | 子进程状态变化通知父进程 |
| SIGALRM | 14 | 终止 | alarm定时器到期 |

#### ③ 信号处理方式

```c
// 1. 默认动作（终止、忽略、core等）
// 2. 忽略信号
signal(SIGINT, SIG_IGN);

// 3. 注册信号处理函数
void handler(int sig) {
    // 只设置标志位，不做复杂逻辑
    flag = 1;
}
signal(SIGINT, handler);
```

#### ④ 工程最佳实践

| 原则 | 说明 |
|------|------|
| 信号处理函数尽量简单 | 只设置标志位或写pipe/eventfd |
| 不调用非异步安全函数 | 不要printf、malloc、mutex_lock |
| SIGKILL不可捕获 | 用于强制杀死失控进程 |
| 用sigaction替代signal | 更可靠，可获取更多信息 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **信号和中断的区别？** | 中断是硬件/内核事件，信号是进程间异步通知 |
| **为什么信号处理函数不能做复杂逻辑？** | 运行在异步上下文，可能打断正常执行流，调用非安全函数会死锁 |
| **SIGTERM和SIGKILL区别？** | TERM可捕获做清理，KILL强制杀死不可捕获 |

### 第129题：守护进程是什么？一般如何创建？

> **守护进程是脱离终端、后台长期运行的进程；创建流程：fork→setsid→再fork→重定向标准IO→进入主循环。**

#### ① 守护进程特点

| 特点 | 说明 |
|------|------|
| 脱离终端 | 不依赖终端交互 |
| 后台运行 | 生命周期长，随系统启动 |
| 日志记录 | 通过syslog或文件记录 |
| 典型应用 | nginx、sshd、crond、syslogd |

#### ② 传统创建流程

```c
// 1. 第一次fork，父进程退出
if (fork() > 0) exit(0);

// 2. 创建新会话，脱离控制终端
setsid();

// 3. 第二次fork，避免重新获得终端
if (fork() > 0) exit(0);

// 4. 修改工作目录
chdir("/");

// 5. 重设文件权限掩码
umask(0);

// 6. 关闭或重定向标准IO
close(STDIN_FILENO);
close(STDOUT_FILENO);
close(STDERR_FILENO);

// 7. 进入主循环
while (1) {
    // 业务逻辑
    syslog(LOG_INFO, "running...");
    sleep(10);
}
```

#### ③ 现代方式（systemd）

```text
# /etc/systemd/system/myapp.service
[Unit]
Description=My Application

[Service]
ExecStart=/usr/bin/myapp
Restart=always
User=nobody

[Install]
WantedBy=multi-user.target
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **为什么fork两次？** | 第一次脱离终端，第二次避免守护进程重新打开终端 |
| **setsid做什么？** | 创建新会话，成为会话首进程，脱离控制终端 |
| **systemd和传统daemon区别？** | systemd自动管理启动、重启、日志、依赖，不需要手写daemon化流程 |

### 第130题：文件描述符是什么？它和 FILE* 有什么区别？

> **文件描述符是内核整数句柄（系统调用层），`FILE*` 是用户态流对象（标准库层，带缓冲）；不要混用 `read/write` 和 `fread/fwrite`。**

#### ① 核心对比

| 对比项 | 文件描述符（fd） | `FILE*` |
|--------|---------------|-------|
| 所在层 | 内核/系统调用 | 用户态/标准库 |
| 类型 | int | 结构体指针 |
| 创建接口 | open/socket/pipe | fopen |
| 读写接口 | read/write | fread/fwrite |
| 缓冲机制 | 无缓冲 | 有用户态缓冲 |
| 适用场景 | socket、epoll、设备文件 | 普通文件格式化读写 |

#### ② 关系

```c
// FILE*内部封装了文件描述符
FILE *fp = fopen("test.txt", "r");
int fd = fileno(fp);  // 获取内部的fd

// fd → FILE*
FILE *fp2 = fdopen(fd, "r");
```

#### ③ 不要混用

```c
// 错误示例：混用导致数据不一致
int fd = open("test.txt", O_RDWR);
FILE *fp = fdopen(fd, "r+");
write(fd, "hello", 5);      // 直接写入内核
fread(buf, 1, 5, fp);        // 从用户缓冲区读，可能读不到"hello"
```

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **文件描述符0/1/2是什么？** | stdin(0)、stdout(1)、stderr(2) |
| **文件描述符有上限吗？** | 有，ulimit -n查看，默认通常1024 |
| **为什么 select/epoll 用 fd 不用 `FILE*`？** | select/epoll 是系统调用，只能操作 fd，不能操作 `FILE*` |

### 第131题：为什么 IO 多路复用适合处理多个连接？

> **IO多路复用让一个线程同时监控多个fd的就绪状态，避免每个连接占一个线程；适合大量连接但不都活跃的场景。**

#### ① 核心问题

传统阻塞IO中，一个线程阻塞在某个socket的read上就无法处理其他连接。为每个连接创建线程，连接数量增大后线程栈内存、上下文切换和调度成本都会明显上升。

#### ② select/poll/epoll 的思路

| 机制 | 特点 |
|------|------|
| select | fd有上限（FD_SETSIZE），每次调用需重新传入fd集合，O(n)扫描 |
| poll | 突破fd数量限制，但仍需线性扫描所有fd |
| epoll | 注册一次，回调通知，只返回就绪的fd，适合高并发 |

应用程序把多个fd交给内核监控，只有某些fd可读/可写/异常时，内核才通知应用程序处理。

#### ③ 工程中的配合

IO多路复用不等于单线程。常见做法：事件循环负责accept/recv/send等IO事件，耗时业务交给线程池处理，避免阻塞事件循环。

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **epoll比select快在哪？** | epoll注册一次回调通知只返回就绪fd，select每次全量扫描 |
| **IO多路复用能提高CPU计算速度吗？** | 不能，它解决的是"一个线程如何等多个IO"的问题 |
| **什么场景不适合IO多路复用？** | 连接少且每个连接都忙的场景，直接多线程更简单 |

### 第132题：epoll 的 LT 和 ET 模式有什么区别？

> **LT条件满足就反复通知（稳妥默认），ET状态变化才通知一次（高性能但要求非阻塞+循环读写）。**

#### ① LT（水平触发）

只要fd上还有数据可读或缓冲区可写，epoll_wait就持续返回这个事件。如果本次没读完，下次还会提醒。**更容易写对**，是默认选择。

#### ② ET（边缘触发）

只在状态变化时通知一次（如从不可读变为可读）。如果通知后没读到EAGAIN，下次不一定再收到事件。要求：

- fd设置为非阻塞
- 收到事件后循环read/write直到返回EAGAIN

#### ③ 对比总结

| 对比项 | LT | ET |
|--------|----|----|
| 触发条件 | 条件满足就通知 | 状态变化才通知 |
| 通知次数 | 多（可能重复） | 少（只通知一次） |
| 编程难度 | 简单 | 高（需非阻塞+循环读写） |
| 性能 | 一般场景够用 | 高并发下减少事件触发次数 |
| 适用场景 | 大多数场景 | 对性能要求高且代码严谨的场景 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **ET模式下不设非阻塞会怎样？** | 循环read可能永远阻塞在最后一次读取上 |
| **ET模式下只读一次会怎样？** | 内核缓冲区还有数据但不会再通知，导致数据丢失 |

### 第133题：epoll 边缘触发模式下如何避免丢事件？

> **fd设非阻塞+收到事件后循环read/write直到EAGAIN；ET难点不在epoll接口，而在状态机和缓冲区管理。**

#### ① 读事件处理

```c
// ET模式读事件处理核心逻辑
while (1) {
    int n = read(fd, buf, sizeof(buf));
    if (n > 0) {
        // 有数据，放入应用层缓冲区
    } else if (n == 0) {
        // 对端关闭连接
        break;
    } else {
        if (errno == EAGAIN) break;  // 数据读完了
        else { perror("read"); break; }  // 真正出错
    }
}
```

#### ② 写事件处理

写也是类似逻辑：持续写到发送缓冲区满或应用层数据全部写完。对于TCP字节流，还需要处理粘包拆包和维护待发送缓冲区。

#### ③ 关键点总结

| 要点 | 说明 |
|------|------|
| 非阻塞fd | 必须设置，否则循环read可能永久阻塞 |
| 循环读到EAGAIN | 确保把内核缓冲区数据全部取出 |
| 处理EPOLLERR/EPOLLHUP | 错误和连接关闭也要正确处理 |
| 应用层缓冲区 | TCP是字节流，需要自己处理消息边界 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **ET和LT能同时注册吗？** | 可以，但实际工程中一般只选一种 |
| **ET模式适合什么场景？** | 连接数极多、每个连接事件频繁的高并发场景 |

### 第134题：零拷贝是什么？常见实现方式有哪些？

> **零拷贝减少用户态/内核态间无效拷贝，让数据尽量在内核路径或DMA路径中完成传输。**

#### ① 传统拷贝的问题

传统文件发送流程：磁盘→内核页缓存→用户缓冲区→内核socket缓冲区→网卡。中间经过用户态的拷贝在很多场景下没有必要。

#### ② 常见零拷贝方式

| 方式 | 原理 | 适用场景 |
|------|------|----------|
| mmap | 文件映射到用户空间，减少显式拷贝 | 大文件随机访问、共享内存 |
| sendfile | 内核中直接从页缓存发送到socket | 静态文件服务器 |
| splice | 在管道和fd之间移动数据 | 内核态数据转发 |

#### ③ 价值与限制

- **价值**：大文件传输、高吞吐网络服务、资源受限设备中减少CPU占用
- **限制**：接口限制、缓存一致性、数据修改不方便、错误处理复杂

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **零拷贝真的没有拷贝吗？** | 不是，是减少用户态/内核态间的无效拷贝，DMA拷贝仍存在 |
| **sendfile和mmap选哪个？** | sendfile适合顺序发送大文件，mmap适合需要随机访问文件内容 |

### 第135题：用户态到内核态一般如何发生切换？

> **系统调用（主动陷入）、异常（缺页/除零）、中断（硬件触发）三种场景统一经由陷入指令进入内核。**

#### ① 三类切换场景

| 场景 | 触发方式 | 典型例子 |
|------|----------|----------|
| 系统调用 | 应用程序主动请求内核服务 | open、read、write、socket |
| 异常 | 当前指令执行中出现特殊情况 | 缺页异常、除零、非法访问 |
| 中断 | 外部硬件设备触发 | 定时器、网卡、串口 |

#### ② 切换过程

用户程序通过特定指令（如ARM的SVC、x86的syscall）陷入内核，CPU切换到内核栈，保存用户态寄存器，跳转到内核入口，执行完后恢复寄存器返回用户态。

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **系统调用开销大吗？** | 相对函数调用较大（切换栈、保存寄存器、权限检查），但通常微秒级 |
| **用户态能直接访问硬件吗？** | 不能，必须通过系统调用或驱动让内核代为访问 |

### 第136题：系统调用和库函数有什么区别？

> [!tip] 🔗 项目关联

> **系统调用进内核（受保护有开销），库函数在用户态运行（快但不一定安全）；printf底层调write。**

#### ① 核心区别

| 对比项 | 系统调用 | 库函数 |
|--------|----------|--------|
| 运行态 | 内核态 | 用户态 |
| 开销 | 大（切换栈+权限检查） | 小（普通函数调用） |

|------|------|
| **printf和write能混用吗？** | 不建议，printf有用户态缓冲，混用可能导致输出顺序混乱 |
| **为什么库函数更快？** | 在用户态完成，不需要陷入内核，且可能带缓冲减少系统调用次数 |

### 第137题：Linux 常见调度策略有哪些？SCHED_OTHER、FIFO、RR 有什么区别？

> **OTHER按nice动态调度（普通进程），FIFO实时抢占先到先跑，RR实时时间片轮转。**

#### ① 三大调度策略

| 策略 | 类型 | 调度方式 | 适用场景 |
|------|------|----------|----------|
| SCHED_OTHER | 普通 | CFS按nice值动态分配时间片 | 大多数普通进程 |
| SCHED_FIFO | 实时 | 先到先服务，不主动让出CPU | 实时任务、硬实时 |
| SCHED_RR | 实时 | 时间片轮转，用完时间片才切换 | 多个同优先级实时任务 |

#### ② 实时 vs 普通

实时进程（FIFO/RR）总是优先于普通进程（OTHER）。如果实时进程不主动让出CPU，普通进程可能饿死。

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **CFS是什么？** | Completely Fair Scheduler，按虚拟运行时间分配CPU |
| **实时进程能抢占普通进程吗？** | 能，实时进程优先级总是高于普通进程 |

### 第138题：nice 值和实时优先级有什么区别？

> **nice影响普通进程（-20~19越大越谦让），实时优先级控制RT进程（数值越大优先级越高）。**

#### ① nice值

范围-20到19，默认0。值越大越"谦让"（优先级越低）。只影响SCHED_OTHER普通进程，由CFS调度器使用。

#### ② 实时优先级

范围1到99，数值越大优先级越高。影响SCHED_FIFO和SCHED_RR实时进程。实时进程总是优先于所有普通进程。

#### ③ 对比

| 对比项 | nice值 | 实时优先级 |
|--------|--------|------------|
| 范围 | -20 ~ 19 | 1 ~ 99 |
| 影响对象 | SCHED_OTHER | SCHED_FIFO/RR |
| 值越大 | 优先级越低 | 优先级越高 |
| 与对方关系 | 实时进程总优先 | 实时进程总优先 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **如何修改nice值？** | nice命令启动或renice修改运行中进程 |
| **嵌入式中什么时候用实时调度？** | 需要严格响应时间的控制任务，如电机控制、数据采集 |

### 第140题：Linux 多线程中栈空间是如何分配的？默认大小一般怎么理解？

### 第141题：pthread_mutex 和 pthread_rwlock 有什么区别？

> **mutex只允许独占访问，rwlock允许多读一写；读多写少场景用rwlock可提升并发。**

#### ① 核心区别

| 对比项 | pthread_mutex | pthread_rwlock |
|--------|---------------|----------------|
| 并发模式 | 独占（互斥） | 多读一写 |
| 读读并发 | 不允许 | 允许 |

- 读写比例接近时用mutex（rwlock内部管理开销更大）
- 读远多于写时用rwlock（读并发提升明显）
- 写操作频繁时mutex可能更优

### 第142题：futex 是什么？它和用户态锁有什么关系？

> **futex是快速用户态互斥基础：无竞争时用户态自旋（快），有竞争才syscall睡眠（省CPU）；pthread_mutex底层用它。**

#### ① 核心原理

| 场景 | 处理方式 |
|------|----------|
| 无竞争 | 用户态CAS操作获取锁，不需要系统调用（快） |
| 有竞争 | 用户态拿不到，syscall进入内核等待队列睡眠（省CPU） |
| 释放锁 | 用户态释放，有等待者时syscall唤醒 |

#### ② 为什么快

大多数情况下锁是无竞争的，futex让用户态直接完成加锁解锁，避免了每次都陷入内核的开销。只有真正有竞争时才付出系统调用的代价。

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **futex是系统调用吗？** | 是，但它只在有竞争时才真正进入内核 |
| **自旋锁和futex锁的区别？** | 自旋锁忙等不睡眠，futex竞争时睡眠让出CPU |

### 第143题：条件变量为什么通常要配合互斥锁使用？

> **防止竞态：先加锁检查条件，不满足则原子释放锁+睡眠，被唤醒后重新加锁再检查。**

#### ① 为什么需要配合

如果不用互斥锁，可能出现：

1. 线程A检查条件不满足，准备等待
2. 线程B此时修改条件并发出信号
3. 线程A才开始等待 → **信号丢失，永远等不到**

#### ② 正确使用模式

```c
// 等待方
pthread_mutex_lock(&mutex);
while (!condition)           // 用while防止虚假唤醒
    pthread_cond_wait(&cond, &mutex);  // 原子：释放锁+睡眠
// 被唤醒后重新持有锁，检查条件
pthread_mutex_unlock(&mutex);

// 通知方
pthread_mutex_lock(&mutex);
condition = 1;
pthread_cond_signal(&cond);  // 唤醒等待者
pthread_mutex_unlock(&mutex);
```

#### ③ 关键点

| 要点 | 说明 |
|------|------|
| while而非if | 防止虚假唤醒（spurious wakeup） |
| cond_wait原子操作 | 释放锁+进入等待是原子的，不会漏信号 |
| 先改条件再signal | 确保等待者被唤醒时条件已满足 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **signal和broadcast区别？** | signal唤醒一个等待者，broadcast唤醒所有等待者 |
| **什么是虚假唤醒？** | 没有signal也可能被唤醒，所以必须用while循环检查条件 |

### 第144题：线程池的作用是什么？设计时需要注意哪些问题？

> **复用线程避免频繁创建销毁开销；控制并发度、削峰填谷的工程工具。**

#### ① 核心组件

| 组件 | 作用 |
|------|------|
| 任务队列 | 存放待执行的任务 |
| 工作线程集合 | 循环从队列取任务执行 |
| 互斥锁+条件变量 | 保护队列、线程间同步 |
| 停止标志 | 控制线程池退出 |

#### ② 基本流程

- 任务提交：放入队列 → 唤醒工作线程
- 工作线程：循环等待任务 → 取到执行 → 继续等
- 销毁：设退出标志 → 唤醒所有线程 → 等待安全退出

#### ③ 设计注意事项

| 问题 | 说明 |
|------|------|
| 任务执行时间 | 不能无限长，否则占满工作线程 |
| 队列容量 | 不能无限增长，否则内存被打爆 |
| 线程数 | CPU密集型接近核心数，IO密集型可适当更多 |
| 异常处理 | 任务异常不能拖垮整个线程池 |
| 优雅退出 | 等待已提交任务完成再退出 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **线程数怎么定？** | CPU密集型≈核心数，IO密集型可以更多，需压测确定 |
| **队列满了怎么办？** | 阻塞等待、丢弃最旧、拒绝新任务、动态扩容 |

> **dmesg偏内核日志，journalctl偏系统服务日志，strace偏系统调用，ltrace偏库函数，perf偏性能热点。**

#### ① 工具对比

| 工具 | 用途 | 典型场景 |
|------|------|----------|
| dmesg | 内核环形缓冲区日志 | 驱动probe失败、USB插拔、OOM killer、内核oops |
| journalctl | systemd系统服务日志 | 服务启动失败、崩溃重启、依赖问题 |
| strace | 跟踪系统调用 | 程序卡在哪个syscall、文件打开失败、网络异常 |
| ltrace | 跟踪用户态库函数调用 | malloc/free调用、动态库加载问题 |
| perf | CPU性能采样分析 | CPU热点函数、调用路径、缓存事件 |

#### ② 使用建议

把工具和使用场景对应起来，比只背工具名更好。比如排查"程序卡住"用strace，排查"CPU高"用perf，排查"驱动加载失败"用dmesg。

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **strace和ltrace哪个更常用？** | strace更常用，因为大多数问题出在系统调用层面 |
| **perf和gprof区别？** | perf是内核级采样（开销小），gprof是编译插桩（需要重新编译） |

### 第150题：Linux 字符设备驱动的大致开发流程是什么？

> **申请设备号→初始化cdev+file_operations→创建设备节点→用户态open/read/write经VFS分发到驱动。**

#### ① 核心链路

```text
用户态: open("/dev/xxx") → 系统调用 → VFS → 驱动file_operations.open
用户态: read/write/ioctl → 系统调用 → VFS → 驱动对应函数
```

#### ② 开发流程

| 步骤 | 说明 |
|------|------|
| 1. 申请设备号 | alloc_chrdev_region（动态）或register_chrdev_region（静态） |
| 2. 初始化cdev | cdev_init绑定file_operations |
| 3. 注册cdev | cdev_add注册到内核 |
| 4. 创建设备节点 | class_create + device_create 让udev自动创建/dev/xxx |
| 5. 实现file_operations | open/read/write/ioctl/release对应具体硬件操作 |

#### ③ 工程扩展

| 要点 | 说明 |
|------|------|
| 设备树匹配 | platform_driver + compatible匹配 |
| probe/remove | 设备发现和移除时的初始化/清理 |
| 并发访问 | 互斥锁/自旋锁保护共享资源 |
| 用户态数据交互 | copy_to_user / copy_from_user |
| 电源管理 | suspend/resume回调 |

#### 面试常问追问

| 追问 | 回答 |
|------|------|
| **字符设备和块设备区别？** | 字符设备按字节流访问（串口/GPIO），块设备按块访问（磁盘/Flash） |
| **设备号由什么组成？** | 主设备号（驱动类型）+次设备号（具体设备实例） |
| **不写驱动怎么访问硬件？** | mmap直接映射寄存器地址（简单GPIO测试常用） |
