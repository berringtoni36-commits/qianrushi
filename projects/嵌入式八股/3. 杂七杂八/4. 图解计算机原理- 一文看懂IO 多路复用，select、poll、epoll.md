# 图解计算机原理: 一文看懂IO 多路复用，select、poll、epoll

> [!info] 原文信息
> 公众号：IT技术小密圈
> 发布时间：2026年6月25日 08:09
> 原文：[微信公众号文章](https://mp.weixin.qq.com/s/Cvd4I7gNw5fR2bADYcOhEg)

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-001.png]]

很多人第一次学 `select`、`poll`、`epoll`，最容易卡在一个地方：

这三个东西看起来都在“等 socket”，为什么还要分这么多种？

更让人迷糊的是，面试里经常会追问：

- `select`为什么有 fd 数量限制？
- `poll`已经改成数组了，为什么还是慢？
- `epoll`到底快在哪里？
- `epoll`是不是永远比 `select`、`poll`快？
- LT 和 ET 为什么会把连接写卡住？

这篇文章从服务器如何同时处理大量连接开始，一层一层拆解一个线程如何高效等待多个 IO 事件。

## 01 一个服务器为什么不能傻等一个连接？

先看一个最普通的 TCP 服务器。

客户端连上来后，服务端拿到一个 socket，然后调用 `read()`读数据。

如果这个 socket 暂时没有数据，在阻塞模式下，线程就会睡眠。

问题来了：服务器不可能只服务一个连接。

如果有 1 万个客户端同时在线，线程卡在其中一个 socket 上，其他连接怎么办？

常见做法有三种。

第一种：一个线程阻塞等待一个 socket。

写起来简单，但一个线程只能盯一个连接。连接多了，线程数量、栈内存、调度成本都会涨上去。

第二种：一个连接配一个线程。

少量连接时没问题。连接规模扩大后，线程本身会变成系统负担。

第三种：一个线程等待多个 socket。

线程把多个 fd 交给内核，自己睡眠。哪个 fd 可读、可写、出错，内核再把线程叫醒。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-002.png]]

IO 多路复用的核心，不是“一个线程把所有数据都读完”，而是：

> 一个线程可以同时等待多个 fd，等其中某些 fd 准备好了，再去处理它们。

注意这里的关键词是“准备好了”。

IO 多路复用只告诉你：这个 fd 现在大概率可以读、可以写，或者发生了异常。

真正的 `read()`、`write()`还是应用程序自己做。

## 02 IO 多路复用到底在复用什么？

“IO 多路复用”这个名字很容易误导人。

它复用的不是网络连接，也不是数据包。

它复用的是：

> 一个线程等待多个 IO 事件的能力。

在 Linux 里，socket、文件、管道等对象都可以用文件描述符表示，也就是 fd。

应用程序看到的是 fd。

内核里真正对应的是 socket 对象、文件对象、管道对象。

对网络服务器来说，最常见的就是 socket fd。

一个 socket 是否“就绪”，通常看几个状态：

- 可读：接收缓冲区里有数据，调用 `read()`不会一直等。
- 可写：发送缓冲区还有空间，调用 `write()`有机会写进去。
- 异常：连接关闭、错误、带外数据等情况。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-003.png]]

所以，`select`、`poll`、`epoll`做的事情可以先简化成一句话：

> 应用把一批 fd 告诉内核，内核帮忙等待这些 fd 的状态变化。

区别在于：这批 fd 怎么传？内核怎么管理？就绪后怎么返回？

这三个问题，正好对应 `select`、`poll`、`epoll`的演进。

## 03 select：每次都把 fd 集合交给内核

`select`是比较早的 IO 多路复用方案。

它的使用方式可以理解为：

应用准备几个 fd 集合，分别表示：

- 关心哪些 fd 可读。
- 关心哪些 fd 可写。
- 关心哪些 fd 出现异常。

然后调用 `select`，把这些集合交给内核。

内核开始检查：

这批 fd 里，有没有已经准备好的？

如果没有，当前线程就睡眠。

如果有 fd 就绪，线程被唤醒，`select`返回。

但事情还没结束。

`select`只会告诉应用：“有几个 fd 就绪了。”

具体是哪几个 fd，就需要应用再遍历一遍集合找出来。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-004.png]]

`select`的成本主要在三处。

第一，每次调用都要重新准备 fd 集合。

因为 `select`会修改传入的集合，把未就绪的 fd 清掉。下一轮循环前，应用通常要重新设置关注集合。

第二，每次调用都要在用户态和内核态之间传递集合。

fd 集合在应用进程里，内核要检查，就要把这部分信息拿到内核侧处理。

第三，内核要线性扫描。

如果你传了 10000 个 fd，只有 3 个有数据，内核仍然要检查这 10000 个 fd。

返回之后，应用还要再扫一遍，找出真正就绪的 fd。

### select 的 fd_set 是什么？

`select`常用 `fd_set`表示 fd 集合。

它可以粗略理解成一个位图：

- 某一位是 1，表示关注这个 fd。
- 某一位是 0，表示不关注这个 fd。

比如第 3 位是 1，就表示关注 fd=3。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-005.png]]

这带来一个很出名的问题：fd 数量限制。

在很多系统和库实现里，`fd_set`会受 `FD_SETSIZE`影响，常见默认值是 1024。

这不是说操作系统只能打开 1024 个 fd，而是 `select`这套位图表达方式通常不适合表示更大的 fd 集合。

因此，`select`的问题可以总结为：

- fd 集合表达能力有限。
- 每次都要重新提交集合。
- 内核每次都要扫描。
- 返回后应用还要扫描。

它能用，但面对大量连接时，成本会变得明显。

## 04 poll：换成数组，但仍然要全量扫描

`poll`看起来像是 `select`的升级版。

最大的变化是：不再使用 `fd_set`位图，而是使用 `pollfd`数组。

每个 `pollfd`结构可以表达三类信息：

- `fd`：要监听哪个文件描述符。
- `events`：应用关心什么事件，比如可读、可写。
- `revents`：内核返回实际发生了什么事件。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-006.png]]

这个设计比 `select`的位图灵活。

因为数组天然可以增长，不再受固定大小位图的表达限制。真正能监听多少 fd，更多取决于内存、进程 fd 上限、系统资源等因素。

但 `poll`没有解决最关键的问题。

每次调用 `poll`，应用还是要把整个 `pollfd`数组交给内核。

内核还是要从头到尾扫描数组。

返回后，应用还是要遍历数组，检查每个元素的 `revents`字段，找出真正就绪的 fd。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-007.png]]

这就解释了为什么很多资料会说：

> poll 解决了 select 的 fd 集合表达问题，但没有解决“大量 fd 下反复扫描”的问题。

假设有 10000 个连接，只有 10 个连接有数据。

`poll`仍然要检查整个数组。

这类场景下，性能消耗和 fd 总数强相关，而不是只和真正活跃的连接数量相关。

## 05 epoll：从“每次提交 fd”变成“提前注册 fd”

`epoll`的关键变化，不是名字更高级，也不是把数组换成另一种数组。

它改变的是使用模型。

`select`和 `poll`是每一轮都问内核：

> 这批 fd 里，谁准备好了？

`epoll`的做法是：

> 这些 fd 你先记住，以后谁准备好了，再放到就绪队列里通知我。

这就是“每次提交 fd”到“提前注册 fd”的变化。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-008.png]]

`epoll`主要有三个 API。

`epoll_create`：创建一个 epoll 实例。

你可以把它理解成在内核里创建一个事件管理对象。

`epoll_ctl`：往这个 epoll 实例里注册、修改、删除 fd。

比如把 fd=8 注册进去，并告诉内核：我关心它的可读事件。

`epoll_wait`：等待就绪事件。

如果没有事件，线程睡眠；如果有事件，返回一批已经就绪的事件。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-009.png]]

这就是 `epoll`写法和 `select`、`poll`最大的差别。

`select`、`poll`的事件循环里，每轮都要提交全量 fd。

`epoll`是连接建立时注册一次，事件循环里反复调用 `epoll_wait`。

fd 关注关系长期保存在内核中。

## 06 epoll 实现原理：监听集合 + 就绪队列

理解 `epoll`，抓住两个结构就够了：

- 监听集合：保存当前 epoll 实例关注了哪些 fd，以及每个 fd 关注什么事件。
- 就绪队列：保存已经准备好的事件，`epoll_wait`从这里取结果。

在 Linux 的常见实现里，epoll 实例对应内核里的 `eventpoll`对象。

它会维护关注关系，也会维护就绪事件列表。

很多资料会提到“红黑树 + 就绪链表”。

可以这样理解：

- 红黑树这类结构负责组织已经注册的 fd，方便增删改查。
- 就绪链表负责保存已经发生的事件，方便 `epoll_wait`直接拿结果。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-010.png]]

那 socket 数据到达时，事件是怎么进入就绪队列的？

可以按这个流程理解。

第一步，应用通过 `epoll_ctl`把 socket fd 注册到 epoll 实例。

第二步，内核把这个 fd 和它关心的事件记录下来，并和 socket 的等待队列建立关系。

第三步，网卡收到数据，内核协议栈处理后，把数据放入 socket 接收缓冲区。

第四步，socket 状态变成可读。

第五步，内核触发回调，把这个 fd 对应的事件放入 epoll 的就绪队列。

第六步，正在 `epoll_wait`睡眠的线程被唤醒，拿到就绪事件数组。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-011.png]]

这里有一个重要点：

`epoll`不是“完全不用检查 fd”。

内核仍然要维护 fd 关注关系，仍然要处理 socket 状态变化，仍然要管理事件队列。

它的优势在于：

> 避免了 select/poll 每次调用都全量提交、全量扫描的固定成本。

所以严格来说，不要简单说 `epoll`一定是 O(1)。

更准确的说法是：

> epoll 把 fd 关注关系留在内核里，通过就绪队列返回已经发生的事件，更适合大量连接场景。

## 07 LT 和 ET：为什么 epoll 还有两种触发模式？

学 `epoll`绕不开两个词：LT 和 ET。

LT 是 Level Triggered，水平触发。

ET 是 Edge Triggered，边缘触发。

它们不是两个不同的 epoll，而是事件通知策略不同。

### LT：只要还有数据，就继续通知

LT 是默认模式。

假设 socket 接收缓冲区里来了 100KB 数据。

`epoll_wait`通知应用：这个 fd 可读。

应用这次只读了 20KB，缓冲区里还剩 80KB。

在 LT 模式下，下次调用 `epoll_wait`时，只要缓冲区里还有数据，它还会继续通知。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-012.png]]

LT 的好处是容易写对。

你这次没读完，下次还会提醒。

代价是通知次数可能更多。

### ET：只在状态变化时通知一次

ET 模式更像是在提醒你：

“刚才这个 fd 从不可读变成可读了。”

如果你收到通知后只读了一部分数据，缓冲区里还剩数据，但 fd 状态一直是“可读”，没有再次发生从不可读到可读的变化。

这时，下一轮可能不会再次通知。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-013.png]]

所以 ET 通常要配合非阻塞 IO。

标准写法是：

收到可读通知后，循环读取。

一直读到 `read()`返回 `EAGAIN`或 `EWOULDBLOCK`，说明当前缓冲区暂时读空了。

如果只读一次就返回，连接可能会卡住。

这也是很多线上 bug 的来源：代码看起来收到了 epoll 通知，但数据没读干净，后面却再也等不到通知。

## 08 select、poll、epoll 全面对比

把三者放在一起，对比就很清楚了。

`select`的核心是位图。

应用每次提交 fd 集合，内核扫描，返回后应用再扫描。

`poll`的核心是数组。

它比位图更灵活，但仍然每轮提交整个数组，内核也仍然线性扫描。

`epoll`的核心是注册和就绪队列。

fd 关注关系先留在内核里，事件就绪后进入 ready list，`epoll_wait`返回就绪事件数组。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-014.png]]

再用一张表总结。

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| fd 表达方式 | `fd_set`位图 | `pollfd`数组 | 内核事件表 |
| 每次是否传全部 fd | 是 | 是 | 否，fd 先注册 |
| 内核是否线性扫描 | 是 | 是 | 避免每轮固定全量扫描 |
| 返回后应用是否再扫描 | 通常需要 | 通常需要 | 直接拿就绪事件数组 |
| fd 数量限制 | 常受 `FD_SETSIZE`影响 | 更灵活，受资源限制 | 适合大量 fd |
| 就绪事件来源 | 扫描结果 | 扫描结果 | 就绪队列 |
| 典型场景 | 少量 fd、兼容性场景 | 中等 fd、跨平台场景 | 高并发网络服务 |

如果只背“epoll 比 select 快”，面试官继续追问时，很容易说空。

更好的回答是：

> select 和 poll 的成本主要来自每轮全量提交、全量扫描；epoll 把关注关系放在内核里，事件就绪后进入就绪队列，减少了大量连接下每轮固定扫描的成本。

## 09 epoll 一定比 select、poll 快吗？

不一定。

要看 fd 数量、活跃比例和业务处理成本。

### fd 很少时

如果只有几十个 fd，`select`、`poll`的扫描成本很低。

这时 `epoll`的注册、维护事件表、回调管理，也不是完全没有成本。

所以少量 fd 场景下，`epoll`未必有明显优势。

### 连接很多，但活跃连接少

这是 `epoll`最舒服的场景。

比如 10000 个连接在线，但同一时间只有几十个连接有数据。

`select`、`poll`每轮仍然要看大量 fd。

`epoll_wait`则主要返回已经就绪的事件。

### 连接很多，而且大部分都很活跃

这时事件等待未必是最大瓶颈。

真正拖慢系统的可能是：

- 业务处理太慢。
- 用户态和内核态数据拷贝。
- 网络带宽打满。
- 多线程锁竞争。
- 应用层协议解析成本。

![[assets/embedded-interview/图解计算机原理- 一文看懂IO 多路复用，select、poll、epoll/img-015.png]]

所以，`epoll`的合理结论是：

> 它非常适合大量连接、活跃连接相对较少的高并发网络服务，但不是所有场景无脑最快。

这也是为什么 Nginx、Redis 这类高并发网络程序，在 Linux 上会使用 `epoll`作为重要的事件通知机制。

## 10 一张图总结：从 select 到 epoll 的演进

最后把整条线串起来。

`select`解决了一个线程等待多个 fd 的问题。

但它用位图表达 fd 集合，每轮都要提交集合，内核要扫，应用也要扫。

`poll`把位图换成数组。

fd 表达更灵活，但每轮全量提交、全量扫描的问题还在。

`epoll`把 fd 关注关系提前注册到内核。

socket 状态变化后，事件进入就绪队列。

`epoll_wait`直接返回就绪事件数组。
