## 一、理解嵌入式内存的"家底"

在动手优化之前，我们得先知道自己手里有什么牌。嵌入式系统的内存不像PC那样"内存就是内存"，它的架构要复杂很多。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-001.jpg]]

#### 1.1 RAM的分类与特性

嵌入式系统里常见的RAM有三种：SRAM、DRAM和PSRAM。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-002.jpg]]

**SRAM（静态随机存取存储器）是嵌入式MCU的主力。** 它不需要像 DRAM 那样周期性刷新，延迟低，接口也更适合处理器直接访问。**任务栈、中断栈、控制变量、实时数据和高频访问的代码，通常应该优先放在内部 SRAM。**

SRAM 的问题就是贵，占芯片面积。

芯片厂商不会无限给。产品经理倒是很愿意无限加需求，这两个趋势经常正面相撞。

**DRAM 和 SDRAM 容量大、单位成本低，常见于带外部存储控制器的高性能 MCU、MPU 和嵌入式 Linux 平台。它们适合放帧缓冲、大数组、模型参数、文件缓存和图像数据。**

但是初始化更复杂，访问延迟更高，需要刷新，PCB 走线也更讲究。部分平台还会引入 Cache，**一旦 Cache 和 DMA 同时操作同一片缓冲区，事情就开始变得刺激了。**

PSRAM 可以理解为对外提供近似 SRAM 接口、内部采用 DRAM 单元实现的一类存储器。它在 IoT、图形显示和摄像头设备中很常见，尤其适合通过 SPI、QSPI 或 Octal SPI 扩展容量。

PSRAM 的容量看着很香，速度却未必能和内部 SRAM 相提并论。**别把高频中断数据、关键控制环变量和所有任务栈一股脑扔进去。** 能跑是能跑，抖动可能也真的夯爆了。

一个比较实用的放置思路是这样的：

**内部 SRAM 留给栈、控制数据、DMA 描述符和高频访问对象。外部 SDRAM 或 PSRAM 放大块、低频、可容忍延迟的数据。只读模型、字库和资源文件优先放在 Flash，需要高速计算时再按需搬到 RAM。**

#### 1.2 非易失性存储：Flash与XIP（就地执行）技术

Flash 断电后仍能保存内容，因此**固件代码、常量表、配置默认值和只读资源通常都放在 Flash 中。**

很多 MCU 支持直接从内部 Flash 取指执行。外接 QSPI NOR Flash 的系统还可能使用 XIP，也就是 Execute In Place，**让 CPU 通过映射窗口直接执行外部 Flash 中的代码，不必先把整段程序搬进 RAM。**

XIP 能节省宝贵的 RAM，也能减少启动阶段的整体复制量。不过它并不免费。

外部 Flash 的访问延迟通常比内部 SRAM 高。顺序取指配合预取和 Cache 时，性能可能还不错。**一旦频繁跳转、Cache 未命中或 Flash 总线同时承担资源读取，执行时间就可能抖起来。**

还有一个经常被忽略的问题。

**就是Flash 在擦除或编程期间，某些芯片无法继续从同一个 Flash Bank 取指。** 假如固件升级代码、参数写入代码和中断处理程序都在这片 Flash 中执行，写 Flash 时就可能卡住甚至跑飞。

因此，**Flash 操作例程和关键中断可以放到 RAM 中执行。**

```
#if defined(__GNUC__)#define RAM_FUNC __attribute__((section(".ramfunc"), noinline))#else#define RAM_FUNC#endifRAM_FUNC void flash_program_page(uint32_t address,                                 const uint8_t *data,                                 size_t length){    flash_unlock();    flash_clear_status();    for (size_t i = 0; i < length; i += 8U) {        uint64_t value = 0;        memcpy(&value, &data[i], sizeof(value));        flash_program_double_word(address + i, value);    }    flash_lock();}
```

链接脚本里还要明确这段代码的加载地址和运行地址。

```
.ramfunc :{    . = ALIGN(4);    __ramfunc_start__ = .;    *(.ramfunc)    *(.ramfunc*)    . = ALIGN(4);    __ramfunc_end__ = .;} >RAM AT>FLASH__ramfunc_load__ = LOADADDR(.ramfunc);
```

**启动时把 `.ramfunc` 从 Flash 复制到 RAM。** 少了这一步，链接看着没问题，运行时却可能跳到一片空白区域。这个坑我见过不止一次，真的，调试器单步进去以后全是 `0xFFFFFFFF`，人会突然安静。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-003.jpg]]

#### 1.3 内存映射（Memory Map）：代码区、数据区、外设寄存器

嵌入式处理器通常把 Flash、RAM、外设寄存器和系统控制空间映射到统一地址空间。**程序通过普通的读写指令访问它们，只是不同地址背后连接着不同硬件。**

一个简化后的内存映射可能长这样：

```
0x0000_0000 ─────────────────────────             启动映射区或代码别名区0x0800_0000 ─────────────────────────             内部 Flash             .isr_vector             .text             .rodata0x2000_0000 ─────────────────────────             内部 SRAM             .data             .bss             heap             task stacks0x6000_0000 ─────────────────────────             外部 SRAM、SDRAM 或 QSPI 映射区0x4000_0000 ─────────────────────────             外设寄存器             GPIO、UART、SPI、DMA、定时器0xE000_0000 ─────────────────────────             Cortex-M 系统控制空间             NVIC、SysTick、MPU、调试组件
```

**你遇到 HardFault 时，故障地址落在 `0x200xxxxx`，往往意味着 SRAM 访问异常。落在 `0x400xxxxx`，可能是外设地址、时钟或权限问题。落在奇怪的 `0xDEADBEEF`，那多半是调试填充值终于抓到现行了。**

**链接脚本决定代码和数据最终放在哪里**，下面是一段简化示例：

```
MEMORY{    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K    SRAM1 (xrw) : ORIGIN = 0x20000000, LENGTH = 192K    SRAM2 (xrw) : ORIGIN = 0x20030000, LENGTH = 64K}SECTIONS{    .text :    {        KEEP(*(.isr_vector))        *(.text*)        *(.rodata*)    } > FLASH    .data :    {        _sdata = .;        *(.data*)        _edata = .;    } > SRAM1 AT> FLASH    .bss (NOLOAD) :    {        _sbss = .;        *(.bss*)        *(COMMON)        _ebss = .;    } > SRAM1    .dma_buffer (NOLOAD) :    {        . = ALIGN(32);        *(.dma_buffer*)        . = ALIGN(32);    } > SRAM2}
```

**我建议每个嵌入式开发者都至少能看懂自己项目的链接脚本。** 不会写完整版本没关系，但得知道 `.text`、`.data`、`.bss`、堆和栈去了哪。

否则你连家底都没盘清楚，就开始谈优化，多少有点空中阁楼。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-004.jpg]]

#### 1.4 嵌入式C语言的内存布局：栈、堆、全局区、常量区

C 程序编译完成后，常见数据大致分布在几个区域。

`.text` 保存机器指令，通常位于 Flash。

`.rodata` 保存只读常量、字符串常量和只读查找表，也通常位于 Flash。

`.data` 保存带非零初始值的全局变量和静态变量。**它们的初始内容存放在 Flash，启动时复制到 RAM。**

`.bss` 保存初始值为零或未显式初始化的全局变量和静态变量。启动时不用从 Flash 复制大量零，只需要把对应 RAM 区域清零。

**栈保存函数调用现场、返回地址、部分局部变量和寄存器。RTOS 环境中，每个任务通常有自己的任务栈，中断还可能使用单独的主栈。**

堆则用于运行时动态分配。

```
const uint8_t gamma_table[256] = { /* 位于只读区 */ };uint32_t boot_count = 1;      /* 位于 .data */static uint8_t rx_cache[512]; /* 位于 .bss */void process_frame(void){    uint8_t header[32];       /* 通常位于栈 */    uint8_t *frame;    frame = malloc(4096);     /* 指向堆上的对象 */    if (frame == NULL) {        return;    }    memset(header, 0, sizeof(header));    free(frame);}
```

局部变量并不意味着一定在栈上。编译器可能把它放进寄存器，也可能优化掉。**大数组、取过地址的变量和复杂调用现场更容易占用栈空间。**

还有一个常见误区：

**`static` 变量不是"放在静态内存里就一定安全"。** 它只是生命周期贯穿整个程序，通常位于 `.data` 或 `.bss`。如果多个任务同时访问它，照样会发生竞态。

内存位置解决不了并发问题。别让一个关键字背太多锅。

# 10大内存管理策略精讲

## 二、策略一：静态内存分配

### 2.1 什么是静态分配：编译链接阶段确定一切

**静态内存分配意味着对象的存储空间在编译和链接阶段就已经确定，运行时不再从通用堆中申请。**

全局数组、静态变量、固定任务栈、静态队列控制块和预分配缓冲区都属于这类思路。

```
#define UART_RX_SIZE 512U#define LOG_QUEUE_LEN 16Ustatic uint8_t uart_rx_buffer[UART_RX_SIZE];static LogMessage log_queue_storage[LOG_QUEUE_LEN];static volatile uint32_t log_write_index;static volatile uint32_t log_read_index;
```

在 FreeRTOS 中，也可以让应用直接提供任务控制块和栈空间。

```
#define SENSOR_TASK_STACK_DEPTH 512Ustatic StaticTask_t sensor_task_tcb;static StackType_t sensor_task_stack[SENSOR_TASK_STACK_DEPTH];static void sensor_task(void *argument){    (void)argument;    for (;;) {        sensor_sample();        vTaskDelay(pdMS_TO_TICKS(10));    }}void create_sensor_task(void){    TaskHandle_t handle;    handle = xTaskCreateStatic(        sensor_task,        "sensor",        SENSOR_TASK_STACK_DEPTH,        NULL,        4,        sensor_task_stack,        &sensor_task_tcb    );    configASSERT(handle != NULL);}
```

FreeRTOS 官方提供静态创建接口。**启用 `configSUPPORT_STATIC_ALLOCATION` 后，任务、队列、信号量和软件定时器等对象可以使用应用提供的内存，而不必依赖 FreeRTOS 堆。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-006.jpg]]

### 2.2 优势：零运行时开销、零碎片、100%可靠

静态分配最大的价值不是省下几次函数调用，而是确定。

**对象是否有空间，在链接阶段基本就能知道。运行时不会突然因为堆不足而创建失败，也不会因为反复分配释放形成外部碎片。**

分配动作本身几乎没有运行时成本。地址固定，调试方便，内存地图也清楚。

但"100% 可靠"这句话得带条件。

**静态分配能保证空间不会因为堆碎片突然消失，却不能保证你不会数组越界、栈溢出或并发踩内存。** 拿到一套固定车位，不代表你停车时不会撞墙。

因此，更准确的说法是，**静态分配为容量和时序提供了高度确定性。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-007.jpg]]

### 2.3 局限：灵活性差、需按最坏情况规划

静态分配的问题也很明显。

**所有资源通常按最坏情况预留。** 某个通信通道平时只需要 256 字节，极端情况下需要 4KB，你为了不在极端情况下挂掉，可能只能长期预留 4KB。

十个通道都这么干，RAM 很快就没了。

静态数组的数量和尺寸还难以动态调整。产品新增功能、协议包长度变化或任务数量改变，都可能要求重新评估整体布局。

这也是为什么"全静态"并不是任何项目的唯一答案。资源特别紧张、业务负载变化明显时，我们还需要内存池和受控动态分配。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-008.jpg]]

#### 2.4 实践建议：安全关键系统应默认选择静态分配

**在电机控制、医疗设备、汽车控制器和工业保护装置中，我更愿意把静态分配作为默认方案，再对确有必要的部分开放受控动态分配。**

**任务、队列、信号量、长期存在的设备对象和关键通信缓冲区，都适合静态创建。**

系统初始化完成后，甚至可以禁止继续创建对象。

```
static bool system_started;void *safe_alloc(size_t size){    if (system_started) {        system_fault(FAULT_RUNTIME_ALLOCATION);        return NULL;    }    return pvPortMalloc(size);}void system_mark_started(void){    system_started = true;}
```

这个做法有点"狠"。

**可安全关键系统本来就不该在运行到第十八天时，突然心血来潮创建一个新任务。系统需要哪些资源，最好在启动阶段就讲清楚。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-009.jpg]]

## 三、策略二：内存池（Memory Pool）

### 3.1 内存池的工作原理：预分配+空闲链表

内存池的思路并不神秘。

**系统启动时先申请或静态保留一大片连续空间，再把它切成若干小块。空闲块通过链表、位图或索引表组织。需要对象时取出一块，释放时再放回去。**

这样做把"不确定的大堆"变成了"可管理的小仓库"。

```
typedef struct PoolNode {    struct PoolNode *next;} PoolNode;typedef struct {    uint8_t *memory;    size_t block_size;    size_t block_count;    PoolNode *free_list;} FixedPool;
```

内存池不是为了炫技。

**它真正解决的是对象规格相对固定、创建销毁频繁、又不希望承受通用堆不确定性的问题。** 网络数据包、消息节点、文件句柄、传感器采样块和协议控制块，都很适合。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-010.jpg]]

### 3.2 固定大小内存池：O(1)分配与释放，无碎片

**固定大小内存池中的每块空间一样大。**

分配时从空闲链表头部取一个节点，释放时插回链表。只要并发保护方式合理，操作时间可以保持常数级。

```
void pool_init(FixedPool *pool,               void *memory,               size_t block_size,               size_t block_count){    if (pool == NULL || memory == NULL ||        block_size < sizeof(PoolNode) || block_count == 0U) {        return;    }    pool->memory = memory;    pool->block_size = block_size;    pool->block_count = block_count;    pool->free_list = NULL;    for (size_t i = 0; i < block_count; ++i) {        PoolNode *node =            (PoolNode *)(pool->memory + i * pool->block_size);        node->next = pool->free_list;        pool->free_list = node;    }}void *pool_alloc(FixedPool *pool){    PoolNode *node;    if (pool == NULL || pool->free_list == NULL) {        return NULL;    }    node = pool->free_list;    pool->free_list = node->next;    return node;}void pool_free(FixedPool *pool, void *ptr){    PoolNode *node;    if (pool == NULL || ptr == NULL) {        return;    }    node = (PoolNode *)ptr;    node->next = pool->free_list;    pool->free_list = node;}
```

严格来说，固定块池不是完全"无浪费"。

申请 33 字节却拿到一个 64 字节块，剩下的 31 字节属于内部碎片。**不过它没有通用堆那种块与块之间散落、难以合并的外部碎片。**

在实时系统里，这种浪费往往比不可预测更容易接受。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-011.jpg]]

### 3.3 多级内存池架构：不同规格应对不同需求

实际项目中的对象大小通常不止一种。

全用 256 字节块，小对象浪费严重。全用 32 字节块，大对象又放不下。比较实用的方案是准备多个规格。

```
Pool A    32 字节 × 64 块Pool B    64 字节 × 48 块Pool C   128 字节 × 32 块Pool D   256 字节 × 16 块Pool E  1024 字节 ×  8 块
```

申请时选择能容纳目标对象的最小规格。

```
void *multi_pool_alloc(size_t size){    if (size <= 32U) {        return pool_alloc(&pool_32);    }    if (size <= 64U) {        return pool_alloc(&pool_64);    }    if (size <= 128U) {        return pool_alloc(&pool_128);    }    if (size <= 256U) {        return pool_alloc(&pool_256);    }    if (size <= 1024U) {        return pool_alloc(&pool_1024);    }    return NULL;}
```

**别急着把规格分得太细。**

规格越多，管理复杂度越高，某个池可能已经耗尽，另一个池却空着。我的经验是**先根据真实分配日志统计对象尺寸分布，再决定池规格，不要凭感觉拍五档、八档、十六档。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-012.jpg]]

### 3.4 主流RTOS实现对比：FreeRTOS heap方案 vs ThreadX块池

FreeRTOS 官方提供多种示例堆实现。

`heap_1` 只分配不释放，最简单。

`heap_2` 支持释放，但不会合并相邻空闲块。

`heap_3` 对标准库 `malloc()` 和 `free()` 做线程安全封装。

`heap_4` 会合并相邻空闲块，能缓解外部碎片。

`heap_5` 在 `heap_4` 的基础上支持多个不连续内存区域。FreeRTOS 官方目前仍把这些方案放在 `Source/Portable/MemMang` 中，并明确说明各自行为。

FreeRTOS 的这些 heap 方案本质上是通用动态分配器或受限动态分配器，不等同于固定块对象池。

ThreadX 则原生提供 Block Pool 和 Byte Pool。**Block Pool 面向固定大小块，适合确定性对象分配；Byte Pool 更像可变尺寸字节堆。** 现在这个项目已经以 Eclipse ThreadX 的名义继续发展，相关调试工具仍能直接显示块池和字节池对象。

怎么选呢？

**对象大小固定、频繁申请释放，块池往往更稳。**

需求多变、对象尺寸跨度大，`heap_4`、`heap_5` 或 TLSF 更灵活。

**关键对象使用静态或块池，非关键业务使用受控堆，这种混合方案在真实项目中很常见，也比"全项目禁止动态内存"更容易落地。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-013.jpg]]

### 3.5 实战：用C++模板实现静态对象池

C++ 模板能把对象大小和数量放到编译期确定，还能避免到处写裸指针转换。

```
#include <array>#include <cstddef>#include <cstdint>#include <new>#include <type_traits>#include <utility>template <typename T, std::size_t Capacity>class StaticObjectPool {public:    StaticObjectPool() = default;    StaticObjectPool(const StaticObjectPool&) = delete;    StaticObjectPool& operator=(const StaticObjectPool&) = delete;    template <typename... Args>    T* create(Args&&... args)    {        for (std::size_t i = 0; i < Capacity; ++i) {            if (!used_[i]) {                used_[i] = true;                void* address = static_cast<void*>(&storage_[i]);                return new (address) T(std::forward<Args>(args)...);            }        }        return nullptr;    }    bool destroy(T* object)    {        if (object == nullptr) {            return false;        }        const auto base =            reinterpret_cast<std::uintptr_t>(storage_.data());        const auto current =            reinterpret_cast<std::uintptr_t>(object);        if (current < base ||            current >= base + sizeof(Storage) * Capacity) {            return false;        }        const std::size_t offset = current - base;        if ((offset % sizeof(Storage)) != 0U) {            return false;        }        const std::size_t index = offset / sizeof(Storage);        if (!used_[index]) {            return false;        }        object->~T();        used_[index] = false;        return true;    }    std::size_t available() const    {        std::size_t count = 0;        for (bool used : used_) {            if (!used) {                ++count;            }        }        return count;    }private:    using Storage =        std::aligned_storage_t<sizeof(T), alignof(T)>;    std::array<Storage, Capacity> storage_{};    std::array<bool, Capacity> used_{};};
```

这个版本为了可读性使用线性扫描，分配复杂度不是 O(1)。想实现 O(1)，可以再维护空闲索引栈。

```
template <std::size_t Capacity>class FreeIndexStack {public:    FreeIndexStack()    {        for (std::size_t i = 0; i < Capacity; ++i) {            indexes_[i] = Capacity - 1U - i;        }        top_ = Capacity;    }    bool pop(std::size_t& index)    {        if (top_ == 0U) {            return false;        }        index = indexes_[--top_];        return true;    }    bool push(std::size_t index)    {        if (top_ >= Capacity || index >= Capacity) {            return false;        }        indexes_[top_++] = index;        return true;    }private:    std::array<std::size_t, Capacity> indexes_{};    std::size_t top_{};};
```

**在多线程或中断环境中，还要加入临界区、锁或无锁同步。** 不要把单线程 Demo 原封不动塞进量产固件，然后问为什么偶尔重复分配同一块对象。

那不叫偶发故障，那叫代码正在按设计爆炸。

## 四、策略三：TLSF算法——实时系统的动态内存利器

### 4.1 TLSF（Two-Level Segregated Fit）算法原理

TLSF 的全称是 Two-Level Segregated Fit。

**它把空闲内存块按大小划分为两级类别。第一级通常按指数范围区分大致尺寸，第二级再把每个范围细分。每个类别都有对应的空闲链表，并通过位图记录哪些类别非空。**

申请一块内存时，**算法不需要从头遍历整条空闲链表。**

**它通过位运算快速定位"能够容纳目标尺寸的最小非空类别"，取出其中一个块，必要时再切分。**

释放时，**算法读取相邻块状态。相邻块空闲就合并，再把新块放回对应类别。**

原始 TLSF 论文将它定位为面向实时系统的动态内存分配器，**核心目标就是让分配和释放拥有有界的最坏执行时间。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-014.jpg]]

### 4.2 O(1)时间复杂度的分配与释放

TLSF 最吸引实时开发者的地方，就是**分配与释放不依赖堆中空闲块数量线性增长。**

通过两级位图查找、双向链表摘除和边界标记合并，核心路径可以保持常数级复杂度。

简化后的查找逻辑大致如下。

```
static int find_suitable_list(uint32_t first_level_bitmap,                              const uint32_t *second_level_bitmap,                              unsigned *first_level,                              unsigned *second_level){    unsigned fl = *first_level;    unsigned sl = *second_level;    uint32_t sl_map =        second_level_bitmap[fl] & (~0UL << sl);    if (sl_map == 0U) {        uint32_t fl_map =            first_level_bitmap & (~0UL << (fl + 1U));        if (fl_map == 0U) {            return -1;        }        fl = count_trailing_zeros(fl_map);        sl_map = second_level_bitmap[fl];    }    sl = count_trailing_zeros(sl_map);    *first_level = fl;    *second_level = sl;    return 0;}
```

工程实现当然比这复杂，还要处理对齐、最小块尺寸、块头、拆分、合并和并发保护。

不过 TLSF 的价值已经很清楚了。

**它不是让每次分配都"绝对一样快"，中断屏蔽、Cache 未命中和锁竞争仍会带来波动。它解决的是搜索路径不会随着碎片数量无限拉长。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-015.jpg]]

### 4.3 碎片率控制在5%以下的秘密

这一节标题很诱人，我得先泼点冷水。

**TLSF 并没有对所有工作负载承诺"碎片率一定低于 5%"。碎片程度与请求尺寸分布、对象生命周期、最小块粒度、对齐要求、池大小和使用模式都有关系。**

所谓 5% 以下，更适合作为经过压力测试后设定的工程目标，而不是算法定理。

TLSF 控制碎片的能力主要来自几件事。

**它会优先选择接近请求大小的空闲类别，减少过度切分。**

释放时会及时合并物理相邻的空闲块。

第二级分类越细，找到的块通常越贴近目标尺寸，但位图和链表管理成本也会增加。

最小块尺寸不能乱设。设得过大，小对象会产生严重内部碎片；设得过小，块头和管理信息占比又会升高。

真正靠谱的做法是记录真实负载。

```
typedef struct {    size_t current_used;    size_t peak_used;    size_t allocation_count;    size_t free_count;    size_t failed_count;    size_t largest_request;} HeapMetrics;static HeapMetrics heap_metrics;void *tracked_alloc(size_t size){    void *ptr = tlsf_malloc(tlsf_handle, size);    heap_metrics.allocation_count++;    if (size > heap_metrics.largest_request) {        heap_metrics.largest_request = size;    }    if (ptr == NULL) {        heap_metrics.failed_count++;        return NULL;    }    size_t actual_size = tlsf_block_size(ptr);    heap_metrics.current_used += actual_size;    if (heap_metrics.current_used > heap_metrics.peak_used) {        heap_metrics.peak_used = heap_metrics.current_used;    }    return ptr;}
```

**然后模拟设备真实运行几天甚至几周，观察最大连续空闲块、总空闲量、分配失败次数和外部碎片趋势。**

别只跑一个"申请十块、释放十块"的单元测试，就宣布碎片率只有 1.2%。那种测试只能证明程序会数到十。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-016.jpg]]

### 4.4 TLSF在嵌入式系统中的优化实践（DBL+POOL）

这里可以采用一种分层思路。

DBL 可以理解为对双向块链表管理的强化，POOL 则代表按用途划分多个独立内存池。不同项目对缩写叫法可能不完全一致，我也不知道这么说对不对，但工程核心是相通的。

**不要让所有内存请求都挤在一个巨大堆里。**

可以给通信、图像、文件系统和通用业务分别建立 TLSF Pool。

```
typedef enum {    MEM_POOL_CONTROL,    MEM_POOL_NETWORK,    MEM_POOL_IMAGE,    MEM_POOL_GENERAL} MemoryPoolId;void *system_alloc(MemoryPoolId pool_id, size_t size){    switch (pool_id) {    case MEM_POOL_CONTROL:        return NULL; /* 控制域禁止动态分配 */    case MEM_POOL_NETWORK:        return tlsf_malloc(network_tlsf, size);    case MEM_POOL_IMAGE:        return tlsf_malloc(image_tlsf, size);    case MEM_POOL_GENERAL:        return tlsf_malloc(general_tlsf, size);    default:        return NULL;    }}
```

这么做有几个实际好处。

**图像算法即使把自己的池折腾碎了，也不会挤占控制任务。**

**网络突发流量耗尽网络池时，系统还能保留日志和故障上报能力。**

每个池可以使用不同物理内存。高频小对象放内部 SRAM，大帧放外部 SDRAM。

**还可以给不同池设置不同失败策略。控制域失败直接进入安全状态，日志域失败则丢弃低优先级记录。**

别让"内存不够"只对应一种处理方式。嵌入式系统得知道什么可以丢，什么绝不能丢。

## 五、策略四：栈空间精细化管理——防患于未然

### 5.1 栈溢出：嵌入式系统最致命的错误之一

栈溢出很阴。

堆分配失败通常还能返回 `NULL`。**栈溢出不会先递一张申请表，它直接越过边界，覆盖旁边的数据、任务控制块或另一个任务栈。**

然后系统在完全不相关的地方崩掉。

我曾经遇到过一个很典型的场景。通信任务新增了一段 JSON 格式化代码，开发板上跑了半天没问题。一开优化、一开日志，再把网络重连压测跑起来，设备就随机 HardFault。

最后发现函数里放了两个 2KB 临时数组，调用链上还有 TLS 握手、日志格式化和驱动回调。任务栈只有 6KB。

最扎心的是，代码审查时我们几个人都看见了那两个数组，谁也没觉得有问题。大家的注意力全在协议逻辑上，栈就这么悄悄被献祭了。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-018.jpg]]

### 5.2 栈大小的精确计算与经验值参考

栈大小不能只靠经验拍脑袋，但经验也不是完全没用。

简单采样任务可能只需几百字节到一两 KB。

带格式化输出、浮点运算和复杂驱动调用的任务，需求会明显增加。

网络协议、TLS、文件系统和图像算法任务，可能需要数 KB 甚至数十 KB。

真正的评估应包含下面几部分。

任务函数及其最深调用链中的局部变量。

编译器保存的寄存器和函数调用现场。

中断嵌套带来的额外上下文。

C 库函数、浮点格式化和第三方库的栈需求。

最坏输入触发的递归或深层分支。

RTOS 上下文切换所需空间。

编译器可以生成栈使用分析文件。

```
arm-none-eabi-gcc \  -O2 \  -fstack-usage \  -c protocol_parser.c
```

生成的 `.su` 文件会列出静态可分析的函数栈使用量。

```
protocol_parser.c:42:5:parse_header    96    staticprotocol_parser.c:87:5:parse_payload   224   staticprotocol_parser.c:131:5:decode_frame   560   dynamic,bounded
```

它很有用，但不是万能的。函数指针、递归、汇编代码、中断嵌套和第三方预编译库可能无法完整分析。

**所以静态分析和运行时测量得一起上。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-019.jpg]]

### 5.3 栈监控技术：魔数（Magic Number）填充法

魔数填充法简单得近乎粗暴，却特别好用。

**任务启动前，用固定字节填满整片栈。系统运行一段时间后，从栈底向上扫描，找到仍未被改写的区域，就能估算历史最大使用量。**

```
#define STACK_PATTERN 0xA5Uvoid stack_fill(uint8_t *stack, size_t size){    if (stack == NULL) {        return;    }    memset(stack, STACK_PATTERN, size);}size_t stack_unused_bytes(const uint8_t *stack, size_t size){    size_t unused = 0;    if (stack == NULL) {        return 0;    }    while (unused < size && stack[unused] == STACK_PATTERN) {        ++unused;    }    return unused;}
```

扫描方向要根据处理器栈增长方向和 RTOS 布局调整。

FreeRTOS 提供栈溢出检查配置和高水位查询接口。**`uxTaskGetStackHighWaterMark()` 一类接口反映任务运行以来曾经出现过的最小剩余栈空间**，静态创建任务时则由应用提供栈缓冲区。

```
void report_task_stack(TaskHandle_t task, const char *name){    UBaseType_t watermark =        uxTaskGetStackHighWaterMark(task);    log_info("%s stack watermark=%lu",             name,             (unsigned long)watermark);}
```

**这里别直接把返回值当成字节。** 不同 FreeRTOS 端口的栈深度单位可能是 `StackType_t` 元素，需要结合端口定义换算。

我以前就犯过这个错，看到高水位还有 300，心想宽裕得很。后来才发现那是元素数，不是我以为的那个口径。虽然最终没出事故，但那几天的报表基本属于精神安慰。

### 5.4 减少栈占用的实战技巧：减少嵌套、优化局部变量

最直接的一招，**是把大数组移出栈。**

```
void bad_decode(void){    uint8_t input[4096];    uint8_t output[4096];    /* 两个数组已经占用 8KB 栈 */}
```

可以改成任务私有静态缓冲区。

```
typedef struct {    uint8_t input[4096];    uint8_t output[4096];} DecoderWorkspace;static DecoderWorkspace decoder_workspace;void decode_frame(void){    decode(decoder_workspace.input,           decoder_workspace.output);}
```

也可以从专用内存池获取工作区。

**减少深层函数嵌套同样有效。** 别把一个数据包处理过程拆成二十层函数，每层都留一堆局部状态，还觉得这叫"架构优雅"。

**递归在资源受限实时系统里要格外谨慎。** 递归深度可严格限定时还能接受，深度取决于输入数据时就危险了。

另外，**`printf()` 家族尤其是浮点格式化，可能带来比想象中更高的栈和代码开销。** 调试阶段随手一打印，量产时可能就成了栈顶最后一根稻草。

## 六、策略五：内存对齐优化——看不见的性能加速器

### 6.1 为什么需要对齐：CPU访问效率与硬件要求

处理器通常更喜欢在自然边界上访问数据。

**32 位整数放在 4 字节对齐地址，64 位数据放在 8 字节对齐地址，CPU 可能一次总线访问就能完成读取。**

未对齐访问的结果取决于处理器和具体配置。

有些核心会自动拆成多次访问，只是变慢。

有些总线或外设不支持未对齐访问，会直接触发 Fault。

DMA 描述符、Cache 操作和某些 SIMD 指令对对齐要求更严格。

**所以，对齐不是 C 语言洁癖，而是软硬件接口的一部分。**

```
#include <stdalign.h>alignas(32) static uint8_t dma_rx_buffer[2048];
```

GCC 也可以这样写。

```
static uint8_t dma_rx_buffer[2048]    __attribute__((aligned(32), section(".dma_buffer")));
```

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-021.jpg]]

### 6.2 结构体内存对齐的"潜规则"

看看下面这个结构体。

```
typedef struct {    uint8_t  enabled;    uint32_t baudrate;    uint8_t  channel;    uint16_t timeout_ms;} ConfigA;
```

很多人会以为它占 8 字节。

**实际尺寸可能是 12 字节。编译器需要在成员之间插入填充字节，还要保证整个结构体数组中的每个元素都满足最大成员对齐要求。**

可以打印验证。

```
printf("ConfigA=%u\n", (unsigned)sizeof(ConfigA));printf("enabled=%u\n",       (unsigned)offsetof(ConfigA, enabled));printf("baudrate=%u\n",       (unsigned)offsetof(ConfigA, baudrate));printf("channel=%u\n",       (unsigned)offsetof(ConfigA, channel));printf("timeout=%u\n",       (unsigned)offsetof(ConfigA, timeout_ms));
```

结构体一两个没什么感觉。数组里放几千个，对齐浪费就很明显。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-022.jpg]]

### 6.3 对齐优化技巧：成员按大小排序、同类型集中

**把大成员放前面，小成员放后面，通常能减少填充。**

```
typedef struct {    uint32_t baudrate;    uint16_t timeout_ms;    uint8_t  enabled;    uint8_t  channel;} ConfigB;
```

这个版本常见情况下只需要 8 字节。

再提醒一句，**不要为了省几个字节，随便给所有结构体加 `packed`。**

```
typedef struct __attribute__((packed)) {    uint8_t  type;    uint32_t timestamp;    uint16_t length;} PacketHeader;
```

打包结构体适合描述外部协议、磁盘格式或硬件寄存器布局，但**直接访问其中的未对齐成员可能变慢，甚至在部分平台触发异常。**

更稳的办法是通过 `memcpy()` 取出多字节字段。

```
uint32_t packet_get_timestamp(const PacketHeader *header){    uint32_t value;    memcpy(&value,           &header->timestamp,           sizeof(value));    return value;}
```

### 6.4 缓存行对齐：Cache Line对齐的进阶应用

带 D-Cache 的 MCU 使用 DMA 时，对齐问题会升级。

CPU 可能修改了缓冲区，但新数据仍停留在 Cache 中，尚未写回物理 RAM。DMA 从 RAM 读取时看到的还是旧内容。

反过来，DMA 已把新数据写入 RAM，CPU 却继续从 Cache 读取旧副本。

**这不是 DMA 坏了，也不是内存"偶尔不稳定"，而是 Cache 一致性没有处理。**

CMSIS 为带 Cache 的 Arm 核心提供按地址清理和失效 D-Cache 的接口。部分 Cortex-M7 相关操作按 32 字节粒度处理，因此**缓冲区起始地址和长度都应按 Cache Line 边界扩展。**

```
#define CACHE_LINE_SIZE 32Ustatic uintptr_t align_down(uintptr_t value, size_t alignment){    return value & ~(uintptr_t)(alignment - 1U);}static uintptr_t align_up(uintptr_t value, size_t alignment){    return (value + alignment - 1U) &           ~(uintptr_t)(alignment - 1U);}void dma_prepare_tx(void *buffer, size_t length){    uintptr_t start =        align_down((uintptr_t)buffer, CACHE_LINE_SIZE);    uintptr_t end =        align_up((uintptr_t)buffer + length,                 CACHE_LINE_SIZE);    SCB_CleanDCache_by_Addr(        (void *)start,        (int32_t)(end - start)    );}void dma_finish_rx(void *buffer, size_t length){    uintptr_t start =        align_down((uintptr_t)buffer, CACHE_LINE_SIZE);    uintptr_t end =        align_up((uintptr_t)buffer + length,                 CACHE_LINE_SIZE);    SCB_InvalidateDCache_by_Addr(        (void *)start,        (int32_t)(end - start)    );}
```

还有个伪共享问题：

**两个任务分别修改不同变量，但变量恰好位于同一 Cache Line。多核系统中，这条 Cache Line 可能在核心之间反复失效，性能莫名其妙下降。**

**把高频并发变量分开并按 Cache Line 对齐，往往比继续优化算法更有效。**

## 七、策略六：零拷贝（Zero-Copy）——消灭内存搬运

### 7.1 零拷贝的核心思想：传指针不传数据

假设摄像头采集一帧数据，随后交给图像算法，再交给编码模块，最后发到网络。

最笨的实现可能复制三四次。

**每次复制都消耗 CPU 时间、内存带宽和额外缓冲区。数据越大，问题越明显。**

**零拷贝的核心并不玄乎，就是让不同模块传递同一块数据的所有权或引用，而不是重复复制内容。**

```
typedef struct {    uint8_t *data;    size_t length;    uint32_t timestamp;    uint16_t buffer_id;} FrameBuffer;
```

任务之间只传递 `FrameBuffer` 描述符。

```
FrameBuffer *frame;if (xQueueReceive(camera_queue,                  &frame,                  portMAX_DELAY) == pdPASS) {    image_process(frame);    xQueueSend(encoder_queue,               &frame,               portMAX_DELAY);}
```

队列里复制的是一个指针，不是几百 KB 的帧数据。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-025.jpg]]

### 7.2 实现手段：mmap、DMA直接传递、共享内存

在嵌入式 Linux 中，`mmap()` 可以把文件、设备内存或共享内存映射到进程地址空间，避免传统 `read()` 加用户缓冲区复制。

**裸机和 RTOS 环境更常见的是 DMA 直接写入预分配缓冲区。**

```
static CameraBuffer camera_buffers[3];void camera_start(void){    for (size_t i = 0; i < 3U; ++i) {        camera_buffers[i].state = BUFFER_FREE;    }    CameraBuffer *buffer = camera_acquire_free();    dma_start(        CAMERA_DMA_CHANNEL,        CAMERA_DATA_REGISTER,        buffer->data,        CAMERA_FRAME_SIZE    );}
```

DMA 完成中断只改变缓冲区状态并投递描述符。

共享内存则适用于多核、异构处理器或进程间通信。**共享数据区之外，还必须设计所有权、缓存一致性和同步协议。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-026.jpg]]

### 7.3 双缓冲（Double Buffer）与缓冲区传递机制

双缓冲最经典。

**DMA 写 A 时，CPU 处理 B。A 写满后交换角色。**

```
static uint16_t adc_buffer_a[1024];static uint16_t adc_buffer_b[1024];static volatile uint16_t *dma_active = adc_buffer_a;static volatile uint16_t *cpu_ready  = adc_buffer_b;void dma_complete_isr(void){    volatile uint16_t *completed = dma_active;    dma_active = cpu_ready;    cpu_ready = completed;    dma_set_destination(        ADC_DMA_CHANNEL,        (void *)dma_active,        sizeof(adc_buffer_a)    );    notify_processing_task_from_isr(        (void *)cpu_ready    );}
```

双缓冲不等于永不丢数据。

**如果 CPU 处理一块缓冲区的时间比 DMA 填满下一块还长，第二次交换时仍会覆盖未处理数据。**

因此，高吞吐系统常使用三缓冲或环形缓冲区，并明确每块缓冲区的状态。

```
typedef enum {    BUFFER_FREE,    BUFFER_DMA_WRITING,    BUFFER_READY,    BUFFER_PROCESSING} BufferState;
```

状态流转必须单向清晰。

```
FREE → DMA_WRITING → READY → PROCESSING → FREE
```

**一旦某块缓冲区在两个模块眼里同时属于自己，零拷贝很快就会变成零证据崩溃。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-027.jpg]]

### 7.4 典型应用场景：网络协议栈、显示驱动、大数据传输

网络协议栈经常通过数据包缓冲区链表实现零拷贝或少拷贝。驱动接收到的数据直接挂到协议栈，协议层只调整指针和长度。

显示驱动可以让 GUI 直接绘制到扫描缓冲区，或通过前后缓冲交换避免整帧复制。

音频、摄像头、雷达点云和高速 ADC 数据也非常适合使用 DMA 加缓冲区所有权传递。

**不过小数据别强行零拷贝。**

一个 8 字节命令，为了传指针又加引用计数、锁、生命周期和回收队列，复杂度可能比复制 8 字节高十倍。

优化得看数据规模和链路瓶颈。不是术语越高级，系统越快。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-028.jpg]]

## 八、策略七：MPU内存保护

### 8.1 MPU（Memory Protection Unit）是什么

MPU 是 Memory Protection Unit，也就是内存保护单元。

它不像带虚拟内存的 MMU 那样负责复杂页表和地址转换。**MPU 主要根据预先配置的区域，对访问权限和内存属性进行检查。**

某片区域可以设为只读。

某片区域可以禁止执行。

某个任务只能访问自己的栈和业务缓冲区。

外设寄存器可以只允许特权代码访问。

许多 Cortex-M 处理器提供可选 MPU。以 Cortex-M55 的资料为例，**RTOS 可以在任务切换时改变可访问区域；未授权任务访问特权数据或其他任务私有内存时，处理器会触发访问违规异常。**

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-029.jpg]]

### 8.2 MPU的核心能力：区域划分、访问权限控制

一个典型任务可以拥有这些区域。

自己的任务栈具有读写权限，禁止执行。

自己的数据区具有读写权限，禁止执行。

共享只读配置区具有只读权限。

系统调用入口和代码区具有只读、可执行权限。

其他任务内存与关键外设不可访问。

下面是基于 CMSIS 风格的示意代码，具体寄存器配置要结合处理器版本调整。

```
void mpu_config_task_stack(uint32_t region,                           void *stack_base,                           size_t stack_size){    ARM_MPU_Disable();    ARM_MPU_SetRegion(        region,        ARM_MPU_RBAR(            (uint32_t)stack_base,            ARM_MPU_SH_NON,            0U,            1U,            1U        ),        ARM_MPU_RLAR(            (uint32_t)stack_base + stack_size - 1U,            0U        )    );    ARM_MPU_Enable(MPU_CTRL_PRIVDEFENA_Msk);    __DSB();    __ISB();}
```

**区域大小、对齐方式和属性编码在 Armv7-M 与 Armv8-M 上有所不同，别从网上复制一份 MPU 初始化代码就直接烧进去。**

那种代码最擅长的事情，是把调试器也一起拦在门外。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-030.jpg]]

### 8.3 阻止代码注入攻击、保护关键数据

**MPU 可以把 SRAM 数据区标记为不可执行，降低攻击者把输入数据当作代码执行的风险。**

Flash 代码区可以标记为只读。

启动参数、加密密钥、校准数据和安全状态可以放入仅特权模式可访问的区域。

外设寄存器也能隔离。普通任务如果不能直接改时钟、Flash 控制器和看门狗寄存器，即使任务出现内存错误，破坏范围也会小很多。

MPU 不是完整安全方案，但它能把一次普通越界从"整机随机损坏"变成"立即产生可定位 Fault"。

我非常喜欢这种失败方式。

早点死，死在现场，还留下地址和原因。比运行三天后在另一个任务里抽风强太多了。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-031.jpg]]

### 8.4 RTOS中的MPU应用：任务级内存隔离

RTOS 可以在上下文切换时重配 MPU，让每个任务看到不同的可访问区域。

普通任务运行在非特权模式。需要操作内核对象或关键外设时，通过受控系统调用进入特权模式。

这样一来，**网络协议栈越界不必然破坏电机控制任务。第三方算法库写飞指针，也不一定能覆盖内核数据。**

代价当然有。

任务切换需要更新 MPU 配置。

区域数量有限，内存布局必须规划。

驱动与应用之间的数据共享更复杂。

旧代码里到处乱访问全局变量的习惯必须改。

可这些代价，和量产设备莫名其妙重启相比，真的不算什么。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-032.jpg]]

## 九、策略八：Rust所有权模型——编译期杜绝内存错误

### 9.1 传统C/C++内存管理的痛点：悬垂指针、双重释放、内存泄漏

C 和 C++ 给开发者很大的自由。

这句话换个角度说，就是它们给了我们非常宽敞的犯错空间。

```
uint8_t *create_buffer(void){    uint8_t local[128];    return local; /* 返回栈上对象地址 */}void double_release(void){    uint8_t *data = malloc(128);    free(data);    free(data);}void leak_on_error(void){    uint8_t *data = malloc(1024);    if (device_open() != 0) {        return; /* data 没有释放 */    }    free(data);}
```

这些问题很多都能通过代码审查、静态分析和规范减少，但很难彻底杜绝。

项目一大，模块一多，指针的所有权就会越来越模糊。

谁申请。

谁释放。

回调失败后谁负责。

消息发送失败时要不要归还。

超时和取消同时发生时会不会释放两次。

这类问题不难理解，难的是每条异常路径都写对。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-033.jpg]]

### 9.2 Rust的所有权系统：每个值只有一个所有者

Rust 用所有权系统管理资源。

**每个值有一个所有者。所有者离开作用域时，资源自动释放。赋值可能转移所有权，转移后原变量不能继续使用。**

```
fn consume_buffer(data: Vec<u8>) {    println!("{}", data.len());}fn main() {    let packet = vec![1, 2, 3, 4];    consume_buffer(packet);    // println!("{:?}", packet);    // 编译失败，所有权已经转移}
```

Rust 官方文档明确说明，**所有权机制让语言能够在不依赖垃圾回收器的前提下提供内存安全保证。**

这对嵌入式系统很重要。

我们不希望突然来一次 GC 暂停，也不希望为了内存安全引入不可预测的后台回收。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-034.jpg]]

### 9.3 借用检查器与生命周期：编译期保证内存安全

不想转移所有权时，可以借用引用。

```
fn checksum(data: &[u8]) -> u32 {    data.iter()        .fold(0u32, |sum, value| sum + *value as u32)}fn main() {    let packet = [1u8, 2, 3, 4];    let value = checksum(&packet);    println!("{}", value);}
```

Rust 限制同一时刻的可变访问关系。

可以存在多个不可变引用。

也可以存在一个可变引用。

**但不能在同一范围内一边多人读，一边有人随意写。**

```
fn main() {    let mut buffer = [0u8; 64];    let first = &mut buffer[0];    // let second = &mut buffer[0];    // 编译器会阻止重叠可变借用    *first = 10;}
```

生命周期用于描述引用与被引用对象之间的有效期关系。

```
fn choose_longer<'a>(    left: &'a [u8],    right: &'a [u8],) -> &'a [u8] {    if left.len() >= right.len() {        left    } else {        right    }}
```

**借用检查器不是魔法，也不是没有学习成本。**

刚开始写 Rust 时，经常有一种感觉，编译器像个特别严格的同事，一直说你不行，还不给你留面子。

写久以后会发现，它是在代码出厂前替你得罪人。总比设备交到客户手里后，客户替你发现悬垂指针强。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-035.jpg]]

### 9.4 零成本抽象：不引入GC，不牺牲性能

Rust 的迭代器、泛型、模式匹配和资源自动释放，很多可以在编译阶段展开或优化，不需要垃圾回收器。

所谓零成本抽象，不意味着任何高级写法都绝对没有成本。

它更接近一个原则。

你不用的能力不该付费。你使用某种抽象时，生成代码应尽量接近手工底层实现。

在嵌入式项目中仍要关注代码体积、单态化膨胀、边界检查和格式化库开销。Rust 不会因为名字很安全，就自动把 Flash 从 256KB 变成 512KB。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-036.jpg]]

### 9.5 Rust在嵌入式领域的实践：Tock OS、Hopter OS

Tock OS 是一个面向低内存、低功耗微控制器的嵌入式操作系统。**它利用 Rust 的类型和内存安全能力保护内核与驱动组件，同时结合硬件保护机制隔离相互不信任的应用。**

Hopter OS 则是较新的 Rust 嵌入式操作系统研究与开源项目。**它强调内存安全、系统鲁棒性和中断响应，并结合定制编译器增强 Rust 本身难以覆盖的系统级约束。** 相关工作在 2025 年发表，项目代码也已公开。

这说明 Rust 在嵌入式领域已经不只是"有人点灯成功"的爱好者阶段。

但迁移也别冲动。

**成熟 C 驱动、芯片厂商 SDK、认证工具链和团队能力都要算成本。** 比较现实的方式是从边界清晰的新模块开始，例如协议解析、升级包处理、安全服务和新驱动，再通过 FFI 与旧 C 系统集成。

## 十、策略九：编译器辅助内存优化——不写一行代码的优化

### 10.1 编译优化选项：-Os（代码体积优先）vs -O3（性能优先）

`-Os` 以减小代码体积为主要目标，同时保留大部分不会明显增大体积的优化。

`-O3` 更激进，可能进行循环展开、向量化和函数内联。速度可能提高，代码体积也可能膨胀。

**别想当然认为 `-O3` 一定更快。**

代码膨胀后，指令 Cache 命中率可能下降。Flash 取指带宽有限时，体积更大的代码反而更慢。更别说某些未定义行为，在高优化级别下会暴露出完全不同的结果。

GCC 文档明确列出了不同优化级别启用的优化集合，`-Os` 与 `-O3` 的目标并不相同。

我通常这样分。

Debug 阶段使用 `-Og -g3`，尽量兼顾调试体验。

资源受限量产固件优先测试 `-Os` 或 `-Oz`。

计算密集模块单独尝试 `-O3`，用真实硬件测周期和体积。

**安全关键代码慎用会改变浮点语义的激进选项。**

不要全局打开 `-ffast-math`，然后发现 NaN、无穷大和浮点比较行为全变了，再说芯片算错。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-038.jpg]]

### 10.2 链接时优化（LTO）与无用代码消除

LTO 让编译器在链接阶段跨源文件分析代码，可能消除无用函数、合并常量并优化跨模块调用。

```
arm-none-eabi-gcc \  -Os \  -flto \  -ffunction-sections \  -fdata-sections \  -c app.c
```

链接时配合下面的选项。

```
-Wl,--gc-sections
```

`--gc-sections` 会根据符号和重定位关系移除未被引用的输入段。必须保留的中断向量、注册表和启动段，需要在链接脚本中使用 `KEEP()`。

```
.isr_vector :{    KEEP(*(.isr_vector))} > FLASH.driver_registry :{    KEEP(*(SORT(.driver_registry.*)))} > FLASH
```

某些驱动采用"只放进特殊段、没有普通代码直接引用"的注册机制。如果忘记 `KEEP()`，链接器可能非常勤快地把它当垃圾删掉。

然后系统启动时找不到驱动。

链接器没有错。它只是太听话。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-039.jpg]]

### 10.3 将关键代码段从Flash移至RAM执行的优化技术

频繁执行、对延迟敏感的代码可以放到 RAM。

常见对象包括 Flash 编程函数、高频中断处理、数字滤波内核和极短控制环。

```
__attribute__((section(".fastcode")))void motor_current_loop(void){    float ia = adc_get_phase_a();    float ib = adc_get_phase_b();    motor_foc_step(ia, ib);}
```

链接脚本负责指定运行位置。

```
.fastcode :{    . = ALIGN(4);    __fastcode_start__ = .;    *(.fastcode*)    . = ALIGN(4);    __fastcode_end__ = .;} > SRAM1 AT> FLASH
```

启动代码负责复制。

```
extern uint8_t __fastcode_load__;extern uint8_t __fastcode_start__;extern uint8_t __fastcode_end__;void copy_fastcode(void){    size_t length =        (size_t)(&__fastcode_end__ -                 &__fastcode_start__);    memcpy(&__fastcode_start__,           &__fastcode_load__,           length);}
```

**别把整个程序都搬进 RAM。**

RAM 本来就紧张，真正的热点通常只占很小一部分。**先用周期计数器、采样分析或 Trace 找到热点，再搬。**

凭感觉优化，十次有八次在优化不重要的地方。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-040.jpg]]

### 10.4 利用硬件特性：FPU、SIMD指令集加速

带 FPU 的 Cortex-M4F、M7、M33 或更高性能核心，可以硬件执行部分浮点运算。

没启用正确编译选项时，代码可能继续调用软件浮点库。

```
-mcpu=cortex-m7-mthumb-mfpu=fpv5-sp-d16-mfloat-abi=hard
```

参数必须与芯片和 ABI 匹配。库文件也要使用相同浮点 ABI，否则链接失败或接口不兼容。

DSP 和 SIMD 指令能一次处理多个窄数据。

```
#include "arm_math.h"void q15_vector_add(const q15_t *a,                    const q15_t *b,                    q15_t *out,                    uint32_t count){    arm_add_q15(a, b, out, count);}
```

**硬件加速不仅减少执行时间，也可能降低临时缓冲区需求。**

但 FPU 上下文会增加任务切换保存成本，部分 RTOS 使用惰性保存机制。高频中断里随手使用浮点，可能让中断栈和延迟一起上涨。

芯片给你一把电锯，不代表切水果也要用它。

![[assets/embedded-interview/嵌入式系统开发，必知的10个内存管理策略/img-041.jpg]]

## 十一、策略十：内存泄漏检测与运行时监控——让问题无所遁形

### 11.1 内存泄漏：长期运行系统的"慢性病"

内存泄漏不像空指针那样痛快。

**它每次只吃掉几十字节，系统还能继续工作。一天少 1KB，半个月也许才出问题。研发测试两小时，当然什么都看不出来。**

典型泄漏经常藏在异常路径里。

```
int send_packet(const uint8_t *data, size_t length){    Packet *packet = packet_alloc(length);    if (packet == NULL) {        return -1;    }    if (network_connect() != 0) {        return -2; /* packet 泄漏 */    }    if (network_send(packet) != 0) {        packet_free(packet);        return -3;    }    packet_free(packet);    return 0;}
```

这类代码可以用统一清理出口改写。

```
int send_packet(const uint8_t *data, size_t length){    int result = -1;    Packet *packet = packet_alloc(length);    if (packet == NULL) {        return -1;    }    if (network_connect() != 0) {        result = -2;        goto cleanup;    }    if (network_send(packet) != 0) {        result = -3;        goto cleanup;    }    result = 0;cleanup:    packet_free(packet);    return result;}
```

很多人嫌 `goto cleanup` 不优雅。

我以前也嫌。后来排查过几次异常路径泄漏，突然觉得它眉清目秀。

### 11.2 运行时监控API：vPortGetFreeHeapSize()等

FreeRTOS 常用接口包括 `xPortGetFreeHeapSize()` 和 `xPortGetMinimumEverFreeHeapSize()`。前者反映当前空闲堆，后者可用于观察系统运行以来出现过的最低空闲量，具体支持情况取决于所选 heap 实现。

```
typedef struct {    size_t free_heap;    size_t minimum_free_heap;    UBaseType_t sensor_stack_watermark;    UBaseType_t network_stack_watermark;} MemorySnapshot;void memory_collect_snapshot(MemorySnapshot *snapshot){    if (snapshot == NULL) {        return;    }    snapshot->free_heap =        xPortGetFreeHeapSize();    snapshot->minimum_free_heap =        xPortGetMinimumEverFreeHeapSize();    snapshot->sensor_stack_watermark =        uxTaskGetStackHighWaterMark(sensor_task_handle);    snapshot->network_stack_watermark =        uxTaskGetStackHighWaterMark(network_task_handle);}
```

**只看总空闲量还不够。**

最好同时记录最大连续空闲块、空闲块数量、最小空闲块、分配失败次数和峰值占用。

```
void report_heap_stats(void){    HeapStats_t stats;    vPortGetHeapStats(&stats);    log_info(        "heap free=%u min=%u largest=%u blocks=%u",        (unsigned)stats.xAvailableHeapSpaceInBytes,        (unsigned)stats.xMinimumEverFreeBytesRemaining,        (unsigned)stats.xSizeOfLargestFreeBlockInBytes,        (unsigned)stats.xNumberOfFreeBlocks    );}
```

总空闲 30KB，最大连续块只剩 2KB，这才是碎片正在恶化的信号。

### 11.3 静态代码分析：提前发现潜在内存问题

静态分析工具能在程序运行前发现不少问题。

数组越界。

空指针解引用。

释放后使用。

未初始化变量。

资源泄漏。

危险类型转换。

不可达分支。

常见工具包括编译器警告、Clang-Tidy、Cppcheck、Coverity、PVS-Studio 和面向安全规范的商业工具。

**先把编译器警告开够。**

```
-Wall-Wextra-Wshadow-Wconversion-Wsign-conversion-Wcast-align-Wformat=2-Wundef-Wdouble-promotion-Werror=return-type
```

别一上来全局 `-Werror`，老项目可能瞬间出现几千条错误，团队当场放弃。

可以先按模块治理，逐步提高门槛。新增代码不允许引入新警告，旧问题建立基线慢慢还。

### 11.4 嵌入式专用调试工具：MemFault、SystemView

Memfault 提供面向嵌入式设备的故障诊断、指标采集和远程可观测能力。开发者可以把堆余量、栈水位、重启原因和断言信息作为设备指标或故障上下文上传，分析现场设备为何逐步走向崩溃。Memfault 自己的工程文章也强调，高栈占用、堆耗尽和严重碎片往往需要在崩溃前记录趋势，而不是只盯着最后一次失败调用。

SEGGER SystemView 能在目标运行时记录任务切换、中断、用户事件和系统行为。它还支持堆监控事件，开发者可以在自定义分配器中调用对应记录接口。

```
void *debug_malloc(size_t size){    void *ptr = pvPortMalloc(size);    if (ptr != NULL) {        SEGGER_SYSVIEW_HeapAlloc(            HEAP_ID,            ptr,            (unsigned)size        );    }    return ptr;}void debug_free(void *ptr){    if (ptr == NULL) {        return;    }    SEGGER_SYSVIEW_HeapFree(        HEAP_ID,        ptr    );    vPortFree(ptr);}
```

**这些工具的意义不是让界面看着专业。**

**它们能把"设备偶尔重启"变成一条时间线。**

重启前两分钟网络任务频繁创建对象。

最大连续空闲块持续下降。

某个任务栈高水位接近零。

随后出现分配失败和看门狗复位。

证据链一出来，问题就从玄学变成工程。

### 11.5 内存使用率预警机制的建立

量产系统至少应该建立三级内存预警。

正常状态继续记录低频指标。

警告状态提高采样频率，限制低优先级任务，停止非必要日志缓存。

**危险状态保留故障上下文，拒绝新业务请求，进入降级或安全模式。**

```
typedef enum {    MEMORY_LEVEL_NORMAL,    MEMORY_LEVEL_WARNING,    MEMORY_LEVEL_CRITICAL} MemoryLevel;MemoryLevel memory_evaluate(size_t free_heap,                            size_t largest_block,                            size_t minimum_stack){    if (free_heap < 4096U ||        largest_block < 2048U ||        minimum_stack < 64U) {        return MEMORY_LEVEL_CRITICAL;    }    if (free_heap < 12288U ||        largest_block < 8192U ||        minimum_stack < 192U) {        return MEMORY_LEVEL_WARNING;    }    return MEMORY_LEVEL_NORMAL;}
```

阈值不能照抄示例。

**它们应该来自项目真实峰值、最坏负载和故障注入测试。**

预警还要考虑趋势。当前剩余 20KB 看似安全，但如果每小时稳定下降 500 字节，四十小时以后照样出事。

```
int32_t memory_leak_rate(const MemorySample *old_sample,                         const MemorySample *new_sample){    uint32_t elapsed =        new_sample->timestamp_s -        old_sample->timestamp_s;    if (elapsed == 0U) {        return 0;    }    return (int32_t)(        ((int64_t)new_sample->free_heap -         (int64_t)old_sample->free_heap) *        3600 /        elapsed    );}
```

**别等分配失败才报警。**

## 十二、真实项目内存优化案例分析

### 12.1 摄像头设备RAM不足优化案例

这个案例来自一类很常见的摄像头终端。

主控拥有 512KB 内部 SRAM，外接 8MB PSRAM。设备需要完成图像采集、简单识别、JPEG 编码和网络上传。

最初版本的设计很直白。

摄像头驱动准备两块完整 RGB 帧缓冲区。

图像算法复制一份输入。

JPEG 编码再申请一块输出缓冲区。

网络发送模块又复制到自己的发送缓存。

单帧分辨率是 640×480，RGB565 每像素 2 字节。

```
单帧大小640 × 480 × 2 = 614400 字节
```

一帧就超过 600KB。

这套方案居然还能在某些测试条件下启动，因为部分缓冲区放在 PSRAM，部分功能没有同时开启。到了网络重传和图像识别并发时，内存立刻不够。

团队一开始把问题归咎于 PSRAM 驱动。

我当时也跟着查了半天时序，甚至怀疑板子焊接。后来把所有内存申请打日志，才发现不是驱动坏，而是我们的架构从一开始就没算过账。

改造分成几步。

摄像头输出从 RGB565 改为更适合后续链路的格式，减少无意义转换。

算法改为分块处理，不再要求完整复制一帧。

编码器直接读取摄像头缓冲区。

网络发送引用 JPEG 输出块，不再复制。

所有大缓冲区放入专用 PSRAM 池，控制任务和网络控制块留在内部 SRAM。

```
typedef struct {    uint8_t *address;    size_t capacity;    size_t valid_length;    uint16_t id;    BufferState state;} ImageBuffer;static ImageBuffer image_buffers[3];ImageBuffer *image_acquire(BufferState expected,                           BufferState next){    taskENTER_CRITICAL();    for (size_t i = 0; i < 3U; ++i) {        if (image_buffers[i].state == expected) {            image_buffers[i].state = next;            taskEXIT_CRITICAL();            return &image_buffers[i];        }    }    taskEXIT_CRITICAL();    return NULL;}
```

处理链变成这样。

```
摄像头 DMA    ↓采集缓冲区    ↓ 传描述符分块识别    ↓ 同一缓冲区JPEG 编码    ↓ 输出块链表网络发送    ↓ 发送完成缓冲区归还池
```

**最终并没有通过"再加一颗更大的 PSRAM"解决问题。**

峰值内存占用下降了接近一半，CPU 搬运时间也明显减少。更关键的是，每块缓冲区有明确状态，出了问题能知道它卡在哪一环。

这个案例给我的教训很直接。

**摄像头项目不能只统计容量，要画出缓冲区生命周期图。哪几块同时存在，谁拥有，什么时候归还，全得写清楚。**

不然再大的 RAM 也只是晚一点爆。

### 12.2 工业设备长期运行崩溃案例

第二个案例是一台工业采集网关。

设备运行几小时一切正常，连续运行大约二十天后偶尔重启。现场环境不方便连接调试器，客户给出的描述只有一句。

机器有时候自己重启。

这种描述对开发者的帮助，大概等于医生听到患者说"我不舒服"。

我们先给系统加了重启原因记录、堆水位、任务栈水位和网络状态统计。数据写入一块循环 Flash 日志区，每次启动后上传最近记录。

观察到的趋势很奇怪。

总空闲堆在网络正常时基本稳定。

**每次服务器断线重连后，最低空闲堆都会下降一小截。**

下降量不固定，几十字节到几百字节都有。

设备经历几百次重连后，最大连续空闲块不断缩小。

最终一次 TLS 会话创建失败，网络任务进入异常循环，看门狗复位。

继续追踪分配来源，发现断线处理路径有两个问题。

一个 DNS 结果对象在超时路径中没有释放。

一组重传节点释放顺序错误，其中部分节点丢失。

原始代码大概是这样。

```
int reconnect_server(void){    DnsResult *dns = dns_lookup(server_name);    if (dns == NULL) {        return -1;    }    Connection *connection =        connection_create(dns->address);    if (connection == NULL) {        return -2; /* dns 没有释放 */    }    if (connection_handshake(connection) != 0) {        connection_destroy(connection);        return -3; /* dns 仍然没有释放 */    }    dns_result_free(dns);    active_connection = connection;    return 0;}
```

改完以后，资源清理统一处理。

```
int reconnect_server(void){    int result = -1;    DnsResult *dns = NULL;    Connection *connection = NULL;    dns = dns_lookup(server_name);    if (dns == NULL) {        result = -1;        goto cleanup;    }    connection = connection_create(dns->address);    if (connection == NULL) {        result = -2;        goto cleanup;    }    if (connection_handshake(connection) != 0) {        result = -3;        goto cleanup;    }    active_connection = connection;    connection = NULL;    result = 0;cleanup:    if (connection != NULL) {        connection_destroy(connection);    }    if (dns != NULL) {        dns_result_free(dns);    }    return result;}
```

我们还做了两件事。

网络会话相关对象改用独立内存池。即使网络模块再次泄漏，也不会吃掉控制域资源。

每次断线重连前后记录池中对象数量。理论上重连结束后，临时对象数量应该回到基线。

```
void network_pool_assert_baseline(void){    NetworkPoolStats stats;    network_pool_get_stats(&stats);    if (stats.allocated_temp_nodes != 0U) {        log_error(            "network temp node leak count=%u",            (unsigned)stats.allocated_temp_nodes        );        fault_capture(FAULT_NETWORK_POOL_LEAK);    }}
```

改造后的设备做了长时间断网重连压测，堆水位不再阶梯式下降。

**这类问题靠人工看代码，未必一眼能发现。靠两小时功能测试，更发现不了。**

**长期运行系统需要长期指标。没有趋势数据，所谓稳定性测试很容易变成"把机器放桌上亮了三天"。**

### 12.3 DMA数据异常问题定位案例

第三个案例特别容易被误判成硬件问题。

一块 Cortex-M7 控制板通过 DMA 接收高速 ADC 数据。低速采样时正常，提高采样率后，偶尔会出现一段旧数据，或者数据块前半段正确、后半段异常。

团队依次怀疑了 ADC、DMA、总线时钟、电源纹波和 PCB 信号完整性。

示波器、逻辑分析仪都上了，硬件看着没毛病。

软件里把缓冲区打印出来，数据确实错。

后来我们关闭 D-Cache，问题消失。

**这时答案已经很明显，DMA 写了内存，CPU 却还在读取 Cache 中的旧副本。**

原始代码只等待 DMA 完成，没有做 Cache 维护。

```
void adc_dma_complete_callback(void){    process_adc_samples(adc_buffer,                        ADC_SAMPLE_COUNT);}
```

改造后，缓冲区按 Cache Line 对齐，并在 CPU 读取前失效对应 D-Cache 区域。

```
#define ADC_SAMPLE_COUNT 2048U#define CACHE_LINE_SIZE  32Ustatic uint16_t adc_buffer[ADC_SAMPLE_COUNT]    __attribute__((aligned(CACHE_LINE_SIZE)));void adc_dma_complete_callback(void){    SCB_InvalidateDCache_by_Addr(        adc_buffer,        sizeof(adc_buffer)    );    __DSB();    __ISB();    process_adc_samples(        adc_buffer,        ADC_SAMPLE_COUNT    );}
```

事情还没结束。

第一次改完后，问题频率降低了，但没有完全消失。后来发现缓冲区长度虽然是 32 字节倍数，起始地址却因链接布局变化偶尔没有落在独立 Cache Line 上。

相邻的一小段状态变量与 ADC 缓冲区共享了同一条 Cache Line。失效 Cache 时，顺带影响了旁边数据。

**最终我们把 DMA 缓冲区放进独立链接段，并保证段首、段尾都按 32 字节对齐。**

```
.dma_buffer (NOLOAD) :{    . = ALIGN(32);    __dma_buffer_start__ = .;    *(.dma_buffer)    *(.dma_buffer*)    . = ALIGN(32);    __dma_buffer_end__ = .;} > SRAM2
```

变量定义也明确指定段。

```
static uint16_t adc_buffer[ADC_SAMPLE_COUNT]    __attribute__((section(".dma_buffer"),                   aligned(32)));
```

问题彻底消失。

这次经历让我记住了一件事。

**DMA 数据异常不一定是 DMA 的错。只要系统带 Cache，就要把 CPU、Cache、物理 RAM 和 DMA 看成四个参与者。**

谁写了数据。

数据现在在哪。

谁能看到最新版本。

需要 Clean 还是 Invalidate。

操作范围有没有按 Cache Line 扩展。

这些问题答不清楚，就会在"硬件偶发异常"上浪费很多天。我们当时就浪费了，真的，还把 ADC 芯片换了两批。现在想想有点丢人，但这种丢人经历比漂亮架构图有用。

## 总结

**静态分配提供确定性，适合长期对象和安全关键资源。**

**内存池在灵活性与可预测性之间找到平衡，特别适合固定规格、频繁创建销毁的对象。**

**TLSF 让可变尺寸动态分配拥有更可控的最坏执行时间，但它不是"碎片自动消失器"，仍然需要真实负载验证。**

**栈管理必须结合静态分析、高水位监控和最坏调用路径，别等溢出以后才发现任务栈是拍脑袋定的。**

**内存对齐看起来不起眼，却直接影响 CPU、Cache、DMA 和总线访问。**

**零拷贝可以大幅减少内存搬运，可它真正的难点是所有权与生命周期，而不是把结构体改成指针。**

**MPU 能把越界和非法访问关进更小的笼子，让错误尽早暴露。**

**Rust 把大量内存安全问题提前到编译期，但工具链、生态和旧代码迁移成本仍要诚实评估。**

**编译器、链接器和硬件指令能帮我们省空间、提速度，前提是你用测量数据，而不是靠选项名字猜性能。**

**运行时监控则是最后一道保险。堆余量、最大连续块、栈水位、分配失败、泄漏趋势和重启原因，都应该成为系统指标。**

**一个成熟的嵌入式系统，应该在资源最紧、输入最坏、网络最差、任务最忙的时候，依然知道自己的内存花在了哪里，剩下多少，还能撑多久。**

做到这一步，系统才算从"能跑"走到了"跑得稳、跑得久"。
