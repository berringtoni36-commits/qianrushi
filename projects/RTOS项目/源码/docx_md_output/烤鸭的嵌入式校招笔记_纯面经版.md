前言

这份资料，最开始不是为了做成一份正式文档。

> 在准备嵌入式校招、整理自己面经，以及和很多同学交流的过程中，我发现大家遇到的问题大致可以分为

两类：一方面，很多同学不知道嵌入式面试到底会问什么；另一方面，即使知道了一些八股题，也很难判断哪

些内容是真正高频、哪些问题会被面试官继续深挖。

> 尤其是嵌入式方向，它不像纯软件岗位那样只考算法和计算机基础，也不像传统硬件岗位那样只看电路和

芯片。很多公司的面试会同时考察 C/C++ 基础、Linux、FreeRTOS、通信协议、单片机外设、网络编程、项目架

构、调试经验和手撕代码。也就是说，嵌入式校招真正难的地方，不是某一个知识点特别深，而是考察范围比

较杂，而且非常看重你能不能把知识和项目经历结合起来讲清楚。

> 所以我把大家真实经历过的面经，以及网络搜集的一些嵌入式方向面经，按照公司和面试轮次做了系统整

理。整理这份资料的目的，并不是让大家机械地背题，而是希望帮助大家建立一个更清晰的认知：嵌入式校招

到底在考什么？不同公司喜欢怎么问？哪些知识点是绕不开的？自己的简历项目可能会被怎么追问？

> 从写《烤鸭的嵌入式校招笔记》开始，我就一直觉得，面经真正有价值的地方，从来不是答案，而是帮你

ꢀ前看到面试官的ꢀ问方式，指明准备方向。可以理解为期末考试时老师给你花了重点，而不是一整本书都丢

给你。比如你简历里写了 FreeRTOS，面试官可能不会只问“FreeRTOS 是什么”，而是会继续问：任务怎么划分？

优先级怎么设计？队列满了怎么办？中断和任务之间如何同步？为什么不用裸机？如果你写了串口通信，面试

官也可能继续问：协议帧怎么设计？DMA 丢帧怎么办？如何判断一帧数据接收完整？通信异常如何恢复？

> 这些问题，单独看每一个都不算特别难，但如果没有ꢀ前准备，很容易在面试中被连续追问打乱节奏。甚

至有可能结合你项目，换个问法我们就不好回答了。

> 因此，这份资料更适合作为一份嵌入式校招面试地图来使用。你可以先通过各公司面经了解真实面试范围，

再结合后面的高频考点统计，判断自己目前在哪些模块还比较薄弱。

> 需要说明的是，面经只能解决**“**知道会问什么**”**的问题。真正决定面试表现的，还是基础知识是否系统、项

目经历是否扎实、表达是否清楚、回答能否经得住追问。如果你只是把这份资料当成题库来背，效果可能有限；

但如果你能把它当成一份检查清单，逐项对照自己的知识体系和简历项目去查漏补缺，它会更有价值。

> 最后，校招准备没有捷径，但有方法。不要只焦虑自己不会什么，而是要把问题拆开，一个模块一个模块

补齐。基础题尽量不丢分，项目问题尽量讲清楚，遇到追问不要慌，能结合自己的实践经历回答出来，就已经

比很多只会背答案的同学更有竞争力了。

> 希望这份资料能成为你准备嵌入式校招过程中的一份参考，也希望你最终不只是**“**看过很多面经**”**，而是真

的能在面试中把自己的能力讲出来。

一、C/C++ 基础

1\. static 关键字有哪些作用？

> 【参考回答】**static** 在 C/C++中常见作用主要有三个：修饰局部变量、修饰全局变量、修饰函数。修饰

局部变量时，变量的生命周期会延长到整个程序运行期间，但作用域仍然只在函数内部；修饰全局变量或

函数时，主要作用是限制链接属性，使其只在当前源文件内可见，避免被其他编译单元访问。

> 在工程中，static 局部变量常用于保存函数多次调用之间的状态，比如状态机状态、滤波器历史值、局

部计数器等；static 全局变量或 static 函数则常用于模块内部封装，减少符号污染，避免其他文件误用。比

如一个.c 文件中有只供本模块使用的协议解析函数，就可以声明为 static，这样其他文件无法直接调用，模

块边界会更清楚。

> 需要注意的是，static 变量本身不保证线程安全。如果 static 变量可能被多个任务、中断或回调函数同

时访问，就需要考虑临界区、互斥锁、关中断或原子操作。另外，局部 static 变量虽然写在函数内部，但

它并不存放在栈区，函数退出后值仍然保留，这一点和普通局部变量完全不同。

2\. const 关键字有什么作用？

> 【参考回答】**const** 的核心作用是表达只读语义，表示某个变量、指针指向的内容或成员函数不应该被

修改。它不仅是语法限制，更重要的是让接口意图更清楚，降低误修改数据的风险。面试中回答 const 时，

不能只说“常量”，更应该强调它在接口约束和代码可维护性上的作用。

> 常见考点是 const 和指针的组合：**const int \*p** 表示不能通过 **p** 修改其指向的内容；**int \* const p** 表示指

针 **p** 本身不能再指向其他地址；**const int \* const p** 表示指针本身和指向内容都不能修改。判断时可以看

**const** 修饰的是指针本身还是指向的内容，这样不容易混淆。

在嵌入式中，const 常用于查表数据、固定配置参数、只读字符串和函数接口参数。例如函数只读取缓冲区

时，可以写成 const uint8_t buf，表示函数不会修改调用方数据，这能让接口边界更清晰，也能让编译器帮

助检查潜在错误。对于一些固定查表数组，**const** 还可能帮助编译器将数据放到只读存储区域，减少误写

风险。（烤鸭嵌入式免费分享，请勿商用）

3\. volatile 关键字在嵌入式开发中有什么作用？

> 【参考回答】**volatile** 的作用是告诉编译器：这个变量的值可能会在当前代码流程之外被改变，因此每

次访问都必须真实地从内存或硬件寄存器中读取，不能随意优化成缓存值。它解决的是编译器优化可见性

问题，而不是线程同步问题。

> 嵌入式中典型场景包括：中断服务函数和主循环共享的变量、硬件寄存器映射地址、被其他任务修改

的标志位。例如主循环等待 rx_done 标志，而 rx_done 在串口中断中置位，如果没有 volatile，编译器可能

认为循环中变量不会变化，从而优化掉重复读取，导致程序一直等待。访问硬件寄存器时也常使用 volatile，

因为寄存器的值可能由外设硬件自动改变。

> 需要注意，volatile 不能保证原子性，也不能解决竞态条件。比如多个任务同时对同一个 volatile 变量

执行自增操作，仍然可能出现数据覆盖，因为自增本身通常包含读、改、写多个步骤。因此 volatile 适合解

决“变量是否每次真实读取”的问题，如果涉及并发修改，还需要使用关中断、临界区、互斥锁或原子操作

来保证安全。

4\. extern 关键字有什么作用？

> 【参考回答】**extern** 主要用于声明某个变量或函数是在其他编译单元中定义的，它告诉编译器“这里存

在这个符号，但实际定义在别处”。在多文件工程中，如果一个全局变量定义在某个.c 文件里，其他文件想

访问，通常会在头文件中使用 extern 进行声明（烤鸭嵌入式免费分享，请勿商用）。

> 需要区分声明和定义：**extern int g_count;**只是声明，不分配实际存储空间；**int g_count=0;**才是定义，

会真正分配存储空间。如果在头文件中直接定义普通全局变量，多个源文件包含后容易在链接阶段出现重

复定义。所以比较规范的方式是：在.c 文件中完成变量定义，在.h 文件中使用 extern 声明，其他源文件通

40\. vector 的底层原理和扩容机制是什么？

> 【参考回答】vector 底层是一段连续内存，因此支持按下标 O(1)随机访问，遍历性能也比较好。它通

或 2 倍。

> vector 扩容会导致原来的指针、引用和迭代器失效，这是常见考点。它的优点是连续内存带来较好的

果不希望运行时突然扩容，可以ꢀ前 reserve，或者使用固定容量容器。

41\. vector 和 list 有什么区别？

> 【参考回答】vector 底层是连续数组结构，支持按下标 O(1)随机访问，遍历效率高，缓存局部性好，

尾部插入效率也比较高；list 通常是双向链表结构，节点在内存中不一定连续，随机访问需要从头或从尾遍

历，但在已知位置插入和删除节点比较方便。

带来管理成本。

知位置频繁插入删除，并且不关心随机访问，可以考虑 list。但在嵌入式项目中，还要额外关注 list 带来的

动态分配、内存碎片和缓存不友好问题。

53\. 什么是中断？

> 【参考回答】中断是 CPU 在执行当前程序时，被外部事件或内部事件打断，转而执行对应中断服务函

数的一种机制。中断处理完成后，CPU 会恢复现场，继续执行原来的程序流程。

> 中断适合处理突发性强、实时性要求较高的事件，比如串口接收、定时器溢出、外部按键、DMA 传输

完成等。相比轮询方式，中断不需要 CPU 一直等待某个事件发生，可以ꢀ高系统响应效率和 CPU 利用率。

> 嵌入式开发中要特别注意，中断服务函数应该尽量短小、快速、确定。通常在中断里只做清除标志位、

读取关键数据、置位通知等简单操作，把复杂处理交给主循环或 RTOS 任务完成。这样既能保证响应及时，

也能避免中断占用时间过长影响系统实时性。

54\. 异常和中断有什么区别？

> 【参考回答】异常和中断都属于打断 CPU 正常执行流程的机制。一般来说，中断更多指外设或外部事

件触发的异步事件，比如串口接收、定时器更新、DMA 完成；异常范围更大，可以包括 CPU 内部错误、系

统调用、系统节拍等事件。

> 在 Cortex-M 内核中，中断也被统一纳入异常体系管理。像 HardFault、SysTick、SVCall、PendSV 属于系

统异常，外设 IRQ 也通过异常机制进入对应处理函数。NVIC 负责管理外部中断的使能、挂起、优先级和嵌

套响应。

> 可以结合例子说明：串口接收中断属于外设中断，HardFault 通常表示严重错误异常，SysTick 常用于系

统节拍，PendSV 常用于 RTOS 任务切换。简单总结就是：异常是更大的概念，中断通常是异常体系中由外

设事件触发的一类。

58\. 中断和轮询有什么区别？

> 【参考回答】轮询是 CPU 主动不断检查某个状态位，发现事件后再处理；中断是事件发生时由硬件通

知 CPU，CPU 暂停当前工作，转去执行对应的中断服务函数。两者的核心区别在于：轮询是主动检查，中

断是事件触发。

> 轮询实现简单、流程可控，适合低频、不紧急、逻辑简单的场景；缺点是会浪费 CPU 资源，响应时间

也取决于轮询周期。中断响应更及时，CPU 利用率更高，适合突发事件和实时性要求较高的场景，但程序

结构更复杂，需要处理共享变量、优先级和临界区问题。

> 实际项目里两者经常结合使用。例如串口接收可以用中断或 DMA 完成数据接收，再由主循环或任务

轮询处理缓冲区中的数据。回答时不要绝对化，关键要结合事件频率、实时性要求、**CPU** 负载和系统复杂

度来选择。

59\. DMA 是什么？有什么作用？

> 【参考回答】DMA 是直接存储器访问机制，可以在外设和内存之间，或者内存和内存之间搬运数据，

而不需要 CPU 逐字节参与。CPU 通常只需要配置源地址、目的地址、数据长度和触发条件，后续搬运由

DMA 控制器完成。

> 使用 DMA 的好处是降低 CPU 占用，ꢀ高数据传输效率，尤其适合大量或连续数据搬运场景，比如 ADC

采样、串口大量数据收发、SPI 屏幕刷新、I2S 音频数据传输等。DMA 传输完成后，通常可以通过传输完成

中断或半传输中断通知 CPU 处理数据。

> 但 DMA 不是配置完就不用管了，工程中还要考虑缓冲区管理、数据覆盖、半传输中断、传输完成中

断、缓存一致性等问题。比如串口 DMA 接收时，通常让 DMA 负责搬运数据，把协议解析放到任务或主循

环中，避免在中断里做复杂处理。

60\. UART DMA 接收不定长数据通常怎么做？

> 【参考回答】UART DMA 适合连续接收数据，但普通 DMA 通常需要ꢀ前知道接收长度，而串口协议中

很多数据帧是不定长的。常见方案是使用 **DMA+IDLE** 空闲中断，或者使用循环 **DMA+**读写指针进行缓冲区

管理。

> DMA+IDLE 方案的思路是：DMA 持续把串口接收到的数据搬到缓冲区中，当串口总线空闲超过一帧时

间后触发 IDLE 中断。此时软件读取 DMA 剩余计数，就可以计算出本次实际接收了多少字节，然后再交给

主循环或任务处理。

> 工程上还要处理缓冲区溢出、半包、粘包、协议校验和重新启动 DMA 等问题。比较稳妥的做法是让

DMA 只负责数据接收，中断里只计算长度、保存状态或通知任务，真正的协议解析放到任务中完成。对于

高吞吐场景，可以使用循环缓冲区，通过读写指针避免频繁停止和重启 DMA。（烤鸭嵌入式免费分享，请

61\. 环形缓冲区是什么？适合什么场景？

> 【参考回答】环形缓冲区是一块固定大小的数组，通过读指针和写指针循环移动来管理数据。写指针

到达数组末尾后会回绕到开头继续写，因此这块缓冲区可以被持续复用，看起来就像一个环。

> 它很适合生产者和消费者速度不完全一致的场景，比如串口接收、日志缓存、音频流、传感器数据缓

存等。典型用法是中断或 DMA 负责写入数据，主循环或任务负责读取和处理数据，从而解耦接收和处理

速度。

> 使用环形缓冲区时，要重点处理满和空的判断。常见做法是牺牲一个存储单元区分满空，或者额外维

护数据长度。多任务或中断环境下，还要注意读写指针的并发访问，必要时使用临界区、原子操作或关闭

中断保护关键操作。

63\. Flash 写入和掉电保护要注意什么？

> 【参考回答】Flash 写入通常需要先擦除再写入，而且擦除单位往往是页或扇区，不是像 RAM 一样可

版本号、有效标志、CRC 校验、写前写后校验，以及先写新数据、确认成功后再切换有效标志。

> 如果保存的是关键参数，建议数据结构中包含 magic、version、length、crc 等字段。启动时先校验数据

合法性，如果当前区校验失败，就回退到备份区或默认参数。这样即使掉电发生在写入过程中，也能尽量

保证系统还能恢复到可用状态。

66\. PWM 是什么？定时器如何产生 PWM？

> 【参考回答】PWM 是脉宽调制，通过改变固定周期内高电平持续时间的比例，来等效控制输出平均

能量。占空比越大，平均输出越高，因此 PWM 常用于电机调速、舵机控制、LED 调光、蜂鸣器驱动等场

景。

> STM32 定时器产生 PWM 时，通常由计数器 **CNT**、自动重装载寄存器 **ARR** 和比较寄存器 **CCR** 配合实

现。ARR 决定计数周期，CCR 决定比较匹配点，当计数值和比较值满足设定关系时，输出电平发生变化，

从而形成固定频率、可调占空比的 PWM 波形。

> 频率通常由定时器时钟、预分频 PSC 和 ARR 共同决定，占空比通常与 CCR 和 ARR 的比例有关。工程

上需要根据负载选择合适频率，比如 LED 调光要避免可见闪烁，电机控制要兼顾噪声、响应和驱动器要求，

舵机则通常需要符合固定周期和脉宽范围。。

67\. STM32 时钟树为什么重要？

> 【参考回答】STM32 的内核、总线和外设都依赖时钟，时钟树决定系统主频、AHB/APB 总线频率以及

各外设时钟来源，所以它直接影响性能、功耗和外设配置。

> 很多外设参数都依赖时钟配置，比如 UART 波特率、定时器周期、ADC 采样速度、SPI 通信速率、USB

或以太网时钟等。如果时钟树配置不对，可能出现串口乱码、定时不准、ADC 采样频率异常，甚至外设无

法正常工作。

> 排查外设问题时，不能只看 GPIO 和外设寄存器，也要检查外设时钟是否打开、总线分频是否正确、

APB 分频是否影响定时器时钟。可以说，时钟树是 STM32 外设能否正常工作的基础，很多看似外设配置错

误的问题，本质上都是时钟配置问题。。

68\. HAL 库开发和寄存器开发有什么区别？

> 【参考回答】HAL 库把底层寄存器操作封装成统一 API，开发效率高、可读性好、移植方便，适合快速

搭建工程；寄存器开发是直接操作硬件寄存器，更贴近底层，执行路径清楚，可控性和优化空间更强。

> HAL 的缺点是封装层较厚，有时执行路径不够直观，代码体积和运行开销也可能更大；寄存器开发则

要求开发者熟悉芯片手册和寄存器位定义，开发成本更高，也更容易因为位配置错误导致问题。

> 工程上常见做法是普通业务和常规外设用 HAL ꢀ高开发效率，对性能敏感、时序严格或问题定位困难

的部分，再深入到底层寄存器分析。即使主要使用 HAL，也应该能看懂它背后的寄存器配置逻辑，这样排

查问题时不会只停留在 API 调用层面。。

69\. MCU 低功耗设计通常从哪些方面考虑？

> 【参考回答】MCU 低功耗设计首先要从电源模式考虑，比如运行模式、睡眠模式、停止模式、待机模

71\. UART 的基本通信原理是什么？

> 【参考回答】UART 是一种异步串行通信方式，通信双方不共享时钟，而是ꢀ前约定相同的波特率、数

据位、校验位和停止位。发送端按照约定格式逐位发送数据，接收端根据波特率进行采样，从而恢复出原

始数据。

> 典型 UART 帧包括起始位、数据位、可选校验位和停止位。空闲状态通常为高电平，起始位为低电平，

接收端检测到起始位后，会按照约定时序采样后续数据位。由于 UART 本身是字节流通信，应用层通常还

需要设计帧头、长度、命令字和校验来区分完整数据包。

> UART 结构简单、成本低，常用于 MCU 和传感器、调试串口、蓝牙模块、上位机之间通信。它的缺点

是点对点通信更常见，抗干扰能力和传输距离有限，如果需要远距离或多节点通信，通常会结合 RS485 等

物理层方案。

72\. UART 和 RS485 有什么区别？

73\. Modbus RTU 的基本特点是什么？

> 【参考回答】ModbusRTU 是工业现场常见的主从式通信协议，通常运行在 RS485 总线上。主机发送请

求，从机根据地址进行响应，通信帧一般包含从机地址、功能码、数据域和 CRC 校验。

> 它的特点是简单、公开、稳定，适合传感器、仪表、变频器、电机驱动器等设备通信。RTU 模式采用

二进制方式传输，相比 ASCII 模式效率更高，但对帧间隔和接收时序也更敏感。

> ModbusRTU 没有显式帧头和帧尾，而是依靠总线空闲时间来区分帧边界。接收时要处理地址匹配、功

74\. 自定义通信协议帧一般怎么设计？

> 【参考回答】一个可靠的自定义通信协议帧通常包含帧头、版本号或命令字、长度、序号、数据区、

校验和帧尾等字段。帧头用于快速定位一帧开始，长度用于确定数据边界，命令字用于区分业务类型，校

验用于发现传输错误。

> 如果数据区中可能出现帧头或帧尾字节，就要考虑转义机制，或者采用以长度字段为主的解析方式。

对于可靠性要求更高的场景，还可以加入序号、应答、重传、超时和错误码机制，避免丢包、粘包或重复

包带来的问题。

> 嵌入式串口协议解析一般建议使用状态机，不要假设一次接收就能拿到完整数据帧。比较稳妥的流程

是先寻找帧头，再读取长度，根据长度接收数据，最后进行校验，校验通过后再交给业务层处理；校验失

败或超时则丢弃异常帧并重新同步。

错误。

> CRC 常见参数包括多项式、初始值、输入输出是否反转、最终异或值等。不同协议使用的 CRC 参数可

> 需要注意，CRC 主要用于检错，不是纠错。通信中如果 CRC 校验失败，通常应丢弃本帧，并根据协议

设计决定是否请求重传、等待下一帧或记录错误次数。相比简单累加和，CRC 可靠性更高；但如果资源非

常有限、数据很短且可靠性要求不高，累加和也可能被采用。

76\. I2C 的基本通信过程是什么？

> 【参考回答】I2C 是一种两线制同步串行总线，主要由 SCL 时钟线和 SDA 数据线组成。通信通常由主

机发起，主机负责产生时钟和起始、停止条件，从机根据地址进行响应。

> 一次典型 I2C 传输包括起始信号、从机地址、读写位、应答位、数据字节和停止信号。主机发送地址

后，匹配地址的从机会返回 ACK；之后每传输 8bit 数据，接收方也会返回 ACK 或 NACK，用来表示是否继

续通信。

> I2C 适合板级短距离、低速多设备通信，比如 EEPROM、IMU、温度传感器等。它的优点是线少、支持

多从机，缺点是速度和抗干扰能力不如 SPI 或差分总线。由于 I2C 依赖总线时序和上拉电阻，实际调试时

也要关注波形质量、地址配置和 ACK 响应。

77\. I2C 为什么需要上拉电阻？

> 【参考回答】I2C 的 SDA 和 SCL 通常采用开漏或开集输出结构，设备只能主动把总线拉低，不能主动

输出高电平。总线释放后，需要依靠上拉电阻把电平拉回高电平。

> 这种设计的好处是多个设备可以共享同一条总线。只要有任意一个设备拉低，总线就是低电平，从而

避免一个设备输出高电平、另一个设备输出低电平造成硬件冲突。同时，这种结构也支持 I2C 的线与逻辑

和多主仲裁机制。

> 上拉电阻的取值不能随便选。阻值太大，上升沿会变慢，影响高速通信；阻值太小，低电平时电流较

大，会增加功耗，也可能超过器件驱动能力。实际选择时要结合总线电容、通信速率、供电电压和器件手

册综合确定。

78\. I2C 仲裁机制是什么？

> 【参考回答】I2C 支持多主机通信，仲裁机制用于解决多个主机同时发起通信的问题。由于 I2C 总线是

开漏结构，多个设备同时驱动时，低电平具有优先权，总线表现出线与特性。

> 仲裁过程中，每个主机一边发送数据，一边读取 SDA 电平。如果某个主机发送高电平，但读到的却是

低电平，说明有其他主机正在拉低总线，它就认为自己失去仲裁，并停止发送；发送低电平的一方可以继

续通信。这样可以在不破坏总线数据的情况下完成仲裁。

> 在普通单主机 MCU 项目中，多主仲裁可能用得不多，但理解这个机制有助于理解 I2C 为什么要使用开

漏输出和上拉电阻。面试中可以总结为：**I2C** 仲裁依赖开漏结构、线与逻辑和边发送边检测 **SDA** 的机制

79\. I2C 时钟延展是什么？

> 【参考回答】I2C 时钟延展是指从机在来不及处理数据时，主动把 SCL 拉低，延长时钟低电平时间，让

主机暂时等待。从机释放 SCL 后，主机才能继续产生后续时钟。

> 这个机制允许慢速从机和快速主机协同工作。比如从机内部需要准备数据、完成转换、处理缓冲区，

或者暂时无法继续响应时，就可能使用 **clockstretching** 来拖慢通信节奏。

> 实际调试中，如果 I2C 总线卡住，可以检查是否有设备一直拉低 SCL 或 SDA。另外，并不是所有主机

驱动都能很好支持时钟延展，所以要结合 MCU 手册、驱动实现和从机规格书确认。可以总结为：时钟延展

本质上是从机通过拉低 **SCL** 让主机等待。

80\. I2C 总线上两个从设备地址冲突会发生什么？

> 【参考回答】如果两个 I2C 从设备地址完全相同，主机发送该地址时，两个设备都会同时响应 ACK。

后续读写过程中，两个设备都会认为主机正在和自己通信，从而导致总线行为异常。

> 写操作时，两个设备可能同时接收同一份数据，造成误配置或状态异常；读操作时，两个设备可能同

时驱动 SDA。如果它们输出的数据不同，总线会呈现线与效果，主机读到的数据可能不是任何一个设备的

真实数据，结果不可预测。

> 解决方法包括修改器件的硬件地址脚、选择不同地址版本的器件、使用 **I2C** 多路复用器、把设备挂到

不同 I2C 控制器，或者通过片选、电源控制等方式让同一时刻只有一个设备在线。工程上在选型阶段就要

检查 I2C 地址，避免后期硬件冲突难以修改。

81\. SPI 的基本通信原理是什么？

> 【参考回答】SPI 是一种同步串行通信协议，通常包含 SCLK、MOSI、MISO 和 CS 四根信号线。主机负

责产生时钟 SCLK，并通过 CS 片选信号选择具体从机，数据则通过 MOSI 和 MISO 两条数据线进行传输。

> SPI 通常支持全双工通信，也就是发送和接收可以同时进行。数据会在时钟边沿移入和移出，因此即使

主机只是想读取从机数据，也需要发送 dummy 字节来产生时钟，让从机把数据移出来。

> SPI 的优点是速度快、协议简单、时序直接，常用于 Flash、屏幕、ADC、传感器等高速外设；缺点是线

数较多，多从机时通常每个从机都需要独立 CS。工程调试时要重点关注片选时序、时钟频率、数据位宽、

位序以及 SPI 模式是否匹配。（烤鸭嵌入式免费分享，请勿商用）

82\. SPI 的 CPOL 和 CPHA 是什么？

> 【参考回答】CPOL 表示时钟空闲电平，CPHA 表示数据采样发生在哪个时钟边沿，两者组合形成 SPI

的四种工作模式。主机和从机的 CPOL、CPHA 配置必须一致，否则很容易出现数据错位或读写错误。

> CPOL=0 表示 SCLK 空闲时为低电平，CPOL=1 表示 SCLK 空闲时为高电平。CPHA=0 通常表示在第一个有

效边沿采样数据，CPHA=1 表示在第二个有效边沿采样数据。具体设备支持哪种模式，要以芯片手册或外设

手册为准。

83\. SPI 和 I2C 有什么区别？

> 【参考回答】I2C 使用 SCL 和 SDA 两根线，支持多从机寻址，硬件连接简单，但速度相对较低，协议

时序也更复杂；SPI 通常至少需要 SCLK、MOSI、MISO 和 CS 四根线，速度更快、时序更直接，但多从机时

> 从通信方式看，I2C 是一条数据线分时读写，更偏半双工思想；SPI 通常可以全双工通信，发送和接收

同时进行。I2C 有 ACK、地址、仲裁、时钟延展等机制，而 SPI 本身通常没有统一的寻址和应答机制，很多

置接口；高速、大数据量、对时序明确的外设更适合 SPI，比如 Flash、屏幕、高速 ADC 等。实际项目中还

要看芯片本身支持什么接口、PCB 布线复杂度和通信速率要求。

84\. CAN 总线有什么特点？

> 【参考回答】CAN 是一种多主、差分、面向消息的现场总线，广泛用于汽车电子和工业控制。它具有

抗干扰能力强、支持多节点通信、实时性较好、错误检测机制完善等特点。

> CAN 不是按传统设备地址通信，而是通过报文 **ID** 表示消息含义和优先级。节点根据 ID 判断是否接收

某条消息；当多个节点同时发送时，CAN 会通过非破坏性仲裁机制决定谁先发送，通常 ID 数值越小，优先

级越高。

> CAN 的优势在于可靠性和现场适应能力强，比如差分传输ꢀ升抗干扰能力，CRC 和错误帧机制ꢀ高通

信可靠性，自动重发和总线仲裁机制ꢀ高系统稳定性。可以总结为：CAN 不是简单串口总线，而是带有仲

裁、错误处理和广播通信思想的工业现场总线。

85\. CAN 仲裁机制是怎么实现的？

> 【参考回答】CAN 使用非破坏性位仲裁机制。总线上显性位可以覆盖隐性位，节点在发送数据的同时

也会监听总线电平，用来判断自己是否仍然拥有总线发送权。

> 仲裁过程中，如果某个节点发送的是隐性位，但监听到总线上是显性位，就说明有更高优先级的报文

正在发送，该节点会退出仲裁并等待下次发送；而发送显性位的节点继续传输。因此仲裁不会破坏总线上

正在传输的高优先级报文。

> 由于仲裁发生在 ID 字段，ID 数值越小，二进制中越早出现显性位 0，优先级通常越高。这个机制保证

多个节点同时发送时，总线上最终留下最高优先级的消息，低优先级节点不会丢失数据，只是延后发送。

86\. CAN 如何进行错误检测和处理？

> 【参考回答】CAN 协议内置了比较完善的错误检测机制，常见包括位错误、填充错误、CRC 错误、格

式错误和 ACK 错误。节点在发送或接收过程中如果检测到错误，会发送错误帧，通知总线上的其他节点当

前报文无效，从而避免错误数据被继续使用。

> CAN 控制器内部还会维护发送错误计数器和接收错误计数器。根据错误计数的变化，节点会处于

ErrorActive、ErrorPassive 或 BusOff 等状态。轻微错误时节点仍可正常参与通信；错误严重时会进入 BusOff

状态，主动脱离总线，避免故障节点持续干扰整个系统。

> 工程调试中，如果 CAN 通信异常，不能只看软件代码，还要检查波特率配置、采样点、终端电阻、总

线电平、CANH/CANL 接线、ID 过滤、收发器供电和共地情况。尤其是 BusOff 问题，往往和总线物理层、波

特率不一致或终端匹配有关，需要结合示波器、逻辑分析仪和错误计数器一起排查。

五、网络通信

87\. TCP 和 UDP 有什么区别？

> 【参考回答】TCP 是面向连接、可靠、字节流协议，会通过确认、重传、排序、流量控制和拥塞控制

等机制，尽量保证数据可靠、有序到达；UDP 是无连接、尽力而为、数据报协议，不保证可靠性和顺序，

但协议开销更小、延迟更低。

> TCP 适合文件传输、远程登录、HTTP、控制命令等对可靠性要求较高的场景；UDP 适合实时音视频、

广播发现、简单查询、部分传感器数据上报等对延迟敏感、能够容忍一定丢包的场景。

> 在嵌入式项目中，选择 TCP 还是 UDP 要结合可靠性、实时性、资源开销和协议复杂度来判断。TCP 省

去了很多应用层可靠性设计，但连接维护和协议栈资源开销更大；UDP 简单快速，但如果业务要求可靠传

输，就需要应用层自己处理丢包、乱序、重传和超时。

88\. TCP 三次握手和四次挥手是什么？

> 【参考回答】TCP 三次握手用于建立连接。客户端先发送 SYN，服务端回复 SYN+ACK，客户端再回复

ACK。这个过程主要是为了确认双方的发送和接收能力都正常，并同步双方的初始序列号。

> TCP 四次挥手用于关闭连接。因为 TCP 是全双工通信，两个方向的数据传输需要分别关闭。一端发送

FIN 表示自己不再发送数据，对端先回复 ACK 确认，等对端数据也发送完后，再发送 FIN，最后由另一端回

复 ACK 完成关闭。

> 可以补充 TIME_WAIT 的作用：主动关闭方会等待一段时间，主要是为了处理可能重传的 FIN，确保最

后的 ACK 能被对端收到，同时避免旧连接残留报文影响后续新连接。面试中可以总结为：三次握手是建立

可靠连接，四次挥手是分别关闭双向通道。

89\. TCP 粘包是什么？如何解决？

> 【参考回答】TCP 是字节流协议，本身没有消息边界。发送端多次 write 的数据，接收端可能一次 read

读到；发送端一次 write 的数据，也可能被接收端分多次 read 读到，这就是常说的粘包和拆包现象。

> 解决方法是在应用层设计明确的消息边界。常见方案包括固定长度消息、分隔符协议、长度字段协议

和 TLV 格式。只要接收端能根据协议准确拆出完整消息，粘包就不是问题。

> 在嵌入式网络通信中，比较推荐使用长度字段**+**校验的方式。接收端先把数据放入缓冲区，判断是否已

经够一帧完整数据；如果不够就继续等待，如果够了再解析和校验。不能假设一次 recv 就一定对应一整帧

数据，这是 TCP 通信中很常见的错误。（烤鸭嵌入式免费分享，请勿商用）

90\. MQTT 的基本原理是什么？

> 【参考回答】MQTT 是一种轻量级的发布**/**订阅协议，常用于物联网设备通信，通常运行在 TCP 之上。

客户端不直接点对点通信，而是连接到 Broker，通过 topic 发布消息或订阅消息。

> 相比传统点对点通信，发布/订阅模式可以降低设备之间的耦合。设备不需要知道其他设备的地址，只

需要约定主题即可。MQTT 还支持 **QoS** 等级、心跳保活、遗嘱消息等机制，用于ꢀ升消息投递可靠性和连

接状态感知能力。

> 嵌入式设备使用 MQTT 时，要关注网络稳定性、心跳间隔、断线重连、消息缓存、功耗和内存占用。

它适合物联网数据上报、远程配置和状态同步，但不适合对延迟和确定性要求极高的强实时闭环控制场景。

六、RTOS / FreeRTOS

91\. 裸机和 RTOS 有什么区别？

> 【参考回答】裸机程序通常是主循环**+**中断的前后台结构，主循环处理主要业务，中断处理实时事件，

整体逻辑简单、资源开销小；RTOS 则ꢀ供任务调度、任务间通信、同步、延时和定时器等机制，可以把系

统拆分成多个任务，让多个功能看起来并发运行。

> 当系统功能较少、实时关系简单时，裸机完全可以胜任，比如简单采集、按键、显示和通信等场景。

随着功能增多，例如通信、控制、传感器采集、日志、状态监控同时存在，RTOS 可以让模块划分更清晰，

也更方便处理不同任务之间的优先级和同步关系。

> RTOS 并不是一定比裸机高级，它也会带来调度开销、任务栈管理、优先级设计和并发访问问题。是否

使用 RTOS，要看系统复杂度、实时性需求、资源余量和后期维护成本。可以总结为：裸机简单可控，**RTOS**

更适合复杂多任务系统。

在 CPU 上执行；就绪态表示任务已经具备运行条件，只是暂时没有抢到 CPU。

93\. FreeRTOS 的任务调度机制是什么？

> 【参考回答】FreeRTOS 通常采用基于优先级的抢占式调度。系统总是优先运行当前就绪任务中优先级

最高的任务，一旦高优先级任务变为就绪态，就可以抢占正在运行的低优先级任务。

> 如果启用了时间片调度，同优先级任务之间可以按照系统 tick 轮转运行；不同优先级任务之间，则始

终优先保证高优先级任务执行。任务调度的触发点包括 tick 中断、任务主动阻塞、任务被唤醒、中断退出

以及显式让出 CPU 等。

> 在 Cortex-M 平台上，FreeRTOS 调度通常和 **SysTick**、**PendSV** 等机制有关。SysTick 负责产生系统节拍，

PendSV 常用于执行上下文切换。这样可以把真正的任务切换放到较低优先级的异常中处理，降低普通中断

服务函数的复杂度。

94\. FreeRTOS 任务优先级如何设计？

> 【参考回答】任务优先级设计要围绕实时性、重要性和阻塞关系来定，而不是谁代码多谁优先级高。

可以缓解优先级反转问题。

106\. 进程和线程有什么区别？

> 【参考回答】进程是操作系统进行资源分配的基本单位，通常拥有独立的虚拟地址空间、文件ꢁ述符

表、信号处理信息等资源；线程是 CPU 调度执行的基本单位，同一进程内的多个线程共享进程的地址空间

和大部分资源，但每个线程有自己的栈、寄存器上下文和线程局部数据。

> 从隔离性看，进程之间隔离更强，一个进程崩溃通常不会直接破坏另一个进程；线程之间共享内存，

通信更方便，切换开销也相对更小，但也更容易产生数据竞争、死锁和同步问题。因此线程适合共享大量

数据、需要较低切换开销的场景，进程适合强调隔离性、稳定性和模块边界的场景。

> 工程上不能简单说线程一定比进程好。比如嵌入式 Linux 应用中，关键服务可以用多进程隔离，避免

一个模块崩溃拖垮整个系统；同一个进程内部的数据处理、通信收发、日志写入可以用多线程ꢀ高并发能

力。可以总结为：进程重隔离，线程重共享；进程更稳定，线程通信更方便但同步更复杂。

107\. 进程间通信方式有哪些？

> 【参考回答】常见进程间通信方式包括管道、FIFO、有名管道、消息队列、共享内存、信号、信号量、

Socket、UnixDomainSocket、eventfd 等。不同 IPC 机制的侧重点不同，有的适合传递字节流，有的适合传递

结构化消息，有的适合大数据共享，有的适合事件通知。

> 管道适合有亲缘关系进程之间的简单字节流通信；FIFO 可以用于无亲缘关系进程；消息队列适合传递

结构化消息；共享内存效率最高，适合图像帧、点云、传感器大块数据等高吞吐场景，但需要额外同步；

Socket 适合跨主机通信，UnixDomainSocket 适合本机进程间通信，接口形式和网络编程类似。

> 回答时不要只机械列名字，最好能按场景比较。比如是否需要跨主机、是否需要高吞吐、是否需要结

构化消息、是否需要同步、是否要求简单可靠，这些都会影响选型。可以总结为：小数据通知可以用管道、

消息队列或信号，大数据共享适合共享内存，跨主机或统一通信接口适合 **Socket**。

108\. 共享内存为什么效率高？需要注意什么？

> 【参考回答】共享内存效率高，是因为它把同一块物理内存映射到多个进程的虚拟地址空间中。多个

进程读写这块数据时，不需要像管道、消息队列那样频繁经过内核拷贝，也不需要在发送方和接收方之间

反复复制大块数据。

> 但共享内存只解决数据共享问题，不解决并发同步问题。多个进程同时读写共享内存时，如果没有同

步机制，就可能出现数据覆盖、读到半包数据、状态不一致等问题。因此共享内存通常要配合互斥锁、信

程上要设计好数据结构、缓冲区长度、读写索引、数据有效标志和生命周期管理。可以总结为：共享内存

快在少拷贝，但难在同步和一致性管理。

109\. 互斥锁和自旋锁有什么区别？

> 【参考回答】互斥锁在拿不到锁时，线程通常会进入阻塞睡眠状态，让出 CPU，等锁释放后再被唤醒；

自旋锁在拿不到锁时，不会睡眠，而是一直循环检查锁状态，直到锁可用为止。

> 互斥锁适合临界区较长、等待时间不确定，或者临界区中可能发生阻塞的场景。自旋锁适合临界区非

常短、等待时间很短，并且当前上下文不能睡眠的场景。自旋锁的好处是避免线程睡眠和唤醒的调度开销，

缺点是等待期间会一直消耗 CPU。

> 在用户态应用中，大多数场景更常用互斥锁；在内核或强实时短临界区中，自旋锁更常见。选择时要

看两个关键点：等待时间长不长，以及当前上下文能不能睡眠。如果临界区很长却使用自旋锁，会浪费CPU；

如果不能睡眠的上下文使用互斥锁，也可能导致严重问题。

110\. 信号量和条件变量有什么区别？

> 【参考回答】信号量内部维护一个计数值，可以表示资源数量或事件次数。post 操作会增加计数，wait

操作会减少计数；如果计数为 0，线程执行 wait 时就会阻塞。它适合资源池、生产者消费者、并发数量限

制等场景。

> 条件变量本身不保存资源数量，也不直接表示事件次数，它通常要配合互斥锁使用，用来让线程等待

某个共享条件变为真。比如队列非空、缓冲区不满、某个状态初始化完成等，这些条件通常由互斥锁保护

的共享变量表示。

> 使用条件变量时，一定要在循环中检查条件，典型写法是加锁后用 while 判断条件，不满足就

pthread_cond_wait，返回后再次判断。这是因为可能存在虚假唤醒，也可能多个线程被唤醒后竞争同一个

条件，导致某个线程醒来时条件已经不满足。可以总结为：信号量自己带计数，条件变量只负责等待条件

变化，真正的条件状态要由共享变量表示。

111\. 死锁发生的四个必要条件是什么？如何避免？

> 【参考回答】死锁的四个必要条件是互斥、占有且等待、不可抢占和循环等待。互斥是指资源同一时

刻只能被一个线程或任务占用；占有且等待是指已经持有资源的同时还在等待其他资源；不可抢占是指资

源不能被强制拿走，只能由持有者主动释放；循环等待是指多个线程之间形成首尾相接的等待关系。

> 四个条件同时成立时，系统就可能进入一组线程互相等待、都无法继续执行的状态。比如线程 A 先拿

锁 1 再等锁 2，线程 B 先拿锁 2 再等锁 1，就形成了典型的循环等待。实际工程中，多个锁的获取顺序不

一致，是非常常见的死锁原因。

> 避免死锁可以从破坏条件入手。常见做法包括统一加锁顺序、减少锁嵌套、缩小临界区、避免持锁调

用外部复杂函数、使用 trylock、设置超时机制等。如果获取多个锁失败，可以释放已经持有的锁后重试。

面试中可以总结为：死锁不是靠某一个技巧解决，而是靠资源顺序、锁粒度和异常路径设计共同避免。

112\. 虚拟内存和物理内存有什么区别？

> 【参考回答】物理内存是真实存在的 RAM，虚拟内存是操作系统ꢀ供给每个进程看到的地址空间。用

户程序中使用的指针通常是虚拟地址，CPU 访问内存时，会通过 MMU 和页表把虚拟地址转换成对应的物

理地址。

> 虚拟内存带来的好处很多。首先，每个进程都有独立的虚拟地址空间，进程之间相互隔离，一个进程

不能随意访问另一个进程的内存；其次，程序可以看到连续的虚拟地址，而底层物理内存可以是不连续的；

此外，操作系统还可以基于虚拟内存实现权限保护、按需分配、共享库映射、文件映射和换页等机制。

> 在嵌入式 Linux 中要特别注意，用户态程序看到的地址一般不是物理地址。比如 malloc 返回的是虚拟

地址，普通应用不能直接拿这个地址给硬件 DMA 使用。驱动开发、DMA 缓冲区、mmap 映射等场景才会

更直接地涉及物理地址、总线地址和缓存一致性问题。可以总结为：虚拟内存面向进程和隔离，物理内存

面向真实硬件资源。

113\. malloc 返回的是虚拟地址还是物理地址？会立即分配物理页吗？

> 【参考回答】在 Linux 用户态，malloc 返回的是进程虚拟地址空间中的地址，也就是虚拟地址，不是

物理地址。程序通过这个地址访问内存时，最终由 CPU、MMU 和页表完成虚拟地址到物理地址的转换。

> 很多情况下，malloc 成功并不一定表示已经立刻分配了等量的物理内存。Linux 通常采用惰性分配策

略，malloc 可能只是分配了一段虚拟地址范围，或者调整了堆管理结构；只有当程序真正读写这块内存时，

才可能触发缺页异常，由内核分配实际物理页并建立页表映射。

> 所以，申请一大块内存但不访问，不一定会马上占用等量物理内存。不过具体行为也和分配大小、glibc

实现、brk/mmap 策略、内核 overcommit 配置等因素有关。工程上要注意，malloc 返回成功不代表后续访

问一定完全安全，内存真正使用时仍可能因为物理内存不足触发 OOM 等问题。可以总结为：**malloc** 返回

虚拟地址，物理页通常在实际访问时才按需分配。

114\. fork 和 exec 有什么区别？

> 【参考回答】fork 用于创建一个新进程，子进程会从父进程复制出一份执行上下文，包括地址空间、

文件ꢁ述符等资源。fork 会返回两次：在父进程中返回子进程 PID，在子进程中返回 0，因此父子进程会从

fork 调用之后继续向下执行。

> exec 系列函数则不是创建新进程，而是用一个新的程序镜像替换当前进程的代码段、数据段、堆栈等

内容。exec 执行成功后，当前进程会变成另一个程序继续运行，但进程 PID 通常不变，原来的用户态代码

不会再继续执行。

> 典型场景是 shell 执行命令：先 fork 创建子进程，再在子进程中 exec 目标程序，父进程则等待或管理

子进程。可以简单总结为：**fork** 负责创建一个新进程，**exec** 负责让当前进程加载并运行新程序。这两个机

制配合起来，就能实现 Linux 中常见的进程创建和程序启动流程。

115\. 用户态和内核态有什么区别？为什么要区分？

> 【参考回答】用户态是普通应用程序运行的权限级别，权限受限，不能直接访问硬件寄存器、内核内

存和关键系统资源；内核态是操作系统内核运行的权限级别，拥有更高权限，可以管理进程调度、内存、

文件系统、网络协议栈和设备驱动等资源。

> 区分用户态和内核态主要是为了安全性和稳定性。如果应用程序可以随意访问硬件或内核内存，一个

普通 bug 就可能破坏整个系统，甚至导致系统崩溃。通过权限隔离，用户程序即使出错，通常也只会影响

自身进程，不会直接破坏内核和其他进程。

> 用户程序需要访问文件、网络、设备或申请系统资源时，不能直接操作底层硬件，而是通过系统调用、

设备文件、ioctl、mmap 等受控入口进入内核，由内核完成实际操作。嵌入式 Linux 中，应用层和驱动层的

边界就是围绕这个机制建立的。可以总结为：用户态负责业务逻辑，内核态负责资源管理和硬件访问，二

者隔离是为了让系统更安全、更稳定。

116\. select、poll 和 epoll 有什么区别？

> 【参考回答】select、poll 和 epoll 都是 Linux 中的 **IO** 多路复用机制，作用是让一个线程同时监听多个

文件ꢁ述符，避免为每个连接都创建一个线程。它们都可以用于网络 socket、管道、设备文件等场景，但

实现方式和适用规模不同。

> select 使用固定大小的 fd_set 保存关注的文件ꢁ述符，通常存在文件ꢁ述符数量限制，并且每次调用

前都要重新设置 fd 集合；poll 使用数组保存 fd，突破了 select 固定大小限制，但本质上仍然需要把数组传

给内核并线性扫ꢁ结果。连接数较少时，select 和 poll 实现简单，性能也通常够用。

> epoll 会把关注的 fd 注册到内核维护的兴趣列表中，事件就绪后返回就绪事件列表，不需要每次都完

整传入和遍历全部 fd，因此更适合大量连接和高并发场景。需要注意，不是任何情况下 epoll 都一定更快，

少量 fd 时 select/poll 也完全够用。工程选型要结合连接数量、事件频率、代码复杂度和平台支持情况。

117\. TCP 服务端建立连接需要哪些 socket API？

> 【参考回答】TCP 服务端典型流程是 **socket**、**bind**、**listen**、**accept**。socket 用于创建套接字，bind 用于

绑定本地 IP 和端口，listen 让套接字进入监听状态，accept 用于接收客户端连接，并返回一个新的连接套

接字。

> 这里要区分监听 **socket** 和连接 **socket**。监听 socket 只负责等待和接受新的客户端连接，不直接用于和

某个客户端收发业务数据；accept 返回的新 socket 才用于和该客户端进行 recv/send 或 read/write 通信。

原来的监听 socket 会继续保留，用来接收后续新的连接。

> 工程中还要考虑端口复用、阻塞或非阻塞模式、超时处理、异常断开、TCP 粘包、多客户端并发管理

等问题。比如服务器重启时常设置 SO_REUSEADDR，避免端口短时间无法绑定；如果要同时处理多个客户

端，可以结合多线程、select/poll/epoll 或事件循环模型来实现。

124\. 写时复制 COW 是什么？它解决了什么问题？

> 【参考回答】写时复制，全称 CopyOnWrite，是一种延迟复制的内存优化机制。它的核心思想是：当

多个进程最初拥有相同数据时，系统不立即复制完整数据，而是先让它们共享同一份物理内存，并把相关

页面设置为只读；只有当某个进程真的要写这块内存时，才触发缺页异常，由内核复制出一份新的物理页

给写入方使用。

> fork 是写时复制最典型的应用场景。如果 fork 时立刻复制父进程完整地址空间，成本会非常高，尤其

是父进程占用内存较大时。但很多场景下，fork 之后子进程马上调用 exec 加载新程序，之前复制的大量内

存根本用不上。COW 可以避免这种浪费，让 fork 更轻量，只有实际被修改的页面才发生复制。

> 从工程角度看，COW 既保证了父子进程地址空间的独立性，又降低了内存和时间开销。它依赖页表权

限、物理页引用计数和缺页异常处理等内核机制。回答时可以抓住三个过程：先共享只读页面，写入时触

发缺页异常，内核复制页面并更新页表。这样能体现对虚拟内存机制的理解，而不是只停留在“延迟拷贝”

这个概念上。

125\. 缺页中断是什么？常见触发场景有哪些？

> 【参考回答】缺页中断也常叫缺页异常，指 CPU 访问某个虚拟地址时，发现页表中没有有效的物理页

映射，或者访问权限不满足要求，于是触发异常交给内核处理。虽然名字里有“中断”，但它更准确地说是

一种同步异常，因为它是由当前指令访问内存直接引发的。

> 常见触发场景有几类。第一类是惰性分配，比如 malloc 申请了一大块虚拟地址空间，但内核不一定立

即分配物理页，只有真正访问时才分配；第二类是文件映射或 mmap，访问尚未加载的页面时需要从文件

加载；第三类是写时复制，fork 后父子进程共享只读页面，某一方写入时触发缺页异常完成复制；第四类

是非法访问，比如访问空指针、越界地址或写只读页面。

> 所以缺页中断本身不一定是错误，它也是虚拟内存正常工作的一部分。关键要看内核能不能为这次访

132\. epoll 的 LT 和 ET 模式有什么区别？

> 【参考回答】epoll 的 LT 是水平触发，ET 是边缘触发。LT 模式的语义比较直观：只要文件ꢁ述符上还

有数据可读，或者缓冲区仍然可写，epoll_wait 就会持续返回这个事件。也就是说，如果本次没有把数据读

完，下次 epoll_wait 还会继续ꢀ醒，因此 LT 模式更容易写对，是比较稳妥的默认选择。

> ET 模式的语义是状态发生变化时才通知一次，比如从不可读变为可读时通知。如果通知后应用没有把

数据一次性读到 EAGAIN，下次不一定再收到事件，可能导致内核缓冲区里还有数据，但程序不再处理。因

此 ET 模式通常要求 fd 设置为非阻塞，并且收到事件后循环 read 或 write，直到返回 EAGAIN 或 EWOULDBLOCK

为止。

> ET 模式的优势是减少重复通知，在高并发场景下可能降低事件触发次数，但对状态机和缓冲区处理要

求更高。LT 模式使用简单、调试方便，适合大多数场景；ET 模式适合对性能要求更高、并且代码能严格处

理非阻塞读写的场景。可以总结为：**LT** 是只要条件满足就反复通知，**ET** 是状态变化时通知一次。

141\. pthread_mutex 和 pthread_rwlock 有什么区别？

> 【参考回答】pthread_mutex 是互斥锁，用来保护临界区，保证同一时刻只有一个线程访问共享资源。

无论是读操作还是写操作，只要进入被 mutex 保护的区域，其他线程都需要等待，因此它语义简单、使用

直观，适合临界区较短、读写比例不明显，或者共享资源状态比较复杂的场景。

> pthread_rwlock 是读写锁，它把访问分为读锁和写锁。多个线程可以同时持有读锁，因为只读操作不

会互相破坏；但写锁是独占的，写线程进入时不能有其他写线程，也不能有读线程。它适合读多写少的场

景，比如配置表、路由表、缓存索引、状态查询表等，可以在大量读操作时ꢀ高并发性能。

> 但读写锁并不一定总比互斥锁好。读写锁内部维护更复杂，如果临界区很短、读写比例不明显，额外

管理开销可能不划算；如果读线程持续不断，还可能导致写线程饥饿，具体取决于实现策略。可以总结为：

**mutex** 简单通用，**rwlock** 适合读多写少；选型要看共享资源访问模式、临界区长度和饥饿风险。

142\. futex 是什么？它和用户态锁有什么关系？

> 【参考回答】futex 全称 FastUserspaceMutex，是 Linux ꢀ供的一种用户态和内核态配合的同步机制。

它的核心思想是：锁没有竞争时，尽量只在用户态通过原子操作完成加锁和解锁；只有发生竞争、线程需

要睡眠等待时，才进入内核使用 futex 系统调用挂起或唤醒线程。

> 如果普通互斥锁每次加锁、解锁都进入内核，开销会比较大。futex 把无竞争路径放在用户态处理，速

度很快；当发生竞争时，再让内核参与线程阻塞和唤醒，避免线程一直自旋浪费 CPU。pthread_mutex 这类

高层同步原语，底层很多实现都会利用 futex 机制来ꢀ高性能。

> 可以把 futex 理解为构建高性能锁、条件变量等同步原语的底层工具，而不是业务代码里最常直接使

用的锁。它通常需要配合用户态的原子变量表示锁状态，内核只负责在指定地址上等待和唤醒。面试中抓

住一句话即可：**futex** 的核心价值是无竞争时用户态解决，有竞争时再进入内核睡眠等待。

143\. 条件变量为什么通常要配合互斥锁使用？

> 【参考回答】条件变量用于线程之间等待某个条件成立，比如队列非空、缓冲区有空间、任务完成等。

它本身不保存业务条件，真正的条件通常由共享变量表示，因此条件变量必须和互斥锁配合使用。互斥锁

负责保护共享条件的检查和修改，条件变量负责让线程在条件不满足时睡眠、在条件变化时被唤醒。

144\. 线程池的作用是什么？设计时需要注意哪些问题？

> 【参考回答】线程池的作用是复用一组已经创建好的工作线程，避免频繁创建和销毁线程带来的开销。

服务端程序、异步任务处理、日志压缩、图像处理等场景中，如果每来一个任务就创建一个线程，任务量

根据业务负载设计。

增长，否则内存可能被打爆；线程数不是越多越好，CPU 密集型任务一般接近 CPU 核心数，IO 密集型任务

可以适当更多；还要处理异常、资源释放和优雅退出。可以总结为：线程池是控制并发度、复用线程、削

峰填谷的工程工具。
