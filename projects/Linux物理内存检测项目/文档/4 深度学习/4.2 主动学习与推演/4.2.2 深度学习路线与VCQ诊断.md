## 深度学习路线与 VCQ 诊断

这份 wiki 的目标不是让你“从第一页看到最后一页”，而是让你最后能：

- 画出完整链路；
- 落到具体函数、字段和 map；
- 手算两个指数；
- 找出代码中的隐式假设和缺陷；
- 面对变体问题时重新设计。

## 每次开始先做 5 问诊断

不要先看答案。每题用自己的话说 60～90 秒，并按 0～10 分自评。

### Q1：项目痛点

这个工具检测的究竟是什么？为什么总空闲内存足够，高阶页分配仍可能失败？

<details>
<summary>标准要点</summary>

Linux 的伙伴系统按 `2^order` 管理连续物理页。频繁分配释放后，空闲页可能分散在许多低阶块中；总页数够，但缺少目标 order 的连续块。项目不是测普通内存占用，而是同时观察迁移类型 fallback 事件和 node/zone/order 的连续块状态。

</details>

### Q2：eBPF 全链路

从执行用户态入口到 eBPF 回调真正运行，中间发生哪些步骤？

<details>
<summary>标准要点</summary>

参数解析 → `ExtFrag` 选择 C 程序 → BCC/Clang 编译 → `bpf()` 创建 map 和加载程序 → verifier → JIT（可选）→ attach tracepoint/kprobe → 内核到达挂点 → eBPF 被动执行 → 写 map → Python 读 map → curses 渲染。当前快照还要先修 import 与路径不一致。

</details>

### Q3：双探针分工

为什么 `mm_page_alloc_extfrag` 用 tracepoint，而 `get_page_from_freelist` 用 kprobe？二者分别何时触发？

<details>
<summary>标准要点</summary>

tracepoint 是内核预定义事件，语义和字段较稳定；该事件在页分配器从 fallback migratetype 获取块时触发，偏事件/症状。`get_page_from_freelist` 是内部函数，没有等价 tracepoint 暴露完整 `alloc_context` 和 zone 状态，因此用 kprobe，偏状态/现场；函数在首次快速尝试和若干慢速重试中都可能被调用，不应简单说“只在 fast path 调一次”。

</details>

### Q4：map 通信

`counts_map`、`pgdat_map`、`zone_map`、`delay_map`、`last_time_map` 分别保存什么？数据方向是什么？

<details>
<summary>标准要点</summary>

`counts_map`：PID → 聚合事件快照；`pgdat_map`：node 指针键 → node 元数据；`zone_map`：zone/order 键 → 状态与指数；`delay_map`：用户态 → 内核态的采样配置；`last_time_map`：内核态维护的节流状态。当前 `last_time_map` 的 key/更新实现有缺陷，不能把设计意图当作已生效事实。

</details>

### Q5：指标计算

`free_pages`、`free_blocks_total`、`free_blocks_suitable` 如何得到？两个指数分别回答什么？

<details>
<summary>标准要点</summary>

遍历所有有效 order：块数直接累加为 total，`blocks << order` 累加为空闲页，高阶块按 `blocks << (order - suitable_order)` 折算为目标阶块。unusable 指数表示多少空闲页无法服务目标请求；extfrag index 更偏向区分“碎片主导”与“总量不足”。有 suitable block 时项目返回 -1000。

</details>

## 根据分数选择路线

| 诊断结果 | 不要做什么 | 今天的主线 |
|---|---|---|
| Q1 < 6 | 背 eBPF API | 先学页、order、伙伴系统、外部碎片 |
| Q2 < 6 | 只背“Python 进入内核” | 手画加载/挂载/触发/map 链路 |
| Q3 < 6 | 把两探针都叫“看碎片” | 对照上游 tracepoint 与页分配调用点 |
| Q4 < 6 | 死记 map 名 | 逐个画 key/value、读写方和生命周期 |
| Q5 < 6 | 背公式 | 用三组数字手算、解释每个中间量 |
| 五题都 ≥ 8 | 重读基础页 | 做源码审计、变体设计和闭卷重构 |

## 推荐的依赖顺序

```text
物理页/PFN
  -> zone/node/NUMA
  -> buddy/order/free_area
  -> 内部碎片 vs 外部碎片
  -> migratetype/pageblock/fallback
  -> get_page_from_freelist 调用路径
  -> tracepoint/kprobe
  -> verifier/helper/map
  -> BCC/Python/curses
  -> 三个中间量
  -> unusable/extfrag 两个指数
  -> 采样、并发、兼容性与生产边界
```

如果后面的概念讲不清，不要继续堆术语，回退到它的前置节点。

## 每个概念都走一遍 8 步闭环

以“BPF map”为例：

1. **动机**：eBPF 为什么不能把复杂数据直接交给 Python？
2. **心智模型**：map 是共享状态容器，不只是单向管道。
3. **最小代码**：一个 array 配置 + 一个 hash 聚合。
4. **手工追踪**：同一 PID 连续触发两次，key/value 如何变化？
5. **费曼检查**：为什么 delay 用 array、counts 用 hash？
6. **故意破坏**：把时间戳当 key，会发生什么？
7. **闭卷重建**：自己写固定 key 节流伪代码。
8. **知识链**：per-CPU map、ring buffer、并发更新、LRU hash。

其他概念也要走同样闭环，不要只阅读定义。

## 变体题库

### 伙伴系统

1. order 3 没块但 order 5 有 1 块，请求 order 3 是否一定失败？
2. 为什么 `free_blocks_suitable` 要折算高阶块，而不是只计块数？
3. PCP 中的 order-0 页是否完整反映在 zone free_area 快照中？这会怎样影响解释？

### tracepoint/kprobe

1. 如果目标内核移除了 `get_page_from_freelist` 符号，如何降级？
2. 如果改成 fentry/BPF CO-RE，兼容性和依赖有什么变化？
3. 入口探针和返回探针分别能回答什么？

### map 与采样

1. 全局 fixed-key 节流在 64 CPU 上是否严格？
2. counts 按 PID 聚合会遗漏哪些维度？
3. 为什么完整事件流更适合 ring buffer，而排行榜更适合 hash？

### 指数

1. suitable > 0 时为什么直接返回 -1000？
2. compaction 能改善碎片，但为什么不能解决总量不足？
3. 为什么必须结合 watermarks、reclaim 与 workload 看指数？

### 用户态

1. 如何让数据模型与 curses 解耦，便于接入 Prometheus/Grafana？
2. map 读取期间内核仍在更新，快照一致性如何定义？
3. 如何写一个无 curses 的 smoke test？

## 最终验收

当你能在不看资料的情况下完成下面五件事，就算真正掌握项目：

1. 两分钟项目介绍，既讲价值也讲边界；
2. 画出两种探针的完整数据流；
3. 手算一组指标并解释分歧；
4. 找出节流、路径/import、硬编码 order 三类问题；
5. 设计一个修复后可验证的最小版本。
