这页专门处理五个最容易“会背定义，却经不起追问”的难点。每一节都从真实痛点开始，落到代码和边界条件，最后用变体题检验。

## 难点一：`mm_page_alloc_extfrag` 不是“高阶请求降成低阶请求”

### 为什么容易理解错

字段名是：

```text
alloc_order
fallback_order
```

“fallback”很容易让人联想到应用层常见的降级：原来要 8 页，最后只给 2 页。但伙伴系统的页分配接口不能静默少给调用者页面；调用者请求 `order=3`，成功就必须返回 8 个连续页，失败就返回 NULL。

所以“实际只分配更小 order”在这里逻辑上就站不住。

### 先补迁移类型

伙伴系统不只按 order 分链表，还按 migratetype 区分页面用途，例如：

- `MIGRATE_UNMOVABLE`：难以迁移；
- `MIGRATE_RECLAIMABLE`：可回收；
- `MIGRATE_MOVABLE`：可迁移；
- 以及 CMA、HIGHATOMIC 等特定类型。

为什么要分？

如果可移动页和不可移动页随意混在一个 pageblock 中，未来 compaction 想搬走可移动页时，会被少数不可移动页卡住，难以形成大连续块。按迁移类型分组是一种“预防碎片”的布局策略。

### fallback 的真实场景

假设请求：

```text
alloc_order = 2
alloc_migratetype = MIGRATE_MOVABLE
```

含义：需要 4 个连续页，希望从 MOVABLE freelist 获取。

可能出现：

1. MOVABLE 的 order-2 及以上链表没有合适块；
2. 分配器按 fallback 规则检查其他 migratetype；
3. 在 UNMOVABLE 的 order-4 链表找到一块；
4. 取出 order-4 块；
5. 拆分成请求需要的 order-2 块与剩余 buddy；
6. 返回 4 个连续页给调用者；
7. 触发 tracepoint，记录：

```text
alloc_order = 2
fallback_order = 4
alloc_migratetype = MOVABLE
fallback_migratetype = UNMOVABLE
```

因此：

```text
fallback_order >= alloc_order
```

### 为什么这仍然叫 extfrag 事件

问题不是“少给了页”，而是**跨迁移类型借块可能破坏 pageblock 的长期布局**。

如果只从一个大 fallback 块取出很小一部分，剩余部分的归属、pageblock ownership 是否改变，会影响后续可移动性与连续块形成。因此上游 tracepoint 还提供 migratetype 和 `change_ownership`；trace 输出中的 `fragmenting` 也与 `pageblock_order` 有关。

### 原项目遗漏了什么

当前 `data_t` 只保存：

- PFN；
- 两个 order；
- PID/comm；
- count。

它没有保存两个 migratetype 和 ownership，所以只能说明“发生过 fallback 取块”，不能完整判断反碎片布局被怎样影响。

### 常见错误

| 错误说法 | 为什么错 | 正确说法 |
|---|---|---|
| fallback_order 是实际分配的更小阶 | 分配接口不能少给页 | 它是找到的 fallback 空闲块阶数 |
| 两个 order 差越大一定越碎 | 还缺 migratetype/pageblock 语义 | 差值只说明拆分跨度，不能单独定性 |
| 事件发生就等于分配失败 | 事件路径可能最终成功返回请求页 | 它记录 fallback 行为，不等于最终失败 |
| count 高的进程就是碎片制造者 | 进程可能只是受害者或触发者 | 需要结合分配生命周期和全局状态 |

### extfrag 事件变体题

`alloc_order=3, fallback_order=5`：最终成功返回多少页？为什么不能仅凭两个数判断 pageblock 是否改变 ownership？

答案要点：返回 `2^3=8` 页；order-5 块被拆分。还必须知道 alloc/fallback migratetype、pageblock order 和 ownership。

## 难点二：`get_page_from_freelist` 的调用时机不是一句“fast path”

### 它解决什么痛点

`alloc_pages()` 不是直接从一个全局数组里拿页。它需要考虑：

- GFP 标志允许哪些 zone；
- NUMA 本地性；
- cpuset/nodemask；
- watermarks；
- migratetype；
- 脏页与回收策略；
- 高阶请求与 compaction。

`get_page_from_freelist()` 的核心职责是沿 zonelist 尝试找到满足约束的 zone，并从伙伴系统取得页。

### 首次快速尝试

简化主线：

```text
__alloc_pages()
  -> prepare_alloc_pages()
  -> get_page_from_freelist()   # 首次尝试
  -> 成功：返回
  -> 失败：进入 __alloc_pages_slowpath()
```

首次调用常被称为 fast path，因为它希望在不做重回收/规整的情况下直接成功。

### 慢速路径里还可能再次调用

进入 slowpath 后，内核可能：

- 唤醒 kswapd；
- 调整 alloc flags；
- 直接回收；
- compaction；
- 放宽 cpuset/水位限制；
- OOM 相关处理；
- 再次尝试 `get_page_from_freelist()`。

因此 kprobe 挂在函数入口时，观测的是**所有进入该函数的尝试**，不是“每个上层分配请求恰好一次”。

### 入口探针能看到什么，不能看到什么

能看到：

- 本次尝试的 `gfp_mask`；
- 请求 `order`；
- `alloc_flags`；
- `alloc_context`；
- 进入函数前的 zone/free_area 快照。

不能直接知道：

- 这次调用最后返回了哪个 page；
- 是哪个 zone 成功；
- 是否进入过 reclaim/compaction；
- 上层整个分配请求最终成功还是失败。

如果要回答返回结果，需要 kretprobe/fexit；如果要关联一次完整请求，还需要 request id、线程上下文或成对状态，并处理嵌套/重入。

### 为什么当前扫描方式不等于内核真实决策

项目从 `preferred_zoneref` 找到 pgdat，然后直接遍历其 fallback zonelist 的前 `MAX_NR_ZONES` 项，统计状态。但内核真实 `get_page_from_freelist()` 还会应用：

- highest zone index；
- nodemask/cpuset；
- watermark；
- dirty spread；
- alloc flags；
- NUMA 与 reclaim 条件。

项目的巡检是“相关 zone 状态快照”，不是对内核分配决策的逐分支复刻。

### 为什么 kprobe 兼容性差

它依赖：

1. 函数符号存在且可探测；
2. 没有因编译优化完全内联；
3. 函数原型与项目声明一致；
4. `alloc_context` 布局一致；
5. 架构参数传递方式被 BCC 正确处理。

tracepoint 的字段是观测接口；内部函数与结构体只是实现细节。这就是两者稳定性差异的根本。

### 分配路径变体题

如果 kprobe 每秒触发 10 万次，但上层只发起 6 万次分配请求，是否一定是统计错了？

答案：不一定。一个上层请求可能在不同约束、回收/规整后多次调用该函数；还要考虑系统内其他分配请求。必须明确计数单位是“函数入口次数”还是“上层请求数”。

## 难点三：三个中间量为什么必须遍历所有 order

### `nr_free` 是块数，不是页数

```text
free_area[order].nr_free
```

表示当前 order 有多少个空闲块。一个块包含：

```text
2^order 个连续页
```

所以 order 3 的 `nr_free=2` 表示两块，每块 8 页，共 16 页。

### `free_pages`

公式：

```text
free_pages += blocks << order
```

左移不是位运算技巧题，它表达块大小：

```text
blocks * 2^order
```

### `free_blocks_total`

公式：

```text
free_blocks_total += blocks
```

它故意不把块换算成页，因为 fragmentation index 关心空闲页被分成了多少块。相同 free_pages 下，块越多通常表示越分散。

### `free_blocks_suitable`

目标 order 为 `s` 时，高阶块也能服务：

```text
等效目标阶块数 = blocks << (order - s), order >= s
```

例：目标 order 2；一个 order 5 块有 32 页，可以拆成：

```text
32 / 4 = 8 个 order-2 块
1 << (5 - 2) = 8
```

### 为什么低阶块不能合并后也算 suitable

你可能问：两个空闲 order-1 块不是能合成一个 order-2 吗？

只有它们满足 buddy 条件才可以：

- 物理相邻；
- 地址按父块对齐；
- 来自同一父块；
- 迁移类型和状态允许合并。

如果它们已经能合并，伙伴系统通常应在释放路径完成合并并把结果挂到更高阶链表。仅知道两个低阶块的数量，不能假设它们互为 buddy。

因此 suitable 只统计已经存在的目标阶及更高阶块。

### 一组完整追踪

目标 order 3：

| order | blocks | free_pages 贡献 | suitable 贡献 |
|---:|---:|---:|---:|
| 0 | 6 | 6 | 0 |
| 1 | 3 | 6 | 0 |
| 2 | 2 | 8 | 0 |
| 3 | 1 | 8 | 1 |
| 4 | 2 | 32 | 4 |

结果：

```text
free_pages = 60
free_blocks_total = 14
free_blocks_suitable = 5
```

真正能服务 order-3 请求的页数：

```text
5 << 3 = 40
```

其余 20 页虽然空闲，但分散在 order 0～2，对当前请求不可直接使用。

### 常见混淆

| 概念 | 单位 |
|---|---|
| `nr_free` | 当前阶的块 |
| `free_blocks_total` | 所有阶的块 |
| `free_pages` | 页 |
| `free_blocks_suitable` | 折算后的目标阶块 |
| `free_blocks_suitable << order` | 可服务目标请求的页 |

## 难点四：两个指数为什么可能一个高、一个低

### `unusable_free_index` 问的是“现在有多难”

```text
unusable =
(free_pages - suitable_pages) * 1000 / free_pages
```

其中：

```text
suitable_pages = free_blocks_suitable << order
```

它看空闲页中有多少比例对目标请求不可直接使用。

边界：

- free_pages=0 → 1000；
- 所有空闲页都 suitable → 0；
- 没有 suitable block 但仍有空闲页 → 1000。

### extfrag index 问的是“为什么难”

项目公式：

```text
requested = 1 << order

if free_blocks_total == 0: 0
if free_blocks_suitable > 0: -1000
else:
  1000 - (1000 + free_pages * 1000 / requested)
         / free_blocks_total
```

直觉：

- 有 suitable block：只要 watermarks 允许，连续性不是障碍 → -1000；
- 没有任何空闲块：更像总量耗尽 → 0；
- 空闲页不少却散成很多小块：更像碎片 → 趋近 1000。

### 四象限理解

| unusable | extfrag | 解释 |
|---|---|---|
| 低 | -1000 | 大部分空闲页可服务，请求健康 |
| 高 | -1000 | 仍有 suitable 块，但很多低阶空闲页用不上 |
| 高 | 接近 1000 | 无 suitable 块且空闲页分散，碎片主导 |
| 高 | 接近 0 | 无 suitable 块且总页数很少，总量不足主导 |

第二行最容易误判。unusable 可以高达 0.9，但只要存在一个 suitable block，extfrag 仍返回 -1。它们回答的不是同一个问题。

### 指数不能脱离 watermarks

extfrag `-1` 只表示“连续块存在”；官方文档的完整语义是“只要水位条件满足，分配可成功”。如果 zone 低于水位、cpuset 不允许、GFP 限制不匹配，仍可能拿不到该块。

### compaction 决策

compaction 通过迁移页来制造连续空间：

- 碎片主导时可能有效；
- 总量不足时无效，因为它不增加 free_pages；
- 大量不可迁移页时也可能失败；
- 本身会消耗 CPU 并带来延迟。

所以不能用单一 UI 红色就下结论“立即 compaction”。

### 碎片指数变体题

两个 zone 的 unusable 都是 1000：

- A：free_pages=1024，全部是 order-0；
- B：free_pages=2，目标 order=4。

哪个更像碎片，哪个更像内存不足？为什么？

答案：A 更像碎片，B 更像总量不足；extfrag index 的作用就是区分这两类根因。

## 难点五：BPF map 节流看似简单，实际包含状态与并发

### 正确的状态机

节流至少要表达三个状态：

```text
配置的间隔 interval
上次成功采样时间 last
当前触发时间 now
```

状态转移：

```text
没有 last -> 采样 -> last=now
now-last < interval -> 跳过 -> last 不变
now-last >= interval -> 采样 -> last=now
```

如果 key 每次变化，就不是在读取同一个 `last` 状态。

### 为什么当前实现失败

第一次：

```text
now = 100
lookup key 100 -> miss
update key 100 = 100
```

第二次：

```text
now = 120
lookup key 120 -> miss
update key 120 = 120
```

key 100 虽然存在，第二次却从未查询它。hash 变成历史时间戳集合，而不是“上次时间”。

### fixed key 为什么有效

```text
key 0 -> last timestamp
```

每次都读写 key 0，才能形成状态闭环。单例状态最适合单元素 array，避免 hash key 无界增长。

### 多 CPU 竞态

假设间隔已到，CPU0 和 CPU1 同时运行：

```text
CPU0 read last=0
CPU1 read last=0
CPU0 decides sample
CPU1 decides sample
CPU0 update last
CPU1 update last
```

结果：一个窗口采样两次。

这不一定不可接受，但必须定义：

- 如果目标是“降低大部分开销”，近似全局节流可能够用；
- 如果目标是“每窗口严格一次”，需要同步；
- 如果用 per-CPU map，则语义变成“每 CPU 每窗口一次”。

### map 类型选择

| 需求 | 合适选择 | 原因 |
|---|---|---|
| 单一 interval | 单元素 array | 固定索引、简单 |
| 单一 last timestamp | 单元素 array / 受保护状态 | 不应增长 |
| 按 PID 聚合 | hash / LRU hash | key 动态 |
| 完整事件流 | ring buffer | 保留顺序与多条事件 |
| 每 CPU 计数 | per-CPU hash/array | 降低共享竞争 |

### `counts_map` 的并发

当前逻辑是：

```text
lookup pointer
data->count += 1
update
```

同一 PID 的事件可能在多个 CPU/线程上下文发生。普通读改写不天然等于严格原子计数。更稳妥的思路包括原子加、per-CPU 聚合后用户态汇总，或把每次事件输出到 ring buffer。

### BPF map 变体题

把 `last_time_map` 改成 per-CPU array 后，interval=2 秒、64 CPU 的系统，理论上最多多久产生多少次完整扫描？

答案：语义是每 CPU 两秒最多一次，理论上一个两秒窗口可有约 64 次扫描，而不是全局一次。是否合适取决于设计目标。

## 六步闭卷验收

1. 用一张图说明 migratetype fallback，明确最终返回页数。
2. 画出一次分配从首次尝试到 slowpath 重试的 `get_page_from_freelist` 调用位置。
3. 给一张 order 表，算三个中间量。
4. 构造“unusable 高、extfrag=-1”的例子。
5. 手推当前时间戳 key 两次触发，指出 bug。
6. 解释 per-CPU 节流和严格全局节流的差异。

只要其中一题只能用“差不多、应该是”回答，就回到对应难点重新手算或画图。
