本页把项目从“能讲”推进到“能重建”。目标不是立刻改源码，而是先给出可验证的工程方案。

## 最小可运行版本的验收条件

不要用“界面出来了”作为唯一成功标准。最小版本应同时满足：

| 层 | 验收条件 | 证据 |
|---|---|---|
| 环境 | BCC Python 模块可导入 | import smoke test |
| 源码 | Python 文件与 C 文件路径一致 | 目录检查 + 单测 |
| 加载 | verifier 接受两个 BPF 程序 | BCC 日志 / 无加载异常 |
| 挂载 | tracepoint 与 kprobe 都 attach 成功 | tracefs/kprobe 检查 |
| 触发 | workload 能让 map 发生变化 | 前后快照 diff |
| 指标 | 固定输入下公式结果正确 | 纯 Python 单元测试 |
| 节流 | 触发频率高于采样频率时，更新次数受控 | 计数与时间戳 |
| 展示 | 无 curses 模式也能输出结构化数据 | JSON/text smoke test |
| 开销 | 开启/关闭探针的 workload 差异可量化 | benchmark |
| 兼容性 | 明确支持的内核/BCC 版本 | compatibility matrix |

## 推荐重构顺序

### 先修可运行性

统一以下内容：

- 模块名：`exfrag.py` 与 `from extfrag import ExtFrag` 二选一统一；
- C 文件路径：移动到 `bpf/` 或改成基于 `__file__` 的绝对路径；
- BCC import：按目标发行版确认 `bcc` / `bpfcc`；
- 工作目录：运行不应依赖调用者恰好位于仓库根目录。

推荐路径模型：

```python
from pathlib import Path

ROOT = Path(__file__).resolve().parent
BPF_DIR = ROOT / "bpf"
```

### 修复节流状态机

设计选择：

| 方案 | 语义 | 优点 | 代价 |
|---|---|---|---|
| 单元素 array | 全局近似节流 | 简单，不增长 | 多 CPU 可能同时越过 |
| per-CPU array | 每 CPU 节流 | 无共享竞争 | 总采样频率约为 CPU 数倍 |
| spin lock 状态 | 严格全局节流 | 语义清楚 | 热路径锁开销、支持限制 |
| 用户态定时触发 | 只在需要时采集 | 不把巡检绑在分配热路径 | 需要不同触发机制 |

重构前先决定需要的是“严格全局一次”还是“低成本近似采样”。

### 拆分事件流与聚合视图

建议：

- ring buffer：输出每次 `mm_page_alloc_extfrag` 的完整字段和时间戳；
- hash：维护按 `(tgid, alloc_order, alloc_mt, fallback_mt)` 聚合的排行榜；
- 用户态：可选择实时事件模式或聚合模式。

这样既保留时间序列，又能低成本展示热点。

### 消除硬编码 order 假设

- 从目标内核/BTF 推导实际范围；
- map key 使用显式结构体 `{zone_id, order}`；
- Python 按真实记录去重 zone；
- UI 根据返回的 order 集合动态建列，不写死 11。

### 建立内核版本边界

`get_page_from_freelist` 是内部函数。至少记录：

```text
kernel release
arch
BCC version
function symbol exists?
function prototype
struct alloc_context layout
MAX order representation
tracepoint format
```

更长期的方案可评估 BPF CO-RE + BTF、fentry/fexit 或稳定 tracepoint，但不能假设换技术后自动跨所有版本。

## 建议的数据模型

```c
struct zone_order_key {
    __u64 zone_cookie;
    __u32 node_id;
    __u32 order;
};

struct extfrag_event {
    __u64 ts_ns;
    __u32 tgid;
    __u32 pid;
    __u64 pfn;
    __s32 alloc_order;
    __s32 fallback_order;
    __s32 alloc_migratetype;
    __s32 fallback_migratetype;
    __s32 change_ownership;
    char comm[16];
};
```

为什么要同时保留 tgid 和 pid？因为 `bpf_get_current_pid_tgid()` 高 32 位通常是 TGID，低 32 位是线程 PID；原项目把高位命名为 PID，语义不够精确。

## 验证矩阵

### 功能测试

| 场景 | 期望 |
|---|---|
| 空闲系统、低 order | suitable 通常存在，extfrag 指数为 -1.000 |
| 制造大量小块 | 高 order 的 unusable 上升 |
| 总空闲页极低 | unusable 高，但 extfrag 未必接近 1 |
| 修改 delay | map 更新频率随窗口变化 |
| 多线程触发 | 聚合计数与 ring buffer 事件数量差异可解释 |
| PID 退出并复用 | 不把两个生命周期误合并 |

### 负向测试

1. C 文件不存在时，错误信息应指出真实绝对路径。
2. kprobe 符号不存在时，应退出并说明不兼容，而不是空界面。
3. map 满时，应记录 update 失败计数。
4. 终端尺寸不足时，不应陷入无法退出的长时间等待。
5. 非 root 或缺 capabilities 时，应给出权限提示。

### 性能测试

至少比较：

```text
baseline
tracepoint only
kprobe without full zone scan
kprobe with full scan, no throttle
kprobe with repaired throttle
```

指标包括吞吐、p50/p99 分配延迟、CPU 使用率、BPF 程序运行时间和 map update 次数。

## 15 道面试追问

### 为什么空闲内存足够还会失败？

答题骨架：总量 vs 连续性 → order → free_area → 高阶块缺失 → 外部碎片 → reclaim 与 compaction 的区别。

### 伙伴系统如何降低外部碎片？

答题骨架：2 的幂次分层 → 拆分 → buddy 地址关系 → 释放时合并 → migratetype/pageblock 进一步隔离。

### SLUB 与伙伴系统是什么关系？

答题骨架：SLUB 管小对象并向伙伴系统申请页；对象级内部浪费与页级外部碎片是不同维度，但二者会互相影响。

### tracepoint 为什么更稳定？

答题骨架：内核显式定义事件与字段；比探测任意内部函数稳定，但也不是永远不变，仍需检查 tracefs format。

### kprobe 为什么风险更高？

答题骨架：内部符号、原型、内联、结构体布局、寄存器参数 ABI 都可能变化。

### `get_page_from_freelist` 只属于 fast path 吗？

严谨答案：它是首次快速尝试的核心，也会在慢速路径的若干重试/特殊路径被再次调用。探测入口表示“每次尝试进入该函数”，不是只观察一次快速分配。

### `mm_page_alloc_extfrag` 是高阶请求降成低阶吗？

不是。它记录从 fallback migratetype 的某个 `current_order` 取得块；`fallback_order` 通常不小于请求 order，之后可拆分到请求大小。

### 为什么只看 buddyinfo 不够？

它给库存快照，但缺少进程/事件上下文、在线聚合和针对目标请求的解释；不过它是重要交叉验证来源，不能被本工具完全替代。

### 两个指数有什么区别？

unusable：空闲页中对目标请求不可用的比例；extfrag：失败更像碎片还是总量不足。有 suitable block 时 extfrag 为 -1。

### 为什么 compaction 不是万能的？

它重排可迁移页以形成连续空闲块，不创造新空闲页；不可迁移/固定页会阻挡，且有 CPU 与延迟成本。

### map 为什么既是通信又是状态？

它可以保存用户态配置、内核态聚合和跨回调状态；方向由读写方决定，而不是由 map 类型自动决定。

### 当前节流代码错在哪里？

用当前时间作 key 查“上次时间”，下一次 key 必然不同；事件程序还不更新 map。应使用稳定 key 并定义并发语义。

### 按 PID 聚合有什么问题？

丢时间序列、PID 复用、线程/TGID 混淆、order/migratetype 维度丢失，并发更新可能不精确。

### 如何证明低开销？

不能靠“eBPF 天生低开销”证明；必须对目标 workload 做开关探针对照、测延迟分位数和 BPF 执行统计。

### 你会怎样把它变成生产工具？

先修可运行与节流；补字段和事件流；版本兼容；错误/丢数指标；结构化输出；权限与安全；基准；测试矩阵；再谈长期部署。

## 两分钟项目答辩模板

> 这个项目面向 Linux 服务器中“总空闲页仍有，但高阶连续页不足”的物理内存外部碎片问题。内核态用了两类互补观测：`mm_page_alloc_extfrag` tracepoint 记录页分配器从 fallback migratetype 取块的事件，`get_page_from_freelist` kprobe 采集分配尝试时各 node/zone/order 的伙伴系统状态。eBPF 把事件聚合和状态写入 BPF map，Python/BCC 负责加载、配置和读取，curses 做终端展示；项目还根据各阶空闲块计算 unusable 与 extfrag 两类指标，分别描述请求不可用程度和碎片是否更像主因。
>
> 我在源码复盘中也识别了原型边界：当前快照的时间 map 使用动态时间戳作 key，节流闭环不成立；tracepoint 的 fallback_order 原先被误读为“降成更小阶”；Python import 与 C 文件路径也不一致。因此我不会直接称它为生产级工具。我的改进顺序是先恢复可运行性和固定 key 节流，再补 migratetype/ownership 字段、ring buffer 事件流、内核兼容矩阵和开销基准。这样既能讲清设计，也能用证据说明实现状态。
