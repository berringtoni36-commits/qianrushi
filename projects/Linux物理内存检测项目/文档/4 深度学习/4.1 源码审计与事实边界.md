这一页是本 wiki 的“校准页”。学习本项目时，必须把以下三层分开：

1. **Linux 内核机制**：上游内核真实提供的语义。
2. **项目设计意图**：作者想实现的监控与展示能力。
3. **当前源码快照**：仓库里的代码实际上做了什么，是否完整、是否能直接运行。

如果把三层混在一起，就会出现最危险的假掌握：能背出“采样节流、fallback 降级、直接运行”，却解释不了源码为什么并不支持这些结论。

## 一页结论

| 主题 | 设计意图 | 当前源码事实 | 学习结论 |
|---|---|---|---|
| 外碎片事件 | 用 `mm_page_alloc_extfrag` 找到迁移类型 fallback | tracepoint 选择正确，但 wiki 原先误解了 `fallback_order` | 它不是“实际降成更小 order” |
| 状态巡检 | 在 `get_page_from_freelist` 入口采集 zone/order 状态 | kprobe 能覆盖高频分配现场，但强依赖内核版本与函数签名 | 这是观测点，不等于只触发一次 fast path |
| 时间节流 | `delay_map + last_time_map` 降低采样频率 | 键使用错误；事件程序还没有更新时间戳 | 当前实现不能证明节流有效 |
| order 范围 | 扫描伙伴系统所有阶 | 本地硬编码 `MAX_ORDER 10` 并使用 `<=` | 只对特定内核布局假设成立 |
| 用户态启动 | Python 加载 C 文件并展示 | 文件名、import 名和 `./bpf/` 路径不一致 | 当前快照不能按原命令直接运行 |
| node/zone 统计 | 每个 node/zone/order 一条状态 | zone map 基本符合该模型，但 node zone 数量靠 `/11` 推算 | 展示层包含硬编码假设 |
| 生产可用性 | 低开销长期监控 | 缺少兼容性矩阵、基准、丢数测试和并发验证 | 应称“教学/原型实现”，不能直接宣称生产级 |

## `mm_page_alloc_extfrag` 到底表示什么

当前源码在 `extfraginfo.c#L19` 使用：

```c
TRACEPOINT_PROBE(kmem, mm_page_alloc_extfrag)
```

这个选择有价值，因为 tracepoint 是内核预定义事件，字段语义比直接探测内部函数稳定。但是原 wiki 多处把它解释成：

> 请求高阶页失败后，实际退化成更小的 `fallback_order`。

这不符合上游内核源码。

在 Linux 页分配器中，该事件出现在 **伙伴系统从其他迁移类型（migratetype）的 freelist 取块** 的 fallback 路径。传入的 `fallback_order` 是找到的空闲块阶数 `current_order`，通常满足：

```text
fallback_order >= alloc_order
```

内核拿到较高阶块后会拆分，最终仍返回请求的 `alloc_order` 大小。事件关注的是：为了满足当前迁移类型的请求，分配器是否“借用/偷取”了另一迁移类型的页块，从而可能破坏反碎片布局。

上游 tracepoint 还包含项目没有采集的字段：

- `alloc_migratetype`
- `fallback_migratetype`
- `change_ownership`
- 由 trace 输出推导的 `fragmenting = fallback_order < pageblock_order`

因此，判断“是否真正造成页块级碎片”的关键，不是比较 `fallback_order < alloc_order`，而要结合迁移类型、pageblock order 与 ownership 变化。

## 时间节流：意图正确，实现没有闭环

### `fraginfo.c` 的问题

`fraginfo.c#L96` 使用当前纳秒时间作为 key：

```c
current_time = bpf_ktime_get_ns();
last_time = last_time_map.lookup(&current_time);
```

采集结束后又在 `fraginfo.c#L166` 写入：

```c
last_time_map.update(&current_time, &current_time);
```

下一次触发会产生新的 `current_time`，因此查找的是另一个 key。正常情况下不会命中“上次时间”，节流判断不会生效；哈希表反而不断累积时间戳 key，直到更新失败。

### `extfraginfo.c` 的问题

`extfraginfo.c#L23` 同样使用 `current_time` 查表，但整个函数没有 `last_time_map.update()`。因此这里连时间记录都没有形成。

### `delay` 的边界问题

两个 C 文件都只在 `delay_ptr != NULL` 时给 `delay` 赋值，随后却无条件使用 `delay`。虽然 `delay_map` 是长度为 1 的 array、Python 也试图写入索引 0，但严谨实现仍应初始化：

```c
int delay = 0;
```

并明确处理 map lookup 失败路径。

### 最小修正模型

全局单窗口的最小设计应使用固定 key：

```c
u32 key = 0;
u64 now = bpf_ktime_get_ns();
u64 *last = last_time_map.lookup(&key);

if (last && now - *last < interval_ns)
    return 0;

last_time_map.update(&key, &now);
```

更深入还要追问：多个 CPU 同时越过判断时会不会重复采样？如果需要严格全局节流，应考虑原子交换、锁或接受近似采样；如果希望每 CPU 节流，则应使用 per-CPU map 并说明语义。

### 破坏实验

| 变体 | 预期现象 | 暴露的知识点 |
|---|---|---|
| key 使用 `current_time` | 基本永不命中，hash 持续增长 | map 的 key 必须表达“同一份状态” |
| 不更新 `last_time` | 每次触发都通过 | 读写必须构成状态闭环 |
| 固定 key 但无并发控制 | 多 CPU 可同时通过窗口 | 观测程序也有并发语义 |
| 把 `last_time_map` 改成单元素 array | key 空间固定、不会膨胀 | 配置/单例状态适合 array |

## order 范围不是一个可随意硬编码的数字

`fraginfo.c#L6` 在包含内核头文件之后重新定义：

```c
#define MAX_ORDER 10
```

随后两处循环都使用 `<= MAX_ORDER`。在某些旧内核默认布局中，`free_area` 的有效下标确实可能是 `0..10`；但这个结论依赖内核版本和配置。现代内核又逐步使用 `MAX_PAGE_ORDER`、`NR_PAGE_ORDERS` 等名称表达最大阶与数组长度。

正确的学习结论不是“MAX_ORDER 永远等于 10”，而是：

1. 确认目标内核头文件中 `struct zone::free_area` 的真实长度。
2. 区分“最大有效 order”和“order 数量”。
3. 避免覆盖内核头文件已经定义的同名宏。
4. 用户态不能再用固定 `/11` 推导 zone 数量。

## 当前目录不能按旧 quick start 直接启动

当前工作区存在三组直接可见的不一致：

1. `exfrag_user.py#L6` 导入 `from extfrag import ExtFrag`，但仓库文件名是 `exfrag.py`。
2. `exfrag.py#L18` 加载 `./bpf/extfraginfo.c` 与 `./bpf/fraginfo.c`，但两个 C 文件位于仓库根目录，没有 `bpf/` 子目录。
3. `exfrag.py#L2` 使用 `from bpfcc import BPF`；许多发行版安装 `python3-bpfcc` 后实际 Python 模块名仍为 `bcc`。必须以目标环境实测为准。

所以正确表述应是：

> 这是一个项目源码快照。先修复目录/import 与目标发行版 BCC 适配，再验证编译、加载和运行；不能把文档中的命令当成已经在当前目录通过的命令。

建议的验证顺序：

```bash
find . -maxdepth 2 -type f -print
python3 -c 'from bcc import BPF; print("BCC import OK")'
python3 -m py_compile exfrag.py exfrag_user.py
sudo bpftrace -l 'tracepoint:kmem:mm_page_alloc_extfrag'
sudo test -r /proc/kallsyms
grep -w get_page_from_freelist /proc/kallsyms
```

最后再运行用户态入口，并分别验证 `counts_map`、`pgdat_map`、`zone_map` 是否真的变化。

## 用户态统计也包含隐式假设

### `nr_zones` 通过 `/11` 推导

`exfrag.py#L116` 用：

```python
nr_zones = int(len(zone_data.get(node_id, [])) / 11)
```

它假设每个 zone 恰好产生 11 个 order 记录。只要内核 order 范围变化、某条 map 更新失败或 key 冲突，结果就会错。更稳妥的方法是按 `(node_id, zone_name)` 或 zone 指针去重。

### `counts_map` 是聚合快照，不是事件日志

`counts_map` 的 key 只有 PID，value 保存累计 count 与最近一次字段。它会丢失：

- 同一 PID 每次事件的时间序列；
- PID 复用前后的进程区分；
- 同一进程不同 migratetype/order 组合的分布；
- 多 CPU 同时更新同一 value 时的精确计数保证。

所以界面表示的是“按 PID 聚合的近似快照”，不能描述为完整历史。

## 项目能力边界

当前工具能帮助学习和原型验证：

- tracepoint 与 kprobe 的互补；
- BCC 加载、BPF map 通信；
- node/zone/order 与伙伴系统；
- 两种碎片指标的计算思路；
- curses 终端展示。

当前工具尚不能单独证明：

- 某次分配失败完全由外部碎片导致；
- 某个进程“制造了”全部碎片；
- compaction 一定能解决问题；
- 采样开销足够低；
- 跨内核版本稳定；
- 数据无丢失、无竞态。

生产诊断至少要联合 `/proc/buddyinfo`、debugfs `extfrag/extfrag_index`、`/proc/vmstat` 的 compaction/reclaim 计数、目标 workload 与内核版本信息。

## 面试时如何诚实又有深度地表达

推荐口述：

> 这个项目采用 tracepoint 记录迁移类型 fallback 事件，采用 kprobe 在页分配路径采集 zone/order 的伙伴系统状态，再通过 BPF map 交给 Python/curses 展示。复盘源码时我还发现，当前快照的时间节流 key 使用错误、事件程序没有更新时间戳，用户态目录和 import 也不一致。因此我把它定位为一个有完整技术主线的教学原型，而不是未经验证的生产工具；后续会先修复可运行性和节流闭环，再做跨内核兼容与开销基准。

这比“项目用了 eBPF，所以低开销、可生产使用”更可信，也更能体现真正的源码阅读能力。
