# 学习工作台蒸馏精华

工作台最重要的设计不是进度条，而是把“看过”“掌握”“需要回看”和“来源在哪里”拆成不同字段。这样复习时不会因为熟悉文件名或完成了很多条目，就误把熟悉感当成可调用能力。

当前自动生成的 [`REVIEW_QUEUE.md`](REVIEW_QUEUE.md) 是一个可执行入口：它只根据工作台现有字段排序，不把排序结果当成掌握度，也不修改原始条目。默认从 `学过 + 待回看` 开始，再进入 `未学 + 待回看`；做项目题时还要回到源码和个人贡献证据。

## 一、先看状态，不先看数量

当前快照有 360 条记录：307 条是 `学过`，53 条是 `未学`，0 条是 `掌握`，360 条是 `待回看`。这只能说明初始化/当前声明如何填写，不能说明真实答题能力。复习入口应优先选择：

1. `学过 + 待回看`：先做无提示口述，看看能否说清定义、机制、边界和一个例子。
2. `未学` 中与近期项目、面试目标或当前模块相邻的条目：先回到主源建立理解，再决定是否进入学过。
3. 重复失败或来源冲突的条目：不要直接升级状态，先记录薄弱环节和事实边界。

## 二、一次回忆会话的最小闭环

对每个条目执行：

1. **遮住答案**：只看标题和来源定位，先说出问题属于哪一层。
2. **给出骨架**：至少回答“是什么、为什么、怎么验证、边界是什么”。项目题再增加源码符号或个人贡献证据。
3. **只给最小提示**：卡住时只补一个关键词或来源位置，重新组织回答；不要立即展示完整答案。
4. **做反例/迁移**：问一个主源没有原样回答的新场景，例如把八股机制映射到 RTOS、Linux 或视觉项目。
5. **记录结果**：记下独立完成、提示后完成、仍不稳定和事实待核对，不把模型评价代替用户状态。

## 三、状态升级的保守口径

- `未学 → 学过`：完成一次真实阅读或理解活动，并能复述至少一个核心关系。
- `学过 → 掌握`：在没有答案的情况下，能解释机制、边界，并应对基本追问；若是代码/项目内容，还要能指出来源或符号。
- `掌握 → 待回看`：掌握不是永久免检；间隔一段时间或遇到新变式后仍可重新排队。
- 任何状态变化都应由用户根据真实行为确认；Skill 只提供建议，不写回原记录。

## 四、来源和技术 Skill 的组合

状态记录只告诉我们“要复习什么”，不告诉我们“技术答案是什么”。复习时应回到 `source_target`，再按问题动作选择专项 Skill：

- FreeRTOS 任务卡死：使用通信/运行时故障 Skill。
- Linux 物理内存碎片：使用 buddy/eBPF/源码审计 Skill。
- 项目面试介绍：使用对应项目 storytelling Skill。
- 算法题主动回忆：使用 `algorithm-active-recall-loop`，不要让本域抢占算法推导。

## 五、最小可持续记录

只需要维护三个字段和一条日志：`mastery`、`review_flag`、`last_studied`，以及 `学习日志.md` 中实际发生的学习记录。不要写预计日期、固定配额或“应该已经掌握”。时间表可以由用户另行制定，不能伪装成事实。
