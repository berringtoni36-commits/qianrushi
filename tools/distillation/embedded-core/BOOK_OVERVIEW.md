# 嵌入式核心资料 — 整体理解

## 基本信息

- 内容类型：个人嵌入式学习资料、项目八股、技术文章摘录与复习卡片集合。
- 来源边界：`projects/嵌入式八股/` 核心笔记、FreeRTOS 源码解析和高频 150 题；项目源码只作为跨域事实证据。
- 处理时间：2026-08-14。
- 当前主域规范 Skill：14 个；INDEX 另链接 3 个以 `linux-systems-tutorial` 为主域的 UDP 合同 Skill。其余未主题化内容仍保留在来源登记簿和待处理清单中。

## 1. 结构

### 一句话主旨

这组资料试图把嵌入式面试所需的语言、内存、操作系统、通信、MCU、嵌入式 Linux 和项目表达串成一条可解释、可追问的知识链。

### 七个一级主题与三条新增分析主线

1. **C 内存与分配策略**：作用域、存储区、所有权、泄漏、碎片和固定块内存池。
2. **C++ 对象与资源生命周期**：构造/析构、RAII、拷贝/移动、智能指针和容器失效。
3. **操作系统与 Linux 基础**：进程、线程、内存、文件、网络和设备模型；大量小林图解内容仍待主题化回链。
4. **STM32 时钟与采样时序**：系统时钟、AHB/APB、定时器、ADC、SysTick 与传感器采样链。
5. **通信协议与总线选型**：UART、RS232/485、I²C、SPI、CAN 及 TCP/IP。
6. **ARM Linux 启动与驱动边界**：Bootloader、设备树、platform 匹配、`probe()`、用户态接口和资源释放。
7. **面试表达与项目落点**：定义→机制→项目/代码→边界→优化，并区分教程、设计意图和源码事实。

本轮继续补齐六条可组合的分析主线：

- **C 构建/启动/镜像审计**：把存储期、链接属性、启动汇编、scatter 文件和 Map 文件连成一条证据链。
- **Linux TCP 丢包路径诊断**：把应用、Socket/TCP 队列、qdisc、网卡、链路和对端应用的“丢失”分层。
- **Linux 虚拟内存回收路径分析**：把虚拟申请、首次触摸、页类型、watermark、kswapd/direct reclaim、Swap 和 OOM 分层；不与高阶 buddy 碎片诊断混淆。
- **UDP 数据报地址合同**：把普通回包、广播作用域和组播入组拆成三个可验证的端点问题。
- **文件持久化与用户态定时**：分别审计 `write` 到稳定介质的承诺，以及相对等待、绝对 deadline、timerfd 和 overrun。
- **C 结构体二进制合同**：把 `sizeof/offsetof`、对齐、端序、位域、DMA、寄存器和协议帧放到同一审计流程。

关系：前六项提供机制和排障材料，第七项把机制转换为可复用的回答与追问程序；RTOS、Linux 内存和视觉项目 Skill 会把这些基础继续落到各自源码。

## 2. 解释

| 术语 | 本资料中的用法 | 事实边界 |
|---|---|---|
| 八股 | 可按层次复述并能被追问的知识单元 | 不等于死记答案，也不等于项目已实现 |
| 所有权 | 约定谁创建、使用、转移和释放资源 | C 指针、C++ RAII、RTOS 对象和 Linux 资源要分别核对 |
| 内存池 | 预分配并按固定规则分配/归还内存块的机制 | 当前 RTOS 工程有 FreeRTOS heap 配置，但没有自定义池实现证据 |
| RAII | 将资源释放绑定到对象析构的 C++ 资源管理方式 | 不自动解决循环引用、DMA/cache 或实时性问题 |
| 采样时序 | 时钟、采样保持、转换完成、软件周期和数据处理的组合 | ADC 平均不等于标定和绝对精度 |
| 设备树 | ARM Linux 向内核描述硬件资源与兼容性的输入 | 不是驱动本身；本仓库无对应完整 Linux 驱动项目 |
| 分层回答 | 定义→机制→项目映射→边界→优化的回答结构 | 项目映射必须有源码、日志或用户确认支撑 |

## 3. 核心命题

1. 先锁定生命周期、时序或启动层级，再选择 API 和动作。
2. 内存问题同时看所有权、上下文、确定性、碎片和可验证性。
3. C++ 抽象的价值取决于资源模型和平台成本，不由语言标签决定。
4. STM32 的时钟配置目标、寄存器推导和目标板实测必须分开记录。
5. 协议选型必须把外设、物理电平、介质、节点和错误处理分开。
6. 设备树描述硬件，Driver Core 负责匹配，`probe()` 获取资源；三者不能互相替代。
7. 面试回答必须把文档设计意图和源码实际行为分开，尤其是没有完整源码或测试时。

## 4. 论证链

资料以教程/面试题解释基础机制，再通过 RTOS、eBPF 和视觉项目将机制落到代码与面试追问，最后用来源审计记录实现缺陷和事实边界。新增三条主线把“C 语义→链接镜像”“TCP 字节→应用交付”和“虚拟申请→缺页/回收→失败出口”补入基础系统分析。小林图解、操作系统、网络和 STM32 其余章节仍有大量 `indexed-only` 内容，不能宣称全量主题已经覆盖。

## 5. 批判

- 来源混杂：文章、个人总结、项目文档和代码事实的可信度不同，不能视为同一权威。
- 固定版本、固定平台和简化数字必须结合芯片手册、内核版本、工具链和实测。
- C/C++ 教程示例不自动代表用户已经使用了对应架构；Linux 驱动主题尤其只有教程证据。
- 合并稿、拆分稿和项目稿存在重复，必须按来源边界和哈希去重。
- `SYSCLK_FREQ_72MHz`、MQ2 经验公式、内存池 O(1) 等表述都需要注明“配置/推导/目标平台实测”的层级。

## 6. 应用潜力

已通过三重验证并形成 14 个本域规范 Skill；另有 3 个以 `linux-systems-tutorial` 为主域的 UDP 合同 Skill 作为跨域导航入口。整体覆盖面包括面试分层、总线选择、ARM Linux 启动链、内存生命周期、C++ 资源、C 存储/链接/Map、STM32 时序、Linux TCP、虚拟内存回收、驱动边界、文件持久化、用户态定时、C 结构体二进制合同和跨表示层数值合同。单个 API 定义、孤立金句、重复转载、无来源经验数字、构建产物和图片不独立 Skill 化；UDP 应用可靠性候选因缺少真实业务实现暂不升格。
