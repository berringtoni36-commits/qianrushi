# 嵌入式核心资料 — 精华

这组资料的核心价值不是给每道题配一条标准句子，而是把嵌入式问题组织成“现象—机制—工程落点—边界”的解释链。面对面试题或现场故障，先判断问题属于生命周期、时序、硬件接口、启动链还是项目表达，再选择对应的分析路径。

本轮新增六条可直接执行的审计路径：C 工程从存储期/链接属性走到启动汇编和 Map 镜像；Linux TCP 工程从应用消息沿 Socket、队列、网卡和链路走到对端应用；Linux 虚拟内存工程从虚拟申请走到缺页、回收和失败出口；UDP 按普通端点、广播和组播拆分地址合同；文件持久化区分写入完成与稳定介质；用户态周期用绝对 deadline 和 expiration count 处理漂移。它们共同强调“某层已确认”不等于“整条链路已完成”。

## 一、先问资源和生命周期

C 代码中，作用域结束不等于堆对象生命周期结束。必须写清谁申请、谁释放、失败路径如何回收、释放后哪些别名仍可见。长期运行系统要区分容量不足、泄漏、越界和外部碎片：总空闲量足够不代表能找到满足大块申请的连续空间。

固定块内存池适合高频、尺寸相近、需要确定性分配的对象；它能降低外部碎片和分配时间，但带来块内浪费、容量上限、并发保护和耗尽策略。当前 RTOS 工程存在 `heap_4.c`、`configTOTAL_HEAP_SIZE` 和动态任务创建证据，但没有自定义内存池或长期压力测量证据。

## 二、C++ 把资源管理绑定到对象

RAII 的关键是把资源获取和析构释放成对绑定，覆盖提前返回和异常路径。使用 `unique_ptr` 表示唯一所有权；只有真实共享所有权时才考虑 `shared_ptr`，观察关系不能让裸指针承担隐含释放责任。拷贝/移动审计不能只看对象值，要沿着文件、锁、DMA 缓冲区或外设句柄检查是否双重释放、移动后使用或析构顺序错误。

容器是另一种生命周期边界。扩容、插入和删除可能使迭代器、引用和指针失效；`reserve` 只能改变某些重新分配风险，不能把所有操作都变成地址稳定。嵌入式应用还要核对堆分配、引用计数、异常/RTTI、代码体积和最坏执行时间。

## 三、Linux 虚拟内存要区分申请、首次触摸和回收

`malloc`、`brk` 或 `mmap` 首先处理的是进程虚拟地址空间；申请返回成功，不代表每一页物理内存已经准备好。首次写入或读取可能触发缺页，由内核建立映射或从文件/Swap 取回页面。排查时把申请时刻、首次触摸时刻和 RSS/PSS、minor/major fault 的变化对齐，不能把所有缺页都叫作异常故障。

页类型决定回收成本。干净文件页可以丢弃后重新读取，脏文件页需要写回；匿名页没有文件载体，通常需要 Swap 才能暂时释放。顺序扫描、预读和一次性大访问可能把冷页带入页缓存并挤出热点，`cache` 增长也不自动等于泄漏。`Active/Inactive` 是分析线索，具体 LRU、MGLRU 或其他实现必须按目标内核版本核对。

内存压力要沿 zone 水位和回收路径观察：后台 `kswapd` 与申请线程执行的 direct reclaim 是不同延迟模型；`pgscank`、`pgscand`、`pgsteal`、`/proc/meminfo`、`/proc/zoneinfo`、Swap I/O 和应用 p99 应放在同一时间窗口。申请失败还要分开 overcommit/地址空间限制、物理回收无效、Swap 耗尽、OOM，以及高阶连续页/伙伴系统问题。`watermark`、页大小、计数器语义和 `swappiness` 都受内核版本、架构、NUMA、cgroup 和配置影响，资料中的示例数字不能直接当成机器实测。

## 四、STM32 时钟是所有外设时序的上游

不要从“宏写了 72MHz”直接跳到“采样正确”。应画出 HSE/HSI → PLL → SYSCLK → HCLK → PCLK1/PCLK2 → 定时器/ADC/UART → 软件触发与任务周期的完整链路。经典 STM32F1 中 APB 预分频和定时器时钟存在易错关系；UART BRR、TIM PSC/ARR、ADC 分频和 SysTick reload 都要用当前寄存器与芯片手册复算。

本仓库 RTOS 工程的 MQ2 事实是：PA4/ADC1_CH4、ADC 时钟注释为 PCLK2/6、采样时间 `239Cycles5`、10 次平均、每次间隔约 100us。`MQ2_Init()` 没有等待预热；经验公式没有 Ro 标定和精度实测。因此可以说“源码这样采集和换算”，不能说“输出是准确绝对 ppm”。

## 五、C 存储期、链接和启动要落到 Map

“全局变量通常在 BSS”只能作为常见工具链模型，不能替代当前构建证据。先区分 C 语言的存储期、作用域和链接属性：文件作用域 `static` 影响跨翻译单元可见性，块作用域 `static` 延长生命周期，普通 `extern` 通常只是声明，`volatile` 也不提供原子性或互斥。

然后追踪裸机启动链。当前 STM32 启动文件的向量表首项是 `__initial_sp`，`Reset_Handler` 调用 `SystemInit` 后跳转到 `__main`；`PWM.sct` 把 `ER_IROM1` 和 `RW_IRAM1` 映射到 Flash/RAM，`PWM.map` 再给出 `.data`、`.bss`、HEAP、STACK 和 region 使用量。Map 是某次工具链配置的快照，换芯片、C 库、链接器或优化选项后必须重审。

因此，`multiple definition` 要回到声明/定义和目标文件，RAM/Flash 超限要回到 region 和对象贡献，BSS/数据初始化要区分 C 语义与启动/C 库实际职责。没有启动代码或 Map 时，只能给验证方法，不能断言当前镜像布局。

## 六、协议和 TCP 交付看约束与层级

UART、RS232、RS485、I²C、SPI、CAN 不能只按理论速率排队。先列距离、节点数、吞吐、是否同步、单双工、电平、噪声、终端和错误恢复，再把外设、物理层和收发器组合起来。短距离高速、长距离差分、多节点寻址和总线仲裁对应不同取舍；接口名称本身不是完整方案。

Linux TCP 的“丢包”也必须先问丢的是连接、TCP 字节、Socket 缓冲中的数据、应用消息还是持久化记录。监听端口分开看 SYN 队列与 accept 队列；已连接 socket 看窗口、Recv-Q/Send-Q、重传和抓包；主机网络栈看 qdisc、接口统计和网卡 RingBuffer；中间链路用 ping/mtr 只能做参考，不能替代 TCP 抓包和应用日志。

TCP ACK 只说明传输层确认了字节，`send()` 成功只说明数据进入本端发送路径，`ESTABLISHED` 也不证明对端仍健康。应用需要消息 ID、业务确认或服务端对账才能把可靠性延伸到处理和持久化。进程退出、主机断电、拔网线、TCP Keepalive 和 HTTP Keep-Alive 分属不同层次，报告中不能混写。

普通 UDP 要先写清四元组：源 IP/端口 → 目的 IP/端口。服务端若忽略 `recvfrom` 返回的来源地址，或者把多客户端共享的 `cliaddr` 当成全局状态，就会出现回错端口和串包。广播还要额外满足 `SO_BROADCAST`、目的地址、出口接口、子网和接收 `bind`；组播则要把发送出口 `IP_MULTICAST_IF` 与接收端 `IP_ADD_MEMBERSHIP` 分开。`sendto` 成功仍只代表本地提交，不代表对端应用收到。

## 七、文件完成与稳定持久化是不同承诺

文件存在、`write()` 返回和用户真正看到内容，分别可能停留在用户缓冲、Page Cache 或 writeback 阶段。要处理进程崩溃、内核崩溃和突然掉电，先明确故障模型，再设计临时文件、完整写入、`fsync`/`fdatasync`、目录同步、原子 `rename`、版本号和恢复扫描的顺序。`fflush` 只处理 stdio 缓冲；`fsync` 也不自动给整个业务记录提供原子更新。视觉项目的文件 IPC 不能用“文件出现”替代完成标记和一致性合同。

## 八、用户态周期要围绕 deadline 和消费模型

相对 `sleep` 循环会把执行时间和调度延迟累加为漂移；用单调时钟计算绝对 deadline，再选择 `clock_nanosleep(TIMER_ABSTIME)`、POSIX timer 或 `timerfd + epoll`。事件循环中必须读取并处理 expiration count，区分“到期次数”与“业务只需执行一次”；回调、阻塞任务和 timer service 上下文也不能混为一谈。周期设计的验收指标应包括抖动、overrun、积压策略和任务执行上界。

## 九、C 结构体不是天然的线协议

把结构体直接当作寄存器、DMA、CAN 帧或 Flash 记录之前，先列外部字段表，核对 `sizeof`、`offsetof`、`_Alignof`、尾部填充、端序、访问宽度和已知字节向量。`#pragma pack` 只能改变部分对齐，位域位序和字节序仍依赖 ABI；未对齐访问、DMA 缓存一致性、柔性数组和 `union` 也要单独审计。对跨平台或安全关键协议，显式编码/解码通常比裸内存映射更容易验证。

## 十、ARM Linux 要按层定位

启动问题沿 Boot ROM/SPL → U-Boot → 内核/设备树 → 驱动 → Rootfs → 应用推进。设备树描述硬件，`compatible` 参与 Driver Core 匹配，`probe()` 获取寄存器/IRQ/时钟/GPIO 等资源，`file_operations` 再把部分能力暴露给用户态。`read/write` 偏数据、`ioctl` 偏控制、`mmap` 适合共享大缓冲区，但都需要长度、权限、并发和生命周期检查。

如果 `probe()` 没进，先查节点状态、匹配表、模块和 `platform_device`；如果进了但初始化失败，逐项审计资源申请和错误回收；IRQ 顶半部不能阻塞，耗时处理要下放。仓库只有 Linux 驱动教程和示例，没有对应完整个人驱动源码，所以这些内容只能作为学习方法和面试边界，不能冒充项目经历。

## 十一、面试表达的统一骨架

用一句话定义问题边界，再沿数据流、控制流或时序解释机制，接着绑定具体函数/模块/配置，最后说误区、限制和验证动作。没有源码、日志、测试或用户确认时，将表述降级为“资料建议”“设计意图”或“可推导方案”。

## 常见陷阱

- 把 `free(p); p = NULL` 当成所有权和别名问题的完整修复。
- 把 RAII、`shared_ptr` 或容器直接等同于零成本和绝对安全。
- 把 `SYSCLK_FREQ_72MHz` 当作目标板已经实测稳定 72MHz。
- 把 ADC 平均或经验公式当作传感器标定和精度证明。
- 把 UART 外设、RS232 电平和 RS485 收发器混为一层。
- 把 `.bss`、`extern`、`volatile` 或一次 Map 结果当成跨工具链的万能结论。
- 把 TCP ACK、`send()` 成功或 `ESTABLISHED` 直接说成应用消息已处理、落盘或对端健康。
- 设备树匹配成功后仍需核对 `reg`、IRQ、电源、时钟和实际硬件。
- 把教程里的 Linux 驱动示例写成个人已经交付的驱动。

## 三句话

1. 先锁定生命周期、层级和证据，再选择内存、API 或排障动作。
2. STM32 时序从时钟树推到外设；C 镜像从链接布局落到 Map；TCP 交付从传输层落到应用确认。
3. 机制决定回答深度，源码落点决定可信度，事实边界决定专业度。
