- **V1 跨域验证**：至少两个独立语境支撑同一方法论；“高”表示来源同时给出机制和执行路径，“中高”表示有直接规则但仍需补最小复现。
- **V2 预测力**：用来源没有直接回答的新问题推导一个可检验答案；不是复述原文案例。
- **V3 独特性**：候选有明确的技术边界、反直觉排序或专门的变量/证据体系，而不是泛泛的“注意性能”“写测试”。

## 一、embedded-core：小林系统、网络与硬件

### G2-E01 CPU 缓存局部性—伪共享—亲和性三段式诊断

- **标题**：CPU 缓存局部性—伪共享—亲和性三段式诊断。
- **适用问题**：多核程序“算法复杂度没变但变慢”、循环重排收益不稳定、两个线程互不共享变量却互相拖慢、绑定 CPU 后性能变化异常时，判断问题究竟来自数据/指令局部性、cache line 争用，还是线程跨核迁移。
- **执行流程**：
  1. 先记录架构、缓存层级、线程数、核亲和性和基线；用访问顺序区分连续/跨步数据，用分支规律区分指令缓存/预测因素。
  2. 对共享热点变量画出 cache line 布局，检查不同核心是否写同一 cache line 的不同成员；不要把“变量逻辑独立”当作“缓存独立”。
  3. 只在证据对应时选择循环/数据布局调整、结构体填充或 cacheline 对齐、计算线程亲和性；实时/交互线程不能为了缓存命中盲目固定到单核。
  4. 用硬件计数器、微基准和端到端基准分别验证 cache miss、迁移/争用和真实延迟；若只有微基准改善，不升格为系统收益。
- **V1 初判**：高。`2.3` 从 cache line、顺序访问、分支规律和跨核迁移给出局部性与亲和性路径；`2.5` 以两个核心改写同一 cache line 的不同变量解释伪共享，并给出对齐/填充方向。
- **V2 初判**：高。新问题：两个计数器各自只被一个线程更新，但放在同一结构体后吞吐随线程数下降，是否需要加锁？推导：先排除锁竞争，再检查 cache-line 共享；若交替写导致 MESI 失效，先做填充/对齐实验，而不是增加互斥锁。
- **V3 初判**：中高。独特处是把“访问模式→伪共享→迁移”作为一条分叉诊断链；仍与一般性能 profiling 有交集，需后续用 counter 和反例确认独立边界。

### G2-E02 硬件 I/O 分阶段交接：控制器→传输方式→驱动→用户态

- **标题**：硬件 I/O 分阶段交接：控制器→轮询/硬中断/DMA→驱动→用户态。
- **适用问题**：设备“能读但 CPU 占用高”、中断风暴、DMA 数据偶发不完整、驱动已经加载但应用收不到数据，以及需要解释一个硬件事件如何变成用户态结果时。
- **执行流程**：
  1. 先识别设备是字符还是块设备，画出控制器的状态/命令/数据寄存器、缓冲区和 CPU/设备之间的所有权。
  2. 按数据量、事件频率和时延要求选择轮询、硬件中断或 DMA；轮询要证明等待短且可接受，中断要限制上半部工作，DMA 要记录缓冲区、完成通知和一致性边界。
  3. 沿“控制器完成→硬中断上半部→软中断/下半部或 DMA 完成→驱动→系统调用→用户缓冲区”逐段找证据，不把“设备节点存在”当作数据链闭合。
  4. 对每一段记录状态位/中断计数/DMA 长度/驱动队列/用户读取结果；用小数据和高频数据各做一次测试，确认方案在不同负载下没有换来新瓶颈。
- **V1 初判**：高。`8.1` 独立讲清控制器寄存器、轮询、中断、DMA 和设备驱动分层；ARM Linux 架构文档把硬件、U-Boot、内核、驱动和应用放入完整启动/运行交接链。
- **V2 初判**：高。新问题：低速传感器偶尔读不到数据但 CPU 已接近满载，推导优先检查是否在状态寄存器上忙等或中断处理过重，再核对驱动队列和用户态读取，而不是先改传感器协议。
- **V3 初判**：高。它不是“设备驱动概念介绍”，而是用“控制器语义+传输策略+软件层交接+证据计数器”定位故障，适用于不同外设。

### G2-E03 网络接收路径：硬中断→NAPI/软中断→协议栈→Socket

- **标题**：网络接收路径：硬中断→NAPI/软中断→协议栈→Socket 的分层诊断。
- **适用问题**：网卡 RX drop、overrun、`NET_RX`/`ksoftirqd` 占用高、抓包能看到但应用读不到、Socket 接收队列溢出，以及“TCP 丢包”被过早归因到传输层时。
- **执行流程**：
  1. 先确认网卡 DMA 写入的 Ring Buffer、驱动/NAPI poll 和硬中断/软中断的 CPU 分布；高包速率时检查是否由 NAPI 合并处理而非逐包中断。
  2. 沿 `Ring Buffer → sk_buff → 网络接口层 → IP/传输层 → 四元组匹配 Socket → Socket 接收缓冲区 → 应用 read/recv` 逐层定位计数器和时间点。
  3. 对照 `/proc/interrupts`、`/proc/softirqs`、网卡统计、Socket 队列和应用消费速率；累计值先做时间差，不能直接比较机器启动以来的绝对数。
  4. 根据最先出现的缺口决定调 Ring、NAPI budget/CPU 分布、协议栈/Socket 缓冲还是应用读取；最后用固定包速率和突发包速率复测。
- **V1 初判**：高。`2.6` 从硬中断上/下半部和 `NET_RX` 变化率给出软中断定位流程；附录网络包文档独立描述 DMA/Ring、NAPI、`sk_buff`、协议栈、Socket 和应用接收链。
- **V2 初判**：高。新问题：`NET_RX` 速率很高但网卡硬件 drop 为零、应用仍超时，推导应继续比较协议栈/Socket 队列和应用消费速度，不能以“没有 NIC drop”结束排查。
- **V3 初判**：高。它把“中断层的变化率”和“网络包的逐层生命周期”拼成证据链，边界明确区别于已有 TCP 传输丢包和 Socket 多路复用框架。

### G2-E04 网络数据复制预算与“零拷贝”真实性审计（补充候选/暂缓升格）

- **标题**：网络数据复制预算与“零拷贝”真实性审计。
- **适用问题**：选择 `mmap`/`write`、`sendfile`、`splice` 或普通 Socket 发送路径，大文件吞吐不达预期，或宣传中的“零拷贝”与 CPU/内存带宽实测不符时。
- **执行流程**：
  1. 画出发送或接收路径上的用户缓冲、页缓存/Socket 缓冲、`sk_buff`、驱动队列、DMA 和目标设备，标记每一段是否复制、映射、校验或仅转移所有权。
  2. 明确数据是否需要用户态修改、是否可直接从文件页缓存发送、目标网卡/文件系统是否支持相应 API，以及缓冲区何时可以复用。
  3. 分开测系统调用次数、CPU 时间、内存带宽、页缺失/缓存命中、端到端吞吐和尾延迟；不要以 API 名称推断拷贝次数。
  4. 在小文件、冷页缓存、大文件、拥塞链路和不同 MTU 下复测；若“少一次 CPU copy”被页缓存缺失或协议处理抵消，记录为不适用而非继续堆 API。
- **V1 初判**：中高。`9.1` 分别讲 DMA、传统文件传输、`mmap+write`/`sendfile` 和 PageCache；网络收发文档提供 Socket 缓冲、协议封装、DMA 发包与接收复制的另一条路径。
- **V2 初判**：中高。新问题：`sendfile` 在本地大文件有效但换成某类设备后吞吐下降，推导需回到目标设备/文件系统是否支持页缓存到 DMA 的直接路径，并检查是否重新发生用户态或内核态复制。
- **V3 初判**：高。把“零拷贝”拆成逐段可核验的复制预算，区别于只按 API 背诵性能结论；因不同内核、文件系统和网卡差异较大，暂缓独立升格。

### G2-E05 Reactor/Proactor 与多 Reactor 并发模型选择（补充候选/暂缓升格）

- **标题**：按“就绪/完成”语义和工作负载选择 Reactor、Proactor 与多 Reactor 拓扑。
- **适用问题**：设计高并发 TCP 服务、决定单 Reactor/线程池/多 Reactor，或出现事件已返回但 `read` 仍短读、业务处理阻塞事件线程、主 Reactor 成为瓶颈时。
- **执行流程**：
  1. 先写清平台通知的是“现在可以进行 I/O”（readiness）还是“异步操作已完成”（completion），并列出连接、读写、错误和关闭事件。
  2. 若用 Reactor，把监听/分发、accept、读写、业务处理和发送分别建模；为非阻塞短 I/O、半包和错误处理保留状态，而不是把一次事件当成完整消息。
  3. 按业务处理耗时、CPU 核数、突发连接数和共享状态选择单 Reactor 单线程、单 Reactor 多线程或 Main/Sub Reactor；若选择 Proactor，验证平台是否真有完成通知及其缓冲区生命周期。
  4. 压测连接建立、慢客户端、长业务和突发事件，分别观察事件线程占用、处理池排队、跨线程转发和尾延迟；最后与 framing/fd 合同分开验收。
- **V1 初判**：高。`9.2` 给出 select/poll/epoll 的就绪通知前提；`9.3` 从单 Reactor、多线程、多 Reactor 到 Proactor 分别说明职责、瓶颈和适用场景。
- **V2 初判**：高。新问题：事件循环频繁收到可读事件但业务延迟随慢请求升高，推导应把业务计算移出 Reactor，并在连接归属和结果回传上选择处理池/子 Reactor；不是简单提高 epoll 轮询频率。
- **V3 初判**：中。核心语义与既有 Socket 多路复用 Skill 交集明显，保留为并发架构决策补充，不单独升格，除非压力测试能证明模型选择边界稳定。

### G2-E06 PCI 拓扑—配置空间—BAR/桥窗口—驱动可见性审计

- **标题**：PCI 拓扑—配置空间—BAR/桥窗口—驱动可见性的资源审计。
- **适用问题**：`lspci` 能看到设备但驱动无法 probe、BAR 映射失败、桥后的设备资源冲突、设备在某平台可用而换平台失效，以及需要解释 PCI 总线初始化为何必须先画拓扑再分配资源时。
- **执行流程**：
  1. 从总线树而不是平面设备列表开始，记录 root bus、PCI-PCI bridge、bus number 和设备的配置空间身份信息。
  2. 读取 BAR 所需 I/O/内存窗口和对齐要求，先做资源探测，再检查设备地址是否被放进上游桥窗口；桥不是透明延长线，还会过滤地址范围。
  3. 把“设备被枚举”“资源分配成功”“驱动匹配”“驱动能访问寄存器”分成四个证据节点，分别核对配置空间、资源表、匹配 ID 和 `ioremap`/访问结果。
  4. 比较平台固件预留、地址空间大小和桥窗口差异；修改资源前先保留启动日志、配置空间和资源树，避免把规划地址误当成硬件现状。
- **V1 初判**：高。PCI 文档独立覆盖树形拓扑、配置空间、BAR、桥总线号、资源分配和桥窗口；ARM Linux 架构文档提供硬件到内核驱动的另一层交接背景。
- **V2 初判**：高。新问题：设备枚举正常、驱动 ID 也匹配但访问 BAR 返回错误，推导先查 BAR 资源是否落在桥窗口、内核是否建立映射，再查协议寄存器，而不是只重装驱动。
- **V3 初判**：高。它把容易被混为一谈的“发现、分配、可达、驱动访问”拆成拓扑资源合同，明显区别于通用设备树/驱动 probe 排障。

### G2-L01 CMake 源码树—构建树—目标依赖—运行时加载分离（补充候选）

- **标题**：CMake 源码树—构建树—目标依赖—运行时加载分离。
- **适用问题**：新增文件未进入目标、子目录库链接关系混乱、静态库能链接而共享库启动失败、源码目录残留缓存导致“改了配置却不生效”时。
- **执行流程**：
  1. 用独立 source/build 目录配置，记录生成器、缓存、工具链和首个配置错误；不要从源码目录残留的 `CMakeCache.txt` 推断当前配置。
  2. 先画 `add_subdirectory` 和 target 依赖图，再为每个 target 设置源文件、include、compile definition 和 `PRIVATE/PUBLIC/INTERFACE` 链接属性。
  3. 对源文件发现明确选择显式列表或 `GLOB`；若使用 `GLOB`，验证新增文件是否触发重新配置，不能因一次构建成功就认定文件已编译。
  4. 把链接期库搜索、生成物目录、运行期 RPATH/RUNPATH/加载器缓存和部署目录分开验证；做一次 clean configure/build/install/run 的闭环。
- **V1 初判**：高。CMake 上篇分别覆盖源文件搜索、静态/动态库、include 和链接；下篇用嵌套目录和 `add_subdirectory` 组织多个 target，支撑源码树到构建树的迁移。
- **V2 初判**：高。新问题：把新 `.cpp` 放进 `src/` 后构建成功但符号仍不存在，推导先查 target 源文件列表/GLOB 重新配置，再查链接；若程序只在开发机启动，则继续查 RPATH/RUNPATH，而不是重复改 C++ 代码。
- **V3 初判**：中高。与已有构建—加载—运行链有交集，独特边界是 CMake target/父子目录/增量配置合同；暂作为补充候选。

### G2-L02 文件元数据感知的递归遍历框架

- **标题**：文件元数据感知的递归遍历框架。
- **适用问题**：递归扫描漏文件、把符号链接目标误当成链接本身、`readdir()` 的 `NULL` 被误判为正常结束、网络文件系统返回 `DT_UNKNOWN`、权限变化导致遍历中途失败时。
- **执行流程**：

  2. `opendir` 后循环 `readdir`，跳过 `.`/`..`；读到 `NULL` 时先清/检查 `errno`，区分 EOF 与错误。
  3. `d_type` 不是可靠的完整合同；遇到 `DT_UNKNOWN` 或需精确元数据时，用 `stat`/`lstat` 回退，记录类型、inode、权限和时间字段。

### G2-M01 事件—状态—趋势三联诊断：从 fallback 到碎片成因

- **标题**：事件—状态—趋势三联诊断：从 fallback 到碎片成因。

  1. 先写问题的观测单位：要的是稳定的语义事件、某个内部决策尝试、函数返回值，还是一次完整上层请求的成功/失败。
  2. 语义事件优先选择字段稳定的 tracepoint；需要内部参数/路径才用 kprobe，并核对符号、内联、原型、结构体布局和架构参数传递；需要结果则配 kretprobe/fexit 或等价返回观测。
  3. 用线程/CPU/请求 ID 或成对状态关联入口与返回，处理 slowpath 重试、嵌套、重入和其他系统分配；明确不能从入口快照推断的字段。
  4. 版本升级和异常计数时先做探针自检与小流量对照，输出“入口次数、尝试次数、上层请求数、成功结果数”各自的单位，避免直接比较。
- **V1 初判**：中高。3.4.1/3.4.2 展示 tracepoint/kprobe 与 Map 采集的不同职责；4.2.3 明确 `get_page_from_freelist` 可能在 fast/slow path 多次进入、入口探针看不到返回结果且内部布局兼容性差。
- **V2 初判**：高。新问题：kprobe 每秒进入 10 万次而上层只发起 6 万次分配，推导不一定是统计错；同一次请求可能经历回收/规整后的多次尝试，且还可能包含其他请求，需改变计数单位或建立关联 ID。
- **V3 初判**：高。它以“问题单位→探针类型→可见字段→关联限制”做选择，反直觉地拒绝把函数入口次数当业务事件；适合独立审计，但需要后续补当前内核版本实验。
