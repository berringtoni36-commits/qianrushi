# 反例／矛盾／失败模式候选 Round 2

> 状态：全局候选池，不是最终 Skill。证据路径均指向原始 vault 中的文档、源码或明确的构建/资产文件；`V1` 表示来源事实是否直接可核验，`V2` 表示能否从规则推导新的失败症状，`V3` 表示相对现有 Skill 是否有稳定、独立的边界。评分是初判。

## embedded-core：网络、OS 与覆盖边界

### EC-01 UART 与 RS232 被放进了错误的层级

- **反例／矛盾**：同一篇材料先说 UART 是集成在 MCU 中的硬件模块、不是协议，随后又说“UART 是协议层、RS232 是物理层”。UART 的异步帧/控制器语义、RS232 的电气接口和更上层的应用协议不能直接套成两个 OSI 层。
- **证据路径**：`projects/嵌入式八股/3. 杂七杂八/1.【图解】5种总线协议：UART、RS232、RS485、I²C、SPI.md:126-132,267-280`。
- **风险**：面试或设计时可能把 TTL UART、RS232 收发器和应用帧格式混为一谈，导致电平不匹配、接口选型错误，或误以为换了 RS232 就改变了数据帧协议。
- **修复建议**：将表述拆成“UART 外设/异步串行帧机制—收发器/电气标准—应用层帧格式”三层；示例必须注明 MCU 引脚电平、是否经过 MAX3232 等收发器，以及应用协议的长度/校验字段。
- **V1/V2/V3 初判**：高 / 高 / 高。

### EC-02 TCP 的可靠字节传输被绝对化为应用消息可靠送达

- **反例／矛盾**：材料把传输层总结为“保证数据正确、顺序到达对应应用”，但另一份 TCP 教程明确说明 TCP 是字节流，多个发送包可能合并或拆分；TCP ACK 只说明字节已被协议栈确认，不等于应用消息已解析、执行业务或落盘。
- **证据路径**：`projects/嵌入式八股/糯叽叽八股/05 计算机网络.md:166-192`；`archive/大丙Linux教程/第4章 套接字通信/05 TCP数据粘包的处理.md:30-36,138-155`。
- **风险**：接收端一次 `read/recv` 就当成一个完整包，或把 `send()` 返回成功当成业务成功，产生短读、粘包、重复处理和持久化丢失等故障；回答中还会夸大 TCP 的责任边界。
- **修复建议**：分别写清 TCP 的字节序列保证、应用层 framing、业务确认和持久化确认；实现长度前缀/分隔符协议，循环处理短读短写，并在业务层定义超时、重试和幂等语义。
- **V1/V2/V3 初判**：高 / 高 / 中高。

### EC-03 `mmap` 被直接等同于“零拷贝”

- **反例／矛盾**：OS 八股把“将内核缓冲区映射到用户空间”直接标成“实现零拷贝”，驱动八股又把 `mmap` 描述成用户直接访问内核内存。映射只改变访问方式，具体数据路径仍可能有 DMA、页缓存、内核内部复制、缺页和同步成本。
- **证据路径**：`projects/嵌入式八股/糯叽叽八股/04 操作系统.md:191-203`；`projects/嵌入式八股/糯叽叽八股/10 嵌入式Linux驱动.md:283-293`。
- **风险**：在没有核对缓冲区所有权、缓存一致性、写回和生命周期的情况下宣称“零拷贝”，可能造成数据竞争、DMA 缓存错读，甚至把吞吐宣传数字当成实测结论。
- **修复建议**：对每个方案画出用户态、内核缓冲、页缓存、设备 DMA 和目标消费者之间的复制/映射边界；补充同步、缓存属性、缓冲区回收和端到端 benchmark，而不是只按 API 名称分类。
- **V1/V2/V3 初判**：高 / 高 / 中高。

### EC-04 Cortex-M、ARM Linux 与 x86 系统调用机制被混成一条链

- **反例／矛盾**：OS 文档先用 x86 的 `int 0x80/syscall` 解释用户态到内核态，又在嵌入式 Linux 应用文档中把“ARM Cortex-M/Linux”并列写成使用 SVC。Cortex-M 裸机通常没有 Linux 用户态/内核态和进程系统调用这一层，ARM Linux 也应按实际 AArch32/AArch64 ABI 说明。
- **证据路径**：`projects/嵌入式八股/糯叽叽八股/04 操作系统.md:12-33`；`projects/嵌入式八股/糯叽叽八股/09 嵌入式Linux应用.md:89-104`。
- **风险**：学习者会把 MCU 异常入口、Linux syscall、CPU 特权级和 C 库封装当成同一个机制；面试时无法说明目标 CPU、启动模式和实际执行环境。
- **修复建议**：按“Cortex-M 裸机/RTOS、ARM Linux 用户态、x86 Linux”分栏，分别写异常向量、SVC/syscall ABI、用户/内核权限和返回路径；任何工程结论都标注目标架构和 OS。
- **V1/V2/V3 初判**：高 / 高 / 中高。

### EC-05 中断上下文“不可被高优先级打断”与“支持中断嵌套”互相冲突

- **反例／矛盾**：同一节先断言中断上下文不可重入、任何高优先级中断都必须等当前 ISR 完成，后面又承认某些系统允许高优先级中断嵌套。不可重入、屏蔽策略、抢占嵌套和 ISR 是否可安全重入不是同一个判断。
- **证据路径**：`projects/嵌入式八股/糯叽叽八股/04 操作系统.md:995-1004,1035-1037`。
- **风险**：可能在 Cortex-M/NVIC 或 Linux IRQ 设计中错误设置屏蔽优先级，或者在 ISR 中使用非重入共享资源；也会把“不能阻塞”误推成“不能发生嵌套”。
- **修复建议**：分别说明硬件是否允许嵌套、当前屏蔽位/优先级配置、ISR 是否可重入和共享数据如何保护；不要用“中断上下文不可重入”替代具体平台的验证。
- **V1/V2/V3 初判**：高 / 高 / 中高。

### EC-06 `embedded-core` 的索引覆盖不能被说成网络/OS 全覆盖

- **反例／矛盾**：域索引明确表示小林图解、C/OS/网络/STM32 章节中仍有大量 `indexed-only`，但根目录资料量、索引页或面试题集合很容易被误读成“已经形成完整规范 Skill”；教程示例也不能自动变成个人项目事实。
- **证据路径**：`distillation/embedded-core/INDEX.md:59-63`；`distillation/coverage-gaps.md:3,11-15`；`projects/嵌入式八股/糯叽叽八股/10 嵌入式Linux驱动.md:1-10`。
- **风险**：候选筛选会把未精确回链的资料当作已审计依据，面试回答会把通用教程代码说成自己完成的完整驱动/系统工程，后续 Skill 也会超出证据边界。
- **修复建议**：对每条结论记录 `source / indexed-only / evidence-layer / derived` 状态；只有存在源码、工程配置、运行日志或明确参与边界时才使用“项目实现”，否则写“教程示例/学习材料”。
- **V1/V2/V3 初判**：高 / 高 / 高。

## RTOS 项目

### RT-01 IAP 默认关闭，却被主程序注释说成双区架构

- **反例／矛盾**：`ifopen=0` 时 IAP 的 DMA 初始化、IAP 任务和 DMA ISR 均被条件编译排除；主程序注释仍把固件更新描述成“boot+app 双区架构”。文档标题虽写 Boot + 单 APP，但单 APP 也不等于 A/B 双槽。
- **证据路径**：`projects/RTOS项目/源码/SYSTEM/sys/sys.h:19-34`；`projects/RTOS项目/源码/USER/main.c:5-14,75-81`；`projects/RTOS项目/源码/APP_TASK/app_tasks.c:576-684`；`projects/RTOS项目/文档/5 系统功能实现/5.3 固件升级（IAP）：Boot + 单APP分区与串口DMA传输.md:1-20`。
- **风险**：把未编译、未验证的可选路径说成默认功能，把单 APP 擦写规划说成带回滚的双镜像升级，导致面试夸大和量产安全误判。
- **修复建议**：在文档和回答中明确“当前默认构建关闭 IAP；设计是 Boot + 单 APP 规划”；若需要 A/B，补充两个独立链接地址、版本选择、启动确认、断电恢复和回滚测试。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-02 IAP 校验失败或写入中断没有事务性回滚

- **反例／矛盾**：CRC 失败分支会清空接收缓冲、重新启 DMA 并擦除 `FLASH_APP1_ADDR`；CRC 成功后也先擦除 APP 区再写入。代码中没有备份槽、版本选择、写入完成标志或断电回滚路径。
- **证据路径**：`projects/RTOS项目/源码/APP_TASK/app_tasks.c:592-605,612-636`；`projects/RTOS项目/源码/BSP/IAP/iap.c:42-60`。
- **风险**：升级失败可能留下不可启动的 APP；“CRC 通过”只能说明传输数据完整，不能证明写入过程、向量表和下次启动安全。
- **修复建议**：采用暂存/备用槽或外部恢复策略，按块写入并记录状态、版本和最终确认；启动时验证镜像长度、向量表范围、完整性和回滚条件。把 CRC 明确为完整性检测，不称为签名或防篡改。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-03 IAP 接收合同固定且缺少奇数长度边界

- **反例／矛盾**：DMA 以 `buff_size` 固定接收，长度只由 DMA 剩余计数推导，没有可审计的帧头、最大长度、序号、超时和分块确认；写 Flash 时每次取两个字节，`appsize` 为奇数时仍读取 `dfu[1]`。
- **证据路径**：`projects/RTOS项目/源码/BSP/DMA/dma.c:20-39,54-67`；`projects/RTOS项目/源码/BSP/IAP/iap.c:19-40`；`projects/RTOS项目/源码/SYSTEM/sys/sys.h:29-33`。
- **风险**：短包、超长包、串口噪声或奇数长度固件可能越界读、错误拼接或把未接收数据写入 Flash；固定缓冲区也无法证明文件传输的完整生命周期。
- **修复建议**：定义长度/序号/CRC/结束标记和超时的帧协议，分块接收并校验边界；对奇数尾字节显式补 `0xFF` 或拒绝，并用 PC 与 MCU 的已知向量/长度测试覆盖短包、满包和断帧。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-04 1 ms 二值信号量通知与“50 ms 测速”语义不一致

- **反例／矛盾**：TIM4 每 1 ms 给一次二值信号量，`SpeedCalcTask` 却按 `get_speed(encoderCount, 50)` 的注释计算“50ms 一次”。二值信号量只能表示“至少有一个事件”，任务未及时消费时多个 tick 会合并。
- **证据路径**：`projects/RTOS项目/源码/APP_TASK/app_tasks.c:182-185,783-797,825-837`。
- **风险**：测速时间窗、计数差分和 PID 输入的实际周期与注释不符；系统负载升高时事件合并会使速度抖动、丢采样或控制周期漂移。
- **修复建议**：让硬件中断周期、采样窗口和算法参数使用同一可测合同；需要每个 tick 时用计数通知/队列并处理 overrun，需要固定周期时直接按周期触发并记录时间戳。用示波器、计数器或日志校准实际周期。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-05 `g_dataMutex` 没有覆盖完整的共享状态访问

- **反例／矛盾**：文档把全局状态描述为由单一互斥量保护，但 `MotorControlTask` 在释放锁后直接读改 `currentMode`、`motorRunning` 等字段，UI 和 `AntiBackflowTask` 也直接读写 `g_systemState`；`System_GetState()` 直接返回全局指针。
- **证据路径**：`projects/RTOS项目/文档/2 系统架构与设计/2.4 任务间通信：互斥信号量与全局状态管理.md:15,50,80-102,134-150`；`projects/RTOS项目/源码/APP_TASK/app_tasks.c:340-369,480-518,525-566,775-778`。
- **风险**：互斥量只保护了部分字段，读—改—写仍可能与其他任务交错；UI 可能读到不一致快照，模式切换可能覆盖传感器或控制任务的新值。
- **修复建议**：定义状态所有权和原子事务；在锁内复制完整快照、计算后用版本或命令提交，避免把可写全局指针暴露给任务；用 ThreadSanitizer（可移植模型）、故障注入或运行时断言验证访问合同。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-06 动态任务创建失败与栈溢出在配置中被关闭

- **反例／矛盾**：工程启用动态分配、堆只有 10 KB，多个 `xTaskCreate()` 的返回值未检查；同时 `configCHECK_FOR_STACK_OVERFLOW=0`、`configUSE_MALLOC_FAILED_HOOK=0`。因此“任务已创建/系统能自动发现栈问题”不能从源码推出。
- **证据路径**：`projects/RTOS项目/源码/APP_TASK/app_tasks.c:136-180`；`projects/RTOS项目/源码/FreeRTOS/include/FreeRTOSConfig.h:109-121`。
- **风险**：内存不足时任务可能静默缺失，栈越界可能破坏相邻对象后才表现为随机 HardFault；调试日志无法区分创建失败、栈耗尽和业务死锁。
- **修复建议**：检查每个创建/信号量返回值，启用并实现 malloc failed hook、栈溢出 hook、`configASSERT` 和 high-water-mark 记录；在启动日志中输出剩余堆和每任务栈余量。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-07 MQ2 的“0–500 浓度”是注释边界，不是校准后的物理量

- **反例／矛盾**：函数注释写返回范围 0–500，但公式结果没有限幅；初始化明确“不在此处等待预热”，代码没有 Ro 标定、曲线来源和 ppm 精度测试。文档已承认该值更像控制量而非绝对 ppm。
- **证据路径**：`projects/RTOS项目/源码/BSP/MQ2/mq2.c:54-55,80-110`；`projects/RTOS项目/文档/4 硬件驱动开发/4.2 传感器与采集/4.2.2 MQ2 气体传感器：ADC采集与数据处理.md:15-29`。
- **风险**：阈值状态机可能因未预热、供电/负载变化或公式奇异值误触发；面试中把经验映射说成精确浓度测量属于夸大。
- **修复建议**：命名为校准前控制指标，记录 ADC 饱和/零值边界；按传感器数据手册完成预热、Ro 标定、气体类别曲线和温湿度补偿，再给出误差范围。若业务只需阈值，直接验证阈值重复性而非宣称 ppm 精度。
- **V1/V2/V3 初判**：高 / 高 / 高。

### RT-08 CRC 查找表“修正五处”与证据内容自相矛盾

- **反例／矛盾**：源码注释和文档称索引 42、43、143、206、207 有错误并已修正，但文档示例中索引 42、43 的原值和修正值相同，并写着“实际为正确值，但需验证”；“与 zlib 完全一致”的结论没有附测试向量或构建日志。
- **证据路径**：`projects/RTOS项目/源码/BSP/CRC32/crc32.c:11-19`；`projects/RTOS项目/文档/5 系统功能实现/5.4 CRC32校验：数据完整性验证机制.md:160-179`。
- **风险**：错误表可能被当作已修复的安全边界；PC 与 MCU 在初始值、反射、最终异或或长度字段上的差异会导致升级拒绝或误接受。
- **修复建议**：从明确多项式/初值/反射/终值重新生成表，提交固定空串、`123456789`、固件片段等跨语言测试向量；报告测试命令和哈希，不用“CRC 完整”替代真实性认证。
- **V1/V2/V3 初判**：高 / 高 / 中高。

## Linux memory / eBPF

### MEM-01 `last_time_map` 用变化的当前时间作 key，节流永远难以命中

- **反例／矛盾**：`fraginfo.c` 和 `extfraginfo.c` 都用本次 `bpf_ktime_get_ns()` 作为 lookup key；`fraginfo.c` 最后也用同一个变化值 update，事件程序甚至没有 update。设计文档却把它解释成“固定保存上次采样时间”。
- **证据路径**：`projects/Linux物理内存检测项目/源码/fraginfo.c:43-46,91-105,166-167`；`projects/Linux物理内存检测项目/源码/extfraginfo.c:16-31`；`projects/Linux物理内存检测项目/文档/3 深入理解/3.5 用户态展示与优化/3.5.2 性能优化与采样控制.md:79-83,96-104`。
- **风险**：高频 kprobe 可能持续执行完整 zone/order 扫描，map 还可能积累大量近似唯一的时间戳；“interval=2 秒、低开销监控”的描述不能作为运行事实。
- **修复建议**：使用固定 key 的 array/hash 或明确 per-CPU key，先读取旧时间、在接受采样后更新；定义并发竞争和 map 容量，再用高频 workload 对触发次数、CPU 开销和丢样本做 benchmark。
- **V1/V2/V3 初判**：高 / 高 / 高。

### MEM-02 zone/order 数据在用户态被覆盖，节点数又硬编码为 11 阶

- **反例／矛盾**：`get_view_data()` 以 `(node_id, comm)` 为 key，遍历同一 zone 的不同 order 时只保留最后一条；`get_node_data()` 再把记录数固定除以 11。内核端的 `MAX_ORDER`、缺失 map update 或不同内核布局都可能改变记录数量。
- **证据路径**：`projects/Linux物理内存检测项目/源码/exfrag.py:64-86,109-124`；`projects/Linux物理内存检测项目/源码/fraginfo.c:6,147-164`；`projects/Linux物理内存检测项目/项目完整代码流程详解.md:571-597`。
- **风险**：视图进度条丢阶数，节点 zone 数被误算；监控输出看似完整但实际是覆盖后的快照，跨内核版本还可能出现系统性计数错误。
